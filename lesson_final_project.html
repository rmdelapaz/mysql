🏗️ Lesson 8.2: Final Project: Design and Build a Database

Until now the bookstore was handed to you. This time you start from a client's description and an empty server, and you finish with a database someone could actually run: designed, built with constraints, filled with test data, answering real questions, protected by its own accounts and backed up. The client is the Maple Street Tool Library, a volunteer-run library that lends drills and ladders instead of books.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Turn a written brief into entities, relationships and business rules, and draw them as a diagram
  • Build a normalized schema in a re-runnable script, with keys, foreign keys and CHECK constraints that you have tested
  • Answer business questions with joins, GROUP BY, CTEs and window functions, using a fixed report date
  • Enforce rules that span several rows in a stored procedure with a transaction
  • Secure the database with roles and least-privilege accounts, then back it up and prove the backup restores

📋 The Brief

Rosa Delgado coordinates the Maple Street Tool Library, a neighborhood project that lends tools to its members. Today everything lives in a shared spreadsheet, and it is falling apart: two people borrowed the same ladder on the same day, nobody knows who has the drill, and a member who never took the chainsaw course went home with the chainsaw. She wrote down what she needs:

📝 What the library needs (in Rosa's words)

  1. "We have members: name, email (one account per email), the date they joined, and whether they are active or suspended."
  2. "We own about a dozen tools. Each has a name, one category (hand tools, power tools, garden...), a condition (good, fair, or out for repair), what it would cost to replace, and the date we got it."
  3. "Some tools need a safety course first: power tools need Power Tools Basics, the chainsaw needs Chainsaw Safety. We need to know which members finished which course, and when."
  4. "A loan is one tool to one member: the day it went out, the day it is due (normally a week later) and the day it came back."
  5. "Rules: a tool can only be out with one person at a time; nothing goes out while it is being repaired; suspended members cannot borrow; nobody may have more than three tools at once; and no course, no chainsaw."
  6. "Every Saturday I need: what is on the shelf, what is overdue and whose email to write to, which tools are popular, and how busy each month was."
  7. "The volunteers at the desk check tools out and in through our little web form. Our treasurer only reads reports. Nobody should be able to delete the loan history."
  8. "If the laptop dies, I do not want to start over."

What you hand in

  • 01_schema.sql: creates the database and every table, and can be run again from scratch
  • 02_data.sql: realistic test data that exercises every rule
  • 03_queries.sql: Rosa's Saturday questions, one commented query each
  • 04_logic.sql: a view and the check-out and return procedures
  • 05_security.sql: roles and accounts
  • A tested backup file and README.md: a one-page write-up of your design, how to rebuild it and what you would do next

💡 How to use this lesson

Each milestone in the project section describes what to build, then hides a complete reference solution that has been run on MySQL 9.7. Do the milestone yourself first, then open the reference and compare. Your solution does not have to match it: different names and designs can be just as good. What matters is that yours meets the rubric and you can explain your choices. Prefer another business? The FAQ has an alternative brief for a small clinic.

🧩 From Requirements to Tables

A reliable way to get from prose to a schema, the same one you used in Lesson 6.3:

  1. Underline the nouns. Things with their own facts become tables (member, tool, category, safety course, loan). Facts about a thing become columns (a member's email, a tool's condition).
  2. Read the verbs for relationships and ask "one or many?" in both directions. A category has many tools, a tool has one category: one-to-many, the foreign key goes in tools. A member can finish many courses and a course is finished by many members: many-to-many, so it needs a junction table, which here carries its own fact (the completion date).
  3. Sort the rules by where they can live. A rule about one value goes in the column type or a constraint (NOT NULL, UNIQUE, ENUM, CHECK). A rule between tables is a foreign key. A rule that needs to look at other rows ("only one open loan per tool", "at most three per member") cannot be a CHECK; it goes in the procedure that creates loans, inside a transaction.
  4. Leave out what can be calculated. "Overdue" and "days late" depend on today's date and the loan's dates, so they are computed in queries, not stored. Whether a tool is "available" is computed from open loans.

Starter schema checklist

Before you write any SQL, your design notes should answer each of these. They are also what the rubric looks for.

  • Every table has a primary key; a junction table's key is the pair of foreign keys
  • Every foreign key is named, has the same type as the column it points to, and has a deliberate ON DELETE rule (or none, meaning "refuse")
  • Required facts are NOT NULL; values that must be unique (email, category name) have UNIQUE
  • Closed lists of values use ENUM or a lookup table, and you can say why you chose which
  • Money is DECIMAL, dates are DATE, text that is searched or joined on has a sensible VARCHAR length
  • At least two CHECK constraints for single-row rules (dates in order, positive amounts)
  • Indexes on the columns your Saturday queries filter and join on
  • No derived data (no stored "is overdue" or "times borrowed" columns)
  • Names are snake_case, tables plural, no reserved words

⚠️ Common Mistakes

These are the problems that cost the most time in projects like this one. The demos use a scratch database so nothing collides with your project:

CREATE DATABASE pitfall_demo;
USE pitfall_demo;

1. A column named after a reserved word

CREATE TABLE demo_tools (
    id        INT AUTO_INCREMENT PRIMARY KEY,
    condition VARCHAR(10)
);

Error

ERROR 1064 (42000): You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near 'condition VARCHAR(10)
)' at line 3

What it means: CONDITION is a reserved word in MySQL (it is used in stored programs), so the parser stops right there. order, group, rank and key cause the same error. Fix: choose a clearer name, such as tool_condition. Backticks would also work, but then every query forever needs them.

2. A foreign key whose type does not match

CREATE TABLE demo_tools (id INT AUTO_INCREMENT PRIMARY KEY, name VARCHAR(50));
CREATE TABLE demo_loans (
    id      INT AUTO_INCREMENT PRIMARY KEY,
    tool_id BIGINT NOT NULL,
    FOREIGN KEY (tool_id) REFERENCES demo_tools (id)
);

Error

ERROR 3780 (HY000): Referencing column 'tool_id' and referenced column 'id' in foreign key constraint 'demo_loans_ibfk_1' are incompatible.

What it means: a foreign key and the key it points to must have the same type (and the same signedness: INT and INT UNSIGNED clash too). Fix: make tool_id an INT. Decide on one key type at the start and use it everywhere.

3. A CHECK constraint that uses today's date

CREATE TABLE demo_loans (
    id     INT AUTO_INCREMENT PRIMARY KEY,
    due_on DATE NOT NULL,
    CONSTRAINT chk_due_future CHECK (due_on >= CURDATE())
);

Error

ERROR 3814 (HY000): An expression of a check constraint 'chk_due_future' contains disallowed function: curdate.

What it means: a CHECK must give the same answer for a row forever. "Due in the future" is true today and false next week, so MySQL refuses functions like CURDATE() and NOW() in constraints. Fix: compare columns of the same row (due_on >= loaned_on), and put time-dependent rules in the procedure that creates the row.

4. Creating a child table before its parent

CREATE TABLE demo_courses_done (
    member_id INT NOT NULL,
    FOREIGN KEY (member_id) REFERENCES demo_members (id)
);

Error

ERROR 1824 (HY000): Failed to open the referenced table 'demo_members'

What it means: demo_members does not exist yet. Fix: order CREATE TABLE statements parents first (lookup tables, then the tables that point at them, junction and history tables last), and drop them in the reverse order.

🐬 Version note: MariaDB's messages

MariaDB refuses the same mistakes with different errors: a mismatched or missing foreign-key target gives ERROR 1005 (HY000): Can't create table ... (errno: 150 "Foreign key constraint is incorrectly formed") for both mistakes 2 and 4, CURDATE() in a CHECK gives error 1901, and a violated CHECK gives error 4025 instead of 3819. The fixes are the same.

5. A LEFT JOIN quietly turned into an inner join (silent)

"How many loans did each member start in June?" Members with none should show 0.

CREATE TABLE demo_members (id INT PRIMARY KEY, name VARCHAR(50));
CREATE TABLE demo_member_loans (member_id INT, loaned_on DATE);
INSERT INTO demo_members VALUES (1, 'Rosa'), (2, 'Kevin'), (3, 'Tessa');
INSERT INTO demo_member_loans VALUES (1, '2026-06-06'), (2, '2026-05-02');

SELECT m.name, COUNT(l.member_id) AS june_loans
FROM demo_members AS m
LEFT JOIN demo_member_loans AS l ON l.member_id = m.id
WHERE l.loaned_on >= '2026-06-01'
GROUP BY m.id, m.name
ORDER BY m.name;

Output

+------+------------+
| name | june_loans |
+------+------------+
| Rosa |          1 |
+------+------------+

What it means: no error, but Kevin and Tessa have vanished. WHERE runs after the join, and for Tessa l.loaned_on is NULL, which fails the test; Kevin's only loan is from May. The LEFT in the join no longer does anything. Fix: move conditions on the right-hand table into ON:

SELECT m.name, COUNT(l.member_id) AS june_loans
FROM demo_members AS m
LEFT JOIN demo_member_loans AS l
       ON l.member_id = m.id AND l.loaned_on >= '2026-06-01'
GROUP BY m.id, m.name
ORDER BY m.name;

DROP DATABASE pitfall_demo;

Output

+-------+------------+
| name  | june_loans |
+-------+------------+
| Kevin |          0 |
| Rosa  |          1 |
| Tessa |          0 |
+-------+------------+

⚠️ Three more traps that do not raise an error

  • Reports that use CURDATE() give different answers every day, so you cannot check them. Set a report date once (SET @today = '2026-06-15';) and use it everywhere; the real report just sets it to CURDATE().
  • Checking a rule, then inserting, without a lock. Two desk volunteers can both see "drill available" and both lend it. The procedure in Milestone 5 locks the tool's row with SELECT ... FOR UPDATE inside a transaction, so the second check-out waits and then sees the first one.
  • Test data that only covers the happy path. If no loan is overdue and every member has borrowed something, a broken overdue query and a broken "never borrowed" query both look fine.

🛠️ Project: The Maple Street Tool Library

Eight milestones, about 240 minutes in total. Keep each milestone's SQL in its own numbered file in a tool-library folder, and run the files with SOURCE as you go. Start the client from inside that folder (cd ~/mysql-course/tool-library, then mysql -u root -p): SOURCE resolves file names from the folder the client was started in, so when 02_data.sql runs SOURCE 01_schema.sql from anywhere else you get Failed to open file '01_schema.sql', error: 2.

🛠️ Milestone 1: Design (30 min)

On paper or in a text file: list the tables with their columns, types and keys; draw the relationships (a sketch like the diagram above is enough); and write each of Rosa's eight requirements next to the place your design enforces or answers it. No SQL yet.

🔒 Reference design (try it yourself first)

1-4 the factsColumns, NOT NULL, UNIQUE, ENUMs, foreign keys

Why an ENUM for condition and status but a table for categories? The library will add categories (and wants to list them), while the conditions and statuses are fixed by the code that uses them. Both choices are defensible; writing down the reason is what counts.

🛠️ Milestone 2: Build the schema (40 min)

Write 01_schema.sql. It should start with DROP DATABASE IF EXISTS tool_library; so it can be rerun, create the tables parents first, name every constraint, and add indexes for the open-loan lookups. Then prove the constraints: write one statement that each constraint must reject.

🔒 Reference solution: 01_schema.sql 
DROP DATABASE IF EXISTS tool_library;
CREATE DATABASE tool_library CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
USE tool_library;

CREATE TABLE members (
    id         INT AUTO_INCREMENT PRIMARY KEY,
    first_name VARCHAR(50)  NOT NULL,
    last_name  VARCHAR(50)  NOT NULL,
    email      VARCHAR(100) NOT NULL,
    joined_on  DATE         NOT NULL,
    status     ENUM('active', 'suspended') NOT NULL DEFAULT 'active',
    CONSTRAINT uq_members_email UNIQUE (email)
);

CREATE TABLE categories (
    id   INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    CONSTRAINT uq_categories_name UNIQUE (name)
);

CREATE TABLE safety_courses (
    id   INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(80) NOT NULL,
    CONSTRAINT uq_courses_name UNIQUE (name)
);

CREATE TABLE tools (
    id                 INT AUTO_INCREMENT PRIMARY KEY,
    name               VARCHAR(100)  NOT NULL,
    category_id        INT           NOT NULL,
    required_course_id INT           NULL,
    tool_condition     ENUM('good', 'fair', 'repair') NOT NULL DEFAULT 'good',
    replacement_value  DECIMAL(8, 2) NOT NULL,
    acquired_on        DATE          NOT NULL,
    CONSTRAINT fk_tools_category FOREIGN KEY (category_id) REFERENCES categories (id),
    CONSTRAINT fk_tools_course   FOREIGN KEY (required_course_id) REFERENCES safety_courses (id),
    CONSTRAINT chk_tools_value   CHECK (replacement_value > 0)
);

CREATE TABLE member_courses (
    member_id    INT  NOT NULL,
    course_id    INT  NOT NULL,
    completed_on DATE NOT NULL,
    PRIMARY KEY (member_id, course_id),
    CONSTRAINT fk_mc_member FOREIGN KEY (member_id) REFERENCES members (id) ON DELETE CASCADE,
    CONSTRAINT fk_mc_course FOREIGN KEY (course_id) REFERENCES safety_courses (id)
);

CREATE TABLE loans (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    tool_id     INT  NOT NULL,
    member_id   INT  NOT NULL,
    loaned_on   DATE NOT NULL,
    due_on      DATE NOT NULL,
    returned_on DATE NULL,
    CONSTRAINT fk_loans_tool      FOREIGN KEY (tool_id)   REFERENCES tools (id),
    CONSTRAINT fk_loans_member    FOREIGN KEY (member_id) REFERENCES members (id),
    CONSTRAINT chk_loans_due      CHECK (due_on >= loaned_on),
    CONSTRAINT chk_loans_returned CHECK (returned_on IS NULL OR returned_on >= loaned_on),
    INDEX idx_loans_tool_open   (tool_id, returned_on),
    INDEX idx_loans_member_open (member_id, returned_on)
);

SHOW TABLES;

The loan foreign keys have no ON DELETE rule, which means "refuse": a member or tool with loan history cannot be deleted, which is requirement 7 at the database level. Members are suspended instead. A member's course records, on the other hand, mean nothing without the member, so they cascade.

Now the constraint tests. Run them inside a transaction and roll it back at the end, so the test rows never stay in the database. The parents need one row each first:

INSERT INTO tools (name, category_id, replacement_value, acquired_on)

ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`tool_library`.`tools`, CONSTRAINT `fk_tools_category` FOREIGN KEY (`category_id`) REFERENCES `categories` (`id`))

Output

+--------------+
| members_left |
+--------------+
|            0 |
+--------------+

Four rules, four rejections, each naming the constraint that fired. That is what "proven" means in the rubric. A failed statement inside a transaction only undoes itself, so the transaction stayed open until ROLLBACK removed the test rows. (CREATE TABLE cannot be rolled back, which is why the tests come after the schema.)

CREATE VIEW v_open_loans AS
SELECT l.id AS loan_id, t.id AS tool_id, t.name AS tool,
       CONCAT(m.first_name, ' ', m.last_name) AS member,
       l.loaned_on, l.due_on
FROM loans AS l
JOIN tools   AS t ON t.id = l.tool_id
JOIN members AS m ON m.id = l.member_id
WHERE l.returned_on IS NULL;

DELIMITER //

CREATE PROCEDURE checkout_tool(IN p_member_id INT, IN p_tool_id INT, IN p_loan_date DATE)
BEGIN
    DECLARE v_status    VARCHAR(10);
    DECLARE v_condition VARCHAR(10);
    DECLARE v_course    INT;
    DECLARE v_open      INT;
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        RESIGNAL;
    END;

    SET p_loan_date = COALESCE(p_loan_date, CURDATE());

    START TRANSACTION;

    SELECT status INTO v_status FROM members WHERE id = p_member_id;
    IF v_status IS NULL THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'No such member';
    ELSEIF v_status <> 'active' THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Member is suspended';
    END IF;

    -- lock the tool's row: a second check-out of the same tool waits here
    SELECT tool_condition, required_course_id INTO v_condition, v_course
    FROM tools WHERE id = p_tool_id FOR UPDATE;
    IF v_condition IS NULL THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'No such tool';
    ELSEIF v_condition = 'repair' THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Tool is out for repair';
    END IF;

    IF EXISTS (SELECT 1 FROM loans WHERE tool_id = p_tool_id AND returned_on IS NULL) THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Tool is already on loan';
    END IF;

    IF v_course IS NOT NULL AND NOT EXISTS (
        SELECT 1 FROM member_courses WHERE member_id = p_member_id AND course_id = v_course) THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Safety course required for this tool';
    END IF;

    SELECT COUNT(*) INTO v_open FROM loans WHERE member_id = p_member_id AND returned_on IS NULL;
    IF v_open >= 3 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Loan limit reached (3 open loans)';
    END IF;

    INSERT INTO loans (tool_id, member_id, loaned_on, due_on)
    VALUES (p_tool_id, p_member_id, p_loan_date, p_loan_date + INTERVAL 7 DAY);

    COMMIT;

    SELECT LAST_INSERT_ID() AS loan_id, p_loan_date + INTERVAL 7 DAY AS due_on;
END //

CREATE PROCEDURE return_tool(IN p_tool_id INT, IN p_return_date DATE)
BEGIN
    UPDATE loans
    SET returned_on = COALESCE(p_return_date, CURDATE())
    WHERE tool_id = p_tool_id AND returned_on IS NULL;

    IF ROW_COUNT() = 0 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Tool is not on loan';
    END IF;
END //

DELIMITER ;

🏋️ Exercise 4 (Stretch): One Open Loan per Tool, Guaranteed

The procedure enforces "one borrower at a time", but an administrator typing an INSERT by hand could still break it. Make the database itself refuse a second open loan for the same tool. A normal UNIQUE (tool_id) will not do, since a tool has many returned loans.

💡 Hint

Add a generated column that equals tool_id while the loan is open and NULL once it is returned, and make that column UNIQUE. A unique index allows any number of NULLs.

    ADD COLUMN open_tool_id INT
        GENERATED ALWAYS AS (IF(returned_on IS NULL, tool_id, NULL)) STORED,

❓ Common Questions at This Stage

Can I build a different business instead?

Yes, as long as it has at least five tables, a many-to-many relationship, a rule that spans rows and two kinds of users. A ready-made alternative: a small physiotherapy clinic. Patients, therapists, treatment types (each with a price and length), and appointments (patient, therapist, treatment, start time, status). Rules: a therapist cannot be booked twice at the same start time (a UNIQUE (therapist_id, starts_at) covers exact clashes; overlapping lengths need a procedure), cancelled appointments stay in the history, and front-desk staff book while therapists only read their own schedule. Keep all patient data fictional.

My design is different from the reference. Is it wrong?

Not necessarily. A lookup table instead of an ENUM, a loan_status column, separate first and last names or one name column: all can be fine. Check yours against the rubric and the starter checklist. It is wrong only if it stores something twice, loses a fact, or cannot enforce a rule from the brief.

Why not store "available" as a column on tools?

Because it would duplicate what the open loans already say, and the two would eventually disagree (a return recorded, the flag not reset). Derive it. If a query ever gets slow, an index on loans (tool_id, returned_on), which the schema has, fixes that long before denormalizing would be needed.

Should this go on GitHub?

Yes: the numbered scripts and the README make a good portfolio piece. Commit the scripts with placeholder passwords only, never a backup file of real data, and never the .mylogin.cnf file.

📝 Lesson Summary

🎓 Key Takeaways

  • Design first: nouns become tables, verbs become relationships, and every rule gets a home before any SQL is written
  • Single-row rules go in types and constraints; rules across rows go in a procedure with a transaction and a row lock
  • Build scripts must be re-runnable, ordered parents first, and every constraint deserves a test that it rejects bad data
  • Test data is a design tool: plant the edge cases that would expose a wrong query
  • Reports use a fixed report date so they can be checked; production sets it to today
  • Applications get their own least-privilege accounts through roles, and a database is only safe once its backup has been restored

🌱 Encouragement for the Journey

This is the moment the course has been building toward: you started from a few paragraphs of a client's worries and ended with a database that protects her data, answers her questions and survives a dead laptop. Real projects are exactly this, just with more tables. If parts of it took longer than planned or needed the reference, that is normal; designing is a skill that grows with every project, and you have just done a complete one.
