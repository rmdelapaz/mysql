🔀 Lesson 4.3: Joins

You split the bookstore into related tables and made MySQL guard the links. Now comes the payoff: reading across them in one query. "Show every order with the customer's name and the books in it" and "which authors have never sold a copy?" are joins. This is the most used, and most interviewed-about, skill in SQL.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Combine matching rows from two or more tables with INNER JOIN ... ON, using table aliases
  • Keep unmatched rows with LEFT JOIN, and find rows with no match using the anti-join pattern
  • Explain what RIGHT JOIN and CROSS JOIN return, and when (rarely) to use them
  • Join a table to itself to read a hierarchy such as employees and managers
  • Combine joins with GROUP BY without the two silent traps: COUNT(*) on outer joins and row fan-out
  • ⏱️ Time 110 minutes
  • 📋 Prerequisites Lesson 4.2: Foreign Keys & Referential Integrity
  • 🛠️ You will build sales_report.sql, a six-part sales and staff report built from joins
  • 🗄️ Database a fresh bookstore from bookstore.sql (load it first: see below)

🧲 What a Join Does

An order row says customer_id = 1. The name "Alice" lives in customers. A join pairs each row of one table with the rows of another table that satisfy a condition, usually "this foreign key equals that primary key", and returns the pairs as one wider row.

graph TD O["order 1: customer_id 1"] --> R["order 1 + Alice"] C["customer 1: Alice"] --> R

In Lessons 4.1 and 4.2 you looked up related rows one at a time with subqueries. A join does it for every row at once, and lets you show columns from both tables side by side.

💡 Start from a fresh copy

Load the course database so your results match the ones shown (on Windows, write the path with forward slashes):

SOURCE ~/mysql-course/bookstore.sql

It holds 10 authors, 11 books, 8 customers, 12 orders with 18 order lines, and 10 employees. A few rows have no partner on the other side, on purpose: Isaac Asimov has no books, Carol and Hank never ordered, and The Great Gatsby and The Catcher in the Rye never sold. Watch what each kind of join does with them.

🤝 INNER JOIN: Only the Matches

An INNER JOIN returns one row for every pair of rows that satisfies the ON condition. A row with no partner does not appear at all.

SELECT columns
FROM left_table
INNER JOIN right_table ON left_table.column = right_table.column;

Books with their authors

SELECT books.title, authors.name AS author
FROM books
INNER JOIN authors ON books.author_id = authors.id
ORDER BY books.title;

Output

+------------------------+---------------------+
| title                  | author              |
+------------------------+---------------------+
| 1984                   | George Orwell       |
| Animal Farm            | George Orwell       |
| Brave New World        | Aldous Huxley       |
| Dune                   | Frank Herbert       |
| Fahrenheit 451         | Ray Bradbury        |
| Lord of the Rings      | J.R.R. Tolkien      |
| Pride and Prejudice    | Jane Austen         |
| The Catcher in the Rye | J.D. Salinger       |
| The Great Gatsby       | F. Scott Fitzgerald |
| The Hobbit             | J.R.R. Tolkien      |
| To Kill a Mockingbird  | Harper Lee          |
+------------------------+---------------------+

Eleven books, eleven rows. Orwell and Tolkien appear twice, once per book. Isaac Asimov does not appear at all: no book row pairs with him, and an inner join keeps only pairs.

Table aliases

Writing books. and authors. everywhere gets long. Give each table a short alias after its name and use the alias instead:

SELECT b.title, b.price, a.name AS author
FROM books AS b
JOIN authors AS a ON b.author_id = a.id
WHERE a.name = 'George Orwell'
ORDER BY b.title;

Output

+-------------+-------+---------------+
| title       | price | author        |
+-------------+-------+---------------+
| 1984        |  9.99 | George Orwell |
| Animal Farm |  8.49 | George Orwell |
+-------------+-------+---------------+

Three things to notice. JOIN on its own means INNER JOIN; most people write the short form. AS before a table alias is optional (FROM books b works too). And WHERE filters the joined rows just as it filters a single table: ON says how the tables connect, WHERE says which results you want.

💡 Alias habits

Use the first letter (b for books, a for authors, c, o) and two letters when they clash (oi for order_items, bc for book_categories). Once a table has an alias, use only the alias in that query (Mistake 2).

⬅️ LEFT JOIN: Keep Every Left Row

A LEFT JOIN (also written LEFT OUTER JOIN) returns every pair an inner join would, plus each row of the left table (the one before the word JOIN) that found no partner. For those rows, the right table's columns are NULL.

graph TD A["each row of the LEFT table"] --> B{"matches on the right?"} B -->|"yes"| C["one row per match"] B -->|"no"| D["one row, right columns NULL"]

Every author, books or not

SELECT a.name AS author, b.title
FROM authors AS a
LEFT JOIN books AS b ON b.author_id = a.id
ORDER BY a.id, b.title;

Output

+---------------------+------------------------+
| author              | title                  |
+---------------------+------------------------+
| Frank Herbert       | Dune                   |
| George Orwell       | 1984                   |
| George Orwell       | Animal Farm            |
| Harper Lee          | To Kill a Mockingbird  |
| F. Scott Fitzgerald | The Great Gatsby       |
| Jane Austen         | Pride and Prejudice    |
| J.R.R. Tolkien      | Lord of the Rings      |
| J.R.R. Tolkien      | The Hobbit             |
| Aldous Huxley       | Brave New World        |
| J.D. Salinger       | The Catcher in the Rye |
| Ray Bradbury        | Fahrenheit 451         |
| Isaac Asimov        | NULL                   |
+---------------------+------------------------+

Twelve rows: the eleven matches, plus Isaac Asimov with NULL for the title. Same tables, same ON, one more row, and the only difference is the word LEFT.

Every customer, orders or not

SELECT c.first_name, o.id AS order_id, o.order_date
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
ORDER BY c.id, o.order_date;

Output

+------------+----------+------------+
| first_name | order_id | order_date |
+------------+----------+------------+
| Alice      |        1 | 2026-01-15 |

| Carol      |     NULL | NULL       |
| Dave       |        4 | 2026-01-22 |

| Frank      |       10 | 2026-05-02 |
| Grace      |        6 | 2026-02-14 |
| Grace      |       11 | 2026-05-19 |

Alice appears three times (three orders), Carol and Hank once each with NULLs. Twelve orders plus two customers without one: 14 rows.

The anti-join: rows with no match

The NULLs are not just a side effect, they are a tool. Keep only the rows where the right side is missing, and you have answered "which X has no Y?":

SELECT c.first_name, c.last_name
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
WHERE o.id IS NULL
ORDER BY c.id;

Output

+------------+-----------+
| first_name | last_name |
+------------+-----------+
| Carol      | Williams  |
| Hank       | Taylor    |
+------------+-----------+
SELECT b.title
FROM books AS b
LEFT JOIN order_items AS oi ON oi.book_id = b.id
WHERE oi.id IS NULL
ORDER BY b.title;

Output

+------------------------+
| title                  |
+------------------------+
| The Catcher in the Rye |
| The Great Gatsby       |
+------------------------+

🔑 The anti-join pattern

LEFT JOIN right ... WHERE right.id IS NULL finds every left row with no partner: customers who never ordered, books never sold, authors without books. Test the right table's primary key (or any NOT NULL column): it can only be NULL when there was no match. NOT EXISTS from Lesson 3.4 answers the same question, and MySQL runs both efficiently; use whichever reads more clearly to you.

↔️ RIGHT JOIN and CROSS JOIN

RIGHT JOIN: the mirror image

A RIGHT JOIN keeps every row of the right table. These two queries return the same rows:

SELECT a.name AS author, b.title
FROM books AS b
RIGHT JOIN authors AS a ON b.author_id = a.id
WHERE b.id IS NULL;

SELECT a.name AS author, b.title
FROM authors AS a
LEFT JOIN books AS b ON b.author_id = a.id
WHERE b.id IS NULL;

Output

+--------------+-------+
| author       | title |
+--------------+-------+
| Isaac Asimov | NULL  |
+--------------+-------+
+--------------+-------+
| author       | title |
+--------------+-------+
| Isaac Asimov | NULL  |
+--------------+-------+

Any RIGHT JOIN can be rewritten as a LEFT JOIN by swapping the tables, and most teams always do, so that "the table I want all of" is always the first one. Recognize RIGHT JOIN when you read it; write LEFT JOIN.

💡 What about FULL OUTER JOIN?

Some databases have a FULL OUTER JOIN that keeps unmatched rows from both sides. MySQL and MariaDB do not. When you need it, combine a LEFT JOIN and a RIGHT JOIN with UNION, which stacks two results and removes duplicate rows.

CROSS JOIN: every combination

A CROSS JOIN has no condition: it pairs every row on the left with every row on the right (the Cartesian product). The marketing team wants one mailing per category for each Chicago customer:

SELECT c.first_name, cat.name AS category
FROM customers AS c
CROSS JOIN categories AS cat
WHERE c.city = 'Chicago'
ORDER BY c.first_name, cat.name;

Output

+------------+-----------------+
| first_name | category        |
+------------+-----------------+
| Bob        | Classic         |
| Bob        | Dystopian       |
| Bob        | Fantasy         |
| Bob        | Fiction         |
| Bob        | Science Fiction |
| Grace      | Classic         |
| Grace      | Dystopian       |
| Grace      | Fantasy         |
| Grace      | Fiction         |
| Grace      | Science Fiction |
+------------+-----------------+

Two customers × five categories = 10 rows. Useful for grids and schedules (every size with every color, every employee with every training module), and dangerous on big tables: two tables of 10,000 rows each make 100 million rows.

⚠️ A JOIN without ON is a CROSS JOIN in MySQL

Forget the ON clause and MySQL does not complain: FROM books JOIN authors quietly returns all 11 × 10 = 110 combinations. If a join returns far more rows than you expected, check the ON first.

SELECT COUNT(*) AS rows_returned
FROM books
JOIN authors;

Output

+---------------+
| rows_returned |
+---------------+
|           110 |
+---------------+

🪞 Self-Joins: A Table and Itself

employees.manager_id points at another row of employees. To show each employee next to their manager, join the table to itself, with two aliases playing two roles: e for the employee and m for the manager.

SELECT
    CONCAT(e.first_name, ' ', e.last_name) AS employee,
    e.department,
    CONCAT(m.first_name, ' ', m.last_name) AS manager
FROM employees AS e
LEFT JOIN employees AS m ON e.manager_id = m.id
ORDER BY e.id;

Output

+---------------+------------+--------------+
| employee      | department | manager      |
+---------------+------------+--------------+
| Maria Santos  | management | NULL         |
| Daniel Reyes  | management | Maria Santos |
| Priya Nair    | sales      | Daniel Reyes |
| Tom Becker    | sales      | Priya Nair   |
| Lena Park     | sales      | Priya Nair   |
| Marcus Hill   | inventory  | Daniel Reyes |
| Sofia Alvarez | inventory  | Marcus Hill  |
| James Okafor  | support    | Maria Santos |
| Nina Kowalski | support    | James Okafor |
| Ben Carter    | sales      | Priya Nair   |
+---------------+------------+--------------+

Maria Santos has no manager, so she survives only because this is a LEFT JOIN; an inner join would drop the head of the company. CONCAT with a NULL argument returns NULL, which is why her manager column says NULL rather than a space.

💡 Aliases are required here

With the same table twice, employees.first_name would be ambiguous: whose first name? The aliases are what make a self-join possible. A self-join reads one level of a hierarchy; to walk the whole tree (Maria to Daniel to Priya to Tom), Lesson 5.1 uses a recursive CTE.

Pairs within one table

Which books share an author? Join books to itself on the author, and keep each pair once:

SELECT b1.title AS book_1, b2.title AS book_2, a.name AS author
FROM books AS b1
JOIN books AS b2 ON b1.author_id = b2.author_id AND b1.id < b2.id
JOIN authors AS a ON a.id = b1.author_id
ORDER BY a.name;

Output

+------------+-------------------+----------------+
| book_1     | book_2            | author         |
+------------+-------------------+----------------+
| 1984       | Animal Farm       | George Orwell  |
| The Hobbit | Lord of the Rings | J.R.R. Tolkien |
+------------+-------------------+----------------+

b1.id < b2.id does two jobs: it stops a book from pairing with itself (1984 with 1984) and keeps only one of the two mirror pairs (1984 + Animal Farm, not also Animal Farm + 1984). An ON clause may hold any condition, not only an equality.

⛓️ Joining Three or More Tables

Each extra JOIN adds one more table to the row you are building. To see who bought what, walk the foreign keys from orders outward:

graph TD O["orders"] -->|"customer_id"| C["customers"] O -->|"order_id"| OI["order_items"] OI -->|"book_id"| B["books"] B -->|"author_id"| A["authors"] 
SELECT o.id AS order_id, o.order_date, c.first_name,
       b.title, oi.quantity, oi.price_at_time
FROM orders AS o
JOIN customers AS c    ON o.customer_id = c.id
JOIN order_items AS oi ON oi.order_id = o.id
JOIN books AS b        ON oi.book_id = b.id
WHERE c.first_name = 'Alice'
ORDER BY o.order_date, b.title;

Output

+----------+------------+------------+---------------------+----------+---------------+
| order_id | order_date | first_name | title               | quantity | price_at_time |
+----------+------------+------------+---------------------+----------+---------------+
|        1 | 2026-01-15 | Alice      | 1984                |        2 |          9.99 |
|        1 | 2026-01-15 | Alice      | Dune                |        1 |         14.99 |
|        2 | 2026-02-20 | Alice      | Pride and Prejudice |        1 |          7.99 |
|        8 | 2026-04-05 | Alice      | Lord of the Rings   |        1 |         15.99 |
+----------+------------+------------+---------------------+----------+---------------+

Alice's three orders hold four lines. Order 1 appears twice because it has two lines: in the joined result there is one row per order line, not per order. Keep that in mind; it matters as soon as you add things up.

Five tables: who reads Orwell?

SELECT DISTINCT c.first_name, c.last_name
FROM customers AS c
JOIN orders AS o       ON o.customer_id = c.id
JOIN order_items AS oi ON oi.order_id = o.id
JOIN books AS b        ON oi.book_id = b.id
JOIN authors AS a      ON b.author_id = a.id
WHERE a.name = 'George Orwell'
ORDER BY c.last_name;

Output

+------------+-----------+
| first_name | last_name |
+------------+-----------+
| Dave       | Brown     |
| Alice      | Johnson   |
| Bob        | Smith     |
| Grace      | Wilson    |
+------------+-----------+

Without DISTINCT, a customer who bought Orwell twice (Bob bought both his books in one order) would be listed twice. The chain reads like a sentence: customers who placed orders that contain items that are books written by Orwell.

📊 Joins with GROUP BY

Joins and the aggregates from Lesson 3.3 together answer most business questions. Join first, then group the joined rows.

Books per author, including zero

SELECT a.name AS author, COUNT(b.id) AS books
FROM authors AS a
LEFT JOIN books AS b ON b.author_id = a.id
GROUP BY a.id, a.name
ORDER BY books DESC, author;

Output

+---------------------+-------+
| author              | books |
+---------------------+-------+
| George Orwell       |     2 |
| J.R.R. Tolkien      |     2 |
| Aldous Huxley       |     1 |
| F. Scott Fitzgerald |     1 |
| Frank Herbert       |     1 |
| Harper Lee          |     1 |
| J.D. Salinger       |     1 |
| Jane Austen         |     1 |
| Ray Bradbury        |     1 |
| Isaac Asimov        |     0 |
+---------------------+-------+

COUNT(b.id) counts the non-NULL book ids, so Asimov's padded row counts as 0. COUNT(*) would count that row and give him 1 (Mistake 4). Grouping by a.id as well as a.name keeps two authors who share a name apart.

What each customer spent

SELECT
    CONCAT(c.first_name, ' ', c.last_name)        AS customer,
    COUNT(DISTINCT o.id)                           AS orders,
    COALESCE(SUM(oi.quantity), 0)                  AS books_bought,
    COALESCE(SUM(oi.quantity * oi.price_at_time), 0) AS spent
FROM customers AS c
LEFT JOIN orders AS o       ON o.customer_id = c.id
LEFT JOIN order_items AS oi ON oi.order_id = o.id
GROUP BY c.id, c.first_name, c.last_name
ORDER BY spent DESC, customer;

Output

+----------------+--------+--------------+-------+
| customer       | orders | books_bought | spent |
+----------------+--------+--------------+-------+
| Alice Johnson  |      3 |            5 | 58.95 |
| Dave Brown     |      2 |            4 | 45.96 |
| Frank Miller   |      2 |            4 | 41.96 |
| Grace Wilson   |      2 |            3 | 33.97 |
| Bob Smith      |      2 |            3 | 33.47 |
| Eve Davis      |      1 |            2 | 22.98 |
| Carol Williams |      0 |            0 |  0.00 |
| Hank Taylor    |      0 |            0 |  0.00 |
+----------------+--------+--------------+-------+

Three details make this right. Both joins are LEFT, so Carol and Hank stay in the list. COUNT(DISTINCT o.id) counts orders, not order lines (Alice has 3 orders but 4 lines). And COALESCE(..., 0) turns their NULL sums into 0.

💡 oi.price_at_time or b.price?

Revenue should use what customers actually paid, order_items.price_at_time. In the course data no price has changed since the orders were placed, so b.price gives the same totals today; it would silently drift the day the store changes a price. It also saves a join.

Revenue per author, with HAVING

SELECT a.name AS author,
       SUM(oi.quantity)                    AS copies_sold,
       SUM(oi.quantity * oi.price_at_time) AS revenue
FROM authors AS a
JOIN books AS b        ON b.author_id = a.id
JOIN order_items AS oi ON oi.book_id = b.id
GROUP BY a.id, a.name
HAVING revenue > 30
ORDER BY revenue DESC;

Output

+----------------+-------------+---------+
| author         | copies_sold | revenue |
+----------------+-------------+---------+
| J.R.R. Tolkien |           5 |   64.95 |
| George Orwell  |           6 |   56.94 |
| Frank Herbert  |           3 |   44.97 |
+----------------+-------------+---------+

Inner joins are right here: an author with no sales has no revenue to report, and HAVING would drop them anyway. The same clauses as in Lesson 3.3, in the same order; the FROM part is just bigger.

⚠️ Common Mistakes

1. A column name that exists in both tables

SELECT id, title, name
FROM books
JOIN authors ON books.author_id = authors.id;

Error

ERROR 1052 (23000): Column 'id' in field list is ambiguous

What it means: both tables have an id, and MySQL will not guess which one you mean. title and name are fine: each exists in only one table. Fix: qualify it, books.id or b.id. Many developers qualify every column in a join, which also tells the next reader where each one comes from.

2. Using the table name after giving it an alias

SELECT books.title, a.name
FROM books AS b
JOIN authors AS a ON b.author_id = a.id;

Error

ERROR 1054 (42S22): Unknown column 'books.title' in 'field list'

What it means: once you write books AS b, the table is called b in this query and books.title refers to nothing. Fix: b.title.

3. Filtering the right table in WHERE after a LEFT JOIN (silent)

The goal: every customer, with their orders from May onward, if any.

SELECT c.first_name, o.order_date
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
WHERE o.order_date >= '2026-05-01'
ORDER BY c.first_name;

Output

+------------+------------+
| first_name | order_date |
+------------+------------+
| Dave       | 2026-06-07 |
| Frank      | 2026-05-02 |
| Grace      | 2026-05-19 |
+------------+------------+

What it means: no error, but "every customer" became three. WHERE runs after the join, and for customers without a May order o.order_date is NULL, which fails the test: the LEFT JOIN has quietly turned into an inner join. Fix: put conditions on the right table in the ON clause, so they decide which orders match without removing any customer:

SELECT c.first_name, o.order_date
FROM customers AS c
LEFT JOIN orders AS o
       ON o.customer_id = c.id
      AND o.order_date >= '2026-05-01'
ORDER BY c.first_name;

Output

+------------+------------+
| first_name | order_date |
+------------+------------+
| Alice      | NULL       |
| Bob        | NULL       |
| Carol      | NULL       |
| Dave       | 2026-06-07 |
| Eve        | NULL       |
| Frank      | 2026-05-02 |
| Grace      | 2026-05-19 |
| Hank       | NULL       |
+------------+------------+

4. COUNT(*) after a LEFT JOIN (silent)

SELECT a.name, COUNT(*) AS books
FROM authors AS a
LEFT JOIN books AS b ON b.author_id = a.id
WHERE a.id IN (2, 10)
GROUP BY a.id, a.name
ORDER BY a.id;

Output

+---------------+-------+
| name          | books |
+---------------+-------+
| George Orwell |     2 |
| Isaac Asimov  |     1 |
+---------------+-------+

What it means: Asimov has no books, yet the count says 1. COUNT(*) counts rows, and the left join gave him one row, padded with NULLs. Fix: count a column of the right table, COUNT(b.id), which skips NULL.

5. Counting after the rows have multiplied (silent)

Books per author and copies sold, in one query:

SELECT a.name, COUNT(b.id) AS books, SUM(oi.quantity) AS copies_sold
FROM authors AS a
JOIN books AS b        ON b.author_id = a.id
JOIN order_items AS oi ON oi.book_id = b.id
WHERE a.id IN (2, 6)
GROUP BY a.id, a.name
ORDER BY a.id;

Output

+----------------+-------+-------------+
| name           | books | copies_sold |
+----------------+-------+-------------+
| George Orwell  |     5 |           6 |
| J.R.R. Tolkien |     4 |           5 |
+----------------+-------+-------------+

What it means: Orwell wrote two books, not five. Joining order_items produced one row per order line, so each book was repeated once per line that sold it ("fan-out"), and COUNT(b.id) counted the repeats. The copies are right, the book count is not. Fix: COUNT(DISTINCT b.id). More generally, before you aggregate, ask "what does one row of this join stand for?" Here it is one order line, not one book.

🛠️ Project: The Sales Report

The owner liked the inventory report from Lesson 3.3; now she wants the sales side. Build sales_report.sql in your mysql-course folder, one query per step, running each as you add it. Allow about 35 minutes.

🛠️ Step 1: One line per order (7 min)

Start the file with USE bookstore;. Show every order with the customer's name, the number of books in it and its total. Group by the order: one result row per order, whatever the number of lines.

USE bookstore;

-- 1. Orders
SELECT
    o.id                                   AS order_id,
    o.order_date,
    CONCAT(c.first_name, ' ', c.last_name) AS customer,
    SUM(oi.quantity)                       AS books,
    SUM(oi.quantity * oi.price_at_time)    AS total
FROM orders AS o
JOIN customers AS c    ON o.customer_id = c.id
JOIN order_items AS oi ON oi.order_id = o.id
GROUP BY o.id, o.order_date, c.first_name, c.last_name
ORDER BY o.order_date;

Output

Database changed
+----------+------------+---------------+-------+-------+
| order_id | order_date | customer      | books | total |
+----------+------------+---------------+-------+-------+
|        1 | 2026-01-15 | Alice Johnson |     3 | 34.97 |
|        4 | 2026-01-22 | Dave Brown    |     2 | 26.98 |
|        5 | 2026-02-03 | Frank Miller  |     2 | 19.98 |

🛠️ Step 2: Revenue by month (5 min)

DATE_FORMAT(o.order_date, '%Y-%m') turns a date into a year-month label such as 2026-01, which sorts correctly as text.

-- 2. Revenue by month
SELECT
    DATE_FORMAT(o.order_date, '%Y-%m')  AS month,
    COUNT(DISTINCT o.id)                AS orders,
    SUM(oi.quantity * oi.price_at_time) AS revenue
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.id
GROUP BY month
ORDER BY month;

🛠️ Step 5: Sales by category (5 min)

Every category, with the copies sold of its books. A book in two categories counts in both, so the column does not add up to the total sold, and the report should say so.

🏋️ Exercise 2: Never Sold, by Author

List the books that have never been ordered together with their authors, and then list the authors who have never sold a single copy (including those with no books at all).

💡 Hint

The first is an anti-join from books to order_items, plus an inner join to authors. For the second, start from authors and LEFT JOIN both books and order_items; an author never sold if no order line matched.

✅ Solution 
SELECT b.title, a.name AS author
FROM books AS b
JOIN authors AS a           ON b.author_id = a.id
LEFT JOIN order_items AS oi ON oi.book_id = b.id
WHERE oi.id IS NULL
ORDER BY b.title;

SELECT a.name AS author
FROM authors AS a
LEFT JOIN books AS b        ON b.author_id = a.id
LEFT JOIN order_items AS oi ON oi.book_id = b.id
GROUP BY a.id, a.name
HAVING COUNT(oi.id) = 0
ORDER BY author;

Output

+------------------------+---------------------+
| title                  | author              |
+------------------------+---------------------+
| The Catcher in the Rye | J.D. Salinger       |
| The Great Gatsby       | F. Scott Fitzgerald |
+------------------------+---------------------+
+---------------------+
| author              |
+---------------------+
| F. Scott Fitzgerald |
| Isaac Asimov        |
| J.D. Salinger       |
+---------------------+

The second query groups per author and keeps those with zero matching order lines. A plain WHERE oi.id IS NULL would not work for an author with one sold and one unsold book: they would appear because of the unsold one.

🏋️ Exercise 3: Category Sizes

Show every category with the number of books in it and the average price of those books (rounded to cents), largest category first.

💡 Hint

Join categories to book_categories to books. Count b.id, and use ROUND(AVG(b.price), 2).

✅ Solution 
SELECT cat.name AS category,
       COUNT(b.id)            AS books,
       ROUND(AVG(b.price), 2) AS avg_price
FROM categories AS cat
LEFT JOIN book_categories AS bc ON bc.category_id = cat.id
LEFT JOIN books AS b            ON bc.book_id = b.id
GROUP BY cat.id, cat.name
ORDER BY books DESC, category;

Output

+-----------------+-------+-----------+
| category        | books | avg_price |
+-----------------+-------+-----------+
| Fiction         |    11 |     10.76 |
| Classic         |     6 |      9.41 |
| Dystopian       |     3 |      9.99 |
| Science Fiction |     3 |     11.66 |
| Fantasy         |     2 |     13.49 |
+-----------------+-------+-----------+

❓ Common Questions at This Stage

Does the order of the tables matter?

For INNER JOIN, no: books JOIN authors and authors JOIN books return the same rows, and MySQL's optimizer picks its own order anyway. For LEFT JOIN, yes, completely: the left table is the one whose rows are all kept.

I have seen FROM books, authors WHERE books.author_id = authors.id. Is that a join?

Yes, the old comma style: the comma is a cross join and WHERE filters it down to the matches. It returns the same rows as an inner join, but it cannot express outer joins, and forgetting the WHERE line gives a silent cross join. Write explicit JOIN ... ON.

What is USING?

A shortcut when both columns have the same name: JOIN order_items USING (order_id) means ON a.order_id = b.order_id. The bookstore's keys are named customer_id on one side and id on the other, so ON is the form you will use here.

Are joins slow? Should I avoid them?

No. Joining on foreign keys is what relational databases are built for, and the index on each foreign key column makes it fast. Slow joins usually come from joining on columns without an index, or from accidental cross joins. Lesson 6.1 shows how to check with EXPLAIN.

📝 Lesson Summary

🎓 Key Takeaways

  • JOIN ... ON (inner) returns one row per matching pair; rows without a partner disappear
  • LEFT JOIN keeps every row of the left table and fills the right side with NULL when nothing matches
  • Anti-join: LEFT JOIN ... WHERE right.id IS NULL finds rows with no match
  • Conditions on the right table of a LEFT JOIN go in ON; in WHERE they turn it into an inner join
  • RIGHT JOIN mirrors LEFT JOIN; CROSS JOIN (or a join without ON) returns every combination
  • A self-join uses two aliases for one table: employee and manager
  • Know what one joined row stands for before aggregating: use COUNT(right.id), COUNT(DISTINCT ...) and COALESCE where needed
