⚡ Lesson 6.1: Indexes & Query Optimization

Your queries return the right answers. Are they fast? With 11 books every query feels instant, but a table with a few hundred thousand rows can turn a lookup into a noticeable wait if MySQL has to read every row to find a handful. Indexes are the main tool for making lookups fast, and EXPLAIN is how you check that MySQL actually uses them.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Explain what an index is, what it costs, and which indexes every bookstore table already has
  • Read a query plan from EXPLAIN and measure a query with EXPLAIN ANALYZE
  • Create single-column, composite and unique indexes, and choose the column order of a composite index
  • Spot and rewrite the patterns that stop an index from being used: functions on the column, leading wildcards, type mismatches
  • List, rename, hide and drop indexes, and fix the errors MySQL raises while you do it

🐌 The Problem: Full Table Scans

Without an index, MySQL has exactly one way to answer WHERE sold_on = '2025-03-15': read every row of the table and test each one. That is a full table scan. On 11 rows nobody notices. On 100,000 rows it is measurable, and on 50 million rows it is the reason a web page takes ten seconds to load.

An index is the fix, and you already know how one works: the index at the back of a textbook. To find "foreign keys" you do not read the whole book. You look the term up in an alphabetical list and jump to the page numbers it gives you.

graph TD Q["WHERE sold_on = '2025-03-15'"] --> N["no index"] Q --> I["index on sold_on"] N --> S["read all 100,000 rows"] I --> J["jump to the 42 matches"]

This lesson works in three moves, and you will repeat them in the project: measure a query with EXPLAIN ANALYZE, index the column it searches, measure again to prove the index helped.

The bookstore tables are far too small to show what an index does. So you will generate a sales_log table: 100,000 rows of sales history, the kind of table a point-of-sale system fills up over a few years. Every value is calculated from a running number n with MOD (the remainder of a division), so your table holds exactly the same rows as the one used for this page.

CREATE TABLE sales_log (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    receipt_no  CHAR(7)     NOT NULL,
    customer_id INT         NOT NULL,
    book_id     INT         NOT NULL,
    sold_on     DATE        NOT NULL,
    quantity    INT         NOT NULL,
    channel     VARCHAR(10) NOT NULL
);

INSERT INTO sales_log (receipt_no, customer_id, book_id, sold_on, quantity, channel)
WITH digits AS (
    SELECT 0 AS d UNION ALL SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3 UNION ALL SELECT 4
    UNION ALL SELECT 5 UNION ALL SELECT 6 UNION ALL SELECT 7 UNION ALL SELECT 8 UNION ALL SELECT 9
),
seq AS (
    SELECT 1 + a.d + 10 * b.d + 100 * c.d + 1000 * e.d + 10000 * f.d AS n
    FROM digits a
    CROSS JOIN digits b CROSS JOIN digits c CROSS JOIN digits e CROSS JOIN digits f
)
SELECT
    LPAD(n, 7, '0'),                               -- receipt 0000001, 0000002, ...
    1 + MOD(n * 7, 8),                             -- customers 1 to 8
    1 + MOD(n * 13, 11),                           -- books 1 to 11
    DATE '2020-01-01' + INTERVAL MOD(n * 37, 2400) DAY,
    1 + MOD(n, 3),                                 -- 1 to 3 copies
    ELT(1 + MOD(n, 4), 'web', 'store', 'phone', 'web')
FROM seq
ORDER BY n;

ANALYZE TABLE sales_log;

Output

+---------------------+---------+----------+----------+
| Table               | Op      | Msg_type | Msg_text |
+---------------------+---------+----------+----------+
| bookstore.sales_log | analyze | status   | OK       |
+---------------------+---------+----------+----------+

Five copies of a ten-row digits list, cross joined (Lesson 4.3), make 10 × 10 × 10 × 10 × 10 = 100,000 numbers, and the CTE (Lesson 5.1) names each step. ANALYZE TABLE tells MySQL to refresh its statistics about the table (roughly how many rows, how many different values per index). The optimizer uses those statistics to plan queries, and they can lag behind after a big load like this one.

SELECT COUNT(*) AS sales, MIN(sold_on) AS first_sale, MAX(sold_on) AS last_sale
FROM sales_log;

Output

| sales  | first_sale | last_sale  |
+--------+------------+------------+
| 100000 | 2020-01-01 | 2026-07-27 |
+--------+------------+------------+

One hundred thousand sales over six and a half years. Run the same query and you should get exactly these numbers. This table stays until you reload bookstore.sql, which the next lesson does anyway.

🌳 What an Index Is

An index is a separate structure, stored next to the table, that holds the values of one or more columns in sorted order, each with a pointer back to its row. MySQL's InnoDB engine stores it as a B-tree: a shallow tree of sorted pages. To find a value, MySQL starts at the root and follows one branch per level, the way you would find a word in a dictionary by opening it near the right letter.

graph TD R["root: 2020 ... 2026"] --> L["2020-01 ... 2022-12"] R --> M["2023-01 ... 2026-07"] M --> P["page: 2025-03-14 ... 2025-03-16"] P --> X["42 rows for 2025-03-15"]

Because every level divides the search, a B-tree over a million values is only three or four levels deep. That is why an index lookup reads a few pages while a full scan reads all of them.

💡 The primary key is the table

InnoDB stores the rows themselves in a B-tree sorted by the primary key, called the clustered index. That is why WHERE id = 42 is always fast and why you never create an index on the primary key. Every other index (a secondary index) stores its column values plus the row's primary key, and MySQL uses that key to fetch the rest of the row.

Indexes are not free

  • Space: each index is a sorted copy of its columns, stored on disk and cached in memory.
  • Slower writes: every INSERT, every DELETE, and every UPDATE that changes an indexed column must update each affected index too.
  • Choices for the optimizer: more indexes means more plans to compare, and occasionally a worse pick.

The goal is not "index everything". It is "index the columns your important queries search, join and sort on".

🗂️ The Indexes You Already Have

The bookstore already has indexes you never created by name. information_schema.STATISTICS lists every index column of every table:

SELECT TABLE_NAME, INDEX_NAME, COLUMN_NAME, NON_UNIQUE
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = 'bookstore'
  AND TABLE_NAME IN ('books', 'customers', 'orders', 'order_items')
ORDER BY TABLE_NAME, INDEX_NAME, SEQ_IN_INDEX;

Output

+-------------+--------------------+-------------+------------+
| TABLE_NAME  | INDEX_NAME         | COLUMN_NAME | NON_UNIQUE |
+-------------+--------------------+-------------+------------+
| books       | fk_books_author    | author_id   |          1 |
| books       | PRIMARY            | id          |          0 |
| customers   | email              | email       |          0 |
| customers   | PRIMARY            | id          |          0 |
| order_items | fk_items_book      | book_id     |          1 |
| order_items | fk_items_order     | order_id    |          1 |

| orders      | fk_orders_customer | customer_id |          1 |
| orders      | PRIMARY            | id          |          0 |
+-------------+--------------------+-------------+------------+

Three sources, all automatic:

  • PRIMARY: every primary key is an index (the clustered index).
  • email: the UNIQUE constraint on customers.email is enforced by a unique index named after the column (NON_UNIQUE is 0).
  • fk_books_author, fk_orders_customer, ...: InnoDB needs an index on every foreign key column to check and cascade quickly, so it creates one, named after the constraint, when none exists. That is why joins on author_id or customer_id were already fast in Lesson 4.3.

The quick way to look at one table is SHOW INDEX. It prints more columns than you need today; the ones to read are Key_name, Seq_in_index, Column_name and Non_unique.

SHOW INDEX FROM orders;

Output (the Cardinality estimates can differ on your server)

+--------+------------+--------------------+--------------+-------------+-----------+-------------+----------+--------+------+------------+---------+---------------+---------+------------+

Cardinality is MySQL's estimate of how many different values the index holds. It comes from the statistics, so it can show 0 or a stale number until ANALYZE TABLE runs. Treat it as a hint, never as a count.

🔬 EXPLAIN: Reading the Plan

Before running a query, MySQL's optimizer chooses a plan: which table to read first, whether to use an index, how to sort. Put EXPLAIN in front of a SELECT and MySQL shows the plan instead of running the query. Ending the statement with \G instead of ; prints it vertically, which is much easier to read.

EXPLAIN SELECT * FROM sales_log WHERE sold_on = '2025-03-15'\G

Output (cost and row estimates differ from server to server)

*************************** 1. row ***************************
EXPLAIN: -> Filter: (sales_log.sold_on = DATE'2025-03-15')  (cost=10078 rows=9990)
    -> Table scan on sales_log  (cost=10078 rows=99900)

Read a plan from the most indented line up: that line runs first and feeds the line above it. Here MySQL will do a Table scan (read every row), then a Filter (keep the rows whose date matches). rows= is the optimizer's estimate of how many rows each step produces, and cost= is its internal score for the step: lower is cheaper. Both are estimates from statistics, which is why your numbers can differ a little.

EXPLAIN ANALYZE: run it and measure

EXPLAIN ANALYZE actually runs the query and adds what really happened to each step: the time in milliseconds to the first row and to the last row, the real number of rows, and how many times the step ran (loops).

EXPLAIN ANALYZE SELECT * FROM sales_log WHERE sold_on = '2025-03-15'\G

Output (your timings and estimates will differ)

*************************** 1. row ***************************
EXPLAIN: -> Filter: (sales_log.sold_on = DATE'2025-03-15')  (cost=10078 rows=9990) (actual time=0.184..16.1 rows=42 loops=1)
    -> Table scan on sales_log  (cost=10078 rows=99900) (actual time=0.129..13.3 rows=100000 loops=1)

The scan read all 100,000 rows to keep 42. Write down the actual time on the top line (the second number is the total): you will compare it after creating the index. Because EXPLAIN ANALYZE really runs the statement, use plain EXPLAIN on a query you only want to look at, and never put ANALYZE in front of a slow query on a busy production server.

Plan words you will see

Plan lineMeaningGood or bad?
Rows fetched before executionA primary or unique key compared with a constant: the one row was found while planningBest possible
Single-row index lookup ... using PRIMARYOne row per lookup through a primary or unique key (typical in joins)Excellent
Index lookup ... using idx_...Jumps to the rows with one valueGood
Index range scan ...Reads a slice of the index (BETWEEN, <, >, LIKE 'abc%')Good
Covering index ...The index alone holds every column the query needs, so the table is never touchedEven better
Index scan ...Reads the whole index from start to endBetter than a table scan, still reads everything
Table scan on ...Reads every rowFine on small tables; the thing to fix on big ones
Sort: ...Sorts rows in memory or on disk (a "filesort")Extra work; an index on the ORDER BY column can avoid it

The classic table format

MySQL 9.7 prints plans as this tree by default. The older traditional format, one table row per table in the query, is still available, and you will meet it in older tutorials:

EXPLAIN FORMAT=TRADITIONAL
SELECT * FROM customers WHERE email = 'alice@example.com';

Output (the rows and filtered estimates can differ)

+----+-------------+-----------+------------+-------+---------------+-------+---------+-------+------+----------+-------+
| id | select_type | table     | partitions | type  | possible_keys | key   | key_len | ref   | rows | filtered | Extra |
+----+-------------+-----------+------------+-------+---------------+-------+---------+-------+------+----------+-------+
|  1 | SIMPLE      | customers | NULL       | const | email         | email | 402     | const |    1 |   100.00 | NULL  |
+----+-------------+-----------+------------+-------+---------------+-------+---------+-------+------+----------+-------+

The columns to read are type (how the table is accessed: const and eq_ref are single-row lookups, ref is an index lookup, range a range scan, index a full index scan, ALL a full table scan), possible_keys (indexes MySQL considered), key (the one it chose, NULL for none) and rows (estimated rows to examine).

🐬 Version note

The default format is the explain_format setting: TREE on MySQL 9.7, TRADITIONAL on MySQL 8.4, which prints the table above for a plain EXPLAIN. On 8.4 write EXPLAIN FORMAT=TREE to get the tree; EXPLAIN ANALYZE always prints a tree. MariaDB has neither FORMAT=TREE nor EXPLAIN ANALYZE: it prints the traditional table, and its own ANALYZE SELECT ... adds the real row counts to it.

Here is the same plain EXPLAIN on a MySQL 8.4 server:

EXPLAIN SELECT * FROM customers WHERE email = 'alice@example.com';

Output on MySQL 8.4 (the rows and filtered estimates can differ)

➕ Creating an Index

CREATE INDEX index_name ON table_name (column_name);

Name indexes so you can tell what they cover from the name alone. This course uses idx_table_column (idx_sales_sold_on) and uq_table_column for unique ones. MySQL does not care about the name; your future self does.

CREATE INDEX idx_sales_sold_on ON sales_log (sold_on);

EXPLAIN ANALYZE SELECT * FROM sales_log WHERE sold_on = '2025-03-15'\G

Output (your timings and estimates will differ)

*************************** 1. row ***************************
EXPLAIN: -> Index lookup on sales_log using idx_sales_sold_on (sold_on = DATE'2025-03-15')  (cost=14.7 rows=42) (actual time=0.0728..0.0758 rows=42 loops=1)

One line instead of two: an Index lookup that goes straight to the 42 matching rows. Compare the total actual time with the one you wrote down. On this page's server it fell from more than 10 milliseconds to well under one; the exact numbers depend on your machine, but a drop of a hundred times or more is typical. The estimate also became accurate (rows=42), because the index knows exactly how many entries hold that date.

Indexes in CREATE TABLE and ALTER TABLE

You can declare indexes when you create a table, or add them later with ALTER TABLE, which can add several in one statement:

CREATE TABLE gift_cards (
    id         INT AUTO_INCREMENT PRIMARY KEY,
    code       CHAR(12) NOT NULL,
    issued_on  DATE NOT NULL,
    balance    DECIMAL(8, 2) NOT NULL,
    UNIQUE KEY uq_gift_cards_code (code),
    INDEX idx_gift_cards_issued_on (issued_on)
);

ALTER TABLE gift_cards
    ADD INDEX idx_gift_cards_balance (balance);

(gift_cards is only an illustration; you do not need to create it. INDEX and KEY mean the same thing in MySQL.)

⚠️ Creating an index on a big table takes time

Building idx_sales_sold_on took a fraction of a second on 100,000 rows. On a table with hundreds of millions of rows it can take minutes and extra disk space. InnoDB builds most indexes "online" (the table stays readable and writable while it works), but on a live server you still schedule it for a quiet moment.

🧱 Composite Indexes and the Leftmost Prefix

A composite index covers several columns, sorted by the first column, then by the second within each first value, and so on, exactly like a phone book sorted by last name and then first name. A common report asks for one customer's sales in one month:

CREATE INDEX idx_sales_customer_date ON sales_log (customer_id, sold_on);

EXPLAIN SELECT COUNT(*) FROM sales_log
WHERE customer_id = 3
  AND sold_on BETWEEN '2025-03-01' AND '2025-03-31'\G

Output (cost and row estimates differ from server to server)

*************************** 1. row ***************************
EXPLAIN: -> Aggregate: count(0)  (cost=73.1 rows=1)
    -> Filter: ((sales_log.customer_id = 3) and (sales_log.sold_on between '2025-03-01' and '2025-03-31'))  (cost=34.6 rows=167)
        -> Covering index range scan on sales_log using idx_sales_customer_date over (customer_id = 3 AND '2025-03-01' <= sold_on <= '2025-03-31')  (cost=34.6 rows=167)

MySQL jumps to customer 3 in the index, and inside customer 3 the dates are already sorted, so it reads just the March slice. It is also a covering index here: COUNT(*) needs nothing but the two indexed columns, so the table itself is never read.

Column order matters

An index on (customer_id, sold_on) is sorted by customer_id first. It helps any query that constrains a leftmost prefix of its columns:

The query filters onCan seek with (customer_id, sold_on)?Why
customer_id = 3YesThe first column
customer_id = 3 AND sold_on BETWEEN ...Yes, best caseBoth columns, in index order
sold_on BETWEEN ... aloneNot directlyThe dates are only sorted within each customer

The order of the conditions in your WHERE clause does not matter (sold_on ... AND customer_id = 3 works the same). The order of the columns in the index does. A good default: put the column you compare with = first and the range column (BETWEEN, <, >) last.

💡 The skip scan exception

Since MySQL 8.0.13 the optimizer can sometimes use a composite index without its first column, when that column has few different values: it does a skip scan, one small range read per customer_id. You will see index skip scan in such plans. It is a bonus, not something to design for: a query that filters on sold_on alone still deserves its own index (which you already created).

graph TD I["index (customer_id, sold_on)"] --> A["customer_id = 3: seek"] I --> C["sold_on range only: no seek"] A --> B["plus a sold_on range: tight slice"] C --> N["give sold_on its own index"]

🔑 Unique Indexes

A unique index is an index plus a rule: no two rows may hold the same value (several NULLs are allowed). A UNIQUE constraint in CREATE TABLE and a unique index are the same thing in MySQL; the constraint is implemented as the index you saw on customers.email.

Every receipt number in sales_log should be unique, so give it a unique index:

CREATE UNIQUE INDEX uq_sales_receipt ON sales_log (receipt_no);

EXPLAIN SELECT * FROM sales_log WHERE receipt_no = '0004242'\G

Output (cost estimates differ from server to server)

*************************** 1. row ***************************
EXPLAIN: -> Rows fetched before execution  (cost=0..0 rows=1)

Rows fetched before execution: because the index is unique and the value is a constant, at most one row can match, so MySQL looks it up while it is still planning and has nothing left to do when the query runs. You saw the same line for the primary key. And the uniqueness rule is enforced from now on:

INSERT INTO sales_log (receipt_no, customer_id, book_id, sold_on, quantity, channel)
VALUES ('0004242', 1, 1, '2026-07-28', 1, 'web');

Error

ERROR 1062 (23000): Duplicate entry '0004242' for key 'sales_log.uq_sales_receipt'

If existing rows already contain duplicates, CREATE UNIQUE INDEX itself fails with the same error 1062, naming the first duplicate it found: clean the data first.

🚫 What Stops an Index from Being Used

An index helps only when MySQL can turn your condition into "jump to this value" or "read this slice". A few common habits make that impossible, and the query silently falls back to a full scan. It still returns the right rows, just slowly.

1. A function around the indexed column

EXPLAIN SELECT * FROM sales_log
WHERE YEAR(sold_on) = 2025 AND MONTH(sold_on) = 3\G

Output (cost and row estimates differ from server to server)

*************************** 1. row ***************************
EXPLAIN: -> Filter: ((year(sales_log.sold_on) = 2025) and (month(sales_log.sold_on) = 3))  (cost=10078 rows=99900)
    -> Table scan on sales_log  (cost=10078 rows=99900)

The index is sorted by sold_on, not by YEAR(sold_on), so MySQL has to compute the function for every row. Rewrite the condition as a range on the bare column:

EXPLAIN SELECT * FROM sales_log
WHERE sold_on >= '2025-03-01' AND sold_on < '2025-04-01'\G

Output (cost and row estimates differ from server to server)

*************************** 1. row ***************************
EXPLAIN: -> Index range scan on sales_log using idx_sales_sold_on over ('2025-03-01' <= sold_on < '2025-04-01'), with index condition: ((sales_log.sold_on >= DATE'2025-03-01') and (sales_log.sold_on < DATE'2025-04-01'))  (cost=581 rows=1291)

An Index range scan over March. Writing the upper bound as "< the first day of the next month" is a good habit: it stays correct even if the column is later changed to DATETIME, where BETWEEN '2025-03-01' AND '2025-03-31' would miss everything after midnight on the 31st. The same rule applies to UPPER(email) = ..., price * 1.1 > 10 and every other expression wrapped around a column: move the arithmetic to the other side.

2. A wildcard at the start of LIKE

EXPLAIN FORMAT=TRADITIONAL
SELECT id, email FROM customers WHERE email LIKE 'gr%';

EXPLAIN FORMAT=TRADITIONAL
SELECT id, email FROM customers WHERE email LIKE '%@example.com';

Output (the rows and filtered estimates can differ)

+----+-------------+-----------+------------+-------+---------------+-------+---------+------+------+----------+--------------------------+
| id | select_type | table     | partitions | type  | possible_keys | key   | key_len | ref  | rows | filtered | Extra                    |
+----+-------------+-----------+------------+-------+---------------+-------+---------+------+------+----------+--------------------------+
|  1 | SIMPLE      | customers | NULL       | range | email         | email | 402     | NULL |    1 |   100.00 | Using where; Using index |
+----+-------------+-----------+------------+-------+---------------+-------+---------+------+------+----------+--------------------------+
+----+-------------+-----------+------------+-------+---------------+-------+---------+------+------+----------+--------------------------+
| id | select_type | table     | partitions | type  | possible_keys | key   | key_len | ref  | rows | filtered | Extra                    |
+----+-------------+-----------+------------+-------+---------------+-------+---------+------+------+----------+--------------------------+
|  1 | SIMPLE      | customers | NULL       | index | NULL          | email | 402     | NULL |    8 |    12.50 | Using where; Using index |
+----+-------------+-----------+------------+-------+---------------+-------+---------+------+------+----------+--------------------------+

Look at the type and rows columns. 'gr%' is a range on the email index: the sorted list tells MySQL exactly where the values starting with "gr" begin and end, and it reads 1 entry. '%@example.com' can start with anything, so there is no place to jump to: possible_keys is NULL, and MySQL reads the whole email index from first entry to last (type index, all 8 rows), testing each one. It only reads the index rather than the table because id and email are both stored in it; select more columns and it becomes a full table scan (ALL). Searching for words in the middle of text is a job for a FULLTEXT index, mentioned in Going Further.

3. Comparing a text column with a number

receipt_no is CHAR(7), but receipt numbers look like numbers, so it is tempting to type 4242:

EXPLAIN SELECT * FROM sales_log WHERE receipt_no = 4242\G

Output (cost and row estimates differ from server to server)

*************************** 1. row ***************************
EXPLAIN: -> Filter: (sales_log.receipt_no = 4242)  (cost=10078 rows=9990)
    -> Table scan on sales_log  (cost=10078 rows=99900)

A full scan, despite the unique index. When a string column meets a number, MySQL converts every value in the column to a number before comparing ('0004242' becomes 4242), and converted values are not in the index's sort order. Compare like with like and the single-row lookup comes back:

SELECT receipt_no, customer_id, book_id, sold_on
FROM sales_log WHERE receipt_no = '0004242';

Output

+------------+-------------+---------+------------+
| receipt_no | customer_id | book_id | sold_on    |
+------------+-------------+---------+------------+
| 0004242    |           7 |       4 | 2022-08-12 |
+------------+-------------+---------+------------+

(Comparing a number column with a string, like id = '42', is harmless: MySQL converts the single constant, not the column.)

4. Conditions the index cannot narrow

  • OR across different columns (WHERE customer_id = 3 OR book_id = 5): one index cannot serve both halves. MySQL can sometimes combine two indexes (the plan says index_merge or "Sort-union"); if it does not, two queries joined with UNION can be faster.
  • Negations (!=, NOT IN, NOT LIKE) usually match most of the table, so a scan is the right plan anyway.
  • Conditions that match a big share of the rows: if half the table matches, reading the index and then fetching each row costs more than one straight scan, and the optimizer will (correctly) ignore your index.

✅ When in doubt, EXPLAIN

You never have to guess whether an index is used. Put EXPLAIN in front of the query and look for Table scan (tree) or type: ALL (traditional) on a big table. That one habit catches every pattern in this section.

🛠️ Managing Indexes

Here is every index on sales_log so far:

SELECT INDEX_NAME, COLUMN_NAME, SEQ_IN_INDEX, NON_UNIQUE, IS_VISIBLE
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = 'bookstore' AND TABLE_NAME = 'sales_log'
ORDER BY INDEX_NAME, SEQ_IN_INDEX;

Output

+-------------------------+-------------+--------------+------------+------------+
| INDEX_NAME              | COLUMN_NAME | SEQ_IN_INDEX | NON_UNIQUE | IS_VISIBLE |
+-------------------------+-------------+--------------+------------+------------+
| idx_sales_customer_date | customer_id |            1 |          1 | YES        |
| idx_sales_customer_date | sold_on     |            2 |          1 | YES        |
| idx_sales_sold_on       | sold_on     |            1 |          1 | YES        |
| PRIMARY                 | id          |            1 |          0 | YES        |
| uq_sales_receipt        | receipt_no  |            1 |          0 | YES        |
+-------------------------+-------------+--------------+------------+------------+

The composite index shows up as two rows: SEQ_IN_INDEX 1 and 2 give its column order.

Rename and drop

ALTER TABLE sales_log RENAME INDEX uq_sales_receipt TO uq_sales_receipt_no;

DROP INDEX uq_sales_receipt_no ON sales_log;
-- the same thing, ALTER TABLE style:
-- ALTER TABLE sales_log DROP INDEX uq_sales_receipt_no;

CREATE UNIQUE INDEX uq_sales_receipt ON sales_log (receipt_no);

(The last line puts the unique index back, because the project needs it.) Dropping an index never touches the rows, only the sorted copy. The primary key is dropped with ALTER TABLE ... DROP PRIMARY KEY, which you will rarely want.

Invisible indexes: test a drop safely

Before dropping an index on a busy table, you want to know whether any query still needs it. Rebuilding a dropped index can take a long time, so MySQL lets you hide one instead. An invisible index is still maintained on every write, but the optimizer ignores it:

ALTER TABLE sales_log ALTER INDEX idx_sales_sold_on INVISIBLE;

EXPLAIN SELECT * FROM sales_log WHERE sold_on = '2025-03-15'\G

Output (cost and row estimates differ from server to server)

*************************** 1. row ***************************
EXPLAIN: -> Filter: (sales_log.sold_on = DATE'2025-03-15')  (cost=10078 rows=41.7)
    -> Table scan on sales_log  (cost=10078 rows=99900)

Back to a full scan: this query does need the index. Turning it back on is instant, because the index was kept up to date the whole time:

ALTER TABLE sales_log ALTER INDEX idx_sales_sold_on VISIBLE;

🐬 Version note

Invisible indexes and RENAME INDEX work on MySQL 9.7 and 8.4. MariaDB has RENAME INDEX too, but hides indexes with a different keyword: ALTER TABLE ... ALTER INDEX name IGNORED (and NOT IGNORED), and its information_schema.STATISTICS has an IGNORED column instead of IS_VISIBLE.

🧭 When to Index (and When Not To)

Usually worth an indexWhy
Columns in frequent WHERE conditionsThe lookups and ranges you saw in this lesson
Join columnsForeign keys already have one; add one when you join on something else
Columns in ORDER BY ... LIMITReading an index in order avoids sorting the whole table
Columns that must be uniqueA unique index enforces the rule and speeds up lookups
Usually not worth oneWhy
Small tables (a few hundred rows)A scan is already fast
Columns no important query filters, joins or sorts onPure write and space overhead
Columns where one value covers a large share of the rows (in_stock, channel)The optimizer will usually scan anyway; such a column can still be useful as the second column of a composite index
A second index that starts with the same columns as an existing oneAn index on (customer_id, sold_on) already serves customer_id alone

Habits that help any query

  • Select only the columns you need. Less data to read and send, and a narrow query may be answered from a covering index alone.
  • Use LIMIT when you want the top ten, not the whole table.
  • Do not fear IN (subquery). Old advice says "always rewrite IN as EXISTS". Modern MySQL turns both into the same semijoin plan in most cases; write the one that reads better, and check with EXPLAIN if it is slow.
  • Measure first. Write the query correctly, then let EXPLAIN ANALYZE show you where the time goes. Index what the plan says, not what you guess.

⚠️ Common Mistakes

1. Reusing an index name

CREATE INDEX idx_sales_sold_on ON sales_log (sold_on, channel);

Error

ERROR 1061 (42000): Duplicate key name 'idx_sales_sold_on'

What it means: index names must be unique within a table ("key" is MySQL's other word for index). Fix: pick a new name, or drop the old index first if you meant to replace it. Check what exists with SHOW INDEX FROM sales_log.

2. Dropping an index that is not there

DROP INDEX idx_sales_date ON sales_log;

Error

ERROR 1091 (42000): Can't DROP 'idx_sales_date'; check that column/key exists

What it means: there is no index with that name (it is idx_sales_sold_on). Fix: look the name up with SHOW INDEX. In a migration script that may run twice, ALTER TABLE ... DROP INDEX IF EXISTS works on MariaDB but not on MySQL, so scripts for MySQL check information_schema.STATISTICS first.

3. Dropping the index a foreign key depends on

DROP INDEX fk_orders_customer ON orders;

Error

ERROR 1553 (HY000): Cannot drop index 'fk_orders_customer': needed in a foreign key constraint

What it means: the foreign key from Lesson 4.2 needs an index on customer_id to check orders quickly, and this is the only one. Fix: leave it alone. If you really want a different index there, create the new one first (any index that starts with customer_id will do); InnoDB then quietly drops its automatic index, because the new one can take over the job.

4. Adding the same index twice (silent)

CREATE INDEX idx_sales_customer ON sales_log (customer_id);
SHOW WARNINGS;

Output

Empty set

What it means: no error, and no warning either, yet this index is pure overhead: idx_sales_customer_date already starts with customer_id, so it serves every query this one could. Every insert now updates one more index for nothing. MySQL only warns (warning 1831, "Duplicate index ... deprecated") when the new index has exactly the same columns as an existing one. Fix: list the existing indexes before you add one, and drop the redundant one:

DROP INDEX idx_sales_customer ON sales_log;

5. Hiding the column inside a function (silent)

SELECT COUNT(*) AS march_sales
FROM sales_log
WHERE DATE_FORMAT(sold_on, '%Y-%m') = '2025-03';

Output

+-------------+
| march_sales |
+-------------+
|        1291 |
+-------------+

What it means: the answer is right, so nothing looks wrong, but EXPLAIN would show a scan of all 100,000 rows: the index on sold_on cannot be used through DATE_FORMAT. Fix: WHERE sold_on >= '2025-03-01' AND sold_on < '2025-04-01', which returns the same count from an index range.

🛠️ Step 4: Measure and fix report C (7 min)

Report C looks up all sales of one book to one customer: "has customer 5 bought book 9 before?". It runs thousands of times a day, from the website.

-- Report C: one customer's purchases of one book
EXPLAIN ANALYZE
SELECT receipt_no, sold_on, quantity
FROM sales_log
WHERE customer_id = 5 AND book_id = 9
ORDER BY sold_on\G

Output (your timings and estimates will differ)

*************************** 1. row ***************************
EXPLAIN: -> Filter: (sales_log.book_id = 9)  (cost=494 rows=2291) (actual time=1.95..9.57 rows=1137 loops=1)
    -> Index lookup on sales_log using idx_sales_customer_date (customer_id = 5)  (cost=494 rows=22912) (actual time=1.9..9.13 rows=12500 loops=1)

MySQL uses idx_sales_customer_date to find customer 5's 12,500 sales, then fetches every one of them to check the book, and keeps 1,137. (There is no Sort step, because that index already returns customer 5's rows in date order.) A composite index that matches the question exactly, with both equality columns first and the sort column last, lets MySQL jump straight to the 1,137 rows, still in date order:

CREATE INDEX idx_sales_customer_book_date ON sales_log (customer_id, book_id, sold_on);

EXPLAIN ANALYZE
SELECT receipt_no, sold_on, quantity
FROM sales_log
WHERE customer_id = 5 AND book_id = 9
ORDER BY sold_on\G

Output (your timings and estimates will differ)

*************************** 1. row ***************************
EXPLAIN: -> Index lookup on sales_log using idx_sales_customer_book_date (customer_id = 5, book_id = 9)  (cost=378 rows=1137) (actual time=0.176..1.21 rows=1137 loops=1)

One index lookup and nothing else: no Filter line, no Sort line, and only the rows that are part of the answer are read.

🛠️ Step 5: Look for a redundant index (5 min)

The new index starts with customer_id, just like idx_sales_customer_date (customer_id, sold_on). Is the old one now redundant? Not completely: the new index has book_id in the middle, so "customer 3 in March" can no longer read a tight date slice from it. Check what the March report uses now:

EXPLAIN SELECT COUNT(*) FROM sales_log
WHERE customer_id = 3
  AND sold_on BETWEEN '2025-03-01' AND '2025-03-31'\G

Output (cost and row estimates differ from server to server)

*************************** 1. row ***************************
EXPLAIN: -> Aggregate: count(0)  (cost=73.1 rows=1)
    -> Filter: ((sales_log.customer_id = 3) and (sales_log.sold_on between '2025-03-01' and '2025-03-31'))  (cost=34.6 rows=167)
        -> Covering index range scan on sales_log using idx_sales_customer_date over (customer_id = 3 AND '2025-03-01' <= sold_on <= '2025-03-31')  (cost=34.6 rows=167)

It still picks idx_sales_customer_date, so both indexes earn their keep. Write the decision in your notes: "keep both; reviewed with EXPLAIN".

❓ Common Questions at This Stage

Should I add an index to every column, just in case?

No. Every index slows down inserts, updates and deletes, uses disk and memory, and gives the optimizer more choices to get wrong. Start with the primary key, the automatic foreign key indexes and the unique columns, then add an index when a real, frequent query is slow and EXPLAIN shows it would help.

I created an index, but EXPLAIN still shows a table scan. Why?

Check, in order: is the column wrapped in a function or compared with the wrong type? Does a composite index start with the column you filter on? Does the condition match a large share of the table (then a scan really is cheaper)? Is the table tiny? Finally, run ANALYZE TABLE: stale statistics after a big load can mislead the optimizer.

Why are my cost and rows numbers different from the ones on this page?

They are estimates built from sampled statistics, and they depend on the server version, its settings and when statistics were last refreshed. Compare the shape of the plan (scan or lookup, which index, any sort) rather than the exact numbers. The actual row counts from EXPLAIN ANALYZE should match exactly.

Can I force MySQL to use my index?

You can, with FORCE INDEX (idx_name) after the table name or with optimizer hints, but treat it as a last resort. The optimizer usually knows something you do not (how many rows match, what is cached), and a forced index stays forced after the data changes. Fix the query or the statistics first.

📝 Lesson Summary

🎓 Key Takeaways

  • An index is a sorted B-tree copy of one or more columns; it turns a full table scan into a jump to the matching rows
  • Primary keys, UNIQUE constraints and foreign keys get indexes automatically
  • EXPLAIN shows the plan; EXPLAIN ANALYZE runs the query and adds real times and row counts; read plans from the innermost line up
  • MySQL 9.7 prints plans as a tree by default; 8.4 prints the traditional table (type, key, rows)
  • A composite index serves its leftmost prefix: equality columns first, range or sort column last
  • Functions on a column, leading % wildcards and string-versus-number comparisons stop an index from being used
  • Indexes cost write time and space: add them for measured, frequent queries, and look for redundant ones
