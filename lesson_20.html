📦 Lesson 8.1: Importing & Exporting Data

A database that only lives inside one server is one bad afternoon away from being lost. In this lesson you learn to move data in and out of MySQL: a complete backup you can restore with one command, a CSV file a colleague can open in a spreadsheet, and a spreadsheet's rows loaded safely into your tables.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Back up a database with mysqldump, choose the right options for MySQL 9.7, and restore the file into a test database
  • Explain what secure_file_priv and local_infile control, and find their values on your server
  • Export query results to a CSV file with SELECT ... INTO OUTFILE, including a header row
  • Import a CSV file through a staging table with LOAD DATA INFILE, converting dates and empty values on the way in
  • Recognize and fix the errors file operations raise (1290, 1086, 3948, 2068, 3546)
  • ⏱️ Time 105 minutes
  • 📋 Prerequisites Lesson 7.4: User Management & Permissions
  • 🛠️ You will build a backup kit: a least-privilege backup account, a tested dump, a monthly sales CSV and a repeatable import script
  • 🗄️ Database bookstore freshly loaded from bookstore.sql

🗺️ The Big Picture

Moving data comes in two flavors, and they use different tools:

  • Whole databases (backups, moving to a new server): mysqldump writes a .sql file full of CREATE TABLE and INSERT statements, and the mysql client plays it back. These are shell commands, typed at your terminal, not at the mysql> prompt.
  • Rows (reports, spreadsheets, data from other systems): SELECT ... INTO OUTFILE writes a CSV file and LOAD DATA INFILE reads one. These are SQL statements, typed at the mysql> prompt.

💾 Backing Up with mysqldump

mysqldump is a separate program that ships with the MySQL client tools. It connects to the server like any client, reads every table, and prints the SQL that would rebuild them. You redirect that output into a file. It is a logical backup: plain text you can read, search and load into a different MySQL version or even MariaDB.

Your first backup

macOS, Linux, WSL

mysqldump -u root -p --single-transaction --routines --events \
    --set-gtid-purged=OFF bookstore > bookstore_backup.sql

Windows (PowerShell)

mysqldump -u root -p --single-transaction --routines --events `
    --set-gtid-purged=OFF --result-file=bookstore_backup.sql bookstore

It asks for the password, prints nothing else, and leaves a file of about 12 KB. On Windows, --result-file replaces the > redirect: Windows PowerShell 5.1 writes redirected text as UTF-16, which the mysql client then refuses to read back.

OptionWhat it doesWhy you want it
--single-transactionReads every InnoDB table from one consistent snapshotThe backup is consistent and the store keeps taking orders while it runs (no table locks)
--routinesIncludes stored procedures and functionsThey are left out by default; you wrote some in Lesson 7.1
--eventsIncludes scheduled eventsAlso left out by default (triggers are included by default)
--set-gtid-purged=OFFLeaves out the server's replication history (GTIDs)MySQL 9.7 turns GTIDs on by default; without this option the file cannot be restored on the same server (see below)
--databases bookstoreAdds CREATE DATABASE and USE to the fileThe file then recreates the database by itself
--no-dataStructure only, no rowsAn empty copy of the schema, for documentation or a new project
--no-create-infoRows only, no CREATE TABLEReload data into tables that already exist
--all-databasesEvery database on the server, including the mysql system databaseA whole-server backup (users included)

What is inside the file

Open bookstore_backup.sql in a text editor. Shortened, it looks like this:

-- MySQL dump 10.13  Distrib 9.7.2, for Linux (x86_64)
--
-- Host: localhost    Database: bookstore
-- ------------------------------------------------------
-- Server version	9.7.2

/*!40101 SET @OLD_CHARACTER_SET_CLIENT=@@CHARACTER_SET_CLIENT */;
/*!50503 SET NAMES utf8mb4 */;
/*!40014 SET @OLD_FOREIGN_KEY_CHECKS=@@FOREIGN_KEY_CHECKS, FOREIGN_KEY_CHECKS=0 */;
...
--
-- Table structure for table `authors`
--

DROP TABLE IF EXISTS `authors`;
CREATE TABLE `authors` (
  `id` int NOT NULL AUTO_INCREMENT,
  `name` varchar(100) COLLATE utf8mb4_unicode_ci NOT NULL,
  `birth_year` int DEFAULT NULL,
  PRIMARY KEY (`id`)
) ENGINE=InnoDB AUTO_INCREMENT=11 DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
...
INSERT INTO `authors` VALUES (1,'Frank Herbert',1920),(2,'George Orwell',1903),...;
...
-- Dump completed on ...

Three things to notice:

  • Every table starts with DROP TABLE IF EXISTS. Restoring a backup replaces the tables it contains. That is what you want in a disaster and exactly what you do not want by accident.
  • Foreign key checks are switched off at the top and back on at the bottom, so tables can be created in alphabetical order (authors, book_categories, books...) even though book_categories points at books.
  • The /*!40101 ... */ lines are "versioned comments": MySQL runs them, other databases skip them. Leave them alone.

Without --databases, the file has no CREATE DATABASE or USE line, so you choose the target database when you restore. That is handy for a test restore under a different name.

🐬 Version note: GTIDs and those warnings

MySQL 9.7 starts with gtid_mode=ON (global transaction IDs, used by replication). A plain mysqldump bookstore then prints two GTID warnings ("A partial dump from a server that has GTIDs..." and a consistency warning; --single-transaction silences the second) and writes a SET @@GLOBAL.GTID_PURGED line into the file. Restoring that file into another database on the same server fails, as you will see in the next section. For a backup you plan to restore yourself, add --set-gtid-purged=OFF. MySQL 8.4 has GTIDs off by default, so the option changes nothing there and is safe to keep. MariaDB uses a different GTID system: its mariadb-dump does not know this option (leave it out), and newer MariaDB packages only install the tools under their mariadb- names (mariadb-dump, mariadb).

⚠️ Passwords on the command line

Always type -p with nothing after it and let the tool ask. -pSecret works, but the password lands in your shell history and in the process list, and MySQL prints "Using a password on the command line interface can be insecure." For unattended backups, use a login path (see the backup plan below).

♻️ Restoring and Testing a Backup

A dump file is just a SQL script, so restoring means running it. The safest habit is to restore into a test database first and compare it with the original. A backup you have never restored is a hope, not a backup.

macOS, Linux, WSL

mysql -u root -p -e "CREATE DATABASE bookstore_test"
mysql -u root -p bookstore_test < bookstore_backup.sql

Windows (PowerShell has no < redirect)

mysql -u root -p -e "CREATE DATABASE bookstore_test"
mysql -u root -p bookstore_test --commands -e "SOURCE bookstore_backup.sql"

On MySQL 9.7, client commands such as SOURCE are switched off when the client runs a script non-interactively, hence --commands. Typing SOURCE at the mysql> prompt needs nothing extra.

Now compare the copy with the original. These queries read both databases side by side:

SELECT
    (SELECT COUNT(*) FROM bookstore.books)            AS books_original,
    (SELECT COUNT(*) FROM bookstore_test.books)       AS books_copy,
    (SELECT COUNT(*) FROM bookstore.order_items)      AS items_original,
    (SELECT COUNT(*) FROM bookstore_test.order_items) AS items_copy;

Output (after the restore above)

+----------------+------------+----------------+------------+
| books_original | books_copy | items_original | items_copy |
+----------------+------------+----------------+------------+
|             11 |         11 |             18 |         18 |
+----------------+------------+----------------+------------+

When the counts agree, drop the copy with DROP DATABASE bookstore_test;. A file made with --databases bookstore restores with just mysql -u root -p < file.sql, because it carries its own CREATE DATABASE and USE; that is the version you want for a real disaster recovery onto an empty server.

🛑 The 9.7 restore trap

If you leave out --set-gtid-purged=OFF on MySQL 9.7 and restore into another database on the same server, the restore stops at the top of the file and creates no tables at all:

ERROR 3546 (HY000) at line 24: @@GLOBAL.GTID_PURGED cannot be changed: the added gtid set must not overlap with @@GLOBAL.GTID_EXECUTED

The file is not broken; it is trying to rewrite the server's replication history. Take the dump again with --set-gtid-purged=OFF.

What a dump does not contain

A single-database dump holds tables, rows, views, triggers and (with the options above) routines and events. It does not hold user accounts and their grants: those live in the mysql system database. Keep your CREATE USER and GRANT statements in a script of their own (the project does this), or print them with SHOW GRANTS.

🔐 Where the Server May Read and Write Files

SELECT ... INTO OUTFILE and LOAD DATA INFILE are run by the server process, on the server's disk. A server that could write anywhere could be tricked into overwriting its own files, so MySQL fences these statements in with two settings and one privilege:

ControlWhat it decidesTypical default
secure_file_privThe only folder the server reads from and writes to. Empty = anywhere (unsafe); NULL = nowhere/var/lib/mysql-files/ on Linux packages and the Docker image; an Uploads folder under C:\ProgramData\MySQL\ with the Windows installer
FILE privilegeWhether an account may use server-side files at allOnly root; never grant it to an application account
local_infileWhether clients may send a file from their own computer with LOAD DATA LOCALOFF since MySQL 8.0

Ask your server where its file folder is:

SHOW VARIABLES LIKE 'secure_file_priv';

Output (MySQL Docker image; Linux packages show the same)

+------------------+-----------------------+
| Variable_name    | Value                 |
+------------------+-----------------------+
| secure_file_priv | /var/lib/mysql-files/ |
+------------------+-----------------------+

Every server-side file in this lesson lives in that folder. If yours shows a different path, use it everywhere this lesson writes /var/lib/mysql-files/. If it shows NULL, file statements are disabled: change secure_file_priv in the server's option file (my.cnf or my.ini) and restart, or use the client-side methods shown later. MariaDB's Docker image shows an empty value, which means "anywhere".

graph TD A["Where is the CSV file?"] -->|"on the server"| B["LOAD DATA INFILE"] A -->|"on my computer"| C["LOAD DATA LOCAL INFILE"] B --> D["secure_file_priv + FILE"] C --> E["local_infile on both sides"]

On a laptop where server and client are the same machine, both routes work. On a hosted server you usually cannot put files into its folder, so LOCAL (or a GUI tool) is the realistic route.

📤 Exporting to CSV

SELECT ... INTO OUTFILE

Write any query, then add INTO OUTFILE and the format at the end. The server writes the rows to a file instead of showing them:

SELECT b.id, b.title, a.name AS author, b.price, b.published
FROM books AS b
JOIN authors AS a ON a.id = b.author_id
ORDER BY b.id
INTO OUTFILE '/var/lib/mysql-files/books_export.csv'
    FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'
    LINES TERMINATED BY '\n';

Output

Query OK, 11 rows affected

"11 rows affected" means 11 lines were written. The file looks like this (open it with cat, a text editor or a spreadsheet; on Linux it belongs to the mysql user, so you may need sudo to read or delete it):

1,"Dune","Frank Herbert",14.99,"1965-08-01"
2,"1984","George Orwell",9.99,"1949-06-08"
3,"To Kill a Mockingbird","Harper Lee",11.99,"1960-07-11"
...
11,"Animal Farm","George Orwell",8.49,"1945-08-17"
  • FIELDS TERMINATED BY ',': a comma between values.
  • OPTIONALLY ENCLOSED BY '"': quotes around text and date values, none around numbers, so a title such as I, Robot keeps its comma inside the quotes. (Without OPTIONALLY, every value is quoted.)
  • LINES TERMINATED BY '\n': one row per line. Use '\r\n' if the file is for Windows tools that insist on it.
  • A NULL is written as \N, which LOAD DATA reads back as NULL but a spreadsheet shows literally. Use COALESCE(city, '') when the file is for people.

🐬 Version note: INTO goes last

Old tutorials put INTO OUTFILE between the column list and FROM. That position is deprecated since MySQL 8.0.20; at the end of the statement it works on 9.7, 8.4 and MariaDB alike.

Adding a header row

INTO OUTFILE writes no column names. To add them, glue a row of names onto the data with UNION ALL, and sort with a helper column so the header is guaranteed to come first:

SELECT id, title, author, price
FROM (
    SELECT 0 AS part, 0 AS sort_id, 'id' AS id, 'title' AS title, 'author' AS author, 'price' AS price
    UNION ALL
    SELECT 1, b.id, b.id, b.title, a.name, b.price
    FROM books AS b
    JOIN authors AS a ON a.id = b.author_id
) AS t
ORDER BY part, sort_id
INTO OUTFILE '/var/lib/mysql-files/books_with_header.csv'
    FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'
    LINES TERMINATED BY '\n';

Output

Query OK, 12 rows affected

Twelve lines: the header plus 11 books. The first lines of the file read "id","title","author","price", then "1","Dune","Frank Herbert","14.99": the header row made every column of the union text, so the numbers are quoted too. Spreadsheets do not mind.

Without the FILE privilege: let the client write the file

If you cannot use the server's folder (a hosted database, an account without FILE), run the query from your terminal with --batch. The client prints tab-separated rows with a header line, and you redirect them into a file on your own computer:

mysql -u root -p --batch -e "SELECT id, title, price FROM books ORDER BY id" bookstore > books.tsv
id	title	price
1	Dune	14.99
2	1984	9.99
3	To Kill a Mockingbird	11.99
...

Spreadsheets open .tsv files directly. Tabs inside values are escaped as \t, so this is safe for ordinary data. Add --skip-column-names to drop the header.

📥 Importing a CSV File

The buyer sends a spreadsheet of four new titles, saved as CSV. Look at it before you load anything:

title,author,price,pages,published
"I, Robot",Isaac Asimov,8.99,253,12/02/1950
Emma,Jane Austen,8.49,474,12/23/1815
Frankenstein,Mary Shelley,7.49,,01/01/1818
The Silmarillion,J.R.R. Tolkien,12.99,365,09/15/1977

Four problems are hiding in it, and they are typical of real files:

  • A header line that is not data.
  • A comma inside a title (I, Robot), protected by quotes.
  • US dates (12/02/1950), while MySQL expects 1950-12-02.
  • An empty value for Frankenstein's pages, which should become NULL, not 0.

And one problem of meaning: the file names authors, while books needs an author_id. Mary Shelley is not in the authors table yet.

Step 1: load into a staging table

Never load a stranger's file straight into a real table. Load it into a staging table with the same columns as the file, inspect it, then copy the good rows across.

graph TD A["new_books.csv"] -->|"LOAD DATA INFILE"| B["import_books (staging)"] B -->|"check with SELECT"| C["fix: add missing authors"] C -->|"INSERT ... SELECT + JOIN"| D["books"] 
CREATE TABLE import_books (
    title     VARCHAR(200),
    author    VARCHAR(100),
    price     DECIMAL(8, 2),
    pages     INT,
    published DATE
);

LOAD DATA INFILE '/var/lib/mysql-files/new_books.csv'
INTO TABLE import_books
    FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'
    LINES TERMINATED BY '\n'
    IGNORE 1 LINES
    (title, author, price, @pages, @published)
SET pages     = NULLIF(@pages, ''),
    published = STR_TO_DATE(@published, '%m/%d/%Y');

Output

Query OK, 0 rows affected
Query OK, 4 rows affected
Records: 4  Deleted: 0  Skipped: 0  Warnings: 0

Read the statement in order:

  • IGNORE 1 LINES skips the header.
  • The column list maps the file's five fields, in file order. @pages and @published are user variables: the raw text lands there instead of in a column.
  • SET converts the raw text: NULLIF(@pages, '') turns an empty string into NULL, and STR_TO_DATE reads the US date with the pattern %m/%d/%Y.
  • The status line is your first check: 4 records, 0 skipped, 0 warnings. Any warning deserves a SHOW WARNINGS; before you go on.
SELECT * FROM import_books;

Output

+------------------+----------------+-------+-------+------------+
| title            | author         | price | pages | published  |
+------------------+----------------+-------+-------+------------+
| I, Robot         | Isaac Asimov   |  8.99 |   253 | 1950-12-02 |
| Emma             | Jane Austen    |  8.49 |   474 | 1815-12-23 |
| Frankenstein     | Mary Shelley   |  7.49 |  NULL | 1818-01-01 |
| The Silmarillion | J.R.R. Tolkien | 12.99 |   365 | 1977-09-15 |
+------------------+----------------+-------+-------+------------+

Step 2: check the rows against the real tables

Which authors in the file are missing from authors? A LEFT JOIN with IS NULL (Lesson 4.3) finds them:

SELECT i.title, i.author
FROM import_books AS i
LEFT JOIN authors AS a ON a.name = i.author
WHERE a.id IS NULL;

Output

+--------------+--------------+
| title        | author       |
+--------------+--------------+
| Frankenstein | Mary Shelley |
+--------------+--------------+
INSERT INTO authors (name, birth_year) VALUES ('Mary Shelley', 1797);

Step 3: copy the rows into books, in one transaction

START TRANSACTION;

INSERT INTO books (title, author_id, price, pages, published)
SELECT i.title, a.id, i.price, i.pages, i.published
FROM import_books AS i
JOIN authors AS a ON a.name = i.author
ORDER BY i.title;

SELECT b.id, b.title, a.name AS author, b.pages, b.published
FROM books AS b
JOIN authors AS a ON a.id = b.author_id
WHERE b.id > 11
ORDER BY b.id;

COMMIT;

Output

+----+------------------+----------------+-------+------------+
| id | title            | author         | pages | published  |
+----+------------------+----------------+-------+------------+
| 12 | Emma             | Jane Austen    |   474 | 1815-12-23 |
| 13 | Frankenstein     | Mary Shelley   |  NULL | 1818-01-01 |
| 14 | I, Robot         | Isaac Asimov   |   253 | 1950-12-02 |
| 15 | The Silmarillion | J.R.R. Tolkien |   365 | 1977-09-15 |
+----+------------------+----------------+-------+------------+

Four new books with the right authors, a real NULL for the missing page count and proper dates. Had anything looked wrong, ROLLBACK instead of COMMIT would have undone the insert (Lesson 7.2). Finally drop the staging table:

DROP TABLE import_books;

💻 LOAD DATA LOCAL: Files on Your Own Computer

With LOCAL, the client reads the file and sends it to the server. The file can be anywhere on your computer, secure_file_priv does not apply, and the account needs no FILE privilege, only INSERT on the table. A relative path is relative to the folder you were in when you started mysql.

Because a server could ask a careless client for any file, both sides must agree to it:

  1. Server: local_infile must be ON. It is OFF by default. An administrator turns it on with SET PERSIST local_infile = ON; (survives restarts) or in the option file.
  2. Client: start it with mysql -u root -p --local-infile=1 bookstore. Without that, the client refuses with ERROR 2068 (HY000): LOAD DATA LOCAL INFILE file request rejected due to restrictions on access.

With both in place, the import from the previous section works from your own folder. Here it loads the same file into a fresh staging table:

CREATE TABLE import_books (
    title VARCHAR(200), author VARCHAR(100), price DECIMAL(8, 2), pages INT, published DATE
);

LOAD DATA LOCAL INFILE 'new_books.csv'
INTO TABLE import_books
    FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'
    LINES TERMINATED BY '\n'
    IGNORE 1 LINES
    (title, author, price, @pages, @published)
SET pages     = NULLIF(@pages, ''),
    published = STR_TO_DATE(@published, '%m/%d/%Y');

SELECT title, author, price FROM import_books ORDER BY title;

Output

Query OK, 0 rows affected
Query OK, 4 rows affected
Records: 4  Deleted: 0  Skipped: 0  Warnings: 0
+------------------+----------------+-------+
| title            | author         | price |
+------------------+----------------+-------+
| Emma             | Jane Austen    |  8.49 |
| Frankenstein     | Mary Shelley   |  7.49 |
| I, Robot         | Isaac Asimov   |  8.99 |
| The Silmarillion | J.R.R. Tolkien | 12.99 |
+------------------+----------------+-------+
4 rows in set

The only differences from the server-side version are the word LOCAL and the path, which now points at your own folder.

DROP TABLE import_books;

⚠️ LOCAL is more forgiving, and that is not always good

With LOCAL, the server cannot stop the client halfway through sending, so bad values and duplicate keys become warnings instead of errors, and the import carries on. Always read the Warnings: count in the status line, and run SHOW WARNINGS; when it is not 0. You will see this in Common Mistakes.

🧰 phpMyAdmin, Other Tools and a Backup Plan

phpMyAdmin

phpMyAdmin wraps the same operations in forms. Select the database in the left panel, then:

  • Export tab: "Quick" gives a SQL dump of the whole database; "Custom" lets you pick tables, choose CSV, and add options like DROP TABLE statements. The file downloads to your computer.
  • Import tab: choose a .sql or .csv file; for CSV, set the separator, enclosure and "skip this number of queries/lines" fields.

It is ideal for small, one-off jobs. Its limits come from PHP's upload settings (upload_max_filesize, post_max_size) and time limits, so large databases belong on the command line.

Other tools worth knowing by name

  • MySQL Shell (mysqlsh) has dump and load utilities (util.dumpSchemas(), util.loadDump()) that work in parallel and are much faster than mysqldump on large databases.
  • Physical backups copy the data files themselves: MySQL Enterprise Backup (commercial) or Percona XtraBackup (check that its version supports your server version). They are the choice for databases of many gigabytes.
  • mysqlimport is a command-line wrapper for LOAD DATA: the file name picks the table (authors.csv loads into authors).
  • mysqlpump, mentioned in older tutorials, was removed in MySQL 9.0.

A backup plan you can follow

  • 3-2-1: three copies of the data, on two kinds of storage, one of them off site (a cloud bucket, a drive at home). A backup on the same disk as the database dies with that disk.
  • A dedicated backup account with only the privileges mysqldump needs (the project creates one), never root.
  • A stored login instead of a password in the script: mysql_config_editor set --login-path=backup --user=bookstore_backup --password asks once and saves it in ~/.mylogin.cnf; then mysqldump --login-path=backup ... needs no -p. The file is obscured, not encrypted, so keep it private to your user.
  • A schedule: cron on Linux and macOS, Task Scheduler on Windows, running a small script that writes a dated, compressed file and deletes old ones.
  • Test restores on a calendar, into a test database, with a count comparison like the one above.

⚠️ Common Mistakes

1. Typing mysqldump at the mysql> prompt

mysqldump -u root -p bookstore > bookstore_backup.sql;

Error

ERROR 1064 (42000): You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near 'mysqldump -u root -p bookstore > bookstore_backup.sql' at line 1

What it means: the server received mysqldump ... as if it were SQL, and no SQL statement starts with that word. Fix: type exit to leave the client, then run mysqldump at your terminal prompt ($ or PS>).

2. Writing a file outside secure_file_priv

SELECT title, price FROM books
INTO OUTFILE '/tmp/books.csv';

Error

ERROR 1290 (HY000): The MySQL server is running with the --secure-file-priv option so it cannot execute this statement

What it means: the server only writes inside its secure_file_priv folder, and /tmp is not it. Fix: check the folder with SHOW VARIABLES LIKE 'secure_file_priv'; and write there. Do not "fix" it by setting secure_file_priv to empty: that lets the server write anywhere it has permission.

3. Exporting to a file that already exists

SELECT title FROM books INTO OUTFILE '/var/lib/mysql-files/titles.txt';
SELECT title FROM books INTO OUTFILE '/var/lib/mysql-files/titles.txt';

Error (MySQL Docker image; same message on 9.7)

ERROR 1086 (HY000): File '/var/lib/mysql-files/titles.txt' already exists

What it means: the first statement wrote the file; the second refuses to overwrite it. This protects you from destroying an earlier export, or a system file. Fix: write to a new name (adding the date works well), or delete the old file from the terminal first (on Linux, sudo rm /var/lib/mysql-files/titles.txt, since the server's user owns it).

4. LOAD DATA LOCAL on a server with local_infile OFF

A fresh install has local_infile off. To see the error on your own server, switch it off for a moment (this needs an administrator account; the next block switches it back on):

SET GLOBAL local_infile = OFF;

LOAD DATA LOCAL INFILE 'new_books.csv' INTO TABLE authors;

Error

ERROR 3948 (42000): Loading local data is disabled; this must be enabled on both the client and server sides
SET GLOBAL local_infile = ON;

What it means: the server refuses files sent by clients. Fix: have an administrator enable local_infile (and start the client with --local-infile=1, or you get error 2068 instead), or put the file in secure_file_priv and drop the word LOCAL. On a shared host where neither is possible, import through phpMyAdmin.

5. Ignoring the warnings of a LOCAL import (silent)

A second file arrives with a price nobody filled in properly:

title,price
Dune,15.49
Emma,N/A

🛠️ Project: The Bookstore Backup Kit

The owner wants three things before the holiday rush: a backup she can trust, a monthly sales file her accountant can open, and a safe way to load new titles from the buyer's spreadsheets. You will build them as a small kit of scripts in your ~/mysql-course folder. Allow about 35 minutes.

🛠️ Step 1: Start clean and create a backup account (5 min)

Reload the database so the earlier experiments are gone, then create an account that can read everything mysqldump needs and change nothing. Save these statements as backup_user.sql: user accounts are not part of a database dump, so this script is how you would recreate the account on a new server.

SOURCE ~/mysql-course/bookstore.sql

CREATE USER IF NOT EXISTS 'bookstore_backup'@'localhost'
    IDENTIFIED BY 'Change-Me-Backup-2026';
GRANT SELECT, SHOW VIEW, TRIGGER, LOCK TABLES, EVENT
    ON bookstore.* TO 'bookstore_backup'@'localhost';

SHOW GRANTS FOR 'bookstore_backup'@'localhost';

Output

+-----------------+-----------+
| table_name      | row_count |
+-----------------+-----------+
| authors         |        10 |
| books           |        11 |
| categories      |         5 |
| book_categories |        25 |
| customers       |         8 |
| orders          |        12 |
| order_items     |        18 |
| employees       |        10 |
+-----------------+-----------+
+---------------------------------------------------------------------------------------------------------+
| Grants for bookstore_backup@localhost                                                                   |
+---------------------------------------------------------------------------------------------------------+
| GRANT USAGE ON *.* TO `bookstore_backup`@`localhost`                                                    |
| GRANT SELECT, LOCK TABLES, SHOW VIEW, EVENT, TRIGGER ON `bookstore`.* TO `bookstore_backup`@`localhost` |

The first table is printed by bookstore.sql itself when it finishes: a row count for every table. SELECT reads the rows, SHOW VIEW and TRIGGER let it read view and trigger definitions, EVENT covers --events, and LOCK TABLES is only used if you ever dump without --single-transaction. Replace the placeholder password with a real one of your own.

🛠️ Step 2: Take the backup with that account (5 min)

A backup account has no PROCESS privilege, so tell mysqldump to skip the tablespace and (on 9.7) masking-policy information it cannot read. Otherwise it prints "Access denied; you need (at least one of) the PROCESS privilege(s)" and "SELECT command denied ... when trying to dump masking policies" (the backup still completes, but noisy output hides real problems).

mysqldump -u bookstore_backup -p \
    --single-transaction --routines --events --set-gtid-purged=OFF \
    --no-tablespaces --skip-masking-policies \
    bookstore > bookstore_$(date +%F).sql

$(date +%F) puts today's date in the name, for example bookstore_2026-11-02.sql, so backups never overwrite each other. In PowerShell, use --result-file="bookstore_$(Get-Date -Format yyyy-MM-dd).sql". On MySQL 8.4, leave out --skip-masking-policies: its mysqldump does not have that option and stops with "unknown option".

🛠️ Step 3: Prove the backup restores (5 min)

Restore into bookstore_test as in the restore section (use root for this; the backup account cannot create databases), then compare the copy with the original:

mysql -u root -p -e "CREATE DATABASE bookstore_test"
mysql -u root -p bookstore_test < bookstore_2026-11-02.sql
mysql -u root -p -e "SELECT COUNT(*) FROM bookstore_test.orders; DROP DATABASE bookstore_test"

You should see 12 orders, the same as in bookstore. Write the date and the result in a restore_log.txt: that line is your evidence the backup works.

🛠️ Step 4: Export the monthly sales file (10 min)

The accountant wants one line per month with the number of orders and the revenue, as CSV with a header. Combine the GROUP BY you know with the header trick from this lesson, and save it as sales_export.sql:

SELECT month, orders, revenue
FROM (
    SELECT 0 AS part, 'month' AS month, 'orders' AS orders, 'revenue' AS revenue
    UNION ALL
    SELECT 1,
           DATE_FORMAT(o.order_date, '%Y-%m'),
           COUNT(DISTINCT o.id),
           SUM(oi.quantity * oi.price_at_time)
    FROM orders AS o
    JOIN order_items AS oi ON oi.order_id = o.id
    GROUP BY DATE_FORMAT(o.order_date, '%Y-%m')
) AS t
ORDER BY part, month
INTO OUTFILE '/var/lib/mysql-files/sales_by_month.csv'
    FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'
    LINES TERMINATED BY '\n';

🛠️ Step 5: Make the new-titles import repeatable (5 min)

Save the import from this lesson as import_new_books.sql, so next month's file goes through the same checks. This version adds any missing authors automatically and wraps the whole load in a transaction:

CREATE TABLE import_books (
    title VARCHAR(200), author VARCHAR(100), price DECIMAL(8, 2), pages INT, published DATE
);

LOAD DATA INFILE '/var/lib/mysql-files/new_books.csv'
INTO TABLE import_books
    FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'
    LINES TERMINATED BY '\n'
    IGNORE 1 LINES
    (title, author, price, @pages, @published)
SET pages = NULLIF(@pages, ''), published = STR_TO_DATE(@published, '%m/%d/%Y');

START TRANSACTION;

INSERT INTO authors (name)
SELECT DISTINCT i.author
FROM import_books AS i
LEFT JOIN authors AS a ON a.name = i.author
WHERE a.id IS NULL;

INSERT INTO books (title, author_id, price, pages, published)
SELECT i.title, a.id, i.price, i.pages, i.published
FROM import_books AS i
JOIN authors AS a ON a.name = i.author
WHERE NOT EXISTS (SELECT 1 FROM books AS b WHERE b.title = i.title)
ORDER BY i.title;

COMMIT;

DROP TABLE import_books;

SELECT COUNT(*) AS books, (SELECT COUNT(*) FROM authors) AS authors FROM books;

Output

+-------+---------+
| books | authors |
+-------+---------+
|    15 |      11 |
+-------+---------+

15 books and 11 authors. Run the script a second time and the counts stay the same: the NOT EXISTS check skips titles that are already in the store, so a file loaded twice does no harm. (A new author added this way has no birth year; fill it in by hand afterwards.)

🛠️ Step 6: Schedule the backup (5 min)

Store the backup account's login once, then write backup.sh:

mysql_config_editor set --login-path=backup --user=bookstore_backup --password
#!/bin/bash
# backup.sh: dated, compressed bookstore backup; keeps 30 days
set -euo pipefail
DIR="$HOME/mysql-course/backups"
mkdir -p "$DIR"
mysqldump --login-path=backup --single-transaction --routines --events \
    --set-gtid-purged=OFF --no-tablespaces --skip-masking-policies \
    bookstore | gzip > "$DIR/bookstore_$(date +%F).sql.gz"
find "$DIR" -name 'bookstore_*.sql.gz' -mtime +30 -delete

Make it executable with chmod +x backup.sh, run it once by hand, then schedule it with crontab -e and a line such as 0 2 * * * $HOME/mysql-course/backup.sh (every night at 2:00). A gzipped dump restores with gunzip < file.sql.gz | mysql -u root -p bookstore_test. On Windows, the same commands go in a .ps1 script run by Task Scheduler.

Export every customer's first name, last name, email and city to /var/lib/mysql-files/customers.csv, sorted by last name. Customers without a city must get an empty field, not \N. How many rows does the status line report?

🏋️ Exercise 2: Import New Customers, Skipping Known Emails

The marketing team sends this sign-up sheet. Two of the people are already customers. Load it into customers so that new people are added and existing customers are left exactly as they are. Then count the customers.

first_name,last_name,email,city
Irene,Lopez,irene@example.com,Boston
Alice,Johnson,alice@example.com,Boston
Jack,Nguyen,jack@example.com,
Bob,Smith,bob@example.com,Chicago
💡 Hint

email is UNIQUE. LOAD DATA ... IGNORE INTO TABLE skips rows that would duplicate a unique key. Jack's empty city should become NULL.

✅ Solution 
LOAD DATA INFILE '/var/lib/mysql-files/signups.csv'
IGNORE INTO TABLE customers
    FIELDS TERMINATED BY ','
    LINES TERMINATED BY '\n'
    IGNORE 1 LINES
    (first_name, last_name, email, @city)
SET city = NULLIF(@city, '');

SELECT id, first_name, last_name, city FROM customers WHERE id > 8 ORDER BY id;

Output

Records: 4  Deleted: 0  Skipped: 2  Warnings: 2

2 rows in set

Four records read, two skipped with a duplicate-key warning each, two added. Alice's city is still New York: IGNORE keeps the existing row. 🏋️ Exercise 3: Write the Backup Commands

Write the terminal commands for: (a) a structure-only backup of bookstore into bookstore_schema.sql; (b) a backup of only the orders and order_items tables; (c) a full backup that recreates the database by itself on an empty server, and the command that restores it. Assume MySQL 9.7 and the root account.

💡 Hint

Table names go after the database name. Which option adds CREATE DATABASE to the file? Keep --set-gtid-purged=OFF on 9.7.

✅ Solution 
# (a) structure only
mysqldump -u root -p --no-data --routines --events --set-gtid-purged=OFF \
    bookstore > bookstore_schema.sql

# (b) two tables
mysqldump -u root -p --single-transaction --set-gtid-purged=OFF \
    bookstore orders order_items > orders_backup.sql

# (c) self-contained backup, and its restore (no database name needed)
mysqldump -u root -p --single-transaction --routines --events --set-gtid-purged=OFF \
    --databases bookstore > bookstore_full.sql
mysql -u root -p < bookstore_full.sql

Restoring (b) into bookstore replaces just those two tables. Careful: orders rows point at customers, so a table-level backup is only consistent with the rest of the database at the moment it was taken.

🏋️ Exercise 4 (Stretch): A Round Trip That Proves Itself

Export order_items (all columns) to items.csv, create an empty copy of the table called items_copy, load the file into it, and prove with one query that the copy has the same number of rows and the same total revenue as the original.

💡 Hint

CREATE TABLE items_copy LIKE order_items; copies the structure. With no options, INTO OUTFILE and LOAD DATA both use tabs and \n, so they understand each other.

✅ Solution 
SELECT * FROM order_items INTO OUTFILE '/var/lib/mysql-files/items.csv';

CREATE TABLE items_copy LIKE order_items;
LOAD DATA INFILE '/var/lib/mysql-files/items.csv' INTO TABLE items_copy;

SELECT
    (SELECT COUNT(*) FROM order_items)                      AS rows_original,
    (SELECT COUNT(*) FROM items_copy)                       AS rows_copy,
    (SELECT SUM(quantity * price_at_time) FROM order_items) AS revenue_original,
    (SELECT SUM(quantity * price_at_time) FROM items_copy)  AS revenue_copy;

DROP TABLE items_copy;

Output

+---------------+-----------+------------------+--------------+
| rows_original | rows_copy | revenue_original | revenue_copy |
+---------------+-----------+------------------+--------------+
|            18 |        18 |           237.29 |       237.29 |
+---------------+-----------+------------------+--------------+

Both pairs match, so nothing was lost or changed on the way out and back in. The default format (tab-separated, no quotes, \N for NULL) is the safest choice when the file only travels between MySQL servers.

❓ Common Questions at This Stage

Can I restore a MySQL 9.7 dump on MySQL 8.4 or MariaDB?

Usually, for plain tables and data like the bookstore's: the file is ordinary SQL, and the versioned comments skip what an older server does not know. Problems appear with features the target lacks, for example the default collation utf8mb4_0900_ai_ci on MariaDB (the course database names utf8mb4_unicode_ci to avoid exactly this). Going from older to newer is the well-trodden direction; always test the restore.

How big can a dump get before mysqldump is the wrong tool?

There is no hard limit, but a logical dump is restored one INSERT at a time. Up to a few gigabytes it is fine; beyond that, restores take hours and MySQL Shell's parallel dump utilities or a physical backup tool become worth learning.

Should I just copy the data folder instead?

Only with the server stopped, and only to restore onto the same MySQL version. Copying the files of a running InnoDB server gives you a backup that may not start. That is why physical backup tools exist.

Is it safe to leave local_infile ON?

On your own development machine, yes. On a shared or production server, turn it on only while you need it, and only connect with --local-infile=1 to servers you trust: the setting exists because a malicious server could ask a client to send files.

🎓 Key Takeaways

  • mysqldump runs at the terminal and writes SQL that rebuilds a database; restore it by running that SQL with the mysql client
  • On MySQL 9.7 use --single-transaction --routines --events --set-gtid-purged=OFF; a backup account also needs --no-tablespaces (and --skip-masking-policies on 9.7)
  • A backup counts only after a test restore; a database dump does not contain user accounts
  • Server-side files (INTO OUTFILE, LOAD DATA INFILE) live in the secure_file_priv folder and need the FILE privilege
  • LOAD DATA LOCAL reads a file from your computer, needs local_infile on the server and --local-infile=1 on the client, and turns errors into warnings
  • Import through a staging table: user variables and SET convert values, a LEFT JOIN finds what is missing, a transaction makes the final copy all or nothing
