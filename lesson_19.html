🛡️ Lesson 7.4: User Management & Permissions

Every query in this course so far ran as root, the account that can do anything, including DROP DATABASE. That is fine on your own laptop and dangerous everywhere else. This lesson gives each person and program its own account with only the privileges it needs, so that a mistake, a bug or a stolen password can do as little damage as possible.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Create accounts as 'user'@'host' and explain how MySQL 9.7 stores their passwords (caching_sha2_password)
  • Grant and revoke privileges at the global, database, table and column level, and read SHOW GRANTS
  • Log in as a restricted user and recognize the access-denied errors (1142, 1143, 1044, 3118)
  • Group privileges into roles, assign them, and make them active with SET DEFAULT ROLE
  • Design least-privilege accounts for an application, a report and staff, and script them
  • ⏱️ Time 105 minutes
  • 📋 Prerequisites Lesson 7.3: JSON Columns
  • 🛠️ You will build team_access.sql, a rerunnable script that creates the bookstore team's roles and accounts
  • 🗄️ Database bookstore freshly loaded from bookstore.sql; you will need the root account (or another administrator) and a second terminal window

🛡️ Why Not Just Use root?

Picture the bookstore running on one shared root login:

  • A sales clerk runs DELETE FROM customers and forgets the WHERE. Every customer is gone.
  • The website has a bug that lets an attacker slip SQL into a search box. With root, the attacker can read every table, create accounts and drop databases.
  • A report dashboard only ever reads, but its password sits in a config file that half the company can see.

None of these needs root. Each needs an account with a short list of privileges. That idea has a name, the principle of least privilege: every account gets the minimum it needs to do its job, and nothing more.

graph TD R["root: administrators only"] --> A["programs: own narrow accounts"] R --> P["people: accounts plus roles"] A --> A1["website, report dashboard"] P --> P1["clerks, support, managers"]

🛑 Ground rules for this lesson

Practice on your own MySQL server, not on one that other people depend on. Never change root's own password or privileges while experimenting: if you lock yourself out, recovering takes a server restart with special options. Every example here creates its own demo accounts. The passwords are obvious placeholders like 'CHANGE-ME-reports-1'; real ones come from a password manager.

Start from a clean bookstore (the JSON lesson added columns to books):

SOURCE ~/mysql-course/bookstore.sql

👤 Accounts: 'user'@'host'

A MySQL account has two parts: a user name and the host the user connects from. 'shop_reports'@'localhost' and 'shop_reports'@'%' are two different accounts, with their own passwords and privileges.

Host partMatches connections fromTypical use
'localhost'The same machine (socket or 127.0.0.1)An app on the same server, you at the console
'10.0.0.25'One IP addressOne application server
'10.0.0.%'A range of addresses (% is a wildcard)An office or internal network
'%'AnywhereOnly with a firewall in front and TLS required

Create the first account, a read-only login for the monthly reports, and look it up in the mysql.user system table:

CREATE USER 'shop_reports'@'localhost' IDENTIFIED BY 'CHANGE-ME-reports-1';

SELECT user, host, plugin, account_locked
FROM mysql.user
WHERE user = 'shop_reports';

Output

+--------------+-----------+-----------------------+----------------+
| user         | host      | plugin                | account_locked |
+--------------+-----------+-----------------------+----------------+
| shop_reports | localhost | caching_sha2_password | N              |
+--------------+-----------+-----------------------+----------------+

The account exists and is not locked. The plugin column says how its password is checked: that is the next section.

💡 Leaving out the host

CREATE USER 'shop_reports' without @'...' means @'%': any host. Always write the host on purpose.

🔐 Passwords and caching_sha2_password

MySQL never stores the password itself. It stores a salted SHA-256 hash, produced by an authentication plugin. In MySQL 8.4 and 9.7, new accounts use caching_sha2_password unless you say otherwise. Every current client speaks it: the mysql client, MySQL Workbench, PHP's mysqlnd, and the current connectors for Python, Java, Node.js and .NET.

The old advice that no longer works

Many older tutorials say: "if your app cannot connect, switch the account to mysql_native_password". That plugin used a weak SHA-1 hash. MySQL 8.4 ships it disabled, and MySQL 9 removed it completely:

CREATE USER 'legacy_app'@'localhost' IDENTIFIED WITH mysql_native_password BY 'CHANGE-ME-legacy-1';

Error

ERROR 1524 (HY000): Plugin 'mysql_native_password' is not loaded

If an old program reports Authentication plugin 'caching_sha2_password' cannot be loaded or a similar message, the fix is to update the program's MySQL driver, not to weaken the server.

🐬 Version note

MySQL 8.4 gives the same ERROR 1524 by default. MariaDB (XAMPP, many shared hosts) is different: it never adopted caching_sha2_password, its new accounts use mysql_native_password, and its stronger alternative is ed25519, set with IDENTIFIED VIA ed25519. CREATE USER, GRANT, REVOKE and ACCOUNT LOCK work as written, but roles and some account options differ: one role per GRANT, SET DEFAULT ROLE role_name FOR 'user'@'host' (one default role, no ALL), no SHOW GRANTS ... USING, no mysql.default_roles table, no account_locked column in mysql.user, and no FAILED_LOGIN_ATTEMPTS. A GRANT to a missing account fails with error 1133 instead of 1410.

CREATE USER 'shop_reports'@'localhost' IDENTIFIED BY 'CHANGE-ME-reports-1';

SELECT user, host, plugin FROM mysql.user WHERE user = 'shop_reports';

Output on MariaDB

+--------------+-----------+-----------------------+
| User         | Host      | plugin                |
+--------------+-----------+-----------------------+
| shop_reports | localhost | mysql_native_password |
+--------------+-----------+-----------------------+

🎁 GRANT: Giving Privileges

A new account can log in and do almost nothing else. SHOW GRANTS lists what an account may do:

SHOW GRANTS FOR 'shop_reports'@'localhost';

Output

+--------------------------------------------------+
| Grants for shop_reports@localhost                |
+--------------------------------------------------+
| GRANT USAGE ON *.* TO `shop_reports`@`localhost` |
+--------------------------------------------------+

USAGE means "no privileges": the account exists and may connect, that is all. Now give it read access to every table in bookstore:

GRANT SELECT ON bookstore.* TO 'shop_reports'@'localhost';

SHOW GRANTS FOR 'shop_reports'@'localhost';

Output

+-------------------------------------------------------------+
| Grants for shop_reports@localhost                           |
+-------------------------------------------------------------+
| GRANT USAGE ON *.* TO `shop_reports`@`localhost`            |
| GRANT SELECT ON `bookstore`.* TO `shop_reports`@`localhost` |
+-------------------------------------------------------------+

The pattern is always GRANT what ON where TO whom. The change takes effect immediately; you do not need FLUSH PRIVILEGES after GRANT, REVOKE or CREATE USER (old tutorials add it out of habit).

PrivilegeAllows
SELECTReading rows
INSERT, UPDATE, DELETEAdding, changing, removing rows
CREATE, ALTER, DROP, INDEXCreating, changing and removing tables and indexes
CREATE VIEW, SHOW VIEWCreating views, reading their definitions
EXECUTECalling stored procedures and functions
CREATE USER, GRANT OPTIONManaging other accounts (administrators only)
ALL PRIVILEGESEverything at that level except GRANT OPTION

An account for the website

The online store reads the catalog and records customers and orders. It never changes prices or deletes anything. Grant exactly that, table by table:

CREATE USER 'shop_app'@'localhost' IDENTIFIED BY 'CHANGE-ME-app-1';

GRANT SELECT ON bookstore.* TO 'shop_app'@'localhost';
GRANT INSERT, UPDATE ON bookstore.customers   TO 'shop_app'@'localhost';
GRANT INSERT         ON bookstore.orders      TO 'shop_app'@'localhost';
GRANT INSERT         ON bookstore.order_items TO 'shop_app'@'localhost';

SHOW GRANTS FOR 'shop_app'@'localhost';

Output

+---------------------------------------------------------------------------+
| Grants for shop_app@localhost                                             |
+---------------------------------------------------------------------------+
| GRANT USAGE ON *.* TO `shop_app`@`localhost`                              |
| GRANT SELECT ON `bookstore`.* TO `shop_app`@`localhost`                   |
| GRANT INSERT, UPDATE ON `bookstore`.`customers` TO `shop_app`@`localhost` |
| GRANT INSERT ON `bookstore`.`order_items` TO `shop_app`@`localhost`       |
| GRANT INSERT ON `bookstore`.`orders` TO `shop_app`@`localhost`            |
+---------------------------------------------------------------------------+

If the website is ever compromised, the attacker can read the catalog and add orders, but cannot change a price, delete a customer or drop a table.

⚠️ WITH GRANT OPTION

Adding WITH GRANT OPTION to a GRANT lets that account pass its privileges on to others. Give it only to real administrators, never to an application.

🎚️ Privilege Levels

The ON part decides how far a privilege reaches:

graph TD G["Global: ON *.*"] --> D["Database: ON bookstore.*"] D --> T["Table: ON bookstore.books"] T --> C["Column: SELECT (email)"] D --> P["Routine: ON PROCEDURE ..."]
LevelSyntaxReaches
GlobalON *.*Every database on the server, now and in future (administrators only)
DatabaseON bookstore.*Every table in one database, including tables created later
TableON bookstore.ordersOne table or view
ColumnSELECT (id, email) ON bookstore.customersSome columns of one table
RoutineEXECUTE ON PROCEDURE bookstore.nameOne stored procedure or function

Column-level privileges

The support desk answers customer emails. It may see a customer's name and email and fix a mistyped email, but it has no business reading anything else:

CREATE USER 'support_desk'@'localhost' IDENTIFIED BY 'CHANGE-ME-support-1';

GRANT SELECT (id, first_name, last_name, email), UPDATE (email)
    ON bookstore.customers TO 'support_desk'@'localhost';

SHOW GRANTS FOR 'support_desk'@'localhost';

Output

+------------------------------------------------------------------------------------------------------------------------------------+
| Grants for support_desk@localhost                                                                                                  |
+------------------------------------------------------------------------------------------------------------------------------------+
| GRANT USAGE ON *.* TO `support_desk`@`localhost`                                                                                   |
| GRANT SELECT (`email`, `first_name`, `id`, `last_name`), UPDATE (`email`) ON `bookstore`.`customers` TO `support_desk`@`localhost` |
+------------------------------------------------------------------------------------------------------------------------------------+

💡 A view is often simpler

Column lists get long and are easy to forget when a table changes. The alternative from Lesson 6.2: create a view with exactly the columns (and rows) someone may see, and grant SELECT on the view only. Exercise 3 does this.

🧪 Testing as the User

A grant you have not tested is a guess. Open a second terminal and log in as the account (your root session stays open in the first one):

mysql -u shop_reports -p bookstore

Type the password when asked; it is not shown and never belongs on the command line, where it would land in your shell history. Then check who you are and try a read and a delete:

SELECT CURRENT_USER();
SELECT COUNT(*) AS books FROM books;
DELETE FROM books WHERE id = 11;

Output (as shop_reports)

+------------------------+
| CURRENT_USER()         |
+------------------------+
| shop_reports@localhost |
+------------------------+
+-------+
| books |
+-------+
|    11 |
+-------+
ERROR 1142 (42000): DELETE command denied to user 'shop_reports'@'localhost' for table 'books'

Reading works; deleting is refused with error 1142, and Animal Farm is safe. Exit and log in as support_desk:

SELECT first_name, email FROM customers WHERE id = 1;
SELECT first_name, city FROM customers WHERE id = 1;
SELECT * FROM customers WHERE id = 1;
SELECT * FROM orders;

Output (as support_desk)

+------------+-------------------+
| first_name | email             |
+------------+-------------------+
| Alice      | alice@example.com |
+------------+-------------------+
ERROR 1143 (42000): SELECT command denied to user 'support_desk'@'localhost' for column 'city' in table 'customers'
ERROR 1142 (42000): SELECT command denied to user 'support_desk'@'localhost' for table 'customers'
ERROR 1142 (42000): SELECT command denied to user 'support_desk'@'localhost' for table 'orders'

Error 1143 is the column-level cousin of 1142: it names the column that was never granted. SELECT * is refused for the whole table (1142), because the account may not read every column; name the allowed columns instead. Type EXIT to leave each test session.

✅ Test both directions

For every account, run one thing it must be able to do and one thing it must not. Both results matter: a grant that is too small breaks the app, one that is too big is a silent security hole.

↩️ REVOKE, ALTER USER and DROP USER

Taking privileges away

REVOKE mirrors GRANT, with FROM instead of TO. The website should not update customers after all (a separate account will handle profile changes):

REVOKE UPDATE ON bookstore.customers FROM 'shop_app'@'localhost';

SHOW GRANTS FOR 'shop_app'@'localhost';

Output

+---------------------------------------------------------------------+
| Grants for shop_app@localhost                                       |
+---------------------------------------------------------------------+
| GRANT USAGE ON *.* TO `shop_app`@`localhost`                        |
| GRANT SELECT ON `bookstore`.* TO `shop_app`@`localhost`             |
| GRANT INSERT ON `bookstore`.`customers` TO `shop_app`@`localhost`   |
| GRANT INSERT ON `bookstore`.`order_items` TO `shop_app`@`localhost` |
| GRANT INSERT ON `bookstore`.`orders` TO `shop_app`@`localhost`      |
+---------------------------------------------------------------------+

Revoke at the same level you granted: UPDATE was granted on the customers table, so it is revoked on that table. The account itself stays; a session that is already connected keeps its current database open but is checked against the new privileges on its next statement.

Changing an account

ALTER USER changes the password and the account's rules. A nightly batch job gets an account that expires its password every 90 days and locks itself for a day after three wrong passwords:

CREATE USER 'night_batch'@'localhost' IDENTIFIED BY 'CHANGE-ME-batch-1'
    PASSWORD EXPIRE INTERVAL 90 DAY
    FAILED_LOGIN_ATTEMPTS 3 PASSWORD_LOCK_TIME 1;

ALTER USER 'night_batch'@'localhost' IDENTIFIED BY 'CHANGE-ME-batch-2';
ALTER USER 'night_batch'@'localhost' ACCOUNT LOCK;

SELECT user, host, password_lifetime, account_locked
FROM mysql.user
WHERE user = 'night_batch';

Output

+-------------+-----------+-------------------+----------------+
| user        | host      | password_lifetime | account_locked |
+-------------+-----------+-------------------+----------------+
| night_batch | localhost |                90 | Y              |
+-------------+-----------+-------------------+----------------+

Locking is how you disable an account without losing its grants (for a staff member on leave, or a job you are about to retire). A login attempt to a locked account fails before the password even matters:

mysql -u night_batch -p

Output (logging in to the locked account)

ERROR 3118 (HY000): Access denied for user 'night_batch'@'localhost'. Account is locked.

ALTER USER ... ACCOUNT UNLOCK opens it again.

🛑 Change other accounts, not your own

ALTER USER CURRENT_USER() IDENTIFIED BY ... changes the password of the account you are logged in with. As root on a practice server, that is the classic way to lock yourself out. Practice password changes on demo accounts like night_batch.

Renaming and removing accounts

RENAME USER 'night_batch'@'localhost' TO 'nightly_import'@'localhost';
DROP USER 'nightly_import'@'localhost';
DROP USER IF EXISTS 'nightly_import'@'localhost';

SELECT user FROM mysql.user WHERE user LIKE 'night%';

Output

Empty set

DROP USER removes the account and all its grants in one step. IF EXISTS turns "no such account" into a warning instead of error 1396, which is what you want in a script that may run twice.

🎭 Roles

The bookstore has several sales clerks who all need the same privileges. Granting them one by one to every clerk means changing every account whenever the job changes. A role is a named bundle of privileges: grant privileges to the role once, then grant the role to people.

graph TD P["SELECT, INSERT on orders..."] --> R["role: bookstore_sales"] R --> T["tom@localhost"] R --> L["lena@localhost"] 
CREATE ROLE 'bookstore_reader', 'bookstore_sales';

GRANT SELECT ON bookstore.* TO 'bookstore_reader';
GRANT INSERT, UPDATE ON bookstore.orders      TO 'bookstore_sales';
GRANT INSERT, UPDATE ON bookstore.order_items TO 'bookstore_sales';

CREATE USER 'tom'@'localhost'  IDENTIFIED BY 'CHANGE-ME-tom-1';
CREATE USER 'lena'@'localhost' IDENTIFIED BY 'CHANGE-ME-lena-1';

GRANT 'bookstore_reader', 'bookstore_sales' TO 'tom'@'localhost', 'lena'@'localhost';

SHOW GRANTS FOR 'tom'@'localhost';

Output

+-------------------------------------------------------------------------+
| Grants for tom@localhost                                                |
+-------------------------------------------------------------------------+
| GRANT USAGE ON *.* TO `tom`@`localhost`                                 |
| GRANT `bookstore_reader`@`%`,`bookstore_sales`@`%` TO `tom`@`localhost` |
+-------------------------------------------------------------------------+

Tom's own grants list only the roles. To see what they add up to, ask with USING:

SHOW GRANTS FOR 'tom'@'localhost' USING 'bookstore_reader', 'bookstore_sales';

Output

+-------------------------------------------------------------------------+
| Grants for tom@localhost                                                |
+-------------------------------------------------------------------------+
| GRANT USAGE ON *.* TO `tom`@`localhost`                                 |
| GRANT SELECT ON `bookstore`.* TO `tom`@`localhost`                      |
| GRANT INSERT, UPDATE ON `bookstore`.`order_items` TO `tom`@`localhost`  |
| GRANT INSERT, UPDATE ON `bookstore`.`orders` TO `tom`@`localhost`       |
| GRANT `bookstore_reader`@`%`,`bookstore_sales`@`%` TO `tom`@`localhost` |
+-------------------------------------------------------------------------+

The step everybody forgets: activating the role

A granted role is not switched on automatically. Until it is active in Tom's session, Tom has nothing but USAGE. If you stop here, mysql -u tom -p bookstore does not even get past the login (ERROR 1044 (42000): Access denied for user 'tom'@'localhost' to database 'bookstore'). Logged in with mysql -u tom -p, without a database, Tom sees this:

SELECT CURRENT_ROLE();
SELECT COUNT(*) FROM bookstore.books;

Output (as tom, before SET DEFAULT ROLE)

+----------------+
| CURRENT_ROLE() |
+----------------+
| NONE           |
+----------------+
ERROR 1142 (42000): SELECT command denied to user 'tom'@'localhost' for table 'books'

Tom could type SET ROLE ALL; in every session, but the real fix is to make the roles default roles, which are activated at every login:

SET DEFAULT ROLE ALL TO 'tom'@'localhost', 'lena'@'localhost';

SELECT * FROM mysql.default_roles ORDER BY user, default_role_user;

Output

+-----------+------+-------------------+-------------------+
| HOST      | USER | DEFAULT_ROLE_HOST | DEFAULT_ROLE_USER |
+-----------+------+-------------------+-------------------+
| localhost | lena | %                 | bookstore_reader  |
| localhost | lena | %                 | bookstore_sales   |
| localhost | tom  | %                 | bookstore_reader  |
| localhost | tom  | %                 | bookstore_sales   |
+-----------+------+-------------------+-------------------+

When Tom logs in now, CURRENT_ROLE() shows `bookstore_reader`@`%`,`bookstore_sales`@`%` and the SELECT works. (A role, like a user, has a host part; for roles it is % unless you choose one.)

✅ Change the role, everyone follows

When the clerks also need to record new customers, one GRANT INSERT ON bookstore.customers TO 'bookstore_sales'; updates Tom, Lena and every future clerk at once. When Lena moves to another job, REVOKE 'bookstore_sales' FROM 'lena'@'localhost'; removes the whole bundle.

🔒 The Principle of Least Privilege

Here is the bookstore's account plan, which you will build in the project:

WhoNeedsGets
WebsiteRead the catalog, record ordersSELECT on the catalog tables, INSERT on orders
Report dashboardRead everythingThe reader role
Inventory staffChange prices and stockReader role + UPDATE (price, in_stock) on books
ManagerEverything in the bookstoreALL on bookstore.*, nothing global
AdministratorRun the serverA personal admin account, not a shared root

🔑 Least-privilege checklist

  • One account per application and per person; never share logins
  • Applications never connect as root, and never get DROP, ALTER or GRANT OPTION
  • Grant at the narrowest level that works: column, then table, then database; global only for administrators
  • Restrict the host; when an account must accept remote connections, add REQUIRE SSL
  • Apps send user input as query parameters (placeholders such as ?), never pasted into the SQL text: least privilege limits the damage of SQL injection, parameters prevent it
  • Review SHOW GRANTS regularly and drop accounts nobody uses

⚠️ Common Mistakes

1. Granting to an account that does not exist

GRANT SELECT ON bookstore.* TO 'reports'@'localhost';

Error

ERROR 1410 (42000): You are not allowed to create a user with GRANT

What it means: very old MySQL versions created the account on the fly in GRANT. Modern MySQL insists on CREATE USER first, so a typo in the name cannot silently create a new, passwordless account. Fix: check the spelling (here the account is shop_reports), or run CREATE USER first.

2. The right user, the wrong host

SHOW GRANTS FOR 'shop_reports'@'%';

Error

ERROR 1141 (42000): There is no such grant defined for user 'shop_reports' on host '%'

What it means: 'shop_reports'@'%' is a different account from 'shop_reports'@'localhost', and it does not exist. The same mismatch causes "Access denied" at login when a program connects over the network (host 10.0.0.25) to an account created for 'localhost'. Fix: list the real accounts with SELECT user, host FROM mysql.user; and use the exact pair.

3. Creating an account twice

CREATE USER 'shop_reports'@'localhost' IDENTIFIED BY 'CHANGE-ME-reports-1';

Error

ERROR 1396 (HY000): Operation CREATE USER failed for 'shop_reports'@'localhost' (User account already exists)

What it means: setup scripts often fail on their second run. Fix: CREATE USER IF NOT EXISTS, or, when the script should rebuild the account from scratch, DROP USER IF EXISTS first.

4. Revoking at a different level than you granted

REVOKE SELECT ON bookstore.books FROM 'shop_reports'@'localhost';

Error

ERROR 1147 (42000): There is no such grant defined for user 'shop_reports' on host 'localhost' on table 'books'

What it means: shop_reports has SELECT on bookstore.* (database level). There is no table-level grant on books to take away, and MySQL cannot cut one table out of a database-level grant. Fix: revoke at the level shown by SHOW GRANTS; to hide one table, grant table by table instead (or through views).

5. A role that was granted but never activated (silent)

CREATE ROLE 'bookstore_inventory';
GRANT UPDATE (price, in_stock) ON bookstore.books TO 'bookstore_inventory';
CREATE USER 'marcus'@'localhost' IDENTIFIED BY 'CHANGE-ME-marcus-1';
GRANT 'bookstore_reader', 'bookstore_inventory' TO 'marcus'@'localhost';

SELECT * FROM mysql.default_roles WHERE user = 'marcus';

Output

Empty set

What it means: every statement succeeded and SHOW GRANTS lists both roles, but Marcus has no default roles, so at login he can do nothing and gets error 1142 on his first query, exactly like Tom before. Fix: SET DEFAULT ROLE ALL TO 'marcus'@'localhost'; right after granting roles. (A server-wide alternative is the setting activate_all_roles_on_login = ON.)

SET DEFAULT ROLE ALL TO 'marcus'@'localhost';

🛠️ Project: Accounts for the Bookstore Team

You will write team_access.sql, a script that creates the bookstore team's roles and accounts from the plan in The Principle of Least Privilege, and that can run again at any time without errors. It uses its own team_ names so it does not collide with this lesson's demo accounts. Allow about 40 minutes.

🛠️ Step 1: Start from a clean slate (5 min)

Create team_access.sql in your mysql-course folder. Its first lines remove everything it is about to create, so a second run rebuilds instead of failing with error 1396. Dropping a role also removes it from every account that had it.

-- team_access.sql: roles and accounts for the bookstore team
DROP USER IF EXISTS 'team_web'@'localhost', 'team_dashboard'@'localhost',
                    'team_sofia'@'localhost', 'team_maria'@'localhost';
DROP ROLE IF EXISTS 'team_reader', 'team_inventory', 'team_manager';

🛠️ Step 2: The roles (5 min)

Three bundles: read everything, change prices and stock, and manage the whole bookstore database.

-- 2. Roles
CREATE ROLE 'team_reader', 'team_inventory', 'team_manager';
GRANT SELECT ON bookstore.* TO 'team_reader';
GRANT UPDATE (price, in_stock) ON bookstore.books TO 'team_inventory';
GRANT ALL PRIVILEGES ON bookstore.* TO 'team_manager';

SHOW GRANTS FOR 'team_inventory';

Output

+-----------------------------------------------------------------------------------+
| Grants for team_inventory@%                                                       |
+-----------------------------------------------------------------------------------+
| GRANT USAGE ON *.* TO `team_inventory`@`%`                                        |
| GRANT UPDATE (`in_stock`, `price`) ON `bookstore`.`books` TO `team_inventory`@`%` |
+-----------------------------------------------------------------------------------+

🛠️ Step 3: The website account (5 min)

The website reads only the catalog tables (not employees, not other customers' orders) and records orders. Applications get direct grants rather than roles, so their privileges are always active and easy to read.

-- 3. The website
CREATE USER 'team_web'@'localhost' IDENTIFIED BY 'CHANGE-ME-web-1';
GRANT SELECT ON bookstore.books           TO 'team_web'@'localhost';
GRANT SELECT ON bookstore.authors         TO 'team_web'@'localhost';
GRANT SELECT ON bookstore.categories      TO 'team_web'@'localhost';
GRANT SELECT ON bookstore.book_categories TO 'team_web'@'localhost';
GRANT INSERT ON bookstore.orders          TO 'team_web'@'localhost';
GRANT INSERT ON bookstore.order_items     TO 'team_web'@'localhost';

SHOW GRANTS FOR 'team_web'@'localhost';

Output

+-------------------------------------------------------------------------+
| Grants for team_web@localhost                                           |
+-------------------------------------------------------------------------+
| GRANT USAGE ON *.* TO `team_web`@`localhost`                            |
| GRANT SELECT ON `bookstore`.`authors` TO `team_web`@`localhost`         |
| GRANT SELECT ON `bookstore`.`book_categories` TO `team_web`@`localhost` |
| GRANT SELECT ON `bookstore`.`books` TO `team_web`@`localhost`           |
| GRANT SELECT ON `bookstore`.`categories` TO `team_web`@`localhost`      |
| GRANT INSERT ON `bookstore`.`order_items` TO `team_web`@`localhost`     |
| GRANT INSERT ON `bookstore`.`orders` TO `team_web`@`localhost`          |

🛠️ Step 4: People and the dashboard (10 min)

Sofia works in inventory, Maria manages the store, and the dashboard only reads. Grant the roles, then make them default roles in the same script.

-- 4. People and the dashboard
CREATE USER 'team_dashboard'@'localhost' IDENTIFIED BY 'CHANGE-ME-dash-1';
CREATE USER 'team_sofia'@'localhost'     IDENTIFIED BY 'CHANGE-ME-sofia-1';
CREATE USER 'team_maria'@'localhost'     IDENTIFIED BY 'CHANGE-ME-maria-1';

GRANT 'team_reader'                   TO 'team_dashboard'@'localhost';
GRANT 'team_reader', 'team_inventory' TO 'team_sofia'@'localhost';
GRANT 'team_manager'                  TO 'team_maria'@'localhost';

SHOW GRANTS FOR 'team_sofia'@'localhost' USING 'team_reader', 'team_inventory';

Output

+---------------------------------------------------------------------------------------+
| Grants for team_sofia@localhost                                                       |
+---------------------------------------------------------------------------------------+
| GRANT USAGE ON *.* TO `team_sofia`@`localhost`                                        |
| GRANT SELECT ON `bookstore`.* TO `team_sofia`@`localhost`                             |
| GRANT UPDATE (`in_stock`, `price`) ON `bookstore`.`books` TO `team_sofia`@`localhost` |

🛠️ Step 5: An inventory of the accounts (5 min)

End the script with a check that lists every team_ account and role, its plugin and its default roles. Roles are stored in mysql.user too, as locked accounts that cannot log in.

-- 5. What the script created
SELECT u.user, u.host, u.plugin, u.account_locked,
       GROUP_CONCAT(d.default_role_user ORDER BY d.default_role_user) AS default_roles
FROM mysql.user AS u
LEFT JOIN mysql.default_roles AS d ON d.user = u.user AND d.host = u.host
WHERE u.user LIKE 'team%'
GROUP BY u.user, u.host, u.plugin, u.account_locked
ORDER BY u.account_locked, u.user;

🏋️ Exercise 4 (Stretch): A Remote, Rate-Limited API Account

A partner's server at 203.0.113.10 may read books and authors. Create 'partner_api'@'203.0.113.10' that must use TLS and may run at most 1000 queries per hour. Grant the two SELECTs, then read the TLS and limit settings back from mysql.user.

✅ Solution 
CREATE USER 'partner_api'@'203.0.113.10' IDENTIFIED BY 'CHANGE-ME-partner-1'

    WITH MAX_QUERIES_PER_HOUR 1000;
GRANT SELECT ON bookstore.books   TO 'partner_api'@'203.0.113.10';
GRANT SELECT ON bookstore.authors TO 'partner_api'@'203.0.113.10';

| partner_api | 203.0.113.10 | ANY      |          1000 |

❓ Common Questions at This Stage

My CREATE USER fails with error 1819 about the password policy. Why?

Your server has the validate_password component installed (some installers enable it). It rejects passwords that are too short or too simple: "Your password does not satisfy the current policy requirements". Use a longer password with mixed case, digits and symbols. Do not uninstall the component to make a weak password fit.

Do I need FLUSH PRIVILEGES?

Not after CREATE USER, GRANT, REVOKE, ALTER USER or DROP USER: they update the server's in-memory privileges immediately. It is only needed if someone edits the mysql system tables directly with INSERT or UPDATE, which you should not do.

I created 'app'@'%', but logging in from the server itself says access denied. Why?

When several accounts could match, MySQL picks the most specific host first. If an anonymous or other localhost account exists, it can win over %. Check with SELECT user, host FROM mysql.user;, and inside a session compare USER() (who you said you are) with CURRENT_USER() (the account MySQL matched).

Where does an application keep its database password?

Outside the source code: in an environment variable, a configuration file that is not committed to version control, or a secrets manager. Each environment (development, production) gets its own account and password, so a leaked development password opens nothing important.

📝 Lesson Summary

🎓 Key Takeaways

  • An account is 'user'@'host'; the same name with another host is another account
  • New accounts use caching_sha2_password; mysql_native_password is gone in MySQL 9 (error 1524) and disabled in 8.4
  • New accounts have only USAGE; GRANT what ON where TO whom adds privileges, REVOKE ... FROM removes them at the same level
  • Levels: global *.*, database db.*, table, column, routine; grant at the narrowest level that works
  • Test every account in a second session: 1142 (table), 1143 (column), 3118 (locked) are the refusals you should see
  • Roles bundle privileges; they work only after SET DEFAULT ROLE (or SET ROLE)
  • Applications get their own narrow accounts and use query parameters; nobody shares root
