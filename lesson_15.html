🪟 Lesson 6.2: Views

You can now write five-table joins with grouping and filters. Do you really want to retype one every time the manager asks for the same report? A view saves a query under a name, so anyone can get the report with a one-line SELECT, as if it were a table. Views also let you show people exactly the rows and columns they need, and nothing else.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Explain what a view stores (a query, not data) and read the definition MySQL saves
  • Create, query, replace and drop views, including views over joins and aggregates
  • Predict whether a view is updatable, and protect it with WITH CHECK OPTION
  • Use a view to hide sensitive columns, and grant access to the view alone
  • Recognize and fix the errors views raise (1050, 1288, 1356, 1369, 1393)

🪟 What Is a View?

A view is a named, saved SELECT. It holds no rows of its own. Every time you query it, MySQL runs the saved query against the real tables (the base tables) and hands you the result as if it came from a table. Think of a window in a wall: it shows a particular part of the room behind it, and when the room changes, the view through the window changes too.

graph TD U["SELECT * FROM v_order_details"] --> V["view: the saved SELECT"] V --> O["orders + customers"] V --> B["order_items + books + authors"] O --> R["result rows, computed now"] B --> R
TableView
StoresRowsOnly the query definition
Query with SELECTYesYes, exactly like a table
Always currentIt is the dataYes: recomputed on every query
INSERT / UPDATE / DELETEYesSometimes (simple views only)
Own indexesYesNo: it uses the base tables' indexes

🧪 Your First View

CREATE VIEW view_name AS
SELECT ...;

The marketing team keeps asking for the Chicago customers. Save that question once:

CREATE VIEW v_chicago_customers AS
SELECT id, first_name, last_name, email
FROM customers
WHERE city = 'Chicago';

SELECT * FROM v_chicago_customers ORDER BY id;

Output

+----+------------+-----------+-------------------+
| id | first_name | last_name | email             |
+----+------------+-----------+-------------------+
|  2 | Bob        | Smith     | bob@example.com   |
|  7 | Grace      | Wilson    | grace@example.com |
+----+------------+-----------+-------------------+

From now on nobody needs to remember the WHERE city = 'Chicago': it is baked into the view. You can still add your own conditions, sorting and limits on top, and join the view to other tables:

SELECT v.first_name, o.id AS order_id, o.order_date
FROM v_chicago_customers AS v
JOIN orders AS o ON o.customer_id = v.id
ORDER BY o.order_date;

Output

+------------+----------+------------+
| first_name | order_id | order_date |
+------------+----------+------------+
| Grace      |        6 | 2026-02-14 |
| Bob        |        3 | 2026-03-10 |
| Bob        |        7 | 2026-03-28 |
| Grace      |       11 | 2026-05-19 |
+------------+----------+------------+

Views live next to your tables

A view shares the table namespace: no table and view in one database can have the same name. That is why this course starts every view name with v_, so you can tell them apart at a glance. SHOW FULL TABLES marks which is which:

SHOW FULL TABLES WHERE Table_type = 'VIEW';

Output

+---------------------+------------+
| Tables_in_bookstore | Table_type |
+---------------------+------------+
| v_chicago_customers | VIEW       |
+---------------------+------------+

What MySQL actually saves

SHOW CREATE VIEW v_chicago_customers\G

Output

*************************** 1. row ***************************
                View: v_chicago_customers
         Create View: CREATE ALGORITHM=UNDEFINED DEFINER=`root`@`localhost` SQL SECURITY DEFINER VIEW `v_chicago_customers` AS select `customers`.`id` AS `id`,`customers`.`first_name` AS `first_name`,`customers`.`last_name` AS `last_name`,`customers`.`email` AS `email` from `customers` where (`customers`.`city` = 'Chicago')
character_set_client: utf8mb4
collation_connection: utf8mb4_0900_ai_ci

MySQL stored a rewritten copy of your query: every name in backticks and qualified with its table, every column given an explicit alias. Three settings were filled in for you:

  • ALGORITHM=UNDEFINED: MySQL decides how to run the view each time (more under Performance).
  • DEFINER=`root`@`localhost`: the account that created the view. Yours shows whatever account you are logged in as.
  • SQL SECURITY DEFINER: the view reads the base tables with the definer's privileges, not the caller's. That is what makes the security trick later in this lesson work.

🔗 Views over Joins

This is where views pay off: a long join written once and given a short name. Here is every line of every order, with the customer, the book and its author:

CREATE VIEW v_order_details AS
SELECT
    o.id                                   AS order_id,
    o.order_date,
    CONCAT(c.first_name, ' ', c.last_name) AS customer,
    b.title,
    a.name                                 AS author,
    oi.quantity,
    oi.price_at_time,
    oi.quantity * oi.price_at_time         AS line_total
FROM orders AS o
JOIN customers   AS c  ON c.id = o.customer_id
JOIN order_items AS oi ON oi.order_id = o.id
JOIN books       AS b  ON b.id = oi.book_id
JOIN authors     AS a  ON a.id = b.author_id;

SELECT * FROM v_order_details
WHERE customer = 'Alice Johnson'
ORDER BY order_date, title;

Output

+----------+------------+---------------+---------------------+----------------+----------+---------------+------------+
| order_id | order_date | customer      | title               | author         | quantity | price_at_time | line_total |
+----------+------------+---------------+---------------------+----------------+----------+---------------+------------+
|        1 | 2026-01-15 | Alice Johnson | 1984                | George Orwell  |        2 |          9.99 |      19.98 |
|        1 | 2026-01-15 | Alice Johnson | Dune                | Frank Herbert  |        1 |         14.99 |      14.99 |
|        2 | 2026-02-20 | Alice Johnson | Pride and Prejudice | Jane Austen    |        1 |          7.99 |       7.99 |
|        8 | 2026-04-05 | Alice Johnson | Lord of the Rings   | J.R.R. Tolkien |        1 |         15.99 |      15.99 |
+----------+------------+---------------+---------------------+----------------+----------+---------------+------------+

The line total uses price_at_time, the price the customer actually paid, not books.price, which can change after the sale. In this database the two are equal, but a report built on today's price would silently rewrite history the first time a price changes.

SELECT author, SUM(quantity) AS copies, SUM(line_total) AS revenue
FROM v_order_details
GROUP BY author
ORDER BY revenue DESC, author;

📊 Views with Aggregates

A view can hold GROUP BY, aggregates, LEFT JOINs and COALESCE, everything a reporting query needs. One row per customer, including the two who never ordered:

CREATE VIEW v_customer_summary AS
SELECT
    c.id                                       AS customer_id,
    CONCAT(c.first_name, ' ', c.last_name)     AS customer,
    COUNT(DISTINCT o.id)                       AS orders,
    COALESCE(SUM(oi.quantity), 0)              AS items,
    COALESCE(SUM(oi.quantity * oi.price_at_time), 0) AS total_spent
FROM customers AS c
LEFT JOIN orders      AS o  ON o.customer_id = c.id
LEFT JOIN order_items AS oi ON oi.order_id = o.id
GROUP BY c.id, c.first_name, c.last_name;

SELECT * FROM v_customer_summary ORDER BY total_spent DESC, customer;

Output

+-------------+----------------+--------+-------+-------------+
| customer_id | customer       | orders | items | total_spent |
+-------------+----------------+--------+-------+-------------+
|           1 | Alice Johnson  |      3 |     5 |       58.95 |
|           4 | Dave Brown     |      2 |     4 |       45.96 |
|           6 | Frank Miller   |      2 |     4 |       41.96 |
|           7 | Grace Wilson   |      2 |     3 |       33.97 |
|           2 | Bob Smith      |      2 |     3 |       33.47 |
|           5 | Eve Davis      |      1 |     2 |       22.98 |
|           3 | Carol Williams |      0 |     0 |        0.00 |
|           8 | Hank Taylor    |      0 |     0 |        0.00 |
+-------------+----------------+--------+-------+-------------+

Two details earn their place. COUNT(DISTINCT o.id): after joining the items, an order with two lines appears twice, and a plain COUNT(o.id) would count it twice. COALESCE(..., 0): Carol and Hank have no items, so their sums are NULL, and a report should say 0.

A manager who has never written a join can now ask "who spent more than $40?" in one line:

SELECT customer, total_spent
FROM v_customer_summary
WHERE total_spent > 40
ORDER BY total_spent DESC;

Output

+---------------+-------------+
| customer      | total_spent |
+---------------+-------------+
| Alice Johnson |       58.95 |
| Dave Brown    |       45.96 |
| Frank Miller  |       41.96 |
+---------------+-------------+

Monthly revenue

CREATE VIEW v_monthly_revenue AS
SELECT
    DATE_FORMAT(o.order_date, '%Y-%m')   AS month,
    COUNT(DISTINCT o.id)                 AS orders,
    SUM(oi.quantity)                     AS items,
    SUM(oi.quantity * oi.price_at_time)  AS revenue
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.id
GROUP BY DATE_FORMAT(o.order_date, '%Y-%m');

SELECT * FROM v_monthly_revenue ORDER BY month;

Output

+---------+--------+-------+---------+
| month   | orders | items | revenue |
+---------+--------+-------+---------+
| 2026-01 |      2 |     5 |   61.95 |
| 2026-02 |      3 |     5 |   51.95 |
| 2026-03 |      2 |     3 |   33.47 |
| 2026-04 |      2 |     3 |   38.97 |
| 2026-05 |      2 |     3 |   31.97 |
| 2026-06 |      1 |     2 |   18.98 |
+---------+--------+-------+---------+

The ORDER BY belongs in the query that reads the view, not in the view. More on that under Performance and Limitations.

✏️ Replacing, Altering and Dropping Views

A view has no data to lose, so changing one is cheap: you replace its query. CREATE OR REPLACE VIEW creates the view if it is missing and replaces it if it exists, in one step, which makes it the right choice for scripts you run more than once. Add the city to the Chicago view:

CREATE OR REPLACE VIEW v_chicago_customers AS
SELECT id, first_name, last_name, email, city
FROM customers
WHERE city = 'Chicago';

SELECT * FROM v_chicago_customers ORDER BY id;

Output

+----+------------+-----------+-------------------+---------+
| id | first_name | last_name | email             | city    |
+----+------------+-----------+-------------------+---------+
|  2 | Bob        | Smith     | bob@example.com   | Chicago |
|  7 | Grace      | Wilson    | grace@example.com | Chicago |
+----+------------+-----------+-------------------+---------+

ALTER VIEW v_chicago_customers AS SELECT ... does the same but only for a view that already exists. Removing a view removes only its definition; the base tables and their rows are untouched:

DROP VIEW v_name;                     -- error 1051 if it does not exist
DROP VIEW IF EXISTS v_name;           -- a note instead of an error
DROP VIEW IF EXISTS v_one, v_two;     -- several at once

⚠️ Dropping a view does not check who uses it

If v_big_spenders is built on v_customer_summary and you drop v_customer_summary, MySQL lets you, and v_big_spenders fails the next time anyone queries it (error 1356, in Common Mistakes). Before dropping or renaming anything, search for dependents: SELECT TABLE_NAME FROM information_schema.VIEWS WHERE VIEW_DEFINITION LIKE '%v_customer_summary%';

🔄 Updatable Views

Some views accept INSERT, UPDATE and DELETE and pass the change through to the base table. MySQL allows it when each row of the view maps to exactly one row of a base table, so it knows which row to change. Grace Wilson has a new email address; change it through the view, inside a transaction so you can undo it (Lesson 7.2 covers transactions; for now, ROLLBACK means "undo everything since START TRANSACTION"):

START TRANSACTION;

UPDATE v_chicago_customers
SET email = 'grace.wilson@example.com'
WHERE id = 7;

SELECT id, first_name, email FROM customers WHERE id = 7;

ROLLBACK;

Output

+----+------------+--------------------------+
| id | first_name | email                    |
+----+------------+--------------------------+
|  7 | Grace      | grace.wilson@example.com |
+----+------------+--------------------------+

The change landed in customers: the view is only a doorway. A view is not updatable when one view row stands for several base rows or for a computed value, that is, when it uses:

  • aggregate functions, GROUP BY or HAVING
  • DISTINCT, UNION or UNION ALL
  • window functions, or a subquery in the select list
  • ALGORITHM=TEMPTABLE

Joins are allowed, with a limit: one UPDATE may change columns of only one of the joined tables, and a computed column such as line_total can never be set. MySQL records its verdict for every view:

SELECT TABLE_NAME, IS_UPDATABLE, CHECK_OPTION
FROM information_schema.VIEWS
WHERE TABLE_SCHEMA = 'bookstore'
ORDER BY TABLE_NAME;

Output

+---------------------+--------------+--------------+
| TABLE_NAME          | IS_UPDATABLE | CHECK_OPTION |
+---------------------+--------------+--------------+
| v_chicago_customers | YES          | NONE         |
| v_customer_summary  | NO           | NONE         |
| v_monthly_revenue   | NO           | NONE         |
| v_order_details     | YES          | NONE         |
+---------------------+--------------+--------------+

v_order_details is a five-table join and still says YES: you could change an item's quantity through it. The two aggregate views say NO.

💡 In practice

Most views in real databases are read-only reports. Updating through a view is useful for one job above all: giving someone write access to a slice of a table (one department's rows, a few safe columns), which is what the next section protects.

🛡️ WITH CHECK OPTION

An update through v_chicago_customers could set city to 'Boston'. MySQL would happily do it, and the row would vanish from the view that changed it. WITH CHECK OPTION makes the view reject any insert or update that produces a row the view itself would not show:

CREATE OR REPLACE VIEW v_chicago_customers AS
SELECT id, first_name, last_name, email, city
FROM customers
WHERE city = 'Chicago'
WITH CHECK OPTION;
UPDATE v_chicago_customers SET city = 'Boston' WHERE id = 2;

Error

ERROR 1369 (HY000): CHECK OPTION failed 'bookstore.v_chicago_customers'

Changes that keep the row inside the view still work. Inserting a new Chicago customer through the view (and rolling it back):

START TRANSACTION;

INSERT INTO v_chicago_customers (first_name, last_name, email, city)
VALUES ('Ivy', 'Lopez', 'ivy@example.com', 'Chicago');

SELECT first_name, last_name, city FROM v_chicago_customers ORDER BY id;

ROLLBACK;

Output

+------------+-----------+---------+
| first_name | last_name | city    |
+------------+-----------+---------+
| Bob        | Smith     | Chicago |
| Grace      | Wilson    | Chicago |
| Ivy        | Lopez     | Chicago |
+------------+-----------+---------+

The insert works because every NOT NULL column of customers without a default (first_name, last_name, email) is in the view. A view that leaves one out cannot be inserted into (error 1423).

💡 CASCADED and LOCAL

MySQL saved this as WITH CASCADED CHECK OPTION, the default. When a view is built on another view, CASCADED checks the conditions of every view underneath too; WITH LOCAL CHECK OPTION checks only the conditions of views that have their own check option. Use the default unless you have a reason not to.

🔐 Views for Security

The employees table holds salaries. The support team needs a staff directory, but not the pay. A view can hide columns (here salary and manager_id) and rows (only active staff):

CREATE VIEW v_staff_directory AS
SELECT first_name, last_name, email, department
FROM employees
WHERE is_active = TRUE;

SELECT * FROM v_staff_directory ORDER BY department, last_name;

Output

+------------+-----------+---------------------------------+------------+
| first_name | last_name | email                           | department |
+------------+-----------+---------------------------------+------------+
| Tom        | Becker    | tom.becker@bookstore.example    | sales      |
| Priya      | Nair      | priya.nair@bookstore.example    | sales      |
| Lena       | Park      | lena.park@bookstore.example     | sales      |
| Sofia      | Alvarez   | sofia.alvarez@bookstore.example | inventory  |
| Marcus     | Hill      | marcus.hill@bookstore.example   | inventory  |
| Daniel     | Reyes     | daniel.reyes@bookstore.example  | management |
| Maria      | Santos    | maria.santos@bookstore.example  | management |
| Nina       | Kowalski  | nina.kowalski@bookstore.example | support    |
| James      | Okafor    | james.okafor@bookstore.example  | support    |
+------------+-----------+---------------------------------+------------+

Ben Carter (inactive) and every salary are gone. Now give an account access to the view and nothing else. You will learn user management properly in Lesson 7.4; this demo account exists only to show the idea, and you will drop it again right away:

CREATE USER 'support_demo'@'localhost' IDENTIFIED BY 'Replace-With-A-Strong-Passw0rd!';
GRANT SELECT ON bookstore.v_staff_directory TO 'support_demo'@'localhost';

SHOW GRANTS FOR 'support_demo'@'localhost';

Output

+-------------------------------------------------------------------------------+
| Grants for support_demo@localhost                                             |
+-------------------------------------------------------------------------------+
| GRANT USAGE ON *.* TO `support_demo`@`localhost`                              |
| GRANT SELECT ON `bookstore`.`v_staff_directory` TO `support_demo`@`localhost` |
+-------------------------------------------------------------------------------+

The account may read the view but has no privilege on employees itself: SELECT salary FROM employees would fail for it with error 1142 (SELECT command denied). The view still works for it because of SQL SECURITY DEFINER: the view reads employees with its creator's rights. Clean up:

DROP USER 'support_demo'@'localhost';

🛑 A view is only as safe as its definer

With SQL SECURITY DEFINER, anyone allowed to query the view sees everything its query can see with the definer's privileges. Never select more columns than the audience should have, and in production create views as a dedicated, least-privileged account rather than as root. SQL SECURITY INVOKER (written after CREATE) does the opposite: the caller needs privileges on the base tables too, so the view becomes a convenience, not a security boundary.

⚙️ Performance and Limitations

A view is as fast as its query

A view has no indexes of its own and stores no results. For simple views MySQL uses the MERGE algorithm: it pastes the view's query into yours and optimizes the combination, so the base tables' indexes work as usual:

EXPLAIN SELECT customer, title FROM v_order_details WHERE order_id = 3\G

Output (cost and row estimates differ from server to server)

*************************** 1. row ***************************
EXPLAIN: -> Nested loop inner join  (cost=1.05 rows=1)
    -> Nested loop inner join  (cost=0.7 rows=1)
        -> Index lookup on oi using fk_items_order (order_id = 3)  (cost=0.35 rows=1)
        -> Single-row index lookup on b using PRIMARY (id = oi.book_id)  (cost=0.35 rows=1)
    -> Single-row covering index lookup on a using PRIMARY (id = b.author_id)  (cost=0.35 rows=1)

No trace of the view: MySQL merged it into the query. Order 3 and its customer are single rows reached through primary keys, so MySQL reads them while planning and they do not even appear as steps. The plan then finds the order's items through the foreign key index fk_items_order (Lesson 6.1) and each book and author through its primary key. Views with GROUP BY, DISTINCT or aggregates cannot be merged; MySQL computes them into a temporary table first (the TEMPTABLE algorithm), so a filter on such a view runs after all the grouping is done. On big tables, filter in the base query instead, or keep a summary table.

Other limits to know

  • No materialized views. MySQL always recomputes. If a report is too slow to recompute on every visit, store its result in an ordinary summary table and refresh it on a schedule (a stored procedure from Lesson 7.1 plus the event scheduler).
  • ORDER BY in a view is unreliable. MySQL ignores it when the outer query has its own ORDER BY, and the SQL standard does not promise any order at all. Sort in the query that reads the view.
  • The column list is frozen. SELECT * is expanded into a fixed column list when the view is created (Common Mistake 5).
  • Schema changes can break views. Rename or drop a column a view uses, and the view fails until you replace it (Common Mistake 4).
  • Keep chains short. A view on a view on a view is hard to read and hard to tune. One level is normal; two is the limit worth aiming for.

🐬 Version note

Everything in this lesson works the same on MySQL 9.7 and 8.4. MariaDB supports the same view syntax; its SHOW CREATE VIEW output and some error texts are worded differently, and its EXPLAIN prints the traditional table (Lesson 6.1).

⚠️ Common Mistakes

1. Creating a view that already exists

CREATE VIEW v_monthly_revenue AS
SELECT DATE_FORMAT(order_date, '%Y-%m') AS month, COUNT(*) AS orders
FROM orders
GROUP BY DATE_FORMAT(order_date, '%Y-%m');

Error

ERROR 1050 (42S01): Table 'v_monthly_revenue' already exists

What it means: the name is taken (by a view or a table: they share one namespace, hence "Table"). Fix: CREATE OR REPLACE VIEW when you mean to change it, or pick a new name.

2. Updating an aggregate view

UPDATE v_customer_summary SET orders = 5 WHERE customer_id = 3;

Error

ERROR 1288 (HY000): The target table v_customer_summary of the UPDATE is not updatable

What it means: orders is a COUNT over many rows; there is no single base row MySQL could change to make it 5. Fix: change the base tables (insert an order), and the view follows automatically.

3. Changing two tables through a join view

UPDATE v_order_details
SET quantity = 2, title = 'Dune (Deluxe)'
WHERE order_id = 3;

Error

ERROR 1393 (HY000): Can not modify more than one base table through a join view 'bookstore.v_order_details'

What it means: quantity lives in order_items and title in books; one statement through a join view may change only one of its tables. Fix: two UPDATEs, or, better, update the base tables directly. (Renaming the book through an order view would rename it in every order, which is rarely what anyone means.)

4. A view broken by a schema change

To see this safely, use a throwaway table, not a course table:

CREATE TABLE demo_products (id INT PRIMARY KEY, name VARCHAR(50), cost DECIMAL(8, 2));
INSERT INTO demo_products VALUES (1, 'Bookmark', 1.50), (2, 'Tote bag', 12.00);

CREATE VIEW v_demo_prices AS SELECT name, cost FROM demo_products;

ALTER TABLE demo_products RENAME COLUMN cost TO unit_cost;
SELECT * FROM v_demo_prices;

Error

ERROR 1356 (HY000): View 'bookstore.v_demo_prices' references invalid table(s) or column(s) or function(s) or definer/invoker of view lack rights to use them

What it means: the view still asks for cost, which no longer exists. MySQL allowed the ALTER TABLE without a word. Fix: replace the view with the new column name. Before changing a table, find the views that use it (information_schema.VIEWS), and run CHECK TABLE v_name afterward to confirm a view still works.

CREATE OR REPLACE VIEW v_demo_prices AS SELECT name, unit_cost FROM demo_products;

5. Expecting SELECT * views to pick up new columns (silent)

CREATE VIEW v_demo_all AS SELECT * FROM demo_products;

ALTER TABLE demo_products ADD COLUMN in_stock BOOLEAN DEFAULT TRUE;

SELECT * FROM v_demo_all ORDER BY id;

Output

+----+----------+-----------+
| id | name     | unit_cost |
+----+----------+-----------+
|  1 | Bookmark |      1.50 |
|  2 | Tote bag |     12.00 |
+----+----------+-----------+

What it means: no error, but no in_stock either. The * was expanded into id, name, unit_cost when the view was created, and that list is what MySQL saved. Fix: list the columns you mean in every view, and replace the view when the table gains a column it should show. Clean up the demo objects:

DROP VIEW v_demo_prices, v_demo_all;
DROP TABLE demo_products;

🛠️ Project: A Reporting Layer

The store manager wants four reports she can run herself, with plain SELECTs, without ever seeing a join. You will write them as views in a script, reporting_views.sql, that can be run again at any time without errors. Allow about 30 minutes.

🛠️ Step 1: The catalog (7 min)

Create reporting_views.sql in your mysql-course folder. Its first view lists every book with its author and all its categories in one cell. GROUP_CONCAT joins the category names of each book into one string.

USE bookstore;

-- 1. Catalog: one row per book
CREATE OR REPLACE VIEW v_book_catalog AS
SELECT
    b.id,
    b.title,
    a.name AS author,
    b.price,
    b.in_stock,
    GROUP_CONCAT(c.name ORDER BY c.name SEPARATOR ', ') AS categories
FROM books AS b
JOIN authors AS a ON a.id = b.author_id
LEFT JOIN book_categories AS bc ON bc.book_id = b.id
LEFT JOIN categories AS c ON c.id = bc.category_id
GROUP BY b.id, b.title, a.name, b.price, b.in_stock;

SELECT title, author, categories FROM v_book_catalog ORDER BY title;

Output

🛠️ Step 2: Order totals (5 min)

The bookstore deliberately stores no order total (it can always be computed, so storing it would invite mistakes; Lesson 6.3 explains why). The view computes it:

-- 2. Order totals: one row per order
CREATE OR REPLACE VIEW v_order_totals AS
SELECT
    o.id AS order_id,
    o.order_date,
    CONCAT(c.first_name, ' ', c.last_name) AS customer,
    SUM(oi.quantity) AS items,
    SUM(oi.quantity * oi.price_at_time) AS order_total
FROM orders AS o
JOIN customers   AS c  ON c.id = o.customer_id
JOIN order_items AS oi ON oi.order_id = o.id
GROUP BY o.id, o.order_date, c.first_name, c.last_name;

SELECT * FROM v_order_totals WHERE order_total >= 25 ORDER BY order_total DESC;

Output

| order_id | order_date | customer      | items | order_total |
+----------+------------+---------------+-------+-------------+
|        1 | 2026-01-15 | Alice Johnson |     3 |       34.97 |
|        4 | 2026-01-22 | Dave Brown    |     2 |       26.98 |

🛠️ Step 3: Bestsellers, including books that never sold (6 min)

-- 3. Sales per book, zero for books never ordered
CREATE OR REPLACE VIEW v_book_sales AS
SELECT
    b.title,
    COALESCE(SUM(oi.quantity), 0) AS copies_sold,
    COALESCE(SUM(oi.quantity * oi.price_at_time), 0) AS revenue
FROM books AS b
LEFT JOIN order_items AS oi ON oi.book_id = b.id
GROUP BY b.id, b.title;

SELECT * FROM v_book_sales ORDER BY copies_sold DESC, title LIMIT 3;
SELECT title FROM v_book_sales WHERE copies_sold = 0 ORDER BY title;

Output

+------------+-------------+---------+
| title      | copies_sold | revenue |
+------------+-------------+---------+
| 1984       |           4 |   39.96 |
| Dune       |           3 |   44.97 |
| The Hobbit |           3 |   32.97 |
+------------+-------------+---------+
+------------------------+
| title                  |
+------------------------+
| The Catcher in the Rye |
| The Great Gatsby       |
+------------------------+

One view answers both "what sells best?" and "what never sells?". Dune and The Hobbit tie at three copies; the title in ORDER BY breaks the tie so the report reads the same every time.

🏋️ Exercise 4 (Stretch): A Safe Editing View

The inventory team may change only the price and stock status of books, and must never be able to set a price of zero or less through their view. Create v_inventory_edit (id, title, price, in_stock, only books priced above 0) with a check option, then show that a price change works and a price of 0 is rejected. Undo the price change with a transaction.

💡 Hint

The view's WHERE price > 0 plus WITH CHECK OPTION turns the condition into a rule for writes. Put the wrong update in its own statement and expect error 1369.

✅ Solution 
CREATE VIEW v_inventory_edit AS
SELECT id, title, price, in_stock
FROM books
WHERE price > 0
WITH CHECK OPTION;

START TRANSACTION;
UPDATE v_inventory_edit SET price = 13.99 WHERE id = 1;
SELECT title, price FROM books WHERE id = 1;
ROLLBACK;

Output

+-------+-------+
| title | price |
+-------+-------+
| Dune  | 13.99 |
+-------+-------+
UPDATE v_inventory_edit SET price = 0 WHERE id = 1;

Error

ERROR 1369 (HY000): CHECK OPTION failed 'bookstore.v_inventory_edit'

A CHECK constraint on books.price (Lesson 2.2) would protect the table for everyone; the view's check option protects this one doorway. Both have their place.

❓ Common Questions at This Stage

Do views make queries faster?

Not by themselves. A merged view runs exactly like the query you would have written by hand, and an aggregate view can be slower if you filter it from the outside, because the grouping happens first. Views make queries easier to write and share; indexes on the base tables make them fast.

Can I put an index on a view?

No. Index the base tables on the columns the view filters and joins on, then check with EXPLAIN that the merged plan uses them, as you did for v_order_details.

Should every query in my application go through a view?

No. Views shine for shared reports, for hiding columns or rows, and for keeping an old "shape" alive while you restructure tables. For one-off queries in application code they only add a layer to look through. Use them where the name carries meaning for the people using it.

What happens to my views when I reload bookstore.sql?

They disappear: the script drops the whole bookstore database, views included. That is why the project keeps them in reporting_views.sql: run it again after any reload and the reporting layer is back.

📝 Lesson Summary

🎓 Key Takeaways

  • A view is a saved SELECT: it stores the query, never the rows, and is recomputed on every use
  • Query a view like a table; put ORDER BY in the outer query, not in the view
  • CREATE OR REPLACE VIEW makes scripts rerunnable; DROP VIEW IF EXISTS removes only the definition
  • Simple views (one row per base row, no grouping or DISTINCT) are updatable; join views may change one table per statement
  • WITH CHECK OPTION stops writes that would push a row out of the view (error 1369)
  • With SQL SECURITY DEFINER, a view can expose chosen columns and rows to an account that has no rights on the table
  • SELECT * is frozen at creation, and renamed or dropped columns break views (error 1356): list columns explicitly
