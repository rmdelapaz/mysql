🧱 Lesson 2.2: Data Types & Constraints

In Lesson 2.1 you typed INT, VARCHAR(200) and DECIMAL(8, 2) on trust. This lesson explains the choices: what each type can hold, what MySQL does when a value does not fit, and how constraints such as NOT NULL, UNIQUE and CHECK stop bad data at the door instead of in next month's report.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Pick an integer type and decide when UNSIGNED makes sense; explain why money is DECIMAL, never FLOAT
  • Choose between CHAR, VARCHAR and TEXT, and between DATE, DATETIME and TIMESTAMP
  • Use BOOLEAN and ENUM correctly, knowing what MySQL really stores
  • Apply PRIMARY KEY, AUTO_INCREMENT, NOT NULL, UNIQUE, DEFAULT and named CHECK constraints
  • Read the errors strict mode raises for bad values (1048, 1062, 1264, 1265, 1292, 1364, 1406, 3819)

🤔 Why Data Types Matter

Why not store everything as text? Because a column's type is a promise about its values, and MySQL keeps that promise for you:

  • Validation: a DATE column refuses '2026-02-30'; an INT column refuses 'many'.
  • Correct behavior: numbers add up, dates sort in time order and can be subtracted. As text, '10' sorts before '9'.
  • Size and speed: an INT always takes 4 bytes, and smaller rows mean more of the table fits in memory.
graph TD A["a value arrives"] --> B{"fits the column type?"} B -->|"yes"| C{"passes the constraints?"} B -->|"no"| D["error: row rejected"] C -->|"yes"| E["row stored"] C -->|"no"| D

🔑 Strict mode

That "row rejected" box depends on a setting. MySQL 9.7 and 8.4 (and MariaDB) start with STRICT_TRANS_TABLES in their sql_mode, so a value that does not fit is an error. Without strict mode, MySQL would quietly change the value (cut text short, clamp a number) and only warn. Old tutorials sometimes show that behavior, and some hosts still turn strict mode off. Keep it on.

🔢 Numbers: Integers and Decimals

Integer types

TypeBytesSigned rangeUNSIGNED rangeTypical use
TINYINT1-128 to 1270 to 255Ratings, small codes, flags
SMALLINT2-32,768 to 32,7670 to 65,535Copies in stock, years
MEDIUMINT3about ±8.4 million0 to about 16.8 millionRarely needed
INT4about ±2.1 billion0 to about 4.3 billionIds, counts, page numbers: the default choice
BIGINT8about ±9.2 quintillion0 to about 18.4 quintillionIds of very large tables, byte counts

UNSIGNED means "no negative numbers"; the range shifts up so it starts at 0 and the maximum roughly doubles. Use it when a negative value would be nonsense, such as a number of copies.

Decimal types

TypePrecisionTypical use
DECIMAL(M, D)Exact: M digits in total, D of them after the pointMoney, and anything that must add up to the cent
FLOATApproximate, about 7 significant digitsSensor readings, where tiny errors do not matter
DOUBLEApproximate, about 15 significant digitsScientific values, coordinates

DECIMAL(8, 2), the type of books.price, holds up to 6 digits before the point and 2 after: the largest value is 999999.99.

A demo table with one column of each kind:

CREATE TABLE number_demo (
    stars     TINYINT,
    copies    SMALLINT UNSIGNED,
    price     DECIMAL(8, 2),
    weight_kg FLOAT
);
INSERT INTO number_demo (stars, copies, price, weight_kg)
VALUES (5, 120, 14.99, 0.1);
SELECT * FROM number_demo;

Output

+-------+--------+-------+-----------+
| stars | copies | price | weight_kg |
+-------+--------+-------+-----------+
|     5 |    120 | 14.99 |       0.1 |
+-------+--------+-------+-----------+

When a number does not fit

INSERT INTO number_demo (stars) VALUES (200);

Error

ERROR 1264 (22003): Out of range value for column 'stars' at row 1

A TINYINT stops at 127, so 200 is out of range. A negative value in the UNSIGNED copies column, or 1234567.00 in price (seven digits before the point), fails with the same error.

Too many decimal places is different: MySQL rounds and records a note.

INSERT INTO number_demo (price) VALUES (12.345);
SHOW WARNINGS;
SELECT price FROM number_demo WHERE stars IS NULL;

Output

Query OK, 1 row affected, 1 warning
+-------+------+--------------------------------------------+
| Level | Code | Message                                    |
+-------+------+--------------------------------------------+
| Note  | 1265 | Data truncated for column 'price' at row 1 |
+-------+------+--------------------------------------------+
1 row in set
+-------+
| price |
+-------+
| 12.35 |
+-------+
1 row in set

12.345 became 12.35. Rounding to the column's precision is usually what you want, but it is worth knowing it happens.

Why money is never FLOAT

FLOAT and DOUBLE store binary fractions, and most decimal fractions, like 0.1, have no exact binary form. Look at what the stored 0.1 really is when you calculate with it:

SELECT
    price * 3                 AS decimal_times_3,
    weight_kg * 3             AS float_times_3,
    weight_kg = 0.1           AS float_equals_0_1
FROM number_demo
WHERE stars = 5;

Output

+-----------------+---------------------+------------------+
| decimal_times_3 | float_times_3       | float_equals_0_1 |
+-----------------+---------------------+------------------+
|           44.97 | 0.30000000447034836 |                0 |
+-----------------+---------------------+------------------+

The DECIMAL result is exactly 44.97. The FLOAT one is 0.30000000447034836, and the stored value is not even equal to 0.1 (the comparison returns 0, false). Over thousands of orders those crumbs add up to real money that no report can explain. Money is always DECIMAL.

🔤 Text: CHAR, VARCHAR and TEXT

TypeHoldsTypical use
CHAR(n)Exactly n characters (n up to 255), padded with spacesCodes that always have the same length: 'US', an ISBN-13
VARCHAR(n)Up to n characters, stored at their real lengthNames, emails, titles, cities: almost all text
TEXTUp to 65,535 bytesDescriptions, reviews
MEDIUMTEXT / LONGTEXTUp to 16 MB / 4 GBWhole articles; rarely needed

The number in VARCHAR(100) counts characters, not bytes. With utf8mb4 a character takes 1 to 4 bytes, so the byte limits in the table above hold fewer characters when the text is not plain English.

CREATE TABLE text_demo (
    code  CHAR(5),
    label VARCHAR(5)
);
INSERT INTO text_demo VALUES ('ab  ', 'ab  ');
SELECT
    CONCAT('[', code, ']')  AS code,
    CONCAT('[', label, ']') AS label
FROM text_demo;

Output

+------+--------+
| code | label  |
+------+--------+
| [ab] | [ab  ] |
+------+--------+

Both columns received 'ab' plus two spaces. VARCHAR kept the spaces; CHAR pads to its length when storing and strips trailing spaces when reading. That is fine for fixed-length codes and surprising for anything else: one more reason VARCHAR is the default choice.

INSERT INTO text_demo (label) VALUES ('Fahrenheit 451');

Error

ERROR 1406 (22001): Data too long for column 'label' at row 1

Fourteen characters do not fit in VARCHAR(5). Strict mode refuses the row rather than storing 'Fahre'.

💡 VARCHAR or TEXT?

If you can name a sensible maximum (a title, an email, a URL), use VARCHAR: it can be fully indexed and can have a plain DEFAULT. Use TEXT for open-ended writing such as reviews or descriptions. Phone numbers, ZIP codes and ISBNs are text too: they can start with 0 or +, contain dashes, and nobody adds them up.

CREATE TABLE date_demo (
    d   DATE,
    dt  DATETIME,
    ts  TIMESTAMP NULL,
    t   TIME
);
INSERT INTO date_demo VALUES
    ('1965-08-01', '2026-03-10 14:30:00', '2026-03-10 14:30:00', '09:00:00');
SELECT * FROM date_demo;

Output

+------------+---------------------+---------------------+----------+
| d          | dt                  | ts                  | t        |
+------------+---------------------+---------------------+----------+
| 1965-08-01 | 2026-03-10 14:30:00 | 2026-03-10 14:30:00 | 09:00:00 |
+------------+---------------------+---------------------+----------+

Dates are always written year first, as text in quotes. MySQL checks that the date really exists:

INSERT INTO date_demo (d) VALUES ('2026-02-30');

Error

ERROR 1292 (22007): Incorrect date value: '2026-02-30' for column 'd' at row 1

DATETIME vs. TIMESTAMP

They look identical, but a TIMESTAMP is stored in UTC and converted to your session's time zone when you read it; a DATETIME is stored exactly as written. Watch both columns after the session's time zone changes (SET time_zone only affects your own connection):

DELETE FROM date_demo;
SET time_zone = '+00:00';
INSERT INTO date_demo (dt, ts)
VALUES ('2026-03-10 14:30:00', '2026-03-10 14:30:00');
SET time_zone = '-05:00';
SELECT dt, ts FROM date_demo;
SET time_zone = SYSTEM;

Output

+---------------------+---------------------+
| dt                  | ts                  |
+---------------------+---------------------+
| 2026-03-10 14:30:00 | 2026-03-10 09:30:00 |
+---------------------+---------------------+

The DATETIME still says 14:30; the TIMESTAMP now shows the same moment in a time zone five hours behind UTC. (DELETE FROM date_demo emptied the demo table first; Lesson 2.3 covers DELETE.) The catch is the range:

INSERT INTO date_demo (ts) VALUES ('2040-01-01 00:00:00');

Error

ERROR 1292 (22007): Incorrect datetime value: '2040-01-01 00:00:00' for column 'ts' at row 1

A TIMESTAMP ends in January 2038, which is already inside the life of a long loan or a subscription. This course uses DATETIME (and DATE) everywhere.

🐬 Version note: TIMESTAMP on MariaDB

Recent MariaDB releases (11.5 and later) extend TIMESTAMP to the year 2106, so the 2040 insert above succeeds there. MySQL 9.7 and 8.4 still stop in 2038. DATETIME behaves the same everywhere.

✅ The created/updated pattern

Many tables record when each row was added and last changed. Both defaults are filled in by MySQL:

created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
updated_at  DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP

created_at is set once, when the row is inserted; updated_at changes every time the row does. customers.created_at in the bookstore uses the first half of this pattern.

🔘 BOOLEAN, ENUM and SET

BOOLEAN is a small number

MySQL has no separate true/false type. BOOLEAN is another name for TINYINT(1), TRUE is 1 and FALSE is 0. You saw this in DESCRIBE books in Lesson 2.1, and it has a consequence you will meet in Common Mistakes.

ENUM: one value from a fixed list

CREATE TABLE format_demo (
    title  VARCHAR(50) NOT NULL,
    format ENUM('paperback', 'hardcover', 'ebook') NOT NULL DEFAULT 'paperback'
);
INSERT INTO format_demo (title, format) VALUES ('Dune', 'hardcover');
INSERT INTO format_demo (title) VALUES ('Emma');
INSERT INTO format_demo (title, format) VALUES ('1984', 'EBOOK');
SELECT title, format FROM format_demo;

Output

+-------+-----------+
| title | format    |
+-------+-----------+
| Dune  | hardcover |
| Emma  | paperback |
| 1984  | ebook     |
+-------+-----------+

Emma got the default, and 'EBOOK' was accepted as 'ebook' because the comparison is case-insensitive. A value that is not on the list is refused (Common Mistakes, number 2).

💡 ENUM: good for short, stable lists

An ENUM is compact and documents the allowed values right in the table. But adding a value means an ALTER TABLE, and ORDER BY format sorts by list position (paperback, hardcover, ebook), not alphabetically. When the list changes often, or needs extra information per value, use a separate lookup table instead: that is exactly what categories is.

SET: several values from a fixed list

SET('signed', 'used', 'bestseller') lets a row hold any combination, written as one string: 'signed,used'. It exists, you may meet it in older databases, and you will rarely want it: Module 4 shows the standard way to store "many values per row" with a junction table.

🛡️ Constraints: Rules for Your Data

A type says what kind of value a column holds. A constraint adds a rule: must be present, must be unique, must be positive. The database enforces it for every program and every person that writes to the table, which is far safer than hoping each one checks.

ConstraintRuleHow many per tableError when broken
PRIMARY KEYIdentifies each row: unique and never NULLOne (it may span several columns)1062
AUTO_INCREMENTMySQL numbers new rows 1, 2, 3...One, and it must be a key(1075 at CREATE time)
NOT NULLA value is requiredAny1048, or 1364 if left out
UNIQUENo two rows share a value (NULLs excepted)Any1062
DEFAULTThe value used when none is givenOne per columnNone: it fills a gap
CHECKA condition every row must meetAny3819
FOREIGN KEYThe value must exist in another tableAny1452 (Lesson 4.2)

Here is a table for the store's discount coupons that uses all but the last:

CREATE TABLE coupons (
    id           INT AUTO_INCREMENT PRIMARY KEY,
    code         VARCHAR(20) NOT NULL UNIQUE,
    percent_off  TINYINT UNSIGNED NOT NULL,
    min_order    DECIMAL(8, 2) NOT NULL DEFAULT 0.00,
    expires      DATE,
    CONSTRAINT chk_coupon_percent CHECK (percent_off BETWEEN 5 AND 50)
);
INSERT INTO coupons (code, percent_off, expires) VALUES ('WELCOME10', 10, '2026-12-31');
INSERT INTO coupons (code, percent_off, min_order) VALUES ('BIGBASKET', 20, 50.00);
SELECT * FROM coupons;

Output

+----+-----------+-------------+-----------+------------+
| id | code      | percent_off | min_order | expires    |
+----+-----------+-------------+-----------+------------+
|  1 | WELCOME10 |          10 |      0.00 | 2026-12-31 |
|  2 | BIGBASKET |          20 |     50.00 | NULL       |
+----+-----------+-------------+-----------+------------+

MySQL numbered the rows, filled min_order with its default for WELCOME10, and left expires empty (NULL) for BIGBASKET, which is allowed because that column has no NOT NULL. Now break each rule in turn.

NOT NULL

INSERT INTO coupons (code, percent_off) VALUES (NULL, 15);

Error

ERROR 1048 (23000): Column 'code' cannot be null
INSERT INTO coupons (code) VALUES ('SPRING15');

Error

ERROR 1364 (HY000): Field 'percent_off' doesn't have a default value

Two flavors of the same rule: an explicit NULL gives 1048; leaving a required column out when it has no default gives 1364. Ask of every column: "does a row make sense without this?" A coupon without a code does not; a coupon without an expiry date can (it never expires).

UNIQUE

INSERT INTO coupons (code, percent_off) VALUES ('WELCOME10', 15);

Error

ERROR 1062 (23000): Duplicate entry 'WELCOME10' for key 'coupons.code'

The message names the value and the key (coupons.code, the name MySQL gave the unique index). A UNIQUE column may hold several NULLs, because NULL means "unknown" and two unknowns are not considered equal; add NOT NULL, as here, when every row needs a value.

CHECK

INSERT INTO coupons (code, percent_off) VALUES ('HALFPRICE', 75);

Error

ERROR 3819 (HY000): Check constraint 'chk_coupon_percent' is violated.

This is why the constraint has a name: chk_coupon_percent tells you exactly which rule failed. Without CONSTRAINT name, MySQL invents one like coupons_chk_1.

🐬 Version note: CHECK in old tutorials

Before MySQL 8.0.16, CHECK was accepted and then silently ignored, so older articles say "MySQL does not support CHECK". MySQL 9.7 and 8.4 enforce it, and so does MariaDB, with a different message: ERROR 4025 (23000): CONSTRAINT `chk_coupon_percent` failed for `bookstore`.`coupons`.

PRIMARY KEY and AUTO_INCREMENT

INSERT INTO coupons (code, percent_off) VALUES ('SUMMER25', 25);
SELECT LAST_INSERT_ID();
SELECT id, code FROM coupons ORDER BY id;

Output (your id numbers could differ)

+------------------+
| LAST_INSERT_ID() |
+------------------+
|                4 |
+------------------+
+----+-----------+
| id | code      |
+----+-----------+
|  1 | WELCOME10 |
|  2 | BIGBASKET |
|  4 | SUMMER25  |
+----+-----------+

LAST_INSERT_ID() returns the id MySQL just gave your row, which a program needs right after an insert. Notice the gap at 3: one of the failed inserts above used up an id number without saving a row. Gaps are normal and harmless; an id is a label, not a count, and is never reused.

A primary key can also span several columns, written as a table-level constraint. A book can be in several categories and a category holds many books, but each pair should appear only once:

CREATE TABLE book_categories (
    book_id     INT,
    category_id INT,
    PRIMARY KEY (book_id, category_id)
);

You will build exactly this table, with foreign keys to books and categories, in Module 4.

🧭 Choosing the Right Type

Most columns fall into a handful of patterns. When in doubt, start here:

The column holdsUseExample
A row's idINT AUTO_INCREMENT PRIMARY KEYid
A count that cannot be negativeINT UNSIGNED (or smaller)copies INT UNSIGNED NOT NULL DEFAULT 0
MoneyDECIMAL(8, 2) or widerprice DECIMAL(8, 2) NOT NULL
A name, title, email, cityVARCHAR(n)email VARCHAR(100) NOT NULL UNIQUE
A fixed-length codeCHAR(n)country CHAR(2), isbn CHAR(13)
A phone number, ZIP codeVARCHAR(n), never a number typephone VARCHAR(20)
Long free textTEXTreview TEXT
A calendar dateDATEpublished DATE
A moment in timeDATETIMEcreated_at DATETIME DEFAULT CURRENT_TIMESTAMP
Yes or noBOOLEAN with a defaultin_stock BOOLEAN DEFAULT TRUE

✅ Rule of thumb

Choose the type that says what the value is, then the smallest size that comfortably fits the biggest value you can imagine. Then add NOT NULL to every column a row cannot do without.

⚠️ Common Mistakes

1. Writing dates the way people do

INSERT INTO date_demo (d) VALUES ('03/10/2026');

Error

ERROR 1292 (22007): Incorrect date value: '03/10/2026' for column 'd' at row 1

What it means: MySQL reads dates only as year, month, day. '03/10/2026' is March 10 to an American and October 3 to most of the world, and MySQL refuses to guess. Fix: write '2026-03-10'. When dates arrive in another format (a spreadsheet export), convert them with STR_TO_DATE('03/10/2026', '%m/%d/%Y').

2. A value that is not on the ENUM list

INSERT INTO format_demo (title, format) VALUES ('Dune', 'audiobook');

Error

ERROR 1265 (01000): Data truncated for column 'format' at row 1

What it means: "Data truncated" is MySQL's way of saying the value could not be stored as one of the allowed options. Fix: use one of the listed values, or add the new one with ALTER TABLE format_demo MODIFY COLUMN format ENUM('paperback', 'hardcover', 'ebook', 'audiobook') NOT NULL DEFAULT 'paperback';, repeating the whole definition as Lesson 2.1 taught.

3. Giving a TEXT column a plain default

CREATE TABLE reviews (
    id   INT AUTO_INCREMENT PRIMARY KEY,
    body TEXT DEFAULT 'No review yet'
);

Error

ERROR 1101 (42000): BLOB, TEXT, GEOMETRY or JSON column 'body' can't have a default value

What it means: TEXT (and BLOB and JSON) columns cannot take a literal default. Fix: use VARCHAR if the text has a sensible maximum, or write the default as an expression in parentheses, DEFAULT ('No review yet'), which MySQL 8.0.13 and later accept. (MariaDB allows a plain literal default on TEXT, so this statement runs there; the parenthesized form works on all three servers.)

4. AUTO_INCREMENT on a column that is not a key

CREATE TABLE gift_cards (
    id      INT AUTO_INCREMENT,
    balance DECIMAL(8, 2) NOT NULL
);

Error

ERROR 1075 (42000): Incorrect table definition; there can be only one auto column and it must be defined as a key

What it means: MySQL needs an index on the counter column to find the next number. Fix: add PRIMARY KEY: id INT AUTO_INCREMENT PRIMARY KEY. Every table in this course has exactly that line.

5. Comparing a BOOLEAN with TRUE (silent)

A program stores "in stock" as the number of copies instead of 1, and nothing stops it:

CREATE TABLE flag_demo (title VARCHAR(50), in_stock BOOLEAN);
INSERT INTO flag_demo VALUES ('Dune', TRUE), ('Emma', FALSE), ('1984', 5);
SELECT title, in_stock FROM flag_demo WHERE in_stock = TRUE;

Output

+-------+----------+
| title | in_stock |
+-------+----------+
| Dune  |        1 |
+-------+----------+

What it means: BOOLEAN is a TINYINT, so 5 is accepted. = TRUE means = 1, and 1984 silently disappears from the "in stock" list. Fix: test truth the way MySQL defines it, WHERE in_stock (any non-zero value) or WHERE in_stock <> 0, and if you want only 0 or 1 in the column, enforce it: CHECK (in_stock IN (0, 1)).

SELECT title, in_stock FROM flag_demo WHERE in_stock;

Output

+-------+----------+
| title | in_stock |
+-------+----------+
| Dune  |        1 |
| 1984  |        5 |
+-------+----------+

🛠️ Project: The Staff Table

The bookstore is hiring, and it needs a table for its staff. You will design it with the right types and constraints, save it as employees.sql, and prove each rule works by trying to break it. Allow about 35 minutes.

🛠️ Step 1: Decide the columns on paper (5 min)

The owner's requirements: a first and last name (required), a work email (required, never shared), a hire date (required), a yearly salary in dollars and cents (required, must be positive), a department (one of sales, inventory, management, support), and whether the person still works there (yes by default). Write down a type and the constraints for each before you look at Step 2.

🛠️ Step 2: Create the table (5 min)

Start employees.sql with USE bookstore; and the table. DROP TABLE IF EXISTS first makes the script rerunnable, like your build script from Lesson 2.1.

USE bookstore;

DROP TABLE IF EXISTS employees;

CREATE TABLE employees (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    first_name  VARCHAR(50) NOT NULL,
    last_name   VARCHAR(50) NOT NULL,
    email       VARCHAR(100) NOT NULL UNIQUE,
    hire_date   DATE NOT NULL,
    salary      DECIMAL(8, 2) NOT NULL,
    department  ENUM('sales', 'inventory', 'management', 'support'),
    is_active   BOOLEAN DEFAULT TRUE,
    CONSTRAINT chk_salary CHECK (salary > 0)
);

Output

Database changed

DECIMAL(8, 2) allows salaries up to 999,999.99, plenty for a bookstore. Compare with your paper design: did you pick the same types?

🛠️ Step 4: Try to break every rule (10 min)

Add these four statements to the script under a comment -- These must fail. Each one should be refused, each for a different reason. Predict the error number before you run it.

-- These must fail
INSERT INTO employees (first_name, last_name, email, hire_date, salary)
VALUES ('Tom', 'Becker', 'tom.becker@bookstore.example', '2022-09-15', 0);

INSERT INTO employees (first_name, last_name, email, hire_date, salary)
VALUES ('Tom', 'Becker', 'priya.nair@bookstore.example', '2022-09-15', 38000.00);

INSERT INTO employees (first_name, last_name, email, hire_date, salary, department)
VALUES ('Tom', 'Becker', 'tom.becker@bookstore.example', '2022-09-15', 38000.00, 'marketing');

INSERT INTO employees (first_name, last_name, email, salary)
VALUES ('Tom', 'Becker', 'tom.becker@bookstore.example', 38000.00);

Error

ERROR 3819 (HY000): Check constraint 'chk_salary' is violated.

A salary of 0 breaks chk_salary (3819), Priya's email is taken (1062), there is no marketing department (1265), and the hire date is required (1364). In a script run with SOURCE, the mysql client reports each error and carries on with the next statement.

  `salary` decimal(8,2) NOT NULL,
  `department` enum('sales','inventory','management','support') COLLATE utf8mb4_unicode_ci DEFAULT NULL,
  `is_active` tinyint(1) DEFAULT '1',
  PRIMARY KEY (`id`),
  UNIQUE KEY `email` (`email`),
  CONSTRAINT `chk_salary` CHECK ((`salary` > 0))
) ENGINE=InnoDB AUTO_INCREMENT=5 DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci

Still three rows. In the definition, find the UNIQUE KEY MySQL built for email and the chk_salary constraint. The AUTO_INCREMENT= value near the end is the next id MySQL will hand out, so it may be higher than 4 after the failed inserts.

🏋️ Exercise 1: Pick the Type

Choose a MySQL type (and constraints, if any) for each value: a customer's ZIP code ("89002" or "89002-1234"); the number of copies of a book in the warehouse; a book's back-cover blurb; a two-letter country code; an average customer rating from 1.0 to 5.0, one decimal; the date and time an order was placed.

💡 Hint

Ask of each: is it a quantity you would do math on, or an identifier that happens to contain digits? Is its length fixed, limited, or open-ended?

✅ Solution
  • ZIP code: VARCHAR(10). It can start with 0 and contain a dash; it is an identifier, not a number.
  • Copies: INT UNSIGNED NOT NULL DEFAULT 0 (or SMALLINT UNSIGNED if 65,535 is surely enough).
  • Blurb: TEXT, or VARCHAR(1000) if the shop sets a limit.
  • Country code: CHAR(2), always exactly two characters.
  • Rating: DECIMAL(2, 1) with CHECK (rating BETWEEN 1.0 AND 5.0).
  • Order time: DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP.

🏋️ Exercise 2: Prove DECIMAL Rounds

Create a table price_test with one column amount DECIMAL(5, 2). Insert 19.999, 0.005 and 999.99, show the stored values, then find the smallest value that does not fit. Drop the table at the end.

💡 Hint

DECIMAL(5, 2) has 3 digits before the point. Values are rounded to 2 decimals before they are checked against the range.

✅ Solution 
CREATE TABLE price_test (amount DECIMAL(5, 2));
INSERT INTO price_test VALUES (19.999), (0.005), (999.99);
SELECT amount FROM price_test;

Output

+--------+
| amount |
+--------+
|  20.00 |
|   0.01 |
| 999.99 |
+--------+
INSERT INTO price_test VALUES (999.995);

Error

ERROR 1264 (22003): Out of range value for column 'amount' at row 1
DROP TABLE price_test;

19.999 rounded up to 20.00 and 0.005 to 0.01. 999.995 would round to 1000.00, which needs four digits before the point, so it is out of range: the largest value is 999.99.

🏋️ Exercise 3: Fix the Bad Table

This statement runs, but almost every column is a poor choice. List the problems and write a better version as orders_demo; create it, check it with DESCRIBE, and drop it.

CREATE TABLE Orders (
    OrderID VARCHAR(10),
    CustomerName VARCHAR(500),
    Total FLOAT,
    OrderDate VARCHAR(20),
    Phone INT,
    Status VARCHAR(100)
);
💡 Hint

Look for: naming conventions, the missing primary key, money, dates, phone numbers, oversized text, and missing NOT NULLs.

    customer_name  VARCHAR(100) NOT NULL,
    total          DECIMAL(8, 2) NOT NULL,
    order_date     DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    phone          VARCHAR(20),
    status         ENUM('pending', 'shipped', 'delivered', 'cancelled') NOT NULL DEFAULT 'pending',
    CONSTRAINT chk_orders_demo_total CHECK (total >= 0)
);
DESCRIBE orders_demo;

| Field         | Type                                              | Null | Key | Default           | Extra             |

| id            | int                                               | NO   | PRI | NULL              | auto_increment    |
| customer_name | varchar(100)                                      | NO   |     | NULL              |                   |

🏋️ Exercise 4 (Stretch): Track Changes Automatically

Create notes_demo with an id, a body VARCHAR(200) NOT NULL, and created_at / updated_at columns that MySQL maintains by itself. Insert a note, change its body with UPDATE notes_demo SET body = 'edited' WHERE id = 1; a few seconds later, and compare the two timestamps. Drop the table when you are done.

💡 Hint

Use the created/updated pattern from the dates section: DEFAULT CURRENT_TIMESTAMP, plus ON UPDATE CURRENT_TIMESTAMP for the second column.

✅ Solution 
CREATE TABLE notes_demo (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    body        VARCHAR(200) NOT NULL,
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
INSERT INTO notes_demo (body) VALUES ('first draft');
UPDATE notes_demo SET body = 'edited' WHERE id = 1;
SELECT * FROM notes_demo;

Output (your timestamps will differ)

+----+--------+---------------------+---------------------+
| id | body   | created_at          | updated_at          |
+----+--------+---------------------+---------------------+
|  1 | edited | 2026-03-10 14:30:00 | 2026-03-10 14:30:12 |
+----+--------+---------------------+---------------------+
DROP TABLE notes_demo;

updated_at moved forward with the edit; created_at stayed. If you run the UPDATE with the same body again, updated_at does not change: MySQL only touches it when a value really changes.

❓ Common Questions at This Stage

Why VARCHAR(255) everywhere in other tutorials?

Habit, mostly: 255 was once the VARCHAR limit. Today a VARCHAR can be much longer, and a number that fits the data is better documentation: VARCHAR(50) for a first name tells the next developer something; VARCHAR(255) tells them nothing. The size also limits what bad input can store.

Is a UUID a better id than AUTO_INCREMENT?

Sometimes. UUIDs (UUID()) are unique across servers and hard to guess, which helps when ids appear in public URLs or several databases create rows. They are larger and slower as primary keys. For a beginner's database, and for most real ones, INT AUTO_INCREMENT (or BIGINT for huge tables) is the right default.

Can I see MySQL's strict mode setting?

Yes: SELECT @@sql_mode;. You should see STRICT_TRANS_TABLES in the list. If it is missing on a shared host, ask for it, or add it for your own session with SET SESSION sql_mode = CONCAT(@@sql_mode, ',STRICT_TRANS_TABLES');. Never remove it to make an insert "work": the insert would then store wrong data.

Can I add a constraint to a table that already exists?

Yes, with ALTER TABLE: ALTER TABLE coupons ADD CONSTRAINT chk_min_order CHECK (min_order >= 0); or ALTER TABLE customers MODIFY COLUMN city VARCHAR(50) NOT NULL;. MySQL first checks the existing rows; if any break the new rule, the change is refused, so clean the data first.

📝 Lesson Summary

🎓 Key Takeaways

  • A column's type validates values, makes math and sorting work, and decides storage size
  • With strict mode (the default), a value that does not fit is an error, not a silent change
  • INT is the default integer; UNSIGNED forbids negatives. Money is DECIMAL, never FLOAT
  • VARCHAR(n) for most text, CHAR(n) for fixed-length codes, TEXT for long writing; phone numbers and ZIP codes are text
  • Dates are written 'YYYY-MM-DD'; prefer DATETIME over TIMESTAMP unless you need time-zone conversion
  • BOOLEAN is TINYINT(1): test it with WHERE col, not = TRUE
  • Constraints enforce rules for every writer: PRIMARY KEY, AUTO_INCREMENT, NOT NULL, UNIQUE, DEFAULT, named CHECK
