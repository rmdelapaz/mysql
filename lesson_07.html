🔍 Lesson 3.1: WHERE Clauses, Operators & Filtering

A table can hold ten rows or ten million, and most questions are about only a few of them: the books under $10, the customers in Chicago, the titles that start with "The". The WHERE clause is how you ask for exactly those rows. This lesson covers every everyday filtering tool, and the quiet mistakes that return the wrong rows without any error.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Filter rows by numbers, text and dates with the comparison operators (=, !=, <, >, <=, >=)
  • Combine conditions with AND, OR and NOT, and use parentheses to say exactly what you mean
  • Match lists, ranges and text patterns with IN, BETWEEN and LIKE
  • Find missing values with IS NULL and explain why = NULL finds nothing
  • Spot the silent filtering mistakes (missing NULL rows, AND/OR mix-ups) and fix error 1054
  • Save a set of reusable searches in a .sql script
  • ⏱️ Time 95 minutes
  • 📋 Prerequisites Lesson 2.3: CRUD Operations
  • 🛠️ You will build saved_searches.sql, six searches the bookstore staff can rerun any time
  • 🗄️ Database bookstore, rebuilt by the setup script in this lesson: 10 books, 8 customers, 5 categories

🧪 How WHERE Works

WHERE is a test that MySQL runs on every row, one row at a time. The test is a condition such as price < 10. For each row the condition comes out true, false or unknown (the third answer appears when a NULL is involved). Only the rows where it is true make it into the result.

graph TD A["each row of books"] --> B["test: price less than 10"] B -->|"true"| C["row is kept"] B -->|"false"| D["row is dropped"] B -->|"unknown (NULL)"| D

The clause goes right after FROM:

SELECT title, price
FROM books
WHERE price < 10
ORDER BY price, title;

Output

+------------------------+-------+
| title                  | price |
+------------------------+-------+
| Pride and Prejudice    |  7.99 |
| The Catcher in the Rye |  8.99 |
| The Great Gatsby       |  8.99 |
| Brave New World        |  9.49 |
| 1984                   |  9.99 |
+------------------------+-------+

Five of the ten books pass the test. The ORDER BY line sorts the result so it reads the same on every server; Lesson 3.2 covers sorting in depth. For now, read it as "cheapest first, then alphabetical".

💡 You can see the test itself

A condition is just an expression that MySQL evaluates to 1 (true), 0 (false) or NULL (unknown). Put it in the SELECT list and you can watch it work row by row:

SELECT title, price, price < 10 AS passes
FROM books
ORDER BY id
LIMIT 4;

Output

+-----------------------+-------+--------+
| title                 | price | passes |
+-----------------------+-------+--------+
| Dune                  | 14.99 |      0 |
| 1984                  |  9.99 |      1 |
| To Kill a Mockingbird | 11.99 |      0 |
| The Great Gatsby      |  8.99 |      1 |
+-----------------------+-------+--------+

This trick is the fastest way to debug a WHERE clause that returns the wrong rows: show the condition as a column and look for the rows where it surprises you.

⚖️ Comparison Operators

Comparison operators compare a column with a value (or with another column). They work on numbers, text and dates.

OperatorMeaningExample
=Equal toWHERE price = 9.99
!= or <>Not equal toWHERE city != 'Chicago'
<Less thanWHERE price < 10
>Greater thanWHERE pages > 300
<=Less than or equal toWHERE price <= 9.99
>=Greater than or equal toWHERE published >= '1950-01-01'

Equal to: =

SELECT title, price
FROM books
WHERE author = 'J.R.R. Tolkien'
ORDER BY title;

Output

+-------------------+-------+
| title             | price |
+-------------------+-------+
| Lord of the Rings | 15.99 |
| The Hobbit        | 10.99 |
+-------------------+-------+

Text values go in single quotes. Numbers do not: WHERE price = 9.99, not '9.99'.

💡 Text comparisons ignore upper and lower case

The bookstore uses the utf8mb4_unicode_ci collation (the setup script above chose it). The ci stands for case-insensitive, so a sloppy search still finds Tolkien:

SELECT title
FROM books
WHERE author = 'j.r.r. tolkien'
ORDER BY title;

Output

+-------------------+
| title             |
+-------------------+
| Lord of the Rings |
| The Hobbit        |
+-------------------+

MySQL's own default collation, utf8mb4_0900_ai_ci, is case-insensitive too. That is usually what people want from a search box, but it also means a UNIQUE email column treats Alice@Example.com and alice@example.com as the same value.

Not equal: != or <>

SELECT first_name, city
FROM customers
WHERE city != 'New York'
ORDER BY first_name;

Output

+------------+-------------+
| first_name | city        |
+------------+-------------+
| Bob        | Chicago     |
| Carol      | Los Angeles |
| Dave       | Houston     |
| Grace      | Chicago     |
+------------+-------------+

!= and <> mean exactly the same thing; <> is the standard SQL spelling. Now count the rows: eight customers, two in New York, yet only four came back. Eve and Hank are missing, because "is an unknown city different from New York?" is unknown, not true. You will fix that in the IS NULL section.

Greater and less than

SELECT title, pages
FROM books
WHERE pages > 400
ORDER BY pages DESC;

Output

+---------------------+-------+
| title               | pages |
+---------------------+-------+
| Lord of the Rings   |  1178 |
| Pride and Prejudice |   432 |
| Dune                |   412 |
+---------------------+-------+

Comparing dates

Write dates as text in the 'YYYY-MM-DD' format and MySQL compares them as dates: earlier is smaller.

SELECT title, published
FROM books
WHERE published >= '1950-01-01'
ORDER BY published;

Output

+------------------------+------------+
| title                  | published  |
+------------------------+------------+
| The Catcher in the Rye | 1951-07-16 |
| Fahrenheit 451         | 1953-10-19 |
| Lord of the Rings      | 1954-07-29 |
| To Kill a Mockingbird  | 1960-07-11 |
| Dune                   | 1965-08-01 |
+------------------------+------------+

This works because published is a DATE column. Had it been stored as VARCHAR with dates typed as 7/16/1951, the comparison would be alphabetical and wrong, which is one more reason to use the proper type (Lesson 2.2).

Comparing text alphabetically

< and > work on text too, in dictionary order:

SELECT first_name, last_name
FROM customers
WHERE last_name < 'M'
ORDER BY last_name;

Output

+------------+-----------+
| first_name | last_name |
+------------+-----------+
| Dave       | Brown     |
| Eve        | Davis     |
| Alice      | Johnson   |
+------------+-----------+

Every last name that sorts before the letter M. Miller is not included: "Miller" sorts after the one-letter string "M".

🔗 AND, OR and NOT

One condition is rarely enough. The logical operators combine conditions into one test.

graph TD A["two conditions"] --> B["AND: both must be true"] A --> C["OR: at least one is true"]

AND: every condition must be true

Books that are cheap and long:

SELECT title, price, pages
FROM books
WHERE price < 10 AND pages > 300
ORDER BY price;

Output

+---------------------+-------+-------+
| title               | price | pages |
+---------------------+-------+-------+
| Pride and Prejudice |  7.99 |   432 |
| Brave New World     |  9.49 |   311 |
| 1984                |  9.99 |   328 |
+---------------------+-------+-------+

Each extra AND makes the filter stricter, so the result can only shrink.

OR: at least one condition must be true

Books that are cheap or short:

SELECT title, price, pages
FROM books
WHERE price < 9 OR pages < 200
ORDER BY title;

Output

+------------------------+-------+-------+
| title                  | price | pages |
+------------------------+-------+-------+
| Fahrenheit 451         | 10.49 |   158 |
| Pride and Prejudice    |  7.99 |   432 |
| The Catcher in the Rye |  8.99 |   234 |
| The Great Gatsby       |  8.99 |   180 |
+------------------------+-------+-------+

The Great Gatsby passes both tests and still appears once: OR keeps a row when either condition is true, and a row is never duplicated. Each extra OR makes the filter looser, so the result can only grow.

NOT: reverse a condition

SELECT title, in_stock
FROM books
WHERE NOT in_stock
ORDER BY title;

Output

+------------------------+----------+
| title                  | in_stock |
+------------------------+----------+
| The Catcher in the Rye |        0 |
| The Great Gatsby       |        0 |
+------------------------+----------+

in_stock holds 1 or 0, so it already is a true-or-false value, and NOT in_stock means "out of stock". WHERE in_stock = FALSE gives the same two rows and may read more clearly to a beginner. NOT pairs naturally with the operators that follow: NOT IN, NOT BETWEEN, NOT LIKE, IS NOT NULL.

📋 IN: Matching a List

Three ORs on the same column are hard to read. IN says the same thing with a list:

SELECT title, author
FROM books
WHERE author IN ('George Orwell', 'Aldous Huxley', 'Ray Bradbury')
ORDER BY author;

Output

+-----------------+---------------+
| title           | author        |
+-----------------+---------------+
| Brave New World | Aldous Huxley |
| 1984            | George Orwell |
| Fahrenheit 451  | Ray Bradbury  |
+-----------------+---------------+

That is exactly author = 'George Orwell' OR author = 'Aldous Huxley' OR author = 'Ray Bradbury'. Lists of numbers work the same way: WHERE id IN (1, 4, 9).

NOT IN: everything except the list

SELECT first_name, city
FROM customers
WHERE city NOT IN ('New York', 'Chicago')
ORDER BY first_name;

Output

+------------+-------------+
| first_name | city        |
+------------+-------------+
| Carol      | Los Angeles |
| Dave       | Houston     |
+------------+-------------+

Only Carol and Dave. Once again Eve and Hank vanish: an unknown city cannot be shown to be outside the list.

⚠️ Never put NULL inside a NOT IN list

city NOT IN ('New York', NULL) means city != 'New York' AND city != NULL. The second half is unknown for every row, so the whole condition can never be true and the query returns no rows at all:

SELECT first_name, city
FROM customers
WHERE city NOT IN ('New York', NULL);

Output

Empty set

No error, just nothing. You will rarely type a NULL into a list by hand, but in Lesson 3.4 the list will come from another query, and a NULL can sneak in that way.

📏 BETWEEN: Matching a Range

BETWEEN low AND high keeps the values from low to high, including both ends. It is shorthand for >= low AND <= high.

SELECT title, price
FROM books
WHERE price BETWEEN 9.49 AND 10.99
ORDER BY price;

Output

+-----------------+-------+
| title           | price |
+-----------------+-------+
| Brave New World |  9.49 |
| 1984            |  9.99 |
| Fahrenheit 451  | 10.49 |
| The Hobbit      | 10.99 |
+-----------------+-------+

Both endpoints, 9.49 and 10.99, are in the result. The smaller value must come first: BETWEEN 10.99 AND 9.49 is not an error, it simply matches nothing.

BETWEEN with dates

SELECT title, published
FROM books
WHERE published BETWEEN '1950-01-01' AND '1959-12-31'
ORDER BY published;

Output

+------------------------+------------+
| title                  | published  |
+------------------------+------------+
| The Catcher in the Rye | 1951-07-16 |
| Fahrenheit 451         | 1953-10-19 |
| Lord of the Rings      | 1954-07-29 |
+------------------------+------------+

⚠️ Date ranges on a DATETIME column

customers.created_at holds a date and a time. BETWEEN '2026-01-01' AND '2026-01-31' stops at midnight at the start of January 31, so anyone who signed up later that day would be missed. For date-and-time columns, use a half-open range: on or after the first day, and before the first day of the next month.

SELECT first_name, created_at
FROM customers
WHERE created_at >= '2026-01-01'
  AND created_at <  '2026-02-01'
ORDER BY created_at;

Output

+------------+---------------------+
| first_name | created_at          |
+------------+---------------------+
| Alice      | 2026-01-04 10:15:00 |
| Bob        | 2026-01-06 14:02:00 |
| Carol      | 2026-01-09 09:40:00 |
| Dave       | 2026-01-12 16:25:00 |
| Eve        | 2026-01-20 11:08:00 |
| Frank      | 2026-01-27 13:30:00 |
+------------+---------------------+

Six customers joined in January. The pattern never misses a late-night row and never counts one twice when you move on to February.

NOT BETWEEN

SELECT title, price
FROM books
WHERE price NOT BETWEEN 9 AND 12
ORDER BY price, title;

Output

+------------------------+-------+
| title                  | price |
+------------------------+-------+
| Pride and Prejudice    |  7.99 |
| The Catcher in the Rye |  8.99 |
| The Great Gatsby       |  8.99 |
| Dune                   | 14.99 |
| Lord of the Rings      | 15.99 |
+------------------------+-------+

The three books under $9 and the two over $12.

🔤 LIKE: Matching a Pattern

LIKE compares text with a pattern that can contain two wildcards:

WildcardMatchesPatternMatches, for example
%Any number of characters, including none'The%'The Hobbit, The Great Gatsby, Theory
_Exactly one character'_984'1984, but not 984 or 19984

Starts with

SELECT title
FROM books
WHERE title LIKE 'The %'
ORDER BY title;

Output

+------------------------+
| title                  |
+------------------------+
| The Catcher in the Rye |
| The Great Gatsby       |
| The Hobbit             |
+------------------------+

The space before % makes the pattern "the word The, then more". Without it, 'The%' would also match a title like Theory of Everything.

Ends with

SELECT DISTINCT author
FROM books
WHERE author LIKE '%ley'
ORDER BY author;

Output

+---------------+
| author        |
+---------------+
| Aldous Huxley |
+---------------+

Only Aldous Huxley ends in "ley". (DISTINCT removes duplicate rows from the result; it matters when an author has several books.)

Contains

SELECT title
FROM books
WHERE title LIKE '%the%'
ORDER BY title;

Output

+------------------------+
| title                  |
+------------------------+
| Lord of the Rings      |
| The Catcher in the Rye |
| The Great Gatsby       |
| The Hobbit             |
+------------------------+

Four titles. LIKE follows the same case-insensitive collation as =, so the lowercase pattern finds "The" at the start of three titles and "the" in the middle of Lord of the Rings.

Exactly one character: _

SELECT first_name
FROM customers
WHERE first_name LIKE '___'
ORDER BY first_name;

Output

+------------+
| first_name |
+------------+
| Bob        |
| Eve        |
+------------+

Three underscores, three characters exactly: Bob and Eve.

SELECT DISTINCT author
FROM books
WHERE author LIKE '_a%'
ORDER BY author;

Output

+--------------+
| author       |
+--------------+
| Harper Lee   |
| Jane Austen  |
| Ray Bradbury |
+--------------+

One character, then an a, then anything: every author whose name has "a" as its second letter.

NOT LIKE

SELECT title
FROM books
WHERE title NOT LIKE 'The %'
ORDER BY title;

Output

+-----------------------+
| title                 |
+-----------------------+
| 1984                  |
| Brave New World       |
| Dune                  |
| Fahrenheit 451        |
| Lord of the Rings     |
| Pride and Prejudice   |
| To Kill a Mockingbird |
+-----------------------+

💡 LIKE and speed

A pattern with a fixed start, such as 'The %', can use an index on the column and stays fast on big tables. A pattern that starts with % (ends-with or contains) has to read every row. You will meet indexes in Lesson 6.1; for real full-text search MySQL offers FULLTEXT indexes.

🕳️ IS NULL: Finding Missing Values

NULL means "no value here": not zero, not an empty string, but unknown. Any comparison with an unknown value gives an unknown answer, even comparing NULL with itself:

SELECT
    NULL = NULL   AS equals,
    NULL != 'x'   AS not_equals,
    NULL IS NULL  AS is_null;

Output

+--------+------------+---------+
| equals | not_equals | is_null |
+--------+------------+---------+
|   NULL |       NULL |       1 |
+--------+------------+---------+

Think of two customers whose cities you do not know. Are they from the same city? You cannot say, so the answer is unknown. That is why WHERE city = NULL finds nothing (you will see it fail in Common Mistakes) and why SQL has a separate operator that asks the right question: IS NULL.

SELECT first_name, last_name, city
FROM customers
WHERE city IS NULL
ORDER BY first_name;

Output

+------------+-----------+------+
| first_name | last_name | city |
+------------+-----------+------+
| Eve        | Davis     | NULL |
| Hank       | Taylor    | NULL |
+------------+-----------+------+
SELECT first_name, city
FROM customers
WHERE city IS NOT NULL
ORDER BY first_name;

Output

+------------+-------------+
| first_name | city        |
+------------+-------------+
| Alice      | New York    |
| Bob        | Chicago     |
| Carol      | Los Angeles |
| Dave       | Houston     |
| Frank      | New York    |
| Grace      | Chicago     |
+------------+-------------+

Keeping the NULL rows on purpose

Back to the customers outside New York. If the people without a city should count as "not New York", say so explicitly:

SELECT first_name, city
FROM customers
WHERE city != 'New York' OR city IS NULL
ORDER BY first_name;

Output

+------------+-------------+
| first_name | city        |
+------------+-------------+
| Bob        | Chicago     |
| Carol      | Los Angeles |
| Dave       | Houston     |
| Eve        | NULL        |
| Grace      | Chicago     |
| Hank       | NULL        |
+------------+-------------+

Six rows now: the four from before plus Eve and Hank.

✅ The NULL-safe equals: <=>

MySQL also has <=>, an "equals" that treats two NULLs as equal and never answers unknown. WHERE city <=> NULL works like IS NULL. It is handy when you compare two columns that may both be empty, but it is MySQL-specific: IS NULL and IS NOT NULL are clearer and work in every database.

🧮 Operator Precedence and Parentheses

When one WHERE clause mixes operators, MySQL does not simply read left to right. Like multiplication before addition in arithmetic, some operators bind more tightly than others:

EvaluatedOperators
1stComparisons: = != < > IS LIKE IN BETWEEN
2ndNOT
3rdAND
4thOR

The rule that bites is the last two lines: AND before OR. Suppose you want "Tolkien or Orwell books under $12" and write it the way you would say it:

SELECT title, author, price
FROM books
WHERE author = 'J.R.R. Tolkien' OR author = 'George Orwell' AND price < 12
ORDER BY price;

Output

+-------------------+----------------+-------+
| title             | author         | price |
+-------------------+----------------+-------+
| 1984              | George Orwell  |  9.99 |
| The Hobbit        | J.R.R. Tolkien | 10.99 |
| Lord of the Rings | J.R.R. Tolkien | 15.99 |
+-------------------+----------------+-------+

Lord of the Rings at $15.99 is in the result. MySQL read the condition as author = 'J.R.R. Tolkien' OR (author = 'George Orwell' AND price < 12): every Tolkien book, plus the cheap Orwell ones. Parentheses say what you meant:

graph TD A["you write: A OR B AND C"] --> B["MySQL reads: A OR (B AND C)"] B --> C["you meant: (A OR B) AND C"] C --> D["so type the parentheses"] 
SELECT title, author, price
FROM books
WHERE (author = 'J.R.R. Tolkien' OR author = 'George Orwell')
  AND price < 12
ORDER BY price;

Output

+------------+----------------+-------+
| title      | author         | price |
+------------+----------------+-------+
| 1984       | George Orwell  |  9.99 |
| The Hobbit | J.R.R. Tolkien | 10.99 |
+------------+----------------+-------+

Now the price limit applies to both authors. Writing the list with IN avoids the trap altogether: WHERE author IN ('J.R.R. Tolkien', 'George Orwell') AND price < 12.

✅ Rule of thumb

Whenever a condition mixes AND and OR, add parentheses, even where they are not strictly needed. They cost nothing and tell the next reader (including you, next month) exactly what you meant.

A longer filter

In-stock books that are either under $10 or by Tolkien:

SELECT title, author, price
FROM books
WHERE in_stock = TRUE
  AND (price < 10 OR author = 'J.R.R. Tolkien')
ORDER BY price;

Output

+---------------------+----------------+-------+
| title               | author         | price |
+---------------------+----------------+-------+
| Pride and Prejudice | Jane Austen    |  7.99 |
| Brave New World     | Aldous Huxley  |  9.49 |
| 1984                | George Orwell  |  9.99 |
| The Hobbit          | J.R.R. Tolkien | 10.99 |
| Lord of the Rings   | J.R.R. Tolkien | 15.99 |
+---------------------+----------------+-------+

Write long filters one condition per line, with the AND or OR at the start of the line: you can read them top to bottom and comment out a line while testing.

⚠️ Common Mistakes

1. Forgetting the quotes around text

SELECT title FROM books WHERE author = Tolkien;

Error

ERROR 1054 (42S22): Unknown column 'Tolkien' in 'where clause'

What it means: without quotes, Tolkien is read as the name of a column, and books has no such column. Fix: put text values in single quotes: WHERE author = 'J.R.R. Tolkien'. (MySQL also accepts double quotes for text by default, but single quotes are standard SQL and work everywhere.)

2. Writing = NULL (silent)

SELECT first_name, city
FROM customers
WHERE city = NULL;

Output

Empty set

What it means: no error, and no rows, even though Eve and Hank have no city. city = NULL is unknown for every row, so nothing passes. Fix: WHERE city IS NULL. The same goes for != NULL, which should be IS NOT NULL.

3. Expecting != to include the missing values (silent)

SELECT COUNT(*) AS not_in_houston
FROM customers
WHERE city != 'Houston';

Output

+----------------+
| not_in_houston |
+----------------+
|              5 |
+----------------+

What it means: eight customers, one in Houston, so you expect 7. You get 5, because the two customers without a city are neither equal nor unequal to Houston: they are unknown and dropped. Fix: decide what the empty rows should do and say it: WHERE city != 'Houston' OR city IS NULL gives 7. The same applies to NOT IN, NOT LIKE and NOT BETWEEN.

4. Mixing AND and OR without parentheses (silent)

The goal: in-stock books by Orwell or Salinger.

SELECT title, author, in_stock
FROM books
WHERE in_stock = TRUE AND author = 'George Orwell' OR author = 'J.D. Salinger'
ORDER BY title;

Output

+------------------------+---------------+----------+
| title                  | author        | in_stock |
+------------------------+---------------+----------+
| 1984                   | George Orwell |        1 |
| The Catcher in the Rye | J.D. Salinger |        0 |
+------------------------+---------------+----------+

What it means: The Catcher in the Rye is out of stock (in_stock is 0), yet it is in the list. AND ran first, so the stock check only applied to Orwell. Fix: group the alternatives: WHERE in_stock = TRUE AND (author = 'George Orwell' OR author = 'J.D. Salinger'), which returns only 1984.

5. Using = with a wildcard (silent)

SELECT title
FROM books
WHERE title = 'The %';

Output

Empty set

What it means: = looks for a title that is literally "The %", percent sign included. Wildcards only mean something to LIKE. Fix: WHERE title LIKE 'The %'.

🏋️ Exercise 4 (Stretch): The Picky Customer

A customer wants a book that is in stock, either under $10 or published after 1960, and not by Jane Austen (she has read them all). Write it as one query showing title, author, price and published date. Then remove your parentheses and explain why the result changes.

💡 Hint

Three conditions joined by AND; the middle one is itself an OR and needs parentheses. "After 1960" means after December 31, 1960.

✅ Solution 
SELECT title, author, price, published
FROM books
WHERE in_stock = TRUE
  AND (price < 10 OR published > '1960-12-31')
  AND author != 'Jane Austen'
ORDER BY price;

Output

+-----------------+---------------+-------+------------+
| title           | author        | price | published  |
+-----------------+---------------+-------+------------+
| Brave New World | Aldous Huxley |  9.49 | 1932-01-01 |
| 1984            | George Orwell |  9.99 | 1949-06-08 |
| Dune            | Frank Herbert | 14.99 | 1965-08-01 |
+-----------------+---------------+-------+------------+

Without the parentheses the condition becomes (in_stock = TRUE AND price < 10) OR (published > '1960-12-31' AND author != 'Jane Austen'), because AND binds before OR. ❓ Common Questions at This Stage

Can I write && and || instead of AND and OR?

MySQL still understands them, but both are deprecated and will be removed in a future release. MySQL tells you so with a warning:

SELECT title FROM books WHERE price > 14 && in_stock;
SHOW WARNINGS;

Output

+-------------------+
| title             |
+-------------------+
| Dune              |
| Lord of the Rings |
+-------------------+
+---------+------+------------------------------------------------------------------------------------+
| Level   | Code | Message                                                                            |
+---------+------+------------------------------------------------------------------------------------+
| Warning | 1287 | '&&' is deprecated and will be removed in a future release. Please use AND instead |
+---------+------+------------------------------------------------------------------------------------+

In standard SQL, || means "join two strings", so code that uses it for OR also breaks when moved to another database. MariaDB accepts both without a warning, which is no reason to use them. Write AND, OR and NOT.

How do I search for a real % or _ character?

Put a backslash in front of it: LIKE '%\_%' finds values containing an underscore, and LIKE '%50\%%' finds "50%". The backslash tells LIKE to treat the next character literally.

How do I make a search case-sensitive?

Compare with a binary collation: WHERE author = 'j.r.r. tolkien' COLLATE utf8mb4_bin finds nothing, because utf8mb4_bin compares the exact characters. Most of the time case-insensitive matching is what users expect, so reach for this only when case really matters (passwords are never compared this way; they are hashed).

Does the order of conditions joined by AND matter for speed?

No. MySQL's optimizer decides which condition to check first, and it uses indexes where it can (Lesson 6.1). Order your conditions for the human reader.

🌟 Going Further: Bonus Challenge

LIKE has only two wildcards. For richer patterns MySQL has regular expressions: WHERE title REGEXP '^[0-9]' finds titles that start with a digit, and REGEXP_LIKE(title, 'the$') is the same idea as a function. Find (1) every title that starts with a digit and (2) every author whose last name starts with B or H. Note that MariaDB understands REGEXP but not the REGEXP_LIKE() function, so prefer REGEXP if your code must run on both.

📝 Lesson Summary

🎓 Key Takeaways

  • WHERE tests every row; only rows where the test is true are kept (false and unknown are dropped)
  • Comparison operators work on numbers, dates and text; text comparisons are case-insensitive with _ci collations
  • AND narrows, OR widens, NOT flips; AND is evaluated before OR, so use parentheses when mixing them
  • IN matches a list, BETWEEN an inclusive range, LIKE a pattern (% any characters, _ one character)
  • NULL is unknown: test it with IS NULL / IS NOT NULL, never = NULL
  • !=, NOT IN and NOT LIKE silently drop NULL rows; add OR col IS NULL when you want them
  • For date-and-time columns, use a half-open range: >= start AND < next_start
