🔄 Lesson 2.3: CRUD Operations

Your bookstore has tables but no books. This lesson fills it: you will add rows, read them back, change them and remove them, the four operations behind every app that stores anything. You will also learn the habits that keep a one-word slip from changing every row in a table.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Create rows with INSERT: one row, many rows, with defaults, and read back the new id
  • Read rows with SELECT: chosen columns, aliases, calculated columns and DISTINCT
  • Update and delete exactly the rows you mean, using the "SELECT first" habit and safe-updates mode
  • Write an upsert with INSERT ... AS new ON DUPLICATE KEY UPDATE, and explain how it differs from REPLACE and INSERT IGNORE
  • Read and fix errors 1054, 1062, 1136 and 1175
  • ⏱️ Time 105 minutes
  • 📋 Prerequisites Lesson 2.2: Data Types & Constraints

🔁 What Is CRUD?

CRUD stands for the four things you can do to stored data, and SQL has one statement for each:

OperationSQLIn the bookstore
CreateINSERTA new customer signs up
ReadSELECTThe website lists the books in stock
UpdateUPDATEA price changes; a customer moves
DeleteDELETEA book is discontinued
graph TD A["INSERT adds rows"] --> B["SELECT reads them"] B --> C["UPDATE changes some"] B --> D["DELETE removes some"] C --> E["WHERE picks which rows"] D --> E

The diagram's last box is the theme of this lesson. INSERT only ever adds; UPDATE and DELETE act on every row their WHERE clause matches, and on every row in the table if there is no WHERE at all.

➕ Create: INSERT

One row

Name the table, list the columns you are filling, then give the values in the same order:

INSERT INTO books (title, author, price, pages, published)
VALUES ('Dune', 'Frank Herbert', 12.99, 412, '1965-08-01');

Output

Query OK, 1 row affected

Text and dates go in single quotes; numbers do not. Two columns were left out on purpose: id (AUTO_INCREMENT fills it) and in_stock (its DEFAULT TRUE applies).

SELECT * FROM books;
SELECT LAST_INSERT_ID();

Output

+----+-------+---------------+-------+-------+------------+----------+
| id | title | author        | price | pages | published  | in_stock |
+----+-------+---------------+-------+-------+------------+----------+
|  1 | Dune  | Frank Herbert | 12.99 |   412 | 1965-08-01 |        1 |
+----+-------+---------------+-------+-------+------------+----------+
+------------------+
| LAST_INSERT_ID() |
+------------------+
|                1 |
+------------------+

SELECT * shows every column. LAST_INSERT_ID() returns the id your session's last insert received, which a program uses to, say, show the new book's page.

Many rows in one statement

Separate the value lists with commas. One statement with many rows is much faster than many one-row statements, because the server does the work of a statement once.

INSERT INTO books (title, author, price, pages, published) VALUES
    ('1984', 'George Orwell', 9.99, 328, '1949-06-08'),
    ('To Kill a Mockingbird', 'Harper Lee', 11.99, 281, '1960-07-11'),
    ('The Great Gatsby', 'F. Scott Fitzgerald', 8.99, 180, '1925-04-10'),
    ('Pride and Prejudice', 'Jane Austen', 7.99, 432, '1813-01-28'),
    ('The Hobbit', 'J.R.R. Tolkien', 10.99, 310, '1937-09-21');

Output

Query OK, 5 rows affected
Records: 5  Duplicates: 0  Warnings: 0

Records: 5 rows were sent and all five were stored. Warnings: 0 is what you want to see.

Giving a value to a column that has a default

A default is only used when you leave the column out. List it and you choose the value:

INSERT INTO books (title, author, price, pages, published, in_stock) VALUES
    ('Brave New World', 'Aldous Huxley', 9.49, 311, '1932-01-01', TRUE),
    ('The Catcher in the Rye', 'J.D. Salinger', 8.99, 234, '1951-07-16', FALSE),
    ('Lord of the Rings', 'J.R.R. Tolkien', 15.99, 1178, '1954-07-29', TRUE);

Output

Query OK, 3 rows affected
Records: 3  Duplicates: 0  Warnings: 0

Without a column list (and why not to)

If you give a value for every column, in table order, you may leave out the column list. NULL for an AUTO_INCREMENT column means "give it the next number":

INSERT INTO books
VALUES (NULL, 'Fahrenheit 451', 'Ray Bradbury', 10.49, 158, '1953-10-19', TRUE);

Output

Query OK, 1 row affected

⚠️ Always list the columns

That statement depends on the table's exact column order. The day someone adds an isbn column, it breaks (error 1136), or worse, puts values in the wrong columns without complaint when the types happen to fit. With a column list, your insert keeps working whatever is added later.

💡 SELECT * is for looking around

SELECT * is perfect at the prompt. In a program or a saved report, name the columns: you fetch only what you use, and the result does not change shape when someone adds a column to the table.

Aliases and calculated columns

A column in the result can be a calculation, and AS gives any result column a name:

SELECT
    title,
    price,
    ROUND(price * 1.08, 2) AS price_with_tax
FROM books
WHERE price > 11;

Output

+-----------------------+-------+----------------+
| title                 | price | price_with_tax |
+-----------------------+-------+----------------+
| Dune                  | 12.99 |          14.03 |
| To Kill a Mockingbird | 11.99 |          12.95 |
| Lord of the Rings     | 15.99 |          17.27 |
+-----------------------+-------+----------------+

ROUND(value, 2) keeps the result to cents. Calculations never change the table: price is still the stored price. The WHERE price > 11 line keeps only the rows that pass the test; Lesson 3.1 is all about WHERE.

SELECT
    CONCAT(first_name, ' ', last_name) AS full_name,
    email
FROM customers;

Output

+----------------+-------------------+
| full_name      | email             |

| Alice Johnson  | alice@example.com |
| Bob Smith      | bob@example.com   |
| Carol Williams | carol@example.com |
| Dave Brown     | dave@example.com  |
| Eve Davis      | eve@example.com   |
+----------------+-------------------+

DISTINCT: each value once

SELECT DISTINCT author
FROM books
ORDER BY author;

Output

+---------------------+
| author              |
+---------------------+
| Aldous Huxley       |
| F. Scott Fitzgerald |
| Frank Herbert       |
| George Orwell       |
| Harper Lee          |
| J.D. Salinger       |
| J.R.R. Tolkien      |
| Jane Austen         |
| Ray Bradbury        |

Ten books, nine authors: Tolkien appears once. ORDER BY author sorts the result alphabetically; without it, rows come back in whatever order the server finds convenient (Lesson 3.2 covers sorting). DISTINCT on a column with NULLs keeps one NULL row.

✏️ Update: Changing Rows

UPDATE has three parts: the table, the new values (SET), and which rows (WHERE).

One row, by its id

The shop raises the price of Dune. The safest way to point at one row is its primary key:

UPDATE books
SET price = 14.99
WHERE id = 1;

Output

Query OK, 1 row affected
Rows matched: 1  Changed: 1  Warnings: 0

Read the second line every time: Rows matched: 1 is how many rows the WHERE found, Changed: 1 how many really got a new value. Run the same statement again:

UPDATE books
SET price = 14.99
WHERE id = 1;

Output

Query OK, 0 rows affected
Rows matched: 1  Changed: 0  Warnings: 0

The row matched, but the price was already 14.99, so nothing changed. "Matched 0" would have told you the WHERE found nothing at all, usually a typo.

Several columns at once

Separate the assignments with commas. The Great Gatsby sells out and gets a new price for its next printing:

UPDATE books
SET in_stock = FALSE,
    price = 9.49
WHERE id = 4;
SELECT title, price, in_stock FROM books WHERE id = 4;

Output

Query OK, 1 row affected
Rows matched: 1  Changed: 1  Warnings: 0
+------------------+-------+----------+
| title            | price | in_stock |
+------------------+-------+----------+
| The Great Gatsby |  9.49 |        0 |
+------------------+-------+----------+
1 row in set

Many rows, the safe way: SELECT first

A sale: 10% off every book over $10. Before changing anything, run a SELECT with the same WHERE to see exactly which rows you are about to touch:

SELECT id, title, price
FROM books
WHERE price > 10;

Output

+----+-----------------------+-------+
| id | title                 | price |
+----+-----------------------+-------+
|  1 | Dune                  | 14.99 |
|  3 | To Kill a Mockingbird | 11.99 |
|  6 | The Hobbit            | 10.99 |
|  9 | Lord of the Rings     | 15.99 |
| 10 | Fahrenheit 451        | 10.49 |
+----+-----------------------+-------+

Five books, the ones you expected. Now change them. A new value can be calculated from the old one:

UPDATE books
SET price = ROUND(price * 0.90, 2)
WHERE price > 10;

Output

Query OK, 5 rows affected
Rows matched: 5  Changed: 5  Warnings: 0

Five matched, five changed: the same five the preview showed. That match between preview and result is the whole point of the habit.

🛑 UPDATE without WHERE changes every row

UPDATE books SET price = 0; is a valid statement. MySQL will set every price in the table to zero, report how many rows it changed, and there is no undo. Write the WHERE clause before the SET clause if that helps, run the SELECT preview, and turn on safe-updates mode (Common Mistakes, number 1) on any server that matters.

🗑️ Delete: Removing Rows

DELETE FROM table WHERE ... removes the rows the WHERE matches, all their columns at once.

DELETE FROM books WHERE id = 10;
SELECT * FROM books WHERE id = 10;

Output

Query OK, 1 row affected
Empty set

"Empty set" is MySQL's way of printing a result with no rows: Fahrenheit 451 is gone. Add it back and look at its id:

INSERT INTO books (title, author, price, pages, published)
VALUES ('Fahrenheit 451', 'Ray Bradbury', 10.49, 158, '1953-10-19');
SELECT id, title FROM books WHERE title = 'Fahrenheit 451';

Output

+----+----------------+
| id | title          |
+----+----------------+
| 11 | Fahrenheit 451 |
+----+----------------+

Id 11, not 10. AUTO_INCREMENT never reuses a number, even a deleted one, so a gap is normal. Never "fill" gaps: other tables, emails or receipts may still mention the old id 10, and it should never come to mean a different book.

Several rows: preview first, again

SELECT id, title, price FROM books WHERE in_stock = FALSE;

Output

+----+------------------------+-------+
| id | title                  | price |
+----+------------------------+-------+
|  4 | The Great Gatsby       |  9.49 |
|  8 | The Catcher in the Rye |  8.99 |
+----+------------------------+-------+
DELETE FROM books WHERE in_stock = FALSE;

Output

Query OK, 2 rows affected

Two rows previewed, two rows deleted.

DELETE, TRUNCATE or DROP?

StatementRemovesTable kept?AUTO_INCREMENT
DELETE FROM t WHERE ...The matching rowsYesContinues
DELETE FROM tEvery row, one by oneYesContinues
TRUNCATE TABLE tEvery row, all at onceYesBack to 1
DROP TABLE tRows and tableNoGone

🛑 DELETE without WHERE empties the table

DELETE FROM customers; removes every customer and reports the count afterward. The table survives, the data does not. The same habits protect you: SELECT with the same WHERE first, and safe-updates mode.

🔀 Upserts: Insert or Update

Sometimes you do not know whether a row exists yet: a nightly import sends every category with its latest description, some new, most already there. A plain INSERT of an existing name fails with error 1062 (the name column is UNIQUE). An upsert means "insert it, or update it if it is already there".

INSERT ... ON DUPLICATE KEY UPDATE

INSERT INTO categories (name, description)
VALUES ('Fiction', 'Imaginative prose of every kind') AS new
ON DUPLICATE KEY UPDATE description = new.description;
SELECT id, name, description FROM categories WHERE name = 'Fiction';

Output

Query OK, 2 rows affected
+----+---------+---------------------------------+
| id | name    | description                     |
+----+---------+---------------------------------+
|  1 | Fiction | Imaginative prose of every kind |
+----+---------+---------------------------------+
1 row in set

Read it in three parts. The INSERT tries to add Fiction. AS new names the row you tried to insert. Because a row with that name already exists (a UNIQUE or primary key clash), the ON DUPLICATE KEY UPDATE part runs instead, setting the existing row's description to new.description. The id stays 1.

The "rows affected" count tells you which branch ran: 1 means a new row was inserted, 2 means an existing row was updated, 0 means it existed and already had those values. Try a name that does not exist yet:

INSERT INTO categories (name, description)
VALUES ('Mystery', 'Crimes, clues and detectives') AS new
ON DUPLICATE KEY UPDATE description = new.description;

Output

Query OK, 1 row affected

The old VALUES() form is deprecated

Many tutorials, and a lot of existing code, write VALUES(column) instead of a row alias. MySQL 9.7 still runs it, but warns:

INSERT INTO categories (name, description)
VALUES ('Mystery', 'Detectives and puzzles')
ON DUPLICATE KEY UPDATE description = VALUES(description);
SHOW WARNINGS;

Output

Query OK, 2 rows affected, 1 warning
+---------+------+---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
| Level   | Code | Message                                                                                                                                                                                                                   |
+---------+------+---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
| Warning | 1287 | 'VALUES function' is deprecated and will be removed in a future release. Please use an alias (INSERT INTO ... VALUES (...) AS alias) and replace VALUES(col) in the ON DUPLICATE KEY UPDATE clause with alias.col instead |
+---------+------+---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
1 row in set

The warning spells out the replacement: the AS alias form you just used. Write new code that way.

🐬 Version note: MariaDB does not have the row alias

MySQL 9.7 and 8.4 support VALUES (...) AS new. MariaDB (XAMPP, many shared hosts) does not, and stops at the alias:

INSERT INTO categories (name, description)
VALUES ('Fiction', 'Imaginative prose of every kind') AS new
ON DUPLICATE KEY UPDATE description = new.description;

Error on MariaDB

ERROR 1064 (42000): You have an error in your SQL syntax; check the manual that corresponds to your MariaDB server version for the right syntax to use near 'AS new
ON DUPLICATE KEY UPDATE description = new.description' at line 2

On MariaDB, write description = VALUES(description), which is not deprecated there and gives no warning. If the same code must run on both, the VALUES() form works on all three servers (with a warning on MySQL) until MySQL removes it.

Two shortcuts with sharp edges

INSERT IGNORE skips a row that would cause a duplicate, and many other errors too, turning them into warnings:

INSERT IGNORE INTO categories (name, description)
VALUES ('Fantasy', 'This text is never stored');
SHOW WARNINGS;

Output

Query OK, 0 rows affected, 1 warning
+---------+------+-----------------------------------------------------+
| Level   | Code | Message                                             |
+---------+------+-----------------------------------------------------+
| Warning | 1062 | Duplicate entry 'Fantasy' for key 'categories.name' |
+---------+------+-----------------------------------------------------+
1 row in set

REPLACE deletes the clashing row and inserts a brand-new one:

REPLACE INTO categories (name) VALUES ('Classic');
SELECT id, name, description FROM categories WHERE name = 'Classic';

Output

Query OK, 2 rows affected
+----+---------+-------------+
| id | name    | description |
+----+---------+-------------+
| 10 | Classic | NULL        |
+----+---------+-------------+
1 row in set

⚠️ REPLACE is delete plus insert

"2 rows affected" is one deleted and one inserted. The Classic category now has a new id, and its description is gone, because a column you do not list gets its default, not its old value. Once other tables point at categories by id (Module 4), that delete can be refused or can take related rows with it. Prefer ON DUPLICATE KEY UPDATE, which changes only the columns you name and keeps the id.

⚠️ Common Mistakes

1. Forgetting WHERE (and the switch that catches it)

The mysql client has a safe-updates mode that refuses UPDATE and DELETE statements whose WHERE does not use a key column. Turn it on for your session and try the classic slip:

SET SQL_SAFE_UPDATES = 1;
UPDATE books SET price = 0;

Error

ERROR 1175 (HY000): You are using safe update mode and you tried to update a table without a WHERE that uses a KEY column.

What it means: without safe-updates, this would have set every price to zero. With it, MySQL refuses any change that does not name rows by a key (such as WHERE id = 3) or carry a LIMIT. Fix: add the WHERE you meant. To make it permanent, start the client with mysql --safe-updates -u root -p, or put safe-updates under [mysql] in your option file. Turn it off again for the rest of this lesson, whose examples filter by non-key columns:

SET SQL_SAFE_UPDATES = 0;

2. Values that do not match the columns

INSERT INTO books (title, author, price)
VALUES ('Emma', 'Jane Austen');

Error

ERROR 1136 (21S01): Column count doesn't match value count at row 1

What it means: three columns, two values. The same error appears when you leave out the column list and give fewer values than the table has columns. Fix: make the two lists the same length, in the same order.

3. Text without quotes

INSERT INTO books (title, author, price)
VALUES (Emma, 'Jane Austen', 7.99);

Error

ERROR 1054 (42S22): Unknown column 'Emma' in 'field list'

What it means: without quotes, Emma is read as a column name, and there is no such column. Fix: put text and dates in single quotes, 'Emma'. For a quote inside the text, double it: 'Charlotte''s Web'.

4. A duplicate in a UNIQUE column

INSERT INTO customers (first_name, last_name, email)
VALUES ('Alicia', 'Jones', 'alice@example.com');

Error

ERROR 1062 (23000): Duplicate entry 'alice@example.com' for key 'customers.email'

What it means: Alice already uses that email, and email is UNIQUE. The constraint is doing its job: two accounts on one email is a support nightmare. Fix: use the right email, or, if you meant "update Alice", use UPDATE or an upsert.

5. AND instead of a comma in SET (silent)

You mean to change Dune's price and mark it out of stock:

UPDATE books
SET price = 15.99 AND in_stock = FALSE
WHERE id = 1;
SELECT title, price, in_stock FROM books WHERE id = 1;

Output

Query OK, 1 row affected
Rows matched: 1  Changed: 1  Warnings: 0
+-------+-------+----------+
| title | price | in_stock |
+-------+-------+----------+
| Dune  |  0.00 |        1 |
+-------+-------+----------+
1 row in set

What it means: no error, no warning, one row changed, and the price is now 0.00 while the book is still in stock. MySQL read the line as price = (15.99 AND (in_stock = FALSE)): in_stock = FALSE is false (0), so the whole expression is 0. Fix: assignments are separated by commas: SET price = 15.99, in_stock = FALSE. After any UPDATE, look at the rows you changed.

🏋️ Exercise 5 (Stretch): An Idempotent Upsert

Write one statement that adds a category Horror ("Stories meant to frighten") or, if it exists, updates its description. Run it twice and explain the two "rows affected" numbers. Then change the description in the statement and run it a third time. Finally, delete Horror.

💡 Hint

INSERT ... VALUES (...) AS new ON DUPLICATE KEY UPDATE description = new.description. Remember: 1 inserted, 2 updated, 0 unchanged.

✅ Solution 
INSERT INTO categories (name, description)
VALUES ('Horror', 'Stories meant to frighten') AS new
ON DUPLICATE KEY UPDATE description = new.description;

INSERT INTO categories (name, description)
VALUES ('Horror', 'Stories meant to frighten') AS new
ON DUPLICATE KEY UPDATE description = new.description;

INSERT INTO categories (name, description)
VALUES ('Horror', 'Ghosts, monsters and dread') AS new
ON DUPLICATE KEY UPDATE description = new.description;

DELETE FROM categories WHERE name = 'Horror';

Output

Query OK, 1 row affected
Query OK, 0 rows affected
Query OK, 2 rows affected
Query OK, 1 row affected

1 (inserted), 0 (already identical, nothing to change), 2 (updated), then 1 row deleted. Because running it twice leaves the same result as running it once, the statement is idempotent, the property that makes import scripts safe to rerun.

❓ Common Questions at This Stage

Can I undo an UPDATE or DELETE?

Not after it has run in a normal session: the mysql client commits each statement immediately. Transactions (Lesson 7.2) let you group statements and roll them back before committing. Until then, your safety nets are the SELECT preview, safe-updates mode, and scripts like load_bookstore_data.sql that rebuild practice data.

How does a website send a customer's input into an INSERT safely?

Never by pasting the text into the SQL string: a name like O'Brien breaks the statement, and a malicious one can change what it does (SQL injection). Applications use parameterized queries (also called prepared statements), where the SQL has placeholders and the values travel separately: INSERT INTO customers (first_name, email) VALUES (?, ?). Every language's MySQL library supports them. In this course you type the values yourself, so quotes are enough.

Why did a failed or updated upsert leave a gap in the ids?

An INSERT reserves the next AUTO_INCREMENT number before it knows whether the row clashes. When ON DUPLICATE KEY UPDATE or INSERT IGNORE ends up not inserting, that number is simply not used. Gaps like this are normal and never a problem.

Should I use double quotes for text?

MySQL accepts "Dune" as text by default, but standard SQL (and MySQL in ANSI_QUOTES mode, and PostgreSQL) reads double quotes as a column name. Single quotes work everywhere, so this course always uses them.

📝 Lesson Summary

🎓 Key Takeaways

  • INSERT INTO t (columns) VALUES (...), (...) adds rows; always list the columns, and let AUTO_INCREMENT and defaults fill the rest
  • SELECT reads rows: name the columns you need, rename with AS, calculate freely, remove duplicates with DISTINCT
  • UPDATE and DELETE touch every row their WHERE matches, and every row in the table without one
  • Preview with a SELECT using the same WHERE, check Rows matched / Changed, and use safe-updates mode
  • Separate SET assignments with commas, never AND
  • AUTO_INCREMENT ids are never reused; gaps are normal
  • Upsert with INSERT ... AS new ON DUPLICATE KEY UPDATE col = new.col (MariaDB: VALUES(col)); avoid REPLACE on rows other tables point to
