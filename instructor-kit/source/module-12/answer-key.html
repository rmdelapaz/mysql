7.4 · User Management & Permissions: self-check

Q1
A server has 'app'@'localhost' and 'app'@'%'. How many accounts is that?
A) One account that may connect from two places
B) Two separate accounts, each with its own password and privileges
C) One account: % already includes localhost, so the second row is ignored
D) None: the second CREATE USER failed because the name was taken
Why: An account is the pair 'user'@'host'. The same name with another host is another account, which is why SHOW GRANTS FOR 'shop_reports'@'%' fails with 1141 when only @'localhost' exists.
A is wrong: Privileges and passwords belong to each pair separately.
C is wrong: Both rows are real accounts; MySQL picks the most specific host that matches a login.
D is wrong: The pair is the identity; the same user name with a different host is allowed.
Q2
How many lines does the SHOW GRANTS print, and what are they?
CREATE USER 'kit_quiz'@'localhost' IDENTIFIED BY 'CHANGE-ME-quiz-1';
GRANT SELECT ON bookstore.* TO 'kit_quiz'@'localhost';
GRANT INSERT ON bookstore.orders TO 'kit_quiz'@'localhost';
SHOW GRANTS FOR 'kit_quiz'@'localhost';
Three: GRANT USAGE ON *.*, GRANT SELECT ON `bookstore`.*, GRANT INSERT ON `bookstore`.`orders`
Why: Every account has the USAGE line ("may connect"). Then one line per level: the database-level SELECT and the table-level INSERT stay separate lines because they are at different levels.
Q3
An app account gets ERROR 1143 (42000): SELECT command denied ... for column 'city' in table 'customers'. What does it mean?
A) The password is wrong
B) The account may not read the customers table at all
C) The account is locked
D) The account has column privileges on customers, and city is not one of them
Why: 1143 is the column-level cousin of 1142: the account may read some columns of customers (granted with SELECT (col, ...)) but not this one. SELECT * fails with 1142 for the same reason.
A is wrong: A wrong password is 1045, at login.
B is wrong: That is 1142 (table level); 1143 names a column.
C is wrong: A locked account is 3118, at login.
Q4
Tom and Lena have the role bookstore_sales as a default role. An administrator runs GRANT INSERT ON bookstore.customers TO 'bookstore_sales';. When can they insert customers?
A) Right away, both of them, and every future account given the role
B) Only after FLUSH PRIVILEGES
C) Only after each is granted INSERT on customers directly
D) Only accounts created after the GRANT
Why: A role is a bundle: changing it changes every account that has it, at once. That is the whole point of roles (and GRANT never needs FLUSH PRIVILEGES).
B is wrong: GRANT, REVOKE and CREATE USER update the privileges in memory immediately.
C is wrong: That would defeat the role.
D is wrong: Existing members get it too.
Q5
shop_reports has GRANT SELECT ON bookstore.*. What does REVOKE SELECT ON bookstore.books FROM 'shop_reports'@'localhost'; do?
A) Hides books and keeps every other table readable
B) Removes SELECT on the whole database
C) Fails with ERROR 1147: there is no table-level grant on books to take away
D) Works only after FLUSH PRIVILEGES
Why: Revoke at the level you granted. A database-level grant cannot have one table cut out of it; to hide one table, grant table by table (or through views).
A is wrong: MySQL has no "all tables except" grant.
B is wrong: The table-level REVOKE does not touch the database-level grant.
D is wrong: The statement fails; FLUSH PRIVILEGES changes nothing about that.
Q6
Write the statement that disables 'kit_mailer'@'localhost' without losing its grants.
ALTER USER 'kit_mailer'@'localhost' ACCOUNT LOCK;
Why: A locked account keeps its privileges; a login fails with 3118 until ALTER USER ... ACCOUNT UNLOCK. DROP USER would delete the account and its grants.

8.1 · Importing & Exporting Data: self-check

Q7
Where do you type mysqldump?
A) At the mysql> prompt, ending with ;
B) In phpMyAdmin's SQL tab
C) At the terminal's shell prompt ($ or PS>), not inside the mysql client
D) Inside a SOURCE file
Why: mysqldump is a separate program that connects like any client. Typed at mysql> the server receives it as SQL and answers ERROR 1064 (debug_import.sql, bug A).
A is wrong: That is the 1064 the demo showed.
B is wrong: phpMyAdmin sends SQL to the server too; it has its own Export tab instead.
D is wrong: A SOURCE file is SQL, read by the client and sent to the server.
Q8
Which mysqldump option puts the stored procedures and functions into the backup?
A) --routines
B) --events
C) --single-transaction
D) --databases
Why: Routines are left out by default; --routines adds them (--events adds scheduled events; triggers are in by default).
B is wrong: --events adds scheduled events, not procedures.
C is wrong: --single-transaction makes the dump consistent without locking tables.
D is wrong: --databases adds CREATE DATABASE and USE lines.
Q9
What does this print?
SELECT STR_TO_DATE('07/04/1976', '%m/%d/%Y') AS published,
       NULLIF('', '') AS pages;
1976-07-04 and NULL
Why: STR_TO_DATE reads the text with the US pattern month/day/year and returns a real DATE. NULLIF returns NULL when its two arguments are equal: the trick that turns empty CSV fields into NULL.
Q10
You restore a dump made WITHOUT --databases using mysql -u root -p < bookstore_backup.sql and get ERROR 1046 (3D000) at line 22: No database selected. What is the fix?
A) Take the dump again with --set-gtid-purged=OFF
B) Run SET FOREIGN_KEY_CHECKS = 0 first
C) Use SOURCE instead of <
D) Name the target database: mysql -u root -p bookstore_test < bookstore_backup.sql (or dump with --databases)
Why: Without --databases the file has no CREATE DATABASE or USE line, so you choose the target when you restore (real output from the demo's shell run).
A is wrong: That fixes ERROR 3546 (GTIDs), a different failure.
B is wrong: Foreign keys are not the problem; no database is selected.
C is wrong: SOURCE without a current database fails the same way.
Q11
Why load a stranger's CSV into a staging table before touching books?
A) LOAD DATA cannot load into a table that has foreign keys
B) To look at, convert and check the rows (dates, empty values, missing authors) before any real table changes
C) Staging tables load faster than real tables
D) LOAD DATA LOCAL only works with staging tables
Why: A staging table with the file's columns lets you SELECT what arrived, find what is missing with a LEFT JOIN, and then copy only the good rows in one transaction.
A is wrong: LOAD DATA can load into any table you may INSERT into.
C is wrong: Speed is not the reason.
D is wrong: LOCAL works with any table.
Q12
You run SELECT title FROM books INTO OUTFILE '/var/lib/mysql-files/titles.txt'; a second time. What happens?
A) The file is overwritten with the new rows
B) The rows are added to the end of the file
C) ERROR 1086: the file already exists
D) MySQL writes titles(1).txt
Why: INTO OUTFILE never overwrites, which protects earlier exports and system files. Write to a new name (add the date) or delete the old file at the terminal.
A is wrong: Overwriting is exactly what MySQL refuses to do.
B is wrong: There is no append mode.
D is wrong: MySQL never renames for you.

SELECT STR_TO_DATE('31.12.1999', '%d.%m.%Y') AS eu_date,

+------------+------------+
| eu_date    | us_pattern |

Why: The European pattern reads the text; the US pattern does not match it, so STR_TO_DATE returns NULL (with warning 1411). In an INSERT, strict mode turns that into an error (debug_import.sql, bug C).

| empty_to_null | pages_text | for_people |
+---------------+------------+------------+
| NULL          | 412        |            |
+---------------+------------+------------+
Why: NULLIF('', '') is NULL (the empty CSV field becomes a real NULL); NULLIF('412', '') keeps the text; COALESCE(NULL, '') turns NULL into an empty string, for files people open.

The Lesson Pages' Own Quick Quizzes

Lesson 7.4 · User Management & Permissions
  1. B Connect, but read or change nothing: A new account only has USAGE, which means no privileges: it can connect, but every table access fails until you GRANT something.
  2. A 'shop_reports'@'%' is a different account, and it does not exist: An account is the pair of user and host. shop_reports at % is a separate account that was never created, so it has no grants to show.
  3. C It fails with error 1524; keep caching_sha2_password and update the app's driver: The plugin was removed in MySQL 9, so the statement fails with ERROR 1524. Use the default caching_sha2_password and update the program's MySQL driver if it cannot connect.
  4. A The role is not active: run SET DEFAULT ROLE ALL TO 'marcus'@'localhost': Granted roles are inactive until activated. SET DEFAULT ROLE ALL TO marcus activates them at every login (or Marcus runs SET ROLE ALL in his session).
  5. B Its own account with SELECT on the catalog tables and INSERT on the order tables: The website reads the catalog and adds orders, so it gets SELECT on those tables and INSERT on the order tables. A bug or attack through the site can do nothing more.
Lesson 8.1 · Importing & Exporting Data
  1. B Take the dump again with --set-gtid-purged=OFF: MySQL 9.7 has GTIDs on by default, and the dump tries to set GTID_PURGED on a server that already has those GTIDs. --set-gtid-purged=OFF leaves that line out.
  2. C Fails with error 1290: The server only reads and writes files inside its secure_file_priv folder, so a path in /tmp is refused with error 1290.
  3. A (..., @d) SET published = STR_TO_DATE(@d, '%m/%d/%Y'): Reading the raw text into a user variable and converting it in SET is the general pattern for any value that needs reshaping on the way in.
  4. C Run SHOW WARNINGS; and inspect the staging rows before using them: With LOCAL, bad values and duplicates become warnings instead of errors. SHOW WARNINGS tells you which rows and why, before the data spreads to real tables.
  5. A It does not contain the user accounts that may use the database: Accounts and grants live in the mysql system database, so a single-database dump does not include them. Keep a separate script for users.

Exit Ticket

  1. Website account: least privilege. It needs to read the catalog and add orders; with no UPDATE or DELETE, a bug or an attacker using its login cannot change prices or erase history.
  2. A trustworthy backup: (1) a dump with the right options (9.7: --single-transaction --routines --events --set-gtid-purged=OFF), (2) a test restore into another database with the counts compared and logged. A dump that was never restored is a hope.
  3. The final project: Rosa Delgado, Maple Street Tool Library. Rules: one open loan per tool; nothing goes out while being repaired; suspended members cannot borrow; at most three tools per member; no safety course, no chainsaw (power tools need Power Tools Basics).

Common Wrong Answers and What They Reveal

  • Q1 C ("% includes localhost"). Treats the host as a filter on one account. Draw two rows of mysql.user.
  • Q3 B (1143 = table). Has not seen column grants; show the support_desk test again.
  • Q4 B (FLUSH PRIVILEGES). Old-tutorial habit; GRANT works at once.
  • Q7 A (mysqldump at mysql>). The most common 8.1 slip; it is bug A of the debug handout.
  • Q10 A (--set-gtid-purged=OFF). Mixes the two restore failures: 3546 is GTIDs, 1046 is a missing database name.
  • Q12 A (overwritten). Expects files to behave like UPDATE; MySQL protects existing files.
  • Exit ticket 2 with only "run mysqldump". The restore test is the half that matters; ask what restore_log.txt would say.
