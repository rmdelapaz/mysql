Session 12: Users, Permissions and Backups

How to teach the twelfth session of MySQL Foundations: user accounts and least privilege (grants at three levels, logging in as each account, roles and the forgotten SET DEFAULT ROLE), then moving data in and out (a mysqldump backup proved by a test restore, the 9.7 GTID trap, a CSV export, a messy file through a staging table), and the hand-out of the final-project brief.

How to Use This Guide

  • Same rhythm for both lessons: frame → live demo → guided lab → start the lesson's own project. The lesson exercises, quiz and journal are homework.
  • Session 12 is the last teaching session of Part 2: it ends with a 20-minute final-project brief before the wrap-up, so each lesson gets 65 minutes in the room (the pages estimate 105 + 105 alone).
  • This session has two windows of a different kind: for 7.4 a second mysql client logged in as another account, for 8.1 a plain terminal for mysqldump. Every output below is real: the logins AS shop_reports, support_desk and tom were made with the mysql client on the kit's MySQL 9.7 test server; the shell commands ran there with the same options (shown as learners type them, -u root -p).
  • Keep lesson_19.html (7.4), lesson_20.html (8.1) and lesson_final_project.html (8.2, for the brief) open in browser tabs. Labs live in labs/module-12/; _solution.sql files are yours.
  • Safety. Never change root's password or privileges in class, and never let learners practice on a server other people depend on. Every lab account is a kit_ demo account that its own file drops again.
The #1 risk of Session 12: someone locks themselves out

Lesson 7.4 is the first lesson where a typo can lock a learner out of their own server: ALTER USER CURRENT_USER() IDENTIFIED BY ..., or a REVOKE aimed at root. Before: say it once at the start of 7.4 and write it on the board: "we only ever change kit_ and demo accounts". In the room: if someone does lose root anyway, do not fix it live; pair them up and help at the break (recovery means restarting the server with special options, Lesson 7.4's ground rules). After: the labs and the checker refuse root and SET GLOBAL, so homework is safe.

Warm-up: Transactions and JSON

10 min
Timing

The questions and their answers
  1. W1 (7.2) START TRANSACTION;, an UPDATE, an ALTER TABLE, then ROLLBACK;. Is the UPDATE undone? Answer: No. ALTER TABLE caused an implicit commit before it ran, so the UPDATE was already committed and the ROLLBACK had nothing to undo.
  2. W2 (7.2) What is the difference between ERROR 1205 and ERROR 1213? Answer: 1205: a lock wait timed out; only the waiting statement failed and the transaction is still open. 1213: a deadlock; InnoDB rolled the whole transaction back, so retry all of it.
  3. W3 (7.3) In WHERE attributes ? '$.format' = 'hardcover', which arrow goes where the ? is, and why? Answer: ->> : it returns plain text; -> would return the JSON string "hardcover" with its quotes, and the comparison would fail.
  4. W4 (7.3) What does JSON_TABLE do, in one sentence? Answer: It turns a JSON array (in a column or a literal) into rows with typed columns that you can join, group and filter.

W5 (7.2 + 7.3) Predict, then run (in a practice database):

CREATE TABLE notes (id INT PRIMARY KEY, doc JSON);
INSERT INTO notes VALUES (1, '{"qty": 2, "tags": ["gift"]}');
START TRANSACTION;
UPDATE notes SET doc = JSON_SET(doc, '$.qty', 5);
ROLLBACK;
SELECT doc->>'$.qty' AS qty, doc->'$.tags' AS tags FROM notes;
+------+----------+
| qty  | tags     |
+------+----------+
| 2    | ["gift"] |
+------+----------+

Lesson Plans

7.4

User Management & Permissions

65 min
Objectives (from the lesson page)
  • Create accounts as 'user'@'host' and explain how MySQL 9.7 stores their passwords (caching_sha2_password)
  • Grant and revoke privileges at the global, database, table and column level, and read SHOW GRANTS
  • Log in as a restricted user and recognize the access-denied errors (1142, 1143, 1044, 3118)
  • Group privileges into roles, assign them, and make them active with SET DEFAULT ROLE
  • Design least-privilege accounts for an application, a report and staff, and script them
Timing in the room
10mFrame: why not root; 'user'@'host'; least privilege; GRANT what ON where TO whom
30mLive demo: grants at three levels, logins as each account, REVOKE, roles, a locked account
15mGuided lab: warehouse_accounts_starter.sql in pairs
10mStart the lesson project: team_access.sql Steps 1 to 3
Mental model to say

Start with the three stories from the lesson: a clerk's DELETE without WHERE, an attacker in the search box, a dashboard password in a shared config file. "None of these needs root. Each needs an account that can do its job and nothing more: the principle of least privilege."

Then the building: "root is the master key. A program gets the key to one room; a report gets a window to look through. Every account is a name AND a door: 'user'@'host'."

Then the sentence pattern on the board, GRANT what ON where TO whom, and the levels from wide to narrow: *.* (administrators only), bookstore.*, bookstore.books, a column list. "Grant at the narrowest level that works, and prove it by logging in as the account."

Live demo (you type, they follow)

The lesson's own accounts, from a fresh bookstore.sql. Root window on the left, the second window on the right: log in there as each account when the step says so. Learners type along in their own two windows; the passwords are the lesson's placeholders.

  1. An account (2m). "An account is a user name AND the host it connects from. Always write the host on purpose." 
    CREATE USER 'shop_reports'@'localhost' IDENTIFIED BY 'CHANGE-ME-reports-1';
SELECT user, host, plugin, account_locked
FROM mysql.user
WHERE user = 'shop_reports';
    +--------------+-----------+-----------------------+----------------+
| user         | host      | plugin                | account_locked |
+--------------+-----------+-----------------------+----------------+
| shop_reports | localhost | caching_sha2_password | N              |
+--------------+-----------+-----------------------+----------------+
    The plugin column: caching_sha2_password, the 9.7 default (Session 1's health check).
  2. A new account can do nothing (1m). "USAGE means: may connect. That is all." 
    SHOW GRANTS FOR 'shop_reports'@'localhost';
    +--------------------------------------------------+
| Grants for shop_reports@localhost                |
+--------------------------------------------------+
| GRANT USAGE ON *.* TO `shop_reports`@`localhost` |
+--------------------------------------------------+
  3. GRANT what ON where TO whom (2m). Write the four words on the board, then read the statement against them. 
    GRANT SELECT ON bookstore.* TO 'shop_reports'@'localhost';
SHOW GRANTS FOR 'shop_reports'@'localhost';
    +-------------------------------------------------------------+
| Grants for shop_reports@localhost                           |
+-------------------------------------------------------------+
| GRANT USAGE ON *.* TO `shop_reports`@`localhost`            |
| GRANT SELECT ON `bookstore`.* TO `shop_reports`@`localhost` |
+-------------------------------------------------------------+
    No FLUSH PRIVILEGES needed: grants take effect at once.
  4. The website's account, table by table (3m). "The site reads the catalog and records orders. It never changes a price or deletes anything." 
    CREATE USER 'shop_app'@'localhost' IDENTIFIED BY 'CHANGE-ME-app-1';
GRANT SELECT ON bookstore.* TO 'shop_app'@'localhost';
GRANT INSERT, UPDATE ON bookstore.customers   TO 'shop_app'@'localhost';
GRANT INSERT         ON bookstore.orders      TO 'shop_app'@'localhost';
GRANT INSERT         ON bookstore.order_items TO 'shop_app'@'localhost';
SHOW GRANTS FOR 'shop_app'@'localhost';
    +---------------------------------------------------------------------------+
| Grants for shop_app@localhost                                             |
+---------------------------------------------------------------------------+
| GRANT USAGE ON *.* TO `shop_app`@`localhost`                              |
| GRANT SELECT ON `bookstore`.* TO `shop_app`@`localhost`                   |
| GRANT INSERT, UPDATE ON `bookstore`.`customers` TO `shop_app`@`localhost` |
| GRANT INSERT ON `bookstore`.`order_items` TO `shop_app`@`localhost`       |
| GRANT INSERT ON `bookstore`.`orders` TO `shop_app`@`localhost`            |
+---------------------------------------------------------------------------+
    If the site is ever broken into, the attacker can read the catalog and add orders, and nothing else.
  5. Column-level privileges (2m). "The support desk sees names and emails, and may fix an email. Nothing else." 
    CREATE USER 'support_desk'@'localhost' IDENTIFIED BY 'CHANGE-ME-support-1';
GRANT SELECT (id, first_name, last_name, email), UPDATE (email)
    ON bookstore.customers TO 'support_desk'@'localhost';
  6. Test as the user: shop_reports (4m). In the SECOND window: mysql -u shop_reports -p bookstore (the password is typed at the prompt, never on the command line). "A grant you have not tested is a guess: test one thing it must do and one it must not." 
    SELECT CURRENT_USER();
SELECT COUNT(*) AS books FROM books;
DELETE FROM books WHERE id = 11;

| CURRENT_USER()         |
+------------------------+
| shop_reports@localhost |
+------------------------+
+-------+
| books |
+-------+
|    11 |
+-------+
ERROR 1142 (42000): DELETE command denied to user 'shop_reports'@'localhost' for table 'books'
  7. Test as the user: support_desk (3m). exit, then mysql -u support_desk -p bookstore. Predict each line first. 
    SELECT first_name, email FROM customers WHERE id = 1;
SELECT first_name, city FROM customers WHERE id = 1;
SELECT * FROM orders;
    +------------+-------------------+
| first_name | email             |
+------------+-------------------+
| Alice      | alice@example.com |

    1143 names the column that was never granted; SELECT * would be refused for the whole table (1142).
  8. REVOKE at the level you granted (2m). Back in the root window.

| GRANT INSERT ON `bookstore`.`order_items` TO `shop_app`@`localhost` |
| GRANT INSERT ON `bookstore`.`orders` TO `shop_app`@`localhost`      |
+---------------------------------------------------------------------+
  9. The old advice, once more (1m). "Session 1 showed this error; here is where it comes from." 
    CREATE USER 'legacy_app'@'localhost' IDENTIFIED WITH mysql_native_password BY 'CHANGE-ME-legacy-1';
    ERROR 1524 (HY000): Plugin 'mysql_native_password' is not loaded
    Fix: update the app's driver, never weaken the server.
  10. Roles (3m). "Several clerks, same job: grant to a role once, then grant the role to people." 
    CREATE ROLE 'bookstore_reader', 'bookstore_sales';
GRANT SELECT ON bookstore.* TO 'bookstore_reader';
GRANT INSERT, UPDATE ON bookstore.orders      TO 'bookstore_sales';
GRANT INSERT, UPDATE ON bookstore.order_items TO 'bookstore_sales';
CREATE USER 'tom'@'localhost'  IDENTIFIED BY 'CHANGE-ME-tom-1';
CREATE USER 'lena'@'localhost' IDENTIFIED BY 'CHANGE-ME-lena-1';
GRANT 'bookstore_reader', 'bookstore_sales' TO 'tom'@'localhost', 'lena'@'localhost';
SHOW GRANTS FOR 'tom'@'localhost';
    +-------------------------------------------------------------------------+
| Grants for tom@localhost                                                |
+-------------------------------------------------------------------------+
| GRANT USAGE ON *.* TO `tom`@`localhost`                                 |
| GRANT `bookstore_reader`@`%`,`bookstore_sales`@`%` TO `tom`@`localhost` |
+-------------------------------------------------------------------------+

SELECT COUNT(*) FROM bookstore.books;

| CURRENT_ROLE() |
+----------------+
| NONE           |
+----------------+

    The second line is the login with bookstore: refused before any query, because no privilege is active yet.

    SET DEFAULT ROLE ALL TO 'tom'@'localhost', 'lena'@'localhost';

| user | default_role_user |
+------+-------------------+
| lena | bookstore_reader  |
| lena | bookstore_sales   |
| tom  | bookstore_reader  |
| tom  | bookstore_sales   |
+------+-------------------+
  13. Tom, again (1m). Second window: mysql -u tom -p bookstore.

+-------+
  14. Lock an account (1m). "Staff on leave, a job you are retiring: lock it, keep its grants." Then try to log in as shop_reports. 
    ALTER USER 'shop_reports'@'localhost' ACCOUNT LOCK;
    ERROR 3118 (HY000): Access denied for user 'shop_reports'@'localhost'. Account is locked.
  15. Two refusals worth reading (1m). A misspelled account, then the right user with the wrong host. 
    GRANT SELECT ON bookstore.* TO 'reports'@'localhost';
SHOW GRANTS FOR 'shop_reports'@'%';
    ERROR 1410 (42000): You are not allowed to create a user with GRANT
ERROR 1141 (42000): There is no such grant defined for user 'shop_reports' on host '%'
  16. Clean up (1m). "Drop what you created; a demo account left on a server is a door left open." 
    DROP USER 'shop_reports'@'localhost', 'shop_app'@'localhost', 'support_desk'@'localhost',
          'tom'@'localhost', 'lena'@'localhost';
DROP ROLE 'bookstore_reader', 'bookstore_sales';
Three mistakes to expect, and how to coach each
  • The right name, the wrong host. "It says access denied but I created the account!" Coach: SELECT user, host FROM mysql.user; and compare the pair; inside a session, SELECT USER(), CURRENT_USER();.
  • Granted but never activated. A role shows in SHOW GRANTS and the user still gets 1142 (or 1044 at login). Coach: "Is the role ACTIVE? SELECT CURRENT_ROLE(); as that user; the fix is SET DEFAULT ROLE ALL."
  • Revoking at another level. 1147 on a REVOKE. Coach: "Read SHOW GRANTS: at which level was it granted? Revoke exactly that line."

Checks for understanding

8.1

Importing & Exporting Data

65 min
Objectives (from the lesson page)
  • Back up a database with mysqldump, choose the right options for MySQL 9.7, and restore the file into a test database
  • Explain what secure_file_priv and local_infile control, and find their values on your server
  • Export query results to a CSV file with SELECT ... INTO OUTFILE, including a header row
  • Import a CSV file through a staging table with LOAD DATA INFILE, converting dates and empty values on the way in
  • Recognize and fix the errors file operations raise (1290, 1086, 3948, 2068, 3546)
Timing in the room
10mFrame: whole databases at the terminal, rows at mysql>; where the server may touch files
30mLive demo: backup, test restore, the GTID trap; a CSV export; a staging-table import; refusals and a silent warning

Mental model to say

"Two kinds of moving data, two kinds of tools." Point at the board: whole databases (backups, a new server) go through mysqldump, a program at the terminal, which writes a .sql file of CREATE and INSERT statements; the mysql client plays it back. Rows (a report for a spreadsheet, a supplier's file) go through SELECT ... INTO OUTFILE and LOAD DATA, SQL at the mysql> prompt.

Then the fence: "INTO OUTFILE and LOAD DATA INFILE run on the SERVER's disk, so the server only touches one folder, secure_file_priv, and only for accounts with the FILE privilege. LOCAL means the client sends a file from your own computer, and both sides must agree to it."

Then the rule that makes a backup a backup: a dump you have never restored is a hope. Back up, restore into a test database, compare the counts, write it down.

Live demo (you type, they follow)

From a fresh bookstore.sql, with three windows: a plain terminal in the course folder (mysqldump), the root mysql client, and the lesson page for the CSV files.

  1. A backup, at the terminal (3m). Open a plain terminal (not mysql>) in the course folder. "mysqldump is a separate program. On 9.7 these four options are the habit." 
    mysqldump -u root -p --single-transaction --routines --events \
    --set-gtid-purged=OFF bookstore > bookstore_backup.sql
    It prints nothing and leaves a file of about 12 KB. Windows PowerShell: --result-file=bookstore_backup.sql instead of >.
  2. What is inside (2m). "Plain SQL: a DROP and a CREATE per table, then the rows." 
    grep -c 'INSERT INTO' bookstore_backup.sql
grep 'DROP TABLE IF EXISTS' bookstore_backup.sql
    8
DROP TABLE IF EXISTS `authors`;
DROP TABLE IF EXISTS `book_categories`;
DROP TABLE IF EXISTS `books`;
DROP TABLE IF EXISTS `categories`;
DROP TABLE IF EXISTS `customers`;
DROP TABLE IF EXISTS `employees`;
DROP TABLE IF EXISTS `order_items`;
DROP TABLE IF EXISTS `orders`;
    Every table starts with DROP TABLE IF EXISTS: a restore replaces tables. Open the file in an editor for the versioned /*!40101 ... */ comments.
  3. A test restore (3m). "A backup you have never restored is a hope." Restore into a test database, then compare. 
    mysql -u root -p -e "CREATE DATABASE bookstore_test"
mysql -u root -p bookstore_test < bookstore_backup.sql
mysql -u root -p -t -e "SELECT
    (SELECT COUNT(*) FROM bookstore.order_items) AS items_original,
    (SELECT COUNT(*) FROM bookstore_test.order_items) AS items_copy"
    +----------------+------------+
| items_original | items_copy |
+----------------+------------+
|             18 |         18 |
+----------------+------------+
    Then DROP DATABASE bookstore_test;.
  4. The 9.7 trap (3m). "Leave out --set-gtid-purged=OFF and watch." 
    mysqldump -u root -p --single-transaction bookstore > plain_dump.sql
mysql -u root -p -e "CREATE DATABASE bookstore_test2"
mysql -u root -p bookstore_test2 < plain_dump.sql
    Warning: A partial dump from a server that has GTIDs will by default include the GTIDs of all transactions, even those that changed suppressed parts of the database. If you don't want to restore GTIDs, pass --set-gtid-purged=OFF. To make a complete dump, pass --all-databases --triggers --routines --events.

Three mistakes to expect, and how to coach each
  • The wrong prompt. mysqldump at mysql> (1064) or SQL at $ ("command not found"). Coach: "Look at the prompt first: $/PS> runs programs, mysql> runs SQL."
  • A path the server cannot use. 1290 for /tmp or a home folder. Coach: "Whose disk is that path on? The server's. Which folder does it allow?" SHOW VARIABLES LIKE 'secure_file_priv';
  • Trusting the status line's first number. "4 rows affected, done." Coach: read the whole line (Skipped, Warnings), SHOW WARNINGS when it is not 0, and SELECT the staging table before copying anything.

Checks for understanding

Ask these out loud during the demo and the lab:

  • Which option does every 9.7 dump you restore yourself need? Answer: --set-gtid-purged=OFF.
  • What does a database dump leave out that the server needs? Answer: the user accounts and their grants (keep team_access.sql and backup_user.sql).
  • Why a staging table? Answer: to look, convert and check before the real tables change.
