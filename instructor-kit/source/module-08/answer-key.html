Answers to W1 to W5 (not graded). W1 and W2 with MySQL's real output on the freshly loaded bookstore:

W1
Which customers have never placed an order? Say the query shape, then the names.
A LEFT JOIN from customers to orders, keeping the customers whose orders side is NULL (or HAVING COUNT(o.id) = 0): Carol and Hank. Lesson 4.3, the anti-join.
+------------+--------+
| first_name | orders |
+------------+--------+
| Carol      |      0 |
| Hank       |      0 |
+------------+--------+
W2
employees has a manager_id. How do you show each employee next to their manager's name? Who is Sofia's manager?
A self-join: the table twice with two aliases, ON m.id = e.manager_id. Sofia (id 7) reports to Marcus.
+----------+---------+
| employee | manager |
+----------+---------+
| Sofia    | Marcus  |
+----------+---------+
W3
SELECT a.name, COUNT(*) FROM authors a LEFT JOIN books b ON b.author_id = a.id GROUP BY a.id, a.name: what does it say for Isaac Asimov, who has no books, and how do you fix it?
1, because COUNT(*) counts the NULL-padded row the LEFT JOIN made. Count a column of the right table, COUNT(b.id), which skips NULL: 0. (Lesson 4.3, Common Mistake 4.)
W4
Books per author and copies sold in one query: Orwell shows 5 books, but he wrote 2. What happened?
Fan-out: joining order_items repeats each book once per order line. COUNT(DISTINCT b.id) fixes it. Ask what one row of the join stands for. (Lesson 4.3, Common Mistake 5.)
W5
A subquery in FROM (a derived table) fails with error 1248. What is missing?
An alias: every derived table needs its own name, ( ... ) AS t (Lesson 3.4). Today's CTEs give such steps a name up front, and read top to bottom.

5.1 · CTEs & Recursive Queries: self-check

Q1
A statement starts WITH monthly AS (...). How long does monthly exist?
A) Until you disconnect
B) Only while that one statement runs
C) Until you DROP it
D) Until the next COMMIT
Why: A CTE is a named result that belongs to the one statement it is written in. After the semicolon it is gone: a second SELECT * FROM monthly; answers 1146 (the lesson's Common Mistake 4).
A is wrong: That is a user variable (@name) or a temporary table.
C is wrong: Only stored objects (tables, views) are dropped; a CTE is never stored.
D is wrong: Transactions have nothing to do with a CTE's lifetime.
Q2
What does this print?
WITH RECURSIVE s AS (
    SELECT 2 AS n
    UNION ALL
    SELECT n * 2 FROM s WHERE n < 20
)
SELECT GROUP_CONCAT(n ORDER BY n) AS series FROM s;
2,4,8,16,32 (one row, column series)
Why: Each round doubles the row the previous round made: 2, 4, 8, 16. The round that reads 16 still passes n < 20 and makes 32; the round that reads 32 fails the test, makes no row, and the recursion stops. The stop condition tests the row a round reads, so the last row can be past the limit.
Q3
A CTE named org joins to itself, but the statement starts WITH org AS ( without RECURSIVE. What happens?
A) ERROR 1146 (42S02): Table 'bookstore.org' doesn't exist
B) ERROR 3636 (HY000): Recursive query aborted after 1001 iterations
C) It runs, but only the anchor's rows come back
D) ERROR 1406 (22001): Data too long for column
Why: Without RECURSIVE a CTE cannot see its own name, so the JOIN inside it looks for a real table called org (the live demo's last step, and the debug handout's query A).
B is wrong: 3636 needs a working recursion that never stops.
C is wrong: MySQL does not quietly drop the recursive member; it refuses the statement.
D is wrong: 1406 is a column too narrow for what the recursive member builds.
Q4
A recursive CTE named chain starts from one employee. Which condition in the recursive member walks UP to the owner?
A) JOIN chain c ON e.manager_id = c.id
B) JOIN chain c ON e.id = c.id
C) JOIN chain c ON e.id = c.manager_id
D) JOIN chain c ON e.manager_id = c.manager_id
Why: "Who is this person's manager?": the next row is the employee whose id is the manager_id of the row found last. That is how the demo climbs from Sofia to Marcus, Daniel and Maria.
A is wrong: That walks DOWN: "whose manager is this person?" (the org chart).
B is wrong: It finds the same person again every round: the recursion would never move.
D is wrong: It finds colleagues with the same manager, not the manager.
Q5
The bookstore has 10 employees. This query prints 30. What is wrong?
WITH RECURSIVE org AS (
    SELECT id, 1 AS level FROM employees
    UNION ALL
    SELECT e.id, o.level + 1
    FROM employees e JOIN org o ON e.manager_id = o.id
)
SELECT COUNT(*) AS rows_back FROM org;
A) RECURSIVE is missing
B) UNION ALL should be UNION
C) The recursion limit is too low
D) The anchor has no WHERE, so every employee starts a walk of their own
Why: With no WHERE manager_id IS NULL in the anchor, all ten employees are starting points, and each deeper person is found again under every manager above them. No error: the lesson's silent Common Mistake 5. Check with COUNT(*) against COUNT(DISTINCT id).
A is wrong: RECURSIVE is there, and without it the query would fail with 1146.
B is wrong: UNION would hide some duplicates and the wrong anchor with them: fix the anchor instead.
C is wrong: The limit is 1000 rounds; this walk needs four.
Q6
In one sentence: why does a monthly report LEFT JOIN a generated calendar of months to the orders, instead of grouping the orders by month directly?
GROUP BY over orders can only show months that have orders; the recursive calendar has every month, and the LEFT JOIN keeps the empty ones (July shows 0)
Why: Real data has holes. The series comes first, then the data is hung on it; COUNT(o.id) counts 0 for a month with no matching order.

5.1 · CTEs & Recursive Queries: predict, then run

P1
Predict the output, then run it.
WITH RECURSIVE countdown AS (
    SELECT 10 AS n
    UNION ALL
    SELECT n - 3 FROM countdown WHERE n > 3
)
SELECT n FROM countdown;
+------+
| n    |
+------+
|   10 |
|    7 |
|    4 |
|    1 |
+------+
Why: Anchor 10; each round subtracts 3 while the row it reads is above 3: 7, 4, 1. The round that reads 1 fails n > 3 and stops.
P2
Predict the output, then run it.
WITH by_city AS (
    SELECT city, COUNT(*) AS customers
    FROM customers
    GROUP BY city
)
SELECT COUNT(*) AS city_groups, SUM(customers) AS customers
FROM by_city;
+-------------+-----------+
| city_groups | customers |
+-------------+-----------+
|           5 |         8 |
+-------------+-----------+
Why: GROUP BY city makes one group per city, and the two customers with no city (Eve, Hank) form one more group: NULL. Five groups, eight customers. (The column is not called groups: GROUPS is a reserved word in MySQL 8 and later, error 1064.)

5.2 · Window Functions: self-check

Q7
employees has 10 rows in 4 departments. How many rows does this return? SELECT first_name, AVG(salary) OVER (PARTITION BY department) FROM employees;
A) 4
B) 1
C) 10
D) None: ERROR 1140 (a column without GROUP BY)
Why: A window function never collapses rows: every employee comes back, each with their own department's average. GROUP BY department would return 4.
A is wrong: That is GROUP BY department.
B is wrong: That is AVG(salary) without OVER.
D is wrong: OVER makes the mix of a plain column and an aggregate legal.
Q8
Copies sold, best first, are 5, 4, 4 and 3. What do RANK() and DENSE_RANK() (both OVER (ORDER BY copies DESC)) give the book with 3?
RANK 4, DENSE_RANK 3
Why: RANK skips after a tie (1, 2, 2, 4: three books are ahead); DENSE_RANK does not (1, 2, 2, 3). ROW_NUMBER would give 4 too, but it would also give the tied books 2 and 3.
Q9
SELECT title FROM books WHERE RANK() OVER (ORDER BY price DESC) <= 3; fails with error 3593. What is the standard fix?
A) Move the condition to HAVING
B) Compute the rank in a CTE, then filter on it in the outer query
C) Replace WHERE with QUALIFY
D) Give the rank a column alias and filter on the alias in WHERE
Why: Window functions run after WHERE, GROUP BY and HAVING, so none of those can see them. One step computes the window, the next filters it: a CTE (or a derived table) is that next step.
A is wrong: HAVING runs before the windows too (3593 again).
C is wrong: QUALIFY is error 6037 on MySQL 9.7 (hypergraph optimizer only) and 1064 on MariaDB.
D is wrong: WHERE cannot see SELECT aliases: error 1054, Unknown column.
Q10
In SUM(price) OVER (ORDER BY price), The Catcher in the Rye and The Great Gatsby (both 8.99) show the same running total, 34.46. Why?
A) SUM skips duplicate values
B) Prices are sorted as text
C) The window has no PARTITION BY
D) The default frame is RANGE: rows with the same ORDER BY value are added in one step
Why: With ORDER BY and no frame, the frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, which lumps ties together. Write ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW and make the order unique (ORDER BY price, title): 25.47 then 34.46.
A is wrong: Both prices are added (34.46 includes both); the problem is when.
B is wrong: price is DECIMAL; the order is numeric.
C is wrong: PARTITION BY would restart the total per group; it does not change how ties are handled.
Q11
Bob (customer 2) has two orders. What does this print?
SELECT id,
       order_date,
       LEAD(order_date) OVER (ORDER BY order_date) AS next_order
FROM orders
WHERE customer_id = 2
ORDER BY order_date;
Two rows: order 3, 2026-03-10, next_order 2026-03-28; order 7, 2026-03-28, next_order NULL
Why: LEAD reads the next row of the window. Order 7 is Bob's last, so there is no next row and LEAD returns NULL (a third argument, LEAD(order_date, 1, ...), would replace it).
Q12
You need exactly one top earner per department, even if two salaries ever tie. Which function numbers the rows?
A) ROW_NUMBER() with a tie-breaker, e.g. ORDER BY salary DESC, id
B) RANK()
C) DENSE_RANK()
D) NTILE(1)
Why: ROW_NUMBER never ties, so pos = 1 is exactly one row per partition; the tie-breaker makes the choice repeatable. RANK and DENSE_RANK would return both tied people.
B is wrong: Two tied top salaries both get rank 1.
C is wrong: Same: both get 1.
D is wrong: NTILE(1) puts every row in bucket 1.

5.2 · Window Functions: predict, then run

P3
Predict the output, then run it.
SELECT first_name,
       COUNT(*) OVER ()                        AS everyone,
       COUNT(*) OVER (PARTITION BY department) AS in_dept
FROM employees
WHERE department = 'support'
ORDER BY first_name;
+------------+----------+---------+
| first_name | everyone | in_dept |
+------------+----------+---------+
| James      |        2 |       2 |
| Nina       |        2 |       2 |
+------------+----------+---------+
Why: WHERE keeps only the two support employees BEFORE the windows are computed, so even OVER () sees two rows. Windows never see rows WHERE removed.
P4
Predict the output, then run it.
SELECT id,
       LAG(id, 1, 0) OVER (ORDER BY id) AS previous_id
FROM orders
WHERE customer_id = 1
ORDER BY id;
+----+-------------+
| id | previous_id |
+----+-------------+
|  1 |           0 |
|  2 |           1 |
|  8 |           2 |
+----+-------------+
Why: LAG's third argument replaces the NULL on the first row: 0. Alice's orders are 1, 2 and 8, so the previous ids are 0, 1, 2.

The Lesson Pages' Own Quick Quizzes

Lesson 5.1 · CTEs & Recursive Queries
  1. B Error 1146: the table does not exist: A CTE exists only inside the statement it is written in. After the semicolon it is gone, so MySQL looks for a real table named monthly and reports error 1146.
  2. A The anchor, before UNION ALL: The anchor, the query before UNION ALL, produces the starting rows once. The recursive member then runs round after round until a round produces no rows.
  3. C 4: The anchor gives 1, then the rounds give 2, 3 and 4. The round that reads 4 fails n less than 4, produces nothing, and the recursion stops: 1, 2, 3, 4.
  4. B Widen the column in the anchor, for example CAST('Maria' AS CHAR(200)): The anchor fixes each column's type and width, and the recursive member can never widen it. CAST('Maria' AS CHAR(200)) in the anchor gives the path room to grow.
  5. C In a view, stored once in the database: A view is stored in the database, so every script and every person can read it by name. CTEs are best for steps that belong to one query.
Lesson 5.2 · Window Functions
  1. C 11: A window function never collapses rows. OVER () makes the whole result the window, so each of the 11 books gets the same average next to its title.
  2. A 4: RANK gives the two books with 3 copies the same rank, 2, then skips: three books are ahead of the one with 2 copies, so it gets 4. DENSE_RANK would give 3.
  3. B Compute the row number in a CTE and filter it in the outer query: Window functions are computed after WHERE, GROUP BY and HAVING. Compute ROW_NUMBER in a CTE, then filter its result with WHERE in the outer query.
  4. C NULL: January is the first row of the window, so there is no previous row and LAG returns NULL. LAG(revenue, 1, 0) would return 0 instead.
  5. A 1: The frame asks for two rows before January, but there are none, so the frame holds only January itself. February averages two months, and from March on every row averages three.

Exit Ticket

  1. Recursive skeleton: WITH RECURSIVE s AS (SELECT 1 AS n UNION ALL SELECT n + 1 FROM s WHERE n < 10) SELECT n FROM s; Anchor = SELECT 1 AS n (runs once); recursive member = SELECT n + 1 FROM s ... (runs per round); stop condition = WHERE n < 10. Accept <= 9; reject a stop condition in the outer SELECT (it would not stop the recursion).
  2. GROUP BY vs PARTITION BY: one row per department versus every employee row with the department's figure added. Accept "collapses" versus "keeps the rows".
  3. WHERE and windows: windows are computed after WHERE (and GROUP BY, HAVING), so WHERE cannot see them (3593); compute the window in a CTE (or derived table) and filter in the outer query.

Common Wrong Answers and What They Reveal

  • Q1 A ("until you disconnect"). Mixes a CTE with a user variable or a temporary table. Show the 1146 from the demo's step 5 again.
  • Q2 2,4,8,16. Reads the stop condition as a filter on the output. Draw the rounds: the round that reads 16 still makes 32.
  • Q4 A. Walks down instead of up: the most common hierarchy slip. Say the two questions aloud: "whose manager is this?" (down) versus "who is this person's manager?" (up).
  • Q7 A (4 rows). Still thinks of grouping. Run it: ten rows.
  • Q8 "3 and 3" or "4 and 4". Mixed up which function skips. The board table: 1, 2, 2, 4 / 1, 2, 2, 3.
  • Q9 A (HAVING). HAVING runs before windows too; the CTE is the only portable fix.
  • Exit ticket 1 with the WHERE in the outer SELECT. The recursion has no stop condition at all (3636). Worth two minutes at the start of Session 9.
