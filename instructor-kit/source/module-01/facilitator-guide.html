Session 1: What Databases Are and Installing MySQL

How to teach the first session of MySQL Foundations. Welcome a room of beginners, find out which machines have a working MySQL 9.7 and what the room already knows about spreadsheets and files, then show why databases exist (a sheet that cannot keep one customer's name straight, a server that refuses bad rows with numbered errors) and make every laptop ready: an install clinic, connect and verify, and a health check learners can rerun all course.

2 lessons 3 hrs session Lessons 1.1–1.2 Session 1 of 14 · Part 1

How to Use This Guide

  • Same rhythm for both lessons: frame (the goal and one mental model) → live demo (you type, they type along) → guided lab (a kit lab, new practice on the lesson's ideas) → start the lesson's own project. The lesson exercises, quiz and journal are homework.
  • Type, do not paste. Every SQL block below was run to produce the output printed under it, on MySQL 9.7.2 with the default settings. Ask for a prediction before every statement that prints something, and read error messages from the left, out loud: the number, then the reason.
  • The lessons are the reference. Keep lesson_01.html and lesson_02.html open in browser tabs for the diagrams (the application, the server and the files; client, port and server) and the per-platform installation sections. Labs live in labs/module-01/: _starter.sql files are handouts, _solution.sql files are yours.
  • Session 1 is different in two ways. It opens with 30 minutes of welcome, environment check and diagnostic instead of the usual 10-minute warm-up, and Lesson 1.2's room time is mostly an install clinic: installing MySQL is prework (the kit's setup guide follows Lesson 1.2), so the room fixes what went wrong instead of watching progress bars.
  • Part 1 (Sessions 1 to 7) can run on its own as a short course; nothing in this session depends on Part 2. Teal blocks are hands-on, amber blocks are watch-outs. Lesson codes (1.1, 1.2) match the course site.
The #1 risk of Session 1: the install eats the session

MySQL installs differently on every platform, and each one has its own trap: the Windows MSI does not put mysql on the PATH; Homebrew's mysql@9.7 is keg-only; Ubuntu's own package is 8.0 or 8.4 and logs root in through sudo; Docker needs a free port 3306. Done together on venue Wi-Fi, installation fills three hours and nobody writes a line of SQL. Before: send the setup guide a week ahead (install MySQL 9.7 with Lesson 1.2's section for your platform, then run the environment check) and ask every learner to reply with the check's last table. In the room: the check gets 12 minutes in the opening; a NOT READY machine gets a ready partner until the 25-minute install clinic at 1:45, not your attention during Lesson 1.1. After: whoever is still not ready leaves with a numbered plan and runs the check again before Session 2.

Sequence and talking points
  • Welcome (5m). One minute on yourself, including a time when data in the wrong place cost someone (a spreadsheet with two versions of the truth works well). Then a quick round: name, where they meet data today (spreadsheets, a web shop, reports), and one question they wish they could ask their data. Write three or four on the board; they come back in the 1.1 journal prompt. Housekeeping in one breath: break at 1:25, where the lab files are, and "if you are stuck, put a sticky note on your laptop lid and keep trying while I get to you."
  • How the course runs (5m). Show the course home page. Say: "Fourteen sessions of three hours in two parts. Part 1, the first seven sessions, takes you from nothing to joining tables; Part 2 goes beyond the basics and ends with a database you design yourself. Every lesson uses the same online bookstore, so by the end you will know its books, customers and orders well." Then the deal: "Each lesson was written for someone working alone for 75 to 110 minutes, so two do not fit in three hours. In this room we do what is hard alone: the mental model, a live demo, a guided lab, and the first steps of each project. At home you finish the projects and do the exercises, quiz and journal: plan on two to three hours a week." Scroll once through lesson_01.html: objectives, sections with real output, common mistakes, a project in steps, exercises with hidden solutions, a quiz, a journal prompt.
  • Environment check (12m). Say: "Before any new ideas, we find out which machines are ready." On the projector, then theirs: 1 open a terminal in the course folder (the one with labs/); 2 macOS/Linux: bash labs/module-01/l1_0-orientation/check_environment.sh, Windows: powershell -ExecutionPolicy Bypass -File labs\module-01\l1_0-orientation\check_environment.ps1; 3 type the root password when asked. Done = the last table says READY for MySQL Foundations (READY WITH NOTES on 8.4 or MariaDB is fine for today). Anyone who saw READY at home runs it again and becomes a helper. NOT READY falls into three piles: client not found (PATH: often one minute, fix now), 1045 / 2002 / 2003 (password or server stopped: two minutes, fix now), nothing installed (do not start a download now: pair with a ready neighbor; install clinic at 1:45). Write the third pile's names on a sticky note.
  • Diagnostic (8m). Say: "Six quick questions on the spreadsheet and computer skills SQL builds on. Not a test, nobody collects it. It tells you what to practice and tells me what to slow down for." Learners answer D1 to D6 on the workbook's Start Here page (about four minutes), then show fingers (1 to 4 for A to D) as you reveal each. Keep a tally of wrong answers per question on a sticky note.
Diagnostic answers and how to read the tally

Answers: D1 B) 2; D2 C) Dune; D3 A) 1; D4 D) 44.97; D5 B) 5; D6 B) Downloads/bookstore.sql.

  • D1 (filter) and D2 (sort) are WHERE and ORDER BY in disguise: the shape of every query in Module 3. Misses here are rare; if a third of the room misses either, read the 1.1 demo's SELECT aloud as a filter ("keep the rows where the city is Chicago").
  • D3 (AND versus OR) is the single best predictor of trouble in Lesson 3.1. Two or more misses: in the 1.1 lab, do TODO 1 together and say the WHERE line aloud each time.
  • D4 (a formula column) and D5 (empty cells) come back as expressions in SELECT and as NULL. Misses on D5 are common and not urgent: Lessons 2.2 and 3.3 teach NULL properly.
  • D6 (paths) predicts trouble with SOURCE labs/... today and with running .sql files in Session 2. Learners who missed it get the typing role in the lab pair, with you nearby for the first SOURCE.
  • Three or more wrong: not a problem to announce. Pair them with a strong neighbor today, and at the wrap-up hand them labs/module-01/l1_0-orientation/diagnostic_starter.sql: the same six moves done in SQL, one small gap each (diagnostic_solution.sql is your reference). The workbook's Start Here page says where each skill comes back.
Watch-outs
  • Do not debug one machine in front of the room. Two minutes per machine during the check, then pair and move on: the install clinic at 1:45 exists so that you can say "we will fix that at 1:45" with a straight face.
  • Mixed backgrounds. Some learners live in spreadsheets and have never opened a terminal; some write code and have never designed a table. The diagnostic and the terminal steps are for both groups.
  • "I already use SQL." Welcome them and give them a job: helper during the check and the clinic, and the stretch tasks in each lab. Ask them to watch for the habits today is about (reading error numbers, checking which server answered), which experienced people skip most.
  • MariaDB and other versions. XAMPP and some hosts ship MariaDB under the name MySQL. Today it only changes a few outputs; the check says so in a CHECK line. Do not reinstall in the room.

Lesson Plans

1.1

What Is a Database?

55 min
Objectives (from the lesson page)
  • Explain what a database and a database management system (DBMS) are, and name three problems a database solves that a spreadsheet does not
  • Tell relational databases apart from the main non-relational kinds, and pick a sensible type for a simple scenario
  • Point to the table, columns, rows, primary key and foreign key in a small example
  • Describe what SQL is and match the four CRUD operations to INSERT, SELECT, UPDATE and DELETE
  • Sketch the tables of a small online bookstore on paper, with keys and relationships
Timing in the room
10mFrame: the bookshop that outgrew its spreadsheet; application, server, files; tables, rows, keys
20mLive demo: the lesson's first taste of SQL, three refused rows, cleanup
15mGuided lab: order_sheet_starter.sql in pairs
10mStart the lesson project: sketch the bookstore, Steps 1 and 2
Mental model to say

Tell the story while you draw it: "A small online bookstore keeps everything in one spreadsheet: one row per order, with the customer's name, email and city, and the books typed into a cell. It works for fifty orders. At five thousand, Alice's name is spelled three ways, Bob lives in two cities at once, and two people saving the file overwrite each other."

Then the three boxes on the board: "Your application never touches the data files. It sends SQL to a server, the DBMS, and the server reads and writes the files, enforces the rules and answers. MySQL is that server. A database is your data inside it."

Then the one idea of relational design, pointing at two small tables you draw: "Store each fact once, and point to it with a key. Alice lives in the customers table exactly once, with id 1. Every order stores only her id. Change her email in one place and every order is right." Write primary key (tells rows apart) and foreign key (points to another table's row) next to the two columns.

Live demo (you type, they follow)

This is the lesson's "A First Taste of SQL" and its Common Mistakes, typed live in the mysql> client on the projector. Ready learners type along; the rest watch and get their turn after the clinic. Ask for a prediction before every statement that prints something; read every error number aloud.

  1. A practice database, and a table (3m). "Everything I type goes to the MySQL server; the server does the reading and writing. First a practice database, then a table for customers. Every column gets a name, a type and its rules." Read the column lines aloud: AUTO_INCREMENT hands out ids, NOT NULL means required, UNIQUE means no two alike. 
    CREATE DATABASE preview_shop;   -- a new, empty database
USE preview_shop;               -- work inside it from now on
CREATE TABLE customers (
    id         INT AUTO_INCREMENT PRIMARY KEY,
    first_name VARCHAR(50)  NOT NULL,
    last_name  VARCHAR(50)  NOT NULL,
    email      VARCHAR(100) NOT NULL UNIQUE,
    city       VARCHAR(50)
);
    Database changed
    MySQL only answers Database changed after USE; the other two statements succeed quietly. Ready learners type along; the others watch (they install at 1:45).
  2. Create: three customers (2m). "INSERT is the C in CRUD. I leave out id: MySQL fills it in." 
    -- @status
INSERT INTO customers (first_name, last_name, email, city)
VALUES ('Alice', 'Johnson',  'alice@example.com', 'New York'),
       ('Bob',   'Smith',    'bob@example.com',   'Chicago'),
       ('Carol', 'Williams', 'carol@example.com', 'Los Angeles');
    Query OK, 3 rows affected
Records: 3  Duplicates: 0  Warnings: 0
  3. Read: one city (2m). "SELECT is the R. You say WHAT you want, never HOW to find it: that is what declarative means." Ask for a prediction first: how many rows? 
    SELECT first_name, last_name, city
FROM customers
WHERE city = 'Chicago';
    +------------+-----------+---------+
| first_name | last_name | city    |
+------------+-----------+---------+
| Bob        | Smith     | Chicago |
+------------+-----------+---------+
    Read the statement as English: select first name, last name and city from customers where the city is Chicago.
  4. Update: Bob moves (2m). "The WHERE line picks the one row to change. Without it, everybody moves to Boston." 
    -- @status
UPDATE customers
SET city = 'Boston'
WHERE id = 2;
    Query OK, 1 row affected
Rows matched: 1  Changed: 1  Warnings: 0
  5. Delete, then look at everything (2m). "DELETE is the D. SELECT star means all columns." Point at the gap: Carol's id 3 is gone and will not be reused. 
    DELETE FROM customers
WHERE id = 3;
SELECT * FROM customers;
    +----+------------+-----------+-------------------+----------+
| id | first_name | last_name | email             | city     |
+----+------------+-----------+-------------------+----------+
|  1 | Alice      | Johnson   | alice@example.com | New York |
|  2 | Bob        | Smith     | bob@example.com   | Boston   |
+----+------------+-----------+-------------------+----------+
  6. Refused 1: a duplicate key (2m). "Now I break the rules on purpose. A spreadsheet takes anything; a database says no, with a number. Read the message from the left: number, then the reason." 
    INSERT INTO customers (id, first_name, last_name, email)
VALUES (1, 'Dave', 'Brown', 'dave@example.com');
    ERROR 1062 (23000): Duplicate entry '1' for key 'customers.PRIMARY'
    id 1 is Alice's. Fix: leave id out and let AUTO_INCREMENT choose.
  7. Refused 2: text where a number belongs (1m). "id is a whole number. 'abc' is not." 
    INSERT INTO customers (id, first_name, last_name, email)
VALUES ('abc', 'Dave', 'Brown', 'dave@example.com');
    ERROR 1366 (HY000): Incorrect integer value: 'abc' for column 'id' at row 1
  8. Refused 3: a required value missing (2m). "last_name was declared NOT NULL and has no default." Then the silent fourth problem from the lesson, said aloud: copying a customer's name into every order raises no error at all; that is what the lab is about. 
    INSERT INTO customers (first_name, email)
VALUES ('Dave', 'dave@example.com');
    ERROR 1364 (HY000): Field 'last_name' doesn't have a default value
  9. Clean up (1m). "DROP DATABASE deletes a database and everything in it, with no undo. Read the name twice before you press Enter." 
    DROP DATABASE preview_shop;
    No output on success. Draw the server / client / database picture again: preview_shop lived INSIDE the server and is now gone; the server is still running.
Three mistakes to expect, and how to coach each
  • Server, client and database blur together. "I installed MySQL but I can't find my database" or "is MySQL the database?" Coach with the board: point at the three boxes and ask "which box are you talking about?" Then the lesson's own line: the server runs in the background, the client is what you type into, a database lives inside the server and you create it.
  • A missing semicolon. The client shows -> and waits; learners think it froze. Coach: "What does the prompt look like? -> means MySQL is waiting for the end of the statement: type ; and Enter." (Lesson 1.3 covers the prompts properly.)
  • Treating every column of a sheet as one table. In the project, a learner draws one big table with book1, book2, book3 or a comma-separated list. Coach with the lab's TODO 3: "How would you find every order that contains Dune? What about Dune Messiah?" Then: "a list in a cell needs its own table, one row per item."
Guided lab

File: learners open labs/module-01/l1_1-what-is-a-database/order_sheet_starter.sql; your reference is labs/module-01/l1_1-what-is-a-database/order_sheet_solution.sql. It practices the lesson's first section (why a spreadsheet is not enough) on a new sheet: each TODO changes one value in a ready-made query and reveals one spreadsheet problem.

  • SOURCE it first, as shipped (2m). Show the command on the projector: SOURCE labs/module-01/l1_1-what-is-a-database/order_sheet_starter.sql from a client started in the course folder. Everyone should see the six-row sheet, three Empty set answers and a 0-row answer. A learner who sees Failed to open file started the client in another folder: exit, cd into the course folder, log in again.
  • TODO 1 together on the projector (3m), TODOs 2 to 4 in pairs (8m). Each TODO is a one-word edit in a text editor, then SOURCE again. Circulate for quotes deleted along with the placeholder (an ERROR 1064 syntax error: show them the quotes in the original) and for edits made in the client instead of the file.
  • Expected: TODO 1 three spellings of Alice (orders 1, 2 and 6); TODO 2 Bob in Chicago (order 3) and Boston (order 4); TODO 3 four rows (orders 1, 3, 4, 5), and order 4 is Dune Messiah, a different book; TODO 4 order 5 with about 26 in the total column.
  • Debrief (2m): one sentence per TODO, from the pairs: copies drift apart (1 and 2), a list in a cell cannot be searched reliably (3), a column with no type accepts anything (4). Then: "Every one of these problems disappears when each fact is stored once, in the right type, and connected with keys. That is what the next twenty-three lessons build." The solution file's step 5 shows the two-table fix in miniature: show its last two results if time allows.
  • Fast finishers: labs/module-01/l1_1-what-is-a-database/crud_tour_starter.sql (the four CRUD statements on a books table, turned off with -- until the learner predicts the result), then labs/module-01/l1_1-what-is-a-database/debug_rules.sql: four INSERTs that MySQL refuses with errors 1062, 1364, 1366 and 1406.
Start the lesson project

The lesson project is Sketch the Bookstore: a paper design of the database this course builds. In the room, do Steps 1 and 2 only (10 minutes).

  • Read the store's description aloud from the lesson page (Step 1). Learners underline the nouns and turn them into about five table names.
  • Step 2 in pairs: four to six columns per table, each with a type (text, whole number, decimal, date, yes/no).
  • Done in the room = five tables (customers, orders, books, authors, categories) with typed columns. Do not show the course design yet.
  • Goes home: Step 3 (primary keys: why a title or an email makes a poor one), Step 4 (foreign keys and the two linking tables) and Step 5 (compare with the course design on the lesson page). They keep the sketch: Sessions 2 and 6 compare it with the real tables.
Checks for understanding

Ask these out loud during the demo and the lab (cold-call gently, or think-pair-share):

  • Is MySQL the database? Answer: no: MySQL is the server software (a DBMS); a database such as preview_shop lives inside it.
  • Which CRUD letter is SELECT? And DROP DATABASE? Answer: SELECT is Read. DROP DATABASE is not CRUD at all: it removes the structure, not rows.
  • Why does an orders table store customer_id instead of the customer's name? Answer: the name lives once in customers; the id points to it, so a correction happens in one place.
  • Which of the three refused rows would a spreadsheet have accepted? Answer: all three: the duplicate id, the text in a number column and the missing last name.

Workbook self-check, items Q1 to Q6 (learners do them at the end of the block or at home).

Answers: Q1 B) MySQL is a database management system: server software that stores databases, enforces their rules and answers SQL; Q2 C) author_id; Q3 Two rows: Tom and Fido; Q4 A) ERROR 1062 (23000): Duplicate entry '2' for key 'pets.PRIMARY'; Q5 D) A key-value store such as Redis; Q6 B) DELETE FROM customers WHERE id = 3;. Full set with explanations in the Answer Key.

Stretch: crud_tour_starter.sql and debug_rules.sql; then the lesson's Exercise 4 (design a table for a collection they know, and spot the column that is secretly a list) and the Bonus Challenge (five tables of an app they use every day).

Installing MySQL

75 min
Objectives (from the lesson page)
  • Choose the right MySQL release (9.7 LTS) and installation method for your computer, and recognize when a package gives you something else (an older MySQL, or MariaDB)
  • Install MySQL 9.7 LTS with the Windows MSI, the macOS package or Homebrew, the MySQL APT repository, or the official Docker image

Mental model to say

Back to the three boxes: "Installing MySQL means two programs. The server, mysqld, runs in the background, owns the data files and listens on a port, 3306, like a shop with a door number. A client, the mysql command, knocks on that door and carries your SQL in. They can be on different machines; today they are on the same laptop."

Then versions, in one breath: "MySQL ships LTS releases that stay the same for years, and innovation releases with new features every few months. This course uses 9.7 LTS. 'Latest' on a download page usually means an innovation release, numbered like 26.x; Ubuntu's own package is older; XAMPP gives you MariaDB, a close relative. Whatever you installed, the first thing you ask after logging in is SELECT VERSION()."

Then the triage line on the board, which is worth the whole lesson: command not found = PATH · 1045 = the server answered and refused you · 2002/2003 = nothing answered.

Twenty-five minutes is enough to fix configuration and start an install, not to download and install on slow Wi-Fi: use the USB stick.

Live demo (you type, they follow)

Connect and verify, from a fresh terminal on the projector. The two shell steps print text that differs on every machine (the lesson shows each platform's version); everything else is real output from a MySQL 9.7 server.

  1. Client version: no server needed (1m). "First the program on my laptop. This works even with the server stopped." 
    mysql --version
    The output is the lesson's "Output" card for your platform (for example mysql Ver 9.7.2 for Linux on x86_64 (MySQL Community Server - GPL)). Your exact text will differ.
  2. Log in (1m). "-u is the user, -p means ask me for the password. Nothing appears while I type it: that is normal." 
    mysql -u root -p
    Docker: docker exec -it mysql97 mysql -u root -p.
  3. Which server answered? (1m). "Now ask the SERVER." 
    SELECT VERSION();
    +-----------+
| VERSION() |
+-----------+
| 9.7.2     |
+-----------+
    Any 9.7.x is right. 8.4, 26.x or a version containing MariaDB means another server than intended: Common Mistake 5.
  4. What is in it? (1m). "A fresh server holds four system databases. Never put your own tables in them." 
    SHOW DATABASES;
    +--------------------+
| Database           |
+--------------------+
| information_schema |
| mysql              |
| performance_schema |
| sys                |
+--------------------+
  5. Who am I? (1m). "root, connected from this computer." 
    SELECT CURRENT_USER();
    +----------------+
| CURRENT_USER() |
+----------------+
| root@localhost |
+----------------+
    Through Docker's published port with -h 127.0.0.1 it says root@%.
  6. The health check, part 1 (2m). "These are the lesson project's Step 3 queries. @@ names read server settings." (The lesson's version also prints @@port: show it on your server; it is 3306 on a standard install.) 
    SELECT VERSION() AS version, @@version_comment AS edition;
    +---------+------------------------------+
| version | edition                      |
+---------+------------------------------+
| 9.7.2   | MySQL Community Server - GPL |
+---------+------------------------------+
  7. The health check, part 2 (2m). "utf8mb4 is full Unicode: every language and emoji. It is the default since 8.0." 
    SELECT
    CURRENT_USER()         AS logged_in_as,
    @@character_set_server AS charset,
    @@collation_server     AS collation;
    +----------------+---------+--------------------+
| logged_in_as   | charset | collation          |
+----------------+---------+--------------------+
| root@localhost | utf8mb4 | utf8mb4_0900_ai_ci |
+----------------+---------+--------------------+
  8. How does root log in? (2m). "Accounts live in the mysql.user table. Look, never edit by hand." 
    SELECT user, host, plugin
FROM mysql.user
WHERE user = 'root'
ORDER BY host;
    +------+-----------+-----------------------+
| user | host      | plugin                |
+------+-----------+-----------------------+
| root | localhost | caching_sha2_password |
+------+-----------+-----------------------+
    Docker shows a second row, root with host %. Ubuntu's own package shows auth_socket until a password is set.
  9. Old advice 1, on purpose (2m). "A forum says: create your app's user with mysql_native_password. On 9.7:" 
    CREATE USER 'legacy_app'@'localhost'
    IDENTIFIED WITH mysql_native_password BY 'placeholder-password';
    ERROR 1524 (HY000): Plugin 'mysql_native_password' is not loaded
    The plugin is gone in 9.x (disabled in 8.4). Fix: leave IDENTIFIED WITH out; update the client instead of weakening the server. No account was created.
  10. Old advice 2, on purpose (1m). "And the setting old tutorials tell you to check:" 
    SELECT @@default_authentication_plugin;
    ERROR 1193 (HY000): Unknown system variable 'default_authentication_plugin'
    Removed too; the modern setting is @@authentication_policy.
  11. Leave cleanly (1m). "exit, or Ctrl+D on macOS and Linux." 
    exit
Three mistakes to expect, and how to coach each
  • Asking the client instead of the server. "mysql --version says 9.7, so my server is 9.7." Coach: "Which box does that command ask? Log in and ask the server." (Self-check Q7 and the lesson's Exercise 1.)
  • Reading the wrong half of an error. Learners stop at "ERROR" and guess. Coach the triage line: "Which number? 1045, the server answered and said no: check the password. 2002 or 2003, nobody answered: check that the server runs and where you are knocking."
  • Weakening the server to fix a client. Someone finds advice to switch root to mysql_native_password (or tries it and gets 1524). Coach: "That method was removed in 9.x for good reasons; update the tool instead." Never run anything that changes root's login method in class.

Checks for understanding

Ask these out loud during the clinic, the demo and the lab:

  • Your client prints 9.7.2 but SELECT VERSION(); prints 8.4.x. Which is the server? Answer: 8.4: only the query asks the server.
  • 1045 or 2003: which one means the server is running? Answer: 1045: it answered and refused the credentials.
  • Why connect to a Docker container with 127.0.0.1 rather than localhost? Answer: on macOS and Linux, localhost makes the client use a local socket file and ignore the port.
  • Is root without a password acceptable on a laptop? Answer: no: any program on the computer could connect. A strong password costs nothing.

Closing

Exit ticket (3 questions, no notes, 4 minutes)

Put the three questions on the slide. Learners answer in the workbook's Exit Ticket box or on a sticky note and leave it on the way out. Sort the notes into "got it" and "not yet" before Session 2: question 1's pile tells you how much of the Session 2 warm-up goes to the server, client and database picture.

  1. In one sentence each: what is the MySQL server, what is a client, and what is a database? Answer: the server (mysqld) is the program that stores data and answers SQL; a client (the mysql command, phpMyAdmin) is what you type into and it sends SQL to the server; a database (such as preview_shop, later bookstore) is a named collection of tables inside the server.
  2. You type mysql -u root -p and get ERROR 2002. What do you check first? And if it were ERROR 1045? Answer: 2002: is the server running (and am I asking the right place)? 1045: the user name and password.
  3. orders(id, customer_id, order_date): name the primary key and the foreign key. Why not store the customer's name in orders? Answer: id is the primary key, customer_id the foreign key. The name lives once in customers; copies in every order would drift apart.
