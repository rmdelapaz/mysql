Session 3: Data Types, Constraints and CRUD

How to teach the third session of MySQL Foundations. Learners see why every column has a type and why rules belong in the database (MySQL refusing bad numbers, money, text, dates and duplicates, each with its own error number), then fill the bookstore with data and change it safely: INSERT, SELECT, UPDATE and DELETE with the preview habit, upserts, safe-updates mode, and a reload script for the data Module 3 queries.

2 lessons 3 hrs session Lessons 2.2–2.3 Session 3 of 14 · Part 1

How to Use This Guide

  • Same rhythm for both lessons: frame → live demo (you type, they follow) → guided lab (a kit lab, new practice) → the lesson's own project. The lesson exercises, quiz and journal are homework.
  • Every SQL block below was run to produce the output under it, on MySQL 9.7.2, inside bookstore as Lesson 2.1's build script leaves it. Ask for a prediction before every statement, especially the ones that fail: predicting the error number is the skill of the day.
  • Keep lesson_05.html and lesson_06.html open for the type tables and the DELETE/TRUNCATE/DROP table. Labs live in labs/module-03/ and run inside bookstore (learners USE bookstore; once).
  • This session has many error numbers. Do not ask learners to memorize them: put the lesson's error table on the board at the start and point at it each time.
  • Session 4 rebuilds bookstore with Lesson 3.1's setup script, so nothing here can leave a learner stuck; the lesson projects (employees.sql, load_bookstore_data.sql) are still worth finishing.
The #1 risk of Session 3: a learner's bookstore is not what the lessons expect

Everything today assumes bookstore with exactly three empty tables. Learners who did not finish create_bookstore.sql, or who left demo tables behind, get different outputs from the first statement on. The warm-up checks it on every laptop (USE bookstore; SHOW TABLES;), and the fix takes ten seconds: rerun create_bookstore.sql, or SOURCE labs/_states/schema.sql (the same three empty tables). The second risk is the 2.2 demo's length: twelve small steps; keep each to its minutes and cut Step 5 (text) first.

Lesson Plans

2.2

Data Types & Constraints

70 min
Objectives (from the lesson page)
  • Pick an integer type and decide when UNSIGNED makes sense; explain why money is DECIMAL, never FLOAT
  • Choose between CHAR, VARCHAR and TEXT, and between DATE, DATETIME and TIMESTAMP
  • Use BOOLEAN and ENUM correctly, knowing what MySQL really stores
  • Apply PRIMARY KEY, AUTO_INCREMENT, NOT NULL, UNIQUE, DEFAULT and named CHECK constraints
  • Read the errors strict mode raises for bad values (1048, 1062, 1264, 1265, 1292, 1364, 1406, 3819)
Timing in the room
10mFrame: a type is a promise, a constraint a rule; strict mode refuses instead of guessing
25mLive demo: numbers, money, text, dates, ENUM; the coupons table; the BOOLEAN trap
20mGuided lab: types_matter_starter.sql in pairs
15mStart the lesson project: employees.sql Steps 1 to 4, then Step 6's cleanup
Mental model to say

Draw the lesson's flowchart: a value arrives → does it fit the column's type? → does it pass the constraints? → stored, or the row is rejected with a number. "Every program and every person that writes to this table goes through this door. That is far safer than hoping each one checks."

Then strict mode in one breath: "MySQL 9.7 starts in strict mode: a value that does not fit is an error. Without it MySQL would quietly cut, round or clamp and only warn. Old tutorials show that; some hosts still do it. Keep it on."

Then the rule of thumb on the board: choose the type that says what the value is, then the smallest size that comfortably fits the biggest value you can imagine, then NOT NULL on every column a row cannot do without. Money is DECIMAL; phone numbers and ZIP codes are text.

Live demo (you type, they follow)

Inside bookstore (USE bookstore;). The demo creates six small demo tables next to the three real ones and drops them in the last step. Ask for the error number before every refused statement.

  1. One column of each kind of number (3m). "A type is a promise about the values; MySQL keeps it for you." Read the four types aloud. 
    CREATE TABLE number_demo (
    stars     TINYINT,
    copies    SMALLINT UNSIGNED,
    price     DECIMAL(8, 2),
    weight_kg FLOAT
);
INSERT INTO number_demo (stars, copies, price, weight_kg)
VALUES (5, 120, 14.99, 0.1);
SELECT * FROM number_demo;
    +-------+--------+-------+-----------+
| stars | copies | price | weight_kg |
+-------+--------+-------+-----------+
|     5 |    120 | 14.99 |       0.1 |
+-------+--------+-------+-----------+
  2. A number that does not fit (1m). "A TINYINT stops at 127. Predict: what happens to 200?" 
    INSERT INTO number_demo (stars) VALUES (200);
    ERROR 1264 (22003): Out of range value for column 'stars' at row 1
    Strict mode (the default) refuses instead of quietly storing 127.
  3. Too many decimals is different (2m). "Three decimals into a two-decimal column." 
    INSERT INTO number_demo (price) VALUES (12.345);
SHOW WARNINGS;
SELECT price FROM number_demo WHERE stars IS NULL;
    +-------+------+--------------------------------------------+
| Level | Code | Message                                    |
+-------+------+--------------------------------------------+
| Note  | 1265 | Data truncated for column 'price' at row 1 |
+-------+------+--------------------------------------------+
+-------+
| price |
+-------+
| 12.35 |
+-------+
    Rounded, with a Note. Rounding to the column's precision is not an error.
  4. Why money is never FLOAT (3m). "Multiply both by 3. And is the stored 0.1 even equal to 0.1?" 
    SELECT
    price * 3        AS decimal_times_3,
    weight_kg * 3    AS float_times_3,
    weight_kg = 0.1  AS float_equals_0_1
FROM number_demo
WHERE stars = 5;
    +-----------------+---------------------+------------------+
| decimal_times_3 | float_times_3       | float_equals_0_1 |
+-----------------+---------------------+------------------+
|           44.97 | 0.30000000447034836 |                0 |
+-----------------+---------------------+------------------+
    The DECIMAL result is exact; FLOAT stores binary fractions. Over thousands of orders the crumbs become real money.
  5. Text that is too long (1m). "Fourteen characters into VARCHAR(5)." 
    CREATE TABLE text_demo (
    code  CHAR(5),
    label VARCHAR(5)
);
INSERT INTO text_demo (label) VALUES ('Fahrenheit 451');
    ERROR 1406 (22001): Data too long for column 'label' at row 1
    Strict mode refuses instead of storing Fahre.
  6. Dates are checked (2m). "February 30th. Then the date the way an American writes it." 
    CREATE TABLE date_demo (d DATE, dt DATETIME);
INSERT INTO date_demo (d) VALUES ('2026-02-30');
INSERT INTO date_demo (d) VALUES ('03/10/2026');
    ERROR 1292 (22007): Incorrect date value: '2026-02-30' for column 'd' at row 1
ERROR 1292 (22007): Incorrect date value: '03/10/2026' for column 'd' at row 1
    Dates are year first: '2026-03-10'. Spreadsheet dates go in with STR_TO_DATE (the lab uses it).
  7. ENUM: one value from a list (2m). "A default, and a value that is not on the list." 
    CREATE TABLE format_demo (
    title  VARCHAR(50) NOT NULL,
    format ENUM('paperback', 'hardcover', 'ebook') NOT NULL DEFAULT 'paperback'
);
INSERT INTO format_demo (title, format) VALUES ('Dune', 'hardcover');
INSERT INTO format_demo (title) VALUES ('Emma');
INSERT INTO format_demo (title, format) VALUES ('1984', 'audiobook');
SELECT title, format FROM format_demo;
    ERROR 1265 (01000): Data truncated for column 'format' at row 1
+-------+-----------+
| title | format    |
+-------+-----------+
| Dune  | hardcover |
| Emma  | paperback |
+-------+-----------+
    1265 "Data truncated" is how MySQL says the value is not one of the options.
  8. A table with every kind of rule (3m). Read the CREATE line by line: "required, never repeated, a default, and a named CHECK." 
    CREATE TABLE coupons (
    id           INT AUTO_INCREMENT PRIMARY KEY,
    code         VARCHAR(20) NOT NULL UNIQUE,
    percent_off  TINYINT UNSIGNED NOT NULL,
    min_order    DECIMAL(8, 2) NOT NULL DEFAULT 0.00,
    expires      DATE,
    CONSTRAINT chk_coupon_percent CHECK (percent_off BETWEEN 5 AND 50)
);
INSERT INTO coupons (code, percent_off, expires) VALUES ('WELCOME10', 10, '2026-12-31');
INSERT INTO coupons (code, percent_off, min_order) VALUES ('BIGBASKET', 20, 50.00);
SELECT * FROM coupons;
    +----+-----------+-------------+-----------+------------+
| id | code      | percent_off | min_order | expires    |
+----+-----------+-------------+-----------+------------+
|  1 | WELCOME10 |          10 |      0.00 | 2026-12-31 |
|  2 | BIGBASKET |          20 |     50.00 | NULL       |
+----+-----------+-------------+-----------+------------+
  9. Break every rule (3m). Ask for the four error numbers BEFORE you run it; write predictions on the board. 
    INSERT INTO coupons (code, percent_off) VALUES (NULL, 15);
INSERT INTO coupons (code) VALUES ('SPRING15');
INSERT INTO coupons (code, percent_off) VALUES ('WELCOME10', 15);
INSERT INTO coupons (code, percent_off) VALUES ('HALFPRICE', 75);
    ERROR 1048 (23000): Column 'code' cannot be null
ERROR 1364 (HY000): Field 'percent_off' doesn't have a default value
ERROR 1062 (23000): Duplicate entry 'WELCOME10' for key 'coupons.code'
ERROR 3819 (HY000): Check constraint 'chk_coupon_percent' is violated.
    Explicit NULL 1048, left out 1364, duplicate 1062, CHECK 3819 (named, so you know which rule).
  10. The id after failed inserts (2m). "Which id does SUMMER25 get?" 
    INSERT INTO coupons (code, percent_off) VALUES ('SUMMER25', 25);
SELECT LAST_INSERT_ID();
SELECT id, code FROM coupons ORDER BY id;
    +------------------+
| LAST_INSERT_ID() |
+------------------+
|                4 |
+------------------+
+----+-----------+
| id | code      |
+----+-----------+
|  1 | WELCOME10 |
|  2 | BIGBASKET |
|  4 | SUMMER25  |
+----+-----------+
    4, not 3: a failed insert used up an id. Gaps are normal; an id is a label, not a count.
  11. The silent BOOLEAN trap (2m). "BOOLEAN is a TINYINT, so 5 goes in. Which books are in stock?" 
    CREATE TABLE flag_demo (title VARCHAR(50), in_stock BOOLEAN);
INSERT INTO flag_demo VALUES ('Dune', TRUE), ('Emma', FALSE), ('1984', 5);
SELECT title, in_stock FROM flag_demo WHERE in_stock = TRUE;
SELECT title, in_stock FROM flag_demo WHERE in_stock;
    +-------+----------+
| title | in_stock |
+-------+----------+
| Dune  |        1 |
+-------+----------+
+-------+----------+
| title | in_stock |
+-------+----------+
| Dune  |        1 |
| 1984  |        5 |
+-------+----------+
    = TRUE means = 1; 1984 disappears. Test truth with WHERE in_stock.
  12. Clean up (1m). "Back to the three tables Lesson 2.3 expects." 
    DROP TABLE IF EXISTS number_demo, text_demo, date_demo, format_demo, coupons, flag_demo;
SHOW TABLES;
    +---------------------+
| Tables_in_bookstore |
+---------------------+
| books               |
| categories          |
| customers           |
+---------------------+
Three mistakes to expect, and how to coach each
  • Numbers that are really identifiers stored as numbers. A ZIP code or phone as INT loses leading zeros. Coach: "Will you ever add two of these together? No? Then it is text."
  • Constraints forgotten for the obvious columns. Learners write email VARCHAR(100) and stop. Coach with the question: "Does a row make sense without this value? Can two rows share it?"
  • Reading 1265 as a rounding message only. It also means "not on the ENUM list". Coach: "Read the column name in the message: price (rounded) or format (not an option)?"

Checks for understanding

Ask these out loud during the demo and the lab:

  • Why is a phone number VARCHAR and not INT? Answer: it can start with 0 or +, has dashes, can be longer than INT allows, and nobody adds phone numbers.
  • 1048 or 1364: which one is an explicit NULL? Answer: 1048; 1364 is a required column left out.
  • Why name a CHECK constraint? Answer: the error then says which rule failed (chk_salary), instead of employees_chk_1.
  • WHERE in_stock = TRUE misses a row holding 5. What should you write? Answer: WHERE in_stock (any non-zero), and a CHECK if only 0/1 is allowed.

CRUD Operations

80 min
Objectives (from the lesson page)
  • Create rows with INSERT: one row, many rows, with defaults, and read back the new id
  • Read rows with SELECT: chosen columns, aliases, calculated columns and DISTINCT
  • Update and delete exactly the rows you mean, using the "SELECT first" habit and safe-updates mode
  • Write an upsert with INSERT ... AS new ON DUPLICATE KEY UPDATE, and explain how it differs from REPLACE and INSERT IGNORE
  • Read and fix errors 1054, 1062, 1136 and 1175

Mental model to say

Write CRUD on the board with its four statements. Then the lesson's key sentence: "INSERT only ever adds. UPDATE and DELETE act on every row their WHERE matches, and on every row in the table if there is no WHERE at all. There is no undo."

Then the habit, as a three-step recipe: 1 SELECT with the WHERE you mean · 2 the UPDATE or DELETE with exactly the same WHERE · 3 compare the counts (the preview's rows and Rows matched). "Safe-updates mode is the seat belt; the preview is looking before you pull out."

And the upsert in one line: "Insert it, or update it if it is already there": the nightly-import problem every shop has.

Live demo (you type, they follow)

Inside bookstore with three empty tables. These blocks keep MySQL's Query OK and Rows matched lines on purpose: read them aloud every time. The demo empties books and categories at the end, so the project starts clean.

  1. Create: one row (2m). "List the columns, then the values in the same order. id and in_stock are left out on purpose."

  11. Categories, then an upsert (3m). Insert the five categories, then: "Fiction exists. Insert it, or update it if it is there." 
    INSERT INTO categories (name, description) VALUES
    ('Fiction', 'Novels, short stories, and other imaginative works'),
    ('Science Fiction', 'Stories exploring futuristic or scientific concepts'),
    ('Classic', 'Timeless literary works recognized across generations'),
    ('Fantasy', 'Stories set in imaginary worlds with magical elements'),
    ('Dystopian', 'Stories about oppressive societies and dark futures');

INSERT INTO categories (name, description)
VALUES ('Fiction', 'Imaginative prose of every kind') AS new
ON DUPLICATE KEY UPDATE description = new.description;
    Query OK, 2 rows affected
    2 rows affected = the update branch ran (1 = inserted, 0 = unchanged). MariaDB has no AS new: VALUES(description) there.
  12. The safety switch (2m). "The classic slip, with safe-updates on." 
    SET SQL_SAFE_UPDATES = 1;
UPDATE books SET price = 0;
    ERROR 1175 (HY000): You are using safe update mode and you tried to update a table without a WHERE that uses a KEY column.
    Then SET SQL_SAFE_UPDATES = 0; again for the rest of the demo (its WHEREs use non-key columns).
  13. AND instead of a comma (2m). "Dune: 15.99 and out of stock. Predict." 
    UPDATE books
SET price = 15.99 AND in_stock = FALSE
WHERE id = 1;
SELECT title, price, in_stock FROM books WHERE id = 1;
    Query OK, 1 row affected
Rows matched: 1  Changed: 1  Warnings: 0
+-------+-------+----------+
| title | price | in_stock |
+-------+-------+----------+
| Dune  |  0.00 |        1 |
+-------+-------+----------+
    No error, one row changed, price 0.00 and still in stock: price = (15.99 AND (in_stock = FALSE)). With TEXT values the same slip is refused (1292), as the debug handout shows.
  14. Empty the tables (1m). "The project loads the official data from nothing." 
    TRUNCATE TABLE books;
TRUNCATE TABLE categories;
Three mistakes to expect, and how to coach each
  • Text without quotes (VALUES (Emma, ...) → 1054 Unknown column 'Emma'). Coach: "Without quotes MySQL thinks Emma is a column." A quote inside text is doubled: 'Charlotte''s Web'.
  • Not reading the second line. Learners see Query OK and move on. Coach: "How many rows did the WHERE match? Is that the number your preview showed?"
  • AND in SET. No error with numbers (price becomes 0.00), ERROR 1292 with text. Coach: "Assignments are separated by commas." Then look at the changed row.

Checks for understanding

Ask these out loud during the demo and the lab:

  • UPDATE books SET price = 0;: what happens in a normal session? Answer: every price becomes 0.00, no undo.
  • You deleted id 10 and inserted a book. Which id? Answer: 11: AUTO_INCREMENT never reuses a number.
  • The upsert says 2 rows affected. Which branch ran? Answer: the update (1 = inserted, 0 = unchanged).
  • Why avoid REPLACE on a row other tables point to? Answer: it deletes and re-inserts: a new id, and the unlisted columns get their defaults.

Workbook self-check, items Q7 to Q12.

Answers: Q7 D) It depends on the table's exact column order: an added column breaks it (1136) or shifts values silently; Q8 2; Q9 A) The WHERE found no rows: often a typo in the value or the wrong column; Q10 C) UPDATE books SET price = 9.99 WHERE id = 2;; Q11 B) INSERT ... AS new ON DUPLICATE KEY UPDATE description = new.description;; Q12 3. Full set with explanations in the Answer Key.

Closing

Exit ticket (3 questions, no notes, 4 minutes)

Put the three questions on the slide; learners answer in the workbook or on a sticky note. Question 3's answers tell you whether the preview habit stuck.

  1. Why is money stored as DECIMAL and never as FLOAT? One sentence and one example. Answer: DECIMAL is exact; FLOAT stores binary fractions, so most decimal values are slightly off and the crumbs add up: 0.1 stored as FLOAT times 3 printed 0.30000000447034836 in the demo, and the lab's FLOAT total was 556.9499866962433 instead of 556.95.
  2. An UPDATE says Rows matched: 3 Changed: 2. What happened to the third row? Answer: The WHERE found it, but it already had the new value, so nothing changed in it. (Matched 0 would mean the WHERE found nothing.)
  3. What do you run before every UPDATE or DELETE that touches more than one row, and why? Answer: A SELECT with exactly the same WHERE: it shows which rows will be touched, and its row count must match the UPDATE's Rows matched. Safe-updates mode (SET SQL_SAFE_UPDATES = 1; or mysql --safe-updates) is the second net.
