Lessons

2.2

Data Types & Constraints

By the end you can
  • Pick an integer type and decide when UNSIGNED makes sense; explain why money is DECIMAL, never FLOAT
  • Choose between CHAR, VARCHAR and TEXT, and between DATE, DATETIME and TIMESTAMP
  • Use BOOLEAN and ENUM correctly, knowing what MySQL really stores
  • Apply PRIMARY KEY, AUTO_INCREMENT, NOT NULL, UNIQUE, DEFAULT and named CHECK constraints
  • Read the errors strict mode raises for bad values (1048, 1062, 1264, 1265, 1292, 1364, 1406, 3819)
Key ideas
  • A type is a promise MySQL keeps: it validates values, makes math and sorting work, and decides the size.
  • Strict mode (the default) turns a value that does not fit into an error instead of a silent change. Keep it on.
  • Numbers: INT is the default; TINYINT/SMALLINT for small ranges; UNSIGNED forbids negatives. Money is DECIMAL(m, d), never FLOAT.
  • Text: VARCHAR(n) for almost everything, CHAR(n) for fixed-length codes, TEXT for long writing. Phone numbers and ZIP codes are text.
  • Dates are 'YYYY-MM-DD'. DATETIME for moments; TIMESTAMP converts time zones but ends in 2038.
  • BOOLEAN is TINYINT(1): test it with WHERE col, not = TRUE. ENUM is one value from a short, stable list.
  • Constraints: PRIMARY KEY, AUTO_INCREMENT, NOT NULL, UNIQUE, DEFAULT, named CHECK. Errors: 1048/1364 required · 1062 duplicate · 1264 out of range · 1265 not on the list · 1292 bad date · 1406 too long · 3819 CHECK.
Worked example: a preorder slip

A preorder slip, with a type and rules for every column: the email and ISBN are required, the number of copies is small and never negative, the deposit is money with a limit, the format is one of three.

CREATE TABLE kit_preorders (
    id         INT AUTO_INCREMENT PRIMARY KEY,
    email      VARCHAR(100) NOT NULL,
    isbn       CHAR(13) NOT NULL,
    copies     TINYINT UNSIGNED NOT NULL DEFAULT 1,
    deposit    DECIMAL(6, 2) NOT NULL DEFAULT 0.00,
    format     ENUM('paperback', 'hardcover', 'ebook') NOT NULL DEFAULT 'paperback',
    wanted_by  DATE,
    CONSTRAINT chk_preorder_deposit CHECK (deposit <= 50)
);
INSERT INTO kit_preorders (email, isbn) VALUES ('ana@example.com', '9780441013593');
INSERT INTO kit_preorders (email, isbn, copies, deposit, format, wanted_by)
VALUES ('ben@example.com', '9780547928227', 2, 10.00, 'hardcover', '2026-12-15');

Ana gave only the required values; the defaults filled in the rest:

SELECT id, email, copies, deposit, format, wanted_by
FROM kit_preorders
ORDER BY id;
+----+-----------------+--------+---------+-----------+------------+
| id | email           | copies | deposit | format    | wanted_by  |
+----+-----------------+--------+---------+-----------+------------+
|  1 | ana@example.com |      1 |    0.00 | paperback | NULL       |
|  2 | ben@example.com |      2 |   10.00 | hardcover | 2026-12-15 |
+----+-----------------+--------+---------+-----------+------------+

MySQL keeps every CHECK in information_schema, under the name you gave it:

SELECT CONSTRAINT_NAME, CHECK_CLAUSE
FROM information_schema.CHECK_CONSTRAINTS
WHERE CONSTRAINT_SCHEMA = DATABASE();
+----------------------+-------------------+
| CONSTRAINT_NAME      | CHECK_CLAUSE      |
+----------------------+-------------------+
| chk_preorder_deposit | (`deposit` <= 50) |
+----------------------+-------------------+

Clean up (the slip was practice):

DROP TABLE kit_preorders;

2.3

CRUD Operations

By the end you can
  • Create rows with INSERT: one row, many rows, with defaults, and read back the new id
  • Read rows with SELECT: chosen columns, aliases, calculated columns and DISTINCT
  • Update and delete exactly the rows you mean, using the "SELECT first" habit and safe-updates mode
  • Write an upsert with INSERT ... AS new ON DUPLICATE KEY UPDATE, and explain how it differs from REPLACE and INSERT IGNORE
  • Read and fix errors 1054, 1062, 1136 and 1175
Key ideas
  • CRUD: INSERT creates, SELECT reads, UPDATE changes, DELETE removes. WHERE picks the rows; without it, every row.
  • INSERT always with a column list; several value lists in one statement; LAST_INSERT_ID() is the id just given (the first one after a multi-row insert).
  • SELECT names the columns it needs; AS renames; calculations never change the table; DISTINCT shows each value once.
  • Preview, change, compare: a SELECT with the same WHERE first; then read Rows matched and Changed.
  • Safe-updates mode (SET SQL_SAFE_UPDATES = 1;, mysql --safe-updates) refuses UPDATE/DELETE without a key in the WHERE: error 1175.
  • SET separates assignments with commas, never AND. AUTO_INCREMENT ids are never reused.
  • Upsert: INSERT ... AS new ON DUPLICATE KEY UPDATE col = new.col (1 inserted, 2 updated, 0 unchanged). REPLACE deletes and re-inserts; INSERT IGNORE skips.
Worked example: a change in three steps

A change to several rows in three steps: preview, change with the same WHERE, check. Four customers first:

INSERT INTO customers (first_name, last_name, email, city, created_at) VALUES
    ('Nina', 'Park', 'nina@example.com', 'Denver', '2026-03-01 09:00:00'),
    ('Omar', 'Haddad', 'omar@example.com', 'Boston', '2026-03-02 10:30:00'),
    ('Paula', 'Reyes', 'paula@example.com', 'Denver', '2026-03-03 12:00:00'),
    ('Quinn', 'Lee', 'quinn@example.com', NULL, '2026-03-04 15:45:00');

Step 1, the preview: who lives in Denver?

SELECT id, first_name, city
FROM customers
WHERE city = 'Denver'
ORDER BY id;
+----+------------+--------+
| id | first_name | city   |
+----+------------+--------+
|  1 | Nina       | Denver |
|  3 | Paula      | Denver |
+----+------------+--------+

Step 2, the same WHERE in the UPDATE. Read the second line: 2 matched, the same 2 the preview showed:

UPDATE customers
SET city = 'Aurora'
WHERE city = 'Denver';
Query OK, 2 rows affected
Rows matched: 2  Changed: 2  Warnings: 0

Step 3, look at the result. Quinn's NULL city was not touched: NULL = 'Denver' is not true.

SELECT id, first_name, city
FROM customers
ORDER BY id;
+----+------------+--------+
| id | first_name | city   |
+----+------------+--------+
|  1 | Nina       | Aurora |
|  2 | Omar       | Boston |
|  3 | Paula      | Aurora |
|  4 | Quinn      | NULL   |
+----+------------+--------+

Glossary

TermMeaning
data typeWhat kind of value a column holds (INT, DECIMAL, VARCHAR, DATE...)
strict modeSTRICT_TRANS_TABLES in sql_mode: values that do not fit are errors, not silent changes
UNSIGNEDNo negative numbers; the range shifts up
DECIMAL(m, d)An exact number: m digits in all, d after the point; the type for money
ENUMOne value from a fixed list; sorts by list position
constraintA rule MySQL enforces for every writer: PRIMARY KEY, NOT NULL, UNIQUE, DEFAULT, CHECK
CRUDCreate, Read, Update, Delete: INSERT, SELECT, UPDATE, DELETE
Rows matched / ChangedHow many rows the WHERE found / how many got a new value
LAST_INSERT_ID()The AUTO_INCREMENT id your session's last INSERT received
ROW_COUNT()How many rows the previous statement changed
safe-updates modeRefuses UPDATE and DELETE without a key column in the WHERE (error 1175)
upsertInsert a row, or update it if its key already exists (ON DUPLICATE KEY UPDATE)
