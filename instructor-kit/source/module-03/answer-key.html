Warm-Up: Session 2

Not graded.

W1
The prompt shows ->. What do you type?
A) exit
B) ; and Enter
C) Ctrl+C
D) USE bookstore;
Why: -> means the statement is not finished: the client waits for the semicolon (Lesson 1.3).
W2
MySQL says ERROR 1146 (42S02): Table 'mysql.books' doesn't exist. What do you check first?
A) Reinstall MySQL
B) Whether books was dropped
C) Which database you are in: the message says mysql, not bookstore
D) The password
Why: The message names the database it looked in. USE bookstore; (or bookstore.books) fixes it.
W3
Which of these works in phpMyAdmin's SQL tab?
A) DESCRIBE books;
B) SOURCE create_bookstore.sql
C) \G
D) exit
Why: DESCRIBE is SQL; the other three are mysql client commands.
W4
What does SHOW COLUMNS print under Null?
CREATE TABLE w4 (id INT PRIMARY KEY, title VARCHAR(200) NOT NULL);
ALTER TABLE w4 MODIFY COLUMN title VARCHAR(250);
SHOW COLUMNS FROM w4 LIKE 'title';
A) NO: NOT NULL is kept
B) YES: MODIFY replaced the whole definition
C) Nothing: ERROR 1064
D) NO, with a warning
Why: MODIFY uses exactly the definition you typed: repeat NOT NULL. Session 2's exit ticket question 3. MySQL prints:
+-------+--------------+------+-----+---------+-------+

+-------+--------------+------+-----+---------+-------+

+-------+--------------+------+-----+---------+-------+

2.2 · Data Types & Constraints: self-check

Q1
A column holds a discount as a whole percentage from 0 to 100. Which type is the smallest sensible choice?
A) TINYINT UNSIGNED
B) INT
C) DECIMAL(5, 2)
D) VARCHAR(3)
Why: TINYINT UNSIGNED holds 0 to 255 in one byte: enough for 0 to 100, and it refuses negatives. Add a CHECK (percent BETWEEN 0 AND 100) to enforce the exact range.
B is wrong: It works, but takes four bytes for a value that fits in one.
C is wrong: There are no decimals to store.
D is wrong: A number stored as text sorts and adds up wrongly.
Q2
What does the SELECT print?
CREATE TABLE q2 (amount DECIMAL(5, 2));
INSERT INTO q2 VALUES (7.005);
SELECT amount FROM q2;
7.01
Why: A DECIMAL(5, 2) keeps two decimals, so 7.005 is rounded (half up) to 7.01, with a Note 1265. Rounding to the column's precision is not an error; a value too big for the column is (1264).
Q3
What happens when this runs?
CREATE TABLE q3 (due DATE);
INSERT INTO q3 VALUES ('2026-04-31');
A) 2026-05-01 is stored
B) 2026-04-30 is stored
C) ERROR 1292 (22007): Incorrect date value: '2026-04-31' for column 'due' at row 1
D) NULL is stored with a warning
Why: April has 30 days. In strict mode (the default) MySQL checks that a date really exists and refuses the row.
A is wrong: MySQL does not roll dates over.
B is wrong: MySQL does not correct your value.
D is wrong: That is what happens with strict mode switched off: a reason to keep it on.
Q4
A library stores the moment each long-term loan ends, some of them in 2045. Which type fits best?
A) TIMESTAMP
B) DATE
C) YEAR
D) DATETIME
Why: A moment needs a date AND a time, and DATETIME runs to the year 9999. This course uses DATETIME everywhere.
A is wrong: TIMESTAMP stops in January 2038 on MySQL (error 1292 for 2040 in the lesson).
B is wrong: A DATE has no time of day.
C is wrong: YEAR holds only a year (1901 to 2155).
Q5
email is NOT NULL. An INSERT gives it the value NULL explicitly. Which error?
A) ERROR 1364: Field 'email' doesn't have a default value
B) ERROR 1048: Column 'email' cannot be null
C) ERROR 1062: Duplicate entry
D) ERROR 3819: Check constraint is violated
Why: Two flavors of NOT NULL: an explicit NULL gives 1048; leaving the column out of the INSERT when it has no default gives 1364.
A is wrong: 1364 is the column left out entirely.
C is wrong: 1062 is a duplicate in a UNIQUE column or primary key.
D is wrong: 3819 is a CHECK constraint.
Q6
In which order does the SELECT list the three sizes?
CREATE TABLE q6 (size ENUM('small', 'medium', 'large'));
INSERT INTO q6 VALUES ('large'), ('small'), ('medium');
SELECT size FROM q6 ORDER BY size;
small, medium, large
Why: ORDER BY on an ENUM sorts by the position in the list the column was declared with, not alphabetically (that would be large, medium, small). Handy here; surprising elsewhere.

2.2 · Data Types & Constraints: predict, then run

P1
Predict the output, then run it.
CREATE TABLE codes (code CHAR(6), label VARCHAR(6));
INSERT INTO codes VALUES ('ab  ', 'ab  ');
SELECT CHAR_LENGTH(code)  AS code_len,
       CHAR_LENGTH(label) AS label_len
FROM codes;
+----------+-----------+
| code_len | label_len |
+----------+-----------+
|        2 |         4 |
+----------+-----------+
Why: Both received 'ab' plus two spaces. CHAR pads when storing and strips trailing spaces when reading (2); VARCHAR keeps them (4).
P2
Predict the output, then run it.
CREATE TABLE counts (n TINYINT UNSIGNED);
INSERT INTO counts VALUES (255);
INSERT INTO counts VALUES (256);
SELECT n FROM counts;
ERROR 1264 (22003): Out of range value for column 'n' at row 1
+------+
| n    |
+------+
|  255 |
+------+
Why: TINYINT UNSIGNED stops at 255: the first INSERT works, the second is refused with 1264, and the table holds one row.

2.3 · CRUD Operations: self-check

Q7
Why should you avoid INSERT INTO books VALUES (NULL, 'Emma', ...); without a column list?
A) It is slower than listing the columns
B) NULL is not allowed in an id
C) It inserts the row twice
D) It depends on the table's exact column order: an added column breaks it (1136) or shifts values silently
Why: With a column list, the INSERT keeps working whatever columns are added later.
A is wrong: Speed is the same.
B is wrong: NULL in an AUTO_INCREMENT column means "give it the next number".
C is wrong: One VALUES list is one row.
Q8
What does the last SELECT print?
CREATE TABLE q8 (id INT AUTO_INCREMENT PRIMARY KEY, t VARCHAR(10));
INSERT INTO q8 (t) VALUES ('a');
INSERT INTO q8 (t) VALUES ('b'), ('c'), ('d');
SELECT LAST_INSERT_ID();
2
Why: After a multi-row INSERT, LAST_INSERT_ID() returns the id of the FIRST row of that statement (b got 2, c 3, d 4).
Q9
An UPDATE reports Rows matched: 0 Changed: 0 Warnings: 0. What is most likely?
A) The WHERE found no rows: often a typo in the value or the wrong column
B) It worked: every row was changed
C) The rows already had those values
D) Safe-updates mode refused it
Why: Rows matched counts what the WHERE found; Changed counts the rows that got a new value. Matched 0 means nothing was found.
B is wrong: Changed 0 says nothing was changed.
C is wrong: That is Rows matched 1 (or more), Changed 0.
D is wrong: A refused statement prints ERROR 1175, not a row count.
Q10
After SET SQL_SAFE_UPDATES = 1;, which statement still runs? (id is the primary key.)
A) UPDATE books SET price = 0;
B) DELETE FROM books WHERE price > 10;
C) UPDATE books SET price = 9.99 WHERE id = 2;
D) DELETE FROM books;
Why: Safe-updates refuses UPDATE and DELETE unless the WHERE uses a key column (or a LIMIT is given). The other three end with ERROR 1175.
A is wrong: No WHERE at all: 1175.
B is wrong: price is not a key column: 1175, even with a WHERE.
D is wrong: No WHERE: 1175.
Q11
A category name already exists. Which statement updates its description and keeps its id and every other column?
A) REPLACE INTO categories (name, description) VALUES (...);
B) INSERT ... AS new ON DUPLICATE KEY UPDATE description = new.description;
C) INSERT IGNORE INTO categories (name, description) VALUES (...);
D) DELETE the old row, then INSERT the new one
Why: The upsert changes only the columns you name in the UPDATE part and keeps the row (and its id).
A is wrong: REPLACE deletes the old row and inserts a new one: a new id, and unlisted columns get their defaults.
C is wrong: INSERT IGNORE skips the row: nothing is updated.
D is wrong: That is what REPLACE does, with the same problems.
Q12
What does ROW_COUNT() print?
CREATE TABLE q12 (name VARCHAR(20) PRIMARY KEY, note VARCHAR(30));
INSERT INTO q12 VALUES ('a', 'x'), ('b', 'y');
INSERT INTO q12 VALUES ('a', 'x'), ('b', 'z'), ('c', 'w') AS new
ON DUPLICATE KEY UPDATE note = new.note;
SELECT ROW_COUNT() AS affected;
3
Why: An upsert counts 1 per inserted row, 2 per updated row, 0 per row that already had those values: a unchanged (0) + b updated (2) + c inserted (1) = 3.

2.3 · CRUD Operations: predict, then run

P3
Predict the output, then run it.
CREATE TABLE notes (id INT AUTO_INCREMENT PRIMARY KEY, t VARCHAR(10));
INSERT INTO notes (t) VALUES ('a'), ('b'), ('c');
DELETE FROM notes WHERE id = 3;
INSERT INTO notes (t) VALUES ('d');
SELECT * FROM notes;
+----+------+
| id | t    |
+----+------+
|  1 | a    |
|  2 | b    |
|  4 | d    |
+----+------+
Why: Id 3 is gone and is never handed out again, so the new row gets 4.
P4
Predict the output, then run it.
CREATE TABLE tags (name VARCHAR(20) PRIMARY KEY, uses INT NOT NULL);
INSERT INTO tags VALUES ('sale', 1);
INSERT INTO tags VALUES ('sale', 1) AS new
ON DUPLICATE KEY UPDATE uses = tags.uses + new.uses;
SELECT * FROM tags;
+------+------+
| name | uses |
+------+------+
| sale |    2 |
+------+------+
Why: The second INSERT finds 'sale' and adds the new uses to the old: 1 + 1 = 2. The column is written tags.uses on purpose: an unqualified uses = uses + new.uses is ERROR 1052 (Column 'uses' in field list is ambiguous) on MySQL 9.7, because the row alias new has a column named uses too.

What each TODO teaches: (1) text sorts character by character, so '9' comes after '15' and '120'; (2) FLOAT stores binary fractions: 556.9499866962433 instead of 556.95, a crumb that grows with every order; (3) dates as text sort by the month digits, so 12/01/2026 looks like the latest; a DATE column refuses the US format (1292), and STR_TO_DATE converts it. Note on Lesson 2.3's Bonus Challenge

The challenge's hint qualifies the old value: copies = stock_counts.copies + new.copies. The unqualified copies = copies + new.copies is ERROR 1052 on MySQL 9.7 (and 8.4), Column 'copies' in field list is ambiguous, because the row alias new has a copies column too. Verified: 5 copies of Dune twice gives 10. Learners who type it without the table name will hit 1052; that is the teaching moment.

The Lesson Pages' Own Quick Quizzes

Lesson 2.2 · Data Types & Constraints
  1. B DECIMAL(8, 2): DECIMAL stores exact decimal values, so prices and totals are correct to the cent. DECIMAL(8, 2) holds up to 999999.99.
  2. C Fails with error 1264, Out of range value: A signed TINYINT holds -128 to 127. In strict mode an out-of-range value is an error (1264) and the row is not stored.
  3. A One with an email that another row already has: UNIQUE refuses a second row with the same value, with error 1062 Duplicate entry. A NULL would fail too, but with 1048, because of NOT NULL.
  4. D A two-letter country code: CHAR suits values that always have the same length, such as a two-letter country code or a 13-digit ISBN.
  5. B WHERE in_stock: BOOLEAN is a TINYINT, and MySQL treats any non-zero number as true. WHERE in_stock keeps 1, 5 and every other non-zero value.
Lesson 2.3 · CRUD Operations
  1. A Every book's price becomes 0.00: Without a WHERE clause, UPDATE applies to every row. Only safe-updates mode (error 1175) would stop it, and it is off by default.
  2. C The row was found but already had those values: The WHERE found one row, but it already had the new values, so there was nothing to change. Matched 0 would point at a WHERE that found nothing.
  3. B ... AS new ON DUPLICATE KEY UPDATE description = new.description: The row alias form (AS new, then new.column) is the current MySQL syntax; VALUES() is deprecated. On MariaDB, which lacks the alias, VALUES() is still the way.
  4. C 11: AUTO_INCREMENT only moves forward. The gap at 10 stays, and the new row gets the next number, 11. Only TRUNCATE resets the counter.
  5. A Sets its price to 0.00 and leaves it in stock: SET reads price = (15.99 AND (in_stock = FALSE)). The book is in stock, so the comparison is false (0), and the price becomes 0.00. Separate assignments with commas.

Exit Ticket

  1. Why is money stored as DECIMAL and never as FLOAT? One sentence and one example. Answer: DECIMAL is exact; FLOAT stores binary fractions, so most decimal values are slightly off and the crumbs add up: 0.1 stored as FLOAT times 3 printed 0.30000000447034836 in the demo, and the lab's FLOAT total was 556.9499866962433 instead of 556.95.
  2. An UPDATE says Rows matched: 3 Changed: 2. What happened to the third row? Answer: The WHERE found it, but it already had the new value, so nothing changed in it. (Matched 0 would mean the WHERE found nothing.)
  3. What do you run before every UPDATE or DELETE that touches more than one row, and why? Answer: A SELECT with exactly the same WHERE: it shows which rows will be touched, and its row count must match the UPDATE's Rows matched. Safe-updates mode (SET SQL_SAFE_UPDATES = 1; or mysql --safe-updates) is the second net.

Common Wrong Answers and What They Reveal

  • Q1 B (INT). Correct but not thoughtful: ask for the smallest type that comfortably fits.
  • Q3 A or B. Expects MySQL to repair a date. Strict mode refuses; that is the point.
  • Q4 A (TIMESTAMP). Has not met the 2038 limit: show the lesson's 2040 error.
  • Q5 A (1364). Mixes the two NOT NULL errors: explicit NULL 1048, left out 1364.
  • Q9 C. Mixes Matched 0 with Changed 0. Write both lines on the board.
  • Q10 B. Thinks any WHERE satisfies safe-updates; it wants a key column.
  • Q11 A (REPLACE). The word sounds right. REPLACE is delete plus insert: a new id.
