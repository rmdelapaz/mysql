Session 9: Indexes and Views

How to teach indexes and views in one session: measure a slow query on 100,000 rows, add the index the plan points at and measure again, learn the habits that hide a column from its index, then save the best queries as views, make some of them safe to update, and use one as a security boundary. A clinic ties them together: a view is exactly as fast as its query.

Warm-up answers (W1 to W5)
  1. W1 What does this print? Answer: 1,3,5,7: the round that reads 7 fails n < 7 and stops.
  2. W2 Which price_level do The Catcher in the Rye and The Great Gatsby (both 8.99) get, and Animal Farm after them? Answer: Both 2, Animal Farm 3: DENSE_RANK ties without a gap (RANK would give Animal Farm 4).
  3. W3 Why can't WHERE filter on ROW_NUMBER(), and what do you write instead? Answer: Windows are computed after WHERE (3593): number the rows in a CTE, filter in the outer query.
  4. W4 In a recursive CTE over employees, which join walks UP the hierarchy? Answer: e.id = cte.manager_id ("who is this person's manager?"); e.manager_id = cte.id walks down.
  5. W5 AVG(salary) with GROUP BY department versus AVG(salary) OVER (PARTITION BY department): how many rows from the 10 employees? Answer: 4 versus 10: GROUP BY collapses, OVER keeps every row.

W1 and W2's real output is in the Answer Key. W3 misses mean the CTE-filter pattern did not stick: it comes back today as a view that filters a window (the 6.2 worked example).

6.1

Indexes & Query Optimization

60 min
Objectives (from the lesson page)
  • Explain what an index is, what it costs, and which indexes every bookstore table already has
  • Read a query plan from EXPLAIN and measure a query with EXPLAIN ANALYZE
  • Create single-column, composite and unique indexes, and choose the column order of a composite index
  • Spot and rewrite the patterns that stop an index from being used: functions on the column, leading wildcards, type mismatches
  • List, rename, hide and drop indexes, and fix the errors MySQL raises while you do it
Timing in the room

15mGuided lab: plan_reading_starter.sql

Mental model to say

Hold up any textbook: "To find 'foreign keys' you do not read the whole book. You look the term up in a sorted list at the back and jump to the pages. An index is that list: a sorted copy of one or more columns, each value with a pointer to its row. Without it, MySQL has one way to answer WHERE: read every row. That is a full table scan."

Point at the B-tree sketch: "Sorted pages in a shallow tree: three or four levels for a million values. The primary key is special: the rows themselves are stored in its order."

Then the price, ticked off on fingers: space, slower writes (every INSERT updates every index), more choices for the optimizer. "The goal is not 'index everything'. It is: measure the slow query, index what the plan points at, measure again."

Live demo (you type, they follow)

The lesson's own examples on a freshly loaded bookstore; learners generate the same sales_log and follow. EXPLAIN ANALYZE times are from the run that produced this guide.

  1. A table big enough to notice (3m). "Eleven books never make a query slow. This builds the lesson's 100,000-row sales log: a CTE and a cross join, every value computed from a running number, so everyone gets the same rows." Paste it from the lesson page; while it runs (about a second), explain ANALYZE TABLE: fresh statistics for the optimizer. 
    CREATE TABLE sales_log (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    receipt_no  CHAR(7)     NOT NULL,
    customer_id INT         NOT NULL,
    book_id     INT         NOT NULL,
    sold_on     DATE        NOT NULL,
    quantity    INT         NOT NULL,
    channel     VARCHAR(10) NOT NULL
);
INSERT INTO sales_log (receipt_no, customer_id, book_id, sold_on, quantity, channel)
WITH digits AS (
    SELECT 0 AS d UNION ALL SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3 UNION ALL SELECT 4
    UNION ALL SELECT 5 UNION ALL SELECT 6 UNION ALL SELECT 7 UNION ALL SELECT 8 UNION ALL SELECT 9
),
seq AS (
    SELECT 1 + a.d + 10 * b.d + 100 * c.d + 1000 * e.d + 10000 * f.d AS n
    FROM digits a
    CROSS JOIN digits b CROSS JOIN digits c CROSS JOIN digits e CROSS JOIN digits f
)
SELECT
    LPAD(n, 7, '0'),                               -- receipt 0000001, 0000002, ...
    1 + MOD(n * 7, 8),                             -- customers 1 to 8
    1 + MOD(n * 13, 11),                           -- books 1 to 11
    DATE '2020-01-01' + INTERVAL MOD(n * 37, 2400) DAY,
    1 + MOD(n, 3),                                 -- 1 to 3 copies
    ELT(1 + MOD(n, 4), 'web', 'store', 'phone', 'web')
FROM seq
ORDER BY n;

  4. Measure (3m). "EXPLAIN ANALYZE runs the query and times every step. Read from the most indented line up: a table scan of 100,000 rows feeds a filter that keeps 42." Write the total time on the board. 
    EXPLAIN ANALYZE SELECT * FROM sales_log WHERE sold_on = '2025-03-15'\G
    *************************** 1. row ***************************
EXPLAIN: -> Filter: (sales_log.sold_on = DATE'2025-03-15')  (cost=10078 rows=9990) (actual time=0.239..16.5 rows=42 loops=1)
    -> Table scan on sales_log  (cost=10078 rows=99900) (actual time=0.134..13.4 rows=100000 loops=1)
    On the run that produced this guide the total was 16.5 ms; yours will differ.
  5. Index, measure again (3m). "One line instead of two: an Index lookup straight to the 42 rows." Compare with the number on the board. 
    CREATE INDEX idx_sales_sold_on ON sales_log (sold_on);
EXPLAIN ANALYZE SELECT * FROM sales_log WHERE sold_on = '2025-03-15'\G
    *************************** 1. row ***************************
EXPLAIN: -> Index lookup on sales_log using idx_sales_sold_on (sold_on = DATE'2025-03-15')  (cost=14.7 rows=42) (actual time=0.075..0.0779 rows=42 loops=1)
    Here 0.0779 ms. A drop of a hundred times or more is typical; the estimate (rows=42) is now exact.
  6. A composite index (3m). "Sorted by customer, then by date within each customer, like a phone book. Customer 3 in March is one slice." Covering: COUNT(*) needs nothing but the indexed columns. 
    CREATE INDEX idx_sales_customer_date ON sales_log (customer_id, sold_on);
EXPLAIN SELECT COUNT(*) FROM sales_log
WHERE customer_id = 3
  AND sold_on BETWEEN '2025-03-01' AND '2025-03-31'\G
    *************************** 1. row ***************************
EXPLAIN: -> Aggregate: count(0)  (cost=73.1 rows=1)
    -> Filter: ((sales_log.customer_id = 3) and (sales_log.sold_on between '2025-03-01' and '2025-03-31'))  (cost=34.6 rows=167)
        -> Covering index range scan on sales_log using idx_sales_customer_date over (customer_id = 3 AND '2025-03-01' <= sold_on <= '2025-03-31')  (cost=34.6 rows=167)
  7. A unique index (2m). "An index plus a rule. A constant on a unique index is found while planning." Then the rule in action. 
    CREATE UNIQUE INDEX uq_sales_receipt ON sales_log (receipt_no);
EXPLAIN SELECT * FROM sales_log WHERE receipt_no = '0004242'\G
INSERT INTO sales_log (receipt_no, customer_id, book_id, sold_on, quantity, channel)
VALUES ('0004242', 1, 1, '2026-07-28', 1, 'web');

EXPLAIN: -> Rows fetched before execution  (cost=0..0 rows=1)
ERROR 1062 (23000): Duplicate entry '0004242' for key 'sales_log.uq_sales_receipt'
  8. Killer 1: a function around the column (3m). "The index is sorted by sold_on, not by YEAR(sold_on)." Same question as a range on the bare column. 
    EXPLAIN SELECT * FROM sales_log
WHERE YEAR(sold_on) = 2025 AND MONTH(sold_on) = 3\G
EXPLAIN SELECT * FROM sales_log
WHERE sold_on >= '2025-03-01' AND sold_on < '2025-04-01'\G
    *************************** 1. row ***************************
EXPLAIN: -> Filter: ((year(sales_log.sold_on) = 2025) and (month(sales_log.sold_on) = 3))  (cost=10078 rows=99900)
    -> Table scan on sales_log  (cost=10078 rows=99900)
*************************** 1. row ***************************
EXPLAIN: -> Index range scan on sales_log using idx_sales_sold_on over ('2025-03-01' <= sold_on < '2025-04-01'), with index condition: ((sales_log.sold_on >= DATE'2025-03-01') and (sales_log.sold_on < DATE'2025-04-01'))  (cost=581 rows=1291)
  9. Killer 2: a number for a text column (1m). "receipt_no is CHAR(7). 4242 is a number, so every row is converted." Fix: compare with '0004242'. 
    EXPLAIN SELECT * FROM sales_log WHERE receipt_no = 4242\G
    *************************** 1. row ***************************
EXPLAIN: -> Filter: (sales_log.receipt_no = 4242)  (cost=10078 rows=9990)
    -> Table scan on sales_log  (cost=10078 rows=99900)
  10. Test a drop safely (2m). "Before dropping an index on a busy table, hide it. The optimizer ignores it; writes still maintain it, so VISIBLE is instant." 
    ALTER TABLE sales_log ALTER INDEX idx_sales_sold_on INVISIBLE;
EXPLAIN SELECT * FROM sales_log WHERE sold_on = '2025-03-15'\G
ALTER TABLE sales_log ALTER INDEX idx_sales_sold_on VISIBLE;
    *************************** 1. row ***************************
EXPLAIN: -> Filter: (sales_log.sold_on = DATE'2025-03-15')  (cost=10078 rows=41.6)
    -> Table scan on sales_log  (cost=10078 rows=99900)
    Back to a table scan: this query does need the index.
  11. Silent: an index you did not need (1m). "No error, no warning, and pure overhead: the composite index already starts with customer_id." 
    CREATE INDEX idx_sales_customer ON sales_log (customer_id);
SHOW WARNINGS;
DROP INDEX idx_sales_customer ON sales_log;
    Empty set
    Then the one MySQL refuses: the foreign key's own index (next step).
  12. Refused: the foreign key's index (1m). 
    DROP INDEX fk_orders_customer ON orders;
    ERROR 1553 (HY000): Cannot drop index 'fk_orders_customer': needed in a foreign key constraint
Three mistakes to expect, and how to coach each
  • Reading the plan top down. Learners report "it filters first". Coach: "Which line is indented most? That one runs first and feeds the line above."
  • Composite index in the wrong order. (sold_on, customer_id) for "customer 3 in March". Coach: "Equality first, range last: which column do you compare with =?" (the lab's TODO 2).
  • Comparing numbers instead of shapes. "My cost is 10083, yours is 10078." Coach: "Same shape? Then same plan. Estimates come from sampled statistics."

Checks for understanding

Ask these out loud:

  • Why does nobody create an index on the primary key? Answer: the table is already stored in primary-key order (the clustered index).
  • What does Covering index mean? Answer: the index alone holds every column the query needs; the table is never read.
  • When is a table scan the right plan? Answer: small tables, or a condition that matches a big share of the rows.
  • Why INVISIBLE before DROP? Answer: hiding is instant to undo; rebuilding a dropped index on a big table can take a long time.

Mental model to say

Point at the window drawn on the board: "A view is a saved SELECT with a name. It holds no rows. Every time you read it, MySQL runs the saved query against the real tables and hands you the result, like a window that shows part of the room behind it. When the room changes, the view changes."

Then three jobs, one line each: reuse (a five-table join written once, read in one line), a safe slice to edit (updatable views with WITH CHECK OPTION), a security boundary (an account may read the view and not the table).

  4. A view with aggregates (2m). "LEFT JOIN, COUNT(DISTINCT), COALESCE: everything a report needs. Now a manager who never wrote a join asks one line." 
    CREATE VIEW v_customer_summary AS
SELECT
    c.id                                       AS customer_id,
    CONCAT(c.first_name, ' ', c.last_name)     AS customer,
    COUNT(DISTINCT o.id)                       AS orders,
    COALESCE(SUM(oi.quantity), 0)              AS items,
    COALESCE(SUM(oi.quantity * oi.price_at_time), 0) AS total_spent
FROM customers AS c
LEFT JOIN orders      AS o  ON o.customer_id = c.id
LEFT JOIN order_items AS oi ON oi.order_id = o.id
GROUP BY c.id, c.first_name, c.last_name;
SELECT customer, total_spent
FROM v_customer_summary
WHERE total_spent > 40
ORDER BY total_spent DESC;
    +---------------+-------------+
| customer      | total_spent |
+---------------+-------------+
| Alice Johnson |       58.95 |
| Dave Brown    |       45.96 |
| Frank Miller  |       41.96 |
+---------------+-------------+
  5. Updating through a view (2m). "Each row of this view is one customer row, so MySQL knows which row to change. The change lands in customers." Inside a transaction, rolled back. 
    START TRANSACTION;
UPDATE v_chicago_customers
SET email = 'grace.wilson@example.com'
WHERE id = 7;
SELECT id, first_name, email FROM customers WHERE id = 7;
ROLLBACK;
    +----+------------+--------------------------+
| id | first_name | email                    |
+----+------------+--------------------------+
|  7 | Grace      | grace.wilson@example.com |
+----+------------+--------------------------+
  6. MySQL's verdict (1m). "Grouping makes a view read-only; a five-table join is still updatable, one table per statement." 
    SELECT TABLE_NAME, IS_UPDATABLE, CHECK_OPTION
FROM information_schema.VIEWS
WHERE TABLE_SCHEMA = 'bookstore'
ORDER BY TABLE_NAME;

| TABLE_NAME          | IS_UPDATABLE | CHECK_OPTION |

| v_chicago_customers | YES          | NONE         |

+---------------------+--------------+--------------+
  7. WITH CHECK OPTION (3m). "Without it, an update could move Bob to Boston and he would vanish from the view that changed him. With it:" 
    CREATE OR REPLACE VIEW v_chicago_customers AS
SELECT id, first_name, last_name, email, city
FROM customers
WHERE city = 'Chicago'
WITH CHECK OPTION;
UPDATE v_chicago_customers SET city = 'Boston' WHERE id = 2;
    ERROR 1369 (HY000): CHECK OPTION failed 'bookstore.v_chicago_customers'
  8. A view as a security boundary (3m). "The support team needs a staff directory without salaries. The view hides columns and rows; the account gets SELECT on the view only." The account is dropped again right away; Lesson 7.4 teaches users properly. 
    CREATE VIEW v_staff_directory AS
SELECT first_name, last_name, email, department
FROM employees
WHERE is_active = TRUE;
CREATE USER 'support_demo'@'localhost' IDENTIFIED BY 'Replace-With-A-Strong-Passw0rd!';
GRANT SELECT ON bookstore.v_staff_directory TO 'support_demo'@'localhost';
SHOW GRANTS FOR 'support_demo'@'localhost';
DROP USER 'support_demo'@'localhost';
    +-------------------------------------------------------------------------------+
| Grants for support_demo@localhost                                             |
+-------------------------------------------------------------------------------+
| GRANT USAGE ON *.* TO `support_demo`@`localhost`                              |

+-------------------------------------------------------------------------------+

  9. Silent: SELECT * is frozen (2m). "The table gains in_stock; the view does not, because * was expanded when it was created." 
    CREATE TABLE demo_products (id INT PRIMARY KEY, name VARCHAR(50), cost DECIMAL(8, 2));
INSERT INTO demo_products VALUES (1, 'Bookmark', 1.50), (2, 'Tote bag', 12.00);
CREATE VIEW v_demo_all AS SELECT * FROM demo_products;
ALTER TABLE demo_products ADD COLUMN in_stock BOOLEAN DEFAULT TRUE;
SELECT * FROM v_demo_all ORDER BY id;
DROP VIEW v_demo_all;
DROP TABLE demo_products;
    +----+----------+-------+
| id | name     | cost  |
+----+----------+-------+
|  1 | Bookmark |  1.50 |
|  2 | Tote bag | 12.00 |
+----+----------+-------+
Three mistakes to expect, and how to coach each
  • Expecting a view to store data. "Do I need to refresh it?" Coach: "Insert an order, then read the view." (Predict P3 shows it.)
  • Updating an aggregate view (1288). Coach: "Which customer row would MySQL change to make orders = 5?" There is none.
  • CREATE VIEW in a script that runs twice (1050). Coach: "What should a rerunnable script say?" CREATE OR REPLACE VIEW.

Checks for understanding

Ask these out loud:

  • Does a view make a query faster? Answer: no; it runs its query. Indexes on the base tables make it fast.
  • Where does ORDER BY go? Answer: in the query that reads the view.
  • What does WITH CHECK OPTION protect against? Answer: writes through the view that would push a row out of it (1369).
  • What happens to your views when you reload bookstore.sql? Answer: they are dropped with the database; keep them in a script.

A view is as fast as its query

Run both on the projector (6.2 demo state). The first view is MERGED into the query: no trace of the view, and the base tables' indexes do the work (fk_items_order, PRIMARY). The second groups rows, so MySQL computes it into a temporary table first (Materialize) and filters after all the grouping. Say: "Views do not have indexes. On big tables, filter in the base query, or keep a summary table."

Closing

Exit ticket (3 questions, no notes, 4 minutes)
  1. A query filters WHERE customer_id = 5 AND book_id = 9 ORDER BY sold_on. Write the one index that serves the filter and the sort. Answer: CREATE INDEX idx_sales_customer_book_date ON sales_log (customer_id, book_id, sold_on); (equality columns first, the sort column last: the lesson project's Step 4).
  2. Name two habits that stop MySQL from using an index on a column. Answer: any two of: a function or arithmetic around the column; a leading % in LIKE; comparing a text column with a number; OR across different columns.
  3. Give one reason to create a view and one thing a view does NOT do for you. Answer: reasons: reuse a long query by name, give a safe updatable slice, hide columns and rows from an account. Does not: store rows, have indexes, make the query faster.
