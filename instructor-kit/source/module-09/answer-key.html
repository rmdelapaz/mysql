6.1 · Indexes & Query Optimization: self-check

Q1
Which index does every InnoDB table have, even though you never created one by name?
A) One index per column
B) The primary key: the rows themselves are stored in its order (the clustered index)
C) An index on every VARCHAR column
D) None: MySQL scans every table until you add indexes
Why: InnoDB stores the rows in a B-tree sorted by the primary key, so WHERE id = ... is always fast. UNIQUE constraints and foreign keys add more indexes automatically (email, fk_orders_customer ...).
A is wrong: Only the columns you (or a constraint) choose are indexed.
C is wrong: Types do not decide it; constraints and CREATE INDEX do.
D is wrong: The primary key is always there.
Q2
sales_log has an index on (customer_id, sold_on) and no other index. Which query can NOT seek with it?
A) WHERE customer_id = 3
B) WHERE customer_id = 3 AND sold_on >= '2025-03-01'
C) WHERE sold_on >= '2025-03-01' AND customer_id = 3
D) WHERE sold_on BETWEEN '2025-03-01' AND '2025-03-31'
Why: A composite index serves its leftmost prefix. The dates are sorted only within each customer, so a date range alone has no place to jump to (at best a skip scan). The order of the conditions in WHERE does not matter, which is why C works as well as B.
A is wrong: customer_id is the first column: a seek.
B is wrong: Both columns, in index order: the best case.
C is wrong: Same as B: MySQL does not care about the order of the AND.
Q3
sold_on has an index. Rewrite WHERE YEAR(sold_on) = 2024 so MySQL can use it.
WHERE sold_on >= '2024-01-01' AND sold_on < '2025-01-01'
Why: The index is sorted by the column, not by YEAR(column). A range on the bare column (up to, but not including, the next January 1) gives the same rows and stays correct if the column ever becomes DATETIME.
Q4
receipt_no is CHAR(7) with a unique index, yet WHERE receipt_no = 4242 shows Table scan. Why?
A) The text column is converted to a number on every row, so the index order no longer helps
B) Unique indexes cannot be used for equality
C) The table needs ANALYZE TABLE first
D) 4242 is too small: receipt numbers start at 1000000
Why: A string column compared with a number is converted row by row ('0004242' becomes 4242), and converted values are not in the index's sort order. WHERE receipt_no = '0004242' is a single-row lookup again. SHOW WARNINGS after the EXPLAIN even says so (warning 1739).
B is wrong: Equality on a unique index is the best case: Rows fetched before execution.
C is wrong: Fresh statistics do not change a type conversion.
D is wrong: The value matches a real row (the count is 1); only the plan is slow.
Q5
An index idx_sales_customer_date (customer_id, sold_on) exists. You run CREATE INDEX idx_sales_customer ON sales_log (customer_id);. What happens?
A) ERROR 1061: Duplicate key name
B) MySQL refuses: the column is already indexed
C) It succeeds without an error or a warning, and the new index is pure overhead
D) It replaces the composite index
Why: The composite index already serves customer_id alone (its leftmost prefix), so the new one only slows every write. MySQL warns only when the columns are exactly the same (1831). Check SHOW INDEX before adding one.
A is wrong: 1061 is about the NAME, and this name is new.
B is wrong: MySQL lets you index a column many times.
D is wrong: Indexes are never replaced silently; both now exist.
Q6
DROP INDEX fk_orders_customer ON orders; fails. Which error number, and why does MySQL refuse?
1553: the foreign key from orders to customers needs an index on customer_id, and this is the only one
Why: InnoDB created fk_orders_customer for the foreign key. To replace it, create another index that starts with customer_id first; InnoDB then drops its own.

6.2 · Views: self-check

Q7
What does MySQL store when you create a view?
A) Only the query: the rows are computed every time the view is read
B) A copy of the rows, refreshed every night
C) A copy of the rows, refreshed on every INSERT
D) An index on the base tables
Why: A view is a named, saved SELECT (with its definer and security settings). Querying it runs the query against the base tables, so it is always current and exactly as fast as that query.
B is wrong: That is a summary table you refresh yourself; MySQL has no materialized views.
C is wrong: Views hold no rows at all.
D is wrong: Views have no indexes; the base tables' indexes do the work.
Q8
What happens when the second statement runs?
CREATE VIEW v_ny AS
SELECT id, first_name, city
FROM customers
WHERE city = 'New York'
WITH CHECK OPTION;
UPDATE v_ny SET city = 'Boston' WHERE id = 1;
ERROR 1369 (HY000): CHECK OPTION failed 'bookstore.v_ny'
Why: Alice would leave the view she was changed through. WITH CHECK OPTION rejects any write through the view that produces a row the view itself would not show; nothing is changed.
Q9
Which of these views accepts an UPDATE that passes through to its base table?
A) SELECT author_id, COUNT(*) AS books FROM books GROUP BY author_id
B) SELECT DISTINCT city FROM customers
C) SELECT id, title, price FROM books WHERE price < 10
D) SELECT title FROM books UNION SELECT name FROM authors
Why: Each row of C is exactly one row of books, so MySQL knows which row to change. Grouping, DISTINCT and UNION make one view row stand for several base rows (error 1288).
A is wrong: A count has no single base row behind it.
B is wrong: DISTINCT merges rows: not updatable (IS_UPDATABLE says NO).
D is wrong: UNION combines two tables' rows.
Q10
v_all was created as SELECT * FROM products. Then a column color is added to products. What does SELECT * FROM v_all return?
A) ERROR 1356
B) All columns, including color
C) An empty result until the view is refreshed
D) The old columns only, without color
Why: The * was expanded into a fixed column list when the view was created, and that list is what MySQL saved. List columns explicitly and replace the view when the table gains one it should show.
A is wrong: 1356 is for a renamed or dropped column the view still names.
B is wrong: The column list is frozen at creation.
C is wrong: Views are never "refreshed"; the rows are current, only the column list is fixed.
Q11
Why does the course put ORDER BY in the query that reads a view, and not inside the view?
MySQL ignores a view's ORDER BY when the outer query has its own, and the SQL standard promises no order from a view: sort where you read
Why: The lesson's "Performance and Limitations" section. The project's checklist says it too: no view contains an ORDER BY; every query that reads one does.
Q12
An account has SELECT on v_staff_directory only. The view uses the default SQL SECURITY DEFINER. What can the account do?
A) Read every column of employees, salaries included
B) Read the directory through the view, but not the employees table itself
C) Nothing: it has no privilege on employees
D) Update salaries through the view
Why: The view reads employees with its definer's rights, so it works for the account; SELECT on employees directly fails with 1142. The view is the security boundary: never select more columns than the audience should see.
A is wrong: Only the view's columns (no salary) are visible.
C is wrong: DEFINER security is exactly what makes the view work for it.
D is wrong: The grant is SELECT only, and the view has no salary column.

6.2 · Views: predict, then run

P3
Predict the output, then run it.
CREATE VIEW v_pricey AS SELECT title FROM books WHERE price > 12;
START TRANSACTION;
UPDATE books SET price = 9.00 WHERE id = 1;
SELECT title FROM v_pricey ORDER BY title;
ROLLBACK;
DROP VIEW v_pricey;
+-------------------+
| title             |
+-------------------+
| Lord of the Rings |
+-------------------+
Why: Only Lord of the Rings: Dune's price dropped to 9.00 inside the transaction, and the view runs its query against the current rows. After ROLLBACK the view shows Dune again; nothing needs refreshing.
P4
Predict the output, then run it.
CREATE VIEW v_cities AS SELECT DISTINCT city FROM customers;
SELECT TABLE_NAME, IS_UPDATABLE
FROM information_schema.VIEWS
WHERE TABLE_SCHEMA = 'bookstore' AND TABLE_NAME = 'v_cities';
DROP VIEW v_cities;
+------------+--------------+
| TABLE_NAME | IS_UPDATABLE |
+------------+--------------+
| v_cities   | NO           |
+------------+--------------+
Why: NO: DISTINCT merges rows, so one view row can stand for several customers and MySQL cannot know which one to change.

The Lesson Pages' Own Quick Quizzes

Lesson 6.1 · Indexes & Query Optimization
  1. B It returns the right rows after reading the whole table: Without an index MySQL reads every row and tests each one: a full table scan. The result is correct, it just takes longer as the table grows.
  2. A WHERE customer_id = 7 AND sold_on >= '2026-01-01': customer_id is the leftmost column, so MySQL can jump to customer 7, and inside it the dates are sorted, so the date range is a tight slice.
  3. C Every row is read and then filtered: no index is used: Table scan means every row is read and the Filter keeps the matches. On a big table that is the step to fix, with an index or a rewritten condition.
  4. C The index is sorted by the column, not by the function's result: The index is sorted by sold_on, not by YEAR(sold_on), so MySQL must compute the function for every row. A range on the bare column (from 2026-01-01 up to 2027-01-01) can use the index.
  5. A Make it INVISIBLE and watch the slow queries: An invisible index is ignored by the optimizer but still maintained, so you can watch for slow queries and make it VISIBLE again instantly if something needed it.
Lesson 6.2 · Views
  1. C The new numbers, including the new order: A view stores only its query. Every SELECT runs that query against the current base tables, so the new order is counted immediately.
  2. B A GROUP BY with COUNT(*): With GROUP BY, one view row stands for many base rows, so MySQL cannot tell which row an update should change. Such views report IS_UPDATABLE = NO and fail with error 1288.
  3. A Rejects writes through the view that would create rows the view cannot show: It rejects inserts and updates through the view that would produce a row the view's WHERE clause excludes, with error 1369.
  4. B The old columns only, without color: The star was expanded into a fixed column list when the view was created, so the new column is silently missing until the view is replaced.
  5. C Read the directory through the view, but not the table itself: The view reads employees with its definer's privileges, so the account sees exactly the view's columns and rows, and nothing else of the table.

Exit Ticket

  1. Index: (customer_id, book_id, sold_on): both equality columns first (either order), the sort column last. (customer_id, sold_on) alone still has to check the book on every row; (sold_on, ...) first cannot seek.
  2. Index killers: a function or arithmetic around the column (YEAR(sold_on), price * 1.1); a leading %; a text column compared with a number; OR across columns. Accept "a condition that matches most of the table" as a reason the optimizer ignores an index.
  3. Views: reasons: reuse a long query, a safe updatable slice (with a check option), a security boundary. Not: stored rows, indexes, speed. Accept "refresh itself" only if they explain it is always current because it stores no rows.

Common Wrong Answers and What They Reveal

  • Q2 C. Believes the order of the conditions in WHERE matters. It does not; the order of the columns in the index does.
  • Q4 B or C. Has not met type conversion. Run the lesson's step with SHOW WARNINGS: 1739 says it in words.
  • Q5 A. Mixes up an index's name with its columns.
  • Q7 B. Expects a cache. MySQL has no materialized views; P3 shows the view is always current.
  • Q9 A or B. Thinks "simple-looking" means updatable. The test: one view row = one base row.
  • Q10 B. The most common view surprise; the lesson's Common Mistake 5.
  • Exit ticket 1 with (sold_on, customer_id, book_id). The sort column first: worth two minutes of the Session 10 warm-up.
