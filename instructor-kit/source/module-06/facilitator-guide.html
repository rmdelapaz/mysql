Session 6: Relationships and Foreign Keys

How to teach the sixth session of MySQL Foundations: from one flat table to a relational database. Learners watch an update anomaly happen, migrate the books' author text into an authors table with a checked, reversible sequence, build a junction table, then put the foreign keys to the test: 1452 and 1451, CASCADE, SET NULL and RESTRICT inside transactions, and keys added to data that already holds an orphan.

2 lessons 3 hrs session Lessons 4.1–4.2 Session 6 of 14 · Part 1

How to Use This Guide

  • Same rhythm for both lessons: frame (one mental model) → live demo → guided lab (new practice, never the lesson project) → start the lesson's own project. Exercises, quiz and journal are homework.
  • Type the short statements; paste the long INSERTs (the 25 links, the authors). Every SQL block below was run on MySQL 9.7.2: Lesson 4.1's demo from the flat bookstore, in one session, through the migration; Lesson 4.2's demo from a fresh bookstore.sql.
  • This session changes the database. Lesson 4.1 turns the flat bookstore into the relational one, and from Lesson 4.2 on every lesson starts by loading bookstore.sql (8 tables: authors 10, books 11, categories 5, links 25, customers 8, orders 12, order items 18, employees 10). After the 4.1 project start, every machine loads it; nobody needs to finish the migration by hand to follow 4.2.
  • The lessons are the reference: keep lesson_11.html (the ER diagrams) and lesson_12.html (the rules diagram) open. Labs live in labs/module-06/.
  • Part 1 (Sessions 1 to 7) can run on its own; Session 7 is the Part 1 assessment. Tell the room today: next session ends with it, and today's tables are in it.
The #1 risk of Session 6: half the room in the flat database, half in the relational one

4.1 migrates live data. Learners who mistype a step (a missing comma in the ALTER, the UPDATE run twice, a DROP COLUMN before the check) end up between the two shapes, and from then on nothing on the projector matches their screen. Prevent it: in the 4.1 demo, ready learners type along in their flat bookstore, but say clearly that the outcome does not matter: at 1:05 EVERYONE loads bookstore.sql (SOURCE bookstore.sql from the course folder, or labs/_states/bookstore.sql), and the counts query proves it (10, 11, 5, 25, 8, 12, 18, 10). Recover: anyone confused before then reloads the flat state (SOURCE labs/_states/flat.sql) and watches. The 4.1 lab works on two practice tables of its own, so it cannot damage either shape.

  • ☐ Board, before learners arrive: "Can one A have many Bs? Can one B have many As?" with the three answers (1:M key on the many side · 1:1 key + UNIQUE · M:M junction table); and the rules diagram: "Can the child exist without its parent? no → CASCADE · yes → must it keep naming the parent? yes → RESTRICT, no → SET NULL".

Retrieval questions and answers

Questions on the slide; learners answer in the workbook's Warm-up box, then you run the SQL ones in the flat bookstore (still loaded from Session 5).

  1. Three numbers: predict them. (Customers 1 to 5 signed up before 25 January; Eve has no city.)
    SELECT COUNT(*), COUNT(city), COUNT(DISTINCT city)
FROM customers
WHERE created_at < '2026-01-25';
    +----------+-------------+----------------------+
| COUNT(*) | COUNT(city) | COUNT(DISTINCT city) |
+----------+-------------+----------------------+
|        5 |           4 |                    4 |
+----------+-------------+----------------------+
    Answer: 5, 4, 4. COUNT(*) counts rows; COUNT(city) skips Eve's NULL; the four filled-in cities are all different.
  2. price > 10 and COUNT(*) > 1: which goes in WHERE and which in HAVING? Answer: price > 10 in WHERE (one row's column), COUNT(*) > 1 in HAVING (a group's aggregate).
  3. Which book is it?
    SELECT title
FROM books
WHERE pages = (SELECT MAX(pages) FROM books);
    +-------------------+
| title             |
+-------------------+
| Lord of the Rings |
+-------------------+
    Answer: Lord of the Rings: the row behind MAX(pages). If two books tied, both would come back.
  4. How many customers? (Customer 7 is Grace in Chicago, 8 is Hank with no city.)
    SELECT COUNT(*)
FROM customers
WHERE city NOT IN (SELECT city FROM customers WHERE id > 6);
    +----------+
| COUNT(*) |
+----------+
|        0 |
+----------+
    Answer: 0. The list is ('Chicago', NULL), and one NULL empties a NOT IN. Fix: AND city IS NOT NULL inside, or NOT EXISTS.
  5. What is wrong, and what is the error number?
    SELECT author, title, MAX(price)
FROM books
GROUP BY author;
    ERROR 1055 (42000): Expression #2 of SELECT list is not in GROUP BY clause and contains nonaggregated column 'bookstore.books.title' which is not functionally dependent on columns in GROUP BY clause; this is incompatible with sql_mode=only_full_group_by
    Answer: 1055: title is neither grouped nor aggregated (Tolkien's pile has two titles). Fix: drop title, or MIN(title).
How to read the warm-up
  • Q4 wrong for more than a third of the room: the NOT IN trap comes back today (the lesson's orphan query uses NOT IN (SELECT id FROM parent), safe only because a primary key is never NULL). Say so when you reach it.
  • Q1 or Q5 wrong: pair these learners with someone confident for the 4.1 lab; the migration's IS NULL check leans on COUNT.
  • Projects not running end to end: a 2-minute fix at the break, not now. Both scripts are good revision for the Part 1 assessment next session.

Lesson Plans

4.1

Table Relationships

65 min
Objectives (from the lesson page)
  • Explain the update, insert and delete problems of a flat table, using the bookstore's own data
  • Tell one-to-many, one-to-one and many-to-many relationships apart, and say where the foreign key goes in each
  • Move a repeated text column into its own table with CREATE TABLE, ALTER TABLE and UPDATE ... JOIN
  • Build a junction table with a composite primary key, with and without extra columns
  • Read a crow's foot ER diagram of the finished bookstore database
Timing in the room
10mFrame: one big sales table and its four anomalies; primary and foreign keys; where the key goes
30mLive demo: the update anomaly, then the migration (parent, column, UPDATE ... JOIN, NULL check, lock-in), one-to-one, a junction table
15mGuided lab: publisher_split_starter.sql in pairs
10mStart the lesson project: load bookstore.sql, read the design of orders, order_items and employees
Mental model to say

Draw the one-big-table sales sheet from the lesson (Alice's name and email on every row she bought) and name the four anomalies as you point: "duplication; change her email and miss a row (update); delete Bob's only sale and Bob is gone (delete); a new customer who bought nothing has nowhere to go (insert)."

Then the relational idea: "Store each fact once, in the table it describes, and let other tables point at it by its id. The table with the id is the parent; the table holding the pointer is the child."

Then the one question that places every foreign key, written on the board: "Can one A have many Bs? Can one B have many As?" One yes: the key goes on the many side. Two yeses: a junction table. One-to-one is a one-to-many whose key is UNIQUE.

Live demo (you type, they follow)

The lesson's own migration, in the flat bookstore, in one session. Ready learners type along; the outcome on their machines does not matter, because everyone loads bookstore.sql at 1:05.

  1. The repeated text (2m). "Lesson 3.3's report counted books per author. Look how the author is stored." 
    SELECT id, title, author
FROM books
WHERE author = 'J.R.R. Tolkien';
    +----+-------------------+----------------+
| id | title             | author         |
+----+-------------------+----------------+
|  6 | The Hobbit        | J.R.R. Tolkien |
|  9 | Lord of the Rings | J.R.R. Tolkien |
+----+-------------------+----------------+
    The same 14 characters typed twice.
  2. The update anomaly, on purpose (3m). "A staff member adds spaces to the initials on one row. No rule stops them." Ask: how many Tolkiens does the database believe in now? 
    UPDATE books SET author = 'J. R. R. Tolkien' WHERE id = 9;
SELECT author, COUNT(*) AS books
FROM books
WHERE author LIKE '%Tolkien%'
GROUP BY author
ORDER BY author;
    +------------------+-------+
| author           | books |
+------------------+-------+
| J. R. R. Tolkien |     1 |
| J.R.R. Tolkien   |     1 |
+------------------+-------+
    No error, and every report that groups by author is quietly wrong.
  3. Put it back (1m). 
    -- @status
UPDATE books SET author = 'J.R.R. Tolkien' WHERE id = 9;
    Query OK, 1 row affected
Rows matched: 1  Changed: 1  Warnings: 0
    Then the relational idea on the board: store each fact once, in the table it describes; point at it by id.
  4. Step 1: the parent table (3m). "Each author once, with an id. Asimov has no books yet: allowed on the 'one' side." Paste the INSERT (the point is the structure, not the typing). 
    CREATE TABLE authors (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    name        VARCHAR(100) NOT NULL,
    birth_year  INT
);
INSERT INTO authors (id, name, birth_year) VALUES
    (1, 'Frank Herbert', 1920), (2, 'George Orwell', 1903),
    (3, 'Harper Lee', 1926), (4, 'F. Scott Fitzgerald', 1896),
    (5, 'Jane Austen', 1775), (6, 'J.R.R. Tolkien', 1892),
    (7, 'Aldous Huxley', 1894), (8, 'J.D. Salinger', 1919),
    (9, 'Ray Bradbury', 1920), (10, 'Isaac Asimov', 1920);
SELECT COUNT(*) AS authors FROM authors;
    +---------+
| authors |
+---------+
|      10 |
+---------+
  5. Step 2: the foreign key column (2m). "Can one author have many books? Yes, so the key goes in books." 
    ALTER TABLE books ADD COLUMN author_id INT AFTER title;
SELECT id, title, author, author_id
FROM books
WHERE id <= 3;
    +----+-----------------------+---------------+-----------+
| id | title                 | author        | author_id |
+----+-----------------------+---------------+-----------+
|  1 | Dune                  | Frank Herbert |      NULL |
|  2 | 1984                  | George Orwell |      NULL |
|  3 | To Kill a Mockingbird | Harper Lee    |      NULL |
+----+-----------------------+---------------+-----------+
    Empty (NULL) on every row: nothing is filled in yet.
  6. Step 3: fill it by matching names (4m). "For every pair of a book and an author whose name equals the book's author text, copy the id." JOIN ... ON pairs rows of two tables; Lesson 4.3 is all about it, today only this one pattern. 
    UPDATE books
JOIN authors ON authors.name = books.author
SET books.author_id = authors.id;
SELECT id, title, author, author_id
FROM books
WHERE id IN (6, 9, 10)
ORDER BY id;
    +----+-------------------+----------------+-----------+
| id | title             | author         | author_id |
+----+-------------------+----------------+-----------+
|  6 | The Hobbit        | J.R.R. Tolkien |         6 |
|  9 | Lord of the Rings | J.R.R. Tolkien |         6 |
| 10 | Fahrenheit 451    | Ray Bradbury   |         9 |
+----+-------------------+----------------+-----------+
    Both Tolkien books carry 6. (The lesson shows all ten rows; three are enough on the projector.)
  7. The check before anything is dropped (2m). "A misspelled name would have matched nothing and left a NULL. Count them BEFORE you drop the text column: DROP COLUMN has no undo." 
    SELECT COUNT(*) AS books_without_author_id
FROM books
WHERE author_id IS NULL;
    +-------------------------+
| books_without_author_id |
+-------------------------+
|                       0 |
+-------------------------+
  8. Step 4: lock it in (4m). "Three changes in one ALTER: required, the old column gone, the key declared and named." Point at MUL in the Key column: MySQL indexed the foreign key. 
    ALTER TABLE books
    MODIFY COLUMN author_id INT NOT NULL,
    DROP COLUMN author,
    ADD CONSTRAINT fk_books_author
        FOREIGN KEY (author_id) REFERENCES authors(id)
        ON DELETE RESTRICT
        ON UPDATE CASCADE;
DESCRIBE books;
    +-----------+--------------+------+-----+---------+----------------+
| Field     | Type         | Null | Key | Default | Extra          |
+-----------+--------------+------+-----+---------+----------------+
| id        | int          | NO   | PRI | NULL    | auto_increment |
| title     | varchar(200) | NO   |     | NULL    |                |
| author_id | int          | NO   | MUL | NULL    |                |
| price     | decimal(8,2) | NO   |     | NULL    |                |
| pages     | int          | YES  |     | NULL    |                |
| published | date         | YES  |     | NULL    |                |

    SELECT
    title,
    (SELECT name FROM authors WHERE authors.id = books.author_id) AS author
FROM books
WHERE author_id IN (2, 6)
ORDER BY title;

| title             | author         |
+-------------------+----------------+
| 1984              | George Orwell  |
| Lord of the Rings | J.R.R. Tolkien |
| The Hobbit        | J.R.R. Tolkien |
+-------------------+----------------+
  10. Add a book the relational way (2m). "Animal Farm: Orwell's second book, by id. His name can never be split again." 
    INSERT INTO books (id, title, author_id, price, pages, published, in_stock) VALUES

| author_id | books |

    CREATE TABLE customer_profiles (
    id             INT AUTO_INCREMENT PRIMARY KEY,
    customer_id    INT NOT NULL UNIQUE,
    favorite_genre VARCHAR(50),

  12. Clean up the profile table.

Three mistakes to expect, and how to coach each
  • The key on the wrong side. customers.order_id "so each customer points at their order". Coach with the question: "Can one customer have many orders? Then where can all those pointers live?"
  • Dropping before checking. DROP COLUMN, then discovering a NULL author_id (and the 1138 at NOT NULL). Coach the order: add, fill, COUNT the NULLs, then lock in. The lab has a typo planted to make the check matter.
  • A list in one column. categories = 'Fiction,Fantasy'. Coach with the lesson's Mistake 4: "= 'Fiction' finds nothing; LIKE '%Fiction%' finds Science Fiction too." Many values = many rows in a junction table.

Checks for understanding

Ask these out loud during the demo and the lab:

  • Where does the key go for authors and books, and why? Answer: books.author_id: one author, many books.
  • Why count the NULL author_ids before DROP COLUMN? Answer: a NULL means a name did not match; dropping the text would lose that book's author for good.
  • What turns a one-to-many into a one-to-one? Answer: UNIQUE on the foreign key column.
  • Why does order_items store price_at_time when books has a price? Answer: it records what the customer paid then; the book's price may change later.

4.2

Foreign Keys & Referential Integrity

75 min
Objectives (from the lesson page)
  • Explain referential integrity and predict when MySQL raises errors 1452 and 1451
  • Choose RESTRICT, CASCADE or SET NULL for ON DELETE and ON UPDATE, and justify the choice
  • Add, drop and change a named foreign key on an existing table, cleaning up orphan rows first
  • List a database's foreign keys and their rules from information_schema
  • Diagnose the errors raised by a badly formed key (3780, 6125, 1830)
Timing in the room
10mFrame: referential integrity; four moments MySQL checks; three rules and the two questions

Mental model to say

"Referential integrity means every foreign key value points at a row that really exists. A child without its parent is an orphan, and a declared key makes orphans impossible." Then the four moments, as a two-by-two on the board: child INSERT or UPDATE of the key → does the parent exist? (1452) · parent DELETE or key UPDATE → do children point at it? then apply the rule (1451 under RESTRICT).

Then the rules, with the two questions: "Can the child exist without its parent? No: CASCADE (an order line without its order). Yes, and it must keep naming the parent: RESTRICT (an order must keep its customer: deactivate the customer instead). Yes, and the link is optional: SET NULL (staff stay when a manager leaves)." And the safety net: when in doubt, RESTRICT: a refused delete costs one step, a wrong cascade costs data.

Live demo (you type, they follow)

From a freshly loaded bookstore.sql. Every destructive test runs inside START TRANSACTION ... ROLLBACK; say so every time, and end every block with ROLLBACK before anything else.

  1. An order for nobody (2m). "Customer 999 does not exist." Read the message from the END: the constraint, the table, the column, the parent. 
    INSERT INTO orders (customer_id, order_date) VALUES (999, '2026-06-15');
    ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`bookstore`.`orders`, CONSTRAINT `fk_orders_customer` FOREIGN KEY (`customer_id`) REFERENCES `customers` (`id`) ON DELETE RESTRICT ON UPDATE CASCADE)
    "add or update a CHILD row": 1452 is always about the child.
  2. Delete a customer with orders (2m). "Alice has three orders, and fk_orders_customer says RESTRICT." 
    DELETE FROM customers WHERE id = 1;
    ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (`bookstore`.`orders`, CONSTRAINT `fk_orders_customer` FOREIGN KEY (`customer_id`) REFERENCES `customers` (`id`) ON DELETE RESTRICT ON UPDATE CASCADE)
    "delete or update a PARENT row": 1451. Alice and her history stay; RESTRICT makes you decide.
  3. CASCADE, safely (4m). "Order lines mean nothing without their order. I wrap the test in a transaction: START TRANSACTION begins, ROLLBACK undoes everything (Lesson 7.2)." 
    START TRANSACTION;
SELECT id, order_id, book_id FROM order_items WHERE order_id = 1;
DELETE FROM orders WHERE id = 1;
SELECT id, order_id, book_id FROM order_items WHERE order_id = 1;
ROLLBACK;
    +----+----------+---------+
| id | order_id | book_id |
+----+----------+---------+
|  1 |        1 |       1 |
|  2 |        1 |       2 |
+----+----------+---------+
Empty set
    One DELETE on orders removed two rows of order_items. After ROLLBACK they are back.
  4. SET NULL (3m). "Priya manages Tom, Lena and Ben. Priya leaves." 
    START TRANSACTION;
DELETE FROM employees WHERE id = 3;
SELECT id, first_name, manager_id
FROM employees
WHERE id IN (4, 5, 10)
ORDER BY id;
ROLLBACK;
    +----+------------+------------+
| id | first_name | manager_id |
+----+------------+------------+
|  4 | Tom        |       NULL |
|  5 | Lena       |       NULL |
| 10 | Ben        |       NULL |
+----+------------+------------+
    The reports stay, with no manager. The column must allow NULL (error 1830 otherwise; Step 11).
  5. ON UPDATE CASCADE (2m). "Renumber Orwell from 2 to 20: his books follow." 
    START TRANSACTION;
UPDATE authors SET id = 20 WHERE id = 2;
SELECT id, title, author_id
FROM books
WHERE author_id = 20
ORDER BY id;
ROLLBACK;
    +----+-------------+-----------+
| id | title       | author_id |
+----+-------------+-----------+
|  2 | 1984        |        20 |
| 11 | Animal Farm |        20 |
+----+-------------+-----------+
  6. No ON UPDATE rule = NO ACTION (1m). "The employees self-reference has no ON UPDATE." 
    UPDATE employees SET id = 100 WHERE id = 1;
    ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (`bookstore`.`employees`, CONSTRAINT `fk_employees_manager` FOREIGN KEY (`manager_id`) REFERENCES `employees` (`id`) ON DELETE SET NULL)
    NO ACTION behaves exactly like RESTRICT in MySQL.
  7. Every rule in the bookstore (3m). "information_schema describes all the other databases. Read each row as a decision." Walk the two-question diagram: can the child exist without its parent? Must it keep naming it? 
    SELECT TABLE_NAME, CONSTRAINT_NAME, REFERENCED_TABLE_NAME,
       DELETE_RULE, UPDATE_RULE
FROM information_schema.REFERENTIAL_CONSTRAINTS
WHERE CONSTRAINT_SCHEMA = 'bookstore'
ORDER BY TABLE_NAME, CONSTRAINT_NAME;
    +-----------------+----------------------+-----------------------+-------------+-------------+
| TABLE_NAME      | CONSTRAINT_NAME      | REFERENCED_TABLE_NAME | DELETE_RULE | UPDATE_RULE |
+-----------------+----------------------+-----------------------+-------------+-------------+
| book_categories | fk_bc_book           | books                 | CASCADE     | NO ACTION   |
| book_categories | fk_bc_category       | categories            | CASCADE     | NO ACTION   |
| books           | fk_books_author      | authors               | RESTRICT    | CASCADE     |
| employees       | fk_employees_manager | employees             | SET NULL    | NO ACTION   |
| order_items     | fk_items_book        | books                 | RESTRICT    | CASCADE     |
| order_items     | fk_items_order       | orders                | CASCADE     | CASCADE     |
| orders          | fk_orders_customer   | customers             | RESTRICT    | CASCADE     |
+-----------------+----------------------+-----------------------+-------------+-------------+
  8. A table that started without a key (2m). "Most real tables get their keys late. Kim's department 7 does not exist." 
    CREATE TABLE demo_departments (
    id   INT PRIMARY KEY,
    name VARCHAR(50) NOT NULL
);
CREATE TABLE demo_staff (
    id            INT PRIMARY KEY,
    name          VARCHAR(50) NOT NULL,
    department_id INT
);
INSERT INTO demo_departments (id, name) VALUES (1, 'Front desk'), (2, 'Warehouse');
INSERT INTO demo_staff (id, name, department_id) VALUES
    (1, 'Ana', 1), (2, 'Raj', 2), (3, 'Kim', 7);
  9. Adding the key fails (2m). "MySQL copies the table to add the key and finds the orphan." The #sql name differs on every server. 
    ALTER TABLE demo_staff
    ADD CONSTRAINT fk_staff_department
        FOREIGN KEY (department_id) REFERENCES demo_departments(id)
        ON DELETE SET NULL;
    ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`bookstore`.`#sql-80218_2020`, CONSTRAINT `fk_staff_department` FOREIGN KEY (`department_id`) REFERENCES `demo_departments` (`id`) ON DELETE SET NULL)
  10. Find the orphan, fix it, add the key (3m). "Find with a subquery, fix with the truth (Kim is not assigned yet: NULL), then the key goes on." 
    SELECT id, name, department_id
FROM demo_staff
WHERE department_id NOT IN (SELECT id FROM demo_departments);
UPDATE demo_staff SET department_id = NULL WHERE id = 3;
ALTER TABLE demo_staff
    ADD CONSTRAINT fk_staff_department
        FOREIGN KEY (department_id) REFERENCES demo_departments(id)
        ON DELETE SET NULL;
    +----+------+---------------+
| id | name | department_id |
+----+------+---------------+
|  3 | Kim  |             7 |
+----+------+---------------+
    Choose the fix that tells the truth about the data; deleting Kim would be the most drastic.
  11. A badly formed key: 1830 (1m). "SET NULL on a column that forbids NULL." 
    CREATE TABLE demo_notes (
    id          INT PRIMARY KEY,
    customer_id INT NOT NULL,
    CONSTRAINT fk_notes_customer FOREIGN KEY (customer_id)
        REFERENCES customers(id) ON DELETE SET NULL
);
    ERROR 1830 (HY000): Column 'customer_id' cannot be NOT NULL: needed in a foreign key constraint 'fk_notes_customer' SET NULL
  12. Clean up. Children first. 
    DROP TABLE demo_staff;
DROP TABLE demo_departments;
Three mistakes to expect, and how to coach each
  • Reading 1451 and 1452 the wrong way round. Coach: "Read the first words: 'add or update a CHILD row' (1452: the parent is missing) or 'delete or update a PARENT row' (1451: children still point at it)."
  • Cascading everything. "CASCADE makes the error go away." Coach with the lesson's warning: if orders cascaded from customers, one DELETE would erase years of sales without a warning. Ask the two questions out loud for that key.
  • Switching the checks off. SET FOREIGN_KEY_CHECKS = 0 to get past an error. Coach: "Turning it back on does not re-check. The error was telling you about bad data." Never in class; the lesson's Mistake 5 shows the orphan that slips in.

Checks for understanding

Ask these out loud during the demo and the lab:

  • 1452 or 1451: which one is about a missing parent? Answer: 1452 ("add or update a child row").
  • Which rule does order_items → orders use, and why? Answer: CASCADE: a line has no meaning without its order.
  • What happens when you leave ON DELETE out? Answer: NO ACTION, which MySQL enforces exactly like RESTRICT.
  • Why must a SET NULL column allow NULL? Answer: the rule writes NULL into it; NOT NULL makes the key impossible (1830).

Closing

Exit ticket (3 questions, no notes, 4 minutes)

Learners answer in the workbook's Exit Ticket box or on a sticky note. Sort before Session 7: question 1's misses predict trouble with the assessment's table-design task; question 2's with reading its error messages.

  1. For one-to-many, one-to-one and many-to-many: where does the foreign key go? Answer: on the many side; on either side with UNIQUE (usually the optional table); in a junction table with two foreign keys and a composite primary key.
  2. You get ERROR 1452. Which table were you changing (parent or child), and what is missing? And ERROR 1451? Answer: 1452: inserting or updating a CHILD whose parent does not exist. 1451: deleting or changing a PARENT that children still point at (under RESTRICT or NO ACTION).
  3. Choose an ON DELETE rule for order_items.book_id → books and justify it. Answer: RESTRICT: a book that was sold must stay on file for the sales history (mark it out of stock instead). CASCADE would delete sales lines; SET NULL would forget what was sold.
