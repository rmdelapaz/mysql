Lessons

4.1

Table Relationships

By the end you can
  • Explain the update, insert and delete problems of a flat table, using the bookstore's own data
  • Tell one-to-many, one-to-one and many-to-many relationships apart, and say where the foreign key goes in each
  • Move a repeated text column into its own table with CREATE TABLE, ALTER TABLE and UPDATE ... JOIN
  • Build a junction table with a composite primary key, with and without extra columns
  • Read a crow's foot ER diagram of the finished bookstore database
Key ideas
  • Store each fact once, in the table it describes; other tables point at it by id. Repeated text causes update, insert and delete anomalies.
  • Primary key identifies a row; foreign key holds another table's primary key. The table with the id is the parent, the one with the pointer the child.
  • Can one A have many Bs? Yes: the foreign key goes in B (the many side). Two yeses: a junction table.
  • One-to-one = a foreign key that is also UNIQUE (or is the primary key).
  • Many-to-many = a junction table: two foreign keys and a composite primary key; it may hold facts about the link (quantity, price_at_time, joined_on).
  • Migrate safely: add the column, fill it (UPDATE ... JOIN), COUNT the NULLs, then NOT NULL, drop the old column, declare the key.
  • Create parents first, children second; drop in the opposite order (1824 for a missing parent table).
Worked example: a many-to-many from scratch

A small many-to-many from scratch, in a practice database of its own: members, clubs, and the memberships that link them (with one fact about each link, the date joined).

DROP DATABASE IF EXISTS kit_clubs;
CREATE DATABASE kit_clubs;
USE kit_clubs;
CREATE TABLE members (
    id   INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(50) NOT NULL
);
CREATE TABLE clubs (
    id   INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(50) NOT NULL UNIQUE
);
CREATE TABLE memberships (
    member_id INT NOT NULL,
    club_id   INT NOT NULL,
    joined_on DATE NOT NULL,
    PRIMARY KEY (member_id, club_id),
    CONSTRAINT fk_ms_member FOREIGN KEY (member_id) REFERENCES members(id) ON DELETE CASCADE,
    CONSTRAINT fk_ms_club   FOREIGN KEY (club_id)   REFERENCES clubs(id)   ON DELETE CASCADE
);
INSERT INTO members (name) VALUES ('Ana'), ('Ben'), ('Cleo');
INSERT INTO clubs (name) VALUES ('Chess'), ('Hiking'), ('Book club');
INSERT INTO memberships VALUES
    (1, 1, '2026-01-10'), (1, 3, '2026-02-01'),
    (2, 2, '2026-01-15'), (3, 2, '2026-03-05'), (3, 3, '2026-03-05');
Database changed

Which clubs is Cleo (member 3) in? Follow the links with a subquery:

SELECT name
FROM clubs
WHERE id IN (SELECT club_id FROM memberships WHERE member_id = 3)
ORDER BY name;
+-----------+
| name      |
+-----------+
| Book club |
| Hiking    |
+-----------+

How many members does each club have? Count the links per club:

SELECT
    name,
    (SELECT COUNT(*) FROM memberships AS ms WHERE ms.club_id = clubs.id) AS members
FROM clubs
ORDER BY members DESC, name;
+-----------+---------+
| name      | members |
+-----------+---------+
| Book club |       2 |
| Hiking    |       2 |
| Chess     |       1 |
+-----------+---------+

Ana is already in Chess. The composite primary key stores each pair once:

INSERT INTO memberships VALUES (1, 1, '2026-04-01');
ERROR 1062 (23000): Duplicate entry '1-1' for key 'memberships.PRIMARY'

Clean up:

DROP DATABASE kit_clubs;

Two one-to-many relationships meeting in the middle: one member, many memberships; one club, many memberships. The junction row is also the right home for joined_on, which belongs to neither the member nor the club.

4.2

Foreign Keys & Referential Integrity

By the end you can
  • Explain referential integrity and predict when MySQL raises errors 1452 and 1451
  • Choose RESTRICT, CASCADE or SET NULL for ON DELETE and ON UPDATE, and justify the choice
  • Add, drop and change a named foreign key on an existing table, cleaning up orphan rows first
  • List a database's foreign keys and their rules from information_schema
  • Diagnose the errors raised by a badly formed key (3780, 6125, 1830)
Key ideas
  • Referential integrity: every foreign key value points at a row that exists. A declared key makes orphans impossible.
  • 1452 = a child row whose parent is missing ("add or update a child row"). 1451 = a parent that children still point at ("delete or update a parent row").
  • RESTRICT refuses · CASCADE deletes or updates the children too · SET NULL keeps them and clears the link (the column must allow NULL: 1830).
  • No rule written = NO ACTION, which MySQL enforces exactly like RESTRICT.
  • Two questions: can the child exist without its parent (no: CASCADE)? Must it keep naming it (yes: RESTRICT; no: SET NULL)? When in doubt, RESTRICT.
  • Name your keys (CONSTRAINT fk_child_parent) and use the table-level form.
  • A key on existing data: find the orphans (NOT IN (SELECT id FROM parent)), fix them truthfully, then ADD CONSTRAINT. To change a rule: DROP FOREIGN KEY, then ADD again.
  • Test destructive changes inside START TRANSACTION ... ROLLBACK.
Worked example: RESTRICT and CASCADE in one transaction

RESTRICT and CASCADE working together, inside one transaction so nothing is lost. Eve (5) has one order with two lines. Try to delete her:

START TRANSACTION;
DELETE FROM customers WHERE id = 5;
ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (`bookstore`.`orders`, CONSTRAINT `fk_orders_customer` FOREIGN KEY (`customer_id`) REFERENCES `customers` (`id`) ON DELETE RESTRICT ON UPDATE CASCADE)

fk_orders_customer RESTRICTs it: her order still names her. Deal with the children first: delete her order (its lines cascade), then her, then undo everything:

SELECT COUNT(*) AS eves_items
FROM order_items
WHERE order_id IN (SELECT id FROM orders WHERE customer_id = 5);
DELETE FROM orders WHERE customer_id = 5;
SELECT COUNT(*) AS items_left FROM order_items;
DELETE FROM customers WHERE id = 5;
SELECT COUNT(*) AS customers_left FROM customers;
ROLLBACK;
+------------+
| eves_items |
+------------+
|          2 |
+------------+
+------------+
| items_left |
+------------+
|         16 |
+------------+
+----------------+
| customers_left |
+----------------+
|              7 |
+----------------+

RESTRICT made the decision explicit ("delete her orders too?"); CASCADE removed the order lines that mean nothing without their order. In a real store you would not do this at all: you would keep the sales history and mark the customer inactive.

Glossary

TermMeaning
anomaly (update, insert, delete)A problem caused by storing one fact in many rows: copies disagree, nothing can be stored, or a fact is lost
parent / child tableThe table whose id is referenced / the table that holds the foreign key
one-to-many (1:M)One parent row, many child rows; the key goes on the many side
one-to-one (1:1)At most one child per parent: a foreign key that is also UNIQUE
many-to-many (M:M)Both sides have many partners: a junction table with two foreign keys
junction tableA table whose rows are links (book_categories, order_items), with a composite or own primary key
composite primary keyA primary key of two or more columns: the combination must be unique
referential integrityEvery foreign key value points at an existing row
orphanA child row whose parent does not exist
RESTRICT / NO ACTIONRefuse to delete or change a parent that children point at (1451)
CASCADEDelete (or renumber) the children along with the parent
SET NULLKeep the children, set their foreign key to NULL (the column must allow NULL)
information_schemaThe built-in database that describes all others (REFERENTIAL_CONSTRAINTS lists keys and rules)
