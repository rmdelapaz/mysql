4.1 · Table Relationships: self-check

Q1
A customer can have many delivery addresses; each address belongs to exactly one customer. Where does the foreign key go?
A) customers.address_id
B) addresses.customer_id
C) A junction table customer_addresses
D) In both tables, one pointing at the other
Why: Ask "can one customer have many addresses?" Yes: the key goes on the many side, in addresses (like books.author_id and orders.customer_id).
A is wrong: A column holds one value: each customer could then have only one address (the lesson's Mistake 5).
C is wrong: A junction table is for many-to-many; an address does not belong to several customers.
D is wrong: Two keys pointing at each other duplicate one fact and make inserting either row first impossible.
Q2
Which of these needs a junction table?
A) One author writes many books
B) Each employee has at most one manager
C) Students and the courses they take
D) Each order belongs to one customer
Why: A student takes many courses and a course has many students: two yeses make many-to-many, and that needs a third table with two foreign keys (enrollments), which can also hold facts about the link such as a grade.
A is wrong: One-to-many: books.author_id.
B is wrong: A self-referencing one-to-many: employees.manager_id.
D is wrong: One-to-many: orders.customer_id.
Q3
In the finished bookstore, what does this print?
SELECT book_id, COUNT(*) AS categories
FROM book_categories
GROUP BY book_id
HAVING COUNT(*) = 3
ORDER BY book_id;
Three rows: books 2, 7 and 10, each with 3
Why: Each row of the junction table is one link. Grouping the links per book and keeping the piles of three finds 1984 (2), Brave New World (7) and Fahrenheit 451 (10): Fiction, plus Dystopian and one more.
Q4
The flat books table types "J.R.R. Tolkien" in two rows. A staff member edits the spelling in one of them only. What is this called?
A) An update anomaly: one fact stored twice now disagrees with itself
B) An insert anomaly
C) A delete anomaly
D) Error 1062, a duplicate entry
Why: One fact (the author's name) is stored in several rows; changing one copy leaves the table believing in two Tolkiens, with no error. Storing the name once in authors removes the cause.
B is wrong: An insert anomaly is having nowhere to store something new (an author with no books).
C is wrong: A delete anomaly is losing a fact by deleting another (the last book removes the author).
D is wrong: No rule is broken: that is exactly why the anomaly is dangerous.
Q5
A colleague builds customer_profiles with customer_id INT NOT NULL and a foreign key, but leaves out UNIQUE. What has the relationship become?
A) Many-to-many
B) Still one-to-one: the foreign key enforces it
C) Nothing: MySQL refuses the CREATE TABLE
D) One-to-many: a customer can now have several profiles
Why: A one-to-one relationship in MySQL is a one-to-many whose foreign key column is also UNIQUE. Without UNIQUE, a second profile for Alice is accepted silently (the lesson's demo shows the 1062 that UNIQUE gives).
A is wrong: Many-to-many needs a junction table with two foreign keys.
B is wrong: A foreign key checks that the parent exists, not that it is referenced only once.
C is wrong: The statement is valid; the design is what changed.
Q6
The bookstore's table is called books. What happens?
CREATE TABLE kit_reviews (
    id      INT PRIMARY KEY,
    book_id INT NOT NULL,
    FOREIGN KEY (book_id) REFERENCES book(id)
);
ERROR 1824 (HY000): Failed to open the referenced table 'book'
Why: The foreign key names a table that does not exist (book). The same error appears when the name is right but the child is created before its parent: create parents first, children second (and drop in the opposite order).

SELECT COUNT(*) AS authors_without_books
FROM authors
WHERE id NOT IN (SELECT author_id FROM books);
+-----------------------+
| authors_without_books |
+-----------------------+
|                     1 |
+-----------------------+
Why: Every book's author_id is NOT NULL, so the NOT IN list holds no NULL and the query is safe: only Isaac Asimov (10) has no book.

4.2 · Foreign Keys & Referential Integrity: self-check

Q7
The bookstore has customers 1 to 8. What happens?
INSERT INTO orders (customer_id, order_date)
VALUES (9, '2026-07-01');
A) ERROR 1451 (23000): Cannot delete or update a parent row
B) ERROR 1452 (23000): Cannot add or update a child row
C) ERROR 1062 (23000): Duplicate entry
D) Order 13 is created for customer 9
Why: orders is the CHILD of customers; inserting a child whose parent (customer 9) does not exist is refused by fk_orders_customer: "add or update a child row", 1452. Nothing is inserted.
A is wrong: 1451 is about a PARENT that still has children (a delete or a key change).
C is wrong: Nothing is duplicated; the id is new.
D is wrong: That is exactly what a declared foreign key prevents: an orphan order.
Q8
The bookstore has 18 order lines; order 5 has two of them. What does the SELECT print?
START TRANSACTION;
DELETE FROM orders WHERE id = 5;
SELECT COUNT(*) FROM order_items;
ROLLBACK;
A) 16
B) 18
C) ERROR 1451 (23000): Cannot delete or update a parent row
D) 0
Why: fk_items_order is ON DELETE CASCADE: deleting the order deletes its two lines too (16 left). ROLLBACK then puts all of it back.
B is wrong: The lines are not left behind as orphans: CASCADE removes them.
C is wrong: The delete is refused only when a RESTRICT rule protects the row; order lines cascade.
D is wrong: Only order 5's lines go, not every line.
Q9
James Okafor (8) manages Nina Kowalski (9). What does the SELECT print?
START TRANSACTION;
DELETE FROM employees WHERE id = 8;
SELECT manager_id FROM employees WHERE id = 9;
ROLLBACK;
NULL (Nina stays, with no manager)
Why: fk_employees_manager is ON DELETE SET NULL: when the manager row is deleted, the reports keep their rows and their manager_id becomes NULL. The column allows NULL, which SET NULL requires (error 1830 otherwise).
Q10
A music app deletes a playlist. Its rows in playlist_songs (the links between the playlist and its songs) should...
A) block the delete: ON DELETE RESTRICT
B) keep the links with playlist_id NULL: ON DELETE SET NULL
C) go with it: ON DELETE CASCADE
D) stay unchanged: leave the rule out (NO ACTION)
Why: A junction row is only the link itself: without the playlist it means nothing. That is the lesson's first question: can the child exist without its parent? No, so CASCADE (like book_categories and order_items).
A is wrong: Users would have to empty a playlist before deleting it: possible, but it protects nothing worth keeping.
B is wrong: The playlist_id is part of the composite primary key, which cannot be NULL, and a link to nothing is meaningless.
D is wrong: NO ACTION behaves like RESTRICT in MySQL: the delete would be refused.
Q11
The accountant wants fk_items_order changed from CASCADE to RESTRICT. How do you do it in MySQL?
A) ALTER TABLE order_items ALTER FOREIGN KEY fk_items_order ON DELETE RESTRICT;
B) ALTER TABLE order_items MODIFY CONSTRAINT fk_items_order ON DELETE RESTRICT;
C) SET FOREIGN_KEY_CHECKS = 0; then delete as usual
D) DROP FOREIGN KEY fk_items_order, then ADD CONSTRAINT fk_items_order ... ON DELETE RESTRICT
Why: There is no ALTER FOREIGN KEY: drop the key by name and add it again with the new rule (the index MySQL created stays and is reused). The lesson's Exercise 4 does exactly this and then restores CASCADE.
A is wrong: MySQL has no such statement (syntax error 1064).
B is wrong: MODIFY changes a column, not a constraint.
C is wrong: That switches checking off for the session; it changes no rule and lets orphans in.
Q12
What does this print?
SELECT DELETE_RULE
FROM information_schema.REFERENTIAL_CONSTRAINTS
WHERE CONSTRAINT_SCHEMA = 'bookstore'
  AND CONSTRAINT_NAME = 'fk_employees_manager';
SET NULL
Why: information_schema.REFERENTIAL_CONSTRAINTS lists every foreign key with its rules. The employees self-reference is ON DELETE SET NULL (and, with no ON UPDATE written, UPDATE_RULE says NO ACTION).

ROLLBACK;

Why: Bob has orders, and fk_orders_customer is RESTRICT: 1451, "delete or update a parent row". Nothing changes.

The Lesson Pages' Own Quick Quizzes

Lesson 4.1 · Table Relationships
  1. B books.author_id: The foreign key goes on the many side. Each book holds one author_id, and any number of books can hold the same one.
  2. C A NULL would mean a name did not match, and dropping the text would lose that author: A NULL after the UPDATE means a name found no match in authors. Dropping the text column would then lose that book's author for good, so you check first.
  3. A The foreign key column is also UNIQUE: The foreign key column is also UNIQUE (or is the primary key), so no parent row can be referenced by more than one child row.
  4. C Error 1062: duplicate entry for the primary key: PRIMARY KEY (book_id, category_id) allows each pair once, so MySQL reports error 1062, a duplicate entry 2-1 for the primary key.
  5. B It records what the customer paid then, which must not change when the price does: books.price is today's price; price_at_time records what was paid on the order date. They are two different facts, so old orders keep their real amounts when prices change.
Lesson 4.2 · Foreign Keys & Referential Integrity
  1. C INSERT INTO order_items (order_id, book_id, price_at_time) VALUES (50, 3, 11.99);: Error 1452 is about a child row: order_items.order_id = 50 points at an order that does not exist. Deleting a referenced parent is error 1451.
  2. A They are deleted too: fk_items_order says ON DELETE CASCADE, so the order's rows in order_items are deleted with it.
  3. B SET NULL cannot work on a NOT NULL column: SET NULL would write NULL into book_id, which is declared NOT NULL. MySQL reports error 1830 when the key is created.
  4. A It refuses, like RESTRICT: The default is NO ACTION, which InnoDB checks immediately, exactly like RESTRICT: the delete is refused with error 1451.
  5. C Nothing: they may contain orphans until you check with a query: Rows inserted while the checks were off were never checked, and turning them back on does not re-check. Run an orphan query per key to be sure.

Exit Ticket

  1. Where the key goes: one-to-many: in the many side's table (books.author_id); one-to-one: a foreign key that is also UNIQUE, usually in the optional table (customer_profiles.customer_id); many-to-many: a junction table with two foreign keys and a composite primary key (book_categories).
  2. 1452 vs 1451: 1452 = you were inserting or updating a CHILD and its parent does not exist. 1451 = you were deleting or changing the key of a PARENT that children still point at, under RESTRICT or NO ACTION.
  3. order_items.book_id → books: RESTRICT (the bookstore's choice): sold books stay on file for the sales history; mark them out of stock. Accept SET NULL only with a reason that the history does not need the book (and note the column is NOT NULL today); CASCADE is a red flag (it deletes sales).

Common Wrong Answers and What They Reveal

  • Q1 A (customers.address_id). Puts the key on the one side: the most common design error. The question "can one A have many Bs?" fixes it; ask it every time.
  • Q4 D (error 1062). Expects the database to catch a spelling difference. It cannot: that is exactly why anomalies are dangerous.
  • Q5 B (still one-to-one). Thinks the foreign key itself limits references. A key checks existence; UNIQUE limits count.
  • Q7 A (1451). Mixes up parent and child. Reteach with the first words of each message.
  • Q8 B or C. B: expects the lines to stay as orphans; C: expects every delete with children to be refused. Look up the rule before predicting.
  • Q10 A or B. Choosing a rule without asking whether the child can exist alone. The two-question diagram is the remedy.
  • Exit ticket 3 with CASCADE. "It makes deleting easy." Ask what the sales report says next year about a book that was deleted.
