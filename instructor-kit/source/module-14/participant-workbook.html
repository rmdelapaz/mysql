8.2

Final Project: Design and Build a Database

By the end you can
  • Turn a written brief into entities, relationships and business rules, and draw them as a diagram
  • Build a normalized schema in a re-runnable script, with keys, foreign keys and CHECK constraints that you have tested
  • Answer business questions with joins, GROUP BY, CTEs and window functions, using a fixed report date
  • Enforce rules that span several rows in a stored procedure with a transaction
  • Secure the database with roles and least-privilege accounts, then back it up and prove the backup restores

Today: the last two, and all five in the showcase.

Key ideas
  • The procedure is the only door into loans. The desk's account gets EXECUTE, not INSERT; the procedure runs with its definer's rights, so every loan passes every rule.
  • Shape: START TRANSACTION → read and lock (SELECT ... FOR UPDATE) → check each rule, SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '...' → INSERT → COMMIT.
  • One handler: DECLARE EXIT HANDLER FOR SQLEXCEPTION BEGIN ROLLBACK; RESIGNAL; END; undoes everything and passes the real message on.
  • Every rule gets a call that must fail, and one call must succeed.
  • Roles per job, accounts per program or person, SET DEFAULT ROLE, no DELETE anywhere. Test by logging in as the account.
  • A backup is only a backup once it has been restored: mysqldump with --single-transaction --routines --events --set-gtid-purged=OFF, restore into a test database, compare counts. Accounts are not in the dump: 05_security.sql is their backup.

8.3

Next Steps & Best Practices

By the end you can
  • Summarize what each module of the course taught and where to look things up again
  • Apply a short list of design, query, security and operations practices to any MySQL project
  • Audit a database with information_schema queries for missing keys, risky types and old character sets
  • Explain SQL injection and write parameterized queries, in SQL and in an application language
  • Choose a next learning step that fits your goal
Key ideas
  • Design: a primary key everywhere; normalize first; DECIMAL for money, DATE for dates, utf8mb4 for text; constraints the database enforces; consistent names.
  • Queries: name the columns; ORDER BY when order matters; preview with SELECT before UPDATE or DELETE; never switch off strict mode to hide an error; EXPLAIN before tuning.
  • Security: parameterized queries always; one least-privilege account per application; secrets outside the code; caching_sha2_password; supported releases.
  • Operations: automatic backups with tested restores; the schema in version-controlled scripts; the slow query log; LTS releases (9.7, 8.4), asked for by name.
  • information_schema describes every database as tables: TABLES, COLUMNS, TABLE_CONSTRAINTS, REFERENTIAL_CONSTRAINTS, KEY_COLUMN_USAGE, STATISTICS.
  • SQL injection: input glued into SQL can rewrite it. A placeholder (?, %s, :name, @name) sends the value separately; at the prompt: PREPARE ... EXECUTE ... USING.

Glossary

TermMeaning
SIGNALRaises an error with your own message from a stored program (SQLSTATE '45000', error 1644)
EXIT HANDLERCode that runs when an error happens in a procedure; with ROLLBACK and RESIGNAL it undoes and reports
SELECT ... FOR UPDATEReads rows and locks them until the transaction ends, so a second writer waits
definer's rightsA procedure runs with the privileges of the account that defined it (SQL SECURITY DEFINER)
least privilegeEvery account gets exactly what its job needs, nothing more
restore testLoading a backup into a test database and comparing it with the original
information_schemaThe read-only database in which MySQL describes every database as tables
SQL injectionInput that changes the meaning of SQL because it was glued into the statement text
parameterized querySQL with placeholders; the values travel separately and stay values
LTS releaseA long-term support version (9.7, 8.4) for production; Innovation releases (26.x) in between
