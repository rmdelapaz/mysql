8.2 · Final Project: Design and Build a Database: self-check

Q1
On the reference tool_library (Milestone 3 data), member 7 is Tessa (active, no safety course) and tool 6 is the chainsaw, on the shelf. What does this print?
CALL checkout_tool(7, 6, '2026-06-15');
A) A new loan: loan_id 17, due_on 2026-06-22
B) ERROR 1644 (45000): Member is suspended
C) ERROR 1644 (45000): Safety course required for this tool
D) ERROR 1142 (42000): INSERT command denied
Why: Tessa is active and the chainsaw is free, so the first checks pass; the course check finds no member_courses row for Chainsaw Safety and SIGNALs. The EXIT HANDLER rolls back and RESIGNALs, so the caller sees the procedure's own message with error 1644 (a user-defined SQLSTATE 45000).
A is wrong: The course rule refuses it before the INSERT.
B is wrong: Tessa is active; that message belongs to Victor (member 8).
D is wrong: root runs it here; and a desk account calling the procedure gets the definer's rights anyway.
Q2
Why does checkout_tool declare EXIT HANDLER FOR SQLEXCEPTION BEGIN ROLLBACK; RESIGNAL; END?
A) So a failed check-out never leaves a half-finished transaction, and the caller still receives the real error message
B) So that errors are ignored and the loan is created anyway
C) Because SIGNAL only works inside a handler
D) To make the procedure run with the definer's rights
Why: Any error after START TRANSACTION (a SIGNAL from a rule, or a constraint) jumps to the handler: ROLLBACK undoes the transaction, RESIGNAL passes the original error on, so the desk's web form can show "Tool is already on loan".
B is wrong: EXIT ends the procedure; nothing after the error runs.
C is wrong: SIGNAL works anywhere in a stored program.
D is wrong: Definer's rights come from SQL SECURITY DEFINER (the default), not from a handler.
Q3
Logged in as tl_desk_app (the reference roles from Milestone 6), what does this print?
DELETE FROM loans WHERE id = 1;
ERROR 1142 (42000): DELETE command denied to user 'tl_desk_app'@'localhost' for table 'loans'
Why: tl_desk has SELECT on everything, INSERT and UPDATE on members and EXECUTE on the two procedures, and nothing else: no DELETE anywhere, so the loan history stays (Rosa's requirement 7). Measured by logging in as the account; INSERT INTO loans is refused the same way, while CALL checkout_tool works.
Q4
Milestone 7: your dump of tool_library restored into tool_library_test with matching counts. What is NOT in that dump?
A) The tables and their rows
B) The view v_open_loans
C) The two procedures (taken with --routines)
D) The accounts tl_desk_app and tl_treasurer and their roles
Why: A single-database dump holds tables, rows, views and (with --routines) procedures, but no accounts and no grants: they live in the mysql system database. 05_security.sql is their backup (measured: the reference dump contains no CREATE USER and no GRANT).
A is wrong: Tables and rows are the core of every dump.
B is wrong: Views are always dumped with their database.
C is wrong: --routines puts them in; the restored copy lists both.
Q5
Why does the reference checkout_tool read the tool with SELECT ... FOR UPDATE?
A) To make the SELECT faster
B) So a second check-out of the same tool waits until the first commits, then sees the new loan
C) Because SELECT INTO needs FOR UPDATE inside a procedure
D) To update the tool's condition
Why: Without the lock, two desk volunteers could both see "drill available" and both lend it. FOR UPDATE locks the tool's row inside the transaction; the second call waits, then its "already on loan" check finds the first loan.
A is wrong: A lock can only make another session wait; it never speeds anything up.
C is wrong: SELECT ... INTO works without it.
D is wrong: FOR UPDATE changes nothing by itself; it only locks the rows read.
Q6
On the Milestone 3 data, Rosa runs the overdue query (Saturday question 2) with a later report date. How many rows come back, and which loan is first?
SET @today = '2026-06-20';
-- then the lesson's query 2: open loans with due_on < @today, worst first
Four rows; loan 13 (the extension ladder, 12 days) first
Why: On June 20 all four open loans (13 to 16) are past due: 12, 7, 3 and 1 days. On June 15 only two were. A report that reads @today can be checked against known answers for any date; one that reads CURDATE() changes every day.

8.2: predict, then run

P1
Predict the output, then run it.
CREATE TABLE tool_loans (tool VARCHAR(20), loans INT);
INSERT INTO tool_loans VALUES ('Hammer', 1), ('Socket set', 1), ('Tile cutter', 0);

SELECT tool, loans,
       RANK()       OVER (ORDER BY loans DESC) AS rnk,
       ROW_NUMBER() OVER (ORDER BY loans DESC, tool) AS row_num
FROM tool_loans
ORDER BY loans DESC, tool;
+-------------+-------+-----+---------+
| tool        | loans | rnk | row_num |
+-------------+-------+-----+---------+
| Hammer      |     1 |   1 |       1 |
| Socket set  |     1 |   1 |       2 |
| Tile cutter |     0 |   3 |       3 |
+-------------+-------+-----+---------+
Why: RANK gives equal values the same rank (both 1, then 3); ROW_NUMBER numbers every row differently, so a WHERE row_num = 1 would keep only the Hammer (it sorts first by name). That is why Saturday question 3 uses RANK.

8.3 · Next Steps & Best Practices: self-check

Q7
What does this print on the bookstore?
SET @input = 'Chicago'' OR ''x''=''x';
SET @sql = CONCAT('SELECT first_name FROM customers WHERE city = ''', @input, ''' ORDER BY id');
PREPARE search FROM @sql;
EXECUTE search;
A) Empty set
B) Two rows: Bob and Grace
C) ERROR 1064 (42000): You have an error in your SQL syntax
D) All eight customers
Why: The quote inside @input closes the string early and OR 'x'='x' becomes part of the SQL: true for every row. That is SQL injection, with no error at all. A placeholder (city = ?) with EXECUTE ... USING @input would print Empty set.
A is wrong: That is what the safe, parameterized version prints.
B is wrong: Only an honest 'Chicago' would give those two.
C is wrong: The quotes are doubled correctly, so the built statement is valid SQL; that is what makes it dangerous.
Q8
Health check 3 lists the bookstore's foreign keys. What happens to an order's rows in order_items when the order is deleted?
A) They are deleted too (fk_items_order is CASCADE)
B) The DELETE is refused (RESTRICT)
C) Their order_id becomes NULL (SET NULL)
D) Nothing: they stay and point at a missing order
Why: The check's output shows order_items · fk_items_order · orders · CASCADE. Deleting a customer with orders, by contrast, is refused (fk_orders_customer RESTRICT), and deleting a manager sets the staff's manager_id to NULL.
B is wrong: RESTRICT is the rule on fk_orders_customer and fk_items_book, not on the order link.
C is wrong: SET NULL is fk_employees_manager; order_items.order_id is NOT NULL anyway.
D is wrong: A foreign key never allows a row that points at nothing.
Q9
What does the DELETE do?
SET SQL_SAFE_UPDATES = 1;
DELETE FROM customers WHERE city = 'Houston';
It is refused: ERROR 1175 (safe update mode: no KEY column in the WHERE)
Why: city is not indexed, so safe-update mode treats the statement as a probably-forgotten WHERE and refuses it. Fix: name the rows by key (WHERE id = 4), or preview with SELECT first. Switch it back with SET SQL_SAFE_UPDATES = 0.
Q10
Why does the "tables without a primary key" check use LEFT JOIN ... WHERE c.CONSTRAINT_NAME IS NULL?
A) Because information_schema does not support inner joins
B) To sort the tables by name
C) It is the "find what is missing" pattern: keep every table, then keep only those that found no PRIMARY KEY row
D) To skip views
Why: The same pattern as "members who never borrowed" (Lesson 4.3), pointed at the catalog. The condition CONSTRAINT_TYPE = 'PRIMARY KEY' sits in ON for the reason of the final project's Mistake 5; views are skipped by TABLE_TYPE = 'BASE TABLE'.
A is wrong: information_schema is queried like any tables; inner joins work.
B is wrong: ORDER BY sorts; the join decides which rows exist.
D is wrong: TABLE_TYPE = 'BASE TABLE' skips views.
Q11
Where should a web application's database password live?
A) In the source code, next to the connection string
B) In an environment variable or a secrets manager, never in the code or the repository
C) In a comment in 05_security.sql, so the team can find it
D) Nowhere: use root without a password on the web server
Why: Lesson 8.3's security practice: secrets outside the code (environment variables, a secrets manager, or an option file only the user can read), and commit placeholder passwords only. The drivers' examples read getenv('DB_PASSWORD').
A is wrong: Code is copied, shared and pushed to repositories; the password goes with it.
C is wrong: A shared script is exactly what must not hold real passwords (the final project's FAQ).
D is wrong: root is for administration only, never for an application.
Q12
A statement has two placeholders, WHERE a.name = ? AND b.price < ?. How must the values be given to EXECUTE?
EXECUTE stmt USING @author, @max_price;: user variables, in the same order as the ? placeholders
Why: EXECUTE ... USING takes user variables (not literals) and fills the placeholders left to right. The lesson's Exercise 1 does exactly this; a driver does the same with a list of values.

The Lesson Pages' Own Quick Quizzes

Lesson 8.2 · Final Project: Design and Build a Database
  1. B In the procedure that creates loans, inside a transaction: The rule depends on other rows, so it belongs in the code that creates loans: a procedure that counts open loans inside a transaction before inserting.
  2. A A junction table with member_id, course_id and completed_on: A many-to-many relationship needs a junction table, and the completion date is a fact about the pair, so it lives there too.
  3. C CURDATE() changes over time, so it is not allowed in a CHECK: A constraint must give the same answer for a row at any time. CURDATE() changes every day, so MySQL disallows it in CHECK.
  4. A So the results are repeatable and can be checked against known answers: With a fixed report date the results can be checked by hand and compared over time; in production the variable is simply set to CURDATE().
  5. C The loan is created, because the procedure runs with its definer's rights: With SQL SECURITY DEFINER (the default) the procedure uses its definer's rights, so it can insert the loan, while the account itself still cannot touch loans directly.
Lesson 8.3 · Next Steps & Best Practices
  1. B The value is sent separately from the SQL text, so it can never become part of the statement: The SQL text and the values travel separately, so the server parses the statement before it sees the input, and the input can only ever be a value.
  2. C It fails with error 1524; update the app's driver instead: MySQL 9.x no longer has the mysql_native_password plugin (error 1524). Maintained drivers support caching_sha2_password, so the fix is a current driver.
  3. A REFERENTIAL_CONSTRAINTS: REFERENTIAL_CONSTRAINTS has one row per foreign key, with its UPDATE_RULE and DELETE_RULE.
  4. B Change the column to DECIMAL(8, 2): DECIMAL stores exact decimal digits, so sums of prices are exact to the cent.
  5. C The current Long-Term Support release, such as 9.7 or 8.4: LTS releases receive bug and security fixes for years without changing behavior, which is what production systems need.

Exit Ticket

  1. Definer's rights: the procedure runs with the privileges of its definer (SQL SECURITY DEFINER is the default); the desk account only needs EXECUTE, and every loan passes the procedure's rules.
  2. Safely: PREPARE s FROM 'SELECT ... WHERE email = ?'; EXECUTE s USING @input; DEALLOCATE PREPARE s; or, in a driver, a placeholder and the value passed separately.
  3. Next step: any path from the table with a start date; check that the plan names one first topic and one small project.

Common Wrong Answers and What They Reveal

  • Q1 A (a loan is created). Expects the procedure to check only availability. Ask which of the five rules reads member_courses.
  • Q2 C or D. Mixes up SIGNAL, handlers and definer's rights: three separate tools. Draw the five-box shape again.
  • Q4 C (the procedures are missing). True only without --routines; the lesson's command has it.
  • Q5 A ("faster"). Thinks of locks as optimizations. Show the two-terminal race once.
  • Q7 A (Empty set). Has seen the safe version and assumes the database protects them. The leak is silent: that is the danger.
  • Q8 B (RESTRICT). Generalizes from customers to orders. Read health check 3's output line by line.
