Session 14: Final Project Studio II, Showcase and Next Steps

How to run the last session of MySQL Foundations. Studio II takes the final project through business logic, least-privilege accounts and a backup proven by a restore; every learner presents in the showcase; Lesson 8.3 turns the course into habits (SQL injection and placeholders, an information_schema health check pointed at their own project) and the course closes with submission, evaluation and next steps.

How to Use This Guide

  • Session 14 closes the course. Before the break: Studio II (Milestones 5 to 7 of the final project, Lesson 8.2), with a short frame and demo. After the break: the showcase (every learner presents for three minutes), then Lesson 8.3 (best practices, the health check, SQL injection, what to learn next) and the course close.
  • Every SQL block below was run for real on MySQL 9.7. The 8.2 outputs come from the lesson's own reference solution run as one session (they match the page); the account logins and the dump and restore were measured by logging in as the accounts and running mysqldump. The 8.3 outputs come from the lesson page's own blocks on a fresh bookstore.
  • Keep lesson_final_project.html, lesson_21.html and final-assessment.html open. The final-assessment page holds the rubric, scoring guidance, the reference numbers for every milestone and the submission rules.
  • Prepare the projector copy before class: in a terminal started inside a folder holding the lesson's reference scripts, build tool_library (Milestones 2, 3 and 5's procedures, not the calls), so the demo's calls answer exactly as above. Do not show the scripts themselves.
  • Teal blocks are hands-on, amber blocks are watch-outs. Lesson codes match the course site.
The #1 risk of Session 14: no time left for the showcase and the close

Milestone 5 expands to fill any time you give it. The showcase and Lesson 8.3 are what turn a project into a finished course, so they are fixed. The defense: at 1:05 everyone moves to Milestone 6 whatever the state of their procedure (a procedure that enforces three rules is "meets" on the rubric; the rest goes home). At 1:30 the break starts on time. A learner whose procedure is broken presents a design decision and a query instead.

Mental model to say

"Last session you sorted the rules: one row → a constraint, other rows → a procedure. Today you write that procedure. It is the only door into the loans table: the desk's account may not INSERT into loans at all, only CALL checkout_tool, and the procedure runs with its definer's rights, so every loan passes through every rule."

"A procedure that checks first and inserts second has a gap: two desk volunteers can both see the drill as free. The transaction and the row lock close the gap; the handler makes sure a refusal undoes everything and tells the caller why."

Three mistakes to expect, and how to coach each
  • Checks without a lock. The procedure checks and inserts correctly, but reads the tool without FOR UPDATE. Coach with two terminals: "open a transaction in each and lend the same drill" (Lesson 7.2's two-session demo). Q5 in the self-check.
  • root everywhere. The desk account was skipped, or created with ALL PRIVILEGES. Coach with Rosa's requirement 7 and the rubric's Security row ("desk account can only change data through procedures").
  • A backup that was never restored. "The dump file exists" is the "meets" level; full points need the restore and the matching counts in the README. Coach: "a backup is only a backup once it has been restored."
Checks for understanding

Ask during the studio check-ins:

  • Why can the desk account create a loan it may not INSERT? Answer: the procedure runs with its definer's rights (SQL SECURITY DEFINER, the default).
  • What does RESIGNAL add to ROLLBACK? Answer: the caller still receives the original error and message.
  • Your dump restored. What else must you keep to rebuild Rosa's system? Answer: 05_security.sql (the accounts are not in the dump) and the numbered scripts.

Mental model to say

Show the lesson's module table ("The Course in One Page") and say: "Every practice in this lesson prevents a problem you met in this course: a missing primary key, FLOAT money, an UPDATE without WHERE, a password in code. Habits are cheap insurance."

Then the one idea that matters most when they leave: "Real users never see a mysql> prompt. Applications send SQL through a driver, and the user's input travels as a PARAMETER, separate from the SQL text. Glue input into SQL and someone else writes your WHERE clause."

Live demo (you type, they follow; 15 minutes)

The lesson's own blocks on a freshly loaded bookstore; outputs are real and match the page.

EXECUTE lookup;
DEALLOCATE PREPARE lookup;

  2. The fix: a placeholder (3m). "The value travels separately and can only ever be a value. Every driver does this." 
    PREPARE lookup FROM 'SELECT first_name, email FROM customers WHERE email = ?';
EXECUTE lookup USING @input;
DEALLOCATE PREPARE lookup;
    Statement prepared
Empty set
    Show one driver example on the lesson page (the language your group uses next): ?, %s, :name, @name are all the same idea.
  3. information_schema checks a design (5m). "Every server describes itself in tables. Plant an old-style table, then let a query find it." 
    CREATE TABLE hc_demo_payments (
    paid_on DATE,
    amount  FLOAT,
    note    VARCHAR(100) CHARACTER SET latin1
);

SELECT t.TABLE_NAME AS table_without_pk
FROM information_schema.TABLES AS t
LEFT JOIN information_schema.TABLE_CONSTRAINTS AS c
       ON c.TABLE_SCHEMA = t.TABLE_SCHEMA
      AND c.TABLE_NAME = t.TABLE_NAME
      AND c.CONSTRAINT_TYPE = 'PRIMARY KEY'
WHERE t.TABLE_SCHEMA = 'bookstore'
  AND t.TABLE_TYPE = 'BASE TABLE'
  AND c.CONSTRAINT_NAME IS NULL
ORDER BY t.TABLE_NAME;

| table_without_pk |
+------------------+
| hc_demo_payments |
+------------------+
  4. Risky types (2m). "FLOAT for money and latin1 text." 
    SELECT TABLE_NAME, COLUMN_NAME, COLUMN_TYPE, CHARACTER_SET_NAME
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = 'bookstore'
  AND (DATA_TYPE IN ('float', 'double')
       OR CHARACTER_SET_NAME NOT IN ('utf8mb4', 'binary'))
ORDER BY TABLE_NAME, ORDINAL_POSITION;
    +------------------+-------------+--------------+--------------------+
| TABLE_NAME       | COLUMN_NAME | COLUMN_TYPE  | CHARACTER_SET_NAME |
+------------------+-------------+--------------+--------------------+
| hc_demo_payments | amount      | float        | NULL               |

    SET SQL_SAFE_UPDATES = 1;

UPDATE books SET price = price * 1.10;

    Then SET SQL_SAFE_UPDATES = 0;.

Three mistakes to expect, and how to coach each
  • "Escaping quotes is enough." Coach: placeholders cost nothing and cannot be gotten wrong; escaping by hand can. The lesson says so in its Common Mistake 1.
  • Health check reports nothing, so the database must be fine. Coach: run it on the planted table (the lab plants one) to see that each check CAN find something. An empty result only means something when the check can fail.
  • Learning plans with no dates. Coach with the lesson's Step 5: a path, one first topic, one small project and a date next to each.
Checks for understanding
  • What makes a parameterized query safe? Answer: the value is sent separately from the SQL text, so it can never become part of the statement.
  • Which information_schema table tells you what deleting a parent does? Answer: REFERENTIAL_CONSTRAINTS (DELETE_RULE).
  • Which MySQL version do you install for production next year? Answer: the current LTS (9.7 or 8.4), asked for by name.

Workbook self-check, items Q7 to Q12.

Answers: Q7 D) All eight customers; Q8 A) They are deleted too (fk_items_order is CASCADE); Q9 It is refused: ERROR 1175 (safe update mode: no KEY column in the WHERE); Q10 C) It is the "find what is missing" pattern: keep every table, then keep only those that found no PRIMARY KEY row; Q11 B) In an environment variable or a secrets manager, never in the code or the repository; Q12 EXECUTE stmt USING @author, @max_price;: user variables, in the same order as the ? placeholders. Full set with explanations in the Answer Key.

Differentiation

Support: the health-check starter has check 1 done; Steps 1 to 4 on the bookstore only are enough for today. Stretch: the lesson's Exercise 3 (a one-line summary per table with correlated subqueries) and its Bonus Challenge (a trigger, a FULLTEXT index or a scheduled event added to the final project, with one thing the manual taught them).

Closing

Course close (10 minutes)
  1. Final submission (3m). On the slide: the zipped tool-library folder (the five scripts, the backup file of the test data, README.md with the restore date and counts, the self-scored rubric), within one week, by the channel your program uses. Placeholder passwords only. The full rules: final-assessment.html.
  2. Exit ticket (3m). Three questions below.
  3. Course evaluation (2m). The link or the paper form; ask for one sentence on what to keep and one on what to change.
  4. What comes next (2m). Show "Choose a path by goal" from Lesson 8.3 once more, and the course's reference pages (cheat sheet, glossary, common errors, troubleshooting). Thank them; name one thing the group did well.
Exit ticket (3 questions, no notes, 3 minutes)
  1. Why can the desk's web form create a loan through checkout_tool although its account may not INSERT into loans? Answer: the procedure runs with its definer's rights (SQL SECURITY DEFINER is the default), so it may insert; the caller only needs EXECUTE, and every loan passes the rules.
  2. Rewrite CONCAT('... WHERE email = ''', @input, '''') safely. Answer: PREPARE s FROM 'SELECT ... WHERE email = ?'; EXECUTE s USING @input; (a driver: a placeholder plus the value in a list).
  3. Name your next step from Lesson 8.3's table and the date you start. Answer: any path with a date (the learning plan's first line).

  • Lesson 8.3: project Step 5, learning_plan.md with dates; Exercises 1 and 2 (Exercise 3 is a stretch); the Quick Quiz; the journal prompt (look back at your Lesson 1.1 entry).
