6.3

Database Design & Normalization

By the end you can
  • Recognize update, insert and delete anomalies, and show each one with a query
  • Find the functional dependencies and the key of a table
  • Normalize a flat table to first, second and third normal form (1NF, 2NF, 3NF)
  • Build the normalized tables with INSERT ... SELECT DISTINCT and prove with EXCEPT that no data was lost
  • Read an ER diagram, and decide when storing derived or duplicated data is worth the risk
Key ideas
  • Anomalies: update (copies drift), insert (a fact needs another fact to exist), delete (removing one fact removes another). One cause: facts about different things in one row.
  • A → B: same A, same B. Dependencies come from business rules; data can disprove one, never prove it.
  • 1NF: one value per cell, no repeating columns, a key. 2NF: no column depends on part of a composite key. 3NF: no column depends on a non-key column.
  • Migrate with INSERT ... SELECT DISTINCT, parents first, children last, joining back on the natural identifiers.
  • Prove it lossless with EXCEPT in both directions: two empty sets.
  • ER diagrams: a line's "one" end holds the primary key, the "many" end the foreign key; many at both ends means a missing junction table.
  • Do not store what you can compute. Denormalize only for a measured problem, with a plan to keep the copy in sync.
Worked example: a key and a dependency, tested on the bookstore

Finding a key with data: if a set of columns has as many distinct values as the table has rows, it COULD be the key (the business decides whether it IS). In order_items, an order has several lines, but each book appears once per order:

SELECT COUNT(*)                          AS item_rows,
       COUNT(DISTINCT order_id)          AS orders,
       COUNT(DISTINCT order_id, book_id) AS order_book_pairs
FROM order_items;
+-----------+--------+------------------+
| item_rows | orders | order_book_pairs |
+-----------+--------+------------------+
|        18 |     12 |               18 |
+-----------+--------+------------------+

Testing a dependency: has any book ever been sold at two different prices? No counterexample today:

SELECT book_id, COUNT(DISTINCT price_at_time) AS prices_paid
FROM order_items
GROUP BY book_id
HAVING COUNT(DISTINCT price_at_time) > 1;
Empty set

But book_id → price_at_time is NOT a rule: price_at_time records what was paid on that order, and prices change. The data cannot tell you that; the business can. That is why price_at_time stays in order_items.

7.1

Stored Procedures & Functions

By the end you can
  • Explain what the DELIMITER client command does, and when you do not need it
  • Create and call stored procedures with IN, OUT and INOUT parameters
  • Write stored functions with the right characteristic (DETERMINISTIC, READS SQL DATA) and use them inside queries
  • Use local variables, IF, CASE and WHILE in a routine, and reject bad input with SIGNAL
  • List, inspect, replace and drop routines, and read the errors MySQL raises for broken ones (1064, 1418, 1172, 1304, 1644)
Key ideas
  • Procedure: CALL name(...); result sets, OUT and INOUT parameters, changes data. Function: returns one value, used inside expressions.
  • DELIMITER // ... // is a client command: the client waits for // so a body with semicolons is sent whole. Switch back with DELIMITER ;.
  • OUT parameters land in user variables: CALL p(1, @x); SELECT @x;. SELECT ... INTO must find at most one row (1172).
  • DECLARE local variables first in a block; p_ and v_ prefixes so names never shadow columns.
  • Function characteristics (DETERMINISTIC, NO SQL, READS SQL DATA) are required with binary logging on (1418), and must be true.
  • SIGNAL SQLSTATE '45000' refuses bad input with your own message (1644). Check before you change.
  • Rerunnable scripts: DROP PROCEDURE IF EXISTS / DROP FUNCTION IF EXISTS, then CREATE (no CREATE OR REPLACE in MySQL).
Worked example: a display function and a date-range procedure

A function for display, pure string work (DETERMINISTIC, NO SQL):

DELIMITER //
CREATE FUNCTION initials(p_name VARCHAR(100))
RETURNS VARCHAR(10)
DETERMINISTIC
NO SQL
BEGIN
    RETURN CONCAT(LEFT(p_name, 1), '.', LEFT(SUBSTRING_INDEX(p_name, ' ', -1), 1), '.');
END //
DELIMITER ;
SELECT name, initials(name) AS initials
FROM authors
WHERE id IN (1, 5, 9)
ORDER BY id;
+---------------+----------+
| name          | initials |
+---------------+----------+
| Frank Herbert | F.H.     |
| Jane Austen   | J.A.     |
| Ray Bradbury  | R.B.     |
+---------------+----------+

A procedure that takes two dates and returns a result set; the range "from, up to but not including, to" is the index-friendly habit from Session 9:

DELIMITER //
CREATE PROCEDURE orders_between(IN p_from DATE, IN p_to DATE)
BEGIN
    SELECT o.id, o.order_date, c.first_name
    FROM orders AS o
    JOIN customers AS c ON c.id = o.customer_id
    WHERE o.order_date >= p_from AND o.order_date < p_to
    ORDER BY o.order_date;
END //
DELIMITER ;
CALL orders_between('2026-03-01', '2026-04-01');
+----+------------+------------+
| id | order_date | first_name |
+----+------------+------------+
|  3 | 2026-03-10 | Bob        |
|  7 | 2026-03-28 | Bob        |
+----+------------+------------+

Glossary

TermMeaning
anomaly (update / insert / delete)Trouble caused by storing facts about different things in one table
functional dependency (A → B)Same A, same B: a business rule
keyA minimal set of columns that determines every other column
1NF / 2NF / 3NFOne value per cell / no dependency on part of the key / no dependency on a non-key column
transitive dependencyA non-key column that depends on another non-key column
surrogate keyAn AUTO_INCREMENT id used as the primary key
junction tableA table with a composite primary key that carries a many-to-many relationship
lossless decompositionA split whose tables, joined back, give exactly the original rows
denormalizationStoring a copy or a computed value on purpose, for speed
stored procedureA named routine run with CALL; result sets, OUT parameters, changes data
stored functionA named routine that returns one value inside an expression
DELIMITERA client command that changes the statement end marker for a while
characteristicDETERMINISTIC, NO SQL, READS SQL DATA ...: what a function promises it does
SIGNALRaises your own error (SQLSTATE '45000', error 1644) and stops the routine
