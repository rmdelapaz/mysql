Session 10: Normalization and Stored Programs

How to teach design and stored programs in one session: make a flat sheet corrupt itself, find its dependencies and key, split it into 3NF tables and prove with EXCEPT that nothing was lost; then save logic next to the data as procedures and functions, with parameters, characteristics and input checks that refuse bad calls.

Warm-up answers (W1 to W5)
  1. W1 Which plan line do you expect, and why is there an index at all? Answer: Index lookup on orders using fk_orders_customer: InnoDB created that index for the foreign key.
  2. W2 Is this view updatable? Answer: YES: each view row is one books row (no grouping, DISTINCT or UNION).
  3. W3 An index on (customer_id, sold_on): can a query on a sold_on range alone seek with it? Answer: No: the dates are sorted only within each customer (leftmost prefix).
  4. W4 What does MySQL store when you create a view? Answer: Only the query; rows are computed on every read.
  5. W5 What does WITH CHECK OPTION refuse? Answer: A write through the view that would produce a row the view cannot show (1369).

Objectives (from the lesson page)

Mental model to say

Start from the warm-up spreadsheets: "Every one of these stores the same fact on many rows. It works until someone changes one copy. A database cannot stop people typing wrong values, but a good design makes sure each fact is typed once, so there is nothing to keep in sync."

Then dependencies, as arrows on the board: "A → B means: same A, same B. order_id → order_date, email → name. They come from the rules of the business, not from today's rows." Point at the board line: 1NF one value per cell and a key; 2NF nothing depends on part of a composite key; 3NF nothing depends on a non-key column. "The key, the whole key, and nothing but the key."

Last, the practical recipe: one table per kind of thing, a surrogate id plus UNIQUE on the natural identifier, foreign keys on the many side, a junction table for many-to-many. "This is exactly the bookstore you have used since Module 4."

Three mistakes to expect, and how to coach each
  • Confusing 2NF and 3NF. Coach with one question per column: "Does it need the whole key, part of the key, or another non-key column?" Part = 2NF, another column = 3NF.
  • Treating data as proof. "The query found no counterexample, so it is a rule." Coach: "Would the business allow two prices for one title next year?" Data can only disprove.
  • Calling price_at_time redundant. Coach: "What does each column answer?" Today's price versus what this customer paid on this order: two facts (self-check and lesson quiz).

Mental model to say

"Until now every query lived in your head or in a file. When five programs need the same ten-line query, someone copies it five times and the copies drift: the same problem as this morning's spreadsheet, in code. A stored routine is a named block of SQL saved next to the tables, with parameters. Everyone calls the one copy."

Point at the two boxes: a procedure is run with CALL, may return result sets, hands values back through OUT parameters and may change data; a function returns one value and lives inside a query, like ROUND or CONCAT.

Then the one confusing thing, said plainly: "The mysql client cuts your typing at every semicolon. A body has several. DELIMITER // tells the CLIENT to wait for // for a while; the server never sees the word."

    SELECT b.title, b.price
    FROM books AS b
    JOIN authors AS a ON a.id = b.author_id
    WHERE a.name = p_author
    ORDER BY b.title;
END //
DELIMITER ;

  3. OUT: an answer through a user variable (2m). "SELECT ... INTO stores instead of printing, so the CALL prints nothing. The answer lands in @tolkien_books." 
    DELIMITER //
CREATE PROCEDURE count_books_by(IN p_author VARCHAR(100), OUT p_count INT)
BEGIN
    SELECT COUNT(*) INTO p_count
    FROM books AS b
    JOIN authors AS a ON a.id = b.author_id
    WHERE a.name = p_author;
END //
DELIMITER ;
CALL count_books_by('J.R.R. Tolkien', @tolkien_books);
SELECT @tolkien_books AS tolkien_books;
    +---------------+
| tolkien_books |
+---------------+
|             2 |
+---------------+
  4. Local variables (3m). "DECLARE comes first in a block; a local variable lives for one call." 34.97 plus 8% tax. 
    DELIMITER //
CREATE PROCEDURE order_receipt(IN p_order_id INT)
BEGIN
    DECLARE v_subtotal DECIMAL(10, 2) DEFAULT 0;
    DECLARE v_tax_rate DECIMAL(4, 3) DEFAULT 0.080;
    DECLARE v_tax      DECIMAL(10, 2);
    SELECT COALESCE(SUM(quantity * price_at_time), 0) INTO v_subtotal
    FROM order_items
    WHERE order_id = p_order_id;
    SET v_tax = ROUND(v_subtotal * v_tax_rate, 2);
    SELECT p_order_id         AS order_id,
           v_subtotal         AS subtotal,
           v_tax              AS tax,
           v_subtotal + v_tax AS total;
END //
DELIMITER ;
CALL order_receipt(1);

  5. IF ... ELSEIF ... ELSE (3m). "Gold from $50, Silver from $30, Bronze above zero, New otherwise." 
    DELIMITER //
CREATE PROCEDURE classify_customer(IN p_customer_id INT, OUT p_tier VARCHAR(10))
BEGIN
    DECLARE v_spent DECIMAL(10, 2);
    SELECT COALESCE(SUM(oi.quantity * oi.price_at_time), 0) INTO v_spent
    FROM orders AS o
    JOIN order_items AS oi ON oi.order_id = o.id
    WHERE o.customer_id = p_customer_id;
    IF v_spent >= 50 THEN
        SET p_tier = 'Gold';
    ELSEIF v_spent >= 30 THEN
        SET p_tier = 'Silver';
    ELSEIF v_spent > 0 THEN
        SET p_tier = 'Bronze';
    ELSE
        SET p_tier = 'New';
    END IF;
END //
DELIMITER ;
CALL classify_customer(1, @alice);
CALL classify_customer(2, @bob);
CALL classify_customer(3, @carol);
SELECT @alice AS alice, @bob AS bob, @carol AS carol;
    +-------+--------+-------+
| alice | bob    | carol |
+-------+--------+-------+
| Gold  | Silver | New   |
+-------+--------+-------+
  6. A stored function (3m). "One value, used inside a query like a built-in function. The characteristics line describes it to the server: same input, same output (DETERMINISTIC), no table read (NO SQL)." 
    DELIMITER //
CREATE FUNCTION with_tax(p_amount DECIMAL(10, 2))
RETURNS DECIMAL(10, 2)
DETERMINISTIC
NO SQL
BEGIN
    RETURN ROUND(p_amount * 1.08, 2);
END //
DELIMITER ;
SELECT title, price, with_tax(price) AS price_with_tax
FROM books
WHERE price >= 11
ORDER BY price DESC;

| To Kill a Mockingbird | 11.99 |          12.95 |
+-----------------------+-------+----------------+
  7. Without characteristics (1m). "Binary logging is on by default since 8.0, so the server wants to know what a function does." 
    CREATE FUNCTION book_count()
RETURNS INT
RETURN (SELECT COUNT(*) FROM books);
    ERROR 1418 (HY000): This function has none of DETERMINISTIC, NO SQL, or READS SQL DATA in its declaration and binary logging is enabled (you *might* want to use the less safe log_bin_trust_function_creators variable)
    Fix: READS SQL DATA after RETURNS INT. Never turn on log_bin_trust_function_creators to silence it.
  8. Check first, then change: SIGNAL (4m). "A procedure that changes data checks its input before the UPDATE. SIGNAL raises your own error, number 1644, with your message." 
    DELIMITER //
CREATE PROCEDURE set_book_price(IN p_book_id INT, IN p_price DECIMAL(8, 2))
BEGIN
    IF p_price IS NULL OR p_price <= 0 THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Price must be greater than zero';
    END IF;
    IF NOT EXISTS (SELECT 1 FROM books WHERE id = p_book_id) THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'No book with that id';
    END IF;
    UPDATE books SET price = p_price WHERE id = p_book_id;
END //
DELIMITER ;
CALL set_book_price(5, -1.00);
CALL set_book_price(99, 9.99);
    ERROR 1644 (45000): Price must be greater than zero
ERROR 1644 (45000): No book with that id
    Both checks run before the UPDATE, so a refused call changes nothing.

Three mistakes to expect, and how to coach each
  • A stuck -> prompt. Coach: "Which delimiter is active? Type // to send, then DELIMITER ;." Every kit example switches back in the same block.
  • Expecting OUT parameters to print. "CALL printed nothing." Coach: "Where did you ask it to put the answer? SELECT @your_variable."
  • SIGNAL after the change. A check placed after the UPDATE stops the procedure too late. Coach: "Which statements already ran when SIGNAL fires?" (Lesson 7.2's transactions handle multi-step changes.)

Checks for understanding

Ask these out loud:

  • Who reads DELIMITER //? Answer: the mysql client (and SOURCE); apps, Workbench and phpMyAdmin's Delimiter box do not need you to type it.
  • Why READS SQL DATA and not DETERMINISTIC for order_total? Answer: it reads rows that change; DETERMINISTIC would be a false promise.
  • What does a procedure give back that a function cannot? Answer: result sets, several OUT values, and transactions inside.
  • Why the p_ prefix? Answer: a parameter named like a column silently shadows it (WHERE id = id).
