6.3 · Database Design & Normalization: self-check

Q1
Alice's email is stored on three order rows. Someone corrects it on one row only, and now the table holds two emails for her. Which anomaly is this?
A) An update anomaly
B) An insert anomaly
C) A delete anomaly
D) A first normal form violation
Why: A fact stored several times was changed in one place: the copies drift apart and no query can tell which is right. The cause is the same as for all three anomalies: facts about a customer stored in an order table.
B is wrong: An insert anomaly is when you cannot add a fact (a customer with no order) without another one.
C is wrong: A delete anomaly is losing a fact (a customer) by deleting another (their only order).
D is wrong: Every cell here holds one value; the problem is repetition, which 2NF and 3NF deal with.
Q2
A contacts table has the columns name, phone1, phone2 and phone3. Which normal form does it break?
A) Second normal form
B) Third normal form
C) First normal form: a repeating group of columns
D) None: three columns are fine
Why: Numbered columns are a list spread across columns: a fourth phone needs a new column, and "who has this number?" must check three columns. 1NF: one row per phone in a child table (contact_id, phone).
A is wrong: 2NF is about partial dependencies on a composite key.
B is wrong: 3NF is about non-key columns that depend on other non-key columns.
D is wrong: It works until someone has four numbers, and every search gets three times longer.
Q3
enrollments(student_id, course, course_room, grade) has the key (student_id, course). Each course meets in one room. Which rule does course → course_room break?
A) 1NF
B) 2NF: course_room depends on only part of the key
C) 3NF: a transitive dependency
D) None: course is part of the key
Why: course_room needs only course, not the whole key, so every student's row repeats the room. Fix: courses(course, room) and enrollments(student_id, course, grade).
A is wrong: Every cell holds one value.
C is wrong: Transitive means through a NON-key column; course is part of the key.
D is wrong: Being part of the key is exactly what makes it a partial dependency.
Q4
employees(id, name, dept_id, dept_name) has the key id. Which dependency breaks 3NF, and what is the fix?
dept_id → dept_name (a transitive dependency: id → dept_id → dept_name); move dept_name to departments(id, name) and keep dept_id as a foreign key
Why: dept_name describes the department, not the employee. As long as it lives in employees, renaming a department means updating every employee in it.
Q5
You split a flat table into four, then run two EXCEPT queries in opposite directions (old rows EXCEPT the rebuilt join, and the other way). Both print Empty set. What does that prove?
A) Every new table has a primary key
B) The new tables contain no duplicates
C) The design is in 3NF
D) The four tables, joined back, hold exactly the original rows: the split lost nothing and added nothing
Why: EXCEPT returns rows of the first query missing from the second. One direction catches lost rows, the other catches invented ones (a wrong join). Both empty = lossless.
A is wrong: Keys are a separate check (SHOW CREATE TABLE).
B is wrong: EXCEPT compares the two sides; it says nothing about duplicates inside one table.
C is wrong: A lossless split can still keep a transitive dependency.
Q6
SELECT member_email FROM club_signups GROUP BY member_email HAVING COUNT(DISTINCT member_name) > 1; prints Empty set. What can you conclude?
A) member_email → member_name is proved
B) The data does not contradict member_email → member_name; whether it is a rule is a business decision
C) member_name → member_email holds
D) The table is in 3NF
Why: Data can disprove a dependency (one counterexample is enough) but never prove one: the next sign-up might break it. The rule comes from the business ("an email belongs to one member").
A is wrong: Six rows cannot prove a rule about all future rows.
C is wrong: The query tests the other direction.
D is wrong: One dependency says nothing about the whole table's normal form.

6.3 · Database Design & Normalization: predict, then run

P1
Predict the output, then run it.
CREATE TABLE sheet (member VARCHAR(30), club VARCHAR(30));
INSERT INTO sheet VALUES ('Ana', 'Chess'), ('Ben', 'Chess'), ('Ana', 'Poetry'),
                         ('Cy', 'Poetry'), ('Ben', 'Chess');
CREATE TABLE members (id INT AUTO_INCREMENT PRIMARY KEY, name VARCHAR(30) UNIQUE);
INSERT INTO members (name) SELECT DISTINCT member FROM sheet ORDER BY member;
SELECT COUNT(*) AS sheet_rows, (SELECT COUNT(*) FROM members) AS members FROM sheet;
+------------+---------+
| sheet_rows | members |
+------------+---------+
|          5 |       3 |
+------------+---------+
Why: Five sheet rows, three distinct members (Ana, Ben, Cy): SELECT DISTINCT collapses the copies, and the UNIQUE on name would refuse a second run (1062).
P2
Predict the output, then run it.
SELECT title FROM books WHERE price < 9
EXCEPT
SELECT title FROM books WHERE in_stock = FALSE
ORDER BY title;
+---------------------+
| title               |
+---------------------+
| Animal Farm         |
| Pride and Prejudice |
+---------------------+
Why: Books under $9 are The Great Gatsby, The Catcher in the Rye, Animal Farm and Pride and Prejudice; EXCEPT removes the two that are out of stock. The ORDER BY sorts the whole EXCEPT result.

7.1 · Stored Procedures & Functions: self-check

Q7
In the mysql client, without changing the delimiter, you type a procedure whose body is BEGIN SELECT ...; END;. What happens?
A) Two ERROR 1064 lines: the client sent the text in two pieces at the semicolons
B) ERROR 1418
C) The procedure is created
D) ERROR 1304: PROCEDURE already exists
Why: The client splits at every ; and sends the unfinished CREATE ... BEGIN SELECT ... (1064 near ''), then the leftover END (1064 near 'END'). DELIMITER // ... // ... DELIMITER ; sends the whole body at once (the debug handout's section A).
B is wrong: 1418 is for functions without characteristics.
C is wrong: Only a one-statement body without BEGIN and END works without a delimiter change.
D is wrong: Nothing was created, so nothing exists yet.
Q8
What does this print? (Books under $9: The Great Gatsby, The Catcher in the Rye, Animal Farm, Pride and Prejudice.)
CREATE PROCEDURE count_cheaper(IN p_price DECIMAL(8, 2), OUT p_n INT)
    SELECT COUNT(*) INTO p_n FROM books WHERE price < p_price;
CALL count_cheaper(9.00, @n);
SELECT @n AS cheaper;
4 (in a column named cheaper)
Why: The one-statement body needs no BEGIN and no delimiter change. SELECT ... INTO stores the count in the OUT parameter, which lands in @n; the CALL itself prints nothing.
Q9
A stored function returns ROUND(p_amount * 1.08, 2) and reads no table. Which characteristics are true of it?
A) READS SQL DATA
B) MODIFIES SQL DATA
C) NOT DETERMINISTIC (the default)
D) DETERMINISTIC and NO SQL
Why: Same input, same output, and no SQL statement in the body: the lesson's with_tax. With binary logging on, one of DETERMINISTIC, NO SQL or READS SQL DATA is required (1418), and the promise must be true.
A is wrong: It reads no table.
B is wrong: It changes nothing.
C is wrong: False modesty is legal but untrue, and on its own it is refused with 1418.
Q10
A procedure runs SELECT title INTO p_title FROM books WHERE author_id = p_author_id;. What happens when it is called for J.R.R. Tolkien, who has two books?
A) p_title gets the first title in id order
B) p_title is NULL
C) ERROR 1172 (42000): Result consisted of more than one row
D) p_title holds both titles, separated by a comma
Why: One variable cannot hold two rows. The procedure was created without complaint; the error appears only on a call that hits it, which is why routines are tested with awkward inputs. Fix: an aggregate (MIN(title)) or ORDER BY ... LIMIT 1.
A is wrong: MySQL does not pick one for you.
B is wrong: NULL comes from an aggregate over no rows, not from two rows.
D is wrong: That would be GROUP_CONCAT.
Q11
What does the CALL print?
DELIMITER //
CREATE PROCEDURE check_qty(IN p_qty INT)
BEGIN
    IF p_qty < 1 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Quantity must be at least 1';
    END IF;
    SELECT p_qty AS accepted;
END //
DELIMITER ;
CALL check_qty(0);
ERROR 1644 (45000): Quantity must be at least 1
Why: SIGNAL SQLSTATE '45000' raises your own error, reported as 1644 with your message, and stops the procedure: the SELECT after it never runs.
Q12
Which of these can a stored function NOT do?
A) Return one value
B) Read tables (declared READS SQL DATA)
C) Run COMMIT or START TRANSACTION
D) Be used inside WHERE
Why: Functions cannot control transactions and cannot return result sets; procedures can (Lesson 7.2 puts transactions inside procedures). Used in WHERE, a function runs once per row, so keep it cheap.
A is wrong: That is what a function is for.
B is wrong: copies_sold and author_revenue do exactly that.
D is wrong: Anywhere an expression fits: the functions lab filters with copies_sold(id) = 0.

7.1 · Stored Procedures & Functions: predict, then run

P3
Predict the output, then run it.
DELIMITER //
CREATE PROCEDURE double_it(INOUT p_n INT)
BEGIN
    SET p_n = p_n * 2;
END //
DELIMITER ;
SET @n = 10;
CALL double_it(@n);
CALL double_it(@n);
SELECT @n AS n;
+------+
| n    |
+------+
|   40 |
+------+
Why: INOUT reads the caller's value and replaces it: 10 → 20 → 40.
P4
Predict the output, then run it.
DELIMITER //
CREATE PROCEDURE first_title(IN p_author_id INT, OUT p_title VARCHAR(200))
BEGIN
    SELECT MIN(title) INTO p_title FROM books WHERE author_id = p_author_id;
END //
DELIMITER ;
SET @t = 'nothing yet';
CALL first_title(10, @t);
SELECT @t AS asimov_first_title;
+--------------------+
| asimov_first_title |
+--------------------+
| NULL               |
+--------------------+
Why: NULL, not 'nothing yet': an OUT parameter starts as NULL inside the procedure (it does not carry the caller's value in), and MIN over no rows is NULL. (With INOUT, 'nothing yet' would come in, but MIN over no rows would still overwrite it with NULL.)

The Lesson Pages' Own Quick Quizzes

Lesson 6.3 · Database Design & Normalization
  1. A First normal form: 1NF requires one value per cell. A comma list puts two values in one cell, which is why SQL cannot sum or join on them.
  2. C A non-key column that depends on another non-key column: A non-key column determined by another non-key column, like order_id determining cust_email and cust_email determining cust_city. 3NF removes it by moving the customer columns to their own table.
  3. B 2NF: it depends on part of the key: order_date depends on order_id, which is only part of the composite key: a partial dependency, so the table is not in 2NF. That is why the date repeats on every line of an order.
  4. A No: it records what was paid on that order, a different fact from today's price: price_at_time is a fact about the sale, determined by (order_id, book_id). books.price is the current price. They only coincide until the first price change, and then old orders must keep what was actually paid.
  5. B When a measured query is too slow and you have a plan to keep the total in sync: Denormalize only for a measured problem that indexes and better queries did not solve, and only with a plan (a transaction, a trigger or a refresh) that keeps the stored value correct.
Lesson 7.1 · Stored Procedures & Functions
  1. B The mysql command-line client: DELIMITER is a client command. The mysql client uses it to decide where one statement ends before sending it; the server only ever receives the finished CREATE PROCEDURE statement.
  2. C Every book in the table: Inside the routine the name id means the parameter, so the condition is 1 = 1 on every row and all the books come back, with no error or warning.
  3. A READS SQL DATA: The function reads tables and changes nothing, so READS SQL DATA is the honest description. It is also enough to avoid error 1418.
  4. C A stored function: Only a stored function returns a single value that can be used inside an expression, once per row of the query.
  5. A Error 1644 with the message from SIGNAL, and nothing is inserted: The IF check runs first and SIGNAL raises error 1644 with the procedure's own message. The procedure stops there, before either INSERT, so no author and no book are added.

Exit Ticket

  1. Partial dependency: order_id → order_date (moves to orders) or book_title → book_price (moves to books). Reject (order_id, book_title) → quantity: that is the whole key, which is fine.
  2. Check before change: so a refused call leaves the data untouched (statements that already ran are not undone by SIGNAL); SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '...', reported as error 1644.
  3. Function / procedure: a function (one value, inside a SELECT); a procedure (it inserts rows and returns the new id through an OUT parameter, like the project's add_book).

Common Wrong Answers and What They Reveal

  • Q2 A or B. Thinks numbered columns are a dependency problem. They are a list: 1NF.
  • Q3 C. Mixes up "part of the key" (2NF) with "another non-key column" (3NF).
  • Q6 A. Treats data as proof; worth repeating with the worked example's price_at_time.
  • Q7 C. Believes the server reads DELIMITER, or has only seen one-statement bodies.
  • Q9 A. Picks READS SQL DATA by reflex: the function reads no table.
  • Q10 A. Expects MySQL to pick a row: it refuses (1172).
  • Exit ticket 3 "procedure" for both. Ask them to write the SELECT with a CALL inside it: impossible.
