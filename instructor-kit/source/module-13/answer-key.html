Session 13 12 self-check items Confidential

Warm-up

W1
The treasurer's account was granted the reporting role, but every SELECT gives ERROR 1142. What was forgotten? (Lesson 7.4)
The role was never activated: SET DEFAULT ROLE ... TO ... (or SET ROLE in the session). Lesson 7.4's silent Common Mistake 5; Milestone 6 has the line for both accounts.
W2
Someone types mysqldump -u root -p bookstore > backup.sql at the mysql> prompt. What happens? (Lesson 8.1)
ERROR 1064: mysqldump is a separate program, typed in the terminal, not at the mysql> prompt (Lesson 8.1, Common Mistake 1).
W3
A dump of one database restores perfectly on a new laptop, but the web form cannot log in. Why? (Lesson 8.1)
A single-database dump has no accounts and no grants: they live in the mysql system database. Keep them in a script of their own (the project's 05_security.sql).
W4
Which mysqldump option puts the stored procedures into the dump? (Lesson 8.1)
--routines (and --events for events; --single-transaction gives a consistent copy without locking). Milestone 7 uses all three, plus --set-gtid-purged=OFF.
W5
From Rosa's brief: name the tables you would build, and one rule that cannot be a CHECK constraint. (the brief)
members, categories, safety_courses, tools, loans, plus the junction member_courses. Rules that look at other rows cannot be a CHECK: one open loan per tool, at most three per member, no course no chainsaw, nothing while in repair or suspended.

8.2 · Final Project: Design and Build a Database: self-check

Q1
Rosa's rule "a tool can only be out with one person at a time": where does the reference design enforce it?
A) A CHECK constraint on loans
B) UNIQUE (tool_id) on loans
C) In checkout_tool, inside a transaction that locks the tool's row
D) An is_available column on tools, set to 0 on check-out
Why: The rule looks at OTHER rows (is there an open loan for this tool?), so no single-row constraint can hold it. The procedure checks it inside a transaction, after locking the tool's row with SELECT ... FOR UPDATE, so two desk volunteers cannot both lend the drill.
A is wrong: A CHECK sees only the row being written; it cannot look for other open loans.
B is wrong: A tool has many loans over time (all returned but one), so a plain UNIQUE would refuse the second loan ever.
D is wrong: That stores derived data twice; a missed reset makes the flag and the loans disagree (the lesson's FAQ).
Q2
In the reference design, which fact belongs in the junction table member_courses and nowhere else?
A) The member's email
B) completed_on, the date the member finished the course
C) The course's name
D) The member's status
Why: The completion date is a fact about the PAIR (this member, this course): it has no home in members or in safety_courses. That is why the junction table carries its own column.
A is wrong: The email is a fact about the member alone: it lives in members, once.
C is wrong: The course name is a fact about the course: safety_courses.
D is wrong: The status is a fact about the member alone.
Q3
What does the last statement print?
CREATE TABLE riders (id INT PRIMARY KEY, name VARCHAR(20));
CREATE TABLE rides  (rider_id INT, started_on DATE);
INSERT INTO riders VALUES (1, 'Ana'), (2, 'Ben'), (3, 'Cy');
INSERT INTO rides  VALUES (1, '2026-06-03'), (1, '2026-06-09'), (2, '2026-05-28');

SELECT r.name, COUNT(x.rider_id) AS june_rides
FROM riders AS r
LEFT JOIN rides AS x ON x.rider_id = r.id
WHERE x.started_on >= '2026-06-01'
GROUP BY r.id, r.name
ORDER BY r.name;
One row only: Ana with 2 (Ben and Cy are gone)
Why: WHERE runs after the join. Cy has no rides, so x.started_on is NULL and fails the test; Ben's only ride is from May. The LEFT no longer does anything: the lesson's silent Common Mistake 5. Move the date test into ON and all three riders come back (Ben 0, Cy 0).
Q4
What happens when this runs?
CREATE TABLE tools (id INT AUTO_INCREMENT PRIMARY KEY, name VARCHAR(50));
CREATE TABLE loans (
    id      INT AUTO_INCREMENT PRIMARY KEY,
    tool_id INT UNSIGNED NOT NULL,
    CONSTRAINT fk_loans_tool FOREIGN KEY (tool_id) REFERENCES tools (id)
);
A) Both tables are created
B) ERROR 3780 (HY000): Referencing column 'tool_id' and referenced column 'id' in foreign key constraint 'fk_loans_tool' are incompatible.
C) ERROR 1824 (HY000): Failed to open the referenced table 'tools'
D) ERROR 1452 (23000): Cannot add or update a child row
Why: A foreign key and the key it points to must have the same type AND signedness: INT and INT UNSIGNED clash. Pick one key type at the start (the reference uses INT everywhere) and use it for every id and every column that points at one.
A is wrong: tools is created, but loans is refused: its foreign key is incompatible.
C is wrong: 1824 means the parent table does not exist yet; tools exists here.
D is wrong: 1452 is about a ROW whose value has no parent; no row is inserted here.
Q5
Why does the reference 01_schema.sql begin with DROP DATABASE IF EXISTS tool_library;?
A) So the script can be run again from scratch and always gives the same result
B) Because MySQL cannot create a table in a database that has data in it
C) To delete the test rows the constraint tests left behind
D) So that the backup in Milestone 7 is smaller
Why: A re-runnable script is the project's safety net: fix a column, run the whole file again, get a clean, identical database. The rubric's Schema row asks for exactly that ("runs twice without errors"), and Milestone 8 rebuilds everything from the files.
B is wrong: MySQL creates tables in databases that hold data all the time.
C is wrong: The tests run inside a transaction and ROLLBACK removes their rows; nothing is left to delete.
D is wrong: The backup copies whatever is there; the DROP plays no part in it.
Q6
Which of these should NOT be a column in the tool library's tables?
A) tools.replacement_value
B) loans.due_on
C) The number of days a loan is overdue
D) members.joined_on
Why: "Days overdue" depends on today's date and the loan's dates, so it changes every day: compute it in the query (DATEDIFF(@today, due_on)). A stored copy would be wrong tomorrow. The same goes for "available" and "times borrowed".
A is wrong: A fact Rosa gave about each tool; nothing else can compute it.
B is wrong: The due date is decided when the loan is made (normally a week later) and must be kept: it is the basis of "overdue".
D is wrong: A fact about the member, recorded once.
Q7
What does the last statement print?
CREATE TABLE courses (
    id    INT PRIMARY KEY,
    seats INT NOT NULL,
    CONSTRAINT chk_courses_seats CHECK (seats > 0)
);
START TRANSACTION;
INSERT INTO courses VALUES (1, 12);
INSERT INTO courses VALUES (2, 0);
ROLLBACK;
SELECT COUNT(*) AS courses_left FROM courses;
0 (in a column named courses_left)
Why: The second INSERT is refused (3819, the CHECK on seats) and undoes only itself; the transaction stays open with course 1 in it. ROLLBACK then removes course 1 too. That is the lesson's pattern for constraint tests: run them in a transaction, roll it back, and no test row ever stays.
Q8
In which order can 01_schema.sql create these tables without an error?
A) loans, tools, members, categories
B) categories, members, tools, loans
C) tools, categories, loans, members
D) Any order: MySQL checks foreign keys only when rows are inserted
Why: Parents first: a foreign key can only point at a table that already exists (error 1824 otherwise). categories and members point at nothing; tools points at categories; loans points at tools and members, so it comes last. Drop in the reverse order.
A is wrong: loans points at tools and members, which do not exist yet: 1824.
C is wrong: tools points at categories before categories exists: 1824.
D is wrong: CREATE TABLE checks the referenced table immediately (1824).
Q9
Rosa: "Nobody should be able to delete the loan history." How does the reference solution make sure?
A) The loans foreign keys have no ON DELETE rule (refuse), and no account is granted DELETE
B) ON DELETE CASCADE on both foreign keys of loans
C) A CHECK (deleted = 0) constraint on loans
D) The desk volunteers are asked not to delete rows
Why: Two layers: a member or tool with history cannot be deleted (the foreign keys refuse), and neither tl_desk nor tl_reports holds DELETE, so the history rows themselves cannot be removed. Members are suspended instead of deleted.
B is wrong: CASCADE does the opposite: deleting a member would silently delete their loans.
C is wrong: A CHECK cannot stop a DELETE; it only tests rows being written.
D is wrong: A rule only people follow is not enforced; the brief asks the database to enforce it.
Q10
Your overdue query and your "never borrowed" query both return nothing on your test data. What is the most likely problem?
A) Both queries need ORDER BY
B) @today was set to the wrong year
C) MySQL caches empty results
D) The test data has no overdue loan and every member has borrowed something
Why: Empty results prove nothing unless the data contains rows that SHOULD come back. Milestone 3 asks you to plant the edge cases (an overdue loan, a member who never borrowed, a tie, a tool in repair) so a broken query is caught.
A is wrong: ORDER BY changes the order of rows, never whether they appear.
B is wrong: Possible for the overdue query, but it would not empty the "never borrowed" one, which uses no date.
C is wrong: There is no such cache: every query reads the current data.
Q11
The reference uses an ENUM for tool_condition but a table for categories. Give the reason in one sentence.
The library adds and lists categories (they are data); the conditions are a fixed list the code relies on
Why: Both choices are defensible; the rubric rewards writing the reason down. A lookup table is right when the list grows or carries its own facts; an ENUM is fine for a short list that only changes with the application.
Q12
What happens when this runs?
CREATE TABLE gear (
    id        INT AUTO_INCREMENT PRIMARY KEY,
    condition VARCHAR(10)
);
A) ERROR 1064 (42000): You have an error in your SQL syntax ... near 'condition VARCHAR(10)
B) The table is created with a column named condition
C) ERROR 3814 (HY000): ... disallowed function
D) MySQL renames the column to condition_1
Why: CONDITION is a reserved word (used in stored programs), so the parser stops there. Rename it (tool_condition). Backticks would work too, but then every query forever needs them.
B is wrong: A reserved word cannot be a bare column name.
C is wrong: 3814 is about functions inside a CHECK constraint; there is no CHECK here.
D is wrong: MySQL never renames your columns.

Milestones 1 to 3: what a passed check-in looks like

  • Milestone 1: all eight requirements have a home. The reference mapping (lesson, hidden block): 1 to 4 = columns, NOT NULL, UNIQUE, ENUMs, foreign keys; 5 = checkout_tool in a transaction with a row lock; 6 = 03_queries.sql and the view v_open_loans; 7 = roles tl_desk and tl_reports, no DELETE granted, loans foreign keys that refuse deleting a member or tool with history; 8 = mysqldump, a tested restore, scripts kept in version control.
  • Milestone 2: the reference 01_schema.sql runs twice without an error (measured: the second run prints the same six tables). Its four tests are refused with 3819 (chk_loans_due), 3819 (chk_tools_value), 1452 (fk_tools_category) and 1062 (members.uq_members_email), and members_left is 0 after ROLLBACK.
  • Milestone 3: the reference counts are members 8, categories 5, safety_courses 2, member_courses 7, tools 12, loans 16. Edge cases: Victor (8) suspended; Tessa (7) never borrowed; the tile cutter (12) in repair and never lent; the hammer and the socket set tied in Hand Tools; loan 5 returned two days late; loans 13 to 16 still out.

Reading it: nine constraints, named so every error explains itself (the starter's PRIMARY keys are the only unnamed ones: MySQL always calls them PRIMARY). Exit Ticket

  1. A rule for a procedure: one open loan per tool, at most three per member, the chainsaw course, not while in repair, not while suspended. Each needs other rows (open loans, the member's status, member_courses) and a CHECK sees only the row being written.
  2. Re-runnable: the first line DROP DATABASE IF EXISTS tool_library; then CREATE DATABASE and USE, and every table created again (or DROP TABLE IF EXISTS, children first).
  3. A test: INSERT INTO loans (tool_id, member_id, loaned_on, due_on) VALUES (1, 1, '2026-06-10', '2026-06-03'); must give ERROR 3819 (HY000): Check constraint 'chk_loans_due' is violated. (or the learner's own constraint name). Inside a transaction, then ROLLBACK.

Common Wrong Answers and What They Reveal

  • Q1 B (UNIQUE (tool_id)). Sees the rule as a property of the table, not of OPEN loans. Ask how many loans the drill has had (four). The lesson's Exercise 4 shows the clever version (a generated column), after Milestone 5.
  • Q3 "three rows". Expects LEFT JOIN to protect the rows whatever WHERE does: the lesson's silent mistake. Send them to edge_cases_starter.sql TODO 3.
  • Q6 B (due_on). Confuses "decided once" with "computed": the due date is a fact recorded at check-out; overdue is computed from it.
  • Q8 D (any order). Thinks foreign keys are checked only on INSERT. Run Mistake 4 again: 1824 at CREATE time.
  • Q9 B (CASCADE). Reads ON DELETE CASCADE as "protects". It deletes the history: the opposite of Rosa's requirement 7.
  • Q10 A or B. Looks for a syntax cause for an empty result. The data has to contain what the query should find.
