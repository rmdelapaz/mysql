Lesson

8.2

Final Project: Design and Build a Database

By the end you can
  • Turn a written brief into entities, relationships and business rules, and draw them as a diagram
  • Build a normalized schema in a re-runnable script, with keys, foreign keys and CHECK constraints that you have tested
  • Answer business questions with joins, GROUP BY, CTEs and window functions, using a fixed report date
  • Enforce rules that span several rows in a stored procedure with a transaction
  • Secure the database with roles and least-privilege accounts, then back it up and prove the backup restores

Today: the first two. Session 14: the other three.

The brief in one page

Rosa Delgado's Maple Street Tool Library (full text on the lesson page, "The Brief"). Her eight requirements, in short:

  1. Members: name, email (one account per email), joined date, active or suspended.
  2. About a dozen tools: name, one category, condition (good, fair, out for repair), replacement value, date acquired.
  3. Safety courses: power tools need Power Tools Basics, the chainsaw needs Chainsaw Safety; who finished which course, and when.
  4. A loan: one tool, one member, out, due (normally a week later), back.
  5. Rules: one borrower per tool at a time; nothing out while in repair; suspended members cannot borrow; three tools at most; no course, no chainsaw.
  6. Every Saturday: what is on the shelf, what is overdue and whom to email, which tools are popular, how busy each month was.
  7. Desk volunteers check tools out and in through a web form; the treasurer only reads reports; nobody may delete the loan history.
  8. "If the laptop dies, I do not want to start over."

Hand in: 01_schema.sql, 02_data.sql, 03_queries.sql, 04_logic.sql, 05_security.sql, a tested backup file and README.md. Timeline: Milestones 1 to 3 today, 4 at home, 5 to 7 in Session 14, 8 and the README at home; due one week after Session 14.

Key ideas
  • Nouns become tables, verbs become relationships. Ask "one or many?" in both directions. Many-to-many needs a junction table; this one carries its own fact (completed_on).
  • Every rule gets a home. One value: a type or a constraint (NOT NULL, UNIQUE, ENUM, CHECK). Between tables: a foreign key. Looks at other rows: the procedure that writes, inside a transaction.
  • No derived data. Overdue, days late, available, times borrowed: compute them in queries.
  • A CHECK must give the same answer forever: compare columns of the same row, never CURDATE() (error 3814).
  • Build scripts are re-runnable: DROP DATABASE IF EXISTS first, parents first, children last, every constraint named.
  • A constraint is proven when a statement that breaks it is refused. Test inside a transaction and roll it back.
  • Test data is a design tool: plant the edge cases (suspended, never borrowed, in repair, never lent, a tie, overdue, late) so a broken query shows.
  • SOURCE looks in the folder the client was started in. Start mysql inside your tool-library folder so SOURCE 01_schema.sql inside 02_data.sql works.

Starter schema checklist (the rubric looks for these):

  • ☐ Every table has a primary key; the junction table's key is the pair of foreign keys
  • ☐ Every foreign key is named, has the same type as its target, and a deliberate ON DELETE rule (or none = refuse)
  • ☐ Required facts NOT NULL; unique values (email, category name) UNIQUE
  • ☐ Closed lists: ENUM or a lookup table, and I can say why
  • ☐ Money DECIMAL, dates DATE, searched text a sensible VARCHAR
  • ☐ At least two CHECKs for single-row rules
  • ☐ Indexes on the columns my Saturday queries filter and join on
  • ☐ No derived data; snake_case, plural table names, no reserved words

Worked example: a constraint test block

The lesson's pattern, run on the reference schema. The parents need one row each first, inside the transaction:

START TRANSACTION;

INSERT INTO categories (name) VALUES ('Hand Tools');
INSERT INTO members (first_name, last_name, email, joined_on)
VALUES ('Test', 'Member', 'test@example.org', '2026-01-01');
INSERT INTO tools (name, category_id, replacement_value, acquired_on)
VALUES ('Test hammer', 1, 15.00, '2026-01-01');

Then one statement per rule; each must be refused:

INSERT INTO tools (name, category_id, replacement_value, acquired_on)
VALUES ('Free saw', 1, 0, '2026-01-01');
ERROR 3819 (HY000): Check constraint 'chk_tools_value' is violated.
INSERT INTO members (first_name, last_name, email, joined_on)
VALUES ('Second', 'Account', 'test@example.org', '2026-02-01');
ERROR 1062 (23000): Duplicate entry 'test@example.org' for key 'members.uq_members_email'

Last, ROLLBACK and a count: nothing stays behind.

ROLLBACK;

SELECT COUNT(*) AS members_left FROM members;
+--------------+
| members_left |
+--------------+
|            0 |

Glossary

TermMeaning
briefThe client's description of what they need, in their words; the starting point of a design
entityA thing with its own facts (member, tool, loan): becomes a table
junction tableA table that links two others in a many-to-many relationship; its key is the pair of foreign keys
business ruleA rule from the brief ("three tools at most"); it needs a home: a constraint, a foreign key or a procedure
derived dataA value that can be computed from other data (days overdue); computed in queries, not stored
re-runnable scriptA script that rebuilds everything from scratch each time it runs (DROP DATABASE IF EXISTS first)
constraint testA statement that breaks a rule on purpose; the constraint is proven when MySQL refuses it
edge caseTest data at the boundary (never borrowed, overdue, a tie) that exposes a broken query
report dateA fixed date in @today so results can be checked; production sets it to CURDATE()
reserved wordA word SQL itself uses (condition, order, group, rank, key): not a column name
