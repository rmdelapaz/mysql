Session 13: Final Project Kickoff and Studio I

How to run the first final-project studio. Launch the Maple Street Tool Library brief and its rubric, show the build mistakes that cost the most time, and get every learner from Rosa's eight requirements to a checked design, a re-runnable schema whose constraints are proven by failing tests, and test data that plants the edge cases.

1 lesson (first half) 3 hrs session Lesson 8.2 · Milestones 1–3 Session 13 of 14 · Part 2

How to Use This Guide

  • Session 13 is a studio: one lesson (8.2, the final project) and most of the room's time spent building. The shape: warm-up → kickoff (the brief, the files, the rubric) → a short frame and live demo → Milestone 1 in the room → a guided lab on the bookstore → Milestones 2 and 3 in the room. You circulate and run short check-ins at the end of each milestone instead of teaching new material.
  • Type, do not paste, in the demo. Every SQL block below was run to produce the output printed under it, on MySQL 9.7 (the lesson's own blocks were run as one session, exactly as the page shows them, and match the page). Read error numbers aloud from the left.
  • The lesson page is the brief and the reference. Keep lesson_final_project.html open in a tab: The Brief, Milestones and Timeline, From Requirements to Tables, How Your Work Is Assessed, Common Mistakes. Do not open the reference solutions on the projector before learners have attempted a milestone; the page hides them on purpose.
  • The assessment, the rubric with scoring guidance and the instructor answer notes with real reference numbers are in final-assessment.html at the kit root (Part 2 section). Print the rubric for learners from there.
  • Session 14 continues the same project (Milestones 5 to 7 in the room, then the showcase and Lesson 8.3). Teal blocks are hands-on, amber blocks are watch-outs.
The #1 risk of Session 13: a design nobody checked

A learner who starts typing CREATE TABLE before every requirement has a home spends Session 14 rebuilding. The two most expensive design errors are (1) trying to put a rule that looks at other rows into a CHECK (it cannot work, and the learner discovers that at Milestone 5) and (2) storing derived data (an is_available or times_borrowed column) that the queries then trust. The defense: nobody starts Milestone 2 without a passed design check-in (two minutes: point at each of Rosa's eight requirements and say where it lives). Keep a tally on the studio tracker below; visit the learners without a tick first.

Final Project: Design and Build a Database

140 min (of 240)
Objectives (from the lesson page)
  • Turn a written brief into entities, relationships and business rules, and draw them as a diagram
  • Build a normalized schema in a re-runnable script, with keys, foreign keys and CHECK constraints that you have tested
  • Answer business questions with joins, GROUP BY, CTEs and window functions, using a fixed report date
  • Enforce rules that span several rows in a stored procedure with a transaction
  • Secure the database with roles and least-privilege accounts, then back it up and prove the backup restores

Today covers the first two objectives in the room (design, schema with tested constraints) and starts the third at home (the Saturday queries). Session 14 covers the last two.

Mental model to say (5 minutes)

Use the lesson's four moves, pointing at the board's empty table: "Underline the nouns. Things with their own facts become tables; facts about a thing become columns. Read the verbs and ask 'one or many?' in both directions: one-to-many puts the foreign key on the many side; many-to-many needs a junction table, and here the junction carries its own fact, the completion date."

Then the move that decides the project: "Sort the rules by where they can live. A rule about ONE value, a type or a constraint: NOT NULL, UNIQUE, ENUM, CHECK. A rule BETWEEN tables, a foreign key. A rule that has to LOOK AT OTHER ROWS (only one open loan per tool, at most three per member) can never be a CHECK: it goes in the procedure that creates loans, inside a transaction." Fill in two rows of the board table together (requirement 2: tools columns, ENUM, CHECK > 0; requirement 5: checkout_tool), then leave the rest for the studio.

Last: "Leave out what can be calculated. Overdue, days late, available: they depend on today or on other rows, so they are computed in queries, never stored."

Live demo (you type, they follow; 15 minutes)

The lesson's Common Mistakes, typed in the mysql> client (any folder; the scratch database is dropped at the end). Ask for a prediction before each block. The outputs are the real ones; they match the lesson page.

  1. A scratch database for the mistakes (1m). "Before you build Rosa's database, five mistakes that cost the most time in projects like this. I make them in a scratch database so nothing collides with your project." 
    CREATE DATABASE pitfall_demo;
USE pitfall_demo;
    Database changed
  2. Mistake 1: a reserved word (2m). Ask first: "tool condition is in the brief. What could go wrong with this column?" Then run it. 
    CREATE TABLE demo_tools (
    id        INT AUTO_INCREMENT PRIMARY KEY,
    condition VARCHAR(10)
);
    ERROR 1064 (42000): You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near 'condition VARCHAR(10)
)' at line 3
    CONDITION is reserved (stored programs use it). Read where the parser stopped: near 'condition. Fix: tool_condition. Same trap: order, group, rank, key.
  3. Mistake 2: a foreign key whose type does not match (3m). "A parent table, then a loans table whose tool_id is BIGINT." 
    CREATE TABLE demo_tools (id INT AUTO_INCREMENT PRIMARY KEY, name VARCHAR(50));

CREATE TABLE demo_loans (
    id      INT AUTO_INCREMENT PRIMARY KEY,
    tool_id BIGINT NOT NULL,
    FOREIGN KEY (tool_id) REFERENCES demo_tools (id)
);
    ERROR 3780 (HY000): Referencing column 'tool_id' and referenced column 'id' in foreign key constraint 'demo_loans_ibfk_1' are incompatible.
    INT and BIGINT clash; so do INT and INT UNSIGNED. Decide one key type now and write it in the design notes.
  4. Mistake 3: today's date in a CHECK (2m). "Due dates must be in the future. Sounds like a CHECK, right?" Let them say yes, then run it. 
    CREATE TABLE demo_loans (
    id     INT AUTO_INCREMENT PRIMARY KEY,
    due_on DATE NOT NULL,
    CONSTRAINT chk_due_future CHECK (due_on >= CURDATE())
);
    ERROR 3814 (HY000): An expression of a check constraint 'chk_due_future' contains disallowed function: curdate.
    A CHECK must give the same answer for a row forever. Compare columns of the same row (due_on >= loaned_on) and put time rules in the procedure.
  5. Mistake 4: the child before the parent (2m). "The course records table, written before the members table." 
    CREATE TABLE demo_courses_done (
    member_id INT NOT NULL,
    FOREIGN KEY (member_id) REFERENCES demo_members (id)
);
    ERROR 1824 (HY000): Failed to open the referenced table 'demo_members'
    Parents first, junction and history tables last; drop in the reverse order.
  6. Mistake 5: the silent one (4m). "June loans per member, members with none should show 0." Ask for a prediction: how many rows? Most say three. 
    CREATE TABLE demo_members (id INT PRIMARY KEY, name VARCHAR(50));
CREATE TABLE demo_member_loans (member_id INT, loaned_on DATE);
INSERT INTO demo_members VALUES (1, 'Rosa'), (2, 'Kevin'), (3, 'Tessa');
INSERT INTO demo_member_loans VALUES (1, '2026-06-06'), (2, '2026-05-02');

SELECT m.name, COUNT(l.member_id) AS june_loans
FROM demo_members AS m
LEFT JOIN demo_member_loans AS l ON l.member_id = m.id
WHERE l.loaned_on >= '2026-06-01'
GROUP BY m.id, m.name
ORDER BY m.name;
    +------+------------+
| name | june_loans |
+------+------------+
| Rosa |          1 |
+------+------------+
    Kevin and Tessa vanished, with no error. WHERE runs after the join and throws away the NULL rows. This is the mistake the rubric's Queries row is most often lost on.
  7. The fix: the condition moves into ON (1m). "Conditions on the right-hand table of a LEFT JOIN belong in ON." 
    SELECT m.name, COUNT(l.member_id) AS june_loans
FROM demo_members AS m
LEFT JOIN demo_member_loans AS l
       ON l.member_id = m.id AND l.loaned_on >= '2026-06-01'
GROUP BY m.id, m.name
ORDER BY m.name;

DROP DATABASE pitfall_demo;
    +-------+------------+
| name  | june_loans |
+-------+------------+
| Kevin |          0 |
| Rosa  |          1 |
| Tessa |          0 |
+-------+------------+
    The DROP at the end removes the scratch database. Leave the four error numbers on the board: 1064, 3780, 3814, 1824.

Three mistakes to expect, and how to coach each
  • Rules that look at other rows written as CHECKs. "CHECK ((SELECT COUNT(*) ...) < 3)" fails (subqueries are not allowed in a CHECK). Coach with the board's last line: "one row or other rows?" and move the rule to the Milestone 5 procedure, written down now in the design notes.
  • Scripts that only run once. A learner fixes a column with ALTER TABLE at the prompt and the script no longer matches the database. Coach: "change the file, run the file": the rubric's Schema row and Milestone 8's rebuild depend on it.
  • Happy-path test data. Every member borrowed, nothing overdue. Coach with the edge-cases lab and Q10: "which of your queries would return nothing? Is that the right answer, or is the data hiding a bug?"
Checks for understanding

Ask these out loud during the check-ins:

  • Where does "at most three tools at once" live, and why not a CHECK? Answer: in checkout_tool, inside a transaction: it counts other rows, and a CHECK sees only the row being written.
  • Which table carries completed_on, and why there? Answer: member_courses: it is a fact about the pair member + course.
  • Why does a failed test INSERT not stop your test block? Answer: a failed statement only undoes itself; the transaction stays open until ROLLBACK.
  • Which of your tables would you create last, and drop first? Answer: loans (it points at tools and members), and member_courses.

Workbook self-check, items Q1 to Q12 (learners do them at home, after Milestone 3).

Answers: Q1 C) In checkout_tool, inside a transaction that locks the tool's row; Q2 B) completed_on, the date the member finished the course; Q3 One row only: Ana with 2 (Ben and Cy are gone); Q4 B) ERROR 3780 (HY000): Referencing column 'tool_id' and referenced column 'id' in foreign key constraint 'fk_loans_tool' are incompatible.; Q5 A) So the script can be run again from scratch and always gives the same result; Q6 C) The number of days a loan is overdue; Q7 0 (in a column named courses_left); Q8 B) categories, members, tools, loans; Q9 A) The loans foreign keys have no ON DELETE rule (refuse), and no account is granted DELETE; Q10 D) The test data has no overdue loan and every member has borrowed something; Q11 The library adds and lists categories (they are data); the conditions are a fixed list the code relies on; Q12 A) ERROR 1064 (42000): You have an error in your SQL syntax ... near 'condition VARCHAR(10). Differentiation

Support: learners who struggle with the design start from the lesson's reference design table (open the hidden block) and write the "why" for each row in their own words: that is honest Design work at the "meets" level. In Milestone 2, pair them for the test block. A learner far behind can type the reference 01_schema.sql and then write their OWN tests (the tests are where the understanding shows).

Stretch: the lesson's Exercise 4 idea early (a generated column that makes "one open loan per tool" a UNIQUE constraint); the FAQ's alternative clinic brief as a second design; a lookup table for tool conditions instead of the ENUM, with the trade-off written down.

Closing

Exit ticket (3 questions, no notes, 4 minutes)

On the slide. Learners answer in the workbook's Exit Ticket box or on a sticky note. Sort into "got it" / "not yet" before Session 14: question 2's pile is the list for the Session 14 warm-up.

  1. Name one of Rosa's rules that must live in a procedure, and say why it cannot be a CHECK. Answer: any of: one open loan per tool, at most three per member, course before the chainsaw, not while in repair, not while suspended: each looks at other rows (or another table), and a CHECK sees only the row being written.
  2. Your 01_schema.sql ran once. What must be true for it to run a second time without an error? Answer: it starts with DROP DATABASE IF EXISTS tool_library; (or drops its tables, children first) and creates everything again.
  3. Write one test statement that proves a CHECK on your loans table works. What should MySQL answer? Answer: for example an INSERT with due_on before loaned_on; MySQL must answer ERROR 3819 ... Check constraint 'chk_loans_due' is violated.

If You Run Long or Short

Running long: what to protect and what to cut first
  • Protect: a passed design check-in for every learner; 01_schema.sql running twice with its tests; the demo's Mistake 5.
  • Cut first (saves 15m): the guided lab. Hand out the gift-cards files as homework; the Milestone 2 mini-demo shows the test pattern.
  • Cut second (saves 6m): demo Mistakes 2 and 4. Point at the lesson page and the trap table.
  • Cut third (saves 25m): the Milestone 3 studio: it becomes homework (it is mostly typing). Make sure everyone has seen the edge-case list on the slide.
Running short: what to add
  • Start Milestone 4 together: query 1 (on the shelf now) with NOT EXISTS, checked by hand against the data (7 of 12 tools for the reference data).
