4.3 · Joins: self-check

Q1
Eight customers placed 12 orders; Carol and Hank placed none. How many rows does this return?
SELECT c.first_name, o.id
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id;
A) 8
B) 12
C) 14
D) 96
Why: A LEFT JOIN returns every matching pair (12 orders, each with its customer) plus one row for each customer with no partner (Carol, Hank), padded with NULL: 14.
A is wrong: One row per customer would need GROUP BY; Alice alone has three orders.
B is wrong: 12 is the inner join: it drops Carol and Hank.
D is wrong: 96 (8 × 12) is a cross join: a join without its ON condition.
Q2
Which query lists the books that have never been sold?
A) FROM books b LEFT JOIN order_items oi ON oi.book_id = b.id WHERE oi.id IS NULL
B) FROM books b JOIN order_items oi ON oi.book_id = b.id WHERE oi.id IS NULL
C) FROM books b LEFT JOIN order_items oi ON oi.book_id = b.id WHERE b.id IS NULL
D) FROM order_items oi LEFT JOIN books b ON oi.book_id = b.id WHERE b.id IS NULL
Why: The anti-join: keep every book (LEFT JOIN from books), then keep only the rows where the right side found nothing (its primary key is NULL). The answer is The Catcher in the Rye and The Great Gatsby.
B is wrong: An inner join has no unmatched rows, so the IS NULL test keeps nothing.
C is wrong: b.id is never NULL: every row starts from a real book.
D is wrong: This keeps order lines whose book is missing; the foreign key makes that impossible, so it returns nothing.
Q3
Alice (customer 1) placed three orders. What does this print?
SELECT COUNT(*) AS rows_returned
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.id
WHERE o.customer_id = 1;
4 (one row per order line, not per order)
Why: Joining order_items makes one row per order LINE: order 1 has two lines, orders 2 and 8 one each. Ask "what does one row of this join stand for?" before counting (COUNT(DISTINCT o.id) gives 3).
Q4
What happens when this runs?
SELECT id, order_date, first_name
FROM orders
JOIN customers ON orders.customer_id = customers.id;
A) It returns 12 rows, using the order's id
B) ERROR 1052 (23000): Column 'id' in field list is ambiguous
C) ERROR 1054 (42S22): Unknown column 'id' in 'field list'
D) It returns 96 rows: a cross join
Why: Both orders and customers have an id, and MySQL will not guess which one you mean. Qualify it: orders.id (or o.id with an alias). first_name and order_date exist in only one table each, so they are fine.
A is wrong: MySQL never guesses between two tables' columns.
C is wrong: 1054 is a column that exists nowhere (or a table name after an alias); here it exists twice.
D is wrong: The ON clause is there: this is an inner join.
Q5
Carol (3) has no orders; Dave (4) has two. What does this print?
SELECT c.first_name, COUNT(o.id) AS orders
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
WHERE c.id IN (3, 4)
GROUP BY c.id, c.first_name
ORDER BY c.id;
Carol | 0 and Dave | 2
Why: The LEFT JOIN gives Carol one row padded with NULL. COUNT(o.id) counts only the non-NULL order ids, so Carol gets 0. COUNT(*) would have counted her padded row and said 1 (the lesson's Mistake 4).
Q6
This was meant to list every author with their in-stock books. Isaac Asimov (no books) and the authors of the two out-of-stock books are missing. Why?
SELECT a.name, b.title
FROM authors AS a
LEFT JOIN books AS b ON b.author_id = a.id
WHERE b.in_stock = TRUE
ORDER BY a.id, b.title;
A) LEFT JOIN cannot be combined with WHERE
B) in_stock is a BOOLEAN, so TRUE must be written as 1
C) The ORDER BY removes the NULL rows
D) The WHERE runs after the join: for the padded rows b.in_stock is NULL, so the LEFT JOIN behaves like an inner join
Why: A condition on the right table belongs in ON when every left row must stay: LEFT JOIN books b ON b.author_id = a.id AND b.in_stock = TRUE. Then Asimov, Fitzgerald and Salinger appear with NULL titles (the lesson's Mistake 3).
A is wrong: WHERE is fine after a LEFT JOIN; it just filters the joined rows, NULL-padded ones included.
B is wrong: TRUE and 1 are the same in MySQL.
C is wrong: ORDER BY only sorts.

4.3 · Joins: predict, then run

P1
Predict the output, then run it.
SELECT COUNT(*) AS rows_returned
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id;
+---------------+
| rows_returned |
+---------------+
|            14 |
+---------------+
Why: Twelve order rows (each with its customer) plus Carol and Hank with NULLs: 14.
P2
Predict the output, then run it.
SELECT c.first_name, COUNT(*) AS n
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
WHERE c.id IN (3, 6)
GROUP BY c.id, c.first_name
ORDER BY c.id;
+------------+---+
| first_name | n |
+------------+---+
| Carol      | 1 |
| Frank      | 2 |
+------------+---+
Why: Carol has no orders, but the LEFT JOIN gives her one padded row, and COUNT(*) counts rows: 1 (COUNT(o.id) would say 0). Frank has two orders: 2.

Part 1 Review: self-check

Q7
Review (Lesson 2.2): which column type fits a book's price?
A) DECIMAL(8, 2)
B) FLOAT
C) VARCHAR(10)
D) INT
Why: DECIMAL stores exact decimal values: right for money. The course stores every price as DECIMAL(8, 2).
B is wrong: FLOAT is approximate: sums of prices can be off by fractions of a cent.
C is wrong: Text accepts "about 26" and cannot be summed or compared as a number (Session 1's order sheet).
D is wrong: INT has no cents (unless you store cents, a different design).
Q8
Review (Lessons 2.2 and 2.3): what happens?
INSERT INTO customers (first_name, last_name, email)
VALUES ('Ivy', 'Lane', 'alice@example.com');
ERROR 1062 (23000): Duplicate entry 'alice@example.com' for key 'customers.email'
Why: customers.email is UNIQUE and alice@example.com belongs to Alice: the INSERT is refused and nothing is added. UNIQUE is a constraint on a column, like the PRIMARY KEY on id.
Q9
Review (Lesson 3.1): how many books does this count?
SELECT COUNT(*) FROM books WHERE title LIKE 'The %';
A) 2
B) 3
C) 4
D) 11
Why: 'The %' means "starts with The and a space": The Great Gatsby, The Hobbit, The Catcher in the Rye. LIKE ignores case with the course's collation.
A is wrong: Count again: three titles start with "The ".
C is wrong: To Kill a Mockingbird starts with "To", not "The".
D is wrong: 11 is every book; the pattern is a real filter.
Q10
Review (Lessons 3.2 and 3.3): in which order must these clauses be written?
A) SELECT, FROM, GROUP BY, WHERE, HAVING, ORDER BY, LIMIT
B) SELECT, FROM, WHERE, ORDER BY, GROUP BY, HAVING, LIMIT
C) SELECT, FROM, WHERE, HAVING, GROUP BY, ORDER BY, LIMIT
D) SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT
Why: The written order (Some Frogs Will Gladly Hop Over Logs). The run order differs: FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT; with a join, the JOINs belong to FROM.
A is wrong: WHERE comes before GROUP BY: it picks rows before the piles are made.
B is wrong: ORDER BY comes after grouping (it sorts the result).
C is wrong: HAVING after GROUP BY: written the other way it is error 1064.
Q11
Review (Lesson 3.4): what does this print?
SELECT title
FROM books
WHERE price = (SELECT MIN(price) FROM books);
Pride and Prejudice (one row)
Why: The inner query finds the lowest price (7.99); the outer query returns the row(s) with it. If two books tied, both would come back, unlike ORDER BY price LIMIT 1.
Q12
Review (Lessons 4.1 and 4.2): what is the bookstore's order_items table?
A) A one-to-one extension of orders
B) A copy of books with a quantity column
C) A junction table linking orders and books (many-to-many), carrying facts about each link: quantity and price_at_time
D) A self-referencing table
Why: An order holds many books and a book appears in many orders: two foreign keys in a third table. Its extra columns describe the link (this book in this order). Deleting an order cascades to its lines; deleting a sold book is RESTRICTed.
A is wrong: An order has MANY lines.
B is wrong: It stores book_id, not a copy of the book; price_at_time is history, not duplication.
D is wrong: That is employees (manager_id points at employees).

The Lesson Page's Own Quick Quiz

Lesson 4.3 · Joins
  1. A 11: An inner join returns one row per matching pair. Every book has exactly one author, so there are 11 pairs, and Asimov, with no partner, is left out.
  2. C FROM customers c LEFT JOIN orders o ON o.customer_id = c.id WHERE o.id IS NULL: The LEFT JOIN keeps every customer and fills the order columns with NULL when there is none; WHERE o.id IS NULL keeps exactly those customers.
  3. B The join gave him one row of NULLs, and COUNT(*) counts rows: The LEFT JOIN gives Asimov one row padded with NULLs, and COUNT(*) counts rows. COUNT(b.id) counts only non-NULL book ids and returns 0.
  4. B Tom, Lena and Ben, each with Priya as manager: It is a self-join: m plays the manager. The rows where the manager is Priya are her three reports, Tom, Lena and Ben (Ben is inactive, but nothing filters on that).
  5. A In the ON clause, after the key condition: In the ON clause the condition only decides which orders match, so customers without a May order still appear with NULLs. In WHERE it would remove them, turning the LEFT JOIN into an inner join.

Exit Ticket

  1. JOIN vs LEFT JOIN: JOIN returns one row per customer-order pair (12 rows; Carol and Hank, who never ordered, are not there). LEFT JOIN also keeps every customer without an order, once, with NULL in the order columns (14 rows).
  2. Hardest task: a reflection. Tally by task: many A1 answers point to Lesson 2.2 and 4.2 (constraints, keys); B4 to the NULL rule (3.3); B7 and B8 to the anti-join and LEFT JOIN with GROUP BY (4.3). If Part 2 follows, open Session 8's refresher with the most frequent one.
  3. Use and practice: a reflection; read them for the course evaluation.

Common Wrong Answers and What They Reveal

  • Q1 B (12). Thinks LEFT JOIN returns the same rows as JOIN when "every order has a customer". It is the customers without orders that LEFT JOIN adds.
  • Q2 B. Uses IS NULL after an inner join: has the pattern's words but not its logic. Draw the NULL-padded rows.
  • Q3 3. Counts orders, not order lines: the fan-out habit is not there yet. The board question is the fix.
  • Q6 B or C. Looks for a syntax cause of a logic bug. Run it without the WHERE and watch the NULL rows appear.
  • Q10 A or C. The written order is still shaky; HAVING before GROUP BY is a 1064 they will meet again.
  • Q12 A or B. Has not connected order_items with junction tables. Session 6's relationship map is the remedy.
