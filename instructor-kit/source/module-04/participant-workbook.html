Lessons

3.1

WHERE Clauses, Operators & Filtering

By the end you can
  • Filter rows by numbers, text and dates with the comparison operators (=, !=, <, >, <=, >=)
  • Combine conditions with AND, OR and NOT, and use parentheses to say exactly what you mean
  • Match lists, ranges and text patterns with IN, BETWEEN and LIKE
  • Find missing values with IS NULL and explain why = NULL finds nothing
  • Spot the silent filtering mistakes (missing NULL rows, AND/OR mix-ups) and fix error 1054
  • Save a set of reusable searches in a .sql script
Key ideas
  • WHERE tests every row; only rows where the test is true are kept. False and unknown (NULL) are dropped.
  • Comparisons = != < > <= >= work on numbers, dates ('YYYY-MM-DD') and text (case-insensitive with _ci collations).
  • AND narrows, OR widens, NOT flips. AND is evaluated before OR: when you mix them, add parentheses.
  • IN a list · BETWEEN an inclusive range · LIKE a pattern (% any characters, _ exactly one).
  • NULL is unknown: test it with IS NULL / IS NOT NULL, never = NULL. !=, NOT IN and NOT LIKE silently drop NULL rows: add OR col IS NULL when you want them. Never a NULL inside NOT IN.
  • Date-and-time columns: a half-open range, >= start AND < next_start.
  • Count first: say how many rows you expect before you run a filter.
Worked example: a flyer list, built and broken

A flyer for customers who joined in January and live in New York or Chicago, plus anyone whose city is unknown (the shop will ask them). First, every condition as a column, to see each row's answers:

SELECT first_name, city, created_at,
       created_at < '2026-02-01'          AS january,
       city IN ('New York', 'Chicago')    AS east_midwest
FROM customers
ORDER BY id;

| first_name | city        | created_at          | january | east_midwest |
+------------+-------------+---------------------+---------+--------------+
| Alice      | New York    | 2026-01-04 10:15:00 |       1 |            1 |
| Bob        | Chicago     | 2026-01-06 14:02:00 |       1 |            1 |
| Carol      | Los Angeles | 2026-01-09 09:40:00 |       1 |            0 |
| Dave       | Houston     | 2026-01-12 16:25:00 |       1 |            0 |

| Hank       | NULL        | 2026-02-10 19:12:00 |       0 |         NULL |
+------------+-------------+---------------------+---------+--------------+

Now the filter, with the OR in parentheses:

SELECT first_name, city
FROM customers
WHERE created_at < '2026-02-01'
  AND (city IN ('New York', 'Chicago') OR city IS NULL)
ORDER BY first_name;
+------------+----------+
| first_name | city     |
+------------+----------+
| Alice      | New York |
| Bob        | Chicago  |
| Eve        | NULL     |
| Frank      | New York |
+------------+----------+

The same conditions without the parentheses. AND runs first, so OR city IS NULL stands on its own and lets Hank in, although he joined in February:

SELECT first_name, city
FROM customers
WHERE created_at < '2026-02-01'
  AND city IN ('New York', 'Chicago') OR city IS NULL
ORDER BY first_name;
+------------+----------+
| first_name | city     |
+------------+----------+
| Alice      | New York |
| Bob        | Chicago  |
| Eve        | NULL     |
| Frank      | New York |
| Hank       | NULL     |
+------------+----------+

3.2

Sorting & Limiting Results

By the end you can
  • Sort results with ORDER BY on one or more columns or expressions, each ascending or descending
  • Predict where NULL values land in a sort and move them to the end
  • Take the top N rows with LIMIT, and add a tie-breaker so the result is always the same
  • Split a result into pages with LIMIT ... OFFSET, and explain when keyset pagination is better
  • Read and fix the errors MySQL raises for misplaced or malformed ORDER BY and LIMIT clauses
Key ideas
  • A table has no order: without ORDER BY, row order is not guaranteed.
  • ORDER BY is ascending by default; DESC belongs only to the column before it. Extra columns break ties.
  • Sort by expressions, aliases and CASE ranks; avoid column numbers in saved queries.
  • NULLs sort first ascending, last descending; ORDER BY col IS NULL, col puts them last (MySQL has no NULLS LAST).
  • LIMIT n OFFSET m skips m rows and keeps n; it runs last. Page N = OFFSET (N - 1) × size, computed before the query.
  • Every ORDER BY that feeds a LIMIT ends with a unique column. Count pages with a separate COUNT(*).
  • Keyset pagination (WHERE id > last_seen ORDER BY id LIMIT n) stays fast on huge tables.
Worked example: pages of recent books, two ways

"Recently published" in pages of three, newest first, with id as the tie-breaker. Page 1:

SELECT title, published
FROM books
ORDER BY published DESC, id
LIMIT 3;
+-----------------------+------------+
| title                 | published  |
+-----------------------+------------+
| Dune                  | 1965-08-01 |
| To Kill a Mockingbird | 1960-07-11 |
| Lord of the Rings     | 1954-07-29 |
+-----------------------+------------+

Page 2 the keyset way: the rows published before the last one we showed (Lord of the Rings, 1954-07-29):

SELECT title, published
FROM books
WHERE published < '1954-07-29'
ORDER BY published DESC, id
LIMIT 3;
+------------------------+------------+
| title                  | published  |
+------------------------+------------+
| Fahrenheit 451         | 1953-10-19 |
| The Catcher in the Rye | 1951-07-16 |
| 1984                   | 1949-06-08 |
+------------------------+------------+

And the OFFSET way. Same rows; the keyset version stays fast however deep the pages go:

SELECT title, published
FROM books
ORDER BY published DESC, id
LIMIT 3 OFFSET 3;
+------------------------+------------+
| title                  | published  |
+------------------------+------------+
| Fahrenheit 451         | 1953-10-19 |
| The Catcher in the Rye | 1951-07-16 |
| 1984                   | 1949-06-08 |
+------------------------+------------+

Glossary

TermMeaning
WHEREA test run on every row; only rows where it is true are kept
three-valued logicA condition is true, false or unknown (NULL); unknown is dropped
IN / BETWEEN / LIKEA list / an inclusive range / a pattern (% any characters, _ one)
IS NULLThe only correct test for a missing value
<=>MySQL's NULL-safe equals: two NULLs count as equal
half-open range>= start AND < next_start: never misses or double-counts a timestamp
precedenceThe order operators are evaluated: comparisons, NOT, AND, then OR
sort key / tie-breakerA column in ORDER BY / an extra, unique one that decides ties
LIMIT / OFFSETHow many rows to keep / how many to skip first
keyset paginationAsk for the rows after the last one seen (WHERE id > 57) instead of skipping
