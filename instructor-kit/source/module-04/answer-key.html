Warm-Up: Session 3

Not graded.

W1
Which type stores a book's price?
A) FLOAT
B) DECIMAL(8, 2)
C) VARCHAR(10)
D) INT
Why: Money is exact: DECIMAL. FLOAT's binary fractions add up to crumbs (the types lab: 556.9499866962433).
W2
An INSERT gives the NOT NULL column email the value NULL. Which error?
A) 1364
B) 1062
C) 1048
D) 3819
Why: 1048 for an explicit NULL; 1364 when the column is left out.
W3
What does the second line say after this UPDATE?
CREATE TABLE w3 (id INT PRIMARY KEY, price DECIMAL(6, 2));
INSERT INTO w3 VALUES (1, 9.99);
UPDATE w3 SET price = 9.99 WHERE id = 1;
A) Rows matched: 0 Changed: 0
B) Rows matched: 1 Changed: 1
C) ERROR 1062
D) Rows matched: 1 Changed: 0
Why: The row was found, but already had that value. MySQL prints:
Query OK, 0 rows affected
Rows matched: 1  Changed: 0  Warnings: 0
W4
What do you run right before an UPDATE that touches several rows?
A) A SELECT with exactly the same WHERE
B) SHOW TABLES;
C) SET SQL_SAFE_UPDATES = 0;
D) Nothing: UPDATE can be undone
Why: The preview: its row count must match Rows matched.
W5
Which statement gives an existing category a NEW id?
A) INSERT ... AS new ON DUPLICATE KEY UPDATE ...
B) INSERT IGNORE ...
C) REPLACE INTO ...
D) UPDATE ... WHERE id = 3
Why: REPLACE deletes and re-inserts; the upsert keeps the row.

3.1 · WHERE Clauses, Operators & Filtering: self-check

Q1
Two of the 8 customers live in Chicago and two have no city. How many rows does this return?
SELECT * FROM customers WHERE city != 'Chicago';
A) 6
B) 4
C) 8
D) 0
Why: != drops the two Chicago rows AND the two NULL cities: "is an unknown city different from Chicago?" is unknown, not true. Add `OR city IS NULL` to keep them (6).
A is wrong: 6 is what you get once you add OR city IS NULL.
C is wrong: Chicago is excluded on purpose.
D is wrong: Only city = NULL (or a NULL inside NOT IN) finds nothing.
Q2
On the Module 3 data, what does this print?
SELECT COUNT(*) AS n
FROM books
WHERE price BETWEEN 8.99 AND 9.99;
4
Why: BETWEEN includes both ends: The Great Gatsby and The Catcher in the Rye (8.99), Brave New World (9.49) and 1984 (9.99).
Q3
Which WHERE keeps every book NOT written by Tolkien or Orwell?
A) WHERE author NOT IN ('J.R.R. Tolkien', 'George Orwell')
B) WHERE author != 'J.R.R. Tolkien' OR author != 'George Orwell'
C) WHERE NOT author = 'J.R.R. Tolkien' OR 'George Orwell'
D) WHERE author NOT LIKE 'Tolkien, Orwell'
Why: NOT IN removes both names: 7 of the 10 books remain (Tolkien and Orwell have three between them).
B is wrong: Every author differs from at least one of the two names, so the condition is always true: all 10 books.
C is wrong: OR 'George Orwell' is a separate test on a piece of text, not on author.
D is wrong: That compares with one literal string, which no author matches.
Q4
created_at is a DATETIME. Which WHERE finds the customers who signed up on January 27, 2026 (Frank, at 13:30)?
A) WHERE created_at = '2026-01-27'
B) WHERE created_at BETWEEN '2026-01-27' AND '2026-01-27'
C) WHERE created_at >= '2026-01-27' AND created_at < '2026-01-28'
D) WHERE created_at LIKE 2026-01-27
Why: A half-open range: on or after midnight of the day, and before midnight of the next. It never misses an evening row.
A is wrong: '2026-01-27' means midnight exactly: 0 rows (measured).
B is wrong: The same single instant, midnight: 0 rows.
D is wrong: Without quotes 2026-01-27 is arithmetic (1998), and LIKE on a date is the wrong tool.
Q5
Which first names does this return, in order?
SELECT first_name
FROM customers
WHERE city = 'New York' OR city = 'Chicago' AND first_name LIKE 'G%'
ORDER BY first_name;
Alice, Frank, Grace
Why: AND runs before OR: city = 'New York' OR (city = 'Chicago' AND first_name LIKE 'G%'). Both New Yorkers pass, and of the Chicago customers only Grace. Written with parentheses, (New York OR Chicago) AND LIKE 'G%', it would return only Grace.
Q6
Which of these returns no rows at all?
A) WHERE city IS NULL
B) WHERE city <=> NULL
C) WHERE city LIKE '%o%'
D) WHERE city NOT IN ('Reno', NULL)
Why: NOT IN ('Reno', NULL) means city != 'Reno' AND city != NULL; the second part is unknown for every row, so nothing passes (COUNT 0 on the course data).
A is wrong: IS NULL finds Eve and Hank.
B is wrong: <=> is NULL-safe: it works like IS NULL here.
C is wrong: New York, Chicago, Los Angeles and Houston all contain an o.

3.2 · Sorting & Limiting Results: self-check

Q7
What does ORDER BY in_stock, price DESC do?
A) in_stock ascending (0 first), then price descending within each group
B) Both columns descending
C) ERROR 1064: DESC must come after every column
D) price first, then in_stock
Why: ASC and DESC belong to the one column right before them; ASC is the default. For both descending write `in_stock DESC, price DESC`.
B is wrong: DESC applies only to price.
C is wrong: It is valid SQL.
D is wrong: The first column listed is the first sort key.
Q8
What does this print?
SELECT title
FROM books
ORDER BY pages DESC
LIMIT 1 OFFSET 2;
Dune (412 pages: the third longest)
Why: Longest first: Lord of the Rings 1178, Pride and Prejudice 432, Dune 412. OFFSET 2 skips two rows, LIMIT 1 keeps the next.
Q9
What happens with 'price' in quotes: ORDER BY 'price' DESC LIMIT 3?
A) The three most expensive books, as intended
B) ERROR 1054: Unknown column
C) No error, but the rows come in no particular order: 'price' is a fixed piece of text
D) The rows are sorted alphabetically by title
Why: In single quotes, price is text, the same for every row, so there is nothing to sort by. Column names are written bare (or in backticks).
A is wrong: On the test server it returned Dune, 1984, To Kill a Mockingbird: not the top three.
B is wrong: A text value is valid, so there is no error: the danger.
D is wrong: Nothing sorts by title here.
Q10
Where do Eve and Hank (no city) appear with ORDER BY city DESC, first_name?
A) First
B) They are left out
C) ERROR 1064
D) Last
Why: MySQL treats NULL as smaller than any value: first in an ascending sort, last in a descending one. To force them last in an ascending sort: `ORDER BY city IS NULL, city`.
A is wrong: That is the ascending sort.
B is wrong: ORDER BY never removes rows.
C is wrong: Valid SQL.
Q11
A list sorted by id shows 20 rows per page, and page 1 ended at id 57. Which query gets the next page fast, even on a huge table?
A) ... ORDER BY id LIMIT 20 OFFSET 57
B) ... WHERE id > 57 ORDER BY id LIMIT 20
C) ... WHERE id >= 57 LIMIT 20
D) ... ORDER BY id LIMIT 57, 20
Why: Keyset pagination: remember the last row seen and ask for the rows after it. With the primary key's index MySQL jumps straight to id 58.
A is wrong: OFFSET counts rows, not ids, and reads and discards them all: slower with every page.
C is wrong: It repeats id 57 and has no ORDER BY.
D is wrong: The comma form is OFFSET 57: the same row-counting problem.
Q12
With 3 books per page, how many pages? What does this print?
SELECT CEILING(COUNT(*) / 3) AS pages FROM books;
4
Why: 10 books / 3 = 3.33, and CEILING rounds up: the last page holds one book.

3.2 · Sorting & Limiting Results: predict, then run

P3
Predict the output, then run it.
SELECT first_name, city
FROM customers
ORDER BY city DESC, first_name
LIMIT 3;
+------------+-------------+
| first_name | city        |
+------------+-------------+
| Alice      | New York    |
| Frank      | New York    |
| Carol      | Los Angeles |
+------------+-------------+
Why: Descending puts New York first and NULLs last; first_name breaks the New York tie: Alice, Frank, then Carol (Los Angeles).
P4
Predict the output, then run it.
SELECT title, pages
FROM books
ORDER BY pages
LIMIT 2 OFFSET 8;
+---------------------+-------+
| title               | pages |
+---------------------+-------+
| Pride and Prejudice |   432 |
| Lord of the Rings   |  1178 |
+---------------------+-------+
Why: Shortest first, skip 8 of the 10: the two longest are left, Pride and Prejudice (432) and Lord of the Rings (1178).

Model answer: labs/module-04/checkpoint-1/checkpoint_solution.sql
-- ---------- Part A · build (rerunnable) ----------
DROP DATABASE IF EXISTS kit_cp1_tradein;
CREATE DATABASE kit_cp1_tradein
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_unicode_ci;
USE kit_cp1_tradein;

-- People who bring books in. email is how the desk finds them again.
CREATE TABLE sellers (
    id     INT AUTO_INCREMENT PRIMARY KEY,
    name   VARCHAR(80)  NOT NULL,
    email  VARCHAR(100) NOT NULL UNIQUE,
    city   VARCHAR(50)
);

-- One row per book brought in. seller_id says whose it is (Module 4 makes it a foreign key).
CREATE TABLE trade_ins (
    id              INT AUTO_INCREMENT PRIMARY KEY,
    seller_id       INT NOT NULL,
    title           VARCHAR(200) NOT NULL,
    book_condition  ENUM('like new', 'good', 'worn') NOT NULL DEFAULT 'good',
    offer           DECIMAL(5, 2) NOT NULL,
    received        DATE NOT NULL,
    paid            BOOLEAN NOT NULL DEFAULT FALSE,
    CONSTRAINT chk_offer CHECK (offer BETWEEN 0.50 AND 20.00)
);

-- ---------- Part B · fill and change ----------
-- B1 · three sellers
INSERT INTO sellers (name, email, city) VALUES
    ('Mo Rahman', 'mo@example.com', 'Reno'),
    ('Ivy Chen', 'ivy@example.com', NULL),
    ('Sam Okoro', 'sam@example.com', 'Sparks');

-- B2 · five trade-ins (paid is left to its default)
INSERT INTO trade_ins (seller_id, title, book_condition, offer, received) VALUES
    (1, 'Dune', 'good', 4.00, '2026-05-01'),
    (1, 'Emma', 'worn', 1.50, '2026-05-01'),
    (2, 'The Hobbit', 'like new', 6.00, '2026-05-03'),
    (3, '1984', 'good', 3.50, '2026-05-04'),
    (3, 'Dracula', 'worn', 1.00, '2026-05-04');

-- B3 · Dune's offer goes up by one dollar (it is id 1)
UPDATE trade_ins SET offer = offer + 1.00 WHERE id = 1;

-- B4 · Mo is paid for all his books: preview, then the same WHERE
SELECT id, title, paid FROM trade_ins WHERE seller_id = 1 ORDER BY id;
UPDATE trade_ins SET paid = TRUE WHERE seller_id = 1;
SELECT ROW_COUNT() AS rows_paid;

-- B5 · Dracula (id 5) was turned down
DELETE FROM trade_ins WHERE id = 5;

-- B6 · Ivy sends her details again, now with a city: insert her, or update her
INSERT INTO sellers (name, email, city)
VALUES ('Ivy Chen', 'ivy@example.com', 'Henderson') AS new
ON DUPLICATE KEY UPDATE city = new.city;

-- ---------- Part C · read ----------
-- C1 · every trade-in, with 10% extra if taken as store credit
SELECT id, title, book_condition, offer,
       ROUND(offer * 1.10, 2) AS store_credit, paid
FROM trade_ins
ORDER BY id;

-- C2 · the conditions that occur, each once
SELECT DISTINCT book_condition FROM trade_ins ORDER BY book_condition;

-- C3 · the sellers now
SELECT id, name, city FROM sellers ORDER BY id;

DROP DATABASE kit_cp1_tradein;

Part D answers (each run after the model answer)
D1
The desk offers 25.00 for a rare copy of Emma.
INSERT INTO trade_ins (seller_id, title, offer, received)
VALUES (1, 'Emma', 25.00, '2026-05-02');
ERROR 3819 (HY000): Check constraint 'chk_offer' is violated.
Why: The CHECK chk_offer keeps offers from 0.50 to 20.00 (the desk's rule). Fix: an offer within the range, or a manager changes the rule with ALTER TABLE.
D2
Mo comes back with a new name on his card, same email.
INSERT INTO sellers (name, email)
VALUES ('Mo R.', 'mo@example.com');
ERROR 1062 (23000): Duplicate entry 'mo@example.com' for key 'sellers.email'
Why: email is UNIQUE: one seller per email, so the desk finds people again. Fix: UPDATE Mo's name by id, or the B6 upsert.
D3
Ivy's Emma is in "mint" condition.
INSERT INTO trade_ins (seller_id, title, book_condition, offer, received)
VALUES (2, 'Emma', 'mint', 3.00, '2026-05-02');
ERROR 1265 (01000): Data truncated for column 'book_condition' at row 1
Why: mint is not on the ENUM list; 1265 "Data truncated" is how MySQL says so. Fix: 'like new', or add the value by redefining the whole column.
Scoring notes
  • Accept DECIMAL(4, 2) or wider for the offer, TINYINT(1) for paid, VARCHAR sizes close to the spec, and B4 without the ROW_COUNT line if the preview is there.
  • B6 by UPDATE gives the right table but not the asked statement: 1 on row 4. B6 by REPLACE gives Ivy a new id (4) and is a 1 too, with a note on why.
  • A file that only runs once (no DROP DATABASE IF EXISTS, or CREATE without IF NOT EXISTS after an edit) loses the hygiene point it most needs.
  • Column named condition: a 1064 they should have fixed with the hint; if the rest runs, score the rest.

The Lesson Pages' Own Quick Quizzes

Lesson 3.1 · WHERE Clauses, Operators & Filtering
  1. B 0: city = NULL is unknown for every row, even for Eve and Hank, and WHERE only keeps rows where the test is true. The query returns an empty set without any error. Use IS NULL instead.
  2. C a = 1 OR (b = 2 AND c = 3): AND is evaluated before OR, just as multiplication comes before addition. Add parentheses whenever you mix the two so the meaning is clear.
  3. A 9.49, 10.99 and everything in between: BETWEEN includes both ends. It is shorthand for: price is at least 9.49 AND price is at most 10.99.
  4. C LIKE '___': Each underscore matches exactly one character, so three underscores match exactly three: Bob and Eve.
  5. A The text value Austen is missing its quotes: Without quotes, Austen is read as a column name. Text values belong in single quotes: WHERE author = 'Jane Austen'.
Lesson 3.2 · Sorting & Limiting Results
  1. A At the top: MySQL sorts NULL as smaller than every value, so NULLs come first in ascending order and last in descending order.
  2. C Rows 7 to 9: OFFSET 6 skips rows 1 to 6, then LIMIT 3 keeps the next three: rows 7, 8 and 9.
  3. B The first row is the 7.99 book; the second can be either 8.99 book: The 7.99 book is certain to come first, but the 8.99 books tie, so which one fills the second slot is up to the server. Add a unique tie-breaker such as title.
  4. A LIMIT 4 OFFSET (3 - 1) * 4: LIMIT and OFFSET accept plain numbers or placeholders, not expressions. Compute 8 first and write OFFSET 8.
  5. C LIMIT 20 OFFSET 80: Page N starts after (N - 1) x page size rows: (5 - 1) x 20 = 80 rows skipped, then 20 returned.

Exit Ticket

  1. Why does WHERE city != 'Chicago' skip Eve and Hank, and how do you include them? Answer: Their city is NULL, so the comparison is unknown, not true, and only true rows are kept. Add OR city IS NULL.
  2. Write the WHERE clause for: books from $9 to $11, both ends included, that are not by Tolkien. Answer: WHERE price BETWEEN 9 AND 11 AND author != 'J.R.R. Tolkien' (on the course data: Brave New World, 1984, Fahrenheit 451).
  3. Why should every ORDER BY that feeds a LIMIT end with a unique column? Answer: If rows tie at the cut-off, the server may return either one, and the choice can change between runs: page 1 and page 2 can repeat or skip a row. A unique column (id, title here) makes the order repeatable.

Common Wrong Answers and What They Reveal

  • Q1 A (6). Counts the NULL cities as "not Chicago". The day's main idea: unknown is dropped.
  • Q3 B. The classic != OR != that is always true. Translate it into English with them.
  • Q4 A. Treats a DATETIME like a DATE: show the 0-row result.
  • Q7 B. Thinks DESC applies to the whole ORDER BY.
  • Q9 A. Does not see the quotes: the most dangerous silent sort mistake.
  • Q11 A or D. Confuses rows skipped with ids: an OFFSET counts rows.
