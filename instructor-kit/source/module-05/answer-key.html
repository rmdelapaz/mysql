Session 5 12 self-check items Confidential

Warm-up

W1
Who comes back, and why?
SELECT first_name, city, id
FROM customers
WHERE city = 'Chicago' OR city = 'Houston' AND id > 5
ORDER BY id;
Bob and Grace. AND binds before OR: city = 'Chicago' OR (city = 'Houston' AND id > 5), and Dave (Houston) has id 4.
+------------+---------+----+
| first_name | city    | id |
+------------+---------+----+
| Bob        | Chicago |  2 |
| Grace      | Chicago |  7 |
+------------+---------+----+
W2
Two customers have no city. Why does this find nobody? What would you write instead?
SELECT first_name FROM customers WHERE city = NULL;
Nobody: nothing equals NULL, not even NULL. Write WHERE city IS NULL (Eve and Hank).
Empty set
W3
In which order must you write WHERE, ORDER BY and LIMIT?
WHERE, then ORDER BY, then LIMIT. Lesson 3.3 adds GROUP BY and HAVING between WHERE and ORDER BY.
W4
Which three books does this show?
SELECT title, price
FROM books
ORDER BY price DESC, title
LIMIT 3 OFFSET 2;
The 3rd, 4th and 5th most expensive: OFFSET 2 skips Lord of the Rings and Dune.
+-----------------------+-------+
| title                 | price |
+-----------------------+-------+
| To Kill a Mockingbird | 11.99 |
| The Hobbit            | 10.99 |
| Fahrenheit 451        | 10.49 |
+-----------------------+-------+
W5
Predict: how many customers live outside Chicago, according to this query?
SELECT first_name
FROM customers
WHERE city NOT IN ('Chicago', NULL);
None: city != 'Chicago' AND city != NULL is unknown for every row. A NULL inside a NOT IN list empties the result (Lesson 3.1), and it comes back inside subqueries in Lesson 3.4.
Empty set

3.3 · Aggregate Functions & GROUP BY: self-check

Q1
Grace (Chicago) and Hank (no city) are the only customers who signed up in February. What does this print?
SELECT COUNT(*), COUNT(city)
FROM customers
WHERE created_at >= '2026-02-01';
A) 2 and 2
B) 2 and 1
C) 1 and 1
D) 8 and 6
Why: WHERE keeps the two February rows first. COUNT(*) counts both rows; COUNT(city) counts only the filled-in cities, and Hank's is NULL.
A is wrong: COUNT(column) skips NULL; only COUNT(*) counts every row.
C is wrong: Hank's row is still a row: COUNT(*) counts rows, not values.
D is wrong: Those are the counts for the whole table; the WHERE line runs before the counting.
Q2
You want only the authors whose books average more than $10. Where does that condition go?
A) In WHERE, before GROUP BY
B) In ORDER BY
C) In HAVING, after GROUP BY
D) In the SELECT list, as AVG(price) > 10
Why: The average belongs to a whole group (an author's pile), so it can only be tested after the piles exist: HAVING. A condition on single rows (price > 10) goes in WHERE.
A is wrong: WHERE runs before the piles exist; an aggregate there is error 1111.
B is wrong: ORDER BY sorts; it never removes rows.
D is wrong: That adds a 0/1 column; every author still appears.
Q3
The flat bookstore has no books by Isaac Asimov. What does this print?
SELECT COUNT(*) AS n, MAX(price) AS top
FROM books
WHERE author = 'Isaac Asimov';
One row: n = 0 and top = NULL
Why: An aggregate over no rows still returns one row. COUNT answers 0; every other aggregate has no values to work with and returns NULL (use COALESCE(MAX(price), 0) when a report needs 0).
Q4
What happens when this runs on MySQL 9.7?
SELECT city, first_name
FROM customers
GROUP BY city;
A) ERROR 1055 (42000): first_name is not in GROUP BY and not aggregated
B) One row per city, each with one customer's first name
C) ERROR 1140: an aggregated query without GROUP BY
D) One row per customer, sorted by city
Why: Chicago's pile holds Bob and Grace: which first name belongs in Chicago's one row? MySQL's default ONLY_FULL_GROUP_BY mode refuses to guess (error 1055). Fix: aggregate it (MIN(first_name)), group by it, or drop it.
B is wrong: That is what MariaDB (no ONLY_FULL_GROUP_BY) does silently: an arbitrary name per city.
C is wrong: 1140 is for an aggregate with no GROUP BY at all; this query has one.
D is wrong: GROUP BY makes one row per group, never one per input row.
Q5
A colleague says: "I don't need ORDER BY after GROUP BY city: the cities always come out sorted." On MySQL 9.7, is that right?
A) Yes: GROUP BY sorts the groups by the grouped column
B) Yes, but only when the column has an index
C) Only on Windows servers
D) No: since MySQL 8.0 the order of groups is not guaranteed; add ORDER BY
Why: MySQL 8.0 and later return groups in whatever order is convenient (the lesson's Common Mistake 5 shows them in first-seen order). MariaDB still sorts, so the same query can come back in a different order on another server. A report always says ORDER BY.
A is wrong: That was true of MySQL 5.7 and is still true of MariaDB, not of MySQL 9.7.
B is wrong: An index may make a sorted order likely, never guaranteed.
C is wrong: The operating system has nothing to do with it.
Q6
What does this print? (Under $10: three books in stock and two out of stock.)
SELECT in_stock, COUNT(*) AS books
FROM books
WHERE price < 10
GROUP BY in_stock
ORDER BY in_stock;
Two rows: 0 | 2 and 1 | 3
Why: WHERE keeps the five books under $10; GROUP BY makes one pile per in_stock value (0 = out of stock, 1 = in stock); ORDER BY in_stock puts 0 first.

3.3 · Aggregate Functions & GROUP BY: predict, then run

P1
Predict the output, then run it.
SELECT COUNT(*), COUNT(city), COUNT(DISTINCT city)
FROM customers
WHERE id > 4;
+----------+-------------+----------------------+
| COUNT(*) | COUNT(city) | COUNT(DISTINCT city) |
+----------+-------------+----------------------+
|        4 |           2 |                    2 |
+----------+-------------+----------------------+
Why: Customers 5 to 8 are Eve (NULL), Frank (New York), Grace (Chicago) and Hank (NULL): four rows, two filled-in cities, two different cities.
P2
Predict the output, then run it.
SELECT in_stock, MAX(pages) AS longest
FROM books
GROUP BY in_stock
HAVING MAX(pages) > 300
ORDER BY in_stock;
+----------+---------+
| in_stock | longest |
+----------+---------+
|        1 |    1178 |
+----------+---------+
Why: Two piles: in stock (longest 1178, Lord of the Rings) and out of stock (longest 234). HAVING drops the out-of-stock pile; one row remains.

3.4 · Subqueries & Nested Queries: self-check

Q7
The average price is 10.99. What does this print?
SELECT COUNT(*)
FROM books
WHERE price < (SELECT AVG(price) FROM books);
A) 4
B) 6
C) 7
D) 10
Why: The subquery returns 10.99; six books cost less (7.99 to 10.49). The Hobbit costs exactly 10.99 and is not less than itself.
A is wrong: Four books cost MORE than or equal to the average (three above, The Hobbit equal).
C is wrong: Seven would include The Hobbit, which costs exactly 10.99.
D is wrong: Ten is every book: the subquery is a real filter, not a decoration.
Q8
What happens when this runs?
SELECT title
FROM books
WHERE price = (SELECT price FROM books
               WHERE author = 'J.R.R. Tolkien');
A) ERROR 1242 (21000): Subquery returns more than 1 row
B) It returns Lord of the Rings
C) ERROR 1241 (21000): Operand should contain 1 column(s)
D) ERROR 1248 (42000): Every derived table must have its own alias
Why: Tolkien has two books, so the subquery returns two prices, and = needs one value. Fix: IN (any of his prices) or an aggregate such as MAX(price). The query would have worked while he had one book: the lesson's warning about queries that break when the data grows.
B is wrong: MySQL does not pick one of the values for you.
C is wrong: 1241 is too many COLUMNS; here there is one column and too many rows.
D is wrong: 1248 is for a subquery in FROM without a name; this one is in WHERE.
Q9
Customer 5 (Eve) has no city; customer 6 (Frank) lives in New York. What does this print?
SELECT COUNT(*)
FROM customers
WHERE city NOT IN (SELECT city FROM customers WHERE id IN (5, 6));
0 (no customer passes the test)
Why: The list is (NULL, 'New York'). city NOT IN (...) means city != NULL AND city != 'New York', and anything compared with NULL is unknown, so no row is ever kept. Add AND city IS NOT NULL inside the subquery, or use NOT EXISTS.
Q10
You need the customers whom no other customer shares a city with, and city can be NULL. Which approach gives a predictable answer with no NULL trap?
A) city NOT IN (SELECT city FROM customers ...)
B) city != ALL (SELECT city ...)
C) NOT EXISTS (SELECT 1 FROM customers AS other WHERE other.city = c.city AND other.id != c.id)
D) city NOT LIKE (SELECT city ...)
Why: NOT EXISTS asks "is there a matching row?": a NULL city never matches, so it cannot empty the result, and the customers with no city are kept (nobody is known to share their city). That is why many developers write NOT EXISTS by default.
A is wrong: One NULL in the list empties a NOT IN.
B is wrong: != ALL is the same as NOT IN, with the same trap.
D is wrong: LIKE compares with one pattern; with several rows it fails with error 1242.
Q11
What does this print? (Two customers have no city.)
SELECT MAX(n) AS biggest_group
FROM (
    SELECT city, COUNT(*) AS n
    FROM customers
    GROUP BY city
) AS per_city;
2
Why: The derived table holds one row per city, NULL included: NULL 2, Chicago 2, New York 2, Houston 1, Los Angeles 1. The outer MAX reads that small table: 2. The alias per_city is required (error 1248 without it).
Q12
This was meant to list the books priced above THEIR OWN author's average. Why does it return three books instead of one?
SELECT title, author, price
FROM books
WHERE price > (
    SELECT AVG(price)
    FROM books
    WHERE author = author
)
ORDER BY price;
A) The subquery runs once per author, but AVG ignores the out-of-stock books
B) MySQL treats the second author as a string literal
C) HAVING is missing from the subquery
D) Both author names refer to the inner table, so author = author is always true and the subquery returns the store average
Why: Inside the subquery the nearest table wins: both sides of author = author are the inner books row. The subquery is not correlated at all and returns 10.99, so you get "above the store average" by accident. Fix: alias both copies (FROM books AS b ... FROM books AS b2 WHERE b2.author = b.author).
A is wrong: AVG uses every book; in_stock plays no part here.
B is wrong: An unquoted name is a column, not a string.
C is wrong: HAVING filters groups; there are no groups in this subquery.

3.4 · Subqueries & Nested Queries: predict, then run

P3
Predict the output, then run it.
SELECT COUNT(*) AS long_books
FROM books
WHERE pages > (SELECT AVG(pages) FROM books);
+------------+
| long_books |
+------------+
|          3 |
+------------+
Why: The inner query returns 382.4; only Lord of the Rings (1178), Pride and Prejudice (432) and Dune (412) are longer.
P4
Predict the output, then run it.
SELECT first_name
FROM customers
WHERE city NOT IN (SELECT city FROM customers WHERE id = 5);
Empty set
Why: The list is just (NULL): Eve's city. city NOT IN (NULL) is unknown for every row, so nobody comes back, not even the customers with a city.

The Lesson Pages' Own Quick Quizzes

Lesson 3.3 · Aggregate Functions & GROUP BY
  1. B 6: COUNT(column) counts only the values that are not NULL: 8 rows minus the 2 missing cities is 6. COUNT(*) would return 8.
  2. C In a HAVING clause after GROUP BY: HAVING runs after GROUP BY, when each author's pile has been counted, so it can keep or drop whole groups by their aggregate.
  3. A 4: AVG skips the NULL completely, so it divides 5 + 3 + 4 = 12 by 3 values, not by 4 rows.
  4. B title is neither in GROUP BY nor inside an aggregate: With ONLY_FULL_GROUP_BY on, every selected column must be grouped or aggregated. An author with two books has two titles, so title is ambiguous.
  5. A Add an ORDER BY clause: Since MySQL 8.0, GROUP BY makes no promise about order (MariaDB still sorts). ORDER BY is the only way to get the same order everywhere.
Lesson 3.4 · Subqueries & Nested Queries
  1. C 3: Only To Kill a Mockingbird, Dune and Lord of the Rings cost more than 10.99. The Hobbit equals the average, and greater-than does not include equal.
  2. B Use IN instead of =, or make the subquery return a single value: The subquery sits next to = or another single-value operator but returned a list. Use IN for a list, or reduce the subquery to one value with MIN, MAX or a unique condition.
  3. A No rows at all: NOT IN means not equal to every item. Not equal to NULL is unknown for every row, so no row can pass. Filter NULLs out of the subquery or use NOT EXISTS.
  4. C It refers to a column of the outer query's current row: A correlated subquery uses a column of the outer query's current row, such as b2.author = b.author, so its answer can differ for every outer row.
  5. B Adding an alias such as AS author_counts after the closing parenthesis: Every derived table must have its own alias. Adding AS author_counts after the closing parenthesis makes the query run.

Exit Ticket

  1. WHERE and HAVING: any single-row condition in WHERE (in_stock = TRUE, price > 10, published < '1950-01-01') and any aggregate condition in HAVING (COUNT(*) > 1, AVG(price) > 10, SUM(pages) > 400). A learner who puts price > 10 in HAVING has the clauses as interchangeable filters: reteach the run order.
  2. NOT IN with NULL: no rows. Fixes: AND city IS NOT NULL inside the subquery, or NOT EXISTS (which also keeps the NULL-city customers, a different but predictable answer).
  3. Correlated: it refers to the outer query's current row, so it is evaluated again for every outer row. With one table used twice, aliases (b for the outer row, b2 for the inner scan) are how you say which copy a column belongs to; without them author = author compares a row with itself.

Common Wrong Answers and What They Reveal

  • Q1 A (2 and 2). Thinks COUNT(column) counts rows. Show COUNT(*) and COUNT(city) side by side again in the Session 6 warm-up.
  • Q2 A (WHERE). Treats WHERE and HAVING as the same filter. The run-order diagram is the cure; ask "when does WHERE run?"
  • Q4 B (one name per city). Has used MariaDB or old MySQL, or imagines MySQL picks "the first". The 1055 check exists so answers are honest.
  • Q7 C (7). Counted The Hobbit (exactly 10.99): < and <= are different questions. Worth ten seconds.
  • Q9 any number other than 0. Has not met the NOT IN trap yet: run the lesson's two queries side by side.
  • Q12 A or C. Looks for a missing clause instead of reading what author refers to. Ask them to run the subquery alone: it returns one number, the store average.
  • Exit ticket 3 with "it is inside another query". That is any subquery; correlated means it uses the OUTER row. Ask: "can you run it on its own?"
