7.2 · Transactions: self-check

Q1
You type START TRANSACTION; and an UPDATE that succeeds, then close the terminal window without COMMIT. What happens to the change?
A) It is kept: the UPDATE succeeded
B) The server rolls it back when the connection ends
C) It waits, and is committed the next time you log in
D) It is kept, but only your account can see it
Why: Nothing is committed unless you say COMMIT (or autocommit does it for you). A dropped connection ends the open transaction with a rollback (the lesson's Common Questions).
A is wrong: Succeeding is not the same as being committed; inside a transaction the change is still provisional.
C is wrong: Transactions do not survive the connection; a new login starts with nothing open.
D is wrong: Uncommitted changes are visible to your own session only while it is open; once it closes they are gone.
Q2
What does the last statement print?
CREATE TABLE stock (id INT PRIMARY KEY, qty INT NOT NULL);
INSERT INTO stock VALUES (1, 5), (2, 5);
START TRANSACTION;
UPDATE stock SET qty = qty - 1 WHERE id = 1;
SAVEPOINT s1;
UPDATE stock SET qty = qty - 1 WHERE id = 2;
ROLLBACK TO SAVEPOINT s1;
UPDATE stock SET qty = qty + 3 WHERE id = 2;
COMMIT;
SELECT id, qty FROM stock ORDER BY id;
Two rows: id 1 qty 4, id 2 qty 8
Why: The first UPDATE (id 1 to 4) happened before the savepoint and stays. ROLLBACK TO SAVEPOINT s1 undoes only the -1 on id 2. The +3 on id 2 comes after the rollback, so id 2 goes from 5 to 8, and COMMIT keeps both.
Q3
Which statement, typed inside an open transaction, commits that transaction on the spot?
A) SAVEPOINT before_change;
B) SELECT price FROM books WHERE id = 1 FOR UPDATE;
C) ALTER TABLE books ADD COLUMN rating INT;
D) ROLLBACK TO SAVEPOINT before_change;
Why: Schema changes (CREATE, ALTER, DROP, RENAME, TRUNCATE) cause an implicit commit before they run, so a later ROLLBACK has nothing left to undo: the trap the demo showed with CREATE TABLE.
A is wrong: A savepoint is a bookmark inside the transaction; the transaction stays open.
B is wrong: FOR UPDATE takes row locks inside the transaction; it does not end it.
D is wrong: Rolling back to a savepoint undoes part of the work and keeps the transaction open.
Q4
Window A runs START TRANSACTION; and UPDATE accounts SET balance = 0 WHERE id = 1; and does not commit. Window B then runs SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;. What does B get?
A) 0, A's new value
B) The last committed balance, at once
C) ERROR 1213 at once: a deadlock
D) Nothing yet: B waits for A's row lock, and fails with ERROR 1205 if A holds it past the timeout
Why: A locking read (FOR UPDATE) needs the same row lock A's UPDATE holds, so it waits like a writer. A plain SELECT would not wait: it reads the committed snapshot.
A is wrong: No session ever sees another's uncommitted value under REPEATABLE READ.
B is wrong: That is what a PLAIN SELECT gets; FOR UPDATE must lock the row first.
C is wrong: A deadlock needs two transactions each waiting for the other; here only B waits.
Q5
In the transfer procedure's handler, why does RESIGNAL come right after ROLLBACK?
A) So the caller still receives the original error after the half-done changes are undone
B) RESIGNAL commits whatever the handler did not roll back
C) Without it, the handler would run again and again
D) Every handler must end with RESIGNAL or the procedure does not compile
Why: ROLLBACK cleans up; RESIGNAL passes the same error (1644, 3819, ...) on, so the app knows the call failed and why. A handler that only rolls back hides the failure.
B is wrong: RESIGNAL raises an error; it never commits anything.
C is wrong: An EXIT handler runs once and leaves the procedure.
D is wrong: RESIGNAL is optional syntax; leaving it out compiles fine, which is exactly why the silent version is a trap.
Q6
An app's checkout fails with ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction. What should the app do?
A) Nothing: the statements before the deadlock were saved
B) Run only the statement that failed again
C) Raise innodb_lock_wait_timeout so it never happens again
D) Run the whole transaction again from the start
Why: InnoDB picked this transaction as the deadlock victim and rolled ALL of it back. The message is the advice: restart the transaction. Short transactions that lock rows in the same order make it rare.
A is wrong: The victim's whole transaction was rolled back; nothing of it was saved.
B is wrong: The earlier statements were undone too; repeating one statement alone leaves the job half done.
C is wrong: A deadlock is detected at once, not after a timeout; the timeout setting does not affect it.

7.2 · Transactions: predict, then run

P1
Predict the output, then run it.
CREATE TABLE counter (n INT);
INSERT INTO counter VALUES (1);
SET autocommit = 0;
UPDATE counter SET n = n + 10;
ROLLBACK;
SET autocommit = 1;
SELECT n FROM counter;
+------+
| n    |
+------+
|    1 |
+------+
Why: With autocommit off, the UPDATE waited for a decision; ROLLBACK discarded it, so n is still 1. Switching autocommit off for a whole session is rare: one forgotten COMMIT and the work is lost at disconnect.
P2
Predict the output, then run it.
CREATE TABLE seats (id INT PRIMARY KEY, taken INT NOT NULL);
INSERT INTO seats VALUES (1, 0), (2, 0);
START TRANSACTION;
UPDATE seats SET taken = 1 WHERE id = 1;
SAVEPOINT one_seat;
UPDATE seats SET taken = 1 WHERE id = 2;
ROLLBACK TO SAVEPOINT one_seat;
COMMIT;
SELECT SUM(taken) AS seats_taken FROM seats;
+-------------+
| seats_taken |
+-------------+
|           1 |
+-------------+
Why: Seat 1 was taken before the savepoint and kept; seat 2 was taken after it and rolled back. COMMIT keeps what is left: one seat.

7.3 · JSON Columns: self-check

Q7
On the web page, CONCAT(title, ': ', attributes->'$.series') prints Dune: "Dune Chronicles". Which change removes the quotes?
A) Wrap the whole CONCAT in TRIM()
B) Use JSON_EXTRACT instead of ->
C) Use ->> instead of ->
D) Store the series without quotes in the document
Why: -> returns a JSON value, and a JSON string keeps its double quotes. ->> (JSON_UNQUOTE of JSON_EXTRACT) returns plain text: use it whenever a value leaves JSON for display, CONCAT or comparison.
A is wrong: TRIM removes spaces, not quote characters.
B is wrong: JSON_EXTRACT is exactly what -> means; same quotes.
D is wrong: Every JSON string is stored with double quotes; that is the format, not a mistake.
Q8
What does the SELECT print?
CREATE TABLE shelf (id INT PRIMARY KEY, info JSON);
INSERT INTO shelf VALUES (1, '{"tags": ["new", "signed", "gift"], "copies": 2}');
SELECT info->>'$.tags[last]' AS last_tag, JSON_LENGTH(info->'$.tags') AS tag_count
FROM shelf;
gift and 3
Why: [last] is the last element of the array, and ->> returns it as plain text; JSON_LENGTH counts the three elements.
Q9
A document already has a format key. What does JSON_INSERT(doc, '$.format', 'ebook') return?
A) The document unchanged
B) The document with format replaced by ebook
C) The document with a second format key
D) An error: the key already exists
Why: JSON_INSERT only adds missing keys; JSON_SET adds or replaces; JSON_REPLACE only replaces existing keys. All three return a changed copy, never an error, for a key that is or is not there.
B is wrong: That is JSON_SET (or JSON_REPLACE).
C is wrong: A JSON object never holds the same key twice.
D is wrong: The JSON_* change functions do not raise errors for existing or missing keys.
Q10
WHERE attributes->>'$.format' = 'hardcover' is slow on a table of a million books. What is MySQL's fix?
A) CREATE INDEX idx_attr ON books (attributes);
B) A generated column for $.format, with an index on that column
C) Change the column type from JSON to TEXT
D) Write JSON_EXTRACT instead of ->>
Why: A JSON column cannot be indexed as a whole (error 3152). A VIRTUAL generated column pulls one path out, and its index is used even by the original ->> expression, as the demo's EXPLAIN showed.
A is wrong: That is error 3152: JSON columns are indexed only through generated columns.
C is wrong: TEXT loses validation and is no easier to index by path.
D is wrong: Same lookup, same full scan.
Q11
What does this print?
SELECT JSON_OBJECT('title', 'Dune', 'id', 1, 'price', 14.99) AS doc;
{"id": 1, "price": 14.99, "title": "Dune"}
Why: MySQL stores JSON in a binary form with the keys of every object sorted: shorter keys first, then alphabetically. The data is the same; only the order changed, so never rely on key order.
Q12
The store wants to record four things. Which ONE belongs in a JSON column rather than a regular column or table?
A) The customer an order belongs to
B) A book's price
C) The line items of an order
D) An optional gift-wrap note some orders have, with a color and a message
Why: Optional, varied, display-only details are what JSON is for. The other three are core data: you join on the customer, sum the price, and line items are a list of related things that need their own table with foreign keys.
A is wrong: You join on it and it needs a foreign key: a column.
B is wrong: Every book has one, and every total uses it: a DECIMAL column.
C is wrong: A list of related rows is a child table (order_items), the lesson's 'when not to use JSON' table.

7.3 · JSON Columns: predict, then run

P3
Predict the output, then run it.
SELECT JSON_VALID('{"a": 1}') AS ok,
       JSON_VALID("{'a': 1}")  AS single_quotes,
       JSON_TYPE('[1, 2]')     AS kind;
+------+---------------+-------+
| ok   | single_quotes | kind  |
+------+---------------+-------+
|    1 |             0 | ARRAY |
+------+---------------+-------+
Why: JSON_VALID accepts double quotes only (single quotes give 0); JSON_TYPE names the kind of value: ARRAY.
P4
Predict the output, then run it.
SET @doc = '{"format": "paperback"}';
SELECT JSON_INSERT(@doc, '$.format', 'ebook')  AS ins,
       JSON_REPLACE(@doc, '$.pages', 300)      AS rep;
+-------------------------+-------------------------+
| ins                     | rep                     |
+-------------------------+-------------------------+
| {"format": "paperback"} | {"format": "paperback"} |
+-------------------------+-------------------------+
Why: JSON_INSERT never replaces an existing key (format stays paperback); JSON_REPLACE never adds a missing key (no pages). Both return the document unchanged here; JSON_SET would have done both.

The Lesson Pages' Own Quick Quizzes

Lesson 7.2 · Transactions
  1. A Atomicity: Atomicity: all of a transaction's changes are kept, or none of them. The order row and its item rows succeed or fail together.
  2. C The last committed value, immediately: InnoDB gives plain readers the last committed version of the row, without waiting. B sees A's change only after A commits.
  3. B The first UPDATE only: In MySQL a failed statement rolls back only itself and the transaction stays open, so COMMIT saves the first UPDATE. Roll back yourself, or use a handler.
  4. B CREATE TABLE demo_audit (note VARCHAR(100)): DDL such as CREATE TABLE causes an implicit commit before it runs, so a later ROLLBACK cannot undo the earlier changes.
  5. C Another transaction held the row's lock longer than the timeout: Another transaction held a lock on the row, and your statement gave up after innodb_lock_wait_timeout seconds (50 by default). Only that statement failed.
Lesson 7.3 · JSON Columns
  1. C attributes->>'$.format': The double arrow extracts and unquotes in one step: it is short for JSON_UNQUOTE(JSON_EXTRACT(attributes, '$.format')).
  2. A JSON keys are case-sensitive, so $.FORMAT is NULL for every book: JSON keys are case-sensitive. No document has a FORMAT key, so the expression is NULL for every row, and NULL never equals anything. MySQL does not warn about a missing key.
  3. B Add a generated column for $.format and index that column: A generated column extracts the value from each document, and an ordinary index on that column can be used, even by queries that write the original JSON expression.
  4. C It fails with error 3140, because JSON keys must be double-quoted strings: The key format has no double quotes, so the text is not valid JSON and the JSON column rejects it with error 3140. The row keeps its old value.
  5. B The price, which every book has and every order total uses: Every book has a price, it needs an exact DECIMAL type and NOT NULL, and orders and reports calculate with it all the time. That is regular-column data.

Exit Ticket

  1. Committed after 3819: every change made before the failed statement in that transaction; the failed statement undid only itself. ROLLBACK after an error, or a handler.
  2. The handler: DECLARE EXIT HANDLER FOR SQLEXCEPTION BEGIN ROLLBACK; RESIGNAL; END; (declared after the variables, before the other statements).
  3. JSON or column: JSON for optional, varied, display-only details (series, edition, awards, illustrated); a column for what every row has or what you join, sum or constrain (price, author_id, customer_id). Accept any pair with a reason from the lesson's table.

Common Wrong Answers and What They Reveal

  • Q1 A ("kept, because the UPDATE succeeded"). Success is not commitment. Rerun the two-window step: B never saw the change until COMMIT.
  • Q3 A or D (a savepoint statement ends the transaction). Confuses bookmarks with endings; only COMMIT, ROLLBACK and implicit commits end it.
  • Q4 B ("the committed value at once"). Right for a plain SELECT, wrong for FOR UPDATE: the whole point of a locking read is to wait.
  • Q6 B ("repeat the failed statement"). The victim's whole transaction is gone; repeating one statement leaves half a transfer.
  • Q7 B (JSON_EXTRACT). Thinks the function is different from the arrow; it is the same thing. Only ->> (or JSON_UNQUOTE) removes quotes.
  • Q12 C (line items in JSON). The most tempting design mistake of the lesson: a list of related things with prices and books needs its own table and foreign keys.
  • Checkpoint, Part 3 orders = 4 for Alice. Counting rows after a join counts the many side; COUNT(DISTINCT) or aggregate before joining.
