What Is a Database?

By the end you can
  • Explain what a database and a database management system (DBMS) are, and name three problems a database solves that a spreadsheet does not
  • Tell relational databases apart from the main non-relational kinds, and pick a sensible type for a simple scenario
  • Point to the table, columns, rows, primary key and foreign key in a small example
  • Describe what SQL is and match the four CRUD operations to INSERT, SELECT, UPDATE and DELETE
  • Sketch the tables of a small online bookstore on paper, with keys and relationships
Key ideas
  • A database is organized data; a DBMS is the server that guards it. MySQL is a DBMS. Your application never touches the data files: it sends SQL to the server.
  • Why not a spreadsheet? Copies of the same fact drift apart, nothing enforces types, searches get slow, two editors overwrite each other, and everyone sees every column.
  • Relational databases keep data in tables with fixed columns, linked by keys. NoSQL databases use other shapes: documents, key-value pairs, graphs, wide columns.
  • Table, column, row. A table holds one kind of thing; a column is one named, typed piece of information; a row is one thing.
  • Primary key: unique, never empty, identifies each row (usually an id MySQL hands out). Foreign key: another table's primary key, stored to say "this row belongs to that one".
  • Store each fact once and point to it with a key. A list in a cell or a many-to-many relationship needs its own table.
  • SQL is declarative: you say what you want, not how to find it. CRUD = INSERT, SELECT, UPDATE, DELETE.
  • The database says no, with a number: 1062 duplicate key, 1366 wrong type, 1364 missing required value. That is a feature.
Worked example: following a key by hand

Keys in action, on two tiny tables: authors and their books. The book does not repeat the author's name; it stores the author's id.

CREATE DATABASE kit_shelf;
USE kit_shelf;
CREATE TABLE authors (
    id   INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);
CREATE TABLE books (
    id        INT AUTO_INCREMENT PRIMARY KEY,
    title     VARCHAR(200) NOT NULL,
    author_id INT NOT NULL            -- which author: a copy of authors.id
);
INSERT INTO authors (name) VALUES ('Frank Herbert'), ('George Orwell');
INSERT INTO books (title, author_id) VALUES
    ('Dune', 1), ('1984', 2), ('Animal Farm', 2);
Database changed

Which books did author 2 write, and who is author 2? Follow the key by hand, one table at a time (Lesson 4.3 teaches the JOIN that does it in one query):

SELECT id, title, author_id FROM books WHERE author_id = 2;
SELECT id, name FROM authors WHERE id = 2;
+----+-------------+-----------+
| id | title       | author_id |
+----+-------------+-----------+
|  2 | 1984        |         2 |
|  3 | Animal Farm |         2 |
+----+-------------+-----------+
+----+---------------+
| id | name          |
+----+---------------+
|  2 | George Orwell |
+----+---------------+

Now correct the author's name. One row changes, and every book that points at id 2 is up to date at once:

UPDATE authors SET name = 'George Orwell (Eric Blair)' WHERE id = 2;
SELECT id, name FROM authors ORDER BY id;
+----+----------------------------+
| id | name                       |
+----+----------------------------+
|  1 | Frank Herbert              |
|  2 | George Orwell (Eric Blair) |
+----+----------------------------+

In a single sheet with the author's name typed next to every book, the same correction would mean finding and fixing every copy. Last, clean up:

DROP DATABASE kit_shelf;

Installing MySQL

By the end you can
  • Choose the right MySQL release (9.7 LTS) and installation method for your computer, and recognize when a package gives you something else (an older MySQL, or MariaDB)
  • Install MySQL 9.7 LTS with the Windows MSI, the macOS package or Homebrew, the MySQL APT repository, or the official Docker image
  • Start and stop the server, and set a strong root password
  • Connect with mysql -u root -p and verify the version, user and character set with SQL
  • Diagnose the four classic first-day errors: command not found, 1045, 2002 and 2003
Key ideas
  • Two programs: the server (mysqld, listening on port 3306) and a client (the mysql command) that sends your SQL to it.
  • Install 9.7 LTS on purpose. "Latest" is an innovation release (26.x); Ubuntu's own package is 8.0 or 8.4; XAMPP and Debian give you MariaDB.
  • One path per laptop: Windows MSI + MySQL Configurator; macOS brew install mysql@9.7 or the DMG; Linux MySQL's APT/Yum repository; anywhere docker run ... mysql:9.7.
  • root gets a strong password and the default caching_sha2_password login. mysql_native_password is gone in 9.x (error 1524).
  • Log in with mysql -u root -p; a Docker container with docker exec -it mysql97 mysql -u root -p, or -h 127.0.0.1 -P <port>.
  • Ask the server, not the client: SELECT VERSION(); describes the server; mysql --version only the program on your laptop.
  • Error triage: command not found = PATH; 1045 = credentials; 2002/2003 = server stopped or wrong address.
Worked example: three questions for any server

Three questions you can ask any server in a second. A comparison prints 1 for true and 0 for false.

SELECT VERSION() LIKE '9.7.%'     AS is_mysql_97,
       VERSION() LIKE '%MariaDB%' AS is_mariadb;
+-------------+------------+
| is_mysql_97 | is_mariadb |
+-------------+------------+
|           1 |          0 |
+-------------+------------+

SHOW VARIABLES LIKE is another way to read a setting, with its name next to its value:

SHOW VARIABLES LIKE 'character_set_server';
+----------------------+---------+
| Variable_name        | Value   |
+----------------------+---------+
| character_set_server | utf8mb4 |
+----------------------+---------+

And is the server in the strict mode that refuses bad data (the mode the lesson's errors rely on)?

SELECT @@sql_mode LIKE '%STRICT_TRANS_TABLES%' AS strict_mode;
+-------------+
| strict_mode |
+-------------+
|           1 |
+-------------+

On MariaDB the first query prints 0 and 1; on a server someone has reconfigured the last one may print 0, and then some of the course's errors become silent warnings.

MySQL CLI & phpMyAdmin

By the end you can
  • Log in to and out of the mysql client, and read its prompts (mysql>, ->, '>)
  • Explore a server with SHOW DATABASES, USE, SHOW TABLES, DESCRIBE and SELECT DATABASE()
  • Tell SQL statements apart from client commands such as \G, \c, SOURCE and help
  • Save SQL in a .sql file and run it with SOURCE and with mysql < file.sql, knowing what MySQL 9.x's client does differently in scripts
  • Find the Structure, SQL, Import and Export tabs in phpMyAdmin and choose the right tool for a task
Key ideas
  • A client is any program that sends SQL to the server: the mysql command, phpMyAdmin, Workbench. Same statement, same result in all of them.
  • Log in with mysql -u root -p (no space and no password after -p); leave with exit, \q or Ctrl+D. Ctrl+C cancels a statement; it does not log you out.
  • Find your way: SHOW DATABASES; · USE name; · SELECT DATABASE(); · SHOW TABLES; · DESCRIBE table;. FROM database and database.table reach other databases without moving.
  • Nothing runs until the semicolon. -> = waiting for the end · '> = a quote is open · \c = give up.
  • SQL versus client commands: SHOW, USE, DESCRIBE work in every client; \G (vertical output), \c, SOURCE, help, status, exit only in the mysql client.
  • Run files with SOURCE path at the prompt or mysql -u root -p < file.sql from the shell (batch mode: no boxes without -t; MySQL 9.x ignores client commands there unless you add --commands).
  • Errors to know: 1049 unknown database · 1146 table not found (the message names the database it looked in) · 1064 cannot read the statement (often a reserved word such as current_time).

Creating Databases & Tables

By the end you can
  • Create, select and drop a database, with the utf8mb4 character set and an explicit collation
  • Write a CREATE TABLE statement with column names, data types and basic constraints

  • Rename, empty and drop tables, and use IF EXISTS / IF NOT EXISTS to write scripts you can rerun

Key ideas
  • Server = cabinet, database = drawer, table = folder. CREATE DATABASE, USE, DROP DATABASE (no undo).
  • Name the text settings: CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci. Never utf8 (a three-byte subset, warning 3719).
  • Names: lowercase, snake_case, plural tables (books), id for the key, customer_id for a link, no reserved words (order).
  • CREATE TABLE lists each column's name, type and rules; commas between columns, none after the last. IF NOT EXISTS leaves an existing table untouched (Note 1050).
  • Inspect: DESCRIBE t; for the columns, SHOW CREATE TABLE t\G for the full definition (engine, charset, collation).
  • ALTER TABLE adds, renames, redefines and drops columns and keeps the rows. MODIFY and CHANGE replace the whole definition: repeat NOT NULL and DEFAULT, then DESCRIBE.
  • TRUNCATE empties a table and resets AUTO_INCREMENT; DROP removes the table or database itself.
  • Build from a script that starts with DROP DATABASE IF EXISTS and can run any number of times. Errors: 1007/1050 exists · 1046 no database selected · 1064 · 1146.

Data Types & Constraints

By the end you can
  • Pick an integer type and decide when UNSIGNED makes sense; explain why money is DECIMAL, never FLOAT
  • Choose between CHAR, VARCHAR and TEXT, and between DATE, DATETIME and TIMESTAMP
  • Use BOOLEAN and ENUM correctly, knowing what MySQL really stores
  • Apply PRIMARY KEY, AUTO_INCREMENT, NOT NULL, UNIQUE, DEFAULT and named CHECK constraints
  • Read the errors strict mode raises for bad values (1048, 1062, 1264, 1265, 1292, 1364, 1406, 3819)
Key ideas
  • A type is a promise MySQL keeps: it validates values, makes math and sorting work, and decides the size.
  • Strict mode (the default) turns a value that does not fit into an error instead of a silent change. Keep it on.
  • Numbers: INT is the default; TINYINT/SMALLINT for small ranges; UNSIGNED forbids negatives. Money is DECIMAL(m, d), never FLOAT.
  • Text: VARCHAR(n) for almost everything, CHAR(n) for fixed-length codes, TEXT for long writing. Phone numbers and ZIP codes are text.
  • Dates are 'YYYY-MM-DD'. DATETIME for moments; TIMESTAMP converts time zones but ends in 2038.
  • BOOLEAN is TINYINT(1): test it with WHERE col, not = TRUE. ENUM is one value from a short, stable list.
  • Constraints: PRIMARY KEY, AUTO_INCREMENT, NOT NULL, UNIQUE, DEFAULT, named CHECK. Errors: 1048/1364 required · 1062 duplicate · 1264 out of range · 1265 not on the list · 1292 bad date · 1406 too long · 3819 CHECK.

CRUD Operations

By the end you can
  • Create rows with INSERT: one row, many rows, with defaults, and read back the new id
  • Read rows with SELECT: chosen columns, aliases, calculated columns and DISTINCT
  • Update and delete exactly the rows you mean, using the "SELECT first" habit and safe-updates mode

  • Read and fix errors 1054, 1062, 1136 and 1175
Key ideas
  • CRUD: INSERT creates, SELECT reads, UPDATE changes, DELETE removes. WHERE picks the rows; without it, every row.
  • INSERT always with a column list; several value lists in one statement; LAST_INSERT_ID() is the id just given (the first one after a multi-row insert).
  • SELECT names the columns it needs; AS renames; calculations never change the table; DISTINCT shows each value once.
  • Preview, change, compare: a SELECT with the same WHERE first; then read Rows matched and Changed.
  • Safe-updates mode (SET SQL_SAFE_UPDATES = 1;, mysql --safe-updates) refuses UPDATE/DELETE without a key in the WHERE: error 1175.
  • SET separates assignments with commas, never AND. AUTO_INCREMENT ids are never reused.
  • Upsert: INSERT ... AS new ON DUPLICATE KEY UPDATE col = new.col (1 inserted, 2 updated, 0 unchanged). REPLACE deletes and re-inserts; INSERT IGNORE skips.

WHERE Clauses, Operators & Filtering

By the end you can
  • Filter rows by numbers, text and dates with the comparison operators (=, !=, <, >, <=, >=)
  • Combine conditions with AND, OR and NOT, and use parentheses to say exactly what you mean
  • Match lists, ranges and text patterns with IN, BETWEEN and LIKE
  • Find missing values with IS NULL and explain why = NULL finds nothing
  • Spot the silent filtering mistakes (missing NULL rows, AND/OR mix-ups) and fix error 1054
  • Save a set of reusable searches in a .sql script
Key ideas
  • WHERE tests every row; only rows where the test is true are kept. False and unknown (NULL) are dropped.
  • Comparisons = != < > <= >= work on numbers, dates ('YYYY-MM-DD') and text (case-insensitive with _ci collations).
  • AND narrows, OR widens, NOT flips. AND is evaluated before OR: when you mix them, add parentheses.
  • IN a list · BETWEEN an inclusive range · LIKE a pattern (% any characters, _ exactly one).
  • NULL is unknown: test it with IS NULL / IS NOT NULL, never = NULL. !=, NOT IN and NOT LIKE silently drop NULL rows: add OR col IS NULL when you want them. Never a NULL inside NOT IN.
  • Date-and-time columns: a half-open range, >= start AND < next_start.
  • Count first: say how many rows you expect before you run a filter.

3.2

Sorting & Limiting Results

By the end you can
  • Sort results with ORDER BY on one or more columns or expressions, each ascending or descending
  • Predict where NULL values land in a sort and move them to the end
  • Take the top N rows with LIMIT, and add a tie-breaker so the result is always the same
  • Split a result into pages with LIMIT ... OFFSET, and explain when keyset pagination is better
  • Read and fix the errors MySQL raises for misplaced or malformed ORDER BY and LIMIT clauses
Key ideas
  • A table has no order: without ORDER BY, row order is not guaranteed.
  • ORDER BY is ascending by default; DESC belongs only to the column before it. Extra columns break ties.
  • Sort by expressions, aliases and CASE ranks; avoid column numbers in saved queries.
  • NULLs sort first ascending, last descending; ORDER BY col IS NULL, col puts them last (MySQL has no NULLS LAST).
  • LIMIT n OFFSET m skips m rows and keeps n; it runs last. Page N = OFFSET (N - 1) × size, computed before the query.
  • Every ORDER BY that feeds a LIMIT ends with a unique column. Count pages with a separate COUNT(*).
  • Keyset pagination (WHERE id > last_seen ORDER BY id LIMIT n) stays fast on huge tables.

Aggregate Functions & GROUP BY

By the end you can
  • Summarize a table with COUNT, SUM, AVG, MIN and MAX, and predict how each one treats NULL
  • Produce one summary row per group with GROUP BY, sorted with ORDER BY
  • Keep or drop whole groups with HAVING, and explain when to use WHERE instead
  • Read and fix the errors MySQL raises for broken aggregate queries (1140, 1055, 1111)
  • Build a small inventory report as a reusable .sql script
Key ideas
  • An aggregate turns many rows into one value: COUNT, SUM, AVG, MIN, MAX.
  • COUNT(*) counts rows; COUNT(col) counts filled-in values; COUNT(DISTINCT col) counts different values.
  • Every aggregate skips NULL (except COUNT(*)). Over no rows, COUNT gives 0 and the others NULL.
  • AVG of a DECIMAL prints extra decimals: show money with ROUND(AVG(price), 2).
  • MIN and MAX give the value, not the row. To see the row, sort and LIMIT (or, after the break, a subquery).
  • GROUP BY makes piles; the aggregate runs once per pile. Every selected column is grouped or aggregated (1140, 1055).
  • WHERE picks rows before the piles; HAVING picks piles after. An aggregate in WHERE is 1111.
  • GROUP BY does not sort on MySQL 8.0 and later: always add ORDER BY.
Worked example: WHERE removes rows, HAVING removes piles

Three small summaries that show which clause does which job. First, one pile per author, kept only when the pile has more than one book, with the first and latest publication date of each kept pile:

SELECT author,
       COUNT(*)       AS books,
       MIN(published) AS first_book,
       MAX(published) AS latest_book
FROM books
GROUP BY author
HAVING COUNT(*) > 1;
+----------------+-------+------------+-------------+
| author         | books | first_book | latest_book |
+----------------+-------+------------+-------------+
| J.R.R. Tolkien |     2 | 1937-09-21 | 1954-07-29  |
+----------------+-------+------------+-------------+

Tolkien is the only author with two books. Now a condition on single rows: WHERE keeps the books over $10 BEFORE they are piled up, so the out-of-stock pile never forms (both out-of-stock books cost 8.99):

SELECT in_stock, COUNT(*) AS books_over_10
FROM books
WHERE price > 10
GROUP BY in_stock
ORDER BY in_stock DESC;
+----------+---------------+
| in_stock | books_over_10 |
+----------+---------------+
|        1 |             5 |
+----------+---------------+

And a condition on whole piles: every book goes into a pile, then HAVING drops the pile that is too small:

SELECT in_stock, COUNT(*) AS books
FROM books
GROUP BY in_stock
HAVING COUNT(*) > 5
ORDER BY in_stock DESC;
+----------+-------+
| in_stock | books |
+----------+-------+
|        1 |     8 |
+----------+-------+

Same table, two different missing rows, for two different reasons: WHERE removed rows, HAVING removed a pile.

Subqueries & Nested Queries

By the end you can

Key ideas
  • A subquery is a SELECT in parentheses inside another statement. The inner query answers first; read from the inside out.
  • Scalar subquery = one value: works with =, >, arithmetic and in the SELECT list. = with several rows is 1242.
  • A one-column list goes with IN, ANY, ALL. Two columns in the list is 1241.
  • One NULL in a NOT IN list empties the result. Add IS NOT NULL inside, or use NOT EXISTS.
  • Correlated = refers to the outer row. Alias both copies of the table and qualify every column inside.
  • EXISTS asks "is there at least one row?" SELECT 1 inside says the columns do not matter.
  • A derived table (subquery in FROM) needs an alias (1248) and allows a summary of a summary.
  • No LIMIT inside an IN subquery (1235): wrap it in a derived table.
Worked example: a correlated subquery in two runs

4.1

Table Relationships

By the end you can
  • Explain the update, insert and delete problems of a flat table, using the bookstore's own data
  • Tell one-to-many, one-to-one and many-to-many relationships apart, and say where the foreign key goes in each

  • Read a crow's foot ER diagram of the finished bookstore database
Key ideas
  • Store each fact once, in the table it describes; other tables point at it by id. Repeated text causes update, insert and delete anomalies.
  • Primary key identifies a row; foreign key holds another table's primary key. The table with the id is the parent, the one with the pointer the child.
  • Can one A have many Bs? Yes: the foreign key goes in B (the many side). Two yeses: a junction table.
  • One-to-one = a foreign key that is also UNIQUE (or is the primary key).
  • Many-to-many = a junction table: two foreign keys and a composite primary key; it may hold facts about the link (quantity, price_at_time, joined_on).
  • Migrate safely: add the column, fill it (UPDATE ... JOIN), COUNT the NULLs, then NOT NULL, drop the old column, declare the key.
  • Create parents first, children second; drop in the opposite order (1824 for a missing parent table).

4.2

Foreign Keys & Referential Integrity

By the end you can
  • Explain referential integrity and predict when MySQL raises errors 1452 and 1451
  • Choose RESTRICT, CASCADE or SET NULL for ON DELETE and ON UPDATE, and justify the choice
  • Add, drop and change a named foreign key on an existing table, cleaning up orphan rows first
  • List a database's foreign keys and their rules from information_schema
  • Diagnose the errors raised by a badly formed key (3780, 6125, 1830)
Key ideas
  • Referential integrity: every foreign key value points at a row that exists. A declared key makes orphans impossible.
  • 1452 = a child row whose parent is missing ("add or update a child row"). 1451 = a parent that children still point at ("delete or update a parent row").
  • RESTRICT refuses · CASCADE deletes or updates the children too · SET NULL keeps them and clears the link (the column must allow NULL: 1830).
  • No rule written = NO ACTION, which MySQL enforces exactly like RESTRICT.
  • Two questions: can the child exist without its parent (no: CASCADE)? Must it keep naming it (yes: RESTRICT; no: SET NULL)? When in doubt, RESTRICT.
  • Name your keys (CONSTRAINT fk_child_parent) and use the table-level form.
  • A key on existing data: find the orphans (NOT IN (SELECT id FROM parent)), fix them truthfully, then ADD CONSTRAINT. To change a rule: DROP FOREIGN KEY, then ADD again.
  • Test destructive changes inside START TRANSACTION ... ROLLBACK.
Worked example: RESTRICT and CASCADE in one transaction

4.3

Joins

By the end you can
  • Combine matching rows from two or more tables with INNER JOIN ... ON, using table aliases
  • Keep unmatched rows with LEFT JOIN, and find rows with no match using the anti-join pattern
  • Explain what RIGHT JOIN and CROSS JOIN return, and when (rarely) to use them
  • Join a table to itself to read a hierarchy such as employees and managers
  • Combine joins with GROUP BY without the two silent traps: COUNT(*) on outer joins and row fan-out
Key ideas
  • JOIN ... ON (INNER) returns one row per matching pair; a row without a partner disappears.
  • LEFT JOIN keeps every row of the left table (the one before JOIN) and fills the right side with NULL when nothing matches.
  • Anti-join: LEFT JOIN right ... WHERE right.id IS NULL finds the rows with no match (or NOT EXISTS).
  • On a LEFT JOIN, conditions on the right table go in ON; in WHERE they turn it into an inner join.
  • A JOIN without ON is a cross join (every combination): check the ON when a join returns too many rows.
  • Self-join: one table, two aliases, two roles (employee and manager).
  • What does one row of this join stand for? Ask before COUNT or SUM: use COUNT(right.id), COUNT(DISTINCT ...), COALESCE.
  • Qualify columns that exist in both tables (1052); after an alias, use only the alias (1054).

By the end you can

  • Chain several CTEs in one statement, letting later steps read earlier ones
  • Choose between a CTE, a derived table and a view for a given job

Key ideas
  • A CTE (WITH name AS (...)) is a named result that lives for ONE statement and is read like a table: select, filter, join, group it.
  • Several CTEs, one WITH, separated by commas; each can read the ones before it, and each can be read more than once.
  • CTE, derived table or view? Derived table: a small one-off step. CTE: multi-step questions and hierarchies. View: a question the whole team asks every day (Session 9).
  • A recursive CTE = anchor (runs once) + UNION ALL + recursive member (runs per round, reading only the previous round's rows) with a stop condition.
  • The anchor fixes every column's type and width: CAST(... AS CHAR(200)) for paths and lists, or error 1406.
  • Down a hierarchy: e.manager_id = cte.id. Up: e.id = cte.manager_id.
  • cte_max_recursion_depth (1000) stops runaway recursion with error 3636; MariaDB stops quietly with a warning.

WITH RECURSIVE weeks AS (
    SELECT DATE('2026-02-01') AS week_start
    UNION ALL
    SELECT week_start + INTERVAL 7 DAY
    FROM weeks
    WHERE week_start < '2026-02-22'
)
SELECT w.week_start, COUNT(o.id) AS orders
FROM weeks AS w
LEFT JOIN orders AS o
       ON o.order_date >= w.week_start
      AND o.order_date <  w.week_start + INTERVAL 7 DAY
GROUP BY w.week_start
ORDER BY w.week_start;

| week_start | orders |

| 2026-02-01 |      1 |
| 2026-02-08 |      1 |
| 2026-02-15 |      1 |
| 2026-02-22 |      0 |
+------------+--------+

5.2

Window Functions

By the end you can
  • Explain how OVER() differs from GROUP BY, and split a window with PARTITION BY
  • Number and rank rows with ROW_NUMBER, RANK and DENSE_RANK, and pick the right one when there are ties
  • Build running totals and moving averages, and control them with a frame (ROWS BETWEEN ...)
  • Compare each row with the one before or after it using LAG and LEAD
  • Return the top N rows per group by filtering a window result in a CTE, and explain why WHERE cannot do it (error 3593)
Key ideas
  • A window function computes across a set of rows (the window) and returns a value for EVERY row: OVER turns an aggregate into one.
  • PARTITION BY splits the window per group without collapsing rows; ORDER BY inside OVER orders each window; the frame (ROWS BETWEEN ...) says which neighbors count.
  • ROW_NUMBER never ties; RANK ties and skips (1, 2, 2, 4); DENSE_RANK ties without gaps (1, 2, 2, 3).
  • Running total: SUM(x) OVER (ORDER BY t ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW). The default frame is RANGE, which lumps ties together.
  • LAG / LEAD read the previous / next row, with an optional offset and default.
  • Windows run after WHERE, GROUP BY and HAVING: filter on them in an outer query over a CTE (error 3593 otherwise). Top N per group = ROW_NUMBER in a CTE, WHERE pos <= N outside.
  • Reserved words: rank, row_number, window, groups: name columns rank_num, pos.
Worked example: two windows per customer, and the first value

Two windows over the same partition: which order is this for the customer (ROW_NUMBER), and how many orders does the customer have in all (COUNT(*) OVER)? No GROUP BY, so every order stays:

SELECT c.first_name,

Indexes & Query Optimization

By the end you can
  • Explain what an index is, what it costs, and which indexes every bookstore table already has
  • Read a query plan from EXPLAIN and measure a query with EXPLAIN ANALYZE
  • Create single-column, composite and unique indexes, and choose the column order of a composite index
  • Spot and rewrite the patterns that stop an index from being used: functions on the column, leading wildcards, type mismatches
  • List, rename, hide and drop indexes, and fix the errors MySQL raises while you do it
Key ideas
  • An index is a sorted B-tree copy of one or more columns: it turns a full table scan into a jump to the matching rows. It costs space and write time.
  • Automatic indexes: every primary key (the clustered index: the table itself), every UNIQUE, every foreign key.
  • EXPLAIN shows the plan (read the most indented line first); EXPLAIN ANALYZE runs the query and adds real times and row counts. End with \G.
  • Plan words: Rows fetched before execution · Single-row lookup · Index lookup · Index range scan · Covering · Index scan · Table scan · Sort.
  • Composite index: serves its leftmost prefix. Equality columns first, the range or sort column last.
  • Index killers: a function or arithmetic around the column, a leading % in LIKE, a text column compared with a number.
  • Manage: SHOW INDEX, RENAME INDEX, INVISIBLE before DROP; 1061 duplicate name, 1091 no such index, 1553 needed by a foreign key.

6.2

Views

By the end you can
  • Explain what a view stores (a query, not data) and read the definition MySQL saves
  • Create, query, replace and drop views, including views over joins and aggregates
  • Predict whether a view is updatable, and protect it with WITH CHECK OPTION
  • Use a view to hide sensitive columns, and grant access to the view alone
  • Recognize and fix the errors views raise (1050, 1288, 1356, 1369, 1393)
Key ideas
  • A view is a saved SELECT: it stores the query, never the rows, and is recomputed every time you read it.
  • Read it like a table; put ORDER BY in the query that reads it, not in the view.
  • CREATE OR REPLACE VIEW makes scripts rerunnable; DROP VIEW removes only the definition.
  • Updatable when each view row is one base row: no GROUP BY, aggregates, DISTINCT, UNION or window functions. A join view may change one table per statement.
  • WITH CHECK OPTION refuses writes that would push a row out of the view (1369).
  • SQL SECURITY DEFINER: an account with SELECT on the view alone sees the view's columns and rows, and nothing else of the table.
  • Frozen and fragile: SELECT * is expanded at creation; renamed or dropped columns break a view (1356).
Worked example: a view that filters a window

A view can hold a window function. Since a view is read like a table, the query that reads it can filter on the window's result: the CTE pattern of Session 8, saved under a name:

CREATE VIEW v_price_rank AS
SELECT title, price,
       ROW_NUMBER() OVER (ORDER BY price DESC, title) AS pos
FROM books;
SELECT pos, title, price FROM v_price_rank WHERE pos <= 3 ORDER BY pos;

Database Design & Normalization

By the end you can
  • Recognize update, insert and delete anomalies, and show each one with a query
  • Find the functional dependencies and the key of a table
  • Normalize a flat table to first, second and third normal form (1NF, 2NF, 3NF)
  • Build the normalized tables with INSERT ... SELECT DISTINCT and prove with EXCEPT that no data was lost
  • Read an ER diagram, and decide when storing derived or duplicated data is worth the risk
Key ideas
  • Anomalies: update (copies drift), insert (a fact needs another fact to exist), delete (removing one fact removes another). One cause: facts about different things in one row.
  • A → B: same A, same B. Dependencies come from business rules; data can disprove one, never prove it.
  • 1NF: one value per cell, no repeating columns, a key. 2NF: no column depends on part of a composite key. 3NF: no column depends on a non-key column.
  • Migrate with INSERT ... SELECT DISTINCT, parents first, children last, joining back on the natural identifiers.
  • Prove it lossless with EXCEPT in both directions: two empty sets.
  • ER diagrams: a line's "one" end holds the primary key, the "many" end the foreign key; many at both ends means a missing junction table.
  • Do not store what you can compute. Denormalize only for a measured problem, with a plan to keep the copy in sync.
Worked example: a key and a dependency, tested on the bookstore

Stored Procedures & Functions

By the end you can

  • Create and call stored procedures with IN, OUT and INOUT parameters
  • Write stored functions with the right characteristic (DETERMINISTIC, READS SQL DATA) and use them inside queries

Key ideas
  • Procedure: CALL name(...); result sets, OUT and INOUT parameters, changes data. Function: returns one value, used inside expressions.
  • DELIMITER // ... // is a client command: the client waits for // so a body with semicolons is sent whole. Switch back with DELIMITER ;.
  • OUT parameters land in user variables: CALL p(1, @x); SELECT @x;. SELECT ... INTO must find at most one row (1172).
  • DECLARE local variables first in a block; p_ and v_ prefixes so names never shadow columns.
  • Function characteristics (DETERMINISTIC, NO SQL, READS SQL DATA) are required with binary logging on (1418), and must be true.
  • SIGNAL SQLSTATE '45000' refuses bad input with your own message (1644). Check before you change.
  • Rerunnable scripts: DROP PROCEDURE IF EXISTS / DROP FUNCTION IF EXISTS, then CREATE (no CREATE OR REPLACE in MySQL).

Transactions

By the end you can
  • Group changes with START TRANSACTION, COMMIT and ROLLBACK, and explain autocommit and implicit commits
  • Undo part of a transaction with SAVEPOINT and ROLLBACK TO SAVEPOINT
  • Predict what a second connection sees and when it has to wait, under MySQL's default REPEATABLE READ isolation
  • Lock rows on purpose with SELECT ... FOR UPDATE, and read lock errors 1205 and 1213
  • Write a stored procedure whose error handler rolls back the whole transaction and passes the error on
Key ideas
  • A transaction is all or nothing: START TRANSACTION, your statements, then COMMIT (keep) or ROLLBACK (discard).
  • Autocommit (on by default) commits every statement by itself. START TRANSACTION suspends it until COMMIT or ROLLBACK.
  • Implicit commits: CREATE, ALTER, DROP, TRUNCATE and account statements commit the open transaction before they run.
  • A failed statement undoes only itself: after an error inside a transaction, ROLLBACK (or let a handler do it).
  • Savepoints undo part of a transaction and keep it open: SAVEPOINT s; ... ROLLBACK TO SAVEPOINT s;
  • Isolation (REPEATABLE READ): plain reads see committed data from a snapshot and never wait; writers wait for row locks (1205 after the timeout).
  • FOR UPDATE locks the rows you are about to change; a deadlock (1213) rolls one transaction back: retry it whole.
  • In procedures: DECLARE EXIT HANDLER FOR SQLEXCEPTION BEGIN ROLLBACK; RESIGNAL; END;

7.3

JSON Columns

By the end you can
  • Add a JSON column and explain how MySQL validates and stores what you put in it
  • Read values with ->, ->> and JSON_EXTRACT, and filter rows on them
  • Change parts of a document with JSON_SET, JSON_INSERT, JSON_REMOVE and JSON_ARRAY_APPEND
  • Turn rows into JSON with JSON_OBJECT and JSON_ARRAYAGG, and JSON back into rows with JSON_TABLE
  • Index a JSON path through a generated column, and decide when data belongs in real columns instead
Key ideas
  • A JSON column holds one validated document per row (error 3140 for invalid JSON), stored in a binary form with sorted keys.
  • Paths start at $: $.format, $.awards[0], $.awards[last], $.awards[*].
  • -> (= JSON_EXTRACT) returns JSON, with quotes; ->> returns plain text for display, comparison and sorting.
  • A missing key is NULL, not an error, so a misspelled key fails silently.
  • JSON_SET / INSERT / REPLACE / REMOVE / ARRAY_APPEND return a changed copy; UPDATE stores it.
  • JSON_OBJECT and JSON_ARRAYAGG build JSON from rows; JSON_TABLE turns JSON back into rows.
  • Index a path through a generated column; protect important keys with a CHECK.
  • Core data stays in columns and tables: what every row has, what you join on or calculate with.
Worked example: a JSON message becomes rows

A review widget sends one JSON message with several reviews. JSON_TABLE turns it into rows that join and group like any table.

SET @reviews = '{"source": "web", "reviews": [
    {"book_id": 1, "stars": 5}, {"book_id": 1, "stars": 4},
    {"book_id": 6, "stars": 5}, {"book_id": 2, "stars": 3}]}';
SELECT b.title, COUNT(*) AS reviews, AVG(r.stars) AS avg_stars

User Management & Permissions

By the end you can
  • Create accounts as 'user'@'host' and explain how MySQL 9.7 stores their passwords (caching_sha2_password)
  • Grant and revoke privileges at the global, database, table and column level, and read SHOW GRANTS

  • Design least-privilege accounts for an application, a report and staff, and script them
Key ideas
  • Least privilege: every account gets the minimum it needs; nobody shares root, applications never use it.
  • An account is 'user'@'host'. The same name with another host is another account.
  • New accounts have only USAGE (may connect). GRANT what ON where TO whom adds; REVOKE ... FROM removes, at the same level.
  • Levels: *.* global, db.* database, db.table, columns SELECT (a, b), routines EXECUTE ON PROCEDURE.
  • Test both directions as the account: 1142 (table), 1143 (column), 1044 (database at login), 3118 (locked).
  • Roles bundle privileges; they work only once active: SET DEFAULT ROLE ALL TO ....
  • ACCOUNT LOCK disables an account and keeps its grants; DROP USER removes both.
  • caching_sha2_password is the default; mysql_native_password is gone in 9.x (1524): update the driver.

Key ideas

  • A dump holds no accounts: keep your CREATE USER and GRANT scripts.
  • Server-side files live in the secure_file_priv folder (1290 elsewhere, 1086 if the file exists) and need FILE.
  • LOCAL sends a file from your computer; local_infile must be on at both ends, and errors become warnings: read them.
  • Staging tables: load as text, convert with @variables, NULLIF, STR_TO_DATE, check with a LEFT JOIN, copy in one transaction.

Today: the last two, and all five in the showcase.

Key ideas
  • The procedure is the only door into loans. The desk's account gets EXECUTE, not INSERT; the procedure runs with its definer's rights, so every loan passes every rule.
  • Shape: START TRANSACTION → read and lock (SELECT ... FOR UPDATE) → check each rule, SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '...' → INSERT → COMMIT.
  • One handler: DECLARE EXIT HANDLER FOR SQLEXCEPTION BEGIN ROLLBACK; RESIGNAL; END; undoes everything and passes the real message on.
  • Every rule gets a call that must fail, and one call must succeed.
  • Roles per job, accounts per program or person, SET DEFAULT ROLE, no DELETE anywhere. Test by logging in as the account.
  • A backup is only a backup once it has been restored: mysqldump with --single-transaction --routines --events --set-gtid-purged=OFF, restore into a test database, compare counts. Accounts are not in the dump: 05_security.sql is their backup.

Next Steps & Best Practices

  • Apply a short list of design, query, security and operations practices to any MySQL project
  • Audit a database with information_schema queries for missing keys, risky types and old character sets

Key ideas
  • Design: a primary key everywhere; normalize first; DECIMAL for money, DATE for dates, utf8mb4 for text; constraints the database enforces; consistent names.
  • Queries: name the columns; ORDER BY when order matters; preview with SELECT before UPDATE or DELETE; never switch off strict mode to hide an error; EXPLAIN before tuning.
  • Security: parameterized queries always; one least-privilege account per application; secrets outside the code; caching_sha2_password; supported releases.
  • Operations: automatic backups with tested restores; the schema in version-controlled scripts; the slow query log; LTS releases (9.7, 8.4), asked for by name.
  • information_schema describes every database as tables: TABLES, COLUMNS, TABLE_CONSTRAINTS, REFERENTIAL_CONSTRAINTS, KEY_COLUMN_USAGE, STATISTICS.
  • SQL injection: input glued into SQL can rewrite it. A placeholder (?, %s, :name, @name) sends the value separately; at the prompt: PREPARE ... EXECUTE ... USING.
