6.3

Database Design & Normalization

Each fact stored once, in the right place.

6.3 · Mental model

One big sheet corrupts itself

  • Update: one copy changes, the others do not
  • Insert: a customer cannot exist without an order
  • Delete: cancel the only order, lose the customer
  • One cause: facts about different things in one row
WHY Fix: a table per kind of thing, connected by keys.

6.3 · Dependencies

A → B: same A, same B

  • order_id → order_date, cust_email
  • cust_email → cust_name, cust_city
  • book_title → book_price
  • Key of the lines: (order_id, book_title)
  • Data can disprove a rule, never prove one
6.3 · Normal forms

The key, the whole key, nothing but the key

  • 1NF: one value per cell, a key: one row per item
  • 2NF: nothing depends on part of the key: a table per part
  • 3NF: nothing depends on a non-key column: a table per hidden thing
  • Result: customers, books, orders, order_items

7.1

Stored Procedures & Functions

Logic saved next to the data, with a name and parameters.

7.1 · Mental model

Procedure or function?

  • Procedure: CALL name(...), result sets, OUT values, changes data
  • Function: one value, inside a query: SELECT with_tax(price)
  • One copy of the rule for every app that calls it
  • Costs: logic in two places, its own version control
7.1 · DELIMITER

A client command

DELIMITER //
CREATE PROCEDURE say_hello()
BEGIN
    SELECT 'Hello from the bookstore!' AS greeting;
    SELECT COUNT(*) AS books_in_stock FROM books WHERE in_stock = TRUE;
END //
DELIMITER ;
CALL say_hello();
WHY The CLIENT waits for //. The server never sees the word DELIMITER.
7.1 · OUT

An answer through a variable

DELIMITER //
CREATE PROCEDURE count_books_by(
    IN  p_author VARCHAR(100),
    OUT p_count  INT)
BEGIN
    SELECT COUNT(*) INTO p_count
    FROM books AS b
    JOIN authors AS a ON a.id = b.author_id
    WHERE a.name = p_author;
END //
DELIMITER ;
CALL count_books_by('J.R.R. Tolkien', @n);
SELECT @n AS tolkien_books;
+---------------+
| tolkien_books |
+---------------+
|             2 |
+---------------+
WHY SELECT ... INTO prints nothing: the answer lands in @n.
7.1 · Characteristics

What a function promises

  • DETERMINISTIC: same inputs, same result
  • NO SQL: no table read · READS SQL DATA: reads, never changes
  • Binary logging is on by default: none of them = ERROR 1418
  • The server cannot check your promise: make it true
7.1 · SIGNAL

Check first, then change

CALL set_book_price(5, -1.00);
CALL set_book_price(99, 9.99);
ERROR 1644 (45000): Price must be greater than zero
ERROR 1644 (45000): No book with that id
WHY '45000' = your own error, reported as 1644. Nothing changed.
7.1 · Silent

Book 1, please

CREATE PROCEDURE book_by_id(IN id INT)
    SELECT b.id, b.title FROM books AS b WHERE id = id ORDER BY b.id;
CALL book_by_id(1);
  • Inside the routine, a bare id is the parameter
  • WHERE id = id is 1 = 1: all eleven books come back
  • Fix: p_id, v_total, or b.id
WATCH Picture this in a DELETE.
7.1 · Common mistakes

Five routine errors

  • 1064 twice: a body without DELIMITER
  • 1418: a function without characteristics
  • 1172: SELECT ... INTO finds two rows
  • 1304: created twice: DROP ... IF EXISTS first
  • 1644: your own SIGNAL (that one is the design working)
