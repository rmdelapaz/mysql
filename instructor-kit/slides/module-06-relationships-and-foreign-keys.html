4.1

Table Relationships

Which facts belong in which table, and how tables point at each other.

4.1 · Mental model

One big table, four anomalies

  • Duplication: Alice's name and email on every row she bought
  • Update: change her email, miss one row: the table disagrees with itself
  • Delete: delete Bob's only sale and Bob is gone
  • Insert: a customer who bought nothing has nowhere to go
WHY Store each fact once, in the table it describes; point at it by id.
4.1 · Where does the key go?

One question places every foreign key

  • Can one A have many Bs? Can one B have many As?
  • One yes: the key on the many side (books.author_id)
  • One-to-one: a foreign key that is also UNIQUE
  • Two yeses: a junction table (book_categories)
4.1 · The problem

An update anomaly, on purpose

UPDATE books SET author = 'J. R. R. Tolkien' WHERE id = 9;
SELECT author, COUNT(*) AS books
FROM books
WHERE author LIKE '%Tolkien%'
GROUP BY author
ORDER BY author;
+------------------+-------+
| author           | books |
+------------------+-------+
| J. R. R. Tolkien |     1 |
| J.R.R. Tolkien   |     1 |
+------------------+-------+
SILENT No error. The books-per-author report is now quietly wrong.
4.1 · Migration

Four steps, in this order

  1. Create the parent and fill it: authors
  2. Add the key column to the child: author_id (NULL everywhere)
  3. Fill it by matching: UPDATE ... JOIN ... SET
  4. COUNT the NULLs, then lock in: NOT NULL, drop the text, add the key
RULE DROP COLUMN has no undo. Check first.

4.1 · The check

Before anything is dropped

SELECT COUNT(*) AS books_without_author_id
FROM books
WHERE author_id IS NULL;
+-------------------------+
| books_without_author_id |
+-------------------------+
|                       0 |
+-------------------------+
WHY A misspelled name would have left a NULL here.
4.1 · Step 4

Lock it in

ALTER TABLE books
    MODIFY COLUMN author_id INT NOT NULL,
    DROP COLUMN author,
    ADD CONSTRAINT fk_books_author
        FOREIGN KEY (author_id) REFERENCES authors(id)
        ON DELETE RESTRICT
        ON UPDATE CASCADE;
DESCRIBE books;   -- the author_id row:
+-----------+--------------+------+-----+---------+----------------+
| Field     | Type         | Null | Key | Default | Extra          |
+-----------+--------------+------+-----+---------+----------------+
| author_id | int          | NO   | MUL | NULL    |                |
+-----------+--------------+------+-----+---------+----------------+
WHY MUL: MySQL indexed the foreign key.
4.1 · Use it

The author is one lookup away

SELECT
    title,
    (SELECT name FROM authors WHERE authors.id = books.author_id) AS author
FROM books
WHERE author_id IN (2, 6)
ORDER BY title;

| title             | author         |
+-------------------+----------------+
| 1984              | George Orwell  |
| Lord of the Rings | J.R.R. Tolkien |
| The Hobbit        | J.R.R. Tolkien |

4.1 · One-to-one

UNIQUE makes the "one"

CREATE TABLE customer_profiles (
    id INT AUTO_INCREMENT PRIMARY KEY,
    customer_id INT NOT NULL UNIQUE,
    favorite_genre VARCHAR(50),
    CONSTRAINT fk_profiles_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
);
INSERT ... VALUES (1, 'Science Fiction');
INSERT ... VALUES (1, 'Fantasy');
ERROR 1062 (23000): Duplicate entry '1' for key 'customer_profiles.customer_id'
WHY Without UNIQUE it silently becomes one-to-many.
4.1 · Many-to-many

A junction table: one row per link

CREATE TABLE book_categories (
    book_id     INT NOT NULL,
    category_id INT NOT NULL,
    PRIMARY KEY (book_id, category_id),
    CONSTRAINT fk_bc_book FOREIGN KEY (book_id)
        REFERENCES books(id) ON DELETE CASCADE,
    CONSTRAINT fk_bc_category FOREIGN KEY (category_id)
        REFERENCES categories(id) ON DELETE CASCADE
);
INSERT INTO book_categories (book_id, category_id) VALUES (2, 5);  -- again
ERROR 1062 (23000): Duplicate entry '2-5' for key 'book_categories.PRIMARY'
WHY The composite key: each pair once.

4.2

Foreign Keys & Referential Integrity

What the keys actually do, and the rules you choose.

4.2 · Mental model

Who is checked, and when

  • Child INSERT or key UPDATE: does the parent exist? No: 1452
  • Parent DELETE or key UPDATE: do children point at it? Apply the rule
  • RESTRICT (or no rule): refuse, 1451
  • CASCADE: the children go too · SET NULL: they stay, unlinked
WHY Read the first words: "child row" = 1452, "parent row" = 1451.
4.2 · Errors

1452 and 1451

INSERT INTO orders (customer_id, order_date) VALUES (999, '2026-06-15');
DELETE FROM customers WHERE id = 1;
ERROR 1452 (23000): Cannot add or update a child row
ERROR 1451 (23000): Cannot delete or update a parent row
  • Customer 999 does not exist: a child without a parent
  • Alice has three orders: fk_orders_customer is RESTRICT
4.2 · CASCADE

Order lines go with their order

START TRANSACTION;
SELECT id, order_id, book_id FROM order_items WHERE order_id = 1;
DELETE FROM orders WHERE id = 1;
SELECT id, order_id, book_id FROM order_items WHERE order_id = 1;
ROLLBACK;
+----+----------+---------+
| id | order_id | book_id |
+----+----------+---------+
|  1 |        1 |       1 |
|  2 |        1 |       2 |
+----+----------+---------+
Empty set
WHY Inside a transaction: ROLLBACK puts everything back.

4.2 · The map

Every delete rule in the bookstore

SELECT TABLE_NAME, CONSTRAINT_NAME, DELETE_RULE
FROM information_schema.REFERENTIAL_CONSTRAINTS
WHERE CONSTRAINT_SCHEMA = 'bookstore' ORDER BY 1, 2;
+-----------------+----------------------+-------------+
| TABLE_NAME      | CONSTRAINT_NAME      | DELETE_RULE |
+-----------------+----------------------+-------------+
| book_categories | fk_bc_book           | CASCADE     |
| book_categories | fk_bc_category       | CASCADE     |
| books           | fk_books_author      | RESTRICT    |
| employees       | fk_employees_manager | SET NULL    |
| order_items     | fk_items_book        | RESTRICT    |
| order_items     | fk_items_order       | CASCADE     |
| orders          | fk_orders_customer   | RESTRICT    |
+-----------------+----------------------+-------------+
4.2 · Choosing

Two questions

  1. Can the child exist without its parent? No: CASCADE
  2. Yes, and it must keep naming the parent: RESTRICT
  3. Yes, and the link is optional: SET NULL (nullable column)
  4. When in doubt: RESTRICT. A wrong cascade costs data.
4.2 · Dirty data

Adding a key to a table with an orphan

ALTER TABLE demo_staff
    ADD CONSTRAINT fk_staff_department
        FOREIGN KEY (department_id) REFERENCES demo_departments(id)
        ON DELETE SET NULL;
ERROR 1452 (23000): Cannot add or update a child row  (#sql-... copy)
  1. Find: WHERE department_id NOT IN (SELECT id FROM demo_departments)
  2. Fix with the truth (here: NULL, not assigned yet)
  3. Then add the key
