6.1

Indexes & Query Optimization

Measure, index, measure again.

6.1 · Mental model

The index at the back of the book

  • Without an index: read every row (a full table scan)
  • An index: the column's values, sorted, each pointing to its row
  • Stored as a B-tree: 3 or 4 levels for a million values
  • The primary key is the table itself (the clustered index)
PRICE Costs: space, slower writes, more plans to choose from.
6.1 · Setup

A table big enough to notice

  • The lesson's sales_log: 100,000 rows, 2020 to 2026
  • Built with a CTE and a cross join: everyone gets the same rows
  • ANALYZE TABLE sales_log;: fresh statistics
  • Paste it from the lesson page; it takes about a second
6.1 · Already there

Indexes you never created

  • PRIMARY: every primary key
  • email: every UNIQUE constraint
  • fk_orders_customer: every foreign key column
  • SHOW INDEX FROM orders; or information_schema.STATISTICS
6.1 · Measure

Before: a full table scan

EXPLAIN SELECT * FROM sales_log WHERE sold_on = '2025-03-15'\G
*************************** 1. row ***************************
EXPLAIN: -> Filter: (sales_log.sold_on = DATE'2025-03-15')  (cost=10078 rows=9990)
    -> Table scan on sales_log  (cost=10078 rows=99900)
WHY Read from the most indented line up: scan 100,000 rows, keep 42.
6.1 · Index

After: one jump

CREATE INDEX idx_sales_sold_on ON sales_log (sold_on);
EXPLAIN SELECT * FROM sales_log WHERE sold_on = '2025-03-15'\G
*************************** 1. row ***************************
EXPLAIN: -> Index lookup on sales_log using idx_sales_sold_on (sold_on =
      DATE'2025-03-15')  (cost=14.7 rows=42)
WHY EXPLAIN ANALYZE here: 16.5 ms before, 0.0779 ms after (your times differ).
6.1 · Plan words

What the plan tells you

  • Rows fetched before execution: a constant on a primary or unique key
  • Index lookup: jump to one value · Index range scan: a slice
  • Covering: the index alone answers
  • Table scan: every row: fine on small tables, fix on big ones
6.1 · Composite

Phone-book order

  • (customer_id, sold_on): by customer, then by date
  • Seeks on customer_id, or customer_id + a date range
  • Not on a date range alone
  • Equality columns first, the range or sort column last
WHY The order in WHERE does not matter. The order in the index does.
6.1 · Index killers

Hiding the column from its index

  • A function: YEAR(sold_on) = 2025 → a range on the bare column
  • Arithmetic: price * 1.1 > 10 → move it to the other side
  • A leading wildcard: '%@example.com'
  • A number for a text column: receipt_no = 4242
WATCH Same rows, but a Table scan. EXPLAIN catches every one.
6.1 · Manage

Hide before you drop

  • ALTER TABLE t ALTER INDEX idx INVISIBLE;: ignored, still maintained
  • Slow queries? VISIBLE again, instantly
  • DROP INDEX idx ON t; never touches the rows
  • 1061 name taken · 1091 no such index · 1553 needed by a foreign key

6.2

Views

A saved SELECT with a name.

6.2 · Mental model

A window in a wall

  • A view stores a query, never rows
  • Read it like a table; it is recomputed every time
  • Three jobs: reuse · a safe slice to edit · security
  • No indexes of its own: it is as fast as its query
6.2 · Code

Your first view

CREATE VIEW v_chicago_customers AS
SELECT id, first_name, last_name, email
FROM customers
WHERE city = 'Chicago';
SELECT * FROM v_chicago_customers ORDER BY id;
+----+------------+-----------+-------------------+
| id | first_name | last_name | email             |
+----+------------+-----------+-------------------+
|  2 | Bob        | Smith     | bob@example.com   |
|  7 | Grace      | Wilson    | grace@example.com |
+----+------------+-----------+-------------------+
WHY The WHERE city = 'Chicago' is baked in.
6.2 · Reuse

A five-table join, one line

SELECT author, SUM(quantity) AS copies, SUM(line_total) AS revenue
FROM v_order_details
GROUP BY author
ORDER BY revenue DESC, author;

6.2 · Updatable?

MySQL's verdict

SELECT TABLE_NAME, IS_UPDATABLE
FROM information_schema.VIEWS
WHERE TABLE_SCHEMA = 'bookstore'
ORDER BY TABLE_NAME;
+---------------------+--------------+
| TABLE_NAME          | IS_UPDATABLE |
+---------------------+--------------+
| v_chicago_customers | YES          |
| v_customer_summary  | NO           |
| v_order_details     | YES          |
| v_staff_directory   | YES          |
+---------------------+--------------+
WHY Grouping = read-only. One view row = one base row = updatable.
6.2 · Guard

WITH CHECK OPTION

CREATE OR REPLACE VIEW v_chicago_customers AS
SELECT id, first_name, last_name, email, city
FROM customers
WHERE city = 'Chicago'
WITH CHECK OPTION;
UPDATE v_chicago_customers SET city = 'Boston' WHERE id = 2;
ERROR 1369 (HY000): CHECK OPTION failed 'bookstore.v_chicago_customers'
WHY Writes that would push a row out of the view are refused.
6.2 · Security

Read the view, not the table

+-------------------------------------------------------------------------------+
| Grants for support_demo@localhost                                             |
+-------------------------------------------------------------------------------+
| GRANT USAGE ON *.* TO `support_demo`@`localhost`                              |
| GRANT SELECT ON `bookstore`.`v_staff_directory` TO `support_demo`@`localhost` |
+-------------------------------------------------------------------------------+
  • The view hides salary and inactive staff
  • SQL SECURITY DEFINER: it reads employees with its creator's rights
RULE A view is only as safe as the columns it selects.
6.2 · Common mistakes

Five view errors

  • 1050: CREATE VIEW twice → CREATE OR REPLACE VIEW
  • 1288: updating a grouped view
  • 1369: a write the check option refuses
  • 1356: a column the view uses was renamed
  • Silent: SELECT * is frozen when the view is created
6.2 · Predict, then run

What does this print?

CREATE VIEW v_pricey AS SELECT title FROM books WHERE price > 12;
START TRANSACTION;
UPDATE books SET price = 9.00 WHERE id = 1;
SELECT title FROM v_pricey ORDER BY title;
ROLLBACK;
DROP VIEW v_pricey;
  • Does the view need refreshing?
  • What does it show after ROLLBACK?
