🛡️ Lesson 4.2: Foreign Keys & Referential Integrity

In the last lesson you declared foreign keys while building the bookstore. Now find out what they actually do. What stops an order for customer 999, who does not exist? What happens to a customer's orders when someone deletes the customer, or to a team when its manager leaves? Foreign key rules answer each question, and you get to choose the answers.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Explain referential integrity and predict when MySQL raises errors 1452 and 1451
  • Choose RESTRICT, CASCADE or SET NULL for ON DELETE and ON UPDATE, and justify the choice
  • Add, drop and change a named foreign key on an existing table, cleaning up orphan rows first
  • List a database's foreign keys and their rules from information_schema
  • Diagnose the errors raised by a badly formed key (3780, 6125, 1830)

  • 📋 Prerequisites Lesson 4.1: Table Relationships
  • 🛠️ You will build a book_reviews table with two different delete rules, and prove each rule works

🔒 What Is Referential Integrity?

Referential integrity means every foreign key value points at a row that really exists: every orders.customer_id is the id of a real customer, every order_items.book_id a real book. A child row whose parent is missing is called an orphan, and a declared foreign key makes orphans impossible.

💡 Start from a fresh copy

From this lesson on, begin by loading the course database, so your results match the ones shown. In the mysql client, give the path to the bookstore.sql you saved in Lesson 4.1 (on Windows, use forward slashes: SOURCE C:/Users/you/mysql-course/bookstore.sql). The file drops and rebuilds bookstore, then selects it.

SOURCE ~/mysql-course/bookstore.sql

From a terminal instead: mysql -u root -p < bookstore.sql, then USE bookstore; in the client. In phpMyAdmin, use the Import tab.

Try to create an order for a customer who does not exist:

INSERT INTO orders (customer_id, order_date) VALUES (999, '2026-06-15');

Error

ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`bookstore`.`orders`, CONSTRAINT `fk_orders_customer` FOREIGN KEY (`customer_id`) REFERENCES `customers` (`id`) ON DELETE RESTRICT ON UPDATE CASCADE)

Read the message from the end: the constraint fk_orders_customer in table bookstore.orders says customer_id must match a customers.id, and 999 does not. Nothing was inserted.

MySQL checks a foreign key in four situations. Two of them happen in the child table, two in the parent:

You do thisOnMySQL checksIf it fails
INSERT or UPDATE a foreign key valuechild (orders)Does the parent row exist?ERROR 1452
DELETE a rowparent (customers)Do children point at it? Then apply ON DELETEERROR 1451 (with RESTRICT)
UPDATE a primary key valueparentDo children point at it? Then apply ON UPDATEERROR 1451 (with RESTRICT)

✅ Why let the database do this?

Your application should validate input too, but applications have bugs, and people run SQL by hand. A constraint protects the data no matter which program, script or person touches it.

📝 Declaring a Foreign Key

Here is how bookstore.sql declares the two keys of order_items. SHOW CREATE TABLE prints a table's full definition; \G prints it vertically, which is easier to read than a very wide table:

SHOW CREATE TABLE order_items\G

Output

*************************** 1. row ***************************
       Table: order_items
Create Table: CREATE TABLE `order_items` (
  `id` int NOT NULL AUTO_INCREMENT,
  `order_id` int NOT NULL,
  `book_id` int NOT NULL,
  `quantity` int NOT NULL DEFAULT '1',
  `price_at_time` decimal(8,2) NOT NULL,
  PRIMARY KEY (`id`),
  KEY `fk_items_order` (`order_id`),
  KEY `fk_items_book` (`book_id`),
  CONSTRAINT `fk_items_book` FOREIGN KEY (`book_id`) REFERENCES `books` (`id`) ON DELETE RESTRICT ON UPDATE CASCADE,
  CONSTRAINT `fk_items_order` FOREIGN KEY (`order_id`) REFERENCES `orders` (`id`) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE=InnoDB AUTO_INCREMENT=19 DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci

Each key has four parts: an optional name (CONSTRAINT fk_items_order), the child column (FOREIGN KEY (order_id)), the parent column (REFERENCES orders (id)), and optional rules (ON DELETE ... ON UPDATE ...). MySQL also added an index for each foreign key column (KEY `fk_items_order`), so it can find a parent's children fast.

Name your keys

Leave the name out and MySQL invents one. Try it on two scratch tables (the demo_ prefix keeps them apart from the real ones):

CREATE TABLE demo_departments (
    id   INT PRIMARY KEY,
    name VARCHAR(50) NOT NULL
);

CREATE TABLE demo_staff (
    id            INT PRIMARY KEY,
    name          VARCHAR(50) NOT NULL,
    department_id INT,
    FOREIGN KEY (department_id) REFERENCES demo_departments(id)
);

SELECT CONSTRAINT_NAME, DELETE_RULE, UPDATE_RULE
FROM information_schema.REFERENTIAL_CONSTRAINTS
WHERE CONSTRAINT_SCHEMA = 'bookstore'
  AND TABLE_NAME = 'demo_staff';

Output

+-------------------+-------------+-------------+
| CONSTRAINT_NAME   | DELETE_RULE | UPDATE_RULE |
+-------------------+-------------+-------------+
| demo_staff_ibfk_1 | NO ACTION   | NO ACTION   |
+-------------------+-------------+-------------+

demo_staff_ibfk_1 ("InnoDB foreign key number 1") tells you nothing when it appears in an error at 2 a.m. The bookstore uses fk_<child>_<parent> names such as fk_orders_customer. Notice also the rules: with no ON DELETE or ON UPDATE written, both are NO ACTION, which in MySQL behaves exactly like RESTRICT (more below).

What a foreign key needs

RequirementIf not
Child and parent columns have the same type, size and sign (INT to INT, not BIGINT or INT UNSIGNED); text columns also need the same character set and collationERROR 3780
The parent column is the primary key or has a UNIQUE indexERROR 6125 (MySQL 8.4 and later)
The parent table existsERROR 1824
Both tables use the InnoDB engine (MySQL's default)other engines ignore foreign keys
A SET NULL rule needs a child column that allows NULLERROR 1830

The short form on a column

You can also write the reference right after the column, without the FOREIGN KEY line:

CREATE TABLE demo_wishlist (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    customer_id INT NOT NULL REFERENCES customers(id)
);

SELECT CONSTRAINT_NAME
FROM information_schema.REFERENTIAL_CONSTRAINTS
WHERE CONSTRAINT_SCHEMA = 'bookstore'
  AND TABLE_NAME = 'demo_wishlist';

Output

+----------------------+
| CONSTRAINT_NAME      |
+----------------------+
| demo_wishlist_ibfk_1 |
+----------------------+

MySQL 9.7 turns it into a real foreign key. MySQL 8.4 and earlier accept the same statement and then silently ignore the reference:

CREATE TABLE demo_wishlist (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    customer_id INT NOT NULL REFERENCES customers(id)
);

SELECT CONSTRAINT_NAME
FROM information_schema.REFERENTIAL_CONSTRAINTS
WHERE CONSTRAINT_SCHEMA = 'bookstore'
  AND TABLE_NAME = 'demo_wishlist';

Output on MySQL 8.4

Empty set

⚠️ Write the long form

A key that exists on one server and not on another is a trap. The table-level form, CONSTRAINT name FOREIGN KEY (col) REFERENCES parent(id), works the same on MySQL 9.7, 8.4 and MariaDB, and it lets you name the key. The course always uses it. Drop the demo table:

DROP TABLE demo_wishlist;

🗑️ ON DELETE: When a Parent Is Deleted

Deleting a parent that still has children forces a decision. The ON DELETE rule makes it in advance:

graph TD A["DELETE a parent row"] --> B{"Any children?"} B -->|"no"| C["row deleted"] B -->|"yes"| D{"ON DELETE rule"} D -->|"RESTRICT"| E["error 1451"] D -->|"CASCADE"| F["children deleted"] D -->|"SET NULL"| G["FK set to NULL"]

RESTRICT: refuse

orders uses ON DELETE RESTRICT toward customers. Alice has three orders:

DELETE FROM customers WHERE id = 1;

Error

ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (`bookstore`.`orders`, CONSTRAINT `fk_orders_customer` FOREIGN KEY (`customer_id`) REFERENCES `customers` (`id`) ON DELETE RESTRICT ON UPDATE CASCADE)

Alice stays, and so does her sales history. To really remove her you would first have to deal with her orders yourself, which is the point: RESTRICT makes you decide. Carol, who never ordered, has no children, so deleting her would succeed.

CASCADE: delete the children too

order_items uses ON DELETE CASCADE toward orders: the lines of a receipt mean nothing without the receipt. To watch it without losing data, wrap the delete in a transaction. START TRANSACTION begins a group of changes, and ROLLBACK undoes all of them (Lesson 7.2 covers transactions properly):

START TRANSACTION;

SELECT id, order_id, book_id FROM order_items WHERE order_id = 1;

DELETE FROM orders WHERE id = 1;

SELECT id, order_id, book_id FROM order_items WHERE order_id = 1;

ROLLBACK;

Output

+----+----------+---------+
| id | order_id | book_id |
+----+----------+---------+
|  1 |        1 |       1 |
|  2 |        1 |       2 |
+----+----------+---------+
Empty set

One DELETE on orders removed two rows from order_items. After ROLLBACK, order 1 and both its lines are back:

SELECT COUNT(*) AS orders, (SELECT COUNT(*) FROM order_items) AS items
FROM orders;

Output

+--------+-------+
| orders | items |
+--------+-------+
|     12 |    18 |
+--------+-------+

🛑 Cascades chain

If orders also cascaded from customers, deleting one customer would silently delete every order and every order line they ever had: years of sales gone in one statement, with no error and no warning. Use CASCADE only for children that truly have no meaning without their parent, like order lines or a junction table's links.

SET NULL: keep the children, forget the parent

employees.manager_id uses ON DELETE SET NULL. Priya (3) manages Tom, Lena and Ben. If Priya leaves:

START TRANSACTION;

DELETE FROM employees WHERE id = 3;

SELECT id, first_name, manager_id
FROM employees
WHERE id IN (4, 5, 10)
ORDER BY id;

ROLLBACK;

Output

+----+------------+------------+
| id | first_name | manager_id |
+----+------------+------------+
|  4 | Tom        |       NULL |
|  5 | Lena       |       NULL |
| 10 | Ben        |       NULL |
+----+------------+------------+

Her three reports stay employed, with no manager until someone is assigned. The column must allow NULL for this rule to be possible (Mistake 4).

NO ACTION: the default

Leave the rule out and you get NO ACTION. Some databases can postpone a NO ACTION check to the end of a transaction; InnoDB checks immediately, so in MySQL it behaves exactly like RESTRICT. Writing RESTRICT says what you mean.

🐬 Version note

MariaDB reports an unwritten rule as RESTRICT rather than NO ACTION in information_schema; the behavior is the same on all three servers. MariaDB also names an unnamed key differently (1 instead of demo_staff_ibfk_1), so a script that drops a generated name works on one server and fails on the other. One more reason to name every key yourself.

✏️ ON UPDATE: When a Parent's Key Changes

ON UPDATE takes the same choices and applies them when a parent's primary key value changes. The bookstore's books.author_id key says ON UPDATE CASCADE, so renumbering an author carries the new number into every one of their books:

START TRANSACTION;

UPDATE authors SET id = 20 WHERE id = 2;

SELECT id, title, author_id
FROM books
WHERE author_id = 20
ORDER BY id;

ROLLBACK;

Output

+----+-------------+-----------+
| id | title       | author_id |
+----+-------------+-----------+
|  2 | 1984        |        20 |
| 11 | Animal Farm |        20 |
+----+-------------+-----------+

Orwell's two books followed him from 2 to 20. The employees self-reference, on the other hand, has no ON UPDATE rule, so it is NO ACTION:

UPDATE employees SET id = 100 WHERE id = 1;

Error

ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (`bookstore`.`employees`, CONSTRAINT `fk_employees_manager` FOREIGN KEY (`manager_id`) REFERENCES `employees` (`id`) ON DELETE SET NULL)

Maria manages Daniel and James, so her id cannot change while they point at it.

💡 ON UPDATE rarely fires

With AUTO_INCREMENT ids, nobody has a reason to change a primary key: the number means nothing outside the database. ON UPDATE CASCADE is a cheap safety net. It matters much more when a key is a real-world value that can change, such as a product code.

🧭 Choosing the Rules

Ask two questions about the child rows, in this order:

graph TD A["Can the child exist without its parent?"] -->|"no"| B["CASCADE"] A -->|"yes"| C["Must the child keep naming its parent?"] C -->|"yes: keep history"| D["RESTRICT"] C -->|"no: the link is optional"| E["SET NULL"]

Here is every rule in the bookstore, read from information_schema, the built-in database that describes all the others:

SELECT TABLE_NAME, CONSTRAINT_NAME, REFERENCED_TABLE_NAME,
       DELETE_RULE, UPDATE_RULE
FROM information_schema.REFERENTIAL_CONSTRAINTS
WHERE CONSTRAINT_SCHEMA = 'bookstore'
  AND TABLE_NAME NOT LIKE 'demo%'
ORDER BY TABLE_NAME, CONSTRAINT_NAME;

Output

+-----------------+----------------------+-----------------------+-------------+-------------+
| TABLE_NAME      | CONSTRAINT_NAME      | REFERENCED_TABLE_NAME | DELETE_RULE | UPDATE_RULE |
+-----------------+----------------------+-----------------------+-------------+-------------+
| book_categories | fk_bc_book           | books                 | CASCADE     | NO ACTION   |
| book_categories | fk_bc_category       | categories            | CASCADE     | NO ACTION   |
| books           | fk_books_author      | authors               | RESTRICT    | CASCADE     |
| employees       | fk_employees_manager | employees             | SET NULL    | NO ACTION   |
| order_items     | fk_items_book        | books                 | RESTRICT    | CASCADE     |
| order_items     | fk_items_order       | orders                | CASCADE     | CASCADE     |
| orders          | fk_orders_customer   | customers             | RESTRICT    | CASCADE     |
+-----------------+----------------------+-----------------------+-------------+-------------+
Child → parentON DELETEWhy
order line → orderCASCADEa line has no meaning without its order
link → book, link → categoryCASCADEa junction row is only the link itself
order → customerRESTRICTsales history must survive; deactivate a customer instead
order line → bookRESTRICTa book that was sold stays on file (mark it out of stock)
book → authorRESTRICTnever lose a book because an author was removed
employee → managerSET NULLstaff stay when a manager leaves

🔑 When in doubt, RESTRICT

A refused delete costs you one extra step. A wrong cascade costs you data. You can always loosen a rule later (next section); you cannot un-delete cascaded rows without a backup.

🔧 Adding, Dropping and Changing Keys

Real tables often exist before anyone declares their keys, as books.author_id did in Lesson 4.1. Rebuild demo_staff the way such a table usually starts, with a department_id column and no key at all, and put some data in it:

DROP TABLE demo_staff;

CREATE TABLE demo_staff (
    id            INT PRIMARY KEY,
    name          VARCHAR(50) NOT NULL,
    department_id INT
);

INSERT INTO demo_departments (id, name) VALUES (1, 'Front desk'), (2, 'Warehouse');
INSERT INTO demo_staff (id, name, department_id) VALUES
    (1, 'Ana', 1),
    (2, 'Raj', 2),
    (3, 'Kim', 7);

Kim's department 7 does not exist: without a key, nothing stopped it. Now try to add the key:

ALTER TABLE demo_staff
    ADD CONSTRAINT fk_staff_department
        FOREIGN KEY (department_id) REFERENCES demo_departments(id)
        ON DELETE SET NULL;

Error (the #sql table name will differ)

ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`bookstore`.`#sql-80218_36b`, CONSTRAINT `fk_staff_department` FOREIGN KEY (`department_id`) REFERENCES `demo_departments` (`id`) ON DELETE SET NULL)

MySQL builds the changed table as a temporary #sql-... copy, finds an orphan while copying, and gives up. Find the orphans with a subquery, fix them, then add the key:

SELECT id, name, department_id
FROM demo_staff
WHERE department_id NOT IN (SELECT id FROM demo_departments);

UPDATE demo_staff SET department_id = NULL WHERE id = 3;

ALTER TABLE demo_staff
    ADD CONSTRAINT fk_staff_department
        FOREIGN KEY (department_id) REFERENCES demo_departments(id)
        ON DELETE SET NULL;

Output

+----+------+---------------+
| id | name | department_id |
+----+------+---------------+
|  3 | Kim  |             7 |
+----+------+---------------+

Setting Kim's department to NULL ("not assigned yet") is one fix; another is to give her a real department. Deleting her would be a third, and the most drastic: choose the fix that tells the truth about the data.

Dropping a key and its index

A foreign key and the index MySQL created for it have the same name but are separate objects. DROP FOREIGN KEY removes the rule and leaves the index:

ALTER TABLE demo_staff DROP FOREIGN KEY fk_staff_department;

SELECT INDEX_NAME, COLUMN_NAME
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = 'bookstore'
  AND TABLE_NAME = 'demo_staff'
ORDER BY INDEX_NAME;

Output

+---------------------+---------------+
| INDEX_NAME          | COLUMN_NAME   |
+---------------------+---------------+
| fk_staff_department | department_id |
| PRIMARY             | id            |
+---------------------+---------------+

The index is harmless (it even speeds up searches by department), but if you want it gone: ALTER TABLE demo_staff DROP INDEX fk_staff_department;

Changing a rule

There is no ALTER FOREIGN KEY. To change a rule, drop the key and add it again with the new rule. The key is already dropped, so add it back with CASCADE this time and check:

ALTER TABLE demo_staff
    ADD CONSTRAINT fk_staff_department
        FOREIGN KEY (department_id) REFERENCES demo_departments(id)
        ON DELETE CASCADE;

SELECT CONSTRAINT_NAME, DELETE_RULE
FROM information_schema.REFERENTIAL_CONSTRAINTS
WHERE CONSTRAINT_SCHEMA = 'bookstore'
  AND TABLE_NAME = 'demo_staff';

Output

+---------------------+-------------+
| CONSTRAINT_NAME     | DELETE_RULE |
+---------------------+-------------+
| fk_staff_department | CASCADE     |
+---------------------+-------------+

The re-added key reused the index that was still there. On a big production table, dropping and re-adding a key takes time and briefly leaves the data unprotected, so plan rule changes as carefully as any other schema change.

🚧 Turning the Checks Off (Carefully)

The session variable foreign_key_checks switches foreign key checking off for your connection only:

SET FOREIGN_KEY_CHECKS = 0;
-- load tables in any order, e.g. a backup file
SET FOREIGN_KEY_CHECKS = 1;

Backup files made by mysqldump (Lesson 8.1) start with exactly this line, so they can create and fill tables in alphabetical order without tripping over missing parents. That is the legitimate use: loading data you already trust.

🛑 Turning checks back on does not re-check

When you set it back to 1, MySQL does not look at the rows inserted in the meantime. Any orphan that slipped in stays, silently (Mistake 5 shows it). Never switch the checks off to make an error go away: the error was telling you about bad data.

⚠️ Common Mistakes

1. A child row with no parent (1452)

INSERT INTO order_items (order_id, book_id, quantity, price_at_time)
VALUES (1, 99, 1, 9.99);

Error

ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`bookstore`.`order_items`, CONSTRAINT `fk_items_book` FOREIGN KEY (`book_id`) REFERENCES `books` (`id`) ON DELETE RESTRICT ON UPDATE CASCADE)

What it means: "add or update a child row": the value you gave a foreign key column (book 99) has no parent. The message names the constraint, fk_items_book, which tells you which column is wrong. Fix: use an id that exists (look it up with a SELECT first), or insert the parent before the child.

2. Deleting a parent that still has children (1451)

DELETE FROM books WHERE id = 1;

Error

ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (`bookstore`.`order_items`, CONSTRAINT `fk_items_book` FOREIGN KEY (`book_id`) REFERENCES `books` (`id`) ON DELETE RESTRICT ON UPDATE CASCADE)

What it means: "delete or update a parent row": Dune appears in sold order lines, and fk_items_book says RESTRICT. Note that its book_categories links would have cascaded; the one RESTRICT is enough to stop the whole delete. Fix: usually, do not delete: mark the book in_stock = FALSE. If it really must go, deal with the children first.

3. Column types that do not match (3780)

CREATE TABLE demo_shelf (
    id      INT PRIMARY KEY,
    book_id BIGINT,
    CONSTRAINT fk_shelf_book FOREIGN KEY (book_id) REFERENCES books(id)
);

Error

ERROR 3780 (HY000): Referencing column 'book_id' and referenced column 'id' in foreign key constraint 'fk_shelf_book' are incompatible.

What it means: books.id is INT, the new column is BIGINT. INT UNSIGNED against INT fails the same way. Fix: copy the parent column's exact type. DESCRIBE books; shows it.

4. SET NULL on a NOT NULL column (1830)

CREATE TABLE demo_notes (
    id          INT PRIMARY KEY,
    customer_id INT NOT NULL,
    CONSTRAINT fk_notes_customer FOREIGN KEY (customer_id)
        REFERENCES customers(id) ON DELETE SET NULL
);

Error

ERROR 1830 (HY000): Column 'customer_id' cannot be NOT NULL: needed in a foreign key constraint 'fk_notes_customer' SET NULL

What it means: the rule promises to write NULL into a column that forbids it. MySQL spots the contradiction when you create the key. Fix: make the column nullable (customer_id INT), or choose RESTRICT or CASCADE.

5. Orphans let in while the checks were off (silent)

SET FOREIGN_KEY_CHECKS = 0;
INSERT INTO demo_staff (id, name, department_id) VALUES (4, 'Lou', 42);
SET FOREIGN_KEY_CHECKS = 1;

SELECT id, name, department_id
FROM demo_staff
WHERE department_id NOT IN (SELECT id FROM demo_departments);

Output

+----+------+---------------+
| id | name | department_id |
+----+------+---------------+
|  4 | Lou  |            42 |
+----+------+---------------+

What it means: no error at any point, yet demo_staff now holds an orphan behind a declared foreign key. Every query that trusts the key ("every department_id has a department") is now wrong. Fix: keep the checks on; after any load done with them off, run an orphan query like this one for every key. Clean up the demo tables now (child first):

DROP TABLE demo_staff;
DROP TABLE demo_departments;

🐬 Version note: errors on MariaDB

MySQL 8.4 and 9.7 give each badly formed key its own message (3780, 6125, 1830). MariaDB reports most of them with one older message, ERROR 1005 (HY000): Can't create table ... (errno: 150 "Foreign key constraint is incorrectly formed"). When you see errno 150, walk through the requirements table above: types, parent key, table name, NULL rules.

🛠️ Project: Book Reviews with the Right Rules

The store wants customers to review books. A review is about one book and written by one customer, so book_reviews is a child of both. The interesting part: the two keys need different delete rules. You will decide them, build the table, and prove each rule with a test you undo. Allow about 30 minutes.

🛠️ Step 1: Decide the rules (5 min)

Walk both keys through the decision diagram. Review to book: can a review exist without its book? No, a review of nothing is meaningless: CASCADE. Review to customer: can it exist without its author? Yes, the store wants to keep the review ("by a former customer"), and it need not name anyone: SET NULL, which means customer_id must allow NULL.

🛠️ Step 2: Create the table (5 min)

CREATE TABLE book_reviews (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    book_id     INT NOT NULL,
    customer_id INT,
    stars       TINYINT NOT NULL,
    comment     VARCHAR(255),
    CONSTRAINT chk_reviews_stars CHECK (stars BETWEEN 1 AND 5),
    CONSTRAINT fk_reviews_book
        FOREIGN KEY (book_id) REFERENCES books(id)
        ON DELETE CASCADE
        ON UPDATE CASCADE,
    CONSTRAINT fk_reviews_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
        ON DELETE SET NULL
        ON UPDATE CASCADE
);

INSERT INTO book_reviews (book_id, customer_id, stars, comment) VALUES
    (1, 1, 5, 'Worth every one of its pages.'),
    (4, 3, 4, 'Short and sharp.'),
    (4, 2, 3, 'Good, not great.'),
    (6, 3, 5, 'Read it to my kids.');

SELECT * FROM book_reviews ORDER BY id;

Output

+----+---------+-------------+-------+-------------------------------+
| id | book_id | customer_id | stars | comment                       |
+----+---------+-------------+-------+-------------------------------+
|  1 |       1 |           1 |     5 | Worth every one of its pages. |
|  2 |       4 |           3 |     4 | Short and sharp.              |
|  3 |       4 |           2 |     3 | Good, not great.              |
|  4 |       6 |           3 |     5 | Read it to my kids.           |
+----+---------+-------------+-------+-------------------------------+

🛠️ Step 3: Prove that orphans are refused (3 min)

INSERT INTO book_reviews (book_id, customer_id, stars) VALUES (42, 1, 5);

Error

ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`bookstore`.`book_reviews`, CONSTRAINT `fk_reviews_book` FOREIGN KEY (`book_id`) REFERENCES `books` (`id`) ON DELETE CASCADE ON UPDATE CASCADE)

🛠️ Step 4: Test the CASCADE rule (5 min)

The Great Gatsby (4) has two reviews and was never sold, so nothing RESTRICTs its deletion. Delete it inside a transaction, look, and undo:

START TRANSACTION;

DELETE FROM books WHERE id = 4;

SELECT book_id, COUNT(*) AS reviews
FROM book_reviews
GROUP BY book_id
ORDER BY book_id;

ROLLBACK;

Output

+---------+---------+
| book_id | reviews |
+---------+---------+
|       1 |       1 |
|       6 |       1 |
+---------+---------+

Book 4's reviews went with it (and so did its two book_categories links, by their own CASCADE). ROLLBACK brought everything back.

🛠️ Step 5: Test the SET NULL rule (5 min)

Carol (3) wrote two reviews and never placed an order, so she can be deleted:

START TRANSACTION;

DELETE FROM customers WHERE id = 3;

SELECT id, book_id, customer_id, stars
FROM book_reviews
ORDER BY id;

ROLLBACK;

Output

+----+---------+-------------+-------+
| id | book_id | customer_id | stars |
+----+---------+-------------+-------+
|  1 |       1 |           1 |     5 |
|  2 |       4 |        NULL |     4 |
|  3 |       4 |           2 |     3 |
|  4 |       6 |        NULL |     5 |
+----+---------+-------------+-------+

Both of Carol's reviews survived with customer_id set to NULL. A website would show them as "by a former customer". Try the same with Alice (1) and you get error 1451: her orders are protected by RESTRICT, whatever her reviews' rule says.

🏋️ Exercise 1: Pick the Rule

Choose an ON DELETE rule for each child and justify it in one sentence: (a) invoices → clients; (b) comments → blog_posts; (c) enrollments → students (a junction table); (d) messages.sender_id → users in a group chat.

💡 Hint

Use the two questions: can the child exist without the parent, and must it keep naming the parent? Money and legal records lean towards keeping everything.

✅ Solution

(a) RESTRICT: invoices are financial records that must outlive any cleanup; deactivate the client instead. (b) CASCADE: comments belong to their post. (c) CASCADE: a junction row is only the link. (d) SET NULL (nullable sender_id): the other members keep the conversation, shown as "deleted user". Other answers can be right if the business rules differ; what matters is that you can justify yours.

🏋️ Exercise 3: Two Authors, Two Outcomes

Predict, then test inside a transaction: what happens when you delete Isaac Asimov (author 10)? And George Orwell (author 2)? Undo with ROLLBACK.

💡 Hint

fk_books_author is RESTRICT. Which of the two authors has books?

✅ Solution 
START TRANSACTION;
DELETE FROM authors WHERE id = 10;
SELECT COUNT(*) AS authors_left FROM authors;
ROLLBACK;

Output

+--------------+
| authors_left |
+--------------+
|            9 |
+--------------+
DELETE FROM authors WHERE id = 2;

Error

ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (`bookstore`.`books`, CONSTRAINT `fk_books_author` FOREIGN KEY (`author_id`) REFERENCES `authors` (`id`) ON DELETE RESTRICT ON UPDATE CASCADE)

Asimov has no books, so RESTRICT has nothing to protect and the delete works (undone by the rollback). Orwell has two books, so the delete is refused and nothing changes; no transaction needed.

🏋️ Exercise 4 (Stretch): Tighten a Rule, Then Restore It

❓ Common Questions at This Stage

Do foreign keys slow the database down?

A little: each insert into a child looks up its parent, and each parent delete looks for children. Both lookups use indexes, so the cost is small next to the bugs they prevent. Some very large systems skip foreign keys and check in the application; for nearly everyone else, declaring them is the right call.

Why are customers protected but order lines cascaded? Isn't deleting a customer the same kind of cleanup?

The difference is what the child means. An order line is part of its order. An order is a business event with its own meaning (money changed hands), and tax rules often require keeping it. Real stores rarely delete customers at all: they mark them inactive, or remove the personal details while keeping the orders.

Can a foreign key point at a column that is not the primary key?

Yes, if that column is UNIQUE, for example customers.email. MySQL 8.4 and later refuse a key to a column that is not unique (error 6125, "Missing unique key"); older versions allowed it with any index, which made "the parent" ambiguous. In practice, point at the primary key.

I got errno: 150 on XAMPP. What is that?

XAMPP ships MariaDB, which reports a badly formed foreign key as ERROR 1005 ... errno: 150 "Foreign key constraint is incorrectly formed". Check the column types (including UNSIGNED), that the parent table and column exist and are a primary or unique key, and that a SET NULL column allows NULL.

📝 Lesson Summary

🎓 Key Takeaways

  • Referential integrity: every foreign key value points at an existing parent row; declared keys make orphans impossible
  • ERROR 1452 = a child row without a parent; ERROR 1451 = a parent that still has children (under RESTRICT)
  • RESTRICT refuses, CASCADE deletes or updates the children too, SET NULL keeps them and clears the link (nullable column required)
  • No rule written means NO ACTION, which MySQL enforces exactly like RESTRICT
  • Name your keys (CONSTRAINT fk_child_parent) and use the table-level form, which behaves the same on every server
  • Before adding a key to existing data, find and fix the orphans; to change a rule, drop and re-add the key
  • FOREIGN_KEY_CHECKS = 0 is for loading trusted data only; turning it back on does not re-check
