📊 Lesson 3.2: Sorting & Limiting Results

A store's website never shows "all books, in whatever order the database felt like". It shows the three newest, the cheapest first, page 2 of 4. This lesson gives you the two clauses behind every one of those lists: ORDER BY decides the order, and LIMIT decides how many rows you get and where they start.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Sort results with ORDER BY on one or more columns or expressions, each ascending or descending
  • Predict where NULL values land in a sort and move them to the end
  • Take the top N rows with LIMIT, and add a tie-breaker so the result is always the same
  • Split a result into pages with LIMIT ... OFFSET, and explain when keyset pagination is better
  • Read and fix the errors MySQL raises for misplaced or malformed ORDER BY and LIMIT clauses

↕️ ORDER BY: Sorting Results

A table is a set of rows, not a list: it has no built-in order. Without ORDER BY, MySQL returns rows in whatever order is cheapest for it, which is often the order they were inserted, until one day it is not (after deletes, an index change or a server upgrade). If the order matters, ask for it.

💡 Follow along

Run USE bookstore; first. This lesson reads the 10 books and 8 customers from the Lesson 3.1 setup script. If your results differ from the ones shown here, run that script again.

Ascending: the default

SELECT title, price
FROM books
ORDER BY price;

Output (the order of the two 8.99 books can differ on your server)

+------------------------+-------+
| title                  | price |
+------------------------+-------+
| Pride and Prejudice    |  7.99 |
| The Great Gatsby       |  8.99 |
| The Catcher in the Rye |  8.99 |
| Brave New World        |  9.49 |
| 1984                   |  9.99 |
| Fahrenheit 451         | 10.49 |
| The Hobbit             | 10.99 |
| To Kill a Mockingbird  | 11.99 |
| Dune                   | 14.99 |
| Lord of the Rings      | 15.99 |
+------------------------+-------+

Cheapest first. ASC (ascending) is the default, so ORDER BY price ASC means exactly the same. Notice the card's label: two books cost 8.99, and nothing in this query says which of them comes first. You will fix that in the next section.

Text and dates

Text sorts alphabetically (with the same case-insensitive rules as =), and dates sort from earliest to latest:

SELECT title
FROM books
ORDER BY title;

Output

+------------------------+
| title                  |
+------------------------+
| 1984                   |
| Brave New World        |
| Dune                   |
| Fahrenheit 451         |
| Lord of the Rings      |
| Pride and Prejudice    |
| The Catcher in the Rye |
| The Great Gatsby       |
| The Hobbit             |
| To Kill a Mockingbird  |
+------------------------+

Digits sort before letters, so 1984 leads. And "The" counts like any other word: all three "The ..." titles sit together near the end. Store websites that file The Hobbit under H keep a separate sort column for that.

SELECT title, published
FROM books

Filter first, then sort

ORDER BY comes after WHERE and sorts only the rows that passed the filter:

SELECT title, price, published
FROM books
WHERE price > 10
ORDER BY published DESC;

🧱 Sorting by Several Columns

List more than one column and MySQL sorts by the first; only where the first column ties does it look at the second, and so on. It works like a phone book: by last name, and by first name only among people with the same last name.

SELECT title, price
FROM books
ORDER BY price, title;

Output

+------------------------+-------+
| title                  | price |
+------------------------+-------+
| Pride and Prejudice    |  7.99 |
| The Catcher in the Rye |  8.99 |
| The Great Gatsby       |  8.99 |
| Brave New World        |  9.49 |
| 1984                   |  9.99 |
| Fahrenheit 451         | 10.49 |
| The Hobbit             | 10.99 |
| To Kill a Mockingbird  | 11.99 |
| Dune                   | 14.99 |
| Lord of the Rings      | 15.99 |
+------------------------+-------+

The two 8.99 books now come out in alphabetical order, every time, on every server. The second column is a tie-breaker.

A direction per column

ASC and DESC apply to one column each. Here, in-stock books first (1 before 0, so descending), then the cheapest first within each group:

SELECT title, in_stock, price
FROM books
ORDER BY in_stock DESC, price, title;

Output

+------------------------+----------+-------+
| title                  | in_stock | price |
+------------------------+----------+-------+
| Pride and Prejudice    |        1 |  7.99 |
| Brave New World        |        1 |  9.49 |
| 1984                   |        1 |  9.99 |
| Fahrenheit 451         |        1 | 10.49 |
| The Hobbit             |        1 | 10.99 |
| To Kill a Mockingbird  |        1 | 11.99 |
| Dune                   |        1 | 14.99 |
| Lord of the Rings      |        1 | 15.99 |
| The Catcher in the Rye |        0 |  8.99 |
| The Great Gatsby       |        0 |  8.99 |
+------------------------+----------+-------+

A common slip is to write ORDER BY in_stock, price DESC and expect both to be descending. They are not: DESC only belongs to the column right before it.

SELECT first_name, last_name, city
FROM customers
WHERE city IS NOT NULL
ORDER BY city, last_name;

Output

+------------+-----------+-------------+
| first_name | last_name | city        |
+------------+-----------+-------------+
| Bob        | Smith     | Chicago     |
| Grace      | Wilson    | Chicago     |
| Dave       | Brown     | Houston     |
| Carol      | Williams  | Los Angeles |
| Alice      | Johnson   | New York    |
| Frank      | Miller    | New York    |
+------------+-----------+-------------+

🧮 Sorting by Expressions and Aliases

You can sort by a calculation, and you can use a column alias from the SELECT list in ORDER BY. Which book gives the most pages per dollar?

SELECT
    title,
    price,
    pages,
    ROUND(pages / price, 1) AS pages_per_dollar
FROM books
ORDER BY pages_per_dollar DESC, title;

Output

+------------------------+-------+-------+------------------+
| title                  | price | pages | pages_per_dollar |
+------------------------+-------+-------+------------------+
| Lord of the Rings      | 15.99 |  1178 |             73.7 |
| Pride and Prejudice    |  7.99 |   432 |             54.1 |
| 1984                   |  9.99 |   328 |             32.8 |
| Brave New World        |  9.49 |   311 |             32.8 |
| The Hobbit             | 10.99 |   310 |             28.2 |
| Dune                   | 14.99 |   412 |             27.5 |
| The Catcher in the Rye |  8.99 |   234 |             26.0 |
| To Kill a Mockingbird  | 11.99 |   281 |             23.4 |
| The Great Gatsby       |  8.99 |   180 |             20.0 |
| Fahrenheit 451         | 10.49 |   158 |             15.1 |
+------------------------+-------+-------+------------------+

Lord of the Rings is the priciest book and also the best value per page. The alias works in ORDER BY because MySQL sorts after it has computed the SELECT list (you will see that run order at the end of this lesson).

A custom order with CASE

Sometimes neither alphabetical nor numeric order is what you want. The Chicago team wants their customers first, then New York, then everyone else. A CASE expression turns each city into a rank number, and the query sorts by that number:

SELECT first_name, city
FROM customers
ORDER BY
    CASE city
        WHEN 'Chicago'  THEN 1
        WHEN 'New York' THEN 2
        ELSE 3
    END,
    first_name;

Output

+------------+-------------+
| first_name | city        |
+------------+-------------+
| Bob        | Chicago     |
| Grace      | Chicago     |
| Alice      | New York    |
| Frank      | New York    |
| Carol      | Los Angeles |
| Dave       | Houston     |
| Eve        | NULL        |
| Hank       | NULL        |
+------------+-------------+

Everyone who is neither in Chicago nor New York gets rank 3, including Eve and Hank, and the second sort column puts that group in name order.

Sorting by column number

MySQL also accepts a position: ORDER BY 2 sorts by the second column of the SELECT list.

SELECT title, price
FROM books
ORDER BY 2 DESC, 1
LIMIT 3;

Output

+-----------------------+-------+
| title                 | price |
+-----------------------+-------+
| Lord of the Rings     | 15.99 |
| Dune                  | 14.99 |
| To Kill a Mockingbird | 11.99 |
+-----------------------+-------+

⚠️ Fine at the prompt, fragile in a file

If someone later adds a column at the front of the SELECT list, ORDER BY 2 quietly sorts by something else. Type positions while exploring if you like, but save queries with column names.

🕳️ Where NULLs Go

MySQL treats NULL as smaller than any value. So in an ascending sort the NULLs come first, and in a descending sort they come last:

SELECT first_name, city
FROM customers
ORDER BY city, first_name;

Output

+------------+-------------+
| first_name | city        |
+------------+-------------+
| Eve        | NULL        |
| Hank       | NULL        |
| Bob        | Chicago     |
| Grace      | Chicago     |
| Dave       | Houston     |
| Carol      | Los Angeles |
| Alice      | New York    |
| Frank      | New York    |
+------------+-------------+

For a customer directory, two empty cities at the top look like a mistake. Push them to the bottom with an extra sort key in front: city IS NULL is 0 for a real city and 1 for a missing one, so sorting by it ascending puts the real cities first.

SELECT first_name, city
FROM customers
ORDER BY city IS NULL, city, first_name;

Output

+------------+-------------+
| first_name | city        |
+------------+-------------+
| Bob        | Chicago     |
| Grace      | Chicago     |
| Dave       | Houston     |
| Carol      | Los Angeles |
| Alice      | New York    |
| Frank      | New York    |
| Eve        | NULL        |
| Hank       | NULL        |
+------------+-------------+
graph TD A["key 1: city IS NULL"] -->|"0 = has a city"| B["listed first"] A -->|"1 = no city"| C["listed last"] B --> D["key 2: city A to Z"] D --> E["key 3: first_name"]

🐬 Version note: no NULLS FIRST / NULLS LAST

PostgreSQL and Oracle let you write ORDER BY city NULLS LAST. MySQL (9.7 and 8.4) and MariaDB do not support it and answer with a syntax error 1064 near 'NULLS LAST'. The city IS NULL trick above is the portable way to get the same result in MySQL.

✂️ LIMIT: The Top N Rows

LIMIT n keeps the first n rows of the sorted result and throws the rest away. Together with ORDER BY it answers every "top N" question:

SELECT title, pages
FROM books
ORDER BY pages DESC
LIMIT 3;

Output

+---------------------+-------+
| title               | pages |
+---------------------+-------+
| Lord of the Rings   |  1178 |
| Pride and Prejudice |   432 |
| Dune                |   412 |
+---------------------+-------+
SELECT title, published
FROM books
ORDER BY published
LIMIT 1;

Output

+---------------------+------------+
| title               | published  |
+---------------------+------------+
| Pride and Prejudice | 1813-01-28 |
+---------------------+------------+

LIMIT 1 is the classic "the oldest", "the cheapest", "the most recent" pattern. It returns one row even when several rows tie for first place; in Lesson 3.4 you will meet a subquery that returns all of them.

LIMIT always runs last

The filter runs first, then the sort, then the cut. The three cheapest books that are in stock:

SELECT title, price
FROM books
WHERE in_stock = TRUE
ORDER BY price, title
LIMIT 3;

Output

+---------------------+-------+
| title               | price |
+---------------------+-------+
| Pride and Prejudice |  7.99 |
| Brave New World     |  9.49 |
| 1984                |  9.99 |
+---------------------+-------+

⚠️ LIMIT needs a complete ORDER BY

LIMIT without ORDER BY returns "some" rows, and which ones is up to the server. With an ORDER BY that has ties at the cut-off point, the last row is still up to the server. Ask yourself: "could two rows have the same value here?" If yes, add a tie-breaker that is unique, such as title or id. You will see what happens without one in Common Mistakes.

⏭️ OFFSET: Skipping Rows

OFFSET m skips the first m rows of the sorted result before LIMIT starts counting. Rows 4 to 6 by price:

SELECT title, price
FROM books
ORDER BY price, title
LIMIT 3 OFFSET 3;

Output

+-----------------+-------+
| title           | price |
+-----------------+-------+
| Brave New World |  9.49 |
| 1984            |  9.99 |
| Fahrenheit 451  | 10.49 |
+-----------------+-------+
graph TD A["10 books sorted by price"] --> B["OFFSET 3: skip rows 1 to 3"] B --> C["LIMIT 3: keep rows 4 to 6"] C --> D["rows 7 to 10 are not returned"]

The comma form

MySQL also accepts LIMIT offset, count, with the offset first:

SELECT title, price
FROM books
ORDER BY price, title
LIMIT 3, 3;

Output

+-----------------+-------+
| title           | price |
+-----------------+-------+
| Brave New World |  9.49 |
| 1984            |  9.99 |
| Fahrenheit 451  | 10.49 |
+-----------------+-------+

Same rows. The comma form is common in older code, and it is easy to misread (is LIMIT 3, 3 "three from three" or "three, three"?). Prefer LIMIT 3 OFFSET 3: it says what each number does, and PostgreSQL and SQLite understand it too.

📄 Pagination Patterns

A website that shows 4 books per page needs, for page N, the rows after the first (N - 1) × 4. In SQL: LIMIT 4 OFFSET (N - 1) * 4, with the offset worked out before the query is sent.

Four books per page, by title

SELECT title, price
FROM books
ORDER BY title
LIMIT 4 OFFSET 0;

Output (page 1)

+-----------------+-------+
| title           | price |
+-----------------+-------+
| 1984            |  9.99 |
| Brave New World |  9.49 |
| Dune            | 14.99 |
| Fahrenheit 451  | 10.49 |
+-----------------+-------+
SELECT title, price
FROM books
ORDER BY title
LIMIT 4 OFFSET 4;

Output (page 2)

+------------------------+-------+
| title                  | price |
+------------------------+-------+
| Lord of the Rings      | 15.99 |
| Pride and Prejudice    |  7.99 |
| The Catcher in the Rye |  8.99 |
| The Great Gatsby       |  8.99 |
+------------------------+-------+
SELECT title, price
FROM books
ORDER BY title
LIMIT 4 OFFSET 8;

Output (page 3)

+-----------------------+-------+
| title                 | price |
+-----------------------+-------+
| The Hobbit            | 10.99 |
| To Kill a Mockingbird | 11.99 |
+-----------------------+-------+

The last page is short: only 2 books are left after skipping 8. A page past the end (OFFSET 12) is not an error, just an empty result. Titles are unique here, so ORDER BY title needs no tie-breaker; sort by price and it would.

💡 LIMIT takes numbers, not formulas

MySQL does not accept LIMIT 4 OFFSET (3 - 1) * 4: it is a syntax error (see Common Mistakes). Your application calculates the offset and passes it in as a parameter of a prepared statement, where LIMIT ? OFFSET ? is allowed.

How many pages?

To print "Page 2 of 3", the website also needs the total, which is a separate query:

SELECT
    COUNT(*)            AS total_books,
    CEILING(COUNT(*) / 4) AS pages_needed
FROM books;

Output

+-------------+--------------+
| total_books | pages_needed |
+-------------+--------------+
|          10 |            3 |
+-------------+--------------+

COUNT(*) counts rows (you will study it properly in Lesson 3.3), and CEILING rounds up: 10 books / 4 per page = 2.5, so 3 pages.

🐬 Version note: SQL_CALC_FOUND_ROWS is deprecated

Older tutorials fetch a page and the total in one go with SELECT SQL_CALC_FOUND_ROWS ... followed by SELECT FOUND_ROWS(). MySQL 8.0.17 deprecated both, and MySQL warns every time you use them:

SELECT SQL_CALC_FOUND_ROWS title
FROM books
ORDER BY title
LIMIT 2;
SHOW WARNINGS;

Output

+-----------------+
| title           |
+-----------------+
| 1984            |
| Brave New World |
+-----------------+
+---------+------+-------------------------------------------------------------------------------------------------------------------------+
| Level   | Code | Message                                                                                                                 |
+---------+------+-------------------------------------------------------------------------------------------------------------------------+
| Warning | 1287 | SQL_CALC_FOUND_ROWS is deprecated and will be removed in a future release. Consider using two separate queries instead. |
+---------+------+-------------------------------------------------------------------------------------------------------------------------+

Use two queries, the page with LIMIT and the total with COUNT(*), as the warning suggests. (MariaDB has not deprecated it and stays silent, but the two-query version works everywhere.)

Keyset pagination

OFFSET has a cost that grows with the page number: for OFFSET 100000, MySQL still reads and sorts 100,000 rows only to throw them away. On a 10-row table you will never notice; on an online store's order history you will. The alternative is keyset pagination: remember the last row the user saw, and ask for the rows after it.

SELECT id, title
FROM books
ORDER BY id
LIMIT 4;

Output (first page)

+----+-----------------------+
| id | title                 |
+----+-----------------------+
|  1 | Dune                  |
|  2 | 1984                  |
|  3 | To Kill a Mockingbird |
|  4 | The Great Gatsby      |
+----+-----------------------+

The last id on this page is 4. The next page starts after it:

SELECT id, title
FROM books
WHERE id > 4
ORDER BY id
LIMIT 4;

Output (next page)

+----+------------------------+
| id | title                  |
+----+------------------------+
|  5 | Pride and Prejudice    |
|  6 | The Hobbit             |
|  7 | Brave New World        |
|  8 | The Catcher in the Rye |
+----+------------------------+

With an index on the sort column (the primary key always has one), MySQL jumps straight to id 5, however far down the list that is. The trade-off: no "jump to page 37" button, only "next" and "previous". That is why endless-scroll feeds use it.

🧭 Clause Order So Far

You must write the clauses in this order:

SELECT title, price           -- 1. which columns
FROM books                    -- 2. which table
WHERE in_stock = TRUE         -- 3. which rows
ORDER BY price DESC, title    -- 4. in what order
LIMIT 3 OFFSET 1;             -- 5. which slice

Output

+-----------------------+-------+
| title                 | price |
+-----------------------+-------+
| Dune                  | 14.99 |
| To Kill a Mockingbird | 11.99 |
| The Hobbit            | 10.99 |
+-----------------------+-------+

The second, third and fourth most expensive in-stock books. MySQL runs the clauses in a different order, and that explains why an alias works in ORDER BY but not in WHERE:

graph TD A["1. FROM: pick the table"] --> B["2. WHERE: keep rows"] B --> C["3. SELECT: compute columns"] C --> D["4. ORDER BY: sort"] D --> E["5. LIMIT / OFFSET: cut"]

In Lesson 3.3 two more clauses, GROUP BY and HAVING, slot in between WHERE and ORDER BY.

⚠️ Common Mistakes

1. Putting ORDER BY before WHERE

SELECT title, price
FROM books
ORDER BY price
WHERE price > 10;

Error

ERROR 1064 (42000): You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near 'WHERE price > 10' at line 4

What it means: error 1064 is MySQL's general "I could not read this", and near 'WHERE price > 10' shows where it got lost: after ORDER BY, a WHERE is out of place. Fix: WHERE first, then ORDER BY, then LIMIT.

2. A formula in LIMIT

SELECT title
FROM books
ORDER BY title
LIMIT 4 OFFSET (3 - 1) * 4;

Error

ERROR 1064 (42000): You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near '(3 - 1) * 4' at line 4

What it means: LIMIT and OFFSET take plain whole numbers (or ? placeholders in a prepared statement), never expressions. Fix: work out the number first and write LIMIT 4 OFFSET 8; in an application, compute the offset in your code and pass it as a parameter.

3. Sorting by a column number that does not exist

SELECT title, price
FROM books
ORDER BY 3;

Error

ERROR 1054 (42S22): Unknown column '3' in 'order clause'

What it means: the SELECT list has only two columns, so there is no column 3 to sort by. This is how a positional ORDER BY breaks when someone shortens the column list. Fix: sort by name: ORDER BY pages (a column you did not select is allowed).

4. Quoting a column name in ORDER BY (silent)

SELECT title, price
FROM books
ORDER BY 'price' DESC
LIMIT 3;

Output (the rows can differ on your server)

+-----------------------+-------+
| title                 | price |
+-----------------------+-------+
| Dune                  | 14.99 |
| 1984                  |  9.99 |
| To Kill a Mockingbird | 11.99 |
+-----------------------+-------+

What it means: no error, but these are not the three most expensive books. In single quotes, 'price' is a piece of text, the same for every row, so there is nothing to sort by and you get three rows in no particular order. Fix: write column names bare (ORDER BY price DESC), or in backticks if a name needs quoting: ORDER BY `price` DESC.

5. A top-N list without a tie-breaker (silent)

SELECT title, price
FROM books
ORDER BY price
LIMIT 2;

Output (the second row can differ on your server)

+---------------------+-------+
| title               | price |
+---------------------+-------+
| Pride and Prejudice |  7.99 |
| The Great Gatsby    |  8.99 |
+---------------------+-------+

What it means: two books cost 8.99 and only one fits in the second slot. Which one wins is up to the server and can change between runs, so a "page 1" and a "page 2" built this way can show the same book twice or skip one. Fix: end every ORDER BY that feeds a LIMIT with a unique column: ORDER BY price, title or ORDER BY price, id.

🛠️ Project: The Storefront Queries

The bookstore is getting a website. The developer has asked you for the SQL behind four pages: the home page's "New and notable" box, a bargain shelf, the catalog with pages, and a customer directory for staff. You will write them all in storefront.sql. Allow about 35 minutes.

🛠️ Step 1: New and notable (5 min)

Create storefront.sql in your mysql-course folder. The home page shows the three most recently published books that are in stock.

USE bookstore;

-- 1. Home page: three newest in-stock books
SELECT title, author, published
FROM books
WHERE in_stock = TRUE
ORDER BY published DESC
LIMIT 3;

Output

Database changed
+-----------------------+----------------+------------+
| title                 | author         | published  |
+-----------------------+----------------+------------+
| Dune                  | Frank Herbert  | 1965-08-01 |
| To Kill a Mockingbird | Harper Lee     | 1960-07-11 |
| Lord of the Rings     | J.R.R. Tolkien | 1954-07-29 |
+-----------------------+----------------+------------+

Publication dates are all different, so no tie-breaker is needed here. Would you bet on that once the store has 5,000 books? Add , title to be safe.

🛠️ Step 2: The bargain shelf (5 min)

The four cheapest books, in stock or not (out-of-stock ones get a "back soon" badge), with a tie-breaker.

-- 2. Bargain shelf: four cheapest books
SELECT title, price, in_stock
FROM books
ORDER BY price, title
LIMIT 4;

Output

+------------------------+-------+----------+
| title                  | price | in_stock |
+------------------------+-------+----------+
| Pride and Prejudice    |  7.99 |        1 |
| The Catcher in the Rye |  8.99 |        0 |
| The Great Gatsby       |  8.99 |        0 |
| Brave New World        |  9.49 |        1 |
+------------------------+-------+----------+

🛠️ Step 3: Catalog, pages 1 and 2 (10 min)

The catalog lists books by author, then title, four per page. Write page 1, then copy it and change only the offset for page 2.

-- 3a. Catalog page 1 (4 per page)
SELECT author, title, price
FROM books
ORDER BY author, title
LIMIT 4 OFFSET 0;

-- 3b. Catalog page 2
SELECT author, title, price
FROM books
ORDER BY author, title
LIMIT 4 OFFSET 4;

Output

| Aldous Huxley       | Brave New World  |  9.49 |
| F. Scott Fitzgerald | The Great Gatsby |  8.99 |

🛠️ Step 4: Last page and the page count (5 min)

Add page 3 and the query that tells the website how many pages there are.

-- 3c. Catalog page 3
SELECT author, title, price
FROM books
ORDER BY author, title
LIMIT 4 OFFSET 8;

-- 4. Page count for "Page X of Y"
SELECT CEILING(COUNT(*) / 4) AS catalog_pages
FROM books;

Output

❓ Common Questions at This Stage

Isn't SELECT * FROM books already in id order?

On a small InnoDB table it usually is, because the rows are stored by primary key. But "usually" is not a promise: the moment MySQL decides to read through an index, or the query gains a WHERE or a join, the order can change. If a person or a program depends on the order, write ORDER BY id.

Can I sort by a column I did not select?

Yes. SELECT title FROM books ORDER BY price DESC; is fine: the sort happens on the full rows before the unselected columns are dropped. (One exception you will meet with SELECT DISTINCT: there, MySQL requires the sort columns to be in the select list.)

Why does "The Hobbit" sort under T, not H?

Because MySQL compares the characters as they are; it knows nothing about English articles. Libraries and stores that file titles under the main word store a second column, for example sort_title = 'Hobbit, The', and sort by that.

Is there a LIMIT for "the top 3, including ties"?

Not with LIMIT alone; it always stops at exactly n rows. "Every book whose price is among the three highest prices" is a job for a subquery (Lesson 3.4) or a window function such as DENSE_RANK() (Lesson 5.2).

📝 Lesson Summary

🎓 Key Takeaways

  • Tables have no built-in order: without ORDER BY, row order is not guaranteed
  • ORDER BY is ascending by default; DESC applies only to the column right before it
  • Extra sort columns break ties; end with a unique column whenever the order must be repeatable
  • You can sort by expressions, aliases and CASE ranks; avoid column numbers in saved queries
  • NULLs sort first ascending and last descending; ORDER BY col IS NULL, col puts them last (MySQL has no NULLS LAST)
  • LIMIT n OFFSET m skips m rows and returns n; page N uses OFFSET (N - 1) × size, computed before the query
  • Count pages with a separate COUNT(*) query; SQL_CALC_FOUND_ROWS is deprecated
  • Keyset pagination (WHERE id > last_seen) stays fast on huge tables
