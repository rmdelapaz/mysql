🗄️ Lesson 1.1: What Is a Database?

Every website that remembers you, every store that knows what is in stock, every app that shows your order history keeps its data in a database. Before you install anything or type a single query, this lesson answers the basic questions: what a database is, why a spreadsheet is not enough, how a relational database arranges data in tables, and where SQL and MySQL fit in.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Explain what a database and a database management system (DBMS) are, and name three problems a database solves that a spreadsheet does not
  • Tell relational databases apart from the main non-relational kinds, and pick a sensible type for a simple scenario
  • Point to the table, columns, rows, primary key and foreign key in a small example
  • Describe what SQL is and match the four CRUD operations to INSERT, SELECT, UPDATE and DELETE
  • Sketch the tables of a small online bookstore on paper, with keys and relationships

🤔 Why Do We Need Databases?

Imagine you run a small online bookstore. You need to keep track of your books, your customers and every order that comes in. Where do you put all of that?

A spreadsheet works for a few dozen rows. Then the store grows to thousands of books, tens of thousands of customers and hundreds of orders a day, and the spreadsheet starts to crack:

  • The same data, copied everywhere: the customer's name and address are pasted into every order row, and when she moves, some copies get updated and some do not
  • No rules: nothing stops someone from typing "abc" into the price column or leaving the email empty
  • Slow searches: "every order from last Tuesday" means scanning every row
  • One editor at a time: two people saving the same file overwrite each other's changes
  • All or nothing access: anyone who can open the file sees every column, salaries included

A database is an organized collection of data that a program stores, protects and lets you query. That program is the database management system (DBMS). When people say "MySQL" or "PostgreSQL", they mean a DBMS. The database is your data; the DBMS is the software that guards it and answers questions about it.

💡 What a DBMS gives you

  • Structure: every piece of data has a defined place and type
  • Integrity: rules (a price must be a number, an email must be unique) are enforced on every change
  • Speed: indexes and a query optimizer find rows quickly, even among millions
  • Concurrency: many users and programs read and write at the same time without trampling each other
  • Security: accounts and permissions decide who may see or change what
  • Durability: once a change is confirmed, it survives a crash or a power cut

Notice that your application never touches the data files itself. It sends a request in SQL to the MySQL server, and the server does the reading and writing. That is why, in the next lesson, you install a server and a client program that talks to it.

🗂️ Types of Databases

Not every database stores data the same way. The two big families are relational and non-relational.

Relational databases (SQL)

A relational database stores data in tables with fixed columns, a bit like a very strict spreadsheet. The key difference is that tables are linked to each other through shared values called keys. This course is about this kind. Well-known relational systems:

  • MySQL: open source, everywhere in web hosting (this course)
  • MariaDB: a fork of MySQL, common on shared hosts and in XAMPP
  • PostgreSQL: open source, known for its rich feature set and standards support
  • SQLite: a whole database in one file, built into phones, browsers and many apps
  • Microsoft SQL Server and Oracle Database: commercial systems common in large companies

Non-relational databases (NoSQL)

Non-relational databases, often called NoSQL, store data in other shapes. Each shape suits particular jobs:

  • Document stores such as MongoDB keep JSON-like documents whose fields can vary from one record to the next
  • Key-value stores such as Redis keep a value under a key, usually in memory, for very fast lookups (sessions, caches)
  • Graph databases such as Neo4j store things and the connections between them (social networks, recommendations)
  • Wide-column stores such as Cassandra spread huge amounts of data across many machines
FeatureRelational (SQL)Non-relational (NoSQL)
Data shapeTables of rows and columnsDocuments, key-value pairs, graphs, wide columns
Structure (schema)Defined before you add dataOften flexible, record by record
Query languageSQL, shared by all of themDifferent for each product

💡 Which one should you learn first?

Relational. Most business data (orders, invoices, inventory, users) is naturally tabular, and most web applications store it in a relational database. The line has also blurred: MySQL can store JSON documents (you will do that in Lesson 7.3), and several NoSQL products now offer SQL-like query languages. Once you think in tables and keys, the other shapes are easy to pick up.

🧱 Relational Databases Up Close

These words come up in every lesson from here on, so it pays to make them precise now.

  • Table: a collection of data about one kind of thing: customers, books, orders. A database usually holds many tables.
  • Column (or field): one piece of information that every row has, with a name and a data type: email is text, price is a decimal number, published is a date.
  • Row (or record): one entry in the table: one customer, one book.
  • Primary key: a column (or a combination of columns) whose value is different in every row and never empty. It is how the database tells rows apart. The usual choice is a number the database hands out automatically: 1, 2, 3...
  • Foreign key: a column that holds another table's primary key, to say "this row belongs to that one". An order's customer_id says which customer placed it.
  • Schema: the blueprint: which tables exist, their columns, types, keys and rules. (In MySQL, "schema" is also simply another word for a database.)

💬 What Is SQL?

SQL (Structured Query Language, pronounced "S-Q-L" or "sequel") is the language you use to talk to a relational database. You describe what you want ("the titles of all books under $10, cheapest first") and the database works out how to get it. That is called a declarative language: you never write the loop that walks through the rows.

SQL dates from the 1970s and has been an official standard since 1986. Every relational database speaks it, each with its own small extras and quirks (called its dialect). The core you learn in this course carries over to PostgreSQL, SQLite and SQL Server with few changes.

The four basic operations: CRUD

OperationSQL statementWhat it does
CreateINSERTAdd new rows to a table
ReadSELECTFetch rows from one or more tables
UpdateUPDATEChange values in existing rows
DeleteDELETERemove rows from a table

Beyond CRUD, SQL also defines structure (CREATE TABLE, ALTER TABLE), enforces rules (constraints such as NOT NULL and UNIQUE), combines tables (joins), summarizes data (COUNT, SUM, AVG), controls access (GRANT) and groups changes so they succeed or fail together (transactions). You will meet every one of these in the course.

👀 A First Taste of SQL

You do not need to understand every detail yet: each statement gets its own lesson later. Read the code, then read the output underneath it, which is exactly what MySQL 9.7 printed for it. Once MySQL is installed (next lesson) you can come back and type these yourself.

First, make a small practice database and a table for customers. The comments after -- are notes for humans; MySQL ignores them.

CREATE DATABASE preview_shop;   -- a new, empty database
USE preview_shop;               -- work inside it from now on

CREATE TABLE customers (
    id         INT AUTO_INCREMENT PRIMARY KEY,  -- 1, 2, 3... handed out by MySQL
    first_name VARCHAR(50)  NOT NULL,           -- text, up to 50 characters, required
    last_name  VARCHAR(50)  NOT NULL,
    email      VARCHAR(100) NOT NULL UNIQUE,    -- no two customers share an email
    city       VARCHAR(50)                      -- optional: may be left empty (NULL)
);

Output

Database changed

MySQL answers Database changed after USE. The other two statements succeed quietly.

Create: add three customers. MySQL fills in id by itself.

INSERT INTO customers (first_name, last_name, email, city)
VALUES ('Alice', 'Johnson',  'alice@example.com', 'New York'),
       ('Bob',   'Smith',    'bob@example.com',   'Chicago'),
       ('Carol', 'Williams', 'carol@example.com', 'Los Angeles');

Output

Query OK, 3 rows affected (0.01 sec)
Records: 3  Duplicates: 0  Warnings: 0

Read: ask for some columns of the rows that match a condition.

SELECT first_name, last_name, city
FROM customers
WHERE city = 'Chicago';

Output

+------------+-----------+---------+
| first_name | last_name | city    |
+------------+-----------+---------+
| Bob        | Smith     | Chicago |
+------------+-----------+---------+

Update: Bob moves to Boston. The WHERE clause picks the one row to change.

UPDATE customers
SET city = 'Boston'
WHERE id = 2;

Output

Query OK, 1 row affected (0.00 sec)
Rows matched: 1  Changed: 1  Warnings: 0

Delete: Carol closes her account. Then look at the whole table.

DELETE FROM customers
WHERE id = 3;

SELECT * FROM customers;

Output

+----+------------+-----------+-------------------+----------+
| id | first_name | last_name | email             | city     |
+----+------------+-----------+-------------------+----------+
|  1 | Alice      | Johnson   | alice@example.com | New York |
|  2 | Bob        | Smith     | bob@example.com   | Boston   |
+----+------------+-----------+-------------------+----------+

SELECT * means "all columns". Bob's row now says Boston, and Carol is gone.

✅ SQL reads almost like English

"Select first name, last name and city from customers where the city is Chicago." That readability is one reason SQL has lasted fifty years. The other is that the same few statements answer an enormous range of questions.

🐬 Why MySQL?

  • Everywhere on the web: WordPress, Drupal and countless custom applications run on MySQL, and almost every web host offers it. Large sites such as YouTube, Meta (Facebook), Uber and Airbnb have run big MySQL installations.
  • Free: MySQL Community Edition is open source (GPL) and free to download and use. Oracle owns MySQL and also sells an Enterprise Edition with extra tools.
  • Part of the classic web stack: LAMP stands for Linux, Apache, MySQL and PHP (or Python/Perl). Modern stacks swap pieces (Nginx, Node.js, Docker), but MySQL keeps its place.
  • A huge community: decades of documentation, answers, books and tools.
  • Skills that transfer: SQL learned on MySQL works, with small changes, on PostgreSQL, SQLite and SQL Server, and MySQL itself shows up in job ads for web developers, data analysts and database administrators.

🐬 Version note: MySQL 9.7 LTS, and MariaDB

This course targets MySQL 9.7 LTS (long-term support: years of bug and security fixes without feature changes). Most of it also works on the previous LTS, 8.4. MariaDB is a fork of MySQL started by MySQL's original creator; it understands nearly all the SQL in this course, but it is a separate product and differs in places a beginner can hit. Where that happens, a version note like this one shows you the difference.

⚠️ Common Mistakes

A database's rules are a feature: they refuse bad data that a spreadsheet would accept without a word. Here is the preview_shop.customers table from above rejecting three kinds of bad data. Read the error messages: you will see them again.

1. Reusing a primary key

INSERT INTO customers (id, first_name, last_name, email)
VALUES (1, 'Dave', 'Brown', 'dave@example.com');

Error

ERROR 1062 (23000): Duplicate entry '1' for key 'customers.PRIMARY'

What it means: id 1 already belongs to Alice, and a primary key must be unique. Fix: leave id out of the INSERT and let AUTO_INCREMENT pick the next number.

2. Text where a number belongs

INSERT INTO customers (id, first_name, last_name, email)
VALUES ('abc', 'Dave', 'Brown', 'dave@example.com');

Error

ERROR 1366 (HY000): Incorrect integer value: 'abc' for column 'id' at row 1

What it means: id is an INT column and 'abc' is not a whole number. A spreadsheet cell would have taken it. Fix: give each column a value of its type. You will choose data types on purpose in Lesson 2.2.

3. Leaving out a required value

INSERT INTO customers (first_name, email)
VALUES ('Dave', 'dave@example.com');

Error

ERROR 1364 (HY000): Field 'last_name' doesn't have a default value

What it means: last_name was declared NOT NULL with no default value, so a row without it is refused. Fix: supply every required column.

4. Copying the same facts into many rows (silent)

No error message warns you about this one. Picture a single orders sheet with the columns order_id, customer_name, customer_email, customer_city, book_title, book_price. Alice's name and email appear in every order she places. When she changes her email, someone must find and fix every copy; miss one and the database now holds two "truths". Fix: one table per kind of thing, each fact stored once, and keys (customer_id, book_id) to connect them. Lesson 6.3 gives this idea its formal name: normalization.

5. Mixing up the server, the client and the database

"I installed MySQL but I can't find my database" usually means one of three different things got confused. The MySQL server is the program running in the background. A client (the mysql command, phpMyAdmin, MySQL Workbench) is what you type into. A database such as bookstore lives inside the server, and you create it yourself. Fix: keep the three apart in your head; Lesson 1.3 makes the difference concrete.

💡 Cleaning up

If you come back and run these examples after installing MySQL, remove the practice database when you are done. DROP DATABASE deletes a database and every table in it, with no undo:

DROP DATABASE preview_shop;

🛠️ Project: Sketch the Bookstore

Throughout this course you will build and query the database of a small online bookstore. Before anyone writes SQL, a database starts on paper: what are the things, what do we know about each one, and how do they connect? You will make that sketch now, then compare it with the design the course actually uses. Allow about 30 minutes, and use pen and paper or a plain text file.

🛠️ Step 1: List the things (5 min)

Read this description and underline every noun that the store needs to remember:

"Customers browse our books and place orders. An order can contain several books, each in some quantity, at the price the book had that day. Every book has an author, and an author can write several books. We sort books into categories such as Fantasy and Classic, and a book can be in more than one category."

Turn the important nouns into table names (plural, lowercase, by convention): you should end up with about five.

🛠️ Step 2: Give each table its columns (10 min)

For each table, list four to six columns and write a type next to each: text, whole number, decimal number, date, or yes/no. Ask "what would a clerk look up about this thing?". Do not put a list into one column: if a book can have several categories, that needs its own design (see step 4).

🛠️ Step 3: Choose the primary keys (5 min)

Mark one column in each table as the primary key. Would a book's title work? (Two different books can share a title.) Would a customer's email work? (People change emails.) Most designers add a plain id number to every table for exactly these reasons.

🛠️ Step 4: Connect the tables (5 min)

Draw a line between tables that refer to each other and write the foreign key column on the "many" side: an order belongs to one customer, so orders gets a customer_id. For "an order contains several books" and "a book has several categories", you need a table in the middle whose rows each link one of each, such as one row per book in an order.

🛠️ Step 5: Compare with the course design (5 min)

Here is the bookstore database as you will build it by Module 4 (simplified: a few columns left out). Compare it with your sketch. Different names are fine; what matters is the shape.

Notice order_items.price_at_time: the price is copied into the order on purpose, because a book's price can change later and an old order must keep the price the customer actually paid. Copying is wrong when it duplicates a fact; it is right when it records a fact of its own (the price on that day).

✅ Project Completion Checklist

  • Your sketch has a table for customers, orders, books, authors and categories
  • Every table has a primary key, and you can say why a title or email would be a poor one
  • Each relationship has a foreign key column on the "many" side
  • The two many-to-many relationships (orders and books, books and categories) each have a linking table
  • You found at least one difference between your sketch and the course design, and can say which you prefer and why

🏋️ Hands-on Exercises

No software needed: these are thinking exercises. Write your answers down before you open the solutions.

🏋️ Exercise 1: Identify the Parts

Look at this table and answer: what would you name it, how many columns and rows does it have, and which column is the primary key?

idtitlepricepublishedin_stock
1Dune14.991965-08-01true
219849.991949-06-08true
4The Great Gatsby8.991925-04-10false
💡 Hint

Each row describes one product the store sells. The primary key is the column whose only job is to tell rows apart.

✅ Solution

Call it books. It has 5 columns (id, title, price, published, in_stock) and 3 rows. id is the primary key: unique, never empty, and meaningless on purpose. The missing id 3 is normal: ids are never reused after a row is deleted, so gaps are expected and harmless.

🏋️ Exercise 2: Spot the Spreadsheet Problems

A store tracks orders in this sheet. Find at least three problems a relational design would prevent.

ordercustomeremailbookstotal
1Alice Johnsonalice@example.comDune, 1984, 198434.97
2Alice Jonsonalice@example.comPride and Prejudice7.99
3Bob Smithbob@exampleDuneabout 15
💡 Hint

Look for the same fact written twice, several values squeezed into one cell, and values of the wrong kind.

✅ Solution
  • The customer's name is typed into every order, and order 2 already misspells it ("Jonson"). A customers table plus customer_id stores it once.
  • The books cell holds a list. You cannot easily count copies of 1984 sold or find every order containing Dune. An order_items table with one row per book (and a quantity) fixes it.
  • "about 15" is not a number. A DECIMAL column would refuse it (error 1366, like mistake 2).
  • bob@example is not a complete email address. Columns can carry rules; at minimum NOT NULL and UNIQUE, and checks for the format can be added.
  • The total can be calculated from the items, so storing it invites totals that disagree with the items.

🏋️ Exercise 3: Pick the Database Type

For each scenario, would you choose a relational database, a key-value store, a document store or a graph database?

  1. An online bookstore's orders, payments and inventory
  2. Remembering which user is logged in, for millions of short website sessions
  3. "People who know someone who knows you" suggestions in a social app
  4. A product catalog where a shirt has sizes and colors but a laptop has a CPU and RAM
💡 Hint

Ask what shape the data has: tables of similar records, a simple key and value, records with varying fields, or a web of connections.

✅ Solution
  1. Relational: structured data, relationships, and money that must add up (transactions).
  2. Key-value (for example Redis): look up one value by one key, very fast, often in memory.
  3. Graph: the question is about chains of connections.
  4. Document store, or a relational table with a JSON column for the varying part. MySQL can do the latter, as you will see in Lesson 7.3. Real systems often mix types.

❓ Common Questions at This Stage

Is SQL a programming language?

It is a language for working with data. It is not used to build whole applications the way Python or JavaScript are, but it is precise, it has its own syntax and errors, and MySQL adds stored procedures (Lesson 7.1) with loops and variables. In practice, applications are written in a general language and send SQL to the database for the data work.

MySQL or PostgreSQL: did I pick the wrong one?

No. Both are excellent, free relational databases, and about 90% of what you learn here transfers directly. MySQL is the most common choice on web hosting and with PHP applications such as WordPress; PostgreSQL is popular for its extra features. Learn one well and the other takes days, not months.

Is MariaDB the same as MySQL?

Almost, but not quite. MariaDB began as a copy of MySQL in 2009 and has gone its own way since. The basic SQL in this course runs on both, but some newer MySQL features and some error messages differ. If your school or web host gives you MariaDB (XAMPP does), you can follow along; the version notes point out where results will look different.

Do I need to be good at math?

No. You need to think clearly about "which rows" and "which columns". The math in this course stops at sums, averages and the occasional percentage.

📝 Lesson Summary

🎓 Key Takeaways

  • A database is organized data; a DBMS such as MySQL is the server software that stores it, enforces its rules and answers queries
  • Relational databases keep data in tables linked by keys; NoSQL databases use documents, key-value pairs, graphs or wide columns
  • A primary key identifies each row; a foreign key points to a row in another table
  • Store each fact once and connect tables with keys; many-to-many relationships need a linking table
  • SQL is the declarative language of relational databases; CRUD maps to INSERT, SELECT, UPDATE, DELETE
  • The database's rules (types, NOT NULL, unique keys) reject bad data with numbered errors such as 1062, 1366 and 1364
  • This course uses MySQL 9.7 LTS; MariaDB is a close but separate relative
