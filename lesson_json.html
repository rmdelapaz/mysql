🧩 Lesson 7.3: JSON Columns

Every book has a title, a price and an author, so those are columns. But only some books belong to a series, only some won awards, and only some come illustrated. Where do details like that go? This lesson shows how a JSON column holds flexible, per-row details, how to read, change, build and index them with SQL, and, just as important, when a plain column or table is still the better choice.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Add a JSON column and explain how MySQL validates and stores what you put in it
  • Read values with ->, ->> and JSON_EXTRACT, and filter rows on them
  • Change parts of a document with JSON_SET, JSON_INSERT, JSON_REMOVE and JSON_ARRAY_APPEND
  • Turn rows into JSON with JSON_OBJECT and JSON_ARRAYAGG, and JSON back into rows with JSON_TABLE
  • Index a JSON path through a generated column, and decide when data belongs in real columns instead
  • ⏱️ Time 100 minutes
  • 📋 Prerequisites Lesson 7.2: Transactions
  • 🛠️ You will build catalog_feed.sql, a script that tags books, lists award winners and prints a JSON feed for the online store
  • 🗄️ Database bookstore freshly loaded from bookstore.sql, plus the attributes column you add in this lesson

🧩 Why a JSON Column?

The bookstore wants to show extra details on its website: the format (paperback or hardcover), the series a book belongs to, the awards it won, whether it is illustrated. Not every book has every detail, and next month the marketing team will invent a new one. You have three ways to store that:

DesignHow it looksThe catch
A column per detailformat, series, illustrated... on booksMostly NULL, and every new detail is an ALTER TABLE
A details tablebook_details(book_id, name, value)Every value becomes text, and reading one book takes many rows
A JSON columnattributes holding {"format": "paperback", ...}Flexible, but the database checks much less for you

JSON (JavaScript Object Notation) is the text format that web APIs and JavaScript use to exchange data. It has objects ({"key": value}), arrays ([1, 2, 3]), strings in double quotes, numbers, true, false and null. A JSON column stores one such document per row, next to the ordinary columns.

graph TD A["books row: Dune"] --> B["regular columns"] A --> C["attributes: JSON"] B --> D["title, price, author_id"] C --> E["format, series"] C --> F["awards: an array"]

🔑 The rule of thumb for this lesson

Data that every row has, that you join on, sum up or protect with constraints goes in columns. Optional, varied, mostly-for-display details can go in JSON. You will test that rule at the end of the lesson.

📦 The JSON Data Type

Start from a clean copy of the bookstore, so your results match the ones shown here. In the mysql client, load the file you downloaded (adjust the path to wherever you saved it):

Now add a JSON column called attributes to books and fill it. Dune gets a series and two awards, the two Tolkien books get a series and an "illustrated" flag, and every other book gets a format and an empty awards list:

ALTER TABLE books ADD COLUMN attributes JSON;
UPDATE books SET attributes = '{"format": "paperback", "series": "Dune Chronicles", "awards": ["Hugo", "Nebula"]}' WHERE id = 1;
UPDATE books SET attributes = '{"format": "hardcover", "series": "Middle-earth", "illustrated": true}' WHERE id IN (6, 9);
UPDATE books SET attributes = '{"format": "paperback", "awards": []}' WHERE attributes IS NULL;

💡 Where did my key order go?

You typed format, series, awards, but Dune shows awards first. MySQL does not keep your text: it parses the document into a compact binary form and sorts the keys of every object (shorter keys first, then alphabetically) so it can find a key quickly. Whitespace is normalized too. The data is identical; only the spelling changed. Never write code that depends on the order of keys inside a JSON object.

MySQL refuses invalid JSON

Unlike a TEXT column, a JSON column checks every value you store. Single quotes are not legal JSON, so this fails (you will meet the error again in Common Mistakes):

UPDATE books SET attributes = "{'format': 'ebook'}" WHERE id = 2;

Error

ERROR 3140 (22032): Invalid JSON text: "Missing a name for object member." at position 1 in value for column 'books.attributes'.

To check a string before you store it, or to ask what kind of value sits at a spot, use JSON_VALID() and JSON_TYPE():

SELECT
    JSON_VALID('{"format": "ebook"}')        AS good_json,
    JSON_VALID("{'format': 'ebook'}")        AS bad_json,
    JSON_TYPE(attributes)                    AS whole_doc,
    JSON_TYPE(attributes->'$.illustrated')  AS illustrated_flag
FROM books
WHERE id = 6;

Output

+-----------+----------+-----------+------------------+
| good_json | bad_json | whole_doc | illustrated_flag |
+-----------+----------+-----------+------------------+
|         1 |        0 | OBJECT    | BOOLEAN          |
+-----------+----------+-----------+------------------+

true without quotes is a real JSON boolean, not the text "true". The -> in that query is the next topic.

🔎 Reading JSON: ->, ->> and JSON_EXTRACT

To reach inside a document you give a path. Every path starts with $, which means "the whole document":

PathMeansOn Dune's attributes
'$'The whole documentthe full object
'$.format'The value of key format"paperback"
'$.awards'The value of key awards["Hugo", "Nebula"]
'$.awards[0]'The first element (counting from 0)"Hugo"
'$.awards[last]'The last element"Nebula"

MySQL gives you three ways to follow a path. Compare them side by side:

SELECT
    title,
    JSON_EXTRACT(attributes, '$.format') AS extracted,
    attributes->'$.format'               AS arrow,
    attributes->>'$.format'              AS double_arrow
FROM books
WHERE id IN (1, 6)
ORDER BY id;

Output

+------------+-------------+-------------+--------------+
| title      | extracted   | arrow       | double_arrow |
+------------+-------------+-------------+--------------+
| Dune       | "paperback" | "paperback" | paperback    |
| The Hobbit | "hardcover" | "hardcover" | hardcover    |
+------------+-------------+-------------+--------------+
graph TD A["attributes"] -->|"arrow or JSON_EXTRACT"| B["JSON value: quoted"] A -->|"double arrow"| C["plain text: unquoted"] B --> D["keep working in JSON"] C --> E["compare, sort, display"]
  • JSON_EXTRACT(doc, path) returns a JSON value. A JSON string keeps its double quotes.
  • doc->path is MySQL's shorthand for exactly the same thing.
  • doc->>path also removes the quotes: it is JSON_UNQUOTE(JSON_EXTRACT(doc, path)), and gives ordinary text you can show to people, compare and sort.

Arrays, nested values and missing keys

SELECT
    title,
    attributes->'$.awards'              AS awards,
    attributes->>'$.awards[0]'          AS first_award,
    JSON_LENGTH(attributes->'$.awards') AS award_count,
    attributes->>'$.series'             AS series
FROM books
WHERE id IN (1, 2, 6)
ORDER BY id;

Output

+------------+--------------------+-------------+-------------+-----------------+
| title      | awards             | first_award | award_count | series          |
+------------+--------------------+-------------+-------------+-----------------+
| Dune       | ["Hugo", "Nebula"] | Hugo        |           2 | Dune Chronicles |
| 1984       | []                 | NULL        |           0 | NULL            |
| The Hobbit | NULL               | NULL        |        NULL | Middle-earth    |
+------------+--------------------+-------------+-------------+-----------------+

Three things to notice. An array comes back as JSON (["Hugo", "Nebula"]). 1984 has an empty array, so it has no first award (NULL) and a length of 0. The Hobbit has no awards key at all, and asking for a key that is not there is not an error: the answer is simply SQL NULL.

🎯 Filtering on JSON Values

Once ->> gives you plain text, filtering looks like any other WHERE:

SELECT title, price
FROM books
WHERE attributes->>'$.format' = 'hardcover'
ORDER BY title;

Output

+-------------------+-------+
| title             | price |
+-------------------+-------+
| Lord of the Rings | 15.99 |
| The Hobbit        | 10.99 |
+-------------------+-------+

Is a value inside an array?

value MEMBER OF (json_array) answers "is this value one of the array's elements?". JSON_CONTAINS(doc, candidate, path) asks the same with a JSON candidate (note the inner double quotes):

SELECT title
FROM books
WHERE 'Hugo' MEMBER OF (attributes->'$.awards');

SELECT title
FROM books
WHERE JSON_CONTAINS(attributes, '"Nebula"', '$.awards');

Output

+-------+
| title |
+-------+
| Dune  |
+-------+
+-------+
| title |
+-------+
| Dune  |
+-------+

Does a key exist?

JSON_CONTAINS_PATH(doc, 'one', path) returns 1 when the path exists, which tells "key missing" apart from "key present but empty":

SELECT
    JSON_CONTAINS_PATH(attributes, 'one', '$.series') AS has_series,
    COUNT(*) AS books
FROM books
GROUP BY has_series
ORDER BY has_series DESC;

Output

+------------+-------+
| has_series | books |
+------------+-------+
|          1 |     3 |
|          0 |     8 |
+------------+-------+

Three books belong to a series (Dune and the two Tolkien books); the other eight have no series key. WHERE attributes->>'$.series' IS NOT NULL finds the same three.

✏️ Changing JSON: JSON_SET and Friends

You rarely rewrite a whole document. MySQL has functions that return a changed copy of a document, and you store that copy with UPDATE. First, see what each one does without changing anything (\G prints one value per line, which is easier to read for wide JSON):

SELECT
    JSON_SET(attributes, '$.format', 'ebook')            AS set_existing,
    JSON_SET(attributes, '$.edition', 'deluxe')          AS set_new,
    JSON_INSERT(attributes, '$.format', 'ebook')         AS insert_existing,
    JSON_REPLACE(attributes, '$.edition', 'deluxe')      AS replace_missing,
    JSON_REMOVE(attributes, '$.series')                  AS remove_key,
    JSON_ARRAY_APPEND(attributes, '$.awards', 'Locus')   AS append_award
FROM books
WHERE id = 1\G

Output

*************************** 1. row ***************************
   set_existing: {"awards": ["Hugo", "Nebula"], "format": "ebook", "series": "Dune Chronicles"}
        set_new: {"awards": ["Hugo", "Nebula"], "format": "paperback", "series": "Dune Chronicles", "edition": "deluxe"}
insert_existing: {"awards": ["Hugo", "Nebula"], "format": "paperback", "series": "Dune Chronicles"}
replace_missing: {"awards": ["Hugo", "Nebula"], "format": "paperback", "series": "Dune Chronicles"}
     remove_key: {"awards": ["Hugo", "Nebula"], "format": "paperback"}
   append_award: {"awards": ["Hugo", "Nebula", "Locus"], "format": "paperback", "series": "Dune Chronicles"}
FunctionKey existsKey missing
JSON_SETReplaces the valueAdds the key
JSON_INSERTLeaves it aloneAdds the key

To keep a change, assign the result back to the column. The Hobbit is about to get a 75th-anniversary edition; one JSON_SET can change several paths at once:

UPDATE books
SET attributes = JSON_SET(attributes, '$.edition', '75th anniversary', '$.format', 'hardcover')
WHERE id = 6;

SELECT title, attributes FROM books WHERE id = 6;

Output

Query OK, 1 row affected
Rows matched: 1  Changed: 1  Warnings: 0
+------------+-------------------------------------------------------------------------------------------------------+
| title      | attributes                                                                                            |
+------------+-------------------------------------------------------------------------------------------------------+
| The Hobbit | {"format": "hardcover", "series": "Middle-earth", "edition": "75th anniversary", "illustrated": true} |
+------------+-------------------------------------------------------------------------------------------------------+
1 row in set

The format was already "hardcover", so only the new edition key really changed. MySQL still counts the row as changed, because the stored document differs.

🏗️ Building JSON from Rows

JSON also flows the other way. A web page or mobile app often wants data as JSON, and MySQL can build it directly from ordinary rows with JSON_OBJECT(key, value, ...) and JSON_ARRAY(value, ...):

SELECT JSON_OBJECT('id', id, 'title', title, 'price', price, 'in_stock', in_stock = 1) AS item
FROM books
WHERE id <= 3
ORDER BY id;

Output

+-------------------------------------------------------------------------------+
| item                                                                          |
+-------------------------------------------------------------------------------+
| {"id": 1, "price": 14.99, "title": "Dune", "in_stock": true}                  |
| {"id": 2, "price": 9.99, "title": "1984", "in_stock": true}                   |
| {"id": 3, "price": 11.99, "title": "To Kill a Mockingbird", "in_stock": true} |
+-------------------------------------------------------------------------------+

Numbers stay numbers. in_stock is a TINYINT, so on its own it would become 1; the comparison in_stock = 1 turns it into a JSON true.

JSON_ARRAYAGG and JSON_OBJECTAGG: aggregates that build JSON

These two work like COUNT or SUM from Lesson 3.3: they collapse a group of rows into one value, here a JSON array or object.

SELECT a.name, JSON_ARRAYAGG(b.title) AS titles
FROM authors AS a
JOIN books AS b ON b.author_id = a.id
GROUP BY a.id, a.name
HAVING COUNT(*) > 1
ORDER BY a.name;

Output (the order of titles inside each array can differ)

+----------------+-------------------------------------+
| name           | titles                              |
+----------------+-------------------------------------+
| George Orwell  | ["1984", "Animal Farm"]             |
| J.R.R. Tolkien | ["The Hobbit", "Lord of the Rings"] |
+----------------+-------------------------------------+

⚠️ No ORDER BY inside JSON_ARRAYAGG

MySQL does not promise any order for the elements of JSON_ARRAYAGG, and unlike GROUP_CONCAT it has no ORDER BY option inside the parentheses. If the order matters to the app, sort in the app, or build the array from rows that the app sorts itself.

SELECT JSON_OBJECTAGG(city, customers) AS customers_per_city
FROM (
    SELECT city, COUNT(*) AS customers
    FROM customers
    WHERE city IS NOT NULL
    GROUP BY city
) AS per_city;

Output

+---------------------------------------------------------------+
| customers_per_city                                            |
+---------------------------------------------------------------+
| {"Chicago": 2, "Houston": 1, "New York": 2, "Los Angeles": 1} |
+---------------------------------------------------------------+

A whole order as one document

Nest the functions and you can hand an app a complete order: customer, date and an array of line items. JSON_PRETTY adds line breaks and indentation for humans:

SELECT JSON_PRETTY(
    JSON_OBJECT(
        'order_id', o.id,
        'customer', CONCAT(c.first_name, ' ', c.last_name),
        'items', JSON_ARRAYAGG(JSON_OBJECT('title', b.title, 'qty', oi.quantity, 'price', oi.price_at_time))
    )
) AS order_doc
FROM orders AS o
JOIN customers AS c    ON c.id = o.customer_id
JOIN order_items AS oi ON oi.order_id = o.id
JOIN books AS b        ON b.id = oi.book_id
WHERE o.id = 1
GROUP BY o.id, c.first_name, c.last_name\G

Output (the order of the two items can differ)

*************************** 1. row ***************************
order_doc: {
  "items": [
    {
      "qty": 1,
      "price": 14.99,
      "title": "Dune"
    },
    {
      "qty": 2,
      "price": 9.99,
      "title": "1984"
    }
  ],
  "customer": "Alice Johnson",
  "order_id": 1
}

Notice the keys again: qty, price, title come out shortest first, whatever order you wrote them in.

🔄 JSON_TABLE: From JSON Back to Rows

Arrays inside a column are awkward to report on: how do you list every award as its own row, or count them? JSON_TABLE turns a JSON document into a temporary table you can use in FROM, like a derived table:

graph TD A["Dune: awards array"] --> B["JSON_TABLE with path $.awards[*]"] B --> C["row: Hugo"] B --> D["row: Nebula"] 
SELECT b.title, aw.award
FROM books AS b,
     JSON_TABLE(
         b.attributes,
         '$.awards[*]'
         COLUMNS (award VARCHAR(40) PATH '$')
     ) AS aw
ORDER BY b.title, aw.award;

Output

+-------+--------+
| title | award  |
+-------+--------+
| Dune  | Hugo   |
| Dune  | Nebula |
+-------+--------+

Read it as: "for every book, take the array at $.awards, make one row per element ([*]), and call the element itself (PATH '$') award". Books with an empty array or no array produce no rows, so only Dune appears. The comma before JSON_TABLE works like a join in which JSON_TABLE can see the current book's columns.

Reading incoming JSON

JSON_TABLE also reads a literal document, which is handy when a supplier or a web form sends you JSON. Here a supplier's price list becomes rows with real SQL types, joined to books to compare prices:

SELECT b.title, b.price AS our_price, sp.new_price, sp.note
FROM JSON_TABLE(
         '[{"id": 1, "price": 15.49}, {"id": 6, "price": 11.49, "note": "reprint"}]',
         '$[*]'
         COLUMNS (
             book_id   INT          PATH '$.id',
             new_price DECIMAL(8,2) PATH '$.price',
             note      VARCHAR(20)  PATH '$.note' DEFAULT '"none"' ON EMPTY
         )
     ) AS sp
JOIN books AS b ON b.id = sp.book_id
ORDER BY b.id;

Output

+------------+-----------+-----------+---------+
| title      | our_price | new_price | note    |
+------------+-----------+-----------+---------+
| Dune       |     14.99 |     15.49 | none    |
| The Hobbit |     10.99 |     11.49 | reprint |
+------------+-----------+-----------+---------+

DEFAULT '"none"' ON EMPTY fills in a value when the key is missing (the default is itself written as JSON, hence the inner double quotes). Without it, Dune's note would be NULL.

⚡ Indexing a JSON Path

With 11 books every query is instant. With a million, WHERE attributes->>'$.format' = 'hardcover' would read every document. You cannot index a JSON column itself (that is error 3152, in Common Mistakes), but you can index a generated column that pulls one value out of it.

A generated column is computed from other columns of the same row. VIRTUAL means it is calculated when read and takes no space in the table; the index on it stores the values.

ALTER TABLE books
    ADD COLUMN format VARCHAR(20)
        GENERATED ALWAYS AS (attributes->>'$.format') VIRTUAL,
    ADD INDEX idx_books_format (format);

SELECT title, format FROM books WHERE format = 'hardcover' ORDER BY title;

Output

+-------------------+-----------+
| title             | format    |
+-------------------+-----------+
| Lord of the Rings | hardcover |
| The Hobbit        | hardcover |
+-------------------+-----------+

Now ask the optimizer (you met EXPLAIN in Lesson 6.1) how it would run the query. The interesting part: MySQL also uses the index when you write the original JSON expression, because it matches the generated column's definition.

EXPLAIN SELECT title FROM books WHERE attributes->>'$.format' = 'hardcover'\G

Output (your cost and row estimates will differ)

*************************** 1. row ***************************
EXPLAIN: -> Index lookup on books using idx_books_format (format = 'hardcover')  (cost=0.7 rows=2)

Index lookup on books using idx_books_format means the index is used. MySQL 9.7 prints EXPLAIN as this tree by default; MySQL 8.4 prints the classic table, where you would look for idx_books_format in the key column.

💡 Generated columns are read-only

You never write to format directly; change attributes and format follows. Use STORED instead of VIRTUAL when you want the value saved in the row (needed, for example, for a foreign key on it).

🚦 When Not to Use JSON

JSON is convenient, and that is its danger: it is easy to dump everything into one column and lose most of what a relational database does for you.

Use real columns or tables when...JSON is reasonable when...
Every row has the value (price, title)Only some rows have it (series, edition)
You join on it (author, customer)You only display it
You sum, average or sort by it oftenYou filter on it now and then (index a path if needed)
It needs a type, NOT NULL, UNIQUE or a foreign keyIts shape varies or changes often
It is a list of related things (order items)It is a small list of labels (awards, tags)

A JSON document cannot hold a foreign key, and nothing stops one row from saying "format": "paperback" and another "Format": "Paperback". If a JSON value matters, protect it with a CHECK constraint (you met CHECK in Lesson 2.2):

ALTER TABLE books
    ADD CONSTRAINT chk_books_format
    CHECK (attributes->>'$.format' IN ('paperback', 'hardcover', 'ebook'));
UPDATE books SET attributes = JSON_SET(attributes, '$.format', 'scroll') WHERE id = 2;

Error

ERROR 3819 (HY000): Check constraint 'chk_books_format' is violated.

🛑 Do not hide the core of your data in JSON

A table with an id and one big data JSON column is a document store wearing a MySQL costume. Prices in JSON cannot be summed reliably, customer ids in JSON cannot be protected by a foreign key, and every query gets harder to read. Design the tables first (Lesson 6.3), then use JSON for the leftovers.

🐬 JSON on MariaDB and MySQL 8.4

Everything in this lesson runs the same on MySQL 8.4 (except the EXPLAIN layout). MariaDB, which XAMPP and many shared hosts install, is different in three ways you will notice:

  • JSON is an alias for LONGTEXT plus a CHECK (json_valid(...)) constraint. The text is stored exactly as you typed it, key order included.
  • There is no -> and no ->>. Use JSON_EXTRACT, JSON_UNQUOTE(JSON_EXTRACT(...)) or JSON_VALUE(doc, path), which work on all three servers.
  • There is no MEMBER OF; use JSON_CONTAINS. Invalid JSON fails with error 4025 (the CHECK constraint) instead of 3140.
ALTER TABLE books ADD COLUMN attributes JSON;
UPDATE books SET attributes = '{"format": "paperback", "series": "Dune Chronicles", "awards": ["Hugo", "Nebula"]}' WHERE id = 1;

SELECT title, attributes, JSON_VALUE(attributes, '$.format') AS format
FROM books
WHERE id = 1;

Output on MariaDB

+-------+------------------------------------------------------------------------------------+-----------+
| title | attributes                                                                         | format    |
+-------+------------------------------------------------------------------------------------+-----------+
| Dune  | {"format": "paperback", "series": "Dune Chronicles", "awards": ["Hugo", "Nebula"]} | paperback |
+-------+------------------------------------------------------------------------------------+-----------+
SELECT title, attributes->>'$.format' AS format FROM books WHERE id = 1;

Error on MariaDB

ERROR 1064 (42000): You have an error in your SQL syntax; check the manual that corresponds to your MariaDB server version for the right syntax to use near '>>'$.format' AS format FROM books WHERE id = 1' at line 1

JSON_VALUE works on MySQL too (it returns the unquoted value, like ->>), so it is the choice for SQL that must run on both.

⚠️ Common Mistakes

1. Writing JSON with single quotes or bare keys

UPDATE books SET attributes = '{format: "ebook"}' WHERE id = 2;

Error

ERROR 3140 (22032): Invalid JSON text: "Missing a name for object member." at position 1 in value for column 'books.attributes'.

What it means: JavaScript lets you write {format: "ebook"}, JSON does not: every key must be a double-quoted string. "At position 1" points at the character right after the {. Fix: '{"format": "ebook"}', or let MySQL write the JSON for you with JSON_OBJECT('format', 'ebook'), which can never be malformed.

2. Leaving out the $

SELECT title, attributes->>'format' FROM books;

Error

ERROR 3143 (42000): Invalid JSON path expression. The error is around character position 1.

What it means: every path starts at the document root, $. Fix: attributes->>'$.format'.

3. Indexing the JSON column itself

CREATE INDEX idx_books_attributes ON books (attributes);

Error

ERROR 3152 (42000): JSON column 'attributes' supports indexing only via generated columns on a specified JSON path.

What it means: a whole document has no useful sort order to index. Fix: index the path you search on, through a generated column, as in Indexing a JSON Path.

4. A misspelled key (silent)

SELECT title
FROM books
WHERE attributes->>'$.Format' = 'hardcover';

Output

Empty set

What it means: keys are case-sensitive, and a missing key is not an error, just NULL. $.Format exists in no document, so nothing matches and nothing warns you. With a real column, a typo would have raised error 1054. Fix: copy key names from the data (SELECT attributes ... LIMIT 1), keep them in one spelling (lowercase is the common choice), and protect important keys with a CHECK or a generated column.

5. Using -> where you meant ->> (silent)

SELECT CONCAT(title, ' (', attributes->'$.format', ')') AS label
FROM books
WHERE id = 1;

Output

+--------------------+
| label              |
+--------------------+
| Dune ("paperback") |
+--------------------+

What it means: -> returns the JSON string with its quotes, and they end up on the web page. Fix: use ->> (or JSON_UNQUOTE) whenever the value leaves JSON: for display, CONCAT, comparisons with text, and sorting.

🛠️ Project: The Catalog Feed

The online store's developer wants a JSON feed of selected books and a few facts for the marketing page. You will write catalog_feed.sql, one step at a time, running each query as you add it. Allow about 35 minutes.

🛠️ Step 1: Add the ebooks (5 min)

The store now sells Brave New World (id 7) and Fahrenheit 451 (id 10) as ebooks. Create catalog_feed.sql in your mysql-course folder, start it with USE bookstore;, and change their format with JSON_SET, adding the file size in megabytes. The CHECK you added allows 'ebook'.

USE bookstore;

-- 1. Two titles become ebooks
UPDATE books
SET attributes = JSON_SET(attributes, '$.format', 'ebook', '$.file_mb', 1.8)
WHERE id IN (7, 10);

SELECT id, title, attributes FROM books WHERE id IN (7, 10) ORDER BY id;

Output

Database changed
+----+-----------------+---------------------------------------------------+
| id | title           | attributes                                        |
+----+-----------------+---------------------------------------------------+

1984 and Fahrenheit 451 are both in the Prometheus Hall of Fame. Append the award to their arrays, then list every award with JSON_TABLE.

🛠️ Step 4: The feed (10 min)

One JSON document per ebook and hardcover, with the author's name from the authors table and the awards copied from attributes. Regular columns and JSON values mix freely inside JSON_OBJECT.

-- 4. The feed: one document per featured book
SELECT JSON_OBJECT(
           'id',     b.id,
           'title',  b.title,
           'author', a.name,
           'price',  b.price,
           'format', b.format,
           'awards', COALESCE(b.attributes->'$.awards', JSON_ARRAY())
       ) AS feed_item
FROM books AS b
JOIN authors AS a ON a.id = b.author_id
WHERE b.format IN ('ebook', 'hardcover')
ORDER BY b.id;

The website gets a "More in this series" box. Add a generated, indexed series column and use it.

🏋️ Exercise 2: A New Edition

Lord of the Rings (id 9) is reissued as a paperback without illustrations. In ONE UPDATE, set its format to paperback and remove the illustrated key. Then show its attributes and its generated format column.

💡 Hint

The functions nest: the result of JSON_SET(...) can be the first argument of JSON_REMOVE(...).

✅ Solution 
UPDATE books
SET attributes = JSON_REMOVE(JSON_SET(attributes, '$.format', 'paperback'), '$.illustrated')
WHERE id = 9;

SELECT title, format, attributes FROM books WHERE id = 9;

🏋️ Exercise 3: Customers per City as JSON

Build one JSON object that maps each city to its number of customers, including the customers without a city under the key "(no city)".

💡 Hint

Start from the JSON_OBJECTAGG query in this lesson and replace the WHERE filter with COALESCE(city, '(no city)') in the inner query. A JSON key cannot be NULL.

✅ Solution 
SELECT JSON_OBJECTAGG(city, customers) AS customers_per_city
FROM (
    SELECT COALESCE(city, '(no city)') AS city, COUNT(*) AS customers
    FROM customers
    GROUP BY COALESCE(city, '(no city)')
) AS per_city;

Output

+-------------------------------------------------------------------------------+
| customers_per_city                                                            |
+-------------------------------------------------------------------------------+
| {"Chicago": 2, "Houston": 1, "New York": 2, "(no city)": 2, "Los Angeles": 1} |
+-------------------------------------------------------------------------------+

Without the COALESCE, MySQL stops with error 3158, "JSON documents may not contain NULL member names".

🏋️ Exercise 4 (Stretch): Price an Incoming Web Order

The website sends this order as JSON: {"customer_id": 3, "items": [{"book_id": 1, "qty": 2}, {"book_id": 11, "qty": 1}]}. With JSON_TABLE, list each item's title, quantity and line total from the current prices, and then, in a second query, the order total.

💡 Hint

The row path is '$.items[*]'; inside COLUMNS, the paths are relative to each item: '$.book_id' and '$.qty'. Join the result to books.

✅ Solution 
SET @web_order = '{"customer_id": 3, "items": [{"book_id": 1, "qty": 2}, {"book_id": 11, "qty": 1}]}';

SELECT b.title, it.qty, b.price * it.qty AS line_total
FROM JSON_TABLE(@web_order, '$.items[*]'
         COLUMNS (book_id INT PATH '$.book_id', qty INT PATH '$.qty')) AS it
JOIN books AS b ON b.id = it.book_id
ORDER BY b.title;

SELECT JSON_VALUE(@web_order, '$.customer_id') AS customer_id, SUM(b.price * it.qty) AS order_total
FROM JSON_TABLE(@web_order, '$.items[*]'
         COLUMNS (book_id INT PATH '$.book_id', qty INT PATH '$.qty')) AS it
JOIN books AS b ON b.id = it.book_id;

Output

+-------------+------+------------+
| title       | qty  | line_total |
+-------------+------+------------+
| Animal Farm |    1 |       8.49 |
| Dune        |    2 |      29.98 |
+-------------+------+------------+
+-------------+-------------+
| customer_id | order_total |
+-------------+-------------+
| 3           |       38.47 |
+-------------+-------------+

Why JSON_VALUE and not @web_order->>'$.customer_id'? The arrow operators only work on a column name; on a variable or a literal they are a syntax error (1064). JSON_VALUE and JSON_EXTRACT work on any JSON value. Note also that the prices come from books, never from the incoming JSON: a browser can send any price it likes.

❓ Common Questions at This Stage

Why not just use a TEXT column for JSON?

A JSON column rejects invalid documents, stores them in a binary form that MySQL can search without re-parsing the text, and lets JSON_SET and friends update a document in place. A TEXT column accepts any typo and must be parsed again on every read. On MariaDB, JSON is text with a validity check, which still beats plain TEXT.

How big can a JSON document be?

Up to the server's max_allowed_packet setting (64 MB by default). In practice, keep documents small: a few keys and short lists. A document that grows without limit (every page view, every price change) is a sign it should be a table.

Can a foreign key point at a value inside JSON?

Not directly. You can add a STORED generated column for the value and put the foreign key on that column. If you find yourself doing that, the value probably deserved a real column from the start.

Should my app build JSON in SQL or in its own code?

Both work. Building it in SQL (JSON_OBJECT, JSON_ARRAYAGG) saves a round of reshaping in the app and is handy for exports. Building it in the app keeps SQL simple and lets the app control ordering. Whichever you choose, values from users go into queries as parameters (placeholders like ?), never pasted into the SQL text.

📝 Lesson Summary

🎓 Key Takeaways

  • A JSON column validates every document (error 3140) and stores it in a binary form with sorted keys
  • Paths start at $: $.format, $.awards[0], $.awards[*]
  • -> (= JSON_EXTRACT) returns JSON with quotes; ->> returns unquoted text for display and comparison
  • A missing key returns NULL, not an error, so a misspelled key fails silently
  • JSON_SET, JSON_INSERT, JSON_REPLACE, JSON_REMOVE and JSON_ARRAY_APPEND return changed copies; store them with UPDATE
  • JSON_OBJECT and JSON_ARRAYAGG build JSON from rows; JSON_TABLE turns JSON back into rows
  • Index a JSON path through a generated column; protect important keys with CHECK
  • Core data (every row has it, you join or calculate with it) belongs in real columns and tables
