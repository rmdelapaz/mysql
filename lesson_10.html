🪆 Lesson 3.4: Subqueries & Nested Queries

Some questions need an answer before they can be asked. "Which books cost more than average?" needs the average first. "Which book is the cheapest one by each author?" needs each author's minimum first. A subquery is a query inside another query: it works out the first answer, and the outer query uses it, all in a single statement.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Compare every row with an aggregate using a scalar subquery ("above average", "equal to the maximum")
  • Filter with IN, NOT IN, ANY and ALL subqueries, and keep NULLs from emptying a NOT IN
  • Write correlated subqueries and EXISTS / NOT EXISTS checks that compare a row with related rows
  • Build derived tables in FROM and computed columns in SELECT
  • Read and fix the subquery errors 1242, 1241, 1248 and 1235
  • ⏱️ Time 100 minutes
  • 📋 Prerequisites Lesson 3.3: Aggregate Functions & GROUP BY

🪆 What Is a Subquery?

A subquery (or inner query, or nested query) is a complete SELECT in parentheses, placed inside another statement, the outer query. Think of filling in a blank: the inner query works out the value, the outer query uses it.

💡 Follow along

Run USE bookstore; first. Every query reads the 10 books and 8 customers from the Lesson 3.1 setup script; rerun it if your results drift.

Here is the question "which books cost more than average?" in two steps. First the average:

SELECT AVG(price) FROM books;

Output

+------------+
| AVG(price) |
+------------+
|  10.990000 |
+------------+

Then the books above it, with the number typed in by hand:

SELECT title, price
FROM books
WHERE price > 10.99
ORDER BY price;

Output

+-----------------------+-------+
| title                 | price |
+-----------------------+-------+
| To Kill a Mockingbird | 11.99 |
| Dune                  | 14.99 |
| Lord of the Rings     | 15.99 |
+-----------------------+-------+

The typed-in 10.99 goes stale the moment a price changes. Put the first query where the number was, in parentheses, and MySQL works it out fresh every time:

SELECT title, price
FROM books
WHERE price > (SELECT AVG(price) FROM books)
ORDER BY price;

Output

+-----------------------+-------+
| title                 | price |
+-----------------------+-------+
| To Kill a Mockingbird | 11.99 |
| Dune                  | 14.99 |
| Lord of the Rings     | 15.99 |
+-----------------------+-------+
graph TD A["inner: SELECT AVG(price)"] --> B["one value: 10.99"] B --> C["outer: WHERE price above 10.99"] C --> D["3 rows"]

Subqueries can sit in three places, and each place expects a different shape of result:

WhereResult shapeExample
WHERE with =, >, ...One value (scalar)WHERE price > (SELECT AVG(price) ...)
WHERE with IN, ANY, ALLOne column, any number of rowsWHERE city IN (SELECT city ...)
WHERE EXISTSAnything; only "any rows?" mattersWHERE EXISTS (SELECT 1 ...)
FROMA whole table (needs an alias)FROM (SELECT ...) AS t
SELECT listOne value per rowSELECT title, (SELECT AVG(price) ...)

🎯 Scalar Subqueries: One Value

A scalar subquery returns exactly one row with one column: a single value. Anywhere you could type a number or a date, you can put a scalar subquery instead.

Which row holds the maximum?

In Lesson 3.3, MAX(price) told you the highest price but not which book has it. A subquery closes that gap:

SELECT title, author, price
FROM books
WHERE price = (SELECT MAX(price) FROM books);

Output

+-------------------+----------------+-------+
| title             | author         | price |
+-------------------+----------------+-------+
| Lord of the Rings | J.R.R. Tolkien | 15.99 |
+-------------------+----------------+-------+

Ties: all of them, not just one

What is the cheapest out-of-stock book? Two books share that price, and the subquery version returns both:

SELECT title, price
FROM books
WHERE in_stock = FALSE
  AND price = (SELECT MIN(price) FROM books WHERE in_stock = FALSE)
ORDER BY title;

Output

+------------------------+-------+
| title                  | price |
+------------------------+-------+
| The Catcher in the Rye |  8.99 |
| The Great Gatsby       |  8.99 |
+------------------------+-------+

Compare ORDER BY price LIMIT 1 from Lesson 3.2: it would return one of the two and silently drop the other. When ties are possible and you want all of them, use the subquery.

Arithmetic with a subquery

The value a subquery returns can be part of a calculation. Books that cost more than twice the cheapest book:

SELECT title, price
FROM books
WHERE price > (SELECT MIN(price) FROM books) * 2
ORDER BY price;

Output

+-------------------+-------+
| title             | price |
+-------------------+-------+
| Lord of the Rings | 15.99 |
+-------------------+-------+

The cheapest book costs 7.99, so the bar is 15.98, and only one book clears it, by a single cent.

📋 IN and NOT IN: A List of Values

When the inner query returns one column but several rows, it is a list, and lists go with IN, exactly like the hand-typed lists in Lesson 3.1. Customers who live in a city with more than one customer:

SELECT first_name, last_name, city
FROM customers
WHERE city IN (
    SELECT city
    FROM customers
    GROUP BY city
    HAVING COUNT(*) > 1
)
ORDER BY city, last_name;

Output

+------------+-----------+----------+
| first_name | last_name | city     |
+------------+-----------+----------+
| Bob        | Smith     | Chicago  |
| Grace      | Wilson    | Chicago  |
| Alice      | Johnson   | New York |
| Frank      | Miller    | New York |
+------------+-----------+----------+

Read it inside out. The inner query is a GROUP BY from Lesson 3.3; on its own it returns Chicago and New York, and also NULL, because Eve and Hank form a group of two. The outer query then becomes WHERE city IN ('Chicago', 'New York', NULL). The NULL in the list does no harm here: Eve's NULL = NULL is unknown, so she is not matched, and the real cities still match.

NOT IN, and the NULL trap

Now a question in the other direction. The team wants to know which January customers live in a city where none of the February customers live (Grace in Chicago and Hank, who has no city, joined in February):

SELECT first_name, city
FROM customers
WHERE created_at < '2026-02-01'
  AND city NOT IN (
      SELECT city
      FROM customers
      WHERE created_at >= '2026-02-01'
  );

Output

Empty set

Nothing, and no error. The inner query returns Chicago and NULL (Hank). So the outer test is city != 'Chicago' AND city != NULL, and the second half is unknown for every row. One NULL in a NOT IN list empties the whole result. Keep the NULLs out of the list:

SELECT first_name, city
FROM customers
WHERE created_at < '2026-02-01'
  AND city NOT IN (
      SELECT city
      FROM customers
      WHERE created_at >= '2026-02-01'
        AND city IS NOT NULL
  )
ORDER BY first_name;

Output

+------------+-------------+
| first_name | city        |
+------------+-------------+
| Alice      | New York    |
| Carol      | Los Angeles |
| Dave       | Houston     |
| Frank      | New York    |
+------------+-------------+

Bob is gone (he shares Chicago with Grace), and so is Eve: her own city is NULL, so NOT IN cannot decide about her either. You will see a version that treats her differently with NOT EXISTS below.

🛑 Rule: every NOT IN subquery gets an IS NOT NULL

A plain IN shrugs off a NULL in the list; NOT IN returns nothing at all. If the column in the subquery can be NULL, add WHERE column IS NOT NULL inside it, or use NOT EXISTS. This bug is common in real reports because the query works fine for months, until the first NULL arrives.

⚖️ ANY and ALL

ANY and ALL let a comparison operator work with a list. > ANY (list) is true if the value beats at least one item; < ALL (list) is true if it beats every item. Tolkien's books cost 10.99 and 15.99. Which books cost less than every Tolkien book?

SELECT title, price
FROM books
WHERE price < ALL (
    SELECT price FROM books WHERE author = 'J.R.R. Tolkien'
)
ORDER BY price, title;

Output

+------------------------+-------+
| title                  | price |
+------------------------+-------+
| Pride and Prejudice    |  7.99 |
| The Catcher in the Rye |  8.99 |
| The Great Gatsby       |  8.99 |
| Brave New World        |  9.49 |
| 1984                   |  9.99 |
| Fahrenheit 451         | 10.49 |
+------------------------+-------+

Less than all of them means less than the smallest, 10.99. And books that cost more than at least one Tolkien book, so more than 10.99:

SELECT title, price
FROM books
WHERE price > ANY (
    SELECT price FROM books WHERE author = 'J.R.R. Tolkien'
)
ORDER BY price;

Output

+-----------------------+-------+
| title                 | price |
+-----------------------+-------+
| To Kill a Mockingbird | 11.99 |
| Dune                  | 14.99 |
| Lord of the Rings     | 15.99 |
+-----------------------+-------+
You writeSame result as
= ANY (subquery)IN (subquery)
> ANY (subquery)> (SELECT MIN(...))
< ANY (subquery)< (SELECT MAX(...))
> ALL (subquery)> (SELECT MAX(...))
< ALL (subquery)< (SELECT MIN(...))

Most people find the MIN/MAX versions easier to read, and you will see ANY/ALL less often. Recognize them when you meet them. (SOME is a synonym for ANY.) One edge case: if the subquery returns no rows at all, > ALL is true for every row, while > (SELECT MAX(...)) compares with NULL and keeps nothing.

🔁 Correlated Subqueries

Every subquery so far could run on its own. A correlated subquery cannot: it refers to a column of the outer query's current row, so its answer is different for every row. Conceptually, MySQL runs it once per outer row.

Which books are priced above their own author's average (not the overall average)?

SELECT b.title, b.author, b.price
FROM books AS b
WHERE b.price > (
    SELECT AVG(b2.price)
    FROM books AS b2
    WHERE b2.author = b.author
);

Output

+-------------------+----------------+-------+
| title             | author         | price |
+-------------------+----------------+-------+
| Lord of the Rings | J.R.R. Tolkien | 15.99 |
+-------------------+----------------+-------+
graph TD A["outer row: The Hobbit, Tolkien"] --> B["inner: AVG for Tolkien = 13.49"] B --> C["10.99 above 13.49? no: dropped"] C --> D["next row: Lord of the Rings"] D --> E["inner: AVG for Tolkien = 13.49"] E --> F["15.99 above 13.49? yes: kept"]

The same table appears twice, so each copy gets an alias: b is the outer row being tested, b2 is the inner scan. WHERE b2.author = b.author is the correlation: "the books by this row's author". Every author with a single book has an average equal to that book's price, and a price is never above itself, so only Lord of the Rings survives.

The cheapest book of each author

Lesson 3.3 could tell you each author's lowest price with GROUP BY, but not which book that is. A correlated subquery can:

SELECT b.author, b.title, b.price
FROM books AS b
WHERE b.price = (
    SELECT MIN(b2.price)
    FROM books AS b2
    WHERE b2.author = b.author
)
ORDER BY b.author;

Output

+---------------------+------------------------+-------+
| author              | title                  | price |
+---------------------+------------------------+-------+
| Aldous Huxley       | Brave New World        |  9.49 |
| F. Scott Fitzgerald | The Great Gatsby       |  8.99 |
| Frank Herbert       | Dune                   | 14.99 |
| George Orwell       | 1984                   |  9.99 |
| Harper Lee          | To Kill a Mockingbird  | 11.99 |
| J.D. Salinger       | The Catcher in the Rye |  8.99 |
| J.R.R. Tolkien      | The Hobbit             | 10.99 |
| Jane Austen         | Pride and Prejudice    |  7.99 |
| Ray Bradbury        | Fahrenheit 451         | 10.49 |
+---------------------+------------------------+-------+

Nine authors, nine rows: for Tolkien, The Hobbit. This "row with the group's minimum" question is very common, and in Lesson 5.2 you will meet window functions that answer it another way.

⚠️ Speed

"Once per outer row" is the mental model, and on ten rows it costs nothing. MySQL's optimizer often rewrites correlated subqueries into something faster, but not always; on large tables, check with EXPLAIN (Lesson 6.1) and consider a join (Lesson 4.3).

❓ EXISTS and NOT EXISTS

EXISTS (subquery) is true if the subquery returns at least one row, whatever the row contains. It is almost always correlated: "is there a related row for this one?"

SELECT EXISTS (SELECT 1 FROM books WHERE price > 15) AS any_over_15,
       EXISTS (SELECT 1 FROM books WHERE price > 20) AS any_over_20;

Output

+-------------+-------------+
| any_over_15 | any_over_20 |
+-------------+-------------+
|           1 |           0 |
+-------------+-------------+

SELECT 1 is a convention: the columns inside EXISTS are never looked at, so 1 says "I only care whether a row exists".

Customers who share a city with someone

SELECT c.first_name, c.city
FROM customers AS c
WHERE EXISTS (
    SELECT 1
    FROM customers AS other
    WHERE other.city = c.city
      AND other.id != c.id
)
ORDER BY c.city, c.first_name;

Output

+------------+----------+
| first_name | city     |
+------------+----------+
| Bob        | Chicago  |
| Grace      | Chicago  |
| Alice      | New York |
| Frank      | New York |
+------------+----------+

For each customer, the subquery looks for another customer (other.id != c.id) in the same city. NOT EXISTS gives the rest:

SELECT c.first_name, c.city
FROM customers AS c
WHERE NOT EXISTS (
    SELECT 1
    FROM customers AS other
    WHERE other.city = c.city
      AND other.id != c.id
)
ORDER BY c.first_name;

Output

+------------+-------------+
| first_name | city        |
+------------+-------------+
| Carol      | Los Angeles |
| Dave       | Houston     |
| Eve        | NULL        |
| Hank       | NULL        |
+------------+-------------+

Eve and Hank are here: neither has a known city, so nobody can be found in "their" city.

NOT EXISTS has no NULL trap

Back to the January-versus-February question that NOT IN got wrong:

SELECT c.first_name, c.city
FROM customers AS c
WHERE c.created_at < '2026-02-01'
  AND NOT EXISTS (
      SELECT 1
      FROM customers AS feb
      WHERE feb.created_at >= '2026-02-01'
        AND feb.city = c.city
  )
ORDER BY c.first_name;

Output

+------------+-------------+
| first_name | city        |
+------------+-------------+
| Alice      | New York    |
| Carol      | Los Angeles |
| Dave       | Houston     |
| Eve        | NULL        |
| Frank      | New York    |
+------------+-------------+

Hank's NULL never matches anyone, so it cannot spoil the result, and Eve is included: no February customer is known to share her city. Whether Eve belongs in the answer is a business decision, but NOT EXISTS gives a sensible, predictable one, which is why many developers use it by default.

💡 Coming in Module 4

Today both sides of every EXISTS are the same table, because the flat bookstore has no links between tables. In Module 4 the store gets an orders table, and the classic questions appear: customers who have placed an order (EXISTS), books that were never ordered (NOT EXISTS). The pattern is exactly the one you just wrote.

🧱 Derived Tables: Subqueries in FROM

A subquery in FROM produces a temporary result that the outer query reads like a table: a derived table. It is how you summarize once and then work with the summary.

On average, how many books does an author have here? First count per author, then average the counts:

SELECT ROUND(AVG(book_count), 2) AS avg_books_per_author,
       MAX(book_count)            AS most_books
FROM (
    SELECT author, COUNT(*) AS book_count
    FROM books
    GROUP BY author
) AS author_counts;

Output

+----------------------+------------+
| avg_books_per_author | most_books |
+----------------------+------------+
|                 1.11 |          2 |
+----------------------+------------+

Ten books over nine authors. You cannot write AVG(COUNT(*)) in one level (try it: error 1111, "Invalid use of group function"); an aggregate of an aggregate needs two levels, and the derived table is the inner one.

Filtering a summary

The price bands from Lesson 3.3, keeping only the bands with more than two books:

SELECT price_band, books, avg_price
FROM (
    SELECT
        CASE
            WHEN price < 10 THEN 'Under $10'
            WHEN price < 13 THEN '$10 to $12.99'
            ELSE '$13 and up'
        END AS price_band,
        COUNT(*)             AS books,
        ROUND(AVG(price), 2) AS avg_price
    FROM books
    GROUP BY price_band
) AS bands
WHERE books > 2
ORDER BY avg_price;

Output

+---------------+-------+-----------+
| price_band    | books | avg_price |
+---------------+-------+-----------+
| Under $10     |     5 |      9.09 |
| $10 to $12.99 |     3 |     11.16 |
+---------------+-------+-----------+

HAVING COUNT(*) > 2 would do the same job here. The derived table earns its keep when the summary needs further work: joining it to another table, aggregating it again, or filtering on several of its columns at once.

⚠️ Every derived table needs a name

The AS author_counts and AS bands are not optional. Without them MySQL stops with error 1248, as you will see in Common Mistakes.

➕ Subqueries in the SELECT List

A scalar subquery in the SELECT list adds a computed column. Each book next to the store average, and how far it is from it:

SELECT
    title,
    price,
    (SELECT ROUND(AVG(price), 2) FROM books)         AS store_avg,
    ROUND(price - (SELECT AVG(price) FROM books), 2) AS diff_from_avg
FROM books
ORDER BY diff_from_avg DESC, title;

Output

+------------------------+-------+-----------+---------------+
| title                  | price | store_avg | diff_from_avg |
+------------------------+-------+-----------+---------------+
| Lord of the Rings      | 15.99 |     10.99 |          5.00 |
| Dune                   | 14.99 |     10.99 |          4.00 |
| To Kill a Mockingbird  | 11.99 |     10.99 |          1.00 |
| The Hobbit             | 10.99 |     10.99 |          0.00 |
| Fahrenheit 451         | 10.49 |     10.99 |         -0.50 |
| 1984                   |  9.99 |     10.99 |         -1.00 |
| Brave New World        |  9.49 |     10.99 |         -1.50 |
| The Catcher in the Rye |  8.99 |     10.99 |         -2.00 |
| The Great Gatsby       |  8.99 |     10.99 |         -2.00 |
| Pride and Prejudice    |  7.99 |     10.99 |         -3.00 |
+------------------------+-------+-----------+---------------+

The subquery does not refer to the outer row, so MySQL works it out once and reuses the value. A plain AVG(price) next to title would fail with error 1140 (Lesson 3.3); wrapping it in a subquery is what lets a per-row column and a whole-table number sit side by side.

Each book's share of the shelf's total value:

SELECT
    title,
    price,
    ROUND(price / (SELECT SUM(price) FROM books) * 100, 1) AS pct_of_total
FROM books
ORDER BY pct_of_total DESC, title
LIMIT 5;

Output

+-----------------------+-------+--------------+
| title                 | price | pct_of_total |
+-----------------------+-------+--------------+
| Lord of the Rings     | 15.99 |         14.5 |
| Dune                  | 14.99 |         13.6 |
| To Kill a Mockingbird | 11.99 |         10.9 |
| The Hobbit            | 10.99 |         10.0 |
| Fahrenheit 451        | 10.49 |          9.5 |
+-----------------------+-------+--------------+

A correlated column

The subquery in the SELECT list can be correlated too. How many books does each book's author have in the store?

SELECT
    b.title,
    b.author,
    (SELECT COUNT(*) FROM books AS b2 WHERE b2.author = b.author) AS author_titles
FROM books AS b
ORDER BY author_titles DESC, b.title
LIMIT 4;

Output

+-------------------+----------------+---------------+
| title             | author         | author_titles |
+-------------------+----------------+---------------+
| Lord of the Rings | J.R.R. Tolkien |             2 |
| The Hobbit        | J.R.R. Tolkien |             2 |
| 1984              | George Orwell  |             1 |
| Brave New World   | Aldous Huxley  |             1 |
+-------------------+----------------+---------------+

🧭 When to Use a Subquery

✅ Subqueries shine at

  • Comparing with an aggregate: above average, equal to the maximum, below the cheapest out-of-stock book
  • Finding the rows behind a number: which book has the maximum, which book is each author's cheapest
  • Existence checks: has a related row / has none (EXISTS, NOT EXISTS)
  • Two-level summaries: aggregate, then aggregate or filter the result again (derived tables)

Subqueries can nest inside subqueries. This works, but each level makes it harder to read:

SELECT title, price
FROM books
WHERE price > (
    SELECT AVG(price)
    FROM books
    WHERE author IN (
        SELECT author
        FROM books
        GROUP BY author
        HAVING COUNT(*) = 1
    )
)
ORDER BY price;

Output

+-----------------------+-------+
| title                 | price |
+-----------------------+-------+
| Fahrenheit 451        | 10.49 |
| The Hobbit            | 10.99 |
| To Kill a Mockingbird | 11.99 |
| Dune                  | 14.99 |
| Lord of the Rings     | 15.99 |
+-----------------------+-------+

Books priced above the average of the single-book authors. Reading it means starting at the innermost query and working outward, which is the opposite of how you read prose. Two tools later in the course make such queries easier: joins (Lesson 4.3) combine columns from several tables, and common table expressions (Lesson 5.1) let you give each step a name and write the steps top to bottom.

⚠️ Common Mistakes

1. Using = with a subquery that returns several rows

SELECT title, price
FROM books
WHERE price = (SELECT price FROM books WHERE in_stock = FALSE);

Error

ERROR 1242 (21000): Subquery returns more than 1 row

What it means: = needs one value, and there are two out-of-stock books, so two prices came back. The query may even work today and break tomorrow when a second row appears. Fix: use IN if any of the values should match, or make the subquery return one value with an aggregate (MIN, MAX) or a WHERE on a unique column.

2. Returning two columns where one is expected

SELECT title, author
FROM books
WHERE author IN (
    SELECT author, COUNT(*)
    FROM books
    GROUP BY author
    HAVING COUNT(*) > 1
);

Error

ERROR 1241 (21000): Operand should contain 1 column(s)

What it means: author IN (...) compares one value with a list of single values, but each row of the subquery has two columns. Fix: select only the column you compare: SELECT author FROM books GROUP BY author HAVING COUNT(*) > 1. The count can stay in HAVING without being selected.

3. A derived table without an alias

SELECT AVG(book_count)
FROM (
    SELECT author, COUNT(*) AS book_count
    FROM books
    GROUP BY author
);

Error

ERROR 1248 (42000): Every derived table must have its own alias

What it means: a table in FROM must have a name, even a temporary one. Fix: add AS author_counts (any name) after the closing parenthesis. On MariaDB the same mistake shows up as a plain syntax error 1064 near '', which is harder to read: if a query with a subquery in FROM fails with an empty near '', look for the missing alias first.

4. LIMIT inside an IN subquery

"Every book priced among the three highest prices" seems to call for a LIMIT in the list:

SELECT title, price
FROM books
WHERE price IN (
    SELECT DISTINCT price FROM books ORDER BY price DESC LIMIT 3
);

Error

ERROR 1235 (42000): This version of MySQL doesn't yet support 'LIMIT & IN/ALL/ANY/SOME subquery'

What it means: a long-standing MySQL (and MariaDB) limitation: LIMIT is not allowed in a subquery used with IN, ALL, ANY or SOME. Fix: wrap the limited query in a derived table, which is allowed, and select from that:

SELECT title, price
FROM books
WHERE price IN (
    SELECT price
    FROM (SELECT DISTINCT price FROM books ORDER BY price DESC LIMIT 3) AS top_prices
)
ORDER BY price DESC;

Output

+-----------------------+-------+
| title                 | price |
+-----------------------+-------+
| Lord of the Rings     | 15.99 |
| Dune                  | 14.99 |
| To Kill a Mockingbird | 11.99 |
+-----------------------+-------+

5. Forgetting the aliases in a correlated subquery (silent)

The goal: books priced above their own author's average, as in the correlated section, but written without aliases:

SELECT title, author, price
FROM books
WHERE price > (
    SELECT AVG(price)
    FROM books
    WHERE author = author
)
ORDER BY price;

Output

+-----------------------+----------------+-------+
| title                 | author         | price |
+-----------------------+----------------+-------+
| To Kill a Mockingbird | Harper Lee     | 11.99 |
| Dune                  | Frank Herbert  | 14.99 |
| Lord of the Rings     | J.R.R. Tolkien | 15.99 |
+-----------------------+----------------+-------+

What it means: no error, but three books instead of one. Inside the subquery, both authors refer to the inner table (the nearest one wins), so author = author is true for every row and the subquery returns the overall average. You got "above the store average" by accident. Fix: give both copies of the table an alias and use it on every column: WHERE b2.author = b.author.

🛠️ Project: The Price Review

Before the spring price update, the owner wants a review she can rerun after every change: what is above average, what each author's entry-level book is, which authors are fully in stock, and which books make up the top price tier. Every answer depends on another answer, which makes it a job for subqueries. You will collect the five queries in price_review.sql. Allow about 40 minutes.

🛠️ Step 1: Above the average (5 min)

Create price_review.sql in your mysql-course folder. The first query lists the books above the store average, with the average and the difference beside each one.

USE bookstore;

-- 1. Books above the store average
SELECT
    title,
    price,
    (SELECT ROUND(AVG(price), 2) FROM books)         AS store_avg,
    ROUND(price - (SELECT AVG(price) FROM books), 2) AS above_by
FROM books
WHERE price > (SELECT AVG(price) FROM books)
ORDER BY above_by DESC;

Output

Database changed
+-----------------------+-------+-----------+----------+
| title                 | price | store_avg | above_by |
+-----------------------+-------+-----------+----------+
| Lord of the Rings     | 15.99 |     10.99 |     5.00 |
| Dune                  | 14.99 |     10.99 |     4.00 |
| To Kill a Mockingbird | 11.99 |     10.99 |     1.00 |
+-----------------------+-------+-----------+----------+

🛠️ Step 2: Each author's entry-level book (10 min)

For the "try this author" shelf, find each author's cheapest book with a correlated subquery. Write the inner query first on its own for one author (WHERE author = 'J.R.R. Tolkien'), check it, then correlate it.

-- 2. Entry-level book per author
SELECT b.author, b.title, b.price
FROM books AS b
WHERE b.price = (
    SELECT MIN(b2.price)
    FROM books AS b2
    WHERE b2.author = b.author
)
ORDER BY b.price, b.author;

🛠️ Step 3: Authors fully in stock (10 min)

An author is "fully in stock" if no book of theirs is out of stock. "No such row" is NOT EXISTS.

-- 3. Authors with every book in stock
SELECT DISTINCT b.author
FROM books AS b
WHERE NOT EXISTS (
    SELECT 1
    FROM books AS missing
    WHERE missing.author = b.author
      AND missing.in_stock = FALSE
)
ORDER BY b.author;

Output

| author         |
+----------------+
| Aldous Huxley  |
| Frank Herbert  |
| George Orwell  |
| Harper Lee     |
| J.R.R. Tolkien |
| Jane Austen    |
| Ray Bradbury   |

Seven of the nine authors. Fitzgerald and Salinger are missing because their only book is out of stock.

🛠️ Step 4: The top price tier (5 min)

Every book priced at one of the three highest prices, using the derived-table workaround for the LIMIT restriction.

-- 4. Top price tier: the three highest prices
SELECT title, author, price
FROM books
WHERE price IN (
    SELECT price
    FROM (SELECT DISTINCT price FROM books ORDER BY price DESC LIMIT 3) AS top3
)
ORDER BY price DESC;

🛠️ Step 5: Stock value summary (5 min)

Finish with one row of headline numbers: the average price per author (a two-level summary), and the share of the shelf value that is out of stock.

-- 5. Headline numbers
SELECT
    (SELECT ROUND(AVG(author_avg), 2)
     FROM (SELECT AVG(price) AS author_avg FROM books GROUP BY author) AS per_author)
        AS avg_of_author_avgs,
    ROUND(
        (SELECT SUM(price) FROM books WHERE in_stock = FALSE)
        / (SELECT SUM(price) FROM books) * 100, 1)
        AS pct_value_out_of_stock;

Output

+--------------------+------------------------+
| avg_of_author_avgs | pct_value_out_of_stock |
+--------------------+------------------------+
|              10.71 |                   16.4 |
+--------------------+------------------------+

A SELECT with no FROM is allowed in MySQL: it returns one row built from the subqueries. The average of the author averages (10.71) is lower than the store average (10.99) because Tolkien's two pricey books count once, as one author, instead of twice. Neither number is wrong; they answer different questions.

🏋️ Exercise 2: Only Customer in Town

List the customers who are the only customer in their city.

💡 Hint

An IN subquery with GROUP BY city HAVING COUNT(*) = 1. Does the NULL group of two cause trouble here?

✅ Solution 
SELECT first_name, last_name, city
FROM customers
WHERE city IN (
    SELECT city
    FROM customers
    GROUP BY city
    HAVING COUNT(*) = 1
)
ORDER BY city;

Output

+------------+-----------+-------------+
| first_name | last_name | city        |
+------------+-----------+-------------+
| Dave       | Brown     | Houston     |
| Carol      | Williams  | Los Angeles |
+------------+-----------+-------------+

The NULL group has two members, so it fails HAVING COUNT(*) = 1 and never reaches the list. And even if it did, a NULL in a plain IN list matches nothing.

🏋️ Exercise 3: Customers per City, on Average

For the cities we know, how many customers does a city have on average? Count per city first, then average the counts.

💡 Hint

A derived table with GROUP BY city (leave the NULL cities out with WHERE), and an outer AVG. Remember the alias.

✅ Solution 
SELECT ROUND(AVG(customer_count), 1) AS avg_customers_per_city
FROM (
    SELECT city, COUNT(*) AS customer_count
    FROM customers
    WHERE city IS NOT NULL
    GROUP BY city
) AS city_counts;

| avg_customers_per_city |
+------------------------+
|                    1.5 |
+------------------------+

Six customers in four cities: 1.5.

🏋️ Exercise 4 (Stretch): Cheaper Than Their Author

Find the books priced below their author's most expensive book, and show that most expensive price beside each one. Then explain why only one author can appear in the result.

💡 Hint

Use the same correlated subquery twice: once in WHERE with MAX, once in the SELECT list to show the value.

✅ Solution 
SELECT
    b.title,
    b.author,
    b.price,
    (SELECT MAX(b2.price) FROM books AS b2 WHERE b2.author = b.author) AS author_max
FROM books AS b
WHERE b.price < (
    SELECT MAX(b2.price)
    FROM books AS b2
    WHERE b2.author = b.author
);

Output

+------------+----------------+-------+------------+
| title      | author         | price | author_max |
+------------+----------------+-------+------------+
| The Hobbit | J.R.R. Tolkien | 10.99 |      15.99 |
+------------+----------------+-------+------------+

An author with one book has a maximum equal to that book's price, and no price is below itself. Only Tolkien has two books, so only his cheaper one can qualify.

❓ Common Questions at This Stage

Should I use IN or EXISTS?

For a positive check, either is fine: MySQL's optimizer usually turns both into the same plan, so pick the one that reads more naturally. For the negative check, prefer NOT EXISTS: it has no NULL trap. If you do use NOT IN, add IS NOT NULL inside the subquery.

Can I use a subquery in UPDATE or DELETE?

Yes, with one MySQL restriction: the subquery cannot read the same table you are changing. "Delete every book cheaper than average" fails (shown inside a transaction, so nothing could change even on a server that allowed it):

START TRANSACTION;
DELETE FROM books WHERE price < (SELECT AVG(price) FROM books);
ROLLBACK;

Error

ERROR 1093 (HY000): You can't specify target table 'books' for update in FROM clause

The usual workaround is to compute the value first, for example into a variable: SET @avg = (SELECT AVG(price) FROM books); and then ... WHERE price < @avg. MariaDB lifts this restriction and runs the DELETE, which is one more reason to test destructive statements inside a transaction.

Is a subquery slower than a join?

Sometimes, not always. Modern MySQL rewrites many IN and EXISTS subqueries into joins internally (it calls them semijoins and antijoins). Write the clearest query first, and measure with EXPLAIN (Lesson 6.1) only if it is slow.

Why SELECT 1 inside EXISTS and not SELECT *?

Both work identically: EXISTS only checks whether a row comes back and never reads the columns. SELECT 1 is simply a signal to the reader that the values do not matter.

📝 Lesson Summary

🎓 Key Takeaways

  • A subquery is a SELECT in parentheses inside another statement; read nested queries from the inside out
  • Scalar subqueries return one value and work with =, >, arithmetic, and in the SELECT list
  • One-column lists go with IN, ANY and ALL; = (list) fails with error 1242
  • A single NULL in a NOT IN list empties the result: filter it with IS NOT NULL or use NOT EXISTS
  • Correlated subqueries refer to the outer row; alias both copies of the table and qualify every column
  • EXISTS asks "is there at least one related row?" and ignores the selected columns
  • Derived tables in FROM must have an alias (error 1248) and allow summaries of summaries
  • MySQL rejects LIMIT in an IN subquery (error 1235); wrap it in a derived table
