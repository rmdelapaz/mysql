🔒 Lesson 7.2: Transactions

Placing an order takes several statements: insert the order, insert its items, charge the customer. What if the third one fails, or the power goes out between the first and the second? A transaction turns several statements into one unit that either happens completely or not at all. This lesson shows how to use one, what other connections see while it runs, and how to make a procedure roll back on any error.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Group changes with START TRANSACTION, COMMIT and ROLLBACK, and explain autocommit and implicit commits
  • Undo part of a transaction with SAVEPOINT and ROLLBACK TO SAVEPOINT
  • Predict what a second connection sees and when it has to wait, under MySQL's default REPEATABLE READ isolation
  • Lock rows on purpose with SELECT ... FOR UPDATE, and read lock errors 1205 and 1213
  • Write a stored procedure whose error handler rolls back the whole transaction and passes the error on
  • ⏱️ Time 110 minutes
  • 📋 Prerequisites Lesson 7.1: Stored Procedures & Functions
  • 🛠️ You will build checkout.sql: a checkout procedure that places an order and charges store credit, all or nothing
  • 🗄️ Database bookstore, freshly loaded from bookstore.sql, plus an accounts table you create below

🧱 Why Transactions?

Many real changes are several statements that only make sense together. Move $30 of store credit from Alice to Bob: subtract from Alice, add to Bob. If the server stops after the first UPDATE, $30 has vanished. A transaction makes the pair atomic: the database keeps both changes or neither.

graph TD A["START TRANSACTION"] --> B["UPDATE: Alice minus 30"] B --> C["UPDATE: Bob plus 30"] C --> D{"Everything worked?"} D -->|"yes"| E["COMMIT: both kept"] D -->|"no"| F["ROLLBACK: neither kept"]

Database people summarize the guarantees as ACID:

PropertyMeaningIn the bookstore
AtomicityAll of the transaction's changes happen, or none doAn order never exists without its items
ConsistencyEvery committed state obeys the constraintsThe CHECK (balance >= 0) holds after every commit
IsolationTransactions running at the same time do not see each other's unfinished workA report never counts a half-placed order
DurabilityOnce committed, a change survives a crash or power cutAfter COMMIT, the order is on disk

💡 InnoDB does the work

Transactions are a feature of the storage engine. InnoDB, MySQL's default engine, supports them; the old MyISAM engine silently ignores them (Common Mistake 5). Every table in bookstore.sql is InnoDB, because no ENGINE= option means the default.

✅ START TRANSACTION, COMMIT, ROLLBACK

COMMIT: keep the changes

Here is the transfer, wrapped in a transaction. The Query OK lines are shown on purpose this time: they tell you each UPDATE changed one row.

START TRANSACTION;

UPDATE accounts SET balance = balance - 30 WHERE id = 1;
UPDATE accounts SET balance = balance + 30 WHERE id = 2;

SELECT * FROM accounts ORDER BY id;

COMMIT;

Output

Query OK, 0 rows affected
Query OK, 1 row affected
Rows matched: 1  Changed: 1  Warnings: 0
Query OK, 1 row affected
Rows matched: 1  Changed: 1  Warnings: 0
+----+----------------+---------+
| id | name           | balance |
+----+----------------+---------+
|  1 | Alice Johnson  |  120.00 |
|  2 | Bob Smith      |   80.00 |
|  3 | Carol Williams |    0.00 |
+----+----------------+---------+
3 rows in set
Query OK, 0 rows affected

Between START TRANSACTION and COMMIT, the changes are visible to your session (the SELECT shows 120.00 and 80.00) but not yet to anyone else. COMMIT makes them permanent and visible to everyone, and ends the transaction. After a COMMIT there is nothing left to roll back.

BEGIN and BEGIN WORK are synonyms for START TRANSACTION at the prompt. Inside a stored procedure, BEGIN opens a BEGIN ... END block instead, so this course always writes START TRANSACTION.

ROLLBACK: throw them away

Now the nightmare: someone deletes every order line. Inside a transaction, it is a rehearsal.

START TRANSACTION;

DELETE FROM order_items;
SELECT COUNT(*) AS items_inside FROM order_items;

ROLLBACK;
SELECT COUNT(*) AS items_after_rollback FROM order_items;

Output

+--------------+
| items_inside |
+--------------+
|            0 |
+--------------+
+----------------------+
| items_after_rollback |
+----------------------+
|                   18 |
+----------------------+

ROLLBACK undoes every change since START TRANSACTION and ends the transaction. All 18 order lines are back.

✅ A habit worth having

Before a risky UPDATE or DELETE by hand, type START TRANSACTION; first. Run the change, check the result with a SELECT, then decide: COMMIT or ROLLBACK. It costs one line and has saved many careers. Just do not walk away with the transaction open (see the two-session section for why).

⚙️ Autocommit and Implicit Commits

If transactions are so useful, why did every UPDATE in earlier lessons stick without a COMMIT? Because of autocommit: unless you start a transaction yourself, MySQL wraps each statement in its own tiny transaction and commits it at once.

SELECT @@autocommit;

Output

+--------------+
| @@autocommit |
+--------------+
|            1 |
+--------------+

1 means on, the default. START TRANSACTION suspends autocommit until the next COMMIT or ROLLBACK. You can also switch it off for your session, and then every statement waits for an explicit decision:

SET autocommit = 0;

UPDATE accounts SET balance = balance + 5 WHERE id = 3;
ROLLBACK;
SELECT id, balance FROM accounts WHERE id = 3;

SET autocommit = 1;

Output

+----+---------+
| id | balance |
+----+---------+
|  3 |    0.00 |
+----+---------+

Carol's balance is back to 0.00. Turning autocommit off for a whole session is rare and risky (forget one COMMIT and your work vanishes when you disconnect); prefer explicit START TRANSACTION ... COMMIT blocks.

Implicit commits

Some statements cannot be part of a transaction. Before they run, MySQL quietly commits whatever transaction is open:

  • Schema changes (DDL): CREATE, ALTER, DROP, RENAME and TRUNCATE TABLE, CREATE INDEX, creating or dropping a database, view or routine
  • Account statements: CREATE USER, GRANT, REVOKE, ALTER USER
  • A second START TRANSACTION while one is open, and LOCK TABLES

So ROLLBACK can only undo data changes made after the last implicit commit. Common Mistake 2 shows how that bites.

📍 Savepoints: Partial Rollback

A savepoint is a named bookmark inside a transaction. ROLLBACK TO SAVEPOINT name undoes everything after the bookmark and keeps everything before it, and the transaction stays open.

Carol phones in an order for The Hobbit. The clerk then adds five copies of Lord of the Rings, and Carol says "no, just the Hobbit". Note that price_at_time is required: the item is inserted with the book's current price.

START TRANSACTION;

INSERT INTO orders (customer_id, order_date) VALUES (3, '2026-06-20');
SET @carol_order = LAST_INSERT_ID();

INSERT INTO order_items (order_id, book_id, quantity, price_at_time)
SELECT @carol_order, id, 1, price FROM books WHERE id = 6;

SAVEPOINT hobbit_added;

INSERT INTO order_items (order_id, book_id, quantity, price_at_time)
SELECT @carol_order, id, 5, price FROM books WHERE id = 9;

ROLLBACK TO SAVEPOINT hobbit_added;

COMMIT;

SELECT o.id AS order_id, b.title, oi.quantity, oi.price_at_time
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.id
JOIN books AS b ON b.id = oi.book_id
WHERE o.id = @carol_order;

Output

+----------+------------+----------+---------------+
| order_id | title      | quantity | price_at_time |
+----------+------------+----------+---------------+
|       13 | The Hobbit |        1 |         10.99 |
+----------+------------+----------+---------------+

Order 13, Carol's first, holds only the Hobbit. The order row and the first item, made before the savepoint, survived; the Lord of the Rings line did not.

StatementEffect
SAVEPOINT nameSet a bookmark (same name again moves it)
ROLLBACK TO SAVEPOINT nameUndo the changes after the bookmark; the transaction continues

👥 Two Sessions: Isolation and Locks

So far you have been alone. Real databases serve many connections at once: the website, the warehouse app, a report. To see what they see of each other, open a second terminal and log in again (mysql -u root -p bookstore), or a second query tab in Workbench. On this page:

  • Session A is your first window, where you have worked all along.
  • Session B is the new window. Its blocks say "Session B" above them.

Run the blocks in exactly the order shown, switching windows as you go.

Uncommitted changes are invisible to others

Session A starts a transaction and takes $20 from Alice, without committing:

START TRANSACTION;
UPDATE accounts SET balance = balance - 20 WHERE id = 1;
SELECT id, balance FROM accounts WHERE id = 1;

Output (session A)

+----+---------+
| id | balance |
+----+---------+
|  1 |  100.00 |
+----+---------+

Session B looks at the same row:

SELECT id, balance FROM accounts WHERE id = 1;

Output (session B)

+----+---------+
| id | balance |
+----+---------+
|  1 |  120.00 |
+----+---------+

B still sees 120.00, the last committed value. It did not have to wait: InnoDB keeps the old version of the row around and hands it to readers (this is called a consistent read). No session ever sees another's uncommitted work, a problem known as a dirty read.

Writers wait for writers

Now session B tries to change the same row:

UPDATE accounts SET balance = balance + 1 WHERE id = 1;

Error (session B, after the wait)

ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction

Session A's UPDATE holds a row lock on Alice's account until A commits or rolls back. Session B's statement waits for it, and gives up after innodb_lock_wait_timeout seconds: 50 by default (this page's test server uses 5 to keep things quick). Only the waiting statement fails; nothing else is undone. If A commits within the timeout, B's UPDATE simply continues.

Session A commits:

COMMIT;

and session B reads again:

SELECT id, balance FROM accounts WHERE id = 1;

Output (session B)

+----+---------+
| id | balance |
+----+---------+
|  1 |  100.00 |
+----+---------+

Repeatable read: a transaction sees a snapshot

MySQL's default isolation level is REPEATABLE READ:

SELECT @@transaction_isolation;

Output

+-------------------------+
| @@transaction_isolation |
+-------------------------+
| REPEATABLE-READ         |
+-------------------------+

It means that inside one transaction, reading the same row twice gives the same answer, even if someone else commits a change in between. Session B starts a transaction and reads Bob's balance:

START TRANSACTION;
SELECT id, balance FROM accounts WHERE id = 2;

Output (session B)

+----+---------+
| id | balance |
+----+---------+
|  2 |   80.00 |
+----+---------+

Session A gives Bob $10 (autocommit, so it is committed at once):

UPDATE accounts SET balance = balance + 10 WHERE id = 2;
SELECT id, balance FROM accounts WHERE id = 2;

Output (session A)

+----+---------+
| id | balance |
+----+---------+
|  2 |   90.00 |
+----+---------+

Session B reads again inside its transaction, then after ending it:

SELECT id, balance AS still_in_transaction FROM accounts WHERE id = 2;
COMMIT;
SELECT id, balance AS after_commit FROM accounts WHERE id = 2;

Output (session B)

+----+----------------------+
| id | still_in_transaction |
+----+----------------------+
|  2 |                80.00 |
+----+----------------------+
+----+--------------+
| id | after_commit |
+----+--------------+
|  2 |        90.00 |
+----+--------------+

Inside its transaction, B keeps seeing the snapshot taken at its first read (80.00). Once it ends the transaction, the next read sees the newest committed value (90.00). A long report run inside one transaction therefore adds up consistently, even while orders keep arriving.

Isolation levelA plain SELECT seesTypical use
READ UNCOMMITTEDEven other sessions' uncommitted changes (dirty reads)Almost never
READ COMMITTEDThe latest committed data, fresh for each statementThe default in PostgreSQL and SQL Server
REPEATABLE READOne snapshot for the whole transactionMySQL and MariaDB default
SERIALIZABLELike repeatable read, but plain reads also take shared locksStrictest, most waiting

You can change the level for your next transaction with SET TRANSACTION ISOLATION LEVEL READ COMMITTED;, but the default is a good choice for almost everything in this course.

🔐 Locking Rows with FOR UPDATE

Snapshots have a catch. Suppose two cashiers both read Alice's balance (100.00), both decide "enough for a $60 purchase", and both subtract 60. Each read was correct, yet together they overspend. The fix is to lock the row when you read it if you intend to change it: SELECT ... FOR UPDATE.

Session A reads Alice's balance with a lock:

START TRANSACTION;
SELECT id, balance FROM accounts WHERE id = 1 FOR UPDATE;

Output (session A)

+----+---------+
| id | balance |
+----+---------+
|  1 |  100.00 |
+----+---------+

Session B, the second cashier, tries the same locking read and has to wait:

SELECT id, balance FROM accounts WHERE id = 1 FOR UPDATE;

Error (session B, after the wait)

ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction

A plain SELECT in session B is not blocked; it reads the committed snapshot as before:

SELECT id, balance FROM accounts WHERE id = 1;

Output (session B)

+----+---------+
| id | balance |
+----+---------+
|  1 |  100.00 |
+----+---------+

Session A finishes its purchase and commits, which releases the lock:

UPDATE accounts SET balance = balance - 60 WHERE id = 1;
COMMIT;
SELECT id, balance FROM accounts WHERE id = 1;

Output (session A)

+----+---------+
| id | balance |
+----+---------+
|  1 |   40.00 |
+----+---------+

Had B waited instead of timing out, its locking read would have returned 40.00, the balance after A's purchase, and B's cashier would have seen there was not enough left. That is the whole point: read-then-write logic needs FOR UPDATE. (FOR SHARE takes a weaker lock that lets others read with FOR SHARE too but blocks writers.)

Deadlocks

If session A locks row 1 and then wants row 2, while session B has locked row 2 and wants row 1, neither can ever continue. InnoDB notices such a deadlock immediately, picks one transaction as the victim, rolls it back completely, and gives it this error:

Error (the victim session)

ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction

The message is the advice: an app catches error 1213 and runs the whole transaction again. You make deadlocks rare by keeping transactions short and by touching rows in the same order everywhere (for example, always lock the lower account id first in a transfer).

graph TD A["Session A locks row 1"] --> B["A waits for row 2"] C["Session B locks row 2"] --> D["B waits for row 1"] B --> E["InnoDB detects the cycle"] D --> E E --> F["One session rolled back: 1213"]

🧰 Transactions in Stored Procedures

At the prompt, you decide whether to commit. In a procedure, the code has to decide, and it has to roll back when any statement fails. That is the job of an error handler:

DROP PROCEDURE IF EXISTS transfer;
DELIMITER //
CREATE PROCEDURE transfer(IN p_from INT, IN p_to INT, IN p_amount DECIMAL(10, 2))
BEGIN
    DECLARE v_balance DECIMAL(10, 2);

    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;   -- undo everything this call did
        RESIGNAL;   -- and pass the original error to the caller
    END;

    IF p_amount IS NULL OR p_amount <= 0 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Amount must be positive';
    END IF;

    START TRANSACTION;

    SELECT balance INTO v_balance FROM accounts WHERE id = p_from FOR UPDATE;
    IF v_balance IS NULL THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'No such source account';
    END IF;
    IF v_balance < p_amount THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Insufficient funds';
    END IF;

    UPDATE accounts SET balance = balance - p_amount WHERE id = p_from;
    UPDATE accounts SET balance = balance + p_amount WHERE id = p_to;
    IF ROW_COUNT() = 0 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'No such destination account';
    END IF;

    COMMIT;
END //
DELIMITER ;

How it fits together:

  • DECLARE EXIT HANDLER FOR SQLEXCEPTION says: if any statement in this procedure raises an error (including our own SIGNALs), run this block, then leave the procedure. Handlers are declared after variables and before other statements.
  • ROLLBACK in the handler undoes the half-done transfer.
  • RESIGNAL re-raises the same error, so the caller still learns what went wrong. A handler that only rolls back and sets a "failed" message hides the real error from the app.
  • FOR UPDATE locks the source account between the check and the debit, the race from the previous section.

A good transfer: Alice sends Carol $5.

CALL transfer(1, 3, 5.00);
SELECT * FROM accounts ORDER BY id;

Output

+----+----------------+---------+
| id | name           | balance |
+----+----------------+---------+
|  1 | Alice Johnson  |   35.00 |
|  2 | Bob Smith      |   90.00 |
|  3 | Carol Williams |    5.00 |
+----+----------------+---------+

Carol tries to send $500 she does not have:

CALL transfer(3, 2, 500.00);

Error

ERROR 1644 (45000): Insufficient funds

The hardest case: the debit succeeds, then the credit finds no account 99. Without the handler, Alice would lose $5 into thin air.

CALL transfer(1, 99, 5.00);

Error

ERROR 1644 (45000): No such destination account
SELECT * FROM accounts ORDER BY id;

Output

+----+----------------+---------+
| id | name           | balance |
+----+----------------+---------+
|  1 | Alice Johnson  |   35.00 |
|  2 | Bob Smith      |   90.00 |
|  3 | Carol Williams |    5.00 |
+----+----------------+---------+

Alice still has 35.00: the handler rolled the debit back before passing the error on.

⚠️ Let the procedure own the transaction

START TRANSACTION inside a procedure first commits any transaction the caller had open (an implicit commit). Decide who controls the transaction, the procedure or the app, and do not do both. The usual choice for a self-contained action like transfer is the procedure.

⚠️ Common Mistakes

1. Committing after an error (silent)

A transfer from Carol (5.00) to Bob, typed by hand. The second UPDATE would make Carol's balance negative:

START TRANSACTION;
UPDATE accounts SET balance = balance + 40 WHERE id = 2;
UPDATE accounts SET balance = balance - 40 WHERE id = 3;
COMMIT;

Error

ERROR 3819 (HY000): Check constraint 'chk_balance' is violated.
SELECT * FROM accounts ORDER BY id;

Output

+----+----------------+---------+
| id | name           | balance |
+----+----------------+---------+
|  1 | Alice Johnson  |   35.00 |
|  2 | Bob Smith      |  130.00 |
|  3 | Carol Williams |    5.00 |
+----+----------------+---------+

What it means: in MySQL, a failed statement undoes only itself; the transaction stays open with the earlier changes in it. The COMMIT then saved Bob's +40 without Carol's -40: $40 created from nothing. (PostgreSQL behaves differently and refuses to commit after an error, which surprises people moving between the two.) Fix: after an error inside a transaction, ROLLBACK; in code, use a handler like transfer's. Now repair Bob's balance:

UPDATE accounts SET balance = balance - 40 WHERE id = 2;

🐬 Version note

MySQL 8.4 and MariaDB behave the same way here: the failed statement is undone, the transaction stays open. MariaDB reports the CHECK violation with a different number and text, ERROR 4025 (23000): CONSTRAINT `chk_balance` failed for `bookstore`.`accounts`, so an app that tests for error 3819 should test for 4025 too if it may run on MariaDB.

2. A schema change in the middle of a transaction (silent)

START TRANSACTION;
UPDATE accounts SET balance = 0 WHERE id = 2;
CREATE TABLE demo_audit (note VARCHAR(100));
ROLLBACK;
SELECT id, balance FROM accounts WHERE id = 2;

Output

+----+---------+
| id | balance |
+----+---------+
|  2 |    0.00 |
+----+---------+

What it means: CREATE TABLE committed the open transaction before it ran, so the ROLLBACK had nothing left to undo, and Bob's balance is really 0. Fix: keep CREATE, ALTER, DROP and TRUNCATE out of transactions; run them before or after. Repair the damage and remove the demo table:

UPDATE accounts SET balance = 90.00 WHERE id = 2;
DROP TABLE demo_audit;

3. Rolling back to a savepoint that does not exist

START TRANSACTION;
UPDATE books SET price = ROUND(price * 0.9, 2);
ROLLBACK TO SAVEPOINT before_sale;

Error

ERROR 1305 (42000): SAVEPOINT before_sale does not exist

What it means: no SAVEPOINT before_sale was set in this transaction (a typo, or it was set in an earlier transaction that has ended). The transaction is still open, with every price cut by 10%. Fix: set the savepoint before the change; here, roll the whole thing back:

ROLLBACK;
SELECT title, price FROM books WHERE id = 1;

Output

+-------+-------+
| title | price |
+-------+-------+
| Dune  | 14.99 |
+-------+-------+

4. Writing in a read-only transaction

START TRANSACTION READ ONLY;
UPDATE accounts SET balance = balance + 1 WHERE id = 3;

Error

ERROR 1792 (25006): Cannot execute statement in a READ ONLY transaction.
ROLLBACK;

What it means: READ ONLY is a promise that lets InnoDB skip some bookkeeping, and MySQL enforces it. It is a good fit for long reports. Fix: use a plain START TRANSACTION (or READ WRITE) when you need to change data.

5. A table that ignores ROLLBACK (silent)

CREATE TABLE demo_log (note VARCHAR(100)) ENGINE = MyISAM;

START TRANSACTION;
INSERT INTO demo_log VALUES ('this should disappear');
ROLLBACK;
SHOW WARNINGS;
SELECT COUNT(*) AS rows_left FROM demo_log;

DROP TABLE demo_log;

Output

+---------+------+---------------------------------------------------------------+
| Level   | Code | Message                                                       |
+---------+------+---------------------------------------------------------------+
| Warning | 1196 | Some non-transactional changed tables couldn't be rolled back |
+---------+------+---------------------------------------------------------------+
+-----------+
| rows_left |
+-----------+
|         1 |
+-----------+

What it means: MyISAM has no transactions, so the insert was permanent the moment it ran. MySQL only warns (1196), and the client shows warnings only when you ask with SHOW WARNINGS. You meet MyISAM in old databases and old tutorials. Fix: use InnoDB, the default (leave out ENGINE=, or convert with ALTER TABLE t ENGINE = InnoDB;). Check a table's engine with SHOW TABLE STATUS LIKE 'accounts';.

🛠️ Project: An All-or-Nothing Checkout

The website's checkout must create an order, add the line item at the current price, and charge the customer's store credit. If any step fails (an unknown book, a book out of stock, not enough credit), nothing may remain: no empty order, no charge. You will write checkout.sql and then try hard to break it. Allow about 40 minutes.

🛠️ Step 1: Write the procedure (12 min)

Create checkout.sql in your mysql-course folder. The procedure validates before it writes anything, then does all three writes inside one transaction guarded by a handler.

USE bookstore;

DROP PROCEDURE IF EXISTS checkout;
DELIMITER //
CREATE PROCEDURE checkout(
    IN  p_customer_id INT,
    IN  p_book_id     INT,
    IN  p_quantity    INT,
    OUT p_order_id    INT
)
BEGIN
    DECLARE v_price    DECIMAL(8, 2);
    DECLARE v_in_stock BOOLEAN;

    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        RESIGNAL;
    END;

    IF p_quantity IS NULL OR p_quantity < 1 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Quantity must be at least 1';
    END IF;

    SELECT MIN(price), MIN(in_stock) INTO v_price, v_in_stock
    FROM books WHERE id = p_book_id;

    IF v_price IS NULL THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'No such book';
    END IF;
    IF NOT v_in_stock THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Book is out of stock';
    END IF;

    START TRANSACTION;

    INSERT INTO orders (customer_id, order_date) VALUES (p_customer_id, CURRENT_DATE);
    SET p_order_id = LAST_INSERT_ID();

    INSERT INTO order_items (order_id, book_id, quantity, price_at_time)
    VALUES (p_order_id, p_book_id, p_quantity, v_price);

    UPDATE accounts SET balance = balance - v_price * p_quantity
    WHERE id = p_customer_id;
    IF ROW_COUNT() = 0 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Customer has no store credit account';
    END IF;

    COMMIT;
END //
DELIMITER ;

Output

Database changed

Two details worth noticing. The CHECK (balance >= 0) constraint does the "enough credit?" test for you: a charge that would go negative fails with error 3819, the handler catches it and rolls back. And the MIN()s make the lookup return one row even for a missing book, as in Lesson 7.1's add_book.

🏋️ Exercise 3: Who Waits?

This time session B holds the lock. In session B, start a transaction and lock Bob's account with FOR UPDATE. In session A, try to add $1 to Bob's balance and watch it wait. Then commit in session B.

💡 Hint

Any UPDATE of a row locked by another transaction waits, whether the lock came from an UPDATE or a FOR UPDATE read.

✅ Solution

Session B:

START TRANSACTION;
SELECT id, balance FROM accounts WHERE id = 2 FOR UPDATE;

Output (session B)

+----+---------+
| id | balance |
+----+---------+
|  2 |   90.00 |
+----+---------+

Session A waits, then gives up:

UPDATE accounts SET balance = balance + 1 WHERE id = 2;

Error (session A, after the wait)

ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction

Session B releases the lock:

COMMIT;

If you commit in B quickly enough (within 50 seconds on a default server), A's UPDATE completes instead of failing.

🏋️ Exercise 4 (Stretch): A Safe Delete Procedure

Write cancel_order(IN p_order_id INT): inside a transaction it deletes the order (its items go with it by cascade), raises "No such order" with SIGNAL if nothing was deleted, and has a handler that rolls back and resignals. Test it on order 999, then cancel order 3.

💡 Hint

Check ROW_COUNT() right after the DELETE; the handler turns your SIGNAL into a rollback too.

✅ Solution 
DROP PROCEDURE IF EXISTS cancel_order;
DELIMITER //
CREATE PROCEDURE cancel_order(IN p_order_id INT)
BEGIN
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        RESIGNAL;
    END;

    START TRANSACTION;
    DELETE FROM orders WHERE id = p_order_id;
    IF ROW_COUNT() = 0 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'No such order';
    END IF;
    COMMIT;
END //
DELIMITER ;
CALL cancel_order(999);

Error

ERROR 1644 (45000): No such order
CALL cancel_order(3);
SELECT COUNT(*) AS orders_left,
       (SELECT COUNT(*) FROM order_items WHERE order_id = 3) AS items_of_order_3
FROM orders;

Output

+-------------+------------------+
| orders_left | items_of_order_3 |
+-------------+------------------+
|          14 |                0 |
+-------------+------------------+

❓ Common Questions at This Stage

What happens to an open transaction if my connection drops?

The server rolls it back. Nothing is committed unless you said COMMIT (or autocommit did it for you). That is also why closing a window with an open transaction loses its work, and why an open transaction left in a forgotten window can block other sessions until it is closed.

How do apps use transactions?

Through the driver: PHP's PDO has beginTransaction(), commit() and rollBack(); Python's connector has conn.commit() and conn.rollback(). The pattern is the same as the handler: start, run the parameterized statements, commit, and roll back in the error branch. Note that some drivers (Python's DB-API ones, for example) switch autocommit off by default, so forgetting commit() loses the change.

Are transactions slow?

Usually the opposite for bulk work. With autocommit, each INSERT waits for its own commit to reach the disk; 1,000 inserts inside one transaction wait once. What hurts is a long transaction: it holds locks and keeps old row versions alive. Keep transactions as short as the job allows, and never wait for a person (a form, a confirmation dialog) in the middle of one.

Why did my AUTO_INCREMENT skip numbers?

Rolled-back inserts, failed inserts and deleted rows all leave gaps, as the project showed. InnoDB hands out ids without waiting for commits, so it cannot take them back. Ids identify rows; they are not a count. Use COUNT(*) to count.

📝 Lesson Summary

🎓 Key Takeaways

  • A transaction makes several changes all-or-nothing: START TRANSACTION, then COMMIT or ROLLBACK
  • Autocommit (on by default) commits each statement by itself; DDL and account statements cause implicit commits
  • A failed statement undoes only itself: after an error, roll back yourself, or let a handler do it
  • Savepoints undo part of a transaction and keep it open
  • Under REPEATABLE READ, plain reads see committed data from a snapshot and never wait; writers wait for row locks (1205 on timeout)
  • SELECT ... FOR UPDATE locks rows you are about to change; deadlocks (1213) roll back one victim, so retry the whole transaction
  • In procedures: DECLARE EXIT HANDLER FOR SQLEXCEPTION BEGIN ROLLBACK; RESIGNAL; END;
