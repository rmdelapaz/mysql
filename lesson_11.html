🔗 Lesson 4.1: Table Relationships

Your bookstore has lived in three separate tables so far, and the books table types every author's name by hand. That works for ten books, but it breaks as soon as a name is spelled two ways or a customer starts placing orders. This lesson answers the question every database designer asks first: which facts belong in which table, and how do the tables point at each other? Then you will rebuild the bookstore the relational way.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Explain the update, insert and delete problems of a flat table, using the bookstore's own data
  • Tell one-to-many, one-to-one and many-to-many relationships apart, and say where the foreign key goes in each
  • Move a repeated text column into its own table with CREATE TABLE, ALTER TABLE and UPDATE ... JOIN
  • Build a junction table with a composite primary key, with and without extra columns
  • Read a crow's foot ER diagram of the finished bookstore database

  • 📋 Prerequisites Lesson 3.4: Subqueries & Nested Queries

  • 🗄️ Database bookstore as loaded in Lesson 3.1 (10 books with a text author column, 8 customers, 5 categories); it ends as bookstore.sql

🧩 Why Split Data into Tables?

Picture the bookstore keeping its sales in one giant spreadsheet-style table, one row per book sold:

salecustomer_namecustomer_emailcustomer_citybook_titlebook_pricesale_date
1Alice Johnsonalice@example.comNew YorkDune14.992026-01-15
2Alice Johnsonalice@example.comNew York19849.992026-01-15
3Bob Smithbob@example.comChicagoDune14.992026-03-10

It looks tidy, but it has four classic problems, called anomalies:

  • Duplication: Alice's name, email and city are stored once per book she buys. Fifty purchases, fifty copies.
  • Update anomaly: when Alice changes her email, every one of her rows must change. Miss one and the table disagrees with itself.
  • Delete anomaly: delete Bob's only sale and Bob himself disappears from the database.
  • Insert anomaly: a new customer who has not bought anything yet has nowhere to go, unless you fill the book columns with NULL.

The bookstore already has this problem

Your books table stores each author as text. Start the lesson in the mysql client, in the bookstore database you have used since Lesson 3.1:

USE bookstore;

SELECT id, title, author
FROM books
WHERE author = 'J.R.R. Tolkien';

Output

Database changed
+----+-------------------+----------------+
| id | title             | author         |
+----+-------------------+----------------+
|  6 | The Hobbit        | J.R.R. Tolkien |
|  9 | Lord of the Rings | J.R.R. Tolkien |
+----+-------------------+----------------+

The same 14 characters are typed twice. Now imagine a staff member adds spaces to the initials on one of the two rows:

UPDATE books SET author = 'J. R. R. Tolkien' WHERE id = 9;

SELECT author, COUNT(*) AS books
FROM books
WHERE author LIKE '%Tolkien%'
GROUP BY author
ORDER BY author;

Output

+------------------+-------+
| author           | books |
+------------------+-------+
| J. R. R. Tolkien |     1 |
| J.R.R. Tolkien   |     1 |
+------------------+-------+

No error, yet the database now believes in two different Tolkiens, and the "books per author" report from Lesson 3.3 is quietly wrong. That is an update anomaly in action. Put the name back before you go on:

UPDATE books SET author = 'J.R.R. Tolkien' WHERE id = 9;

🔑 The relational idea

Store each fact once, in the table it describes, and let other tables point at it by its id. An author's name belongs in an authors table; a book only needs to say "my author is number 6". Change the name in one place and every book sees the new spelling.

🔑 Primary Keys and Foreign Keys

Two kinds of key make relationships work. You have used the first one since Lesson 2.1.

  • A primary key (PK) identifies each row of a table: unique, never NULL. In the bookstore every table has an id INT AUTO_INCREMENT PRIMARY KEY.
  • A foreign key (FK) is a column in one table that holds a primary key value from another table. orders.customer_id = 1 means "this order belongs to customer 1".
graph TD C["customers: id 1, Alice"] -->|"referenced by"| O1["orders: id 1, customer_id 1"] C -->|"referenced by"| O2["orders: id 2, customer_id 1"]

The table that holds the primary key is the parent (customers); the table that holds the foreign key is the child (orders). Foreign key columns are usually named after the parent in the singular: customer_id, book_id, author_id.

💡 Declaring the key

A column called customer_id is only a naming habit until you declare it with FOREIGN KEY (customer_id) REFERENCES customers(id). Then MySQL checks every value: an order for a customer who does not exist is refused. In this lesson you will declare foreign keys as you build tables; Lesson 4.2 is all about the rules they enforce.

👩‍👧‍👦 One-to-Many: Authors and Books

In a one-to-many (1:M) relationship, one parent row can have many child rows, but each child has exactly one parent. It is by far the most common relationship: one author writes many books, one customer places many orders, one order holds many items.

🔑 Where does the foreign key go?

Ask "can one A have many Bs?" If yes, the foreign key goes in B's table, the "many" side. Can one author have many books? Yes, so books gets author_id. Can one book have many authors? Not in this store, so authors gets no book_id.

Now turn the text column into a real relationship, in four steps. Run each block and look at the result before you move on.

Step 1: Create the parent table and fill it

CREATE TABLE authors (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    name        VARCHAR(100) NOT NULL,
    birth_year  INT
);

INSERT INTO authors (id, name, birth_year) VALUES
    (1, 'Frank Herbert', 1920),
    (2, 'George Orwell', 1903),
    (3, 'Harper Lee', 1926),
    (4, 'F. Scott Fitzgerald', 1896),
    (5, 'Jane Austen', 1775),
    (6, 'J.R.R. Tolkien', 1892),
    (7, 'Aldous Huxley', 1894),
    (8, 'J.D. Salinger', 1919),
    (9, 'Ray Bradbury', 1920),
    (10, 'Isaac Asimov', 1920);

SELECT * FROM authors ORDER BY id;

The first nine authors are numbered in the order their first book appears in books. The tenth, Isaac Asimov, has no books in the store yet. That is allowed on the "one" side of a relationship (an author with zero books), and he will be useful in Lesson 4.3 when you look for rows with no match.

Step 2: Add the foreign key column to the child

ALTER TABLE books ADD COLUMN author_id INT AFTER title;

SELECT id, title, author, author_id
FROM books
WHERE id <= 3;

Output

+----+-----------------------+---------------+-----------+
| id | title                 | author        | author_id |
+----+-----------------------+---------------+-----------+
|  1 | Dune                  | Frank Herbert |      NULL |
|  2 | 1984                  | George Orwell |      NULL |
|  3 | To Kill a Mockingbird | Harper Lee    |      NULL |
+----+-----------------------+---------------+-----------+

The new column exists but is empty (NULL) on every row. AFTER title only decides where it appears in SELECT * and DESCRIBE.

Step 3: Fill author_id by matching names

Every book's author text equals exactly one authors.name. An UPDATE that joins the two tables can copy the matching id into each book in one statement:

UPDATE books
JOIN authors ON authors.name = books.author
SET books.author_id = authors.id;

SELECT id, title, author, author_id
FROM books
ORDER BY id;

Output

+----+------------------------+---------------------+-----------+
| id | title                  | author              | author_id |
+----+------------------------+---------------------+-----------+
|  1 | Dune                   | Frank Herbert       |         1 |
|  2 | 1984                   | George Orwell       |         2 |
|  3 | To Kill a Mockingbird  | Harper Lee          |         3 |
|  4 | The Great Gatsby       | F. Scott Fitzgerald |         4 |
|  5 | Pride and Prejudice    | Jane Austen         |         5 |
|  6 | The Hobbit             | J.R.R. Tolkien      |         6 |
|  7 | Brave New World        | Aldous Huxley       |         7 |
|  8 | The Catcher in the Rye | J.D. Salinger       |         8 |
|  9 | Lord of the Rings      | J.R.R. Tolkien      |         6 |
| 10 | Fahrenheit 451         | Ray Bradbury        |         9 |

Read the UPDATE as "for every pair of a book and an author whose name equals the book's author text, set the book's author_id to that author's id". JOIN ... ON pairs rows from two tables; it is the subject of Lesson 4.3, and here you only need this one pattern. Both Tolkien books now carry 6.

Before you delete the old text column, prove that nothing was missed. If a name had been misspelled, its book would still have a NULL:

SELECT COUNT(*) AS books_without_author_id
FROM books
WHERE author_id IS NULL;

Output

+-------------------------+
| books_without_author_id |
+-------------------------+
|                       0 |
+-------------------------+

Step 4: Lock it in

Three changes in one ALTER TABLE: every book must now have an author (NOT NULL), the redundant text column goes, and the foreign key is declared and named fk_books_author.

ALTER TABLE books
    MODIFY COLUMN author_id INT NOT NULL,
    DROP COLUMN author,
    ADD CONSTRAINT fk_books_author
        FOREIGN KEY (author_id) REFERENCES authors(id)
        ON DELETE RESTRICT
        ON UPDATE CASCADE;

DESCRIBE books;

Output

+-----------+--------------+------+-----+---------+----------------+
| Field     | Type         | Null | Key | Default | Extra          |
+-----------+--------------+------+-----+---------+----------------+
| id        | int          | NO   | PRI | NULL    | auto_increment |
| title     | varchar(200) | NO   |     | NULL    |                |
| author_id | int          | NO   | MUL | NULL    |                |
| price     | decimal(8,2) | NO   |     | NULL    |                |
| pages     | int          | YES  |     | NULL    |                |
| published | date         | YES  |     | NULL    |                |
| in_stock  | tinyint(1)   | YES  |     | 1       |                |
+-----------+--------------+------+-----+---------+----------------+

author_id now shows MUL in the Key column: MySQL created an index on it to check the foreign key quickly. The ON DELETE RESTRICT and ON UPDATE CASCADE rules say what happens when an author is deleted or renumbered; Lesson 4.2 explains each choice.

🛑 Drop a column only after you have checked the copy

DROP COLUMN cannot be undone. That is why Step 3 ends with the IS NULL count: on a real system you would also back up the table first (Lesson 8.1 shows how).

Using the relationship

A book's author is now one lookup away. With a correlated subquery from Lesson 3.4:

SELECT
    title,
    (SELECT name FROM authors WHERE authors.id = books.author_id) AS author
FROM books
WHERE author_id IN (2, 6)
ORDER BY title;

Output

+-------------------+----------------+
| title             | author         |
+-------------------+----------------+
| 1984              | George Orwell  |
| Lord of the Rings | J.R.R. Tolkien |
| The Hobbit        | J.R.R. Tolkien |
+-------------------+----------------+

And a new book is added the relational way, by id. The store just got Animal Farm, Orwell's second title:

INSERT INTO books (id, title, author_id, price, pages, published, in_stock) VALUES
    (11, 'Animal Farm', 2, 8.49, 112, '1945-08-17', TRUE);

SELECT author_id, COUNT(*) AS books
FROM books
GROUP BY author_id
HAVING COUNT(*) > 1
ORDER BY author_id;

Output

+-----------+-------+
| author_id | books |
+-----------+-------+
|         2 |     2 |
|         6 |     2 |
+-----------+-------+

Orwell (2) and Tolkien (6) each have two books, and the spelling of their names can never split them again: the name lives in exactly one row of authors.

🪪 One-to-One: Optional Extra Details

In a one-to-one (1:1) relationship each parent row has at most one child row. It is rarer, and usually a design choice rather than a necessity:

  • Optional data: only some customers fill in a profile (a bio, a favorite genre).
  • Security: employees' bank details in a table only payroll may read (Lesson 7.4 grants access per table).
  • Wide or rarely read columns: a long description kept out of the table every query scans.

Technically it is a one-to-many relationship with one extra rule: the foreign key column is UNIQUE, so no parent can be referenced twice. Try it with a small profile table:

CREATE TABLE customer_profiles (
    id             INT AUTO_INCREMENT PRIMARY KEY,
    customer_id    INT NOT NULL UNIQUE,
    favorite_genre VARCHAR(50),
    bio            VARCHAR(255),
    CONSTRAINT fk_profiles_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
);

INSERT INTO customer_profiles (customer_id, favorite_genre, bio)
VALUES (1, 'Science Fiction', 'Reads on the subway.');

SELECT * FROM customer_profiles;

Output

+----+-------------+-----------------+----------------------+
| id | customer_id | favorite_genre  | bio                  |
+----+-------------+-----------------+----------------------+
|  1 |           1 | Science Fiction | Reads on the subway. |
+----+-------------+-----------------+----------------------+

Alice has a profile. A second one for her is refused, which is exactly the "one" in one-to-one:

INSERT INTO customer_profiles (customer_id, favorite_genre)
VALUES (1, 'Fantasy');

Error

ERROR 1062 (23000): Duplicate entry '1' for key 'customer_profiles.customer_id'

Without UNIQUE, that insert would succeed and the relationship would silently become one-to-many. The bookstore does not need profiles, so remove the demo table to keep your database identical to bookstore.sql:

DROP TABLE customer_profiles;

💡 Another common 1:1 layout

You can also make customer_id itself the primary key of the profile table (customer_id INT PRIMARY KEY plus the foreign key). A primary key is already unique, so the extra id column disappears. Both layouts are correct.

🕸️ Many-to-Many: Books and Categories

In a many-to-many (M:M) relationship both sides can have many partners. 1984 is Fiction, Classic and Dystopian; the Fiction category holds every book. One foreign key column cannot express that: books.category_id holds one category, and a comma-separated list in one column is a trap (Common Mistakes, number 4).

The answer is a third table, a junction table (also called a bridge, link or join table). Each row is one link, "book X is in category Y", and holds two foreign keys:

graph TD B["books"] -->|"one book, many links"| BC["book_categories"] C["categories"] -->|"one category, many links"| BC

So a many-to-many relationship is really two one-to-many relationships that meet in the middle. Create the junction table:

CREATE TABLE book_categories (
    book_id     INT NOT NULL,
    category_id INT NOT NULL,
    PRIMARY KEY (book_id, category_id),
    CONSTRAINT fk_bc_book
        FOREIGN KEY (book_id) REFERENCES books(id)
        ON DELETE CASCADE,
    CONSTRAINT fk_bc_category
        FOREIGN KEY (category_id) REFERENCES categories(id)
        ON DELETE CASCADE
);

PRIMARY KEY (book_id, category_id) is a composite primary key: the pair must be unique. Book 2 may appear many times and category 1 may appear many times, but the link "book 2 is in category 1" can be stored only once. Now add the 25 links (every book is Fiction plus one or two more; the category ids are 1 Fiction, 2 Science Fiction, 3 Classic, 4 Fantasy, 5 Dystopian):

INSERT INTO book_categories (book_id, category_id) VALUES
    (1, 1), (1, 2),
    (2, 1), (2, 3), (2, 5),
    (3, 1), (3, 3),
    (4, 1), (4, 3),
    (5, 1), (5, 3),
    (6, 1), (6, 4),
    (7, 1), (7, 2), (7, 5),
    (8, 1), (8, 3),
    (9, 1), (9, 4),
    (10, 1), (10, 2), (10, 5),
    (11, 1), (11, 3);

SELECT COUNT(*) AS links FROM book_categories;

Output

+-------+

+-------+

Which categories is 1984 (book 2) in? Follow the links with a subquery:

SELECT name
FROM categories
WHERE id IN (SELECT category_id FROM book_categories WHERE book_id = 2)
ORDER BY name;

Output

+-----------+
| name      |
+-----------+
| Classic   |
| Dystopian |
| Fiction   |
+-----------+

And from the other side, how many books does each category hold?

SELECT
    name,
    (SELECT COUNT(*)
     FROM book_categories AS bc
     WHERE bc.category_id = categories.id) AS books
FROM categories
ORDER BY books DESC, name;

Output

+-----------------+-------+
| name            | books |
+-----------------+-------+
| Fiction         |    11 |
| Classic         |     6 |
| Dystopian       |     3 |
| Science Fiction |     3 |
| Fantasy         |     2 |
+-----------------+-------+

Junction tables with extra data

Sometimes the link itself has facts. When Alice orders two copies of 1984, the "2" belongs neither to the order nor to the book: it describes this book in this order. Orders and books are many-to-many (an order holds many books, a book appears in many orders), and the junction table order_items carries the extra columns quantity and price_at_time. You will build it in the project.

✅ Why store the price twice?

books.price is today's price; order_items.price_at_time is what the customer paid. When the store raises the price of Dune next year, last January's receipts must not change. Copying a value on purpose because it describes a different moment is not duplication; it is history.

🗺️ Reading ER Diagrams

An entity-relationship (ER) diagram is the map of a database: one box per table, one line per relationship. The most common style, crow's foot notation, draws the "how many" at each end of a line:

End of the lineMeans
||exactly one
o|zero or one
|{ (crow's foot with a bar)one or many
o{ (crow's foot with a circle)zero or many

Here is the bookstore you are building, relationships only, in two parts. The catalog:

erDiagram authors ||--o{ books : "writes" books ||--o{ book_categories : "tagged" categories ||--o{ book_categories : "holds"

The sales side and the staff:

erDiagram customers ||--o{ orders : "places" orders ||--|{ order_items : "contains" books ||--o{ order_items : "sold as" employees |o--o{ employees : "manages"

Read each line out loud from one end to the other:

  • An author writes zero or many books (Asimov: zero); a book has exactly one author.
  • A customer places zero or many orders (Carol and Hank: zero); an order belongs to exactly one customer.
  • An order contains one or many items: an empty order makes no business sense. (MySQL cannot enforce "at least one" with a key; the application or a transaction, Lesson 7.2, takes care of it.)
  • An employee has zero or one manager (the store manager has none) and manages zero or many employees.

💡 Tools that draw these for you

MySQL Workbench (Database, Reverse Engineer) and phpMyAdmin (the Designer tab of a database) read your foreign keys and draw the diagram. They can only draw relationships you declared: a column named author_id without a FOREIGN KEY is invisible to them.

⚠️ Common Mistakes

1. Creating the child before the parent

CREATE TABLE reviews (
    id      INT AUTO_INCREMENT PRIMARY KEY,
    book_id INT NOT NULL,
    stars   INT,
    FOREIGN KEY (book_id) REFERENCES book (id)
);

Error

ERROR 1824 (HY000): Failed to open the referenced table 'book'

What it means: the foreign key points at a table called book, which does not exist (the real one is books). The same error appears when the name is right but you create the child first. Fix: create parent tables first, children second, and check the table name. When you drop tables, go the other way: children first.

🐬 Version note: MariaDB words these differently

On MariaDB (XAMPP, many shared hosts) the missing parent table shows up as ERROR 1005 (HY000): Can't create table `bookstore`.`reviews` (errno: 150 "Foreign key constraint is incorrectly formed"), and Mistake 2 below as ERROR 1265 (01000): Data truncated for column 'author_id' at row 2. Same causes, same fixes. MariaDB's duplicate-key messages also leave out the table name (for key 'PRIMARY').

2. Requiring a value before filling it

To see this one safely, make a two-row scratch table where one row has no author yet:

CREATE TABLE demo_books (id INT PRIMARY KEY, author_id INT);
INSERT INTO demo_books VALUES (1, 6), (2, NULL);
ALTER TABLE demo_books MODIFY COLUMN author_id INT NOT NULL;

Error

ERROR 1138 (22004): Invalid use of NULL value

What it means: a column cannot become NOT NULL while a row still holds NULL (strict mode, MySQL's default, refuses instead of inventing a 0). Fix: fill the column first, count the NULLs (Step 3 above), then add NOT NULL. Clean up:

DROP TABLE demo_books;

3. Storing the same link twice

INSERT INTO book_categories (book_id, category_id) VALUES (2, 5);

Error

ERROR 1062 (23000): Duplicate entry '2-5' for key 'book_categories.PRIMARY'

What it means: 1984 is already Dystopian, and the composite primary key allows each pair once. The message shows the pair as '2-5'. This error is the junction table doing its job. Fix: nothing to fix unless you meant a different pair; to add links without failing on existing ones, check first with a subquery.

4. A list of values in one column (silent)

A shortcut that looks harmless: one text column with all the categories, separated by commas. Here are two books stored that way, built on the spot with UNION ALL like the ratings in Lesson 3.3. Both are Fiction. Which books does the query find?

SELECT title
FROM (
    SELECT 'Dune' AS title, 'Fiction,Science Fiction' AS categories
    UNION ALL
    SELECT 'The Hobbit', 'Fiction,Fantasy'
) AS flat_books
WHERE categories = 'Fiction';

Output

Empty set

What it means: no error, just a wrong answer: neither row's text equals 'Fiction'. Switching to LIKE '%Fiction%' brings them back, but then a search for Fiction also matches every row that only says "Science Fiction". Renaming a category means editing text inside every row, and no foreign key can check a list. Fix: one value per column; many values become many rows in a junction table.

5. Putting the foreign key on the "one" side (silent)

A designer adds order_id to customers "so each customer points at their order". It runs without an error, but a column holds one value, so every customer can now have only one order. What it means: the design limits the data instead of describing it. Fix: ask "can one customer have many orders?" Yes, so the foreign key is orders.customer_id, on the many side.

🛠️ Project: Orders, Order Items and Staff

Authors, books and categories are now related. To finish the bookstore that the rest of the course uses, add the sales side (customers place orders, orders contain books) and the staff, whose managers are other staff members. Long INSERTs are fine to paste with the Copy button: the point is the structure. Allow about 30 minutes.

🛠️ Step 1: The orders table (5 min)

One customer, many orders: the foreign key goes in orders. There is no total column on purpose: a total can always be calculated from the items, and a stored copy could drift out of date (Lesson 6.3 returns to this).

CREATE TABLE orders (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    customer_id INT NOT NULL,
    order_date  DATE NOT NULL,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
        ON DELETE RESTRICT
        ON UPDATE CASCADE
);

INSERT INTO orders (id, customer_id, order_date) VALUES

    (4, 4, '2026-01-22'),

    (6, 7, '2026-02-14'),

🛠️ Step 2: The order_items junction table (7 min)

Each row is one book in one order, with the extra facts about that link. Deleting an order should delete its lines (CASCADE), but a book that was ever sold must not be deleted (RESTRICT).

CREATE TABLE order_items (
    id            INT AUTO_INCREMENT PRIMARY KEY,
    order_id      INT NOT NULL,
    book_id       INT NOT NULL,
    quantity      INT NOT NULL DEFAULT 1,
    price_at_time DECIMAL(8, 2) NOT NULL,
    CONSTRAINT fk_items_order
        FOREIGN KEY (order_id) REFERENCES orders(id)
        ON DELETE CASCADE
        ON UPDATE CASCADE,
    CONSTRAINT fk_items_book
        FOREIGN KEY (book_id) REFERENCES books(id)
        ON DELETE RESTRICT
        ON UPDATE CASCADE
);

🏋️ Exercise 1: Name the Relationship

For each pair, decide whether it is one-to-one, one-to-many or many-to-many, and say which table gets the foreign key (or that a junction table is needed): (a) a country and its capital city; (b) a blog post and its comments; (c) students and courses; (d) a user and their login settings; (e) actors and movies; (f) a playlist and the songs on it.

💡 Hint

Ask the question both ways: "can one A have many Bs?" and "can one B have many As?" Two yeses mean many-to-many.

✅ Solution

(a) One-to-one: capitals.country_id UNIQUE. (b) One-to-many: comments.post_id. (c) Many-to-many: a junction table such as enrollments(student_id, course_id), which can also hold a grade. (d) One-to-one: settings.user_id UNIQUE (or the PK). (e) Many-to-many: movie_cast(actor_id, movie_id), perhaps with the character's name. (f) Many-to-many: a song appears on many playlists, so playlist_songs(playlist_id, song_id), with a position column for the track order.

🏋️ Exercise 4 (Stretch): A Music Library Schema

Design and create, in a new database called music_demo, the tables for a streaming service: artists (name, country); albums (title, release year; one artist per album); songs (title, length in seconds; each song is on one album); playlists (name); and the songs on each playlist, in order. 💡 Hint

Three one-to-many relationships (artist to albums, album to songs) and one many-to-many (playlists and songs). Create parents first: artists, albums, songs, playlists, then the junction table.

✅ Solution 
CREATE DATABASE music_demo;
USE music_demo;

CREATE TABLE artists (
    id      INT AUTO_INCREMENT PRIMARY KEY,
    name    VARCHAR(100) NOT NULL,
    country VARCHAR(50)
);

CREATE TABLE albums (
    id           INT AUTO_INCREMENT PRIMARY KEY,
    artist_id    INT NOT NULL,
    title        VARCHAR(200) NOT NULL,
    release_year INT,
    FOREIGN KEY (artist_id) REFERENCES artists(id)
);

CREATE TABLE songs (
    id               INT AUTO_INCREMENT PRIMARY KEY,
    album_id         INT NOT NULL,
    title            VARCHAR(200) NOT NULL,
    duration_seconds INT,
    FOREIGN KEY (album_id) REFERENCES albums(id)
);

CREATE TABLE playlists (
    id   INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);

CREATE TABLE playlist_songs (
    playlist_id INT NOT NULL,
    song_id     INT NOT NULL,
    position    INT NOT NULL,
    PRIMARY KEY (playlist_id, song_id),
    FOREIGN KEY (playlist_id) REFERENCES playlists(id) ON DELETE CASCADE,
    FOREIGN KEY (song_id) REFERENCES songs(id) ON DELETE CASCADE
);

❓ Common Questions at This Stage

Why not just keep the author's name in books? It is simpler.

For ten books it is, and many small spreadsheets live happily that way. The problems grow with the data: two spellings split one author, an author's birth year has nowhere to go, and an author with no books cannot exist. A separate table costs one lookup per query (a join, next lesson), which MySQL does extremely fast with the foreign key's index.

Do I have to use INT AUTO_INCREMENT ids? Could the author's name be the primary key?

A meaningful value used as a key is called a natural key (an ISBN, an email). It works, but names are not unique and can change, and every child row would repeat the long text. A meaningless number, a surrogate key, never needs to change. The course uses surrogate keys everywhere and adds UNIQUE to natural identifiers like customers.email.

Why did the UPDATE ... JOIN work before I learned joins?

It is a MySQL (and MariaDB) form of UPDATE that pairs the rows of two tables before setting values. The same JOIN ... ON pairing powers SELECT in Lesson 4.3, where you will learn every variant. Other databases write it differently (PostgreSQL uses UPDATE ... FROM).

I made a mistake halfway through the migration. How do I start over?

Either reload Lesson 3.1's flat database (its reload block) and repeat the lesson's blocks, or skip straight to the end state: SOURCE bookstore.sql builds the finished relational database in one go. Your counts in Step 5 tell you which state you are in.

📝 Lesson Summary

🎓 Key Takeaways

  • Store each fact once, in the table it describes; repeated text invites update, insert and delete anomalies
  • A primary key identifies a row; a foreign key holds another table's primary key and is checked once declared
  • One-to-many: the foreign key goes on the "many" side (books.author_id)
  • One-to-one: a foreign key that is also UNIQUE
  • Many-to-many: a junction table with two foreign keys and a composite primary key; it may carry facts about the link (quantity, price_at_time)
  • Migrate safely: add the column, fill it, count what is missing, then add NOT NULL, drop the old column and declare the key
  • Create parents before children; drop children before parents
