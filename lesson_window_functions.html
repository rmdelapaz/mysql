🪟 Lesson 5.2: Window Functions

GROUP BY answers "what is the total?" by squashing rows into one. Many questions need the rows and the total side by side: each book next to the average price, each month next to last month, each salary ranked within its department. Window functions compute across a set of rows, the window, and still return every row.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Explain how OVER() differs from GROUP BY, and split a window with PARTITION BY
  • Number and rank rows with ROW_NUMBER, RANK and DENSE_RANK, and pick the right one when there are ties
  • Build running totals and moving averages, and control them with a frame (ROWS BETWEEN ...)
  • Compare each row with the one before or after it using LAG and LEAD
  • Return the top N rows per group by filtering a window result in a CTE, and explain why WHERE cannot do it (error 3593)

🪟 What Is a Window?

Start from a fresh copy of the bookstore so your results match the ones shown here (use the path where you saved the file):

Here is the problem window functions solve. The average book price is easy:

SELECT ROUND(AVG(price), 2) AS avg_price FROM books;

Output

+-----------+
| avg_price |
+-----------+
|     10.76 |
+-----------+

But one number is all you get: the eleven books are gone. To show every book next to the average, add OVER () to the aggregate. That turns it into a window function: it still averages, but it hands the answer back to every row instead of collapsing them.

SELECT title,
       price,
       ROUND(AVG(price) OVER (), 2)         AS avg_price,
       ROUND(price - AVG(price) OVER (), 2) AS vs_average
FROM books
ORDER BY price DESC, title;

Output

+------------------------+-------+-----------+------------+
| title                  | price | avg_price | vs_average |
+------------------------+-------+-----------+------------+
| Lord of the Rings      | 15.99 |     10.76 |       5.23 |
| Dune                   | 14.99 |     10.76 |       4.23 |
| To Kill a Mockingbird  | 11.99 |     10.76 |       1.23 |
| The Hobbit             | 10.99 |     10.76 |       0.23 |
| Fahrenheit 451         | 10.49 |     10.76 |      -0.27 |
| 1984                   |  9.99 |     10.76 |      -0.77 |
| Brave New World        |  9.49 |     10.76 |      -1.27 |
| The Catcher in the Rye |  8.99 |     10.76 |      -1.77 |
| The Great Gatsby       |  8.99 |     10.76 |      -1.77 |
| Animal Farm            |  8.49 |     10.76 |      -2.27 |
| Pride and Prejudice    |  7.99 |     10.76 |      -2.77 |
+------------------------+-------+-----------+------------+

Eleven rows in, eleven rows out. The empty parentheses in OVER () mean "the window is the whole result", so every book is compared with the same average, 10.76.

The OVER clause has three optional parts, and the rest of the lesson takes them one at a time:

PartSaysExample
PARTITION BYSplit the rows into separate windowsPARTITION BY department
ORDER BYPut the rows of each window in orderORDER BY salary DESC

🧱 PARTITION BY: One Window per Group

PARTITION BY does what GROUP BY does, split rows by a value, but without collapsing them. Each row sees only the rows of its own partition. How does each employee's salary compare with their department's average?

SELECT first_name,
       department,
       salary,
       ROUND(AVG(salary) OVER (PARTITION BY department), 2) AS dept_avg,
       COUNT(*) OVER (PARTITION BY department)              AS dept_size
FROM employees
ORDER BY department, salary DESC;

Output

+------------+------------+----------+----------+-----------+
| first_name | department | salary   | dept_avg | dept_size |
+------------+------------+----------+----------+-----------+
| Priya      | sales      | 46000.00 | 39625.00 |         4 |
| Lena       | sales      | 39500.00 | 39625.00 |         4 |
| Tom        | sales      | 38000.00 | 39625.00 |         4 |
| Ben        | sales      | 35000.00 | 39625.00 |         4 |
| Marcus     | inventory  | 47000.00 | 42000.00 |         2 |
| Sofia      | inventory  | 37000.00 | 42000.00 |         2 |
| Maria      | management | 92000.00 | 80000.00 |         2 |
| Daniel     | management | 68000.00 | 80000.00 |         2 |
| James      | support    | 52000.00 | 44250.00 |         2 |
| Nina       | support    | 36500.00 | 44250.00 |         2 |
+------------+------------+----------+----------+-----------+

Every sales row shows the sales average (39625.00) and the sales head count (4); every support row shows the support figures. The departments come out as sales, inventory, management, support because department is an ENUM, and an ENUM sorts in the order its values were declared, not alphabetically.

💡 Several windows in one query

Each window function has its own OVER, so one query can mix them: AVG(salary) OVER (PARTITION BY department) next to AVG(salary) OVER () gives the department average and the company average on the same row.

🏅 ROW_NUMBER, RANK and DENSE_RANK

Three functions exist only as window functions. They need an ORDER BY inside OVER, because a rank only makes sense in some order. To see how they treat ties, rank the books by copies sold (a CTE adds up the copies first):

WITH copies AS (
    SELECT b.title, SUM(oi.quantity) AS sold
    FROM books b
    JOIN order_items oi ON oi.book_id = b.id
    GROUP BY b.id, b.title
)
SELECT title,
       sold,
       ROW_NUMBER() OVER (ORDER BY sold DESC, title) AS row_num,
       RANK()       OVER (ORDER BY sold DESC)        AS rank_num,
       DENSE_RANK() OVER (ORDER BY sold DESC)        AS dense_num
FROM copies
ORDER BY sold DESC, title;

Output

+-----------------------+------+---------+----------+-----------+
| title                 | sold | row_num | rank_num | dense_num |
+-----------------------+------+---------+----------+-----------+
| 1984                  |    4 |       1 |        1 |         1 |
| Dune                  |    3 |       2 |        2 |         2 |
| The Hobbit            |    3 |       3 |        2 |         2 |
| Animal Farm           |    2 |       4 |        4 |         3 |
| Fahrenheit 451        |    2 |       5 |        4 |         3 |
| Lord of the Rings     |    2 |       6 |        4 |         3 |
| Pride and Prejudice   |    2 |       7 |        4 |         3 |
| To Kill a Mockingbird |    2 |       8 |        4 |         3 |
| Brave New World       |    1 |       9 |        9 |         4 |
+-----------------------+------+---------+----------+-----------+
FunctionOn a tieAfter the tieUse it for
ROW_NUMBER()Different numbers (order decides)Continues: 1, 2, 3, 4Exactly N rows, numbering, paging
RANK()Same numberSkips: 1, 2, 2, 4Sports-style standings
DENSE_RANK()Same numberNo gap: 1, 2, 2, 3"Top 3 sales levels", ties included

Dune and The Hobbit both sold 3. ROW_NUMBER must still give them different numbers, so the query adds title as a tie-breaker; without one, which of the two gets 2 is up to the server. RANK gives both 2 and jumps to 4 (three books are ahead of the next one); DENSE_RANK gives both 2 and continues with 3. The aliases end in _num on purpose: rank is a reserved word (Common Mistake 2).

Naming a window once

When several functions share the same window, define it once in a WINDOW clause after FROM/WHERE/GROUP BY/HAVING and refer to it by name:

SELECT first_name,
       salary,
       RANK()       OVER by_pay AS rank_num,
       DENSE_RANK() OVER by_pay AS dense_num
FROM employees
WINDOW by_pay AS (ORDER BY salary DESC)
ORDER BY salary DESC
LIMIT 4;

Output

+------------+----------+----------+-----------+
| first_name | salary   | rank_num | dense_num |
+------------+----------+----------+-----------+
| Maria      | 92000.00 |        1 |         1 |
| Daniel     | 68000.00 |        2 |         2 |
| James      | 52000.00 |        3 |         3 |
| Marcus     | 47000.00 |        4 |         4 |
+------------+----------+----------+-----------+

📈 Running Totals and Frames

Add ORDER BY inside OVER to an aggregate like SUM, and it no longer sums the whole window: it sums from the first row up to the current one. That is a running total. Here is the half year's revenue, month by month, with the total so far:

WITH monthly AS (
    SELECT MONTH(o.order_date)                 AS month_num,
           SUM(oi.quantity * oi.price_at_time) AS revenue
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.id
    GROUP BY MONTH(o.order_date)
)
SELECT month_num,
       revenue,
       SUM(revenue) OVER (ORDER BY month_num) AS running_total
FROM monthly
ORDER BY month_num;

Output

+-----------+---------+---------------+
| month_num | revenue | running_total |
+-----------+---------+---------------+
|         1 |   61.95 |         61.95 |
|         2 |   51.95 |        113.90 |
|         3 |   33.47 |        147.37 |
|         4 |   38.97 |        186.34 |
|         5 |   31.97 |        218.31 |
|         6 |   18.98 |        237.29 |
+-----------+---------+---------------+

Each row adds its own month to the total of the rows before it, and June's running total, 237.29, is the whole half year.

The frame: which rows count

The set of rows an aggregate sees for the current row is its frame. You can set it yourself with ROWS BETWEEN start AND end. A three-month moving average looks at the current month and the two before it:

WITH monthly AS (
    SELECT MONTH(o.order_date)                 AS month_num,
           SUM(oi.quantity * oi.price_at_time) AS revenue
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.id
    GROUP BY MONTH(o.order_date)
)
SELECT month_num,
       revenue,
       ROUND(AVG(revenue) OVER (ORDER BY month_num
                                ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 2) AS moving_avg_3
FROM monthly
ORDER BY month_num;

Output

+-----------+---------+--------------+
| month_num | revenue | moving_avg_3 |
+-----------+---------+--------------+
|         1 |   61.95 |        61.95 |
|         2 |   51.95 |        56.95 |
|         3 |   33.47 |        49.12 |
|         4 |   38.97 |        41.46 |
|         5 |   31.97 |        34.80 |
|         6 |   18.98 |        29.97 |
+-----------+---------+--------------+

January has no earlier months, so its "average" is January alone; February averages two months; from March on, every row averages exactly three. A moving average smooths out a lucky or unlucky month and shows the trend: steadily down.

graph TD A["current row: April"] --> B["frame: 2 preceding + current"] B --> C["February, March, April"] C --> D["AVG of 3 values: 41.46"]
FrameRows it covers
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROWFirst row to here (a running total)
ROWS BETWEEN 2 PRECEDING AND CURRENT ROWThe last three rows
ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWINGPrevious, current and next row
ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWINGThe whole partition

⚠️ The default frame is RANGE, not ROWS

With ORDER BY and no frame, MySQL uses RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. RANGE treats rows with the same ORDER BY value as one step, so tied rows get the same running total. The months above have no ties, so it made no difference; Common Mistake 4 shows when it does. Write ROWS BETWEEN ... whenever you mean "row by row".

Share of the total

An empty OVER () gives the grand total on every row, which makes percentages one division away:

WITH monthly AS (
    SELECT MONTH(o.order_date)                 AS month_num,
           SUM(oi.quantity * oi.price_at_time) AS revenue
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.id
    GROUP BY MONTH(o.order_date)
)
SELECT month_num,
       revenue,
       ROUND(100 * revenue / SUM(revenue) OVER (), 1) AS pct_of_half_year
FROM monthly
ORDER BY month_num;

Output

+-----------+---------+------------------+
| month_num | revenue | pct_of_half_year |
+-----------+---------+------------------+
|         1 |   61.95 |             26.1 |
|         2 |   51.95 |             21.9 |
|         3 |   33.47 |             14.1 |
|         4 |   38.97 |             16.4 |
|         5 |   31.97 |             13.5 |
|         6 |   18.98 |              8.0 |
+-----------+---------+------------------+

⏮️ LAG and LEAD: The Row Before and After

In Lesson 5.1 you compared each month with the month before by joining a CTE to itself. LAG(column) does it directly: it returns the value of column from the previous row of the window. LEAD(column) returns the next row's value.

WITH monthly AS (
    SELECT MONTH(o.order_date)                 AS month_num,
           SUM(oi.quantity * oi.price_at_time) AS revenue
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.id
    GROUP BY MONTH(o.order_date)
)
SELECT month_num,
       revenue,
       LAG(revenue)  OVER (ORDER BY month_num)           AS prev_month,
       revenue - LAG(revenue) OVER (ORDER BY month_num)  AS change_amount,
       LEAD(revenue) OVER (ORDER BY month_num)           AS next_month
FROM monthly
ORDER BY month_num;

Output

+-----------+---------+------------+---------------+------------+
| month_num | revenue | prev_month | change_amount | next_month |
+-----------+---------+------------+---------------+------------+
|         1 |   61.95 |       NULL |          NULL |      51.95 |
|         2 |   51.95 |      61.95 |        -10.00 |      33.47 |
|         3 |   33.47 |      51.95 |        -18.48 |      38.97 |
|         4 |   38.97 |      33.47 |          5.50 |      31.97 |
|         5 |   31.97 |      38.97 |         -7.00 |      18.98 |
|         6 |   18.98 |      31.97 |        -12.99 |       NULL |
+-----------+---------+------------+---------------+------------+

January has no row before it, so LAG returns NULL (and so does the subtraction); June has no row after it, so LEAD returns NULL. The numbers match the self-join of Lesson 5.1, with a third of the code.

Offsets and defaults

Both functions take two optional arguments: how many rows back (or ahead) to look, and what to return when there is no such row. Percent change against the previous month, with 0 instead of NULL for "two months ago" when there is none:

WITH monthly AS (
    SELECT MONTH(o.order_date)                 AS month_num,
           SUM(oi.quantity * oi.price_at_time) AS revenue
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.id
    GROUP BY MONTH(o.order_date)
)
SELECT month_num,
       revenue,
       ROUND(100 * (revenue - LAG(revenue) OVER w) / LAG(revenue) OVER w, 1) AS pct_change,
       LAG(revenue, 2, 0) OVER w AS two_months_ago
FROM monthly
WINDOW w AS (ORDER BY month_num)
ORDER BY month_num;

Output

+-----------+---------+------------+----------------+
| month_num | revenue | pct_change | two_months_ago |
+-----------+---------+------------+----------------+
|         1 |   61.95 |       NULL |           0.00 |
|         2 |   51.95 |      -16.1 |           0.00 |
|         3 |   33.47 |      -35.6 |          61.95 |
|         4 |   38.97 |       16.4 |          51.95 |
|         5 |   31.97 |      -18.0 |          33.47 |
|         6 |   18.98 |      -40.6 |          38.97 |
+-----------+---------+------------+----------------+

🐬 Version note: no default argument on MariaDB

MySQL 8.4 runs this exactly like 9.7. MariaDB accepts LAG(revenue, 2) but not the third argument: LAG(revenue, 2, 0) is a syntax error (1064) there. Wrapping the function in COALESCE gives the same result on every server:

WITH monthly AS (
    SELECT MONTH(o.order_date)                 AS month_num,
           SUM(oi.quantity * oi.price_at_time) AS revenue
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.id
    GROUP BY MONTH(o.order_date)
)
SELECT month_num,
       COALESCE(LAG(revenue, 2) OVER (ORDER BY month_num), 0) AS two_months_ago
FROM monthly
ORDER BY month_num;

Output on MariaDB

+-----------+----------------+
| month_num | two_months_ago |
+-----------+----------------+
|         1 |           0.00 |
|         2 |           0.00 |
|         3 |          61.95 |
|         4 |          51.95 |
|         5 |          33.47 |
|         6 |          38.97 |
+-----------+----------------+

LAG within each customer

Add PARTITION BY and "the previous row" means "the previous row for the same customer". How many days passed between each customer's orders?

SELECT c.first_name,
       o.order_date,
       LAG(o.order_date) OVER (PARTITION BY o.customer_id ORDER BY o.order_date) AS previous_order,
       DATEDIFF(o.order_date,
                LAG(o.order_date) OVER (PARTITION BY o.customer_id ORDER BY o.order_date)) AS days_between
FROM orders o
JOIN customers c ON c.id = o.customer_id
ORDER BY c.first_name, o.order_date;

🥇 Top N per Group

"The best-selling book in each category", "the highest-paid person in each department": these top-N-per-group questions are where window functions earn their keep. The recipe has two steps: number the rows inside each group, then keep the low numbers.

WITH ranked AS (
    SELECT first_name,
           last_name,
           department,
           salary,
           ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS pos
    FROM employees
)
SELECT department, first_name, last_name, salary
FROM ranked
WHERE pos = 1
ORDER BY salary DESC;

Output

+------------+------------+-----------+----------+
| department | first_name | last_name | salary   |
+------------+------------+-----------+----------+
| management | Maria      | Santos    | 92000.00 |
| support    | James      | Okafor    | 52000.00 |
| inventory  | Marcus     | Hill      | 47000.00 |
| sales      | Priya      | Nair      | 46000.00 |
+------------+------------+-----------+----------+

The window numbers each department's staff from the highest salary down, and the outer query keeps number 1 from every department. Change pos = 1 to pos <= 2 and you get the top two per department.

When ties matter

Which book sold the most copies in each category? Several categories have ties, and ROW_NUMBER would quietly drop one of the tied books. DENSE_RANK keeps them all:

WITH copies AS (
    SELECT cat.name AS category, b.title, SUM(oi.quantity) AS sold
    FROM categories cat
    JOIN book_categories bc ON bc.category_id = cat.id
    JOIN books b            ON b.id = bc.book_id
    JOIN order_items oi     ON oi.book_id = b.id
    GROUP BY cat.id, cat.name, b.id, b.title
),
ranked AS (
    SELECT category, title, sold,
           DENSE_RANK() OVER (PARTITION BY category ORDER BY sold DESC) AS rank_num
    FROM copies
)
SELECT category, title, sold, rank_num
FROM ranked
WHERE rank_num <= 2
ORDER BY category, rank_num, title;

Output

+-----------------+-----------------------+------+----------+
| category        | title                 | sold | rank_num |
+-----------------+-----------------------+------+----------+
| Classic         | 1984                  |    4 |        1 |
| Classic         | Animal Farm           |    2 |        2 |
| Classic         | Pride and Prejudice   |    2 |        2 |
| Classic         | To Kill a Mockingbird |    2 |        2 |
| Dystopian       | 1984                  |    4 |        1 |
| Dystopian       | Fahrenheit 451        |    2 |        2 |
| Fantasy         | The Hobbit            |    3 |        1 |
| Fantasy         | Lord of the Rings     |    2 |        2 |
| Fiction         | 1984                  |    4 |        1 |
| Fiction         | Dune                  |    3 |        2 |
| Fiction         | The Hobbit            |    3 |        2 |
| Science Fiction | Dune                  |    3 |        1 |
| Science Fiction | Fahrenheit 451        |    2 |        2 |
+-----------------+-----------------------+------+----------+

"Top 2" in Classic returns four books: 1984 first, then three books tied at 2 copies. In Fiction, Dune and The Hobbit share second place. Whether that is right depends on the question. For "the two books to put in the window", use ROW_NUMBER with a tie-breaker; for "every book at the top two sales levels", use DENSE_RANK.

🚧 Why WHERE Cannot Filter a Window

Why the CTE in the last section? Why not write WHERE ROW_NUMBER() OVER (...) = 1? Because of the order in which MySQL runs a query's clauses. Window functions are computed late, after the rows have been filtered and grouped:

graph TD A["1. FROM and JOIN"] --> B["2. WHERE: keep rows"] B --> C["3. GROUP BY and HAVING"] C --> D["4. window functions"] D --> E["5. SELECT list"] E --> F["6. ORDER BY, then LIMIT"]

When WHERE runs, the windows do not exist yet; and if WHERE could see them, it would change the very rows they are computed over. So MySQL allows window functions only in the SELECT list and ORDER BY. To filter on a window's result, compute it in one step and filter in the next: a CTE (or a derived table) is that next step.

WITH priced AS (
    SELECT title, price,
           ROW_NUMBER() OVER (ORDER BY price DESC) AS pos
    FROM books
)
SELECT pos, title, price
FROM priced
WHERE pos <= 3
ORDER BY pos;

Output

+-----+-----------------------+-------+
| pos | title                 | price |
+-----+-----------------------+-------+
|   1 | Lord of the Rings     | 15.99 |
|   2 | Dune                  | 14.99 |
|   3 | To Kill a Mockingbird | 11.99 |
+-----+-----------------------+-------+

For a plain "top 3 of everything" like this one, ORDER BY price DESC LIMIT 3 is simpler. The CTE pattern matters as soon as there is a PARTITION BY: LIMIT cuts the whole result, not each group.

⚠️ Common Mistakes

1. Filtering on a window function in WHERE

SELECT first_name, department, salary
FROM employees
WHERE ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) = 1;

Error

ERROR 3593 (HY000): You cannot use the window function 'row_number' in this context.'

What it means: window functions are computed after WHERE, so WHERE cannot use them. (The stray quote at the end of the message is MySQL's typo, not yours.) Trying the alias instead, WHERE pos = 1, fails too, with error 1054 "Unknown column 'pos' in 'where clause'". On MariaDB the same mistake is error 4015, "Window function is allowed only in SELECT list and ORDER BY clause". Fix: compute the window in a CTE and filter in the outer query, as in the Top N section.

2. Naming a column rank

SELECT title, price,
       RANK() OVER (ORDER BY price DESC) AS rank
FROM books;

Error

ERROR 1064 (42000): You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near 'rank
FROM books' at line 2

What it means: since MySQL 8.0, RANK, ROW_NUMBER, DENSE_RANK, WINDOW, OVER and the other window keywords are reserved words, so AS rank confuses the parser. Old tutorials and MariaDB (which still accepts AS rank) make this easy to copy by accident. Fix: pick a different name (rank_num, price_rank), or quote it with backticks: AS `rank`.

3. Copying QUALIFY from another database

SELECT title, price,
       ROW_NUMBER() OVER (ORDER BY price DESC) AS pos
FROM books
QUALIFY pos <= 3;

Error

ERROR 6037 (HY000): 'QUALIFY clause' can be used only if the hypergraph optimizer is enabled.

What it means: some databases (Snowflake, BigQuery, DuckDB) have a QUALIFY clause that filters on window results directly. MySQL 9.7 and 8.4 recognize the word but only run it under an alternative query optimizer (the "hypergraph" optimizer) that is switched off by default; MariaDB does not know it at all (error 1064). Fix: use the CTE pattern, which works on every server.

4. A running total that jumps on ties (silent)

SELECT title, price,
       SUM(price) OVER (ORDER BY price) AS running_total
FROM books
ORDER BY price, title
LIMIT 5;

Output

+------------------------+-------+---------------+
| title                  | price | running_total |
+------------------------+-------+---------------+
| Pride and Prejudice    |  7.99 |          7.99 |
| Animal Farm            |  8.49 |         16.48 |
| The Catcher in the Rye |  8.99 |         34.46 |
| The Great Gatsby       |  8.99 |         34.46 |
| Brave New World        |  9.49 |         43.95 |
+------------------------+-------+---------------+

What it means: no error, but The Catcher in the Rye and The Great Gatsby both cost 8.99, and both show 34.46, as if they had been added at the same moment. That is the default RANGE frame: rows with the same ORDER BY value are one step. Fix: say "row by row" and make the order unique:

SELECT title, price,
       SUM(price) OVER (ORDER BY price, title
                        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total
FROM books
ORDER BY price, title
LIMIT 5;

Output

+------------------------+-------+---------------+
| title                  | price | running_total |
+------------------------+-------+---------------+
| Pride and Prejudice    |  7.99 |          7.99 |
| Animal Farm            |  8.49 |         16.48 |
| The Catcher in the Rye |  8.99 |         25.47 |
| The Great Gatsby       |  8.99 |         34.46 |
| Brave New World        |  9.49 |         43.95 |
+------------------------+-------+---------------+

5. LAST_VALUE that returns the current row (silent)

SELECT title, price,
       FIRST_VALUE(title) OVER (ORDER BY price) AS cheapest,
       LAST_VALUE(title)  OVER (ORDER BY price) AS priciest
FROM books
ORDER BY price, title
LIMIT 2;

Output

+---------------------+-------+---------------------+---------------------+
| title               | price | cheapest            | priciest            |
+---------------------+-------+---------------------+---------------------+
| Pride and Prejudice |  7.99 | Pride and Prejudice | Pride and Prejudice |
| Animal Farm         |  8.49 | Pride and Prejudice | Animal Farm         |
+---------------------+-------+---------------------+---------------------+

What it means: FIRST_VALUE works, but LAST_VALUE echoes each row's own title. The default frame ends at the current row (plus any rows tied with it), so the "last" row of the frame is the current one, never the priciest book. Fix: extend the frame to the end of the window:

SELECT title, price,
       LAST_VALUE(title) OVER (ORDER BY price
                               ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS priciest
FROM books
ORDER BY price, title
LIMIT 2;

Output

+---------------------+-------+-------------------+
| title               | price | priciest          |
+---------------------+-------+-------------------+
| Pride and Prejudice |  7.99 | Lord of the Rings |
| Animal Farm         |  8.49 | Lord of the Rings |
+---------------------+-------+-------------------+

Or skip LAST_VALUE entirely: FIRST_VALUE(title) OVER (ORDER BY price DESC) gives the priciest book with the default frame.

🛠️ Step 2: Month over month (10 min)

Add the change from the previous month and the three-month moving average, sharing one named window:

-- 2. Month over month
WITH monthly AS (
    SELECT MONTH(o.order_date)                 AS month_num,
           SUM(oi.quantity * oi.price_at_time) AS revenue
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.id
    GROUP BY MONTH(o.order_date)
)
SELECT month_num,
       revenue,
       revenue - LAG(revenue) OVER w AS change_amount,
       ROUND(AVG(revenue) OVER (w ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 2) AS moving_avg_3
FROM monthly
WINDOW w AS (ORDER BY month_num)
ORDER BY month_num;

🛠️ Step 4: Top customer in every city (5 min)

Total each customer's spending, number the customers within their city from the biggest spender down, and keep number 1. Customers with no city get a readable label:

-- 4. Top customer per city
WITH spending AS (
    SELECT COALESCE(c.city, '(no city)')        AS city,
           CONCAT(c.first_name, ' ', c.last_name) AS customer,
           SUM(oi.quantity * oi.price_at_time)  AS spent
    FROM customers c
    JOIN orders o       ON o.customer_id = c.id
    JOIN order_items oi ON oi.order_id = o.id
    GROUP BY c.id, c.city, c.first_name, c.last_name
),
ranked AS (
    SELECT city, customer, spent,
           ROW_NUMBER() OVER (PARTITION BY city ORDER BY spent DESC, customer) AS pos
    FROM spending
)
SELECT city, customer, spent
FROM ranked
WHERE pos = 1
ORDER BY spent DESC;

Output

For every author who has books, show their cheapest book, its price, and how many books the author has. Use one window for the position and another for the count, and keep exactly one row per author even if two books ever cost the same.

)

FROM by_author
WHERE pos = 1

❓ Common Questions at This Stage

Does the ORDER BY inside OVER sort my result?

No. It only orders the rows inside the window for the function's sake. The result often comes out in that order because of how MySQL computes it, but nothing promises that. Always add a final ORDER BY to the query itself, as every example in this lesson does.

Can I use window functions together with GROUP BY?

Yes. The grouping happens first, then the window functions run over the grouped rows. That is why the lesson's CTEs group first and rank after, but you can also write it in one query: SELECT department, SUM(salary), RANK() OVER (ORDER BY SUM(salary) DESC) FROM employees GROUP BY department ranks the departments by payroll.

Which window functions does MySQL have besides the ones in this lesson?

All the usual aggregates (SUM, AVG, COUNT, MIN, MAX) work with OVER. The dedicated ones are ROW_NUMBER, RANK, DENSE_RANK, PERCENT_RANK, CUME_DIST, NTILE(n) (split rows into n buckets), LAG, LEAD, FIRST_VALUE, LAST_VALUE and NTH_VALUE. MySQL 8.4 and MariaDB support the same set.

Are window functions slow?

Each distinct window usually means one sort of the rows. On the bookstore's tables that is instant; on millions of rows, an index that matches the PARTITION BY and ORDER BY columns helps, and reusing one named window instead of several slightly different ones avoids extra sorts. Lesson 6.1 covers indexes.

📝 Lesson Summary

🎓 Key Takeaways

  • A window function computes across a set of rows and returns a value for every row: OVER turns an aggregate into one
  • PARTITION BY splits the window per group without collapsing rows; ORDER BY inside OVER orders each window
  • ROW_NUMBER never ties; RANK ties and skips; DENSE_RANK ties without gaps
  • An aggregate with ORDER BY in OVER is a running total; the frame (ROWS BETWEEN ...) decides which rows count, and the default is RANGE, which lumps ties together
  • LAG and LEAD read the previous and next row, with an optional offset and default
  • Window functions run after WHERE, GROUP BY and HAVING: filter on them in an outer query over a CTE (error 3593 otherwise)
  • rank, row_number and window are reserved words: name columns rank_num and similar
You wantWrite
A total next to every rowSUM(x) OVER ()
A per-group figure next to every rowAVG(x) OVER (PARTITION BY g)
Rank with tiesRANK() or DENSE_RANK() OVER (ORDER BY x DESC)
A running totalSUM(x) OVER (ORDER BY t ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
A 3-row moving averageAVG(x) OVER (ORDER BY t ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)
Change from the previous rowx - LAG(x) OVER (ORDER BY t)
