🏗️ Lesson 6.3: Database Design & Normalization

Why is the bookstore split into customers, orders, order items, books and authors, instead of one big sheet with everything on it? Because one big sheet quietly corrupts itself: the same email stored twice drifts apart, a customer cannot exist without an order, deleting an order deletes a person. Normalization is the step-by-step method for splitting data so that each fact is stored once, in the right place. In this lesson you do it for real, on a flat order sheet, and prove that the split loses nothing.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Recognize update, insert and delete anomalies, and show each one with a query
  • Find the functional dependencies and the key of a table
  • Normalize a flat table to first, second and third normal form (1NF, 2NF, 3NF)
  • Build the normalized tables with INSERT ... SELECT DISTINCT and prove with EXCEPT that no data was lost
  • Read an ER diagram, and decide when storing derived or duplicated data is worth the risk

🧭 Why Design Matters

Picture the bookstore's first year, run from a spreadsheet: one row per order, with the customer's name, email and city typed on every row, and the books squeezed into one cell. It works until Alice changes her email and someone updates three of her eleven rows. Now the store has two emails for Alice, and no query can tell which one is right.

A database cannot stop people from typing wrong values, but a good design can make sure each fact is typed once. Then there is nothing to keep in sync. Normalization is the classic method for getting there, defined as a series of normal forms, each removing one kind of duplication.

It looks tidy. Now ask it a simple question: how many copies of 1984 did the store sell? The answer (3) is in there, spread over two cells of comma-separated text, and no aggregate can add up "the second number in a list". The best SQL can do is find the rows that mention the title somewhere:

SELECT order_id, book_titles, quantities
FROM order_sheet
WHERE book_titles LIKE '%1984%'
ORDER BY order_id;

Output

|        1 | Dune, 1984        | 1, 2       |
|        7 | 1984, Animal Farm | 1, 1       |

You would now have to work out by hand which quantity belongs to 1984 on each row. And LIKE '%Dune%' would also match a later book called "Dune Messiah". The sheet holds the data but hides it from SQL.

💥 Update, Insert and Delete Anomalies

Mixing several kinds of facts in one table (facts about customers, about books, about orders) causes three classic problems, called anomalies. Each one is easy to show.

1. Update anomaly: copies drift apart

Alice's email is stored on two rows. Someone updates the one in front of them (inside a transaction, so you can undo it):

START TRANSACTION;

UPDATE order_sheet SET cust_email = 'alice.j@example.com' WHERE order_id = 2;

SELECT DISTINCT cust_name, cust_email
FROM order_sheet
WHERE cust_name = 'Alice Johnson';

ROLLBACK;

Output

+---------------+---------------------+
| cust_name     | cust_email          |
+---------------+---------------------+
| Alice Johnson | alice@example.com   |
| Alice Johnson | alice.j@example.com |
+---------------+---------------------+

No error, and now the table holds two emails for one person. Which one gets the receipt? The database cannot know: a fact stored twice can disagree with itself.

2. Insert anomaly: a customer needs an order

Carol Williams signs up for the newsletter but has not ordered yet. There is nowhere to put her:

INSERT INTO order_sheet (cust_name, cust_email, cust_city)
VALUES ('Carol Williams', 'carol@example.com', 'Los Angeles');

Error

ERROR 1364 (HY000): Field 'order_id' doesn't have a default value

Every row is an order, so every row needs an order id, a date and books. The only ways around it are inventing a fake order or making those columns nullable, and both make the data lie.

3. Delete anomaly: deleting an order deletes a person

START TRANSACTION;

DELETE FROM order_sheet WHERE order_id = 4;

SELECT COUNT(*) AS rows_about_dave
FROM order_sheet
WHERE cust_name = 'Dave Brown';

ROLLBACK;

Output

+-----------------+
| rows_about_dave |
+-----------------+
|               0 |
+-----------------+

Order 4 was Dave's only order in this sheet. Cancel it, and the store forgets Dave's email and city too, along with the fact that Lord of the Rings costs 15.99.

🔑 The cause of all three

Each anomaly comes from storing facts about different things (a customer, a book, an order) in the same row. The fix is always the same: give each kind of thing its own table, and connect the tables with keys.

1️⃣ First Normal Form: One Value per Cell

📜 The 1NF rule

A table is in first normal form when every cell holds a single value (no lists, no "Dune, 1984"), there are no repeating column groups (book1, book2, book3), and every row can be identified by a key.

The fix for the comma lists: one row per book per order. The order_total column goes too, for a reason you will see at the end of the lesson: it can always be computed from the lines.

CREATE TABLE order_lines_1nf (
    order_id    INT NOT NULL,
    order_date  DATE NOT NULL,
    cust_name   VARCHAR(100) NOT NULL,
    cust_email  VARCHAR(100) NOT NULL,
    cust_city   VARCHAR(50),
    book_title  VARCHAR(200) NOT NULL,
    book_price  DECIMAL(8, 2) NOT NULL,
    quantity    INT NOT NULL,
    PRIMARY KEY (order_id, book_title)
);

INSERT INTO order_lines_1nf VALUES
    (1, '2026-01-15', 'Alice Johnson', 'alice@example.com', 'New York', 'Dune', 14.99, 1),
    (1, '2026-01-15', 'Alice Johnson', 'alice@example.com', 'New York', '1984', 9.99, 2),
    (2, '2026-02-20', 'Alice Johnson', 'alice@example.com', 'New York', 'Pride and Prejudice', 7.99, 1),
    (3, '2026-03-10', 'Bob Smith', 'bob@example.com', 'Chicago', 'Dune', 14.99, 1),
    (4, '2026-01-22', 'Dave Brown', 'dave@example.com', 'Houston', 'The Hobbit', 10.99, 1),
    (4, '2026-01-22', 'Dave Brown', 'dave@example.com', 'Houston', 'Lord of the Rings', 15.99, 1),
    (7, '2026-03-28', 'Bob Smith', 'bob@example.com', 'Chicago', '1984', 9.99, 1),
    (7, '2026-03-28', 'Bob Smith', 'bob@example.com', 'Chicago', 'Animal Farm', 8.49, 1);

SELECT book_title, SUM(quantity) AS copies
FROM order_lines_1nf
GROUP BY book_title
ORDER BY copies DESC, book_title;

Output

+---------------------+--------+
| book_title          | copies |
+---------------------+--------+
| 1984                |      3 |
| Dune                |      2 |
| Animal Farm         |      1 |
| Lord of the Rings   |      1 |
| Pride and Prejudice |      1 |

Every cell holds one value, and the question that defeated the sheet is now an ordinary GROUP BY. The primary key is (order_id, book_title): one order can contain many books and one book many orders, but each book appears once per order.

1NF fixed querying, not duplication. Alice's name, email and city are now on three rows instead of two, and every anomaly from the previous section is still there. The next two normal forms deal with that, and they need one new idea.

🧩 Functional Dependencies and Keys

A functional dependency, written A → B ("A determines B"), means: whenever two rows have the same value of A, they must have the same value of B. Knowing A tells you B. Dependencies come from the rules of the business, not from the current rows: "every order has one date" is a rule, so order_id → order_date.

Dependency in order_lines_1nfThe business rule behind it
order_id → order_date, cust_emailAn order has one date and is placed by one customer
cust_email → cust_name, cust_cityAn email address belongs to one customer, who has one name and city
book_title → book_priceA book has one price (here, the title identifies the book)
(order_id, book_title) → quantityThe quantity belongs to one line: this book in this order

A key is a set of columns that determines every other column, with nothing unnecessary in it. Here only (order_id, book_title) does: order_id alone does not tell you the book, book_title alone does not tell you the order.

graph TD K["whole key"] --> Q["quantity"] K --> H["part of the key"] H --> O["order_id: date, email"] H --> T["book_title: price"] O --> E["cust_email: name, city"]

You can test a dependency against the data with a query: if book_title → book_price holds, no title may have two different prices.

SELECT book_title, COUNT(DISTINCT book_price) AS prices
FROM order_lines_1nf
GROUP BY book_title
HAVING COUNT(DISTINCT book_price) > 1;

Output

Empty set

No violations. Remember the direction of the evidence, though: data can disprove a dependency (one counterexample is enough), but it can never prove one. Five orders happen to show one customer per city; that does not make cust_city → cust_name a rule.

With dependencies in hand, the next two normal forms are easy to state: they say which dependencies a table must not contain.

2️⃣ Second Normal Form: The Whole Key

📜 The 2NF rule

A table is in second normal form when it is in 1NF and no non-key column depends on only part of a composite key. (A table whose key is a single column is automatically in 2NF.)

The key is (order_id, book_title), and the dependency diagram shows the trouble: order_date and the customer columns depend on order_id alone, and book_price on book_title alone. Only quantity needs the whole key. Those partial dependencies are why the same order date and the same price are repeated on several rows.

The fix: move each group of columns into a table keyed by the column it really depends on. SELECT DISTINCT shows what each new table would hold:

-- what depends on order_id alone: one row per order
SELECT DISTINCT order_id, order_date, cust_name, cust_email, cust_city
FROM order_lines_1nf
ORDER BY order_id;

-- what depends on book_title alone: one row per book
SELECT DISTINCT book_title, book_price
FROM order_lines_1nf
ORDER BY book_title;

Output

|        1 | 2026-01-15 | Alice Johnson | alice@example.com | New York  |
|        2 | 2026-02-20 | Alice Johnson | alice@example.com | New York  |
|        3 | 2026-03-10 | Bob Smith     | bob@example.com   | Chicago   |

Eight lines become five orders and six books, plus a lines table that keeps only (order_id, book_title, quantity). Each price is now stored once. But look at the orders: Alice's name, email and city still appear twice, and so do Bob's. There is a dependency left that 2NF does not cover.

3️⃣ Third Normal Form: Nothing but the Key

📜 The 3NF rule

A table is in third normal form when it is in 2NF and no non-key column depends on another non-key column. Such a chain (order_id → cust_email → cust_city) is called a transitive dependency.

In the orders table the key is order_id, but cust_name and cust_city are not facts about the order. They are facts about the customer, reached through cust_email. As long as they live in the orders table, they are copied onto every order the customer places. The fix: a customers table, and a reference to it from each order.

SELECT DISTINCT cust_email, cust_name, cust_city
FROM order_lines_1nf
ORDER BY cust_email;

Output

+-------------------+---------------+-----------+
| cust_email        | cust_name     | cust_city |
+-------------------+---------------+-----------+
| alice@example.com | Alice Johnson | New York  |
| bob@example.com   | Bob Smith     | Chicago   |
| dave@example.com  | Dave Brown    | Houston   |
+-------------------+---------------+-----------+

Three customers, each stored once. The design is now four tables, and every non-key column depends on the key, the whole key, and nothing but the key (the classic summary, often finished with "so help me Codd", after Edgar F. Codd, who invented the relational model).

🔨 Building and Checking the Normalized Tables

Now build the four tables and fill them from order_lines_1nf with INSERT ... SELECT, the same technique Lesson 4.1 used to move the bookstore from a text author column to an authors table. Customers and books get their own id (a surrogate key), and the natural identifiers (email, title) get UNIQUE so they cannot be duplicated.

CREATE TABLE customers (
    id     INT AUTO_INCREMENT PRIMARY KEY,
    name   VARCHAR(100) NOT NULL,
    email  VARCHAR(100) NOT NULL UNIQUE,
    city   VARCHAR(50)
);

INSERT INTO customers (name, email, city)
SELECT DISTINCT cust_name, cust_email, cust_city
FROM order_lines_1nf
ORDER BY cust_email;

CREATE TABLE books (
    id     INT AUTO_INCREMENT PRIMARY KEY,
    title  VARCHAR(200) NOT NULL UNIQUE,
    price  DECIMAL(8, 2) NOT NULL
);

INSERT INTO books (title, price)
SELECT DISTINCT book_title, book_price
FROM order_lines_1nf
ORDER BY book_title;

SELECT * FROM customers ORDER BY id;
SELECT * FROM books ORDER BY id;

The ORDER BY in each INSERT ... SELECT makes the new ids come out the same every time. Now the two tables that point at them. To fill in each foreign key, join the old rows to the new table on the natural identifier:

CREATE TABLE orders (
    id           INT PRIMARY KEY,
    customer_id  INT NOT NULL,
    order_date   DATE NOT NULL,
    CONSTRAINT fk_lab_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
);

INSERT INTO orders (id, customer_id, order_date)
SELECT DISTINCT l.order_id, c.id, l.order_date
FROM order_lines_1nf AS l
JOIN customers AS c ON c.email = l.cust_email;

CREATE TABLE order_items (
    order_id       INT NOT NULL,
    book_id        INT NOT NULL,
    quantity       INT NOT NULL,
    price_at_time  DECIMAL(8, 2) NOT NULL,
    PRIMARY KEY (order_id, book_id),
    CONSTRAINT fk_lab_items_order FOREIGN KEY (order_id) REFERENCES orders(id),
    CONSTRAINT fk_lab_items_book  FOREIGN KEY (book_id)  REFERENCES books(id)
);

INSERT INTO order_items (order_id, book_id, quantity, price_at_time)
SELECT l.order_id, b.id, l.quantity, l.book_price
FROM order_lines_1nf AS l
JOIN books AS b ON b.title = l.book_title;

SELECT * FROM orders ORDER BY id;
SELECT * FROM order_items ORDER BY order_id, book_id;

💡 Is price_at_time a duplicate of books.price?

No, and the difference matters. books.price is what a book costs today; price_at_time is what this customer paid on this order, a fact determined by (order_id, book_id), the full key of order_items. When the price of Dune goes up next year, old orders must not change. They happen to be equal right now, but they answer different questions, so storing both is not redundancy. The real bookstore makes the same choice.

Prove that nothing was lost

A split is only correct if joining the tables back together gives exactly the rows you started with (a lossless decomposition). EXCEPT returns the rows of the first query that are missing from the second, so two EXCEPTs in opposite directions that both come back empty prove the two sides hold the same rows:

SELECT order_id, order_date, cust_name, cust_email, cust_city, book_title, book_price, quantity
FROM order_lines_1nf
EXCEPT
SELECT o.id, o.order_date, c.name, c.email, c.city, b.title, oi.price_at_time, oi.quantity
FROM orders AS o
JOIN customers   AS c  ON c.id = o.customer_id
JOIN order_items AS oi ON oi.order_id = o.id
JOIN books       AS b  ON b.id = oi.book_id;

SELECT o.id, o.order_date, c.name, c.email, c.city, b.title, oi.price_at_time, oi.quantity
FROM orders AS o
JOIN customers   AS c  ON c.id = o.customer_id
JOIN order_items AS oi ON oi.order_id = o.id
JOIN books       AS b  ON b.id = oi.book_id
EXCEPT
SELECT order_id, order_date, cust_name, cust_email, cust_city, book_title, book_price, quantity
FROM order_lines_1nf;

Output

Empty set
Empty set

Two empty sets: the four tables hold exactly the eight lines, no more, no fewer. (EXCEPT works on MySQL 8.0.31 and later, including 8.4 and 9.7, and on MariaDB.)

The anomalies are gone

Alice's email change is now one row in one table, and every order sees it, because orders only point at her:

START TRANSACTION;

UPDATE customers SET email = 'alice.j@example.com' WHERE id = 1;

SELECT o.id AS order_id, c.name, c.email
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id
WHERE c.name = 'Alice Johnson'
ORDER BY o.id;

ROLLBACK;

Output

+----------+---------------+---------------------+
| order_id | name          | email               |
+----------+---------------+---------------------+
|        1 | Alice Johnson | alice.j@example.com |
|        2 | Alice Johnson | alice.j@example.com |
+----------+---------------+---------------------+

Likewise, Carol can be inserted into customers without an order, and deleting order 4 removes only the order, not Dave or the price of Lord of the Rings. This four-table shape is exactly the core of the bookstore you have used since Module 4.

🗺️ ER Diagrams

An entity-relationship (ER) diagram draws a design: each box is a table (an entity) with its columns, and each line is a relationship labeled with how many rows can sit at each end. Here is the sales side of the real bookstore:

erDiagram customers ||--o{ orders : "places" orders ||--|{ order_items : "contains" books ||--o{ order_items : "sold as"

The keys behind each line: orders.customer_id points at customers.id, and order_items holds both order_id and book_id. (Mermaid and most tools can also list every column inside the boxes; on a small screen the lines alone are easier to read.) And the catalog side, where a many-to-many relationship (a book has several categories, a category has many books) becomes two one-to-many relationships through the junction table book_categories:

erDiagram authors ||--o{ books : "writes" books ||--o{ book_categories : "is in" categories ||--o{ book_categories : "groups"

Reading the line ends

Symbol at a line endMeansBookstore example
||exactly onean order belongs to exactly one customer
o{zero or morea customer places zero or more orders (Carol: zero)
|{one or morean order contains at least one item
o|zero or onean employee has at most one manager

The "one" side of each line holds the primary key; the "many" side holds the foreign key. If you ever find a line with "many" at both ends, you have found a missing junction table.

✅ Draw before you code

It is far easier to spot a missing table or a misplaced column in a sketch than in twenty CREATE TABLE statements. Pen and paper is fine; tools like MySQL Workbench (its EER diagram editor), dbdiagram.io or draw.io help when you share the design. Workbench can also draw the diagram of an existing database for you (Database, Reverse Engineer).

📐 From Requirements to Tables

Normalizing an existing sheet is one way in. Designing from a description is the other, and it uses the same ideas in a different order:

  1. Find the things (entities). The nouns the business keeps track of: customers, books, orders. Each becomes a table.
  2. Find their facts (attributes). Put each fact in the table of the thing it describes: the city describes the customer, not the order.
  3. Choose keys. Usually an AUTO_INCREMENT id, plus UNIQUE on natural identifiers (email).
  4. Find the relationships and their counts. One-to-many: a foreign key on the "many" side. Many-to-many: a junction table with a composite primary key. One-to-one: a foreign key with UNIQUE.
  5. Check each table against 1NF, 2NF and 3NF, asking "what does this column depend on?" for every column.
  6. Write it down: an ER sketch first, then the SQL, with foreign keys, NOT NULL and CHECK constraints doing the guarding.

You will practice this in the stretch exercise below, and do it end to end in Lesson 8.2: Final Project, where you design and build a database of your own.

⚖️ When to Denormalize

Normalization is the default, not a law. Sometimes a design deliberately stores a fact twice, or stores a value it could compute, to make an important read cheaper. That is denormalization, and it always trades read speed for the duty to keep the copies in sync.

TechniqueExampleThe price you pay
Stored derived valueorders.total instead of summing the itemsEvery change to an item must update the total (Common Mistake 4)
Copied columnThe customer's name stored on each orderA rename must update every order, or the copies drift
Summary tablesales_by_month, refreshed every nightThe numbers are up to a day old

⚠️ The golden rule

Normalize first. Denormalize one specific thing only when a measured query is too slow (Lesson 6.1 showed how to measure), indexes and a better query did not fix it, and you have a plan for keeping the copy correct: a transaction (Lesson 7.2), a trigger, or a scheduled refresh. A view (Lesson 6.2) often gives you the convenience of a "flat" table with no copies at all.

The bookstore makes exactly this choice: there is no stored total column on orders, because SUM(quantity * price_at_time) is cheap for an order with a handful of lines, and a total that can never be wrong is worth more than a few microseconds.

⚠️ Common Mistakes

1. Loading a lookup table twice

You rerun your migration script, and the customers INSERT ... SELECT runs a second time:

INSERT INTO customers (name, email, city)
SELECT DISTINCT cust_name, cust_email, cust_city
FROM order_lines_1nf;

Error

ERROR 1062 (23000): Duplicate entry 'alice@example.com' for key 'customers.email'

What it means: the UNIQUE on email refused a second Alice. That error is the design working. Without UNIQUE, the statement would have succeeded silently, every customer would exist twice with two ids, and later joins on email would double every order. Fix: always put UNIQUE on the natural identifier of a lookup table, and make migration scripts start from a clean state (or insert only rows that are not there yet, with WHERE NOT EXISTS).

2. A foreign key whose type does not match

CREATE TABLE reviews (
    id       INT AUTO_INCREMENT PRIMARY KEY,
    book_id  BIGINT NOT NULL,
    stars    TINYINT NOT NULL,
    CONSTRAINT fk_lab_reviews_book FOREIGN KEY (book_id) REFERENCES books(id)
);

Error

ERROR 3780 (HY000): Referencing column 'book_id' and referenced column 'id' in foreign key constraint 'fk_lab_reviews_book' are incompatible.

What it means: books.id is INT, and a foreign key column must have the same type (and the same signedness: INT and INT UNSIGNED do not match either). Fix: declare book_id INT NOT NULL. Decide on one id type for the whole design and use it everywhere. (MariaDB reports the same mistake less helpfully, as error 1005: "Foreign key constraint is incorrectly formed".)

3. Deleting a row that others still point to

DELETE FROM customers WHERE email = 'bob@example.com';

Error

ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (`normalize_lab`.`orders`, CONSTRAINT `fk_lab_orders_customer` FOREIGN KEY (`customer_id`) REFERENCES `customers` (`id`))

What it means: Bob has two orders that reference him. In the flat sheet, deleting rows silently destroyed facts; now the foreign key (from Lesson 4.2) refuses to leave orders pointing at nobody. Fix: decide what should happen to the orders first, and if the answer is "keep them", keep the customer too (many systems mark customers inactive instead of deleting them).

4. Storing a total that can drift (silent)

It is tempting to add the order total back "for speed". Watch what happens after one ordinary update:

ALTER TABLE orders ADD COLUMN total DECIMAL(8, 2);

UPDATE orders AS o
SET total = (SELECT SUM(quantity * price_at_time) FROM order_items WHERE order_id = o.id);

-- later, a customer service agent fixes a quantity
UPDATE order_items SET quantity = 3
WHERE order_id = 1 AND book_id = (SELECT id FROM books WHERE title = '1984');

SELECT o.id, o.total AS stored_total, SUM(oi.quantity * oi.price_at_time) AS real_total
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.id
GROUP BY o.id, o.total
ORDER BY o.id;

Output

+----+--------------+------------+
| id | stored_total | real_total |
+----+--------------+------------+
|  1 |        34.97 |      44.96 |
|  2 |         7.99 |       7.99 |
|  3 |        14.99 |      14.99 |
|  4 |        26.98 |      26.98 |
|  7 |        18.48 |      18.48 |
+----+--------------+------------+

What it means: no error anywhere, and order 1 now has two totals that disagree. Every report that reads total is wrong by 9.99, and nothing will ever tell you. Fix: do not store what you can compute; use a view such as v_order_totals from Lesson 6.2. If you truly must store it, update it in the same transaction as every change to the items. Undo the experiment:

ALTER TABLE orders DROP COLUMN total;
UPDATE order_items SET quantity = 2
WHERE order_id = 1 AND book_id = (SELECT id FROM books WHERE title = '1984');

🛠️ Step 4: Migrate the data (7 min)

Parents first, children last, joining on the natural identifiers to find the new ids:

🏋️ Exercise 1: Name the Violations

A school keeps this table, with key (student_id, course): student_id, student_name, course, course_room, grade, advisor_name, advisor_office. Each student has one advisor; each advisor has one office; each course meets in one room. List every functional dependency and say which normal form each one breaks.

💡 Hint

For each non-key column ask: does it need the whole key, part of the key, or another non-key column?

✅ Solution

(student_id, course) → grade is fine: the whole key. student_id → student_name, advisor_name and course → course_room depend on part of the key: 2NF violations. advisor_name → advisor_office is a non-key column determining another: a 3NF violation (transitive through student_id → advisor_name). Fix: students(id, name, advisor_id), advisors(id, name, office), courses(id, name, room), enrollments(student_id, course_id, grade).

🏋️ Exercise 2: Test a Dependency with Data

Using club_signups, write one query that checks whether member_email → member_name is contradicted by the data, and one that checks leader_email → club_name. What does each result mean?

💡 Hint

Group by the left side and count the distinct values of the right side; any group with more than one value is a counterexample.

✅ Solution 
SELECT member_email, COUNT(DISTINCT member_name) AS names
FROM club_signups
GROUP BY member_email
HAVING COUNT(DISTINCT member_name) > 1;

SELECT leader_email, COUNT(DISTINCT club_name) AS clubs
FROM club_signups
GROUP BY leader_email
HAVING COUNT(DISTINCT club_name) > 1;

Output

Empty set
+------------------------------+-------+
| leader_email                 | clubs |
+------------------------------+-------+
| priya.nair@bookstore.example |     2 |
+------------------------------+-------+

The first query finds no counterexample, which is consistent with the rule (but does not prove it). The second finds Priya leading two clubs, which proves leader_email → club_name is not a dependency, and is exactly why clubs points at leaders and not the other way around.

A supplier's invoices arrive as rows of invoice_no, invoice_date, vendor_name, vendor_city, items, amounts, where items and amounts are comma lists ("Paper, Ink" and "120.00, 45.50"). Design and create the 3NF tables in normalize_lab, with keys and foreign keys.

🏋️ Exercise 4 (Stretch): Design a Recipe Site

Requirements: users have a name, a unique email and a join date. A user submits recipes (title, prep minutes). A recipe has ingredients, each with a quantity and a unit ("2 cups flour"), and the same ingredient (flour) appears in many recipes. Recipes belong to one or more categories. Users can bookmark recipes. Sketch the ER diagram, then write the CREATE TABLE statements in normalize_lab.

💡 Hint

Look for every "many" at both ends: recipes and ingredients, recipes and categories, users and bookmarked recipes. Each needs a junction table, and the quantity belongs on the recipe-ingredient junction. Name the tables so they do not clash with this lesson's books and customers.

✅ Solution 
CREATE TABLE site_users (
    id         INT AUTO_INCREMENT PRIMARY KEY,
    name       VARCHAR(100) NOT NULL,
    email      VARCHAR(100) NOT NULL UNIQUE,
    joined_on  DATE NOT NULL DEFAULT (CURRENT_DATE)
);

CREATE TABLE recipes (
    id            INT AUTO_INCREMENT PRIMARY KEY,
    title         VARCHAR(200) NOT NULL,
    prep_minutes  INT,
    user_id       INT NOT NULL,
    CONSTRAINT fk_recipes_user FOREIGN KEY (user_id) REFERENCES site_users(id)
);

CREATE TABLE ingredients (
    id    INT AUTO_INCREMENT PRIMARY KEY,
    name  VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE recipe_ingredients (
    recipe_id      INT NOT NULL,
    ingredient_id  INT NOT NULL,
    quantity       DECIMAL(8, 2) NOT NULL,
    unit           VARCHAR(20) NOT NULL,
    PRIMARY KEY (recipe_id, ingredient_id),
    CONSTRAINT fk_ri_recipe FOREIGN KEY (recipe_id) REFERENCES recipes(id) ON DELETE CASCADE,
    CONSTRAINT fk_ri_ingredient FOREIGN KEY (ingredient_id) REFERENCES ingredients(id)
);

CREATE TABLE recipe_categories (
    id    INT AUTO_INCREMENT PRIMARY KEY,
    name  VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE recipe_in_category (
    recipe_id    INT NOT NULL,
    category_id  INT NOT NULL,
    PRIMARY KEY (recipe_id, category_id),
    CONSTRAINT fk_ric_recipe FOREIGN KEY (recipe_id) REFERENCES recipes(id) ON DELETE CASCADE,
    CONSTRAINT fk_ric_category FOREIGN KEY (category_id) REFERENCES recipe_categories(id)
);

CREATE TABLE bookmarks (
    user_id    INT NOT NULL,
    recipe_id  INT NOT NULL,
    saved_on   DATE NOT NULL DEFAULT (CURRENT_DATE),
    PRIMARY KEY (user_id, recipe_id),
    CONSTRAINT fk_bookmarks_user FOREIGN KEY (user_id) REFERENCES site_users(id),
    CONSTRAINT fk_bookmarks_recipe FOREIGN KEY (recipe_id) REFERENCES recipes(id) ON DELETE CASCADE
);

SELECT TABLE_NAME, COUNT(*) AS foreign_keys
FROM information_schema.REFERENTIAL_CONSTRAINTS
WHERE CONSTRAINT_SCHEMA = 'normalize_lab'
  AND TABLE_NAME IN ('recipes', 'recipe_ingredients', 'recipe_in_category', 'bookmarks')
GROUP BY TABLE_NAME
ORDER BY TABLE_NAME;

Output

+--------------------+--------------+
| TABLE_NAME         | foreign_keys |
+--------------------+--------------+
| bookmarks          |            2 |
| recipe_in_category |            2 |
| recipe_ingredients |            2 |
| recipes            |            1 |
+--------------------+--------------+

Three junction tables, each with a composite primary key, carry the three many-to-many relationships; the quantity and unit live on recipe_ingredients, because they depend on the pair (this ingredient in this recipe). ❓ Common Questions at This Stage

Are there normal forms beyond 3NF?

Yes: Boyce-Codd normal form (BCNF) tightens 3NF for tables with several overlapping candidate keys, and 4NF and 5NF deal with independent multi-valued facts stored in one table. A careful 3NF design is in BCNF almost every time, and the higher forms rarely come up in everyday business databases. Learn 3NF thoroughly first; it does nearly all the work.

Should I use surrogate keys (id) or natural keys (email)?

This course uses AUTO_INCREMENT ids as primary keys and puts UNIQUE on natural identifiers. Natural values change (people change emails) and are often long; an id never needs to change, so foreign keys stay stable. Junction tables are the exception: their natural composite key, such as (member_id, club_id), is the perfect primary key.

Is a JSON column a 1NF violation?

A JSON column holding a list is, in spirit, a list in a cell: you lose foreign keys and simple joins on its contents. That is fine for data you only store and display (a book's optional attributes), and wrong for data you join, sum or constrain (order lines). Lesson 7.3 shows where JSON columns fit.

Is normalization bad for performance?

Rarely, at the sizes most applications reach. Joins on indexed keys are what relational databases are built for, and a normalized design writes less data and keeps indexes small. Measure before you denormalize, as Lesson 6.1 showed.

📝 Lesson Summary

🎓 Key Takeaways

  • Storing facts about different things in one table causes update, insert and delete anomalies
  • A functional dependency A → B is a business rule: same A, same B; data can disprove one but never prove it
  • 1NF: one value per cell and a key. 2NF: no dependency on part of the key. 3NF: no dependency on a non-key column
  • "The key, the whole key, and nothing but the key"
  • Migrate with INSERT ... SELECT DISTINCT, parents first; prove the split with EXCEPT in both directions
  • ER diagrams show tables and relationship counts; many-to-many always means a junction table
  • Do not store what you can compute; denormalize only for a measured problem, with a plan to keep copies in sync
You seeIt breaksDo this
Lists or col1, col2, col3 columns1NFOne row per item, in a child table
A column that needs only part of a composite key2NFMove it to the table of that part
A column that describes another non-key column3NFGive that thing its own table and a foreign key
"Many" at both ends of a relationship(a missing table)A junction table with a composite primary key
A stored value you could compute(a drift risk)Compute it, or use a view
