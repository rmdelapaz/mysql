🔧 Lesson 7.1: Stored Procedures & Functions

Until now every query has lived in your head or in a .sql file. When an app needs the same ten-line query in five places, someone copies it five times, and sooner or later the copies drift apart. Stored procedures and stored functions let you save that logic inside the database, give it a name and parameters, and call it from anywhere. This lesson shows how to write them, and when not to.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Explain what the DELIMITER client command does, and when you do not need it
  • Create and call stored procedures with IN, OUT and INOUT parameters
  • Write stored functions with the right characteristic (DETERMINISTIC, READS SQL DATA) and use them inside queries
  • Use local variables, IF, CASE and WHILE in a routine, and reject bad input with SIGNAL
  • List, inspect, replace and drop routines, and read the errors MySQL raises for broken ones (1064, 1418, 1172, 1304, 1644)
  • ⏱️ Time 105 minutes
  • 📋 Prerequisites Lesson 6.3: Database Design & Normalization
  • 🛠️ You will build bookstore_routines.sql: two functions and two procedures the bookstore's app can call
  • 🗄️ Database bookstore, freshly loaded from bookstore.sql

🧩 Why Stored Routines?

A stored routine is a named block of SQL saved in a database, next to its tables. MySQL has two kinds:

  • A stored procedure is run with CALL name(...). It can return result sets, hand values back through OUT parameters, and change data.
  • A stored function returns exactly one value and is used inside an expression, like a built-in function: SELECT title, with_tax(price) FROM books.
graph TD A["App or mysql client"] -->|"CALL customer_report(1)"| B["Stored procedure"] B --> C["JOINs, checks, updates"] C --> D["Tables in bookstore"] B -->|"result sets"| A

What they buy you:

  • One copy of the logic. The PHP site, the Python report and the admin at the mysql> prompt all call the same routine.
  • Fewer round trips. One CALL can run ten statements on the server instead of ten requests over the network.
  • A narrow door. You can let an account run a procedure (the EXECUTE privilege, Lesson 7.4) without letting it read or change the tables directly.

And what they cost: the logic is now in two places (app and database), it needs its own version control, and MySQL's routine language is small and old-fashioned compared to Python or JavaScript. The last section of the lesson helps you decide.

💡 Follow along

Every output in this lesson comes from a fresh copy of the bookstore. Reload it now, with the path to your download (on Windows, use forward slashes, for example SOURCE C:/Users/you/mysql-course/bookstore.sql):

SOURCE ~/mysql-course/bookstore.sql

It prints a row count for every table and leaves you in the bookstore database: 11 books, 8 customers, 12 orders.

✂️ DELIMITER: A Client Command

A procedure body holds several statements, each ending in ;. That is a problem for the mysql command-line client: it reads your typing, and every time it sees a ; it sends what it has collected to the server. It would send the first half of your procedure and the server would answer with a syntax error.

The fix is DELIMITER. It tells the client (not the server) to wait for a different end marker for a while:

DELIMITER //

CREATE PROCEDURE say_hello()
BEGIN
    SELECT 'Hello from the bookstore!' AS greeting;
    SELECT COUNT(*) AS books_in_stock FROM books WHERE in_stock = TRUE;
END //

DELIMITER ;

Read it as three steps. DELIMITER //: "from now on, a statement ends at //". Then the whole CREATE PROCEDURE ... END, semicolons and all, goes to the server as one statement when the client reaches //. Finally DELIMITER ; switches back. Now run it:

CALL say_hello();

Output

+---------------------------+
| greeting                  |
+---------------------------+
| Hello from the bookstore! |
+---------------------------+
+----------------+
| books_in_stock |
+----------------+
|              9 |
+----------------+

A procedure may return several result sets: each SELECT in the body that is not stored into a variable sends one back to the caller.

graph TD A["You type the CREATE"] --> B["mysql client"] B -->|"DELIMITER // : wait for //"| C["One whole statement"] C --> D["MySQL server"] D --> E["Procedure saved"]

🔑 Who needs DELIMITER?

Only tools that split your text at semicolons: the mysql client, SOURCE and mysql < file.sql. The server never sees the word DELIMITER, so you do not write it when an app sends CREATE PROCEDURE through a driver (PHP's PDO, Python's connector), or in MySQL Workbench, which understands DELIMITER lines in its SQL editor. phpMyAdmin's SQL tab has a Delimiter box under the query area; set it to // there instead of typing the command. // and $$ are both popular; pick one and use it everywhere.

⚠️ Always switch back

If you forget DELIMITER ;, your next ordinary query just sits there: the client prints -> and waits for //. Type // to send it, then DELIMITER ;. In this course every example that changes the delimiter changes it back in the same block, so you can copy any block on its own.

One shortcut: a routine whose body is a single statement needs no BEGIN ... END and no delimiter change at all, because the only ; is the one at the very end:

CREATE PROCEDURE count_customers()
    SELECT COUNT(*) AS customers FROM customers;

CALL count_customers();

Output

+-----------+
| customers |
+-----------+
|         8 |
+-----------+

📦 Your First Stored Procedure

The general shape, with placeholders (not runnable as written):

DELIMITER //
CREATE PROCEDURE procedure_name(parameter_list)
BEGIN
    statements;
END //
DELIMITER ;

Here is a real one. The bookstore's website needs "every book with its author" on several pages. Instead of repeating the join in each page's code, wrap it:

DELIMITER //
CREATE PROCEDURE list_books()
BEGIN
    SELECT b.id, b.title, a.name AS author, b.price
    FROM books AS b
    JOIN authors AS a ON a.id = b.author_id
    ORDER BY b.title;
END //
DELIMITER ;

CALL list_books();

Output

+----+------------------------+---------------------+-------+
| id | title                  | author              | price |
+----+------------------------+---------------------+-------+
|  2 | 1984                   | George Orwell       |  9.99 |
| 11 | Animal Farm            | George Orwell       |  8.49 |
|  7 | Brave New World        | Aldous Huxley       |  9.49 |
|  1 | Dune                   | Frank Herbert       | 14.99 |
| 10 | Fahrenheit 451         | Ray Bradbury        | 10.49 |
|  9 | Lord of the Rings      | J.R.R. Tolkien      | 15.99 |
|  5 | Pride and Prejudice    | Jane Austen         |  7.99 |
|  8 | The Catcher in the Rye | J.D. Salinger       |  8.99 |
|  4 | The Great Gatsby       | F. Scott Fitzgerald |  8.99 |
|  6 | The Hobbit             | J.R.R. Tolkien      | 10.99 |
|  3 | To Kill a Mockingbird  | Harper Lee          | 11.99 |
+----+------------------------+---------------------+-------+

The caller does not need to know that books and authors live in separate tables. If you later rename a column, you fix one procedure, not every page. The empty parentheses are required, both when you create it and when you call it (MySQL also accepts CALL list_books;, but the parentheses make it obvious that it is a call).

💡 A procedure belongs to a database

list_books was created in bookstore because that was the current database. From another database you would call it as CALL bookstore.list_books();. Dropping the database drops its routines too, so reloading bookstore.sql wipes everything you create in this lesson. Keep your routines in a script file (the project does exactly that).

🎛️ Parameters: IN, OUT, INOUT

Parameters make a procedure flexible. Each one has a direction:

ModeDirectionUse it for
IN (the default)caller to procedureInputs: an id, a name, a price
OUTprocedure to callerAnswers: a count, a total, a status message
INOUTboth waysA value the procedure reads and then replaces

IN: passing a value in

DELIMITER //
CREATE PROCEDURE books_by_author(IN p_author VARCHAR(100))
BEGIN
    SELECT b.title, b.price
    FROM books AS b
    JOIN authors AS a ON a.id = b.author_id
    WHERE a.name = p_author
    ORDER BY b.title;
END //
DELIMITER ;

CALL books_by_author('George Orwell');

Output

+-------------+-------+
| title       | price |
+-------------+-------+
| 1984        |  9.99 |
| Animal Farm |  8.49 |
+-------------+-------+

The p_ prefix marks p_author as a parameter. It is a convention, not a rule, but Common Mistake 3 shows the silent bug it prevents.

OUT: handing a value back

An OUT parameter needs somewhere to land on the caller's side. At the mysql> prompt that is a user variable: a name starting with @ that lives until you disconnect.

DELIMITER //
CREATE PROCEDURE count_books_by(IN p_author VARCHAR(100), OUT p_count INT)
BEGIN
    SELECT COUNT(*) INTO p_count
    FROM books AS b
    JOIN authors AS a ON a.id = b.author_id
    WHERE a.name = p_author;
END //
DELIMITER ;

CALL count_books_by('J.R.R. Tolkien', @tolkien_books);
SELECT @tolkien_books AS tolkien_books;

Output

+---------------+
| tolkien_books |
+---------------+
|             2 |
+---------------+

SELECT ... INTO stores the query's values in variables instead of sending a result set, which is why the CALL itself prints nothing. The query must return at most one row (Common Mistake 4).

INOUT: change a value in place

DELIMITER //
CREATE PROCEDURE apply_discount(INOUT p_price DECIMAL(8, 2), IN p_percent INT)
BEGIN
    SET p_price = ROUND(p_price * (100 - p_percent) / 100, 2);
END //
DELIMITER ;

SET @price = 14.99;
CALL apply_discount(@price, 20);
SELECT @price AS price_after_20_percent_off;

Output

+----------------------------+
| price_after_20_percent_off |
+----------------------------+
|                      11.99 |
+----------------------------+

Several outputs at once

A procedure can fill as many OUT parameters as you like. This one summarizes a customer. It totals quantity * price_at_time, the price the customer actually paid, rather than today's books.price (equal in our data, but prices change).

DELIMITER //
CREATE PROCEDURE customer_stats(
    IN  p_customer_id INT,
    OUT p_orders      INT,
    OUT p_spent       DECIMAL(10, 2)
)
BEGIN
    SELECT COUNT(DISTINCT o.id),
           COALESCE(SUM(oi.quantity * oi.price_at_time), 0)
    INTO p_orders, p_spent
    FROM orders AS o
    JOIN order_items AS oi ON oi.order_id = o.id
    WHERE o.customer_id = p_customer_id;
END //
DELIMITER ;

CALL customer_stats(1, @orders, @spent);
SELECT @orders AS alice_orders, @spent AS alice_spent;

Output

+--------------+-------------+
| alice_orders | alice_spent |
+--------------+-------------+
|            3 |       58.95 |
+--------------+-------------+

Alice placed three orders worth $58.95 in total. Try CALL customer_stats(3, @orders, @spent); for Carol, who never ordered: the COALESCE turns her missing total into 0.00.

📥 Local Variables

Inside BEGIN ... END you can declare local variables for intermediate results. They exist only while the routine runs.

DELIMITER //
CREATE PROCEDURE order_receipt(IN p_order_id INT)
BEGIN
    DECLARE v_subtotal DECIMAL(10, 2) DEFAULT 0;
    DECLARE v_tax_rate DECIMAL(4, 3) DEFAULT 0.080;
    DECLARE v_tax      DECIMAL(10, 2);

    SELECT COALESCE(SUM(quantity * price_at_time), 0) INTO v_subtotal
    FROM order_items
    WHERE order_id = p_order_id;

    SET v_tax = ROUND(v_subtotal * v_tax_rate, 2);

    SELECT p_order_id         AS order_id,
           v_subtotal         AS subtotal,
           v_tax              AS tax,
           v_subtotal + v_tax AS total;
END //
DELIMITER ;

CALL order_receipt(1);

Output

+----------+----------+------+-------+
| order_id | subtotal | tax  | total |
+----------+----------+------+-------+
|        1 |    34.97 | 2.80 | 37.77 |
+----------+----------+------+-------+

Order 1 is one copy of Dune (14.99) and two of 1984 (2 x 9.99), so 34.97 before an 8% tax.

KindWrittenLives
Local variableDECLARE v_total DECIMAL(10,2); then SET v_total = ...Inside one BEGIN ... END, during one call
ParameterIN p_id INT in the headerDuring one call
User variable@total, no declarationYour whole connection, until you disconnect

DECLARE lines must come first in a BEGIN ... END block, before any other statement. Use local variables inside routines and user variables only to talk to the routine from the prompt.

🔀 Control Flow: IF, CASE, WHILE

Routines can make decisions and repeat work. These statements exist only inside stored programs; you cannot type an IF ... END IF at the prompt.

IF ... ELSEIF ... ELSE

The bookstore rewards its customers by how much they have spent: Gold from $50, Silver from $30, Bronze for anything above zero, and New for customers who have not ordered yet.

DELIMITER //
CREATE PROCEDURE classify_customer(IN p_customer_id INT, OUT p_tier VARCHAR(10))
BEGIN
    DECLARE v_spent DECIMAL(10, 2);

    SELECT COALESCE(SUM(oi.quantity * oi.price_at_time), 0) INTO v_spent
    FROM orders AS o
    JOIN order_items AS oi ON oi.order_id = o.id
    WHERE o.customer_id = p_customer_id;

    IF v_spent >= 50 THEN
        SET p_tier = 'Gold';
    ELSEIF v_spent >= 30 THEN
        SET p_tier = 'Silver';
    ELSEIF v_spent > 0 THEN
        SET p_tier = 'Bronze';
    ELSE
        SET p_tier = 'New';
    END IF;
END //
DELIMITER ;

CALL classify_customer(1, @alice);
CALL classify_customer(2, @bob);
CALL classify_customer(3, @carol);
SELECT @alice AS alice, @bob AS bob, @carol AS carol;

Output

+-------+--------+-------+
| alice | bob    | carol |
+-------+--------+-------+
| Gold  | Silver | New   |
+-------+--------+-------+

The IF statement here is not the same thing as the IF(condition, a, b) function from Lesson 3.3: the statement runs whole statements, ends with END IF;, and only works inside routines.

CASE

The CASE statement picks one branch, like a chain of ELSEIFs. Unlike the CASE expression you used in SELECT, it raises an error when no branch matches and there is no ELSE, so always write one:

DELIMITER //
CREATE PROCEDURE shelf_for(IN p_book_id INT, OUT p_shelf VARCHAR(20))
BEGIN
    DECLARE v_pages INT;
    SELECT pages INTO v_pages FROM books WHERE id = p_book_id;

    CASE
        WHEN v_pages >= 500 THEN SET p_shelf = 'Doorstoppers';
        WHEN v_pages >= 250 THEN SET p_shelf = 'Novels';
        ELSE SET p_shelf = 'Quick reads';
    END CASE;
END //
DELIMITER ;

CALL shelf_for(9, @lotr);
CALL shelf_for(10, @f451);
SELECT @lotr AS lord_of_the_rings, @f451 AS fahrenheit_451;

Output

+-------------------+----------------+
| lord_of_the_rings | fahrenheit_451 |
+-------------------+----------------+
| Doorstoppers      | Quick reads    |
+-------------------+----------------+

WHILE loops

A loop repeats statements while a condition holds. This procedure plans how to read a book at a fixed number of pages per day and stores the plan in a temporary table, which only your connection can see and which disappears when you disconnect:

DELIMITER //
CREATE PROCEDURE reading_plan(IN p_book_id INT, IN p_pages_per_day INT)
BEGIN
    DECLARE v_pages INT;
    DECLARE v_day   INT DEFAULT 1;
    DECLARE v_done  INT DEFAULT 0;

    SELECT pages INTO v_pages FROM books WHERE id = p_book_id;

    DROP TEMPORARY TABLE IF EXISTS plan;
    CREATE TEMPORARY TABLE plan (day INT, from_page INT, to_page INT);

    WHILE v_done < v_pages DO
        INSERT INTO plan VALUES (v_day, v_done + 1, LEAST(v_done + p_pages_per_day, v_pages));
        SET v_done = v_done + p_pages_per_day;
        SET v_day = v_day + 1;
    END WHILE;

    SELECT * FROM plan ORDER BY day;
END //
DELIMITER ;

CALL reading_plan(10, 40);

Output

+------+-----------+---------+
| day  | from_page | to_page |
+------+-----------+---------+
|    1 |         1 |      40 |
|    2 |        41 |      80 |
|    3 |        81 |     120 |
|    4 |       121 |     158 |
+------+-----------+---------+

Fahrenheit 451 has 158 pages, so the fourth day is a short one. LEAST() keeps the last range from running past the end of the book.

MySQL also has REPEAT ... UNTIL ... END REPEAT (the body runs at least once) and a bare label: LOOP ... END LOOP that you leave with LEAVE label. ITERATE label skips to the next round, like continue in other languages.

⚠️ Prefer one query to a loop

SQL is built to work on whole sets of rows at once. A loop that handles one row per round is usually far slower than a single INSERT ... SELECT or UPDATE. The reading plan above could be one recursive CTE from Lesson 5.1. Reach for a loop when the steps really depend on each other, not out of habit from other languages.

🧮 Stored Functions

A stored function returns one value through RETURN, and you use it wherever an expression fits: in SELECT, WHERE, ORDER BY, even inside another function. Function parameters are always input, so you write no IN.

DELIMITER //
CREATE FUNCTION with_tax(p_amount DECIMAL(10, 2))
RETURNS DECIMAL(10, 2)
DETERMINISTIC
NO SQL
BEGIN
    RETURN ROUND(p_amount * 1.08, 2);
END //
DELIMITER ;

SELECT title, price, with_tax(price) AS price_with_tax
FROM books
WHERE price >= 11
ORDER BY price DESC;

Output

+-----------------------+-------+----------------+
| title                 | price | price_with_tax |
+-----------------------+-------+----------------+
| Lord of the Rings     | 15.99 |          17.27 |
| Dune                  | 14.99 |          16.19 |
| To Kill a Mockingbird | 11.99 |          12.95 |
+-----------------------+-------+----------------+

The characteristics line, and why MySQL insists on it

Between RETURNS and BEGIN you describe the function to the server:

CharacteristicPromiseExample
DETERMINISTICThe same inputs always give the same resultwith_tax(10.00) is always 10.80
NOT DETERMINISTIC (default)The result can change between callsAnything using NOW(), RAND() or table data that changes
NO SQLThe body runs no SQL statements on tablesPure arithmetic or string work
READS SQL DATAThe body reads tables but never changes themA total computed with SELECT ... INTO
MODIFIES SQL DATAThe body changes tablesRare in functions; use a procedure

Why it matters: MySQL 8.0 and later turn on the binary log by default. It records every change so the server can be copied to replicas and restored to a point in time. A function the server knows nothing about could produce different results when a replica replays it, so with binary logging on, MySQL refuses to create a function unless it declares at least one of DETERMINISTIC, NO SQL or READS SQL DATA (error 1418, Common Mistake 2). The server cannot check your promise, so make it true: a function that reads tables whose rows change is READS SQL DATA, not DETERMINISTIC.

A function that reads data

DELIMITER //
CREATE FUNCTION author_revenue(p_author_id INT)
RETURNS DECIMAL(10, 2)
READS SQL DATA
BEGIN
    DECLARE v_revenue DECIMAL(10, 2);

    SELECT COALESCE(SUM(oi.quantity * oi.price_at_time), 0) INTO v_revenue
    FROM order_items AS oi
    JOIN books AS b ON b.id = oi.book_id
    WHERE b.author_id = p_author_id;

    RETURN v_revenue;
END //
DELIMITER ;

SELECT name, author_revenue(id) AS revenue
FROM authors
ORDER BY revenue DESC, name;

Output

+---------------------+---------+
| name                | revenue |
+---------------------+---------+
| J.R.R. Tolkien      |   64.95 |
| George Orwell       |   56.94 |
| Frank Herbert       |   44.97 |
| Harper Lee          |   23.98 |
| Ray Bradbury        |   20.98 |
| Jane Austen         |   15.98 |
| Aldous Huxley       |    9.49 |
| F. Scott Fitzgerald |    0.00 |
| Isaac Asimov        |    0.00 |
| J.D. Salinger       |    0.00 |
+---------------------+---------+

Isaac Asimov has no books, and Fitzgerald and Salinger have books nobody ordered, so their revenue is 0.00 instead of NULL thanks to COALESCE.

⚠️ A function in SELECT runs once per row

author_revenue(id) runs its own query for each of the 10 authors. On ten rows nobody notices; on a million it is a million small queries. For big reports a single JOIN ... GROUP BY (Lessons 3.3 and 4.3) is the faster tool. Functions shine for small, reusable calculations.

🚦 Rejecting Bad Input with SIGNAL

A procedure that changes data should check its inputs first. SIGNAL raises your own error, which stops the procedure and reaches the caller like any MySQL error. SQLSTATE '45000' means "unhandled user-defined exception"; MySQL reports it as error 1644.

DELIMITER //
CREATE PROCEDURE set_book_price(IN p_book_id INT, IN p_price DECIMAL(8, 2))
BEGIN
    IF p_price IS NULL OR p_price <= 0 THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Price must be greater than zero';
    END IF;

    IF NOT EXISTS (SELECT 1 FROM books WHERE id = p_book_id) THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'No book with that id';
    END IF;

    UPDATE books SET price = p_price WHERE id = p_book_id;
END //
DELIMITER ;
CALL set_book_price(5, -1.00);

Error

ERROR 1644 (45000): Price must be greater than zero
CALL set_book_price(99, 9.99);

Error

ERROR 1644 (45000): No book with that id

Both checks run before the UPDATE, so a refused call changes nothing. (Checking ROW_COUNT() after the UPDATE is a tempting shortcut, but it counts rows changed: setting a book to the price it already has would count 0 and wrongly report a missing book.) A call with good input goes through:

CALL set_book_price(5, 8.49);
SELECT id, title, price FROM books WHERE id = 5;
CALL set_book_price(5, 7.99);

Output

+----+---------------------+-------+
| id | title               | price |
+----+---------------------+-------+
|  5 | Pride and Prejudice |  8.49 |
+----+---------------------+-------+

The last line puts the original price back, so the rest of the lesson matches the download.

💡 Errors and transactions come next

SIGNAL stops the procedure, but statements that already ran are not undone by it. When a procedure makes several changes that must succeed or fail together, you need a transaction and an error handler (DECLARE ... HANDLER). That is the heart of Lesson 7.2.

🗃️ Managing Routines

List them

SHOW PROCEDURE STATUS WHERE Db = 'bookstore'; and SHOW FUNCTION STATUS ... work, but print eleven wide columns. The information_schema.ROUTINES table lets you pick the columns you care about:

SELECT ROUTINE_NAME, ROUTINE_TYPE, IS_DETERMINISTIC, SQL_DATA_ACCESS
FROM information_schema.ROUTINES
WHERE ROUTINE_SCHEMA = 'bookstore'
ORDER BY ROUTINE_TYPE, ROUTINE_NAME;

Output

+-------------------+--------------+------------------+-----------------+
| ROUTINE_NAME      | ROUTINE_TYPE | IS_DETERMINISTIC | SQL_DATA_ACCESS |
+-------------------+--------------+------------------+-----------------+
| author_revenue    | FUNCTION     | NO               | READS SQL DATA  |
| with_tax          | FUNCTION     | YES              | NO SQL          |
| apply_discount    | PROCEDURE    | NO               | CONTAINS SQL    |
| books_by_author   | PROCEDURE    | NO               | CONTAINS SQL    |
| classify_customer | PROCEDURE    | NO               | CONTAINS SQL    |
| count_books_by    | PROCEDURE    | NO               | CONTAINS SQL    |
| count_customers   | PROCEDURE    | NO               | CONTAINS SQL    |
| customer_stats    | PROCEDURE    | NO               | CONTAINS SQL    |
| list_books        | PROCEDURE    | NO               | CONTAINS SQL    |
| order_receipt     | PROCEDURE    | NO               | CONTAINS SQL    |
| reading_plan      | PROCEDURE    | NO               | CONTAINS SQL    |
| say_hello         | PROCEDURE    | NO               | CONTAINS SQL    |
| set_book_price    | PROCEDURE    | NO               | CONTAINS SQL    |
| shelf_for         | PROCEDURE    | NO               | CONTAINS SQL    |
+-------------------+--------------+------------------+-----------------+

Procedures say CONTAINS SQL unless you declare otherwise: the characteristics are optional for procedures, because the binary log records the statements a procedure runs, not the CALL.

Read one back

SHOW CREATE FUNCTION with_tax\G

Output (the character set lines can differ on your machine)

            Function: with_tax
            sql_mode: ONLY_FULL_GROUP_BY,STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION
     Create Function: CREATE DEFINER=`root`@`localhost` FUNCTION `with_tax`(p_amount DECIMAL(10, 2)) RETURNS decimal(10,2)

MySQL saved the sql_mode that was active when you created the function, and runs the function under it. It also added DEFINER=`root`@`localhost`: the account that owns the routine. By default a routine runs with its definer's privileges (SQL SECURITY DEFINER), which is what makes the "narrow door" from the start of the lesson work. Lesson 7.4 introduces the EXECUTE privilege, and in Lesson 8.2 you grant it to an app account.

Change or remove one

ALTER PROCEDURE only changes characteristics such as the comment; it cannot change the body. To change the body, drop the routine and create it again:

DROP PROCEDURE IF EXISTS say_hello;

DELIMITER //
CREATE PROCEDURE say_hello()
BEGIN
    SELECT CONCAT('Hello! We stock ', COUNT(*), ' titles.') AS greeting FROM books;
END //
DELIMITER ;

CALL say_hello();

Output

+----------------------------+
| greeting                   |
+----------------------------+
| Hello! We stock 11 titles. |
+----------------------------+

DROP FUNCTION IF EXISTS name; works the same way. IF EXISTS turns "it is not there" into a warning instead of an error, so a script can run twice.

🐬 Version note

MySQL (9.7 and 8.4) has no CREATE OR REPLACE PROCEDURE; it answers with error 1064. It does have CREATE PROCEDURE IF NOT EXISTS and CREATE FUNCTION IF NOT EXISTS, which skip the statement when the routine is already there. MariaDB supports CREATE OR REPLACE as well. "Drop, then create" works on all three, so that is the pattern this course uses.

✅ Good jobs for routines

  • A business rule several programs share: tax, discounts, loyalty tiers
  • A multi-step change that must happen on the server, close to the data (an order, a transfer)
  • Admin chores: archiving old rows, cleaning up test data
  • A security boundary: the app may CALL place_order but not UPDATE books

⚠️ Better in the app

  • Rules that change every week: shipping an app update is usually easier than migrating routines
  • Heavy text processing, sending email, calling web APIs: the database cannot or should not
  • Logic your team cannot read or test: a routine nobody understands becomes a trap

Whichever you choose, when an app passes user input to the database (including to CALL), it uses parameterized queries (placeholders such as CALL place_order(?, ?, ?)), never strings glued together. A procedure does not make string-built SQL safe.

⚠️ Common Mistakes

1. Forgetting DELIMITER in the mysql client

CREATE PROCEDURE out_of_stock()
BEGIN
    SELECT title FROM books WHERE in_stock = FALSE;
END;

Error

ERROR 1064 (42000): You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near '' at line 3
ERROR 1064 (42000): You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near 'END' at line 1

What it means: the client sent everything up to the first ;, an unfinished CREATE PROCEDURE ... BEGIN SELECT ..., and the server reported a syntax error at the end of it (near ''). Then it sent the leftover END as a statement of its own, which is a second 1064. Fix: wrap the definition in DELIMITER // ... END // ... DELIMITER ;, or, for a one-statement body, leave out BEGIN and END.

2. A function without its characteristics

CREATE FUNCTION book_count()
RETURNS INT
RETURN (SELECT COUNT(*) FROM books);

Error

ERROR 1418 (HY000): This function has none of DETERMINISTIC, NO SQL, or READS SQL DATA in its declaration and binary logging is enabled (you *might* want to use the less safe log_bin_trust_function_creators variable)

What it means: binary logging is on (the default since MySQL 8.0) and the function does not say what it does. Fix: add the true characteristic, here READS SQL DATA after RETURNS INT. The message mentions log_bin_trust_function_creators; turning that server setting on silences the check for everyone, which is why the manual calls it "less safe". Leave it off and declare your functions properly.

On a MariaDB install (XAMPP, many shared hosts) the binary log is usually off, so the same statement succeeds there, and fails later when someone turns on replication:

CREATE FUNCTION book_count()
RETURNS INT
RETURN (SELECT COUNT(*) FROM books);

SELECT book_count() AS books;

Output on MariaDB

+-------+
| books |
+-------+
|    11 |
+-------+

3. A parameter with the same name as a column (silent)

CREATE PROCEDURE book_by_id(IN id INT)
    SELECT b.id, b.title FROM books AS b WHERE id = id ORDER BY b.id;

CALL book_by_id(1);

Output

+----+------------------------+
| id | title                  |
+----+------------------------+
|  1 | Dune                   |
|  2 | 1984                   |
|  3 | To Kill a Mockingbird  |
|  4 | The Great Gatsby       |
|  5 | Pride and Prejudice    |
|  6 | The Hobbit             |
|  7 | Brave New World        |
|  8 | The Catcher in the Rye |
|  9 | Lord of the Rings      |
| 10 | Fahrenheit 451         |
| 11 | Animal Farm            |
+----+------------------------+

What it means: you asked for book 1 and got all eleven. Inside the routine, a bare id means the parameter, not the column, so WHERE id = id compares 1 with 1 on every row, which is always true. (The SELECT list says b.id, so it shows the real column; a bare id there would print 1 eleven times.) No error, no warning. Picture the same mistake in an UPDATE or DELETE. Fix: give parameters and variables a prefix that no column uses (p_id, v_total), or qualify columns with the table alias (b.id).

4. SELECT ... INTO that finds more than one row

DELIMITER //
CREATE PROCEDURE first_book_by(IN p_author_id INT, OUT p_title VARCHAR(200))
BEGIN
    SELECT title INTO p_title FROM books WHERE author_id = p_author_id;
END //
DELIMITER ;

CALL first_book_by(2, @title);

Error

ERROR 1172 (42000): Result consisted of more than one row

What it means: George Orwell (author 2) has two books, and one variable cannot hold two titles. The procedure was created without complaint; the error only appears when a call hits the problem, which is why you test routines with awkward inputs. Fix: make the query return one row on purpose: ORDER BY published LIMIT 1, or an aggregate such as MIN(title). (If it finds no row, the variable keeps its old value and MySQL only warns, "No data - zero rows fetched".)

5. Creating a routine that already exists

CREATE PROCEDURE count_customers()
    SELECT COUNT(*) AS customers FROM customers;

Error

ERROR 1304 (42000): PROCEDURE count_customers already exists

What it means: you ran your script a second time. Fix: start every routine in a script with DROP PROCEDURE IF EXISTS name; (or DROP FUNCTION IF EXISTS name;), so the file can be rerun after every edit. The project below does this.

CREATE FUNCTION customer_tier(p_customer_id INT)
RETURNS VARCHAR(10)
READS SQL DATA
BEGIN
    DECLARE v_spent DECIMAL(10, 2);
    SELECT COALESCE(SUM(oi.quantity * oi.price_at_time), 0) INTO v_spent
    FROM orders AS o
    JOIN order_items AS oi ON oi.order_id = o.id

        WHEN v_spent >= 30 THEN 'Silver'
        WHEN v_spent > 0 THEN 'Bronze'
        ELSE 'New'
    END;
END //
DELIMITER ;

🛠️ Step 4: Adding a book safely (10 min)

The admin page needs "add this book by this author". The procedure checks the price, looks the author up by name, creates the author if needed, inserts the book, and hands back the new book's id.

DROP PROCEDURE IF EXISTS add_book;
DELIMITER //
CREATE PROCEDURE add_book(
    IN  p_title   VARCHAR(200),
    IN  p_author  VARCHAR(100),
    IN  p_price   DECIMAL(8, 2),
    OUT p_book_id INT
)
BEGIN
    DECLARE v_author_id INT;

    IF p_price IS NULL OR p_price <= 0 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Price must be greater than zero';
    END IF;

    SELECT MIN(id) INTO v_author_id FROM authors WHERE name = p_author;

    IF v_author_id IS NULL THEN
        INSERT INTO authors (name) VALUES (p_author);
        SET v_author_id = LAST_INSERT_ID();
    END IF;

    INSERT INTO books (title, author_id, price) VALUES (p_title, v_author_id, p_price);
    SET p_book_id = LAST_INSERT_ID();
END //
DELIMITER ;

CALL add_book('Foundation', 'Isaac Asimov', 9.99, @foundation);
CALL add_book('The Left Hand of Darkness', 'Ursula K. Le Guin', 10.99, @left_hand);

SELECT b.id, b.title, a.id AS author_id, a.name AS author, b.price
FROM books AS b
JOIN authors AS a ON a.id = b.author_id
WHERE b.id IN (@foundation, @left_hand)
ORDER BY b.id;

Output

+----+---------------------------+-----------+-------------------+-------+
| id | title                     | author_id | author            | price |
+----+---------------------------+-----------+-------------------+-------+
| 12 | Foundation                |        10 | Isaac Asimov      |  9.99 |
| 13 | The Left Hand of Darkness |        11 | Ursula K. Le Guin | 10.99 |
+----+---------------------------+-----------+-------------------+-------+

Asimov already existed (author 10), so Foundation reused him; Ursula K. Le Guin was new and got id 11. SELECT MIN(id) INTO always returns exactly one row (NULL when nobody matches), which avoids both error 1172 and the "no data" warning.

🏋️ Exercise 2: Sale Prices

Write a function sale_price(price, percent) that takes a percentage off and rounds to cents. Use it to show the three most expensive books at 15% off.

💡 Hint

The result depends only on the two inputs and reads no table, so the function is DETERMINISTIC and NO SQL. price * (100 - percent) / 100 avoids rounding percent / 100 too early.

✅ Solution 
DROP FUNCTION IF EXISTS sale_price;
DELIMITER //
CREATE FUNCTION sale_price(p_price DECIMAL(8, 2), p_percent INT)
RETURNS DECIMAL(8, 2)
DETERMINISTIC
NO SQL
BEGIN
    RETURN ROUND(p_price * (100 - p_percent) / 100, 2);
END //
DELIMITER ;

SELECT title, price, sale_price(price, 15) AS sale
FROM books
ORDER BY price DESC
LIMIT 3;

🏋️ Exercise 3: City Statistics

Write a procedure city_stats with one IN parameter (a city) and two OUT parameters: how many customers live there and how many orders they placed. Call it for Chicago and show both values.

💡 Hint

Two SELECT ... INTO statements are easiest: one counts customers, one counts orders joined to customers. Customers without orders must still count, so do not answer both with one inner join.

✅ Solution 
DROP PROCEDURE IF EXISTS city_stats;
DELIMITER //
CREATE PROCEDURE city_stats(IN p_city VARCHAR(50), OUT p_customers INT, OUT p_orders INT)
BEGIN
    SELECT COUNT(*) INTO p_customers
    FROM customers
    WHERE city = p_city;

    SELECT COUNT(*) INTO p_orders
    FROM orders AS o
    JOIN customers AS c ON c.id = o.customer_id
    WHERE c.city = p_city;
END //
DELIMITER ;

CALL city_stats('Chicago', @customers, @orders);
SELECT @customers AS chicago_customers, @orders AS chicago_orders;

| chicago_customers | chicago_orders |
+-------------------+----------------+
|                 2 |              4 |
+-------------------+----------------+

Bob and Grace live in Chicago and placed two orders each.

🏋️ Exercise 4 (Stretch): Chain of Command

Every employee has a manager_id pointing at another employee (NULL for the owner). Write a procedure chain_of_command(IN p_employee_id INT, OUT p_chain VARCHAR(500)) that walks up the managers with a WHILE loop and builds a string like Tom Becker > Priya Nair > .... Call it for Tom Becker (id 4).

💡 Hint

Keep a variable with the current employee id. In each round, read that employee's name and manager_id into variables, append the name, then move to the manager. Stop when the id becomes NULL.

✅ Solution 
DROP PROCEDURE IF EXISTS chain_of_command;
DELIMITER //
CREATE PROCEDURE chain_of_command(IN p_employee_id INT, OUT p_chain VARCHAR(500))
BEGIN
    DECLARE v_id      INT DEFAULT p_employee_id;
    DECLARE v_name    VARCHAR(101);
    DECLARE v_manager INT;

    SET p_chain = NULL;
    WHILE v_id IS NOT NULL DO
        SELECT CONCAT(first_name, ' ', last_name), manager_id
        INTO v_name, v_manager
        FROM employees
        WHERE id = v_id;

        SET p_chain = IF(p_chain IS NULL, v_name, CONCAT(p_chain, ' > ', v_name));
        SET v_id = v_manager;
    END WHILE;
END //
DELIMITER ;

CALL chain_of_command(4, @chain);
SELECT @chain AS chain;

Output

+-------------------------------------------------------+
| chain                                                 |
+-------------------------------------------------------+
| Tom Becker > Priya Nair > Daniel Reyes > Maria Santos |
+-------------------------------------------------------+

The loop runs four times and stops after Maria Santos, whose manager_id is NULL. A bad id would loop forever if v_manager kept an old value, which is a real risk with SELECT ... INTO and no matching row: a safer version sets v_manager = NULL at the top of each round. In Lesson 5.1 the same walk is a single recursive query.

❓ Common Questions at This Stage

Are stored procedures faster than sending the same queries from my app?

Sometimes, mostly because of fewer network round trips: one CALL instead of ten statements. MySQL does not keep a shared, precompiled plan for routines the way some databases do; it caches the parsed routine per connection. Do not move logic into the database for speed alone; measure first.

Can a function change data, or run a transaction?

A function may run INSERT or UPDATE (declared MODIFIES SQL DATA), but it cannot COMMIT, ROLLBACK or start a transaction, and it cannot return a result set. A function that changes data whenever a SELECT happens to call it is a surprise for everyone reading the query. Use a procedure.

How do I see the routines in phpMyAdmin or Workbench?

phpMyAdmin: select the database, open the Routines tab; it lists procedures and functions with Edit, Execute and Drop links. MySQL Workbench: expand the schema in the Navigator and open Stored Procedures or Functions. Both tools send the CREATE statement for you, so you do not type DELIMITER there.

Can I write routines in a language other than SQL?

In the MySQL Community Server you installed, no: routines are written in SQL. MySQL Enterprise Edition and the HeatWave cloud service can also run stored programs written in JavaScript. The SQL routines in this lesson work everywhere, including MariaDB.

🎓 Key Takeaways
