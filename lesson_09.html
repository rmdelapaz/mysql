📈 Lesson 3.3: Aggregate Functions & GROUP BY

So far every query has returned rows: this book, those customers. Many real questions want a single number instead: how many books do we stock, what do they cost on average, how many customers live in each city? Aggregate functions boil many rows down to one answer, and GROUP BY gives you one answer per group.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Summarize a table with COUNT, SUM, AVG, MIN and MAX, and predict how each one treats NULL
  • Produce one summary row per group with GROUP BY, sorted with ORDER BY
  • Keep or drop whole groups with HAVING, and explain when to use WHERE instead
  • Read and fix the errors MySQL raises for broken aggregate queries (1140, 1055, 1111)
  • Build a small inventory report as a reusable .sql script

🧮 What Are Aggregate Functions?

A plain SELECT returns one result row for every table row that matches. An aggregate function reads many rows and returns one value: a count, a total, an average, a smallest or a largest value. Think of a cashier's end-of-day slip: nobody reads every receipt, they read the totals at the bottom.

graph TD A["10 rows in books"] --> B["price column: 10 values"] B --> C["AVG(price)"] C --> D["one value: 10.99"]

MySQL has five aggregate functions you will use constantly:

FunctionReturnsBookstore question
COUNT()How many rows (or non-NULL values)How many books do we stock?
SUM()The total of the valuesWhat does one copy of every book cost?
AVG()The average (mean) of the valuesWhat is the average price?
MIN()The smallest valueWhat is the cheapest price?
MAX()The largest valueWhat is the newest publication date?

Open the mysql client (or phpMyAdmin's SQL tab) and run USE bookstore; first. Every query in this lesson reads the 10 books and 8 customers you loaded in Lesson 3.1. If you changed or deleted rows since then, run that lesson's reload block again and your results will match the ones shown here.

🔢 COUNT: Counting Rows

COUNT is the aggregate you will reach for most. It comes in three forms, and the difference between them matters.

COUNT(*): count every row

SELECT COUNT(*) AS total_books FROM books;

Output

+-------------+
| total_books |
+-------------+
|          10 |
+-------------+

The AS total_books alias gives the result column a readable name. Without it the column would be headed COUNT(*).

COUNT(column): count the values that are not NULL

SELECT
    COUNT(*)    AS customers,
    COUNT(city) AS customers_with_a_city
FROM customers;

Output

+-----------+-----------------------+
| customers | customers_with_a_city |
+-----------+-----------------------+
|         8 |                     6 |
+-----------+-----------------------+

Eight customers, but only six have a city: Eve and Hank have NULL there, and COUNT(city) skips them.

COUNT(DISTINCT column): count the different values

SELECT COUNT(DISTINCT author) AS authors FROM books;
SELECT COUNT(DISTINCT city) AS cities FROM customers;

Output

+---------+
| authors |
+---------+
|       9 |
+---------+
+--------+
| cities |
+--------+
|      4 |
+--------+

Ten books but nine authors, because J.R.R. Tolkien wrote two of them. Four cities, because New York and Chicago each appear twice and NULL is not a value to count. A block with two statements prints two result tables, one after the other.

Counting with a condition

Add a WHERE clause and COUNT only sees the rows that pass it:

SELECT COUNT(*) AS in_stock_books
FROM books
WHERE in_stock = TRUE;

Output

+----------------+
| in_stock_books |
+----------------+
|              8 |
+----------------+

➕ SUM and AVG: Totals and Averages

SUM adds the values in a column and AVG divides that total by the number of values. Both expect numbers.

SELECT
    SUM(price) AS one_of_each,
    SUM(pages) AS total_pages
FROM books;

Output

+-------------+-------------+
| one_of_each | total_pages |
+-------------+-------------+
|      109.90 |        3824 |
+-------------+-------------+
SELECT
    AVG(price)           AS avg_price,
    ROUND(AVG(price), 2) AS avg_price_rounded,
    AVG(pages)           AS avg_pages
FROM books;

Output

+-----------+-------------------+-----------+
| avg_price | avg_price_rounded | avg_pages |
+-----------+-------------------+-----------+
| 10.990000 |             10.99 |  382.4000 |
+-----------+-------------------+-----------+

💡 Why 10.990000?

price is DECIMAL(8, 2), exact to the cent. MySQL keeps AVG exact too, so it adds four extra decimal places to the result (and four places to the average of the whole-number pages column). Wrap the average in ROUND(value, 2) whenever you show money to a person.

↕️ MIN and MAX: Extremes

MIN and MAX work on any type that can be put in order: numbers, dates, and text (alphabetical order).

SELECT
    MIN(price)     AS cheapest,
    MAX(price)     AS priciest,
    MIN(published) AS oldest,
    MAX(published) AS newest
FROM books;

Output

+----------+----------+------------+------------+
| cheapest | priciest | oldest     | newest     |
+----------+----------+------------+------------+
|     7.99 |    15.99 | 1813-01-28 | 1965-08-01 |
+----------+----------+------------+------------+
SELECT
    MIN(title) AS first_title,
    MAX(title) AS last_title
FROM books;

Output

+-------------+-----------------------+
| first_title | last_title            |
+-------------+-----------------------+
| 1984        | To Kill a Mockingbird |
+-------------+-----------------------+

Digits sort before letters, so 1984 comes first alphabetically.

⚠️ MIN tells you the value, not the row

MIN(price) says the cheapest price is 7.99, but not which book costs that. To see the whole row, sort and take the first one, as you did in Lesson 3.2:

SELECT title, price
FROM books
ORDER BY price
LIMIT 1;

Output

+---------------------+-------+
| title               | price |
+---------------------+-------+
| Pride and Prejudice |  7.99 |
+---------------------+-------+

In Lesson 3.4 you will combine both ideas with a subquery: "show every book whose price equals the maximum".

🕳️ Aggregates and NULL

🔑 The NULL rule

Every aggregate function skips NULL values. The one exception is COUNT(*), which counts rows, not values.

The bookstore's prices and page counts have no gaps, so here is a tiny four-row table built on the spot with UNION ALL: four ratings, one of them missing. (You do not need to know UNION ALL yet; read it as "these four values, one per row".)

SELECT
    COUNT(*)                AS rows_counted,
    COUNT(rating)           AS ratings_given,
    AVG(rating)             AS avg_rating,
    AVG(COALESCE(rating, 0)) AS avg_if_missing_is_zero
FROM (
    SELECT 5 AS rating
    UNION ALL SELECT 3
    UNION ALL SELECT NULL
    UNION ALL SELECT 4
) AS ratings;

Output

+--------------+---------------+------------+------------------------+
| rows_counted | ratings_given | avg_rating | avg_if_missing_is_zero |
+--------------+---------------+------------+------------------------+
|            4 |             3 |     4.0000 |                 3.0000 |
+--------------+---------------+------------+------------------------+

AVG(rating) is (5 + 3 + 4) / 3 = 4: the missing rating is left out of both the total and the count. COALESCE(rating, 0) swaps each NULL for 0 first, so the average becomes 12 / 4 = 3. Which one is right depends on the question: "average of the ratings we have" or "average where no rating counts as zero".

Aggregates over no rows at all

When the WHERE clause matches nothing, COUNT still answers 0, but the other aggregates have no values to work with and return NULL:

SELECT
    COUNT(*)   AS books_over_100,
    SUM(price) AS their_total,
    MAX(price) AS their_top_price
FROM books
WHERE price > 100;

Output

+----------------+-------------+-----------------+
| books_over_100 | their_total | their_top_price |
+----------------+-------------+-----------------+
|              0 |        NULL |            NULL |
+----------------+-------------+-----------------+

A report that adds this total to something else would turn the whole sum into NULL. Use COALESCE(SUM(price), 0) when you need a 0 instead.

🗂️ GROUP BY: One Summary per Group

Without GROUP BY, an aggregate summarizes the whole table. With it, MySQL first sorts the rows into piles that share a value, then runs the aggregate once per pile and returns one row per pile.

graph TD A["books: 10 rows"] --> B["GROUP BY author"] B --> C["9 piles, one per author"] C --> D["COUNT(*) on each pile"] D --> E["9 result rows"]

Books per author

SELECT author, COUNT(*) AS book_count
FROM books
GROUP BY author
ORDER BY book_count DESC, author;

Output

+---------------------+------------+
| author              | book_count |
+---------------------+------------+
| J.R.R. Tolkien      |          2 |
| Aldous Huxley       |          1 |
| F. Scott Fitzgerald |          1 |
| Frank Herbert       |          1 |
| George Orwell       |          1 |
| Harper Lee          |          1 |
| J.D. Salinger       |          1 |
| Jane Austen         |          1 |
| Ray Bradbury        |          1 |
+---------------------+------------+

Every author lands in exactly one pile. Tolkien's pile holds two books, everyone else's holds one. The ORDER BY puts the biggest piles first and breaks ties alphabetically.

⚠️ GROUP BY does not sort

Older MySQL versions happened to return groups in sorted order. MySQL 8.0 and later (including 9.7 and 8.4) do not: groups come back in whatever order the server finds convenient. If the order matters, and in a report it always does, add ORDER BY. MariaDB still sorts groups, which is one more reason not to rely on it: the same query can come back in a different order on a different server.

Customers per city

SELECT city, COUNT(*) AS customers
FROM customers
WHERE city IS NOT NULL
GROUP BY city
ORDER BY customers DESC, city;

Output

+-------------+-----------+
| city        | customers |
+-------------+-----------+
| Chicago     |         2 |
| New York    |         2 |
| Houston     |         1 |
| Los Angeles |         1 |
+-------------+-----------+

Leave out the WHERE line and you get one more group: all the NULL cities land together in a single pile. You will use that in the project.

Several aggregates per group

SELECT
    in_stock,
    COUNT(*)             AS books,
    ROUND(AVG(price), 2) AS avg_price,
    MIN(price)           AS cheapest,
    MAX(price)           AS priciest
FROM books
GROUP BY in_stock
ORDER BY in_stock DESC;

Output

+----------+-------+-----------+----------+----------+
| in_stock | books | avg_price | cheapest | priciest |
+----------+-------+-----------+----------+----------+
|        1 |     8 |     11.49 |     7.99 |    15.99 |
|        0 |     2 |      8.99 |     8.99 |     8.99 |
+----------+-------+-----------+----------+----------+

in_stock is a BOOLEAN, which MySQL stores as 1 (true) and 0 (false). Two books are out of stock, and both happen to cost 8.99.

Grouping by an expression

You can group by a calculated value, not just a column. Here a CASE expression (an if/else for SQL) puts every book into a price band, and the bands become the groups:

SELECT
    CASE
        WHEN price < 10 THEN 'Under $10'
        WHEN price < 13 THEN '$10 to $12.99'
        ELSE '$13 and up'
    END AS price_band,
    COUNT(*)             AS books,
    ROUND(AVG(price), 2) AS avg_price
FROM books
GROUP BY price_band
ORDER BY MIN(price);

Output

+---------------+-------+-----------+
| price_band    | books | avg_price |
+---------------+-------+-----------+
| Under $10     |     5 |      9.09 |
| $10 to $12.99 |     3 |     11.16 |
| $13 and up    |     2 |     15.49 |
+---------------+-------+-----------+

Sorting by MIN(price) keeps the bands in price order. Sorting by the band's name would put "$10 to $12.99" first, because $1 sorts before $13 and U.

🔍 HAVING: Filtering Groups

WHERE decides which rows go into the piles. HAVING decides which piles make it into the result, after the aggregates have been calculated.

graph TD A["all rows"] -->|"WHERE keeps rows"| B["matching rows"] B -->|"GROUP BY"| C["groups"] C -->|"HAVING keeps groups"| D["result"] 
SELECT city, COUNT(*) AS customers
FROM customers
WHERE city IS NOT NULL
GROUP BY city
HAVING customers > 1
ORDER BY city;

Output

+----------+-----------+
| city     | customers |
+----------+-----------+
| Chicago  |         2 |
| New York |         2 |
+----------+-----------+

Houston and Los Angeles each have one customer, so their piles fail HAVING customers > 1 and disappear.

WHERE vs. HAVING

WHEREHAVING
FiltersIndividual rowsWhole groups
RunsBefore groupingAfter grouping
Can use COUNT(), AVG()...No (error 1111)Yes
Typical conditionprice > 10COUNT(*) > 1

Using both together

Which authors have in-stock books worth more than $10 on average?

SELECT author, ROUND(AVG(price), 2) AS avg_price
FROM books
WHERE in_stock = TRUE           -- 1. drop out-of-stock books
GROUP BY author                 -- 2. one pile per author
HAVING AVG(price) > 10          -- 3. keep piles averaging over $10
ORDER BY avg_price DESC;        -- 4. most expensive first

Output

+----------------+-----------+
| author         | avg_price |
+----------------+-----------+
| Frank Herbert  |     14.99 |
| J.R.R. Tolkien |     13.49 |
| Harper Lee     |     11.99 |
| Ray Bradbury   |     10.49 |
+----------------+-----------+

✅ Rule of thumb

If the condition is about a single row's column (price > 10), it goes in WHERE. If it is about a group's aggregate (COUNT(*) > 1, AVG(price) > 10), it goes in HAVING. Filtering in WHERE when you can is also faster: fewer rows reach the grouping step.

🧭 Clause Order: Written vs. Run

You must write the clauses in this order, or MySQL reports a syntax error:

SELECT city, COUNT(*) AS customers   -- 1. what to show
FROM customers                       -- 2. which table
WHERE city IS NOT NULL               -- 3. which rows
GROUP BY city                        -- 4. how to pile them
HAVING customers > 1                 -- 5. which piles
ORDER BY customers DESC, city        -- 6. in what order
LIMIT 5;                             -- 7. how many

Output

+----------+-----------+
| city     | customers |
+----------+-----------+
| Chicago  |         2 |
| New York |         2 |
+----------+-----------+

A memory aid for the written order: Some Frogs Will Gladly Hop Over Logs. The server, however, runs them in a different order:

graph TD A["1. FROM: pick the table"] --> B["2. WHERE: keep rows"] B --> C["3. GROUP BY: make piles"] C --> D["4. HAVING: keep piles"] D --> E["5. SELECT: compute columns"] E --> F["6. ORDER BY: sort"] F --> G["7. LIMIT: cut"]

The run order explains two rules you will bump into. WHERE cannot use COUNT(*) because the piles do not exist yet when it runs. And ORDER BY can use the alias customers because SELECT has already named it. (Using an alias in HAVING, as above, is a MySQL and MariaDB convenience; strict standard SQL and some other databases make you repeat COUNT(*) there.)

⚠️ Common Mistakes

1. Mixing a plain column with an aggregate, no GROUP BY

SELECT title, COUNT(*) FROM books;

Error

ERROR 1140 (42000): In aggregated query without GROUP BY, expression #1 of SELECT list contains nonaggregated column 'bookstore.books.title'; this is incompatible with sql_mode=only_full_group_by

What it means: COUNT(*) squashes ten rows into one, but title has ten different values. Which one should go in that single row? MySQL refuses to guess. Fix: either aggregate everything (SELECT COUNT(*) FROM books;) or add GROUP BY so that every row of the result is one group.

2. Selecting a column that is not in GROUP BY

SELECT author, title, COUNT(*) AS books
FROM books
GROUP BY author;

Error

ERROR 1055 (42000): Expression #2 of SELECT list is not in GROUP BY clause and contains nonaggregated column 'bookstore.books.title' which is not functionally dependent on columns in GROUP BY clause; this is incompatible with sql_mode=only_full_group_by

What it means: Tolkien's pile holds two titles, so "the title" of that group is ambiguous. This check is the ONLY_FULL_GROUP_BY setting, on by default in MySQL. Fix: every column in SELECT must be inside an aggregate or listed in GROUP BY. Here, drop title, or use MIN(title) if one example title is enough.

MariaDB (the database XAMPP and many shared hosts install) does not turn this check on, so the same query runs there and quietly picks one title per author:

SELECT author, title, COUNT(*) AS books
FROM books
GROUP BY author;

Output on MariaDB (which title it picks for Tolkien could differ)

+---------------------+------------------------+-------+
| author              | title                  | books |
+---------------------+------------------------+-------+
| Aldous Huxley       | Brave New World        |     1 |
| F. Scott Fitzgerald | The Great Gatsby       |     1 |
| Frank Herbert       | Dune                   |     1 |
| George Orwell       | 1984                   |     1 |
| Harper Lee          | To Kill a Mockingbird  |     1 |
| J.D. Salinger       | The Catcher in the Rye |     1 |
| J.R.R. Tolkien      | The Hobbit             |     2 |
| Jane Austen         | Pride and Prejudice    |     1 |
| Ray Bradbury        | Fahrenheit 451         |     1 |
+---------------------+------------------------+-------+

No error, and a result that looks fine, but "The Hobbit" stands for a group of two books. Write your queries so they would pass MySQL's check, and they will give honest answers everywhere.

3. Putting an aggregate in WHERE

SELECT author, COUNT(*) AS books
FROM books
WHERE COUNT(*) > 1
GROUP BY author;

Error

ERROR 1111 (HY000): Invalid use of group function

What it means: WHERE runs before the piles exist, so there is nothing to count yet. Fix: move the condition to HAVING COUNT(*) > 1 after GROUP BY.

4. Writing HAVING before GROUP BY

SELECT city, COUNT(*) AS customers
FROM customers
HAVING customers > 1
GROUP BY city;

Error

ERROR 1064 (42000): You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near 'GROUP BY city' at line 4

What it means: error 1064 is MySQL's general "I could not read this statement". The near 'GROUP BY city' part points at where it got lost: a GROUP BY after HAVING is out of order. Fix: GROUP BY, then HAVING.

5. Trusting the order of GROUP BY results (silent)

SELECT city, COUNT(*) AS customers
FROM customers
WHERE city IS NOT NULL
GROUP BY city;

Output (the row order can differ on your server)

+-------------+-----------+
| city        | customers |
+-------------+-----------+
| New York    |         2 |
| Chicago     |         2 |
| Los Angeles |         1 |
| Houston     |         1 |
+-------------+-----------+

What it means: no error, and the numbers are right, but the rows are neither alphabetical nor sorted by count. On MySQL 9.7 they come out in the order the cities were first seen; MariaDB sorts them by city. Fix: say what you want with ORDER BY.

🛠️ Project: The Inventory Report

The bookstore's owner wants a one-page summary she can rerun every Monday. You will build it as a script file, inventory_report.sql, one query per step, then run the whole file at once. Allow about 30 minutes.

🛠️ Step 1: Create the script with the headline numbers (5 min)

In VS Code (or any text editor), create inventory_report.sql in a folder you can find again, for example mysql-course in your home folder. Start it with USE bookstore; and a first query that answers four questions in one row. Run each new query in the mysql client as you add it, so you can see it work.

USE bookstore;

-- 1. Headline numbers
SELECT
    COUNT(*)             AS titles,
    SUM(in_stock)        AS titles_in_stock,
    SUM(pages)           AS total_pages,
    ROUND(AVG(price), 2) AS avg_price
FROM books;

Output

Database changed
+--------+-----------------+-------------+-----------+
| titles | titles_in_stock | total_pages | avg_price |
+--------+-----------------+-------------+-----------+
|     10 |               8 |        3824 |     10.99 |
+--------+-----------------+-------------+-----------+

SUM(in_stock) is a handy trick: because true is stored as 1 and false as 0, adding them up counts the true rows.

🛠️ Step 2: Stock value by status (5 min)

Add a query that shows, for in-stock and out-of-stock books, how many titles there are and what one copy of each would cost. IF(condition, a, b) turns the 1 and 0 into words.

-- 2. Stock value by status
SELECT
    IF(in_stock, 'In stock', 'Out of stock') AS status,
    COUNT(*)   AS titles,
    SUM(price) AS one_copy_each
FROM books
GROUP BY status
ORDER BY status;

Output

+--------------+--------+---------------+
| status       | titles | one_copy_each |
+--------------+--------+---------------+
| In stock     |      8 |         91.92 |
| Out of stock |      2 |         17.98 |
+--------------+--------+---------------+

🛠️ Step 3: Price bands (5 min)

Reuse the CASE expression from this lesson, and add the cheapest and priciest book in each band.

-- 3. Price bands
SELECT
    CASE
        WHEN price < 10 THEN 'Under $10'

🛠️ Step 4: Authors worth a display table (5 min)

The owner sets up a display table for any author with more than one title, or with more than 400 pages in total. One HAVING can test both:

-- 4. Authors for the display table
SELECT
    author,
    COUNT(*)   AS titles,
    SUM(pages) AS pages
FROM books
GROUP BY author
HAVING COUNT(*) > 1 OR SUM(pages) > 400
ORDER BY pages DESC;

Output

+----------------+--------+-------+
| author         | titles | pages |
+----------------+--------+-------+
| J.R.R. Tolkien |      2 |  1488 |
| Jane Austen    |      1 |   432 |
| Frank Herbert  |      1 |   412 |
+----------------+--------+-------+

🛠️ Step 5: Where the customers are (5 min)

This time keep the customers without a city. COALESCE(city, '(no city)') gives their group a readable label instead of NULL.

-- 5. Customers by city
SELECT
    COALESCE(city, '(no city)') AS city,

GROUP BY COALESCE(city, '(no city)')

Two customers have no city on file. That is worth a follow-up email, and it is exactly the kind of fact a summary should surface.

🏋️ Exercise 1: Quick Facts

In one query, show the number of books published before 1950, their average page count rounded to a whole number, and the earliest publication date among them.

💡 Hint

Filter with WHERE published < '1950-01-01', then use COUNT, ROUND(AVG(...)) and MIN side by side.

✅ Solution 
SELECT
    COUNT(*)          AS books_before_1950,
    ROUND(AVG(pages)) AS avg_pages,
    MIN(published)    AS earliest
FROM books
WHERE published < '1950-01-01';

Output

+-------------------+-----------+------------+
| books_before_1950 | avg_pages | earliest   |
+-------------------+-----------+------------+
|                 5 |       312 | 1813-01-28 |
+-------------------+-----------+------------+

🏋️ Exercise 2: Out-of-Stock Check

For each value of in_stock, show how many books there are and their total page count. Sort so that in-stock books come first.

💡 Hint

Group by in_stock. True is stored as 1, so "in stock first" means descending order.

✅ Solution 
SELECT in_stock, COUNT(*) AS books, SUM(pages) AS pages
FROM books
GROUP BY in_stock
ORDER BY in_stock DESC;

Output

+----------+-------+-------+
| in_stock | books | pages |
+----------+-------+-------+
|        1 |     8 |  3410 |
|        0 |     2 |   414 |
+----------+-------+-------+

🏋️ Exercise 3: Pricey Authors

List the authors whose books average more than $10, with that average rounded to cents, most expensive first. Then change the query so that only in-stock books count. Does the list change? Why?

💡 Hint

The average belongs in HAVING. The in-stock condition is about single rows, so it belongs in WHERE.

✅ Solution 
SELECT author, ROUND(AVG(price), 2) AS avg_price
FROM books
GROUP BY author
HAVING AVG(price) > 10
ORDER BY avg_price DESC;

Output

+----------------+-----------+
| author         | avg_price |
+----------------+-----------+
| Frank Herbert  |     14.99 |
| J.R.R. Tolkien |     13.49 |
| Harper Lee     |     11.99 |
| Ray Bradbury   |     10.49 |
+----------------+-----------+

Adding WHERE in_stock = TRUE gives the same four authors (compare the "Using both together" query above). The two out-of-stock books cost 8.99, so removing them cannot push any author over or under $10. With different data it could: WHERE changes which rows feed each average.

🏋️ Exercise 4 (Stretch): Books by Decade

Count the books published in each decade (1810, 1920, 1930, ...), oldest decade first. Which decade has the most books?

💡 Hint

YEAR(published) gives the year. Dividing by 10, rounding down with FLOOR() and multiplying by 10 turns 1937 into 1930. Group by that expression.

✅ Solution 
SELECT
    FLOOR(YEAR(published) / 10) * 10 AS decade,
    COUNT(*) AS books
FROM books
GROUP BY decade
ORDER BY decade;

Output

❓ Common Questions at This Stage

Is COUNT(1) or COUNT(id) faster than COUNT(*)?

No. MySQL treats COUNT(*) and COUNT(1) exactly the same, and COUNT(id) on a primary key (which can never be NULL) gives the same answer too. Write COUNT(*): it says "count the rows" most clearly.

Can I use a column alias in WHERE?

No. WHERE runs before SELECT has named anything, so WHERE avg_price > 10 fails with error 1054, "Unknown column 'avg_price' in 'where clause'". Aliases work in ORDER BY, and MySQL and MariaDB also accept them in GROUP BY and HAVING.

Should I switch off ONLY_FULL_GROUP_BY to make an old query work?

Please don't. Old tutorials suggest SET sql_mode = '' to silence error 1055, but the query then returns an arbitrary value for the ungrouped column, which is a bug waiting to happen. Fix the query instead: group by the column, aggregate it, or remove it.

Why can't I use SUM() on the title column?

You can type it, but it is meaningless: MySQL tries to read each title as a number, gets 1984 for "1984" and 0 for the rest, and adds warnings. SUM and AVG are for numbers; COUNT, MIN and MAX work on text and dates too.

📝 Lesson Summary

🎓 Key Takeaways

  • Aggregate functions turn many rows into one value: COUNT, SUM, AVG, MIN, MAX
  • COUNT(*) counts rows; COUNT(column) counts non-NULL values; COUNT(DISTINCT column) counts different values
  • Every aggregate skips NULL (except COUNT(*)); over no rows, everything but COUNT returns NULL
  • GROUP BY returns one row per group; add ORDER BY, because grouping does not sort in MySQL 8.0 and later
  • WHERE filters rows before grouping; HAVING filters groups after it
  • Every selected column must be grouped or aggregated (ONLY_FULL_GROUP_BY, error 1055)
  • Written order: SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT
